62.1  Lifecycle Stages — Discovery → Design → Build → Deploy → Monitor → Iterate

📌 Concept Overview

An AI/ML solution moves through six repeating stages. Crucially, this is a loop, not a straight line: signals collected during Monitor feed the Iterate stage, which re-opens Discovery/Design for the next release. Treating the lifecycle as a one-way waterfall is the classic beginner mistake — real systems continuously re-enter earlier stages as data, requirements, and model behavior evolve.

📖 Key Terminology

TermDefinition
DiscoveryGathering stakeholder requirements, defining the business problem, success metrics, and feasibility — before building anything.
DesignChoosing the approach: data sources, model/architecture (e.g., prompt + RAG vs. fine-tune), evaluation strategy, and system integration.
BuildImplementation and validation: data pipelines, prompts/model, and internal testing including user acceptance testing (UAT).
DeployReleasing to production infrastructure with rollout controls (canary, blue-green) and go-live sign-off.
MonitorObserving live performance, quality, cost, and drift; capturing user feedback.
IteratePrioritizing improvements from monitoring signals and looping back into Discovery/Design for the next version.

🔁 Visualization — Iterative Lifecycle

flowchart LR A([1 · Discovery]) --> B([2 · Design]) B --> C([3 · Build]) C --> D([4 · Deploy]) D --> E([5 · Monitor]) E --> F([6 · Iterate]) F -. feedback loop .-> A E -. hotfix / drift .-> C classDef stage fill:#eef2ff,stroke:#4338ca,stroke-width:2px,color:#1a2233; class A,B,C,D,E,F stage;
The lifecycle is cyclical — Iterate re-enters Discovery, and drift/incidents can loop straight back to Build.
🌐 Real-World Example: A support-triage assistant launches (Deploy) and Monitor shows accuracy dropping as new product lines appear in tickets. Instead of scrapping it, the team Iterates: back to Discovery to capture the new categories, Design updated retrieval, Build, and re-deploy — one full turn of the loop.
💡 Tips & Tricks
  • Mnemonic: "Discover Design Build, then Deploy Monitor & Iterate" → DDB-DMI.
  • Requirements = Discovery; architecture choices = Design. Don't confuse them.
  • UAT lives at the Build→Deploy boundary, not in Discovery.
🎯 Exam Strategy: Questions present a scenario and ask which stage it describes. Watch keywords: "stakeholder requirements / success metrics" → Discovery; "selecting RAG vs fine-tune" → Design; "UAT / integration testing" → Build; "canary rollout" → Deploy; "drift alert / feedback" → Monitor. If an option says the lifecycle is "linear/one-time," it's a distractor.

62.2  Prototyping vs. Proof of Concept (POC)

📌 Concept Overview

Both de-risk a project early, but they answer different questions. A POC asks "Is this technically possible at all?" — it validates the single riskiest technical assumption on a narrow slice. A Prototype asks "What should this feel like and how should it work?" — it explores UX, workflow, and stakeholder fit, often with more breadth but less technical rigor. Choosing the wrong one wastes time: a polished prototype proves nothing if the core model approach can't work.

📖 Key Terminology

TermDefinition
POCProof of Concept — a minimal experiment validating that a specific technical approach is feasible. Narrow, throwaway, feasibility-focused.
PrototypeAn interactive mock/early build exploring user experience, workflow, and requirements. Broader, may evolve toward the product.
Pilot / MVPA limited but production-grade release to real users — the step after POC/prototype, not a substitute.
Risk mitigationDeliberately testing the highest-uncertainty assumption first to fail cheaply.

Pick the artifact that attacks the biggest unknown first.

✅ Risk-Mitigation Checklist

Riskiest assumption named
The one thing that, if false, kills the project.
Time-boxed
Fixed budget (e.g., 1–2 weeks) so failure is cheap.
Clear success criteria
A measurable go/no-go threshold set beforehand.
Representative data
Real (or realistic) samples, not cherry-picked demos.
Disposable by design
No pressure to ship POC code to production.
🌐 Real-World Example: Before committing to an AI contract-review tool, the team runs a POC: can Claude extract clause obligations from 50 real contracts at ≥90% precision? That's the make-or-break unknown. Separately, a clickable prototype tests whether reviewers prefer inline highlights or a side panel — a UX question that only matters if the POC succeeds.
💡 Tips & Tricks
  • POC = "Proof of Can-it". Prototype = "Proto-type of the experience."
  • A POC that looks ugly but works is a success; a prototype that looks great but hides an infeasible core is a trap.
  • Always set the go/no-go metric before starting to avoid moving goalposts.
🎯 Exam Strategy: Watch for "validate technical feasibility / riskiest assumption" → POC; "gather user feedback / explore workflow / UX" → Prototype. Distractors swap these. Answers implying a prototype/POC should be hardened directly into production ignore the "throwaway" principle and are usually wrong.

62.3  Definition of "Done" — Production Readiness

📌 Concept Overview

"Working in a demo" is not "done." A solution is production-ready only when it meets agreed SLAs, has complete documentation, ships with operational safeguards (monitoring, rollback, security review), and includes the handoff artifacts the operating team needs to run it. A shared, explicit Definition of Done (DoD) prevents "90% done forever" and unsafe launches.

📖 Key Terminology

TermDefinition
SLAService-Level Agreement — the committed target (e.g., 99.9% uptime, p95 latency < 2 s) the solution must meet.
SLO / SLIObjective (internal target) and Indicator (the measured metric) that underpin an SLA.
Handoff artifactsRunbooks, architecture docs, eval reports, on-call/escalation contacts — what ops needs to own the system.
RunbookStep-by-step guide for operating and recovering the system during incidents.
DoDDefinition of Done — the agreed, checkable criteria that mark a deliverable complete.

All six gates must be green before "Done." One red gate blocks go-live.
🌐 Real-World Example: An AI email-summarizer "works," but the team blocks launch because there's no rollback path and no p95 latency SLO. They add a canary + rollback, define "p95 < 3 s, groundedness ≥ 95%," write a runbook, and pass a PII review. Now it's Done.
💡 Tips & Tricks
  • Memory aid: "Q-O-G" — Quality, Operations, Governance gates.
  • DoD must be agreed before Build, not negotiated at launch.
  • Documentation & a tested rollback are part of "Done" — not optional extras.
🎯 Exam Strategy: If a scenario says a model "hits target accuracy" but lacks monitoring, rollback, or docs, the correct answer is "not production-ready." Keywords: SLA, runbook, handoff, security review. Beware options that equate "passing offline eval" with "done."

62.4  Monitoring, Feedback Loops & Drift Detection

📌 Concept Overview

Once live, you monitor three layers: operational health (latency, error rate, cost/throughput), output quality (accuracy, precision/recall, or for LLMs groundedness, hallucination rate, refusal rate), and drift (the world changing under the model). Feedback loops — explicit thumbs-up/down and implicit signals like edits or abandonment — feed the Iterate stage and can be used to build evaluation sets.

📖 Key Terminology

TermDefinition
Data driftThe distribution of inputs shifts from what the model saw in development (e.g., new slang, new topics).
Concept driftThe relationship between inputs and correct outputs changes (the "right answer" itself moves).
Feedback loopCapturing user/system signals and routing them back to improve the model or prompts.
Ground truth lagDelay before you learn the true outcome, complicating live quality measurement.
Guardrail metricA safety/quality threshold that triggers an alert when breached.

data & concept] DR -->|threshold breach| AL[[Alert]] O --> FB[User feedback

Monitoring detects drift and feeds alerts + feedback data into the Iterate stage.
🌐 Real-World Example: A demand-forecasting model degrades after a market shift — same inputs now map to different outcomes (concept drift). A dashboard tracking rolling prediction error crosses its guardrail, fires an alert, and the flagged cases become a fresh eval set for retraining.
💡 Tips & Tricks
  • Data drift = inputs change; Concept drift = the answer changes. If unsure, ask "did the questions change, or did the correct answers change?"
  • Always monitor cost for LLM apps — token spend is an ops metric.
  • Implicit feedback (user edits/abandonment) is often richer than sparse thumbs-up/down.
🎯 Exam Strategy: Distinguishing data vs. concept drift is a favorite question. "Input distribution shifted" → data drift. "Label/target relationship changed" → concept drift. Keywords: "performance degraded over time," "distribution shift," "feedback loop." A response that says "no monitoring needed after a good launch" is always wrong.

62.5  Versioning, Migration Playbook & Rollback

📌 Concept Overview

Every deployable asset — model, prompt, dataset, config — should be versioned so you can reproduce, compare, and revert. Migrating to a new version uses progressive rollout strategies (shadow → canary → blue-green) that limit blast radius, and every migration must have a tested rollback so a bad release can be reverted in minutes, not hours.

📖 Key Terminology

TermDefinition
Model registryCentral catalog of versioned models with lineage, metrics, and stage (staging/prod/archived).
Semantic versioningMAJOR.MINOR.PATCH — signals breaking vs. compatible changes.
Shadow deployNew version runs on live traffic in parallel, results logged but not served — zero user risk.
CanaryRoute a small % of traffic to the new version; expand only if metrics hold.
Blue-greenTwo identical environments; switch traffic all-at-once and revert instantly by switching back.
RollbackReverting to the last known-good version when a release regresses.

🚦 Visualization — Migration & Rollback Playbook

5% → 25% → 50%] CN --> OK{Metrics OK?} OK -->|Yes| BG[Blue-Green switch
100% to v2] OK -->|No| RB[[Rollback to v1]] BG --> DONE([v2 promoted]) RB --> V1 classDef n fill:#eef2ff,stroke:#4338ca,color:#1a2233; classDef ok fill:#ecfdf3,stroke:#15803d,color:#1a2233; classDef bad fill:#fef2f2,stroke:#b91c1c,color:#1a2233; class V1,SH,CN,BG n; class DONE ok; class RB bad;
Progressive exposure limits blast radius; a tested rollback is the safety net at every step.
🌐 Real-World Example: Upgrading a chatbot from prompt v2.3.0 to v3.0.0 (a MAJOR, breaking change), the team shadow-tests for a day, then canaries 5%. Groundedness dips, so they auto-rollback to v2.3.0 — users never notice — then fix and retry. The registry keeps both versions reproducible.
💡 Tips & Tricks
  • Shadow = no risk, Canary = small risk, Blue-green = instant switch/revert.
  • Bump MAJOR for breaking changes, MINOR for compatible features, PATCH for fixes.
  • An untested rollback is not a rollback plan — rehearse it.
🎯 Exam Strategy: Match the strategy to intent: "test on real traffic with no user impact" → shadow; "gradually expose a small %" → canary; "instant cut-over / instant revert" → blue-green. Keywords: registry, lineage, canary, rollback. If a scenario deploys a breaking change to 100% at once with no rollback, that's the wrong practice.

★  Practice Question Bank 8 Questions

Q1A team gathers stakeholder requirements and defines success metrics before any building. Which lifecycle stage is this?
Show answer & explanation
Answer: Discovery. Requirements gathering and success-metric definition occur in Discovery — before architecture (Design) or implementation (Build). "Success metrics / stakeholder requirements" are Discovery keywords.
Q2You must validate whether Claude can extract legal clauses at ≥90% precision before committing. Prototype or POC?
Show answer & explanation
Answer: POC. The unknown is technical feasibility of the core approach — the classic POC trigger. A prototype would explore UX, which is premature until feasibility is proven.
Q3A model passes offline evaluation at target accuracy but has no monitoring, rollback, or runbook. Is it production-ready?
Show answer & explanation
Answer: No. The Definition of Done requires Operations (monitoring, tested rollback) and Governance (docs/runbook, security review) gates — not just Quality. Passing eval alone is insufficient.
Q4A live model's accuracy drops because the relationship between inputs and correct outputs has changed. What is this called?
Show answer & explanation
Answer: Concept drift. When the input→correct-output mapping changes, it's concept drift. If only the input distribution shifted (same correct answers), that would be data drift.
Q5You want to test a new model version on real production traffic with zero user impact. Which deployment strategy?
Show answer & explanation
Answer: Shadow deployment. The new version processes live traffic in parallel; outputs are logged but not served, so users are unaffected. Canary exposes a small % of real users; blue-green cuts over fully.
Q6A prompt change fixes wording but adds no new capability and breaks nothing. Under semantic versioning, which number bumps?
Show answer & explanation
Answer: PATCH. MAJOR.MINOR.PATCH: PATCH for backward-compatible fixes, MINOR for compatible new features, MAJOR for breaking changes.
Q7After launch, users frequently edit the AI's output before accepting it. How should this be used?
Show answer & explanation
Answer: As implicit feedback feeding the Iterate stage. Edits are rich implicit signals; captured as feedback they become evaluation/retraining data that drives the next iteration — closing the monitoring→iterate loop.
Q8A canary release shows quality metrics below the guardrail threshold. What is the correct immediate action?
Show answer & explanation
Answer: Roll back to the last known-good version. A breached guardrail during canary means the new version regressed; revert immediately (limiting blast radius), then diagnose and retry. Never expand a failing canary to 100%.

★  Common Exam Traps

⚠️ Frequently Confused Concepts
  • Linear vs. iterative lifecycle: Any answer treating the lifecycle as one-way/waterfall is a distractor — it's a loop.
  • POC vs. Prototype: POC = technical feasibility; Prototype = UX/workflow. Exam options deliberately swap these.
  • "Passes eval" vs. "Done": Offline accuracy alone is not production-ready — monitoring, rollback, docs, and security review are required.
  • Data drift vs. Concept drift: Inputs changing (data) vs. the correct answer changing (concept). Read the stem carefully.
  • Discovery vs. Design: Requirements & metrics = Discovery; choosing RAG/fine-tune/architecture = Design.
  • Shadow vs. Canary: Shadow serves nothing to users (zero risk); canary serves a small real % (small risk).
  • Rollback that was never tested: Having a plan on paper ≠ a working rollback. The exam rewards tested rollbacks.
  • UAT placement: User acceptance testing sits at the Build→Deploy boundary, not in Discovery.
