61.1 Documenting AI Architectures: What to Include and Why

Architecture documentation is the single source of truth for how an AI system is designed, why those design choices were made, and how it behaves under normal and failure conditions. For LLM systems built on Claude, good docs must go beyond boxes-and-arrows: they capture model choices, prompt/context strategy, guardrails, data flow, and rollback plans so the system can be audited, scaled, and safely operated.

🧩 Key Components & Why Each Matters

ComponentWhat it capturesWhy it matters (audit / scale / compliance)
System Context Diagram (C4 Level 1)The AI system as one box, plus users, upstream/downstream systems, and external APIs (e.g. the Anthropic Messages API).Sets scope and trust boundaries; auditors immediately see what data crosses which boundary.
Data Flow Diagram (DFD)How a request travels: input → preprocessing → retrieval → model call → post-processing → output, plus where data is stored/logged.Core to privacy & compliance — shows where PII lives, what is sent to the model provider, and what is retained.
Model Choices & RationaleWhich Claude model per task (e.g. a smaller/faster model for routing, a larger model for reasoning), context-window sizing, temperature, and fallback models.Justifies cost/latency/quality trade-offs; supports scaling decisions and model-upgrade planning.
Prompt & Context StrategySystem-prompt design, tool-use definitions, retrieval (RAG) sources, and context-management approach (e.g. prompt caching, truncation).Prompts are part of the architecture — reproducibility and change control depend on documenting them.
Guardrails & Safety ControlsInput validation, output filtering/moderation, allow/deny policies, human-in-the-loop checkpoints, and refusal handling.Most-audited section; demonstrates responsible-AI controls and how misuse is prevented.
Non-Functional Requirements (NFRs)Latency/throughput targets, availability SLOs, cost budgets, token limits, and quality/eval thresholds.Defines "done"; scaling and capacity planning are impossible without them.
Failure Modes & Rollback PlanWhat happens on timeout, rate limit, degraded quality, or a bad prompt/model release; how to revert.Frequently the missing section — critical for operational safety and change management.
Assumptions, Risks & Decisions (ADR log)Why alternatives were rejected, open risks, and dated decision records.Preserves intent so future engineers don't re-litigate settled choices.

💡 Tips & Tricks
  • Mnemonic for the core sections: C-DIME-GR → Context, Data flow, Implementation notes, Model choices, Evaluation/NFRs, Guardrails, Rollback.
  • The two sections candidates forget — and exams love to test — are Guardrails and Rollback. If a doc is described as "complete" but has neither, that's usually the trap.
  • Use the C4 model (Context → Container → Component → Code) to scale diagram detail to the audience. Executives read Level 1; engineers read Levels 3–4.
  • Always record the "why," not just the "what." An ADR (Architecture Decision Record) answers audit questions before they're asked.
🎯 Exam Strategy

Questions here typically present a scenario ("A team wrote a doc containing X, Y, Z…") and ask "what's missing?" or "what should be added before an audit?"

  • Keyword "audit / compliance / regulator" → the answer usually involves data flow, guardrails, or PII handling.
  • Keyword "scale / grow / more traffic" → answer involves NFRs, model choice, cost/latency trade-offs.
  • Keyword "safely change / new model version" → answer involves rollback plan & versioning.
  • Distractor watch: options that add more diagrams when the real gap is a guardrail/rollback section.

61.2 Implementation Guides for Development Teams

An implementation guide translates the architecture into concrete, reproducible engineering steps. Its reader is a developer who needs to build or extend the system — so it is prescriptive, example-heavy, and testable. Where architecture docs answer "what and why," the implementation guide answers "how do I build it correctly."

🧱 Structure of a Dev-Facing Implementation Guide

SectionContents
PrerequisitesSDK versions, API keys/secrets management, environment setup, required permissions.
Setup & ConfigurationEnvironment variables, model IDs, timeouts, retry policy, rate-limit handling.
Core Integration PatternsHow to call the Messages API, system-prompt conventions, tool-use (function calling), streaming, and RAG wiring.
Code & Config ExamplesCopy-pasteable, minimal-but-complete snippets in the team's language.
Error HandlingHandling 429 rate limits (exponential backoff), timeouts, malformed tool calls, and refusals.
Testing ChecklistUnit, integration, prompt/eval, and regression tests before merge.
Security & Cost NotesSecret handling, PII redaction, token budgeting, prompt caching to cut cost.

⌨️ Example: Configuration & a Guarded API Call

# config (env-driven — never hardcode keys)
ANTHROPIC_API_KEY=${SECRET_FROM_VAULT}
CLAUDE_MODEL=claude-sonnet-4-5
MAX_TOKENS=1024
REQUEST_TIMEOUT_S=30
MAX_RETRIES=3

# pseudo-code: retry with backoff + guardrail
def generate(user_input):
    validate_input(user_input)            # input guardrail
    for attempt in range(MAX_RETRIES):
        try:
            resp = client.messages.create(
                model=CLAUDE_MODEL,
                max_tokens=MAX_TOKENS,
                system=SYSTEM_PROMPT,     # versioned, source-controlled
                messages=[{"role":"user","content":user_input}],
            )
            return filter_output(resp)      # output guardrail
        except RateLimitError:            # HTTP 429
            backoff(2 ** attempt)

✅ Pre-Merge Testing Checklist

Test typeVerifies
UnitInput validation, parsing, output filtering logic in isolation.
IntegrationLive/mocked API call succeeds, retries fire, timeouts respected.
Prompt / EvalOutputs meet quality thresholds on a fixed eval set (accuracy, format, safety).
RegressionNew prompt/model version does not degrade prior passing cases.
SecurityNo secrets in logs, PII redacted, injection attempts refused.
⚠️ Accuracy note

Model IDs and exact parameters evolve — an implementation guide should reference model names and API parameters from the current official Anthropic documentation rather than hardcoding assumptions. Treat prompts and model IDs as versioned config, not code constants.

💡 Tips & Tricks
  • Mnemonic for guide sections: PSCET-S → Prerequisites, Setup, Core patterns, Examples, Testing, Security/cost.
  • Every code example should be minimal but runnable — enough to copy, paste, and get a green result.
  • Treat the system prompt as source-controlled config: version it, review it, and reference the version in the guide.
  • Always show the 429 / rate-limit backoff pattern — it's the most common real-world integration bug.
🎯 Exam Strategy

Questions distinguish who the document is for. If the reader is a developer building the system, the answer is the implementation guide (not the runbook or architecture doc).

  • Keyword "onboard a new engineer to build/extend" → implementation guide.
  • Keyword "reproducible / step-by-step / code example" → implementation guide.
  • Trap: choosing the runbook when the scenario is about building, not operating. Runbooks are for production incidents (see 61.3).
  • If asked what to add before merge, look for a testing/eval checklist — commonly the omitted answer.

61.3 Runbooks for Operational Teams

A runbook is an operational playbook for the team that keeps the system running in production. It is action-oriented and read under pressure: during an incident, on-call engineers should be able to follow it step-by-step without needing to understand the full design. Runbooks answer "it's broken / behaving oddly — what do I do right now?"

🆚 Runbook vs. Implementation Guide

Implementation Guide (61.2)

  • Audience: developers building the system
  • When used: during development / onboarding
  • Goal: build it correctly & reproducibly
  • Tone: explanatory, example-rich
  • Content: setup, code, integration patterns, tests

Runbook (61.3)

  • Audience: operators / on-call / SRE
  • When used: in production, often during incidents
  • Goal: detect, diagnose, restore, escalate
  • Tone: terse, imperative, checklist-driven
  • Content: alerts, procedures, escalation, rollback

🚨 Incident-Response Flow

📈 Monitoring & Alerting for LLM Systems

SignalWhy monitor it
Latency (p50/p95/p99)LLM calls are slow & variable; tail latency breaks SLOs.
Error / rate-limit (4xx/5xx, 429)Provider throttling and outages are top incident causes.
Token usage & costRunaway prompts/loops can spike spend fast.
Output quality / eval driftA model or prompt change can silently degrade answers.
Guardrail / refusal rateSpikes can indicate abuse, prompt injection, or a broken prompt.

Escalation Path (example)

  1. L1 On-call — follow runbook, attempt standard mitigation (rollback, failover, disable feature flag).
  2. L2 Service owner — engaged if not mitigated within the SEV time budget.
  3. L3 Architecture / vendor — deeper design issue or provider-side incident; open a support case.
  4. Incident commander + comms — for high-severity, customer-impacting events.
💡 Tips & Tricks
  • Incident-response mnemonic: D-T-D-M-E-R → Detect, Triage, Diagnose, Mitigate, Escalate, Resolve (+ post-mortem).
  • A good runbook step is copy-pasteable and unambiguous — exact command, exact dashboard link, exact threshold. No prose essays.
  • Mitigate before you fully diagnose: restore service (rollback/failover) first, root-cause later.
  • Every alert should link to the specific runbook entry that resolves it — an alert with no runbook is a design gap.
🎯 Exam Strategy

The classic question contrasts runbook vs. implementation guide vs. architecture doc. Anchor on the audience + moment of use.

  • Keyword "on-call / production incident / 3 a.m. / restore service" → runbook.
  • Keyword "alert / escalation / monitoring / SLO" → runbook territory.
  • Keyword "build / integrate / code example" → implementation guide (61.2), not runbook.
  • Trap: an answer that says "add more architecture diagrams" to fix an operational gap — the fix is usually a runbook step, alert, or escalation path.

61.4 Knowledge Transfer and Handoff Strategies

Knowledge transfer (KT) moves understanding — not just files — from the people who built the system to those who will own, operate, or extend it. A handoff fails not when documents are missing, but when context, rationale, and tacit knowledge don't survive the transition. Effective KT combines artifacts (docs from 61.1–61.3) with interaction (walkthroughs, shadowing, Q&A).

📋 Handoff Checklist

CategoryMust be handed over
DocumentationArchitecture doc, implementation guide, runbooks, ADR log — all current and versioned.
Access & credentialsRepos, secrets/vault, dashboards, cloud consoles, provider (API) accounts — transferred, not shared personally.
Operational knowledgeKnown issues, recurring incidents, "here be dragons" areas, on-call expectations.
Decisions & rationaleWhy key choices were made; rejected alternatives; open risks.
Contacts & ownershipUpstream/downstream owners, vendor support, escalation contacts, RACI.
Live walkthroughAt least one guided demo + a Q&A/shadowing period before sign-off.

🗣️ Stakeholder Communication Plan (RACI-style)

StakeholderInterestWhat they receive
Receiving engineersHow to run & extend itFull docs + walkthroughs + shadowing
Operations / SREKeeping it healthyRunbooks, alerts, escalation paths
Product / BusinessCapabilities & risksSummary of what it does, limits, roadmap
Security / ComplianceControls & data handlingGuardrails, data-flow, audit evidence
LeadershipContinuity & ownershipOwnership transfer confirmation, sign-off

🕳️ Common KT Pitfalls & How to Avoid Them

PitfallFix
"Docs = KT" — dumping files without interactionPair docs with live walkthroughs, shadowing, and a Q&A window.
Bus-factor of one — one expert holds all contextTransfer to a team, not a person; record sessions; write down tacit knowledge.
Big-bang handoff on the last dayUse a phased overlap period; shadow → reverse-shadow → own.
Stale documentationRefresh docs immediately before handoff; verify against the running system.
No acceptance criteriaDefine "handoff complete" (checklist signed, receiver runs it solo, incident simulated).
💡 Tips & Tricks
  • Handoff readiness mnemonic: D-A-R-C → Documentation, Access, Rationale, Contacts. (Add a live walkthrough on top.)
  • Phased overlap beats a single meeting: Shadow → Reverse-shadow → Solo. The receiver proves readiness by operating it while the expert watches.
  • Handoff isn't done when docs are delivered — it's done when the receiver can operate the system without the original owner.
  • Record walkthroughs; the recording captures tacit knowledge no document will.
🎯 Exam Strategy

KT questions often describe a failed or risky handoff and ask what went wrong or what to add.

  • Keyword "only one person knows / left the company" → bus-factor; answer = transfer to a team + document tacit knowledge.
  • Keyword "handed over docs but team still can't operate it" → missing walkthrough / shadowing, not more docs.
  • Keyword "how do we know handoff is complete?" → acceptance criteria (receiver operates solo / simulated incident).
  • Trap: assuming "write more documentation" is always the fix — for KT gaps the fix is usually interaction and ownership transfer.

📄 Architecture Doc Template (fill in)

# [System Name] — Architecture Document  (v1.0, owner, date)

1. Overview & Purpose      — what it does, who uses it, success metrics
2. System Context          — C4 L1 diagram; external systems & APIs
3. Data Flow               — request path; where PII lives; retention/logging

5. Guardrails & Safety      — input validation, output filtering, HITL, refusals
6. NFRs                     — latency/SLO, throughput, cost budget, quality thresholds

8. Decisions (ADRs)          — key choices, rejected alternatives, dated
9. Open Risks & Assumptions
10. Glossary & References

💼 Worked Example — "SupportBot" (Claude-based support assistant)

Doc sectionFilled-in example
OverviewAnswers customer questions from a help-center knowledge base; deflects tickets. Success = deflection rate & CSAT.
System ContextUser → Web app → SupportBot service → (Retrieval over KB index) + (Anthropic Messages API) → response; tickets logged to CRM.
Data FlowQuestion → PII redaction → retrieve top-k KB chunks → build prompt → Claude call → output filter → answer. Transcripts stored 30 days.
Model & PromptSmaller/faster Claude model for intent routing; larger model for answer generation. Versioned system prompt; RAG grounding; prompt caching for the static KB preamble.
GuardrailsBlock prompt-injection patterns; refuse out-of-scope/PII requests; escalate low-confidence answers to a human.
NFRsp95 < 4s; 99.9% availability; cost ≤ $X / 1k conversations; answer-eval score ≥ threshold.
Failure & RollbackOn 429 → backoff + queue; on quality regression → revert to previous prompt/model version via feature flag; degraded mode = "connect to a human."
📝 Practice Exercise

Take a system you know and produce a one-page version of the template above. Deliberately draft Section 5 (Guardrails) and Section 7 (Rollback) first — these are the sections most often missing and most often tested. Then have a peer play "auditor" and ask "what's missing?"

💡 Tips & Tricks
  • Workflow mnemonic: S-D-D-S-R-P → Scope, Diagram, Decide, Specify, Review, Publish.
  • Write to the audience: one document can carry layered detail (C4 levels) so execs and engineers each find their level.
  • Draft the hard/omitted sections first (guardrails, rollback) while energy is high — don't leave them as afterthoughts.
  • A doc isn't finished at "Publish" — the Maintain step (61.1 lifecycle) keeps it a source of truth.
🎯 Exam Strategy

Hands-on / scenario questions ask you to sequence steps or pick the next action in building a doc.

  • Keyword "first step / before writing" → define scope, purpose, audience (not jump to diagrams or code).
  • Keyword "who is this for?" → drives diagram depth (C4 level) and language.
  • Keyword "what's still missing before publish?" → check for guardrails, rollback, NFRs, ADRs.
  • Trap: options that start with implementation code before scope/context are defined — sequence matters.

🗺️ Chapter Map: How the Subsections Depend on Each Other

The five subsections aren't independent — they form a chain from design to build to operate to hand off, all validated by the hands-on practice. Understanding these dependencies is itself commonly tested.

Read it as: 61.1 defines the design → 61.2 turns it into buildable steps → 61.3 keeps the built system alive → 61.4 transfers all of it to new owners. 61.5 is the practical skill that produces these artifacts, and guardrails + rollback recur across all of them as the most-tested, most-omitted content.

📋 Chapter Summary & Quick Revision Checklist

  • 61.1 — Architecture docs: capture Context, Data flow, Model choices, Prompt strategy, Guardrails, NFRs, and Rollback. Mnemonic C-DIME-GR. Document the why (ADRs) for audits. Lifecycle = Draft → Review → Publish → Maintain.
  • 61.2 — Implementation guides are for developers building the system: prerequisites, setup, integration patterns, runnable examples, and a testing/eval checklist. Mnemonic PSCET-S. Prompts & model IDs are versioned config; always show 429 backoff.
  • 61.3 — Runbooks are for operators in production: alerts, monitoring signals, incident flow D-T-D-M-E-R, escalation paths, and rollback. Mitigate first, diagnose later. Every alert links to a runbook step.
  • 61.4 — Knowledge transfer = artifacts + interaction. Readiness mnemonic D-A-R-C (Docs, Access, Rationale, Contacts) + live walkthrough. Beat bus-factor; use Shadow → Reverse-shadow → Solo; define "done" with acceptance criteria.
  • 61.5 — Hands-on: workflow S-D-D-S-R-P (Scope, Diagram, Decide, Specify, Review, Publish). Use the 10-section template; draft Guardrails & Rollback first — most omitted, most tested.
  • Cross-cutting exam anchors: match the doc to its audience (build → impl guide; operate → runbook; design → architecture doc; own → handoff). "What's missing?" answers are usually guardrails, rollback, NFRs, or interaction, rarely "more diagrams."
