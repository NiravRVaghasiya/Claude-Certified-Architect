Evaluating Tool/Agent Configuration for Capability Bloat

Concept Overview

Capability bloat is the accumulation of tools, functions, scopes, and permissions that an agent can invoke but does not actually need for its intended workflows. In production AI systems, every registered tool expands the agent's blast radius — the range of damage possible if the model is manipulated (prompt injection), misconfigured, or simply hallucinates a tool call. Bloat also degrades reliability: larger tool schemas crowd the context window, increase token cost, and raise the odds of the model selecting the wrong tool.

Evaluating for bloat means periodically answering one question for every capability: "Is this tool exercised by at least one active, justified workflow — and is its scope no broader than that workflow requires?" If not, it is bloat and should be removed or narrowed.

Key Definitions

Capability bloat
Tools/permissions granted beyond what active workflows require.
Blast radius
The total harm an agent can cause if compromised or misused; grows with each capability.
Attack surface
The sum of all entry points (tools, endpoints, scopes) an attacker could exploit.
Tool sprawl
Uncontrolled growth of registered tools across many agents without governance.
Utilization rate
How often a granted tool is actually invoked in production. Near-zero utilization signals bloat.
Confused-deputy risk
A privileged agent being tricked into misusing its authority on an attacker's behalf — worsened by excess capability.

✕Common Pitfalls / Anti-Patterns
  • "Grant now, prune later." Later never comes; bloat calcifies.
  • Bundling tools by convenience (e.g., one "admin" tool exposing dozens of actions) instead of by task.
  • Copying a toolset from another agent without re-justifying each tool for the new use case.
  • Confusing "might need it" with "needs it." Speculative capability is still blast radius.
✦Tips & Tricks — Mnemonics
  • JUST — every tool must be Justified, Used, Scoped, and Tracked.
  • Rule of thumb: "If you can't name the workflow, you can't keep the tool."
  • Bloat ≈ unused capability. Frame it as attack surface you're paying to store.
Q1. An agent that only summarizes support tickets is configured with read_tickets, post_reply, and delete_ticket. The workflow never deletes tickets. What best describes the issue and fix?
  1. Authentication gap — add a service token for delete_ticket.
  2. Capability bloat — remove delete_ticket (and re-check post_reply if replies aren't needed).
  3. No issue — deletion may be useful later.
  4. Authorization gap — grant admin scope to cover all actions.
Correct: B. An unused destructive tool is classic capability bloat that inflates blast radius. Remove it; also question post_reply against the stated "summarize only" workflow. "Might be useful later" (C) is the trap answer.
◎Exam Strategy — 44.1
  • Framing: "Identify the flaw" and scenario configs listing several tools where one clearly doesn't fit the stated task.
  • Trigger keywords: "only requires…", "just in case", "unused", "delete/drop/admin present in a read-only task", "might need later".
  • Elimination: Reject options that add capability or defer removal. The security-correct answer almost always removes or narrows. Match the tool list against the one-sentence use case and flag the outlier.

Least-Privilege Principles for Agent Tool Access

Concept Overview

The Principle of Least Privilege (PoLP) states that any actor — human, service, or agent — should hold only the minimum permissions required to perform its function, for the minimum time, over the minimum scope. For agents, "privilege" means the set of tools and the granularity of each tool's action (read vs. write vs. delete) and data scope (one folder vs. whole filesystem; one project vs. whole org). Least privilege is the single most effective control for shrinking blast radius, because it caps damage even when other controls (like prompt-injection defenses) fail.

Key Definitions

Least privilege (PoLP)
Minimum permissions, minimum scope, minimum duration.
Scope
The boundary a permission applies to (resource, path, project, action verb).
Just-in-time (JIT) access
Privileges granted only for the moment they're needed, then revoked.
Separation of duties
Splitting sensitive workflows so no single agent/tool can complete a high-risk action alone.
Privilege escalation
Gaining access beyond what was granted, often by chaining over-broad tools.
Human-in-the-loop (HITL)
Requiring human approval before an agent executes a high-impact action.

Core Framework — Least-Privilege Design Ladder

  1. Deny by default — start with no tools; add only what a named workflow needs.
  2. Narrow the verb — prefer read over write, write over delete.
  3. Narrow the scope — one directory/table/project, not *.
  4. Time-box — short-lived, rotating credentials; JIT elevation for rare high-risk actions.
  5. Gate the dangerous — put destructive/irreversible actions behind human approval.
  6. Separate duties — no single agent both approves and executes.

✕Common Pitfalls / Anti-Patterns
  • Wildcard scopes (resource:*, s3:*) because "it's easier."
  • Shared god-credential reused across many agents — one leak compromises everything.
  • Standing privilege for rare actions instead of JIT elevation.
  • No HITL gate on irreversible actions (mass delete, payments, prod deploys).
  • Role reuse — attaching an existing broad human/service role to an agent.
✦Tips & Tricks — Heuristics
  • R-W-D ladder: default to Read; earn Write; strongly justify Delete.
  • Mnemonic "MST": Minimum Scope, minimum Time (and minimum tools).
  • Ask "What's the worst a leaked token for this tool could do?" — the answer is the blast radius.
  • Prefer many narrow tools over one broad tool: easier to reason about, revoke, and audit.
Q2. An agent needs to append rows to one analytics table. Which grant best reflects least privilege?
  1. db_owner on the database (so future needs are covered).
  2. INSERT on the single analytics table, via a short-lived scoped credential.
  3. SELECT, INSERT, UPDATE, DELETE on all tables.
  4. Read/write on the whole schema with a permanent token.
Correct: B. Narrow verb (INSERT only), narrow scope (one table), short-lived credential. A, C, D all over-grant scope, verbs, or duration.
◎Exam Strategy — 44.2
  • Framing: "Which configuration best follows least privilege?" — pick the narrowest option that still completes the task.
  • Trigger keywords: "minimum necessary", "scope", "wildcard", "admin/owner", "permanent vs. temporary token", "read-only".
  • Elimination: Discard any answer containing *, owner/admin, "all tables/resources", or "permanent/never expires". Beware distractors justified by future needs — least privilege is about now.

Authentication and Authorization Requirements

Concept Overview

Two distinct controls govern every tool call. Authentication (AuthN) answers "Who are you?" — it verifies the identity of the caller (the agent, the service, and often the end-user on whose behalf it acts). Authorization (AuthZ) answers "What are you allowed to do?" — it checks whether that verified identity may perform the requested action on the requested resource. AuthN always precedes AuthZ. In production agents, both must be enforced server-side at the tool/API, never merely by the model's own reasoning — because a compromised or injected prompt can make the model ask for anything.

!Do not confuse them. AuthN = identity (login, token issuance, MFA). AuthZ = permission (scopes, roles, policies). A valid token proves who you are; it does not automatically prove what you may do. Both checks are required on every request.

Key Definitions

Authentication (AuthN)
Verifying identity of the caller/agent/user.
Authorization (AuthZ)
Deciding whether the authenticated identity may perform an action.
OAuth 2.0
A delegated authorization framework: issues scoped access tokens so an app acts on a user's behalf without their password.
OIDC
OpenID Connect — an identity layer on top of OAuth 2.0 (adds the id_token for AuthN).
Scope
A permission string bound to a token (e.g., tickets:read) limiting what it authorizes.
Access vs. refresh token
Short-lived credential for calls vs. long-lived credential to mint new access tokens.
RBAC / ABAC
Role-Based vs. Attribute-Based Access Control — two AuthZ models.
mTLS
Mutual TLS — both client and server present certificates (strong service-to-service AuthN).
Token expiry & rotation
Limiting a token's lifetime and periodically replacing secrets.

✕Common Pitfalls / Anti-Patterns
  • Treating AuthN as AuthZ — accepting any valid token without a scope/role check.
  • Non-expiring tokens or missing rotation — a leaked secret is valid forever.
  • Hard-coded secrets in prompts, code, or the tool schema (use a secrets manager).
  • Client-side / model-side enforcement — relying on the LLM to "not call" a tool instead of the API refusing.
  • Over-scoped tokens (scope=*) and confused-deputy: agent uses its broad rights on an attacker's request.
  • Not verifying JWT signature/audience — accepting forged or replayed tokens.
✦Tips & Tricks
  • "N before Z": AutheNtication always comes before AuthoriZation.
  • 401 vs. 403: 401 = not logged in (identity problem); 403 = logged in, not allowed (permission problem).
  • OAuth is about authorization/delegation; OIDC adds identity. If a stem says "verify who the user is," think OIDC.
  • Every token needs an expiry and a rotation plan — no exceptions for "internal" tools.
Q3. A tool endpoint verifies the bearer token is valid and unexpired, then executes any requested action. During a prompt-injection incident, the agent calls a delete action it should never use, and it succeeds. What was missing?
  1. Authentication — the token should have been rejected.
  2. Authorization — a scope/role check that the identity may perform this action.
  3. Encryption — the call needed TLS.
  4. Nothing — a valid token implies permission.
Correct: B. AuthN succeeded (valid token), but AuthZ was absent — no per-action scope check. The delete should have returned 403. This is the classic "valid token ≠ permitted action" distinction, amplified by missing least-privilege scoping.
Q4. Which statement is correct?
  1. OIDC is purely an authorization protocol; OAuth handles identity.
  2. OAuth 2.0 is a delegated authorization framework; OIDC layers identity (AuthN) on top of it.
  3. An API key provides strong per-user authorization out of the box.
  4. A signed JWT never needs its signature verified if it came over HTTPS.
Correct: B. OAuth 2.0 = authorization/delegation; OIDC = identity layer atop OAuth. API keys give weak AuthN with no user scoping (C wrong). JWTs must always be signature/claim-verified regardless of transport (D wrong).
◎Exam Strategy — 44.3
  • Framing: Definition-matching ("AuthN vs. AuthZ"), protocol identification (OAuth vs. OIDC), and "valid token but wrong action" scenarios.
  • Trigger keywords: "who vs. what", "valid token", "scope/role", "401 vs. 403", "on behalf of a user", "verify identity", "token expiry/rotation".
  • Elimination: Any option implying a valid token alone authorizes an action is wrong. Any option skipping expiry/rotation or trusting the model to self-restrict is wrong. If the stem stresses identity, favor OIDC/AuthN; if it stresses permission/delegation, favor OAuth/AuthZ.

Identifying and Closing Security Gaps

Concept Overview

A security gap is any discrepancy between how an agent is configured and how it should be configured to safely meet its purpose. Identifying gaps is a structured comparison of the live configuration against a baseline of controls (least privilege, AuthN/AuthZ, logging, input/output handling). Closing them means remediating the highest-risk gaps first, then adding defense in depth so that no single failure is catastrophic. For agents specifically, the highest-signal gaps cluster around excess capability, missing authorization checks, unbounded inputs (prompt injection), and lack of observability.

Key Definitions

Threat model
Structured view of what can go wrong: assets, actors, entry points, and impacts.
Defense in depth
Layered controls so one failure doesn't breach the system.
Prompt injection
Malicious instructions smuggled via inputs/tool outputs that hijack the agent's behavior.
Guardrails
Input/output filters, allow-lists, and policy checks around the model.
Risk score
Prioritization value, commonly Likelihood × Impact.
Observability
Logging, tracing, and monitoring of every tool invocation and decision.
Fail-safe / fail-closed
On error/ambiguity, deny rather than allow.

✕Common Pitfalls / Anti-Patterns
  • Trusting tool output as instructions — a fetched web page or file becomes an injected command.
  • Single-layer defense — relying only on the system prompt to prevent misuse.
  • Fail-open — on timeout/error, proceeding as if allowed.
  • Fixing easy gaps first instead of highest-risk gaps.
  • No monitoring — you cannot close gaps you cannot see.
✦Tips & Tricks
  • Mnemonic "CLAP" for the top agent gap classes: Capability excess, Logging absent, Authz missing, Prompt-injection exposure.
  • Prioritize with Likelihood × Impact; a "hard to fix but CRITICAL" gap beats an "easy but LOW" one.
  • Treat all tool output as untrusted input. Isolate it; never let it silently become an instruction.
  • Default posture is fail closed and defense in depth.
Q5. During review you find: (i) a tool with write scope used only for reads, and (ii) tool-call logging is disabled. Under Likelihood × Impact, how should you sequence remediation?
  1. Fix logging first because it's the quickest change.
  2. Rank by risk: over-broad write scope (HIGH) before enabling logging (MED) — but do both.
  3. Neither is a real gap.
  4. Only enable logging; scope is fine because it "works."
Correct: B. Prioritize by risk score, not by ease. The over-broad write scope is higher impact/likelihood (escalation, blast radius) than the missing logs — though both must be remediated. "Quickest first" (A) and "it works" (D) are traps.
◎Exam Strategy — 44.4
  • Framing: Multi-issue scenarios ("find and prioritize the gaps"), risk-ranking, and "which remediation closes the gap without over-correcting."
  • Trigger keywords: "prioritize", "highest risk", "defense in depth", "fail open/closed", "untrusted tool output", "no logging", "prompt injection".
  • Elimination: Reject "fix the easiest first" and "single control is enough." Favor answers that rank by Likelihood × Impact, add layered controls, and fail closed. Watch for a distractor that fixes a real-but-lower gap while ignoring the CRITICAL one.

Hands-On: Auditing an Agent's Tool Configuration

Concept Overview

An audit operationalizes 44.1–44.4: you take a real agent configuration and systematically verify each tool is justified, minimally scoped, properly authenticated/authorized, logged, and gated where dangerous. The output is a prioritized remediation list and a hardened config. Below is a full worked example with a realistic (insecure) starting config, a step-by-step process, before/after remediation, and a reusable self-check checklist.

Scenario

Agent support-summarizer has one job: read incoming support tickets and produce a daily summary document. It should not reply to customers, delete data, run code, or touch production. Here is its current configuration.

Step-by-Step Audit Process

  1. State the intended purpose in one sentence (above). Everything is judged against it.
  2. Inventory every tool and its scope, auth method, token lifetime, and logging status.
  3. Justify or remove each tool: is it used by the stated workflow? (44.1)
  4. Right-size scope: read vs. write vs. delete; single resource vs. wildcard. (44.2)
  5. Verify AuthN & AuthZ: valid identity + per-action scope check server-side; token expiry + rotation. (44.3)
  6. Hunt gaps: logging, untrusted tool output, HITL on destructive actions, fail-closed behavior. (44.4)
  7. Score & prioritize findings (Likelihood × Impact); remediate CRITICAL/HIGH first.
  8. Re-issue hardened config; re-run the checklist; enable monitoring/alerting.
!BEFORE — Insecure configuration (annotated) Read the inline comments; each flags a specific finding.
agent: support-summarizer
purpose: "Summarize incoming support tickets daily"
tools:
  - name: read_tickets
    scope: "tickets:read:all_projects"   # ⚠ scope too broad (all projects)
    auth: api_key                        # ⚠ weak AuthN, no user context
    token_ttl: null                      # ✕ never expires (no rotation)
    logging: false                       # ✕ no invocation logging

    approval_required: false             # ✕ no human-in-the-loop gate
    logging: false

    scope: "host:exec"                   # ✕ code exec on host, unrelated to task

✦Tips & Tricks — Audit Heuristics
  • Start from the one-sentence purpose; any tool not serving it is a finding.
  • Scan for the "big four" red flags: auth: none, ttl: null, */all scopes, on_error: allow.
  • Destructive verb (delete/drop/exec) with approval_required: false = automatic HIGH.
  • "Trusted tool output" is always a finding — tool output is untrusted input.
Q6. In the BEFORE config, which single change removes the most blast radius fastest?
  1. Enable logging on all tools.
  2. Remove run_shell (host exec, no auth, open egress).
  3. Shorten the delete_ticket token TTL.
  4. Rename the agent.
Correct: B. An unauthenticated host-exec tool with open network egress is the CRITICAL, highest-blast-radius capability and is unrelated to the task — removing it is the highest-value single action. Logging (A) matters but is MED; TTL tweaks (C) don't fix that delete shouldn't exist.

Reusable Self-Check Checklist (for real audits)

  • Written the agent's purpose in one sentence and judged every tool against it
  • Listed all tools currently granted to the agent
  • For each tool, confirmed it is used in ≥1 active, justified workflow
  • Verified scope is minimum necessary (read < write < delete; single resource, no wildcards)
  • Removed all unused / speculative / duplicate tools (capability bloat)
  • Confirmed strong AuthN (no auth: none, no shared god-keys)
  • Confirmed AuthZ (scope/role) is enforced server-side on every action
  • Verified tokens have expiry and a rotation policy; secrets in a vault, not in prompts/code
  • Gated destructive/irreversible actions behind human-in-the-loop approval
  • Set fail-closed behavior (on_error: deny)
  • Treated tool output as untrusted; enabled input/output guardrails
  • Enabled logging & monitoring of every tool invocation, with alerts on denied/scope-violation calls
  • Scored findings by Likelihood × Impact and remediated CRITICAL/HIGH first
  • Re-ran this checklist after remediation
◎Exam Strategy — 44.5
  • Framing: A config snippet is shown; questions ask you to spot the flaw, pick the correct remediation, or rank fixes. Expect "which line is the biggest risk?" items.
  • Trigger keywords in configs: auth: none, ttl/expiry: null, scope: * / all, on_error: allow, approval_required: false, treat_output_as_trusted, unused destructive tools.
  • Time management: Scan the config for the "big four" red flags first, tag the destructive/unauthenticated line as CRITICAL, then read the options. The security-correct answer removes/narrows/enforces — never "add more capability" or "rename/cosmetic."

Top 10 Things to Remember Before the Exam

  1. Justify or remove. Every tool must map to an active workflow — unused capability is bloat and blast radius.
  2. Least privilege = min permissions, min scope, min time. Prefer many narrow tools over one broad tool.
  3. Read < Write < Delete. Default to read-only; strongly justify anything destructive.

  5. 401 = not authenticated, 403 = not authorized. Enforce both server-side, on every call.

  7. Tokens need expiry + rotation; secrets live in a vault, never in prompts, code, or schemas.
  8. Treat all tool output as untrusted input — it's a top prompt-injection vector; isolate and sanitize it.
  9. Fail closed and layer defenses. On error/ambiguity, deny; never rely on the model alone to self-restrict.
  10. Prioritize by Likelihood × Impact, gate destructive actions behind human approval, and log/monitor every invocation.
◎Final exam heuristic When in doubt, choose the option that reduces capability, narrows scope, enforces an explicit permission check, or fails closed. Options that add capability, defer removal, trust the model, or fix the easy-but-low-risk item are almost always distractors.
