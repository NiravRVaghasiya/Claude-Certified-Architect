47.1 Retrieval-Augmented Generation: Architecture Overview

Concept Summary

RAG (Retrieval-Augmented Generation) is a pattern that grounds a language model's answer in external, retrieved knowledge instead of relying only on the model's trained-in (parametric) memory. At ingestion time, source documents are loaded, split into chunks, embedded, and stored in an index. At query time, the user's question is embedded, the most relevant chunks are retrieved, and those chunks are inserted into the prompt as context so the model can answer from evidence it can cite. RAG reduces hallucination, lets you update knowledge without retraining, and keeps answers traceable to sources.

Key Terminology

RAG (Retrieval-Augmented Generation)
Architecture that retrieves relevant text and feeds it to an LLM as grounding context before it generates an answer.
Ingestion / Indexing pipeline
The offline path: load → chunk → embed → store. Runs when documents are added or refreshed.
Retrieval / Generation pipeline
The online path: embed query → retrieve chunks → assemble prompt → generate grounded answer.
Embedding
A numeric vector representing the meaning of text, so similar meanings sit close together in vector space.
Context window
The maximum tokens the model can read at once; retrieved chunks must fit within it alongside the prompt and answer.
Grounding
Constraining the model to answer only from retrieved evidence, ideally with citations.

💡 Tips & Tricks
  • Use the same embedding model for documents and queries — mixing models breaks the shared vector space.
  • Store rich metadata (source, title, section, timestamp) alongside each chunk to enable filtering and citations.
  • Always return source references so answers are auditable and users can verify claims.
  • Treat RAG as two independently tunable systems — you can improve retrieval without touching generation and vice-versa.
⚠️ Common Pitfalls
  • Assuming RAG "fixes" hallucination — it only helps if retrieval surfaces the right evidence and the prompt instructs the model to stay grounded.
  • Stuffing too many chunks into context, causing "lost in the middle" degradation and higher cost.
  • Forgetting that a wrong answer can come from either bad retrieval or bad generation — diagnose the two separately.
🎯 Exam Strategy

Likely phrasing: "Which component is responsible for…", "In what order do the stages execute?", or "A system answers from outdated info even though the model is current — what is the most likely cause?"

Eliminating distractors: Answers that describe fine-tuning or retraining are usually wrong for a RAG question — RAG's whole point is updating knowledge without retraining. Discard options that place generation before retrieval.

Worked example. Q: "A RAG chatbot returns confidently wrong answers about a policy that was correctly ingested. What should you investigate first?"
Reason: The doc is present, so ingestion is fine → the fault is downstream. The two candidates are (a) retrieval didn't surface the right chunk, or (b) the prompt didn't constrain the model to use context. Since the info exists but isn't used, check retrieval recall first (did the relevant chunk appear in top-k?), then prompt grounding. → Answer: inspect retrieval, not the training data.

47.2 Chunking Strategies: Size, Overlap & Semantic Boundaries

Concept Summary

Chunking splits documents into retrievable units. Chunk size trades off precision against context: smaller chunks give sharper matches but may lose surrounding meaning, while larger chunks carry more context but dilute the embedding and can retrieve irrelevant material. Overlap repeats a slice of text between adjacent chunks so a fact sitting on a boundary isn't cut in half. The best chunking respects semantic boundaries — headings, paragraphs, sentences, list items — rather than slicing blindly at a fixed character count.

Key Terminology

Chunk size
How much text (usually measured in tokens) each retrievable unit contains.
Overlap
Text shared between consecutive chunks to preserve context at boundaries; commonly 10–20% of chunk size.
Recursive / structural chunking
Splitting along a hierarchy of separators (sections → paragraphs → sentences) so chunks align with natural structure.
Semantic chunking
Grouping sentences by embedding similarity so a chunk holds one coherent idea, splitting where topic shifts.
Parent-document retrieval
Embed small chunks for precise matching but return the larger parent passage for full context.

💡 Tips & Tricks
  • Start with recursive/structural splitting before reaching for expensive semantic chunking — it's often "good enough".
  • For narrative text, an overlap of 10–20% of chunk size is a solid default.
  • Keep one coherent idea per chunk; if a chunk mixes topics, its embedding becomes "muddy" and matches poorly.
  • Use parent-document retrieval when you need pinpoint matching and broad context.
⚠️ Common Pitfalls
  • Fixed-character splitting that cuts sentences, tables, or code mid-structure.
  • Zero overlap — facts on boundaries become unretrievable.
  • Excessive overlap (e.g. 50%+) — inflates index size, cost, and returns near-duplicate chunks.
  • One-size-fits-all sizing across heterogeneous content types.
🎯 Exam Strategy

Likely phrasing: Scenario gives you a document type (long manual, FAQ, code) and asks for the "optimal chunking approach" or "why answers miss context at boundaries."

Eliminating distractors: Discard options that mention size alone without overlap or boundary awareness. The correct answer usually pairs size + overlap + semantic boundary together. Beware answers proposing 50%+ overlap as "safer" — that's a distractor.

Worked example. Q: "Users report the assistant loses information that spans two paragraphs of a policy manual. Best fix?"
Reason: Symptom = boundary loss → overlap is too small or zero. Manuals have clear structure → respect headings/paragraphs. So the fix combines modest overlap (10–20%) with structure-aware splitting, not merely "increase chunk size" (which lowers precision) or "remove chunking" (impossible at scale). → Answer: structural chunking with 10–20% overlap.

47.3 Indexing Strategies: Vector, Keyword & Hybrid

Concept Summary

An index is the searchable structure retrieval queries against. A vector (dense) index stores embeddings and finds chunks by semantic similarity — great for paraphrases and concepts, but weak on exact strings. A keyword (sparse) index such as BM25 matches literal terms — excellent for names, error codes, and acronyms, but blind to synonyms. A hybrid index runs both and fuses the results (commonly with Reciprocal Rank Fusion, RRF), capturing the strengths of each. In production, hybrid is a common default because real queries mix conceptual and exact-match intent.

Key Terminology

Dense / vector index
Stores embeddings; retrieves by vector similarity (cosine/dot product) using approximate nearest neighbour (ANN) search.
ANN & HNSW
Approximate Nearest Neighbour search; HNSW is a popular graph-based ANN algorithm trading a little accuracy for large speed gains.
Sparse / keyword index (BM25)
Term-frequency ranking that matches exact tokens; strong on rare/specific terms.
Hybrid search
Combines dense + sparse results into one ranked list.
Reciprocal Rank Fusion (RRF)
A simple, score-agnostic method to merge multiple ranked lists by summing 1/(k + rank) across lists.
Metadata filtering
Restricting search to chunks matching structured fields (date, source, tenant) before/after ranking.

💡 Tips & Tricks
  • Default to hybrid when queries are mixed; fall back to pure vector or pure keyword only when the workload is clearly one-sided.
  • RRF needs no score normalization — a robust first choice for fusion.
  • Push metadata filters (tenant, date, permissions) into the query to cut candidates and enforce access control.
  • Tune ANN parameters (e.g. HNSW ef_search) to balance recall vs. latency.
⚠️ Common Pitfalls
  • Using pure vector search for identifier-heavy data (SKUs, error codes) and getting fuzzy near-misses.
  • Ignoring keyword search entirely — semantic search alone often misses exact-string queries.
  • Forgetting access-control filters, leaking chunks across tenants/users.
  • Setting ANN accuracy too low to save latency, silently dropping relevant results.
🎯 Exam Strategy

Likely phrasing: "A search over product SKUs and part numbers returns close-but-wrong items" or "Which index best serves a mix of conceptual and exact-match queries?"

Eliminating distractors: If the scenario stresses exact identifiers, pure vector is a distractor. If it stresses synonyms/paraphrase, pure keyword is a distractor. When both are mentioned, the answer is almost always hybrid.

Worked example. Q: "Support search must find both 'can't log in' (natural language) and exact error code ERR_4013. Best index?"
Reason: Natural-language phrasing needs semantics → dense. Exact code needs literal match → BM25. Both present → combine. → Answer: hybrid with RRF fusion.

47.4 Retrieval Strategies Matched to Data Shape and Query Pattern

Concept Summary

Retrieval is not one algorithm — the right strategy depends on the shape of your data (short FAQ vs. long reports vs. structured records) and the pattern of your queries (specific vs. vague, single-fact vs. multi-hop). Beyond plain dense top-k, common techniques include reranking (a cross-encoder re-scores candidates for precision), MMR (Maximal Marginal Relevance, which trades some relevance for diversity to reduce redundancy), and query transformation (multi-query or HyDE) for under-specified questions. The architect's job is to match the tool to the situation, not to always reach for the most complex option.

Key Terminology

Top-k
Return the k most similar chunks; k is a key tuning knob (too small = missed context, too large = noise/cost).
Reranking (cross-encoder)
A second-stage model that scores each (query, chunk) pair jointly for higher precision than embedding similarity alone.
MMR (Maximal Marginal Relevance)
Selection that balances relevance to the query against novelty vs. already-picked chunks, reducing duplicates.
Multi-query
Generate several rephrasings of the question and union their results to boost recall.
HyDE (Hypothetical Document Embeddings)
Draft a hypothetical answer, embed it, and retrieve against that — helps for vague queries.
Multi-hop retrieval
Iterative retrieval where one result informs the next query, for questions needing chained evidence.

Visualization

Fig 47.4 — A decision tree for matching retrieval strategy to query specificity and precision needs.
💡 Tips & Tricks
  • Retrieve a wide candidate set (e.g. top-20–50) then rerank down to a few high-precision chunks for the prompt.
  • Use MMR when top-k returns many near-duplicates covering the same point.
  • Reach for multi-query / HyDE only when queries are genuinely vague — they add latency and cost.
  • Match k to the context budget: leave room for the system prompt and the answer.
⚠️ Common Pitfalls
  • Over-engineering: applying multi-hop or HyDE to simple, specific queries — pure cost with no benefit.
  • Setting k so large that irrelevant chunks crowd out the answer ("lost in the middle").
  • Skipping reranking when precision matters and false positives are expensive.
  • Ignoring redundancy — feeding the model five chunks that all say the same thing.
🎯 Exam Strategy

Likely phrasing: "Retrieved results are relevant but repetitive," "vague user questions return poor context," or "precision must be high because wrong context is costly."

Eliminating distractors: Map the symptom to the tool: redundancy → MMR; vague queries → multi-query/HyDE; low precision → reranking; chained facts → multi-hop. Answers that propose the most complex technique for a simple query are distractors.

Worked example. Q: "A legal-search RAG surfaces the right documents but the top 5 chunks are near-identical excerpts, so the answer misses a second relevant clause. Best change?"
Reason: Relevance is fine, diversity is the problem → the symptom is redundancy, not recall or precision. The tool that maximizes coverage while staying relevant is MMR. → Answer: apply MMR to diversify retrieved chunks.

47.5 Handling Document Refreshes and Stale Embeddings

Concept Summary

A RAG index is only as trustworthy as it is fresh. When source documents change, the corresponding chunks and embeddings must be updated or the system will retrieve stale content. Two distinct staleness problems exist: (1) content drift — the source text changed, so chunks need re-ingestion; and (2) embedding drift — you switched or upgraded the embedding model, so all vectors must be recomputed to stay in one comparable space. Robust pipelines use change detection (hashes/timestamps), incremental re-indexing, versioning, and TTL / scheduled refresh to keep the index current without rebuilding everything each time.

Key Terminology

Content drift
Source documents change over time, making stored chunks outdated.
Embedding drift / model change
Changing the embedding model invalidates comparisons — mixing vectors from two models corrupts similarity. Full re-embedding is required.
Incremental / delta indexing
Only re-process documents that actually changed, detected via content hash or modified timestamp.
Change data capture (CDC)
Detecting inserts/updates/deletes at the source so the index can be patched accordingly.
TTL (time-to-live)
An expiry after which a chunk is considered stale and re-checked or removed.
Versioning
Tracking document/embedding versions so you can roll back and know which model produced which vector.
Tombstoning
Explicitly marking deleted source docs so their chunks are removed from retrieval.

Visualization

Fig 47.5 — Incremental refresh: skip unchanged docs, delta-update changed ones. A model change forces a full re-embed of the whole corpus.
💡 Tips & Tricks
  • Store a content hash per chunk so you re-embed only what actually changed.
  • Keep timestamps/version tags in metadata; expose "last updated" in answers for time-sensitive domains.
  • Schedule refreshes to match the source's real update cadence — near-real-time for news, nightly/weekly for docs.
  • On an embedding-model upgrade, re-embed everything and cut over atomically (blue/green index) to avoid mixed spaces.
  • Tombstone deleted sources so removed content stops being retrieved.
⚠️ Common Pitfalls
  • Mixing vectors from two embedding models in one index — silently corrupts similarity ranking.
  • Rebuilding the entire index on every small change — slow and expensive.
  • Deleting a source document but leaving its orphaned chunks retrievable.
  • No freshness signal, so users can't tell whether an answer reflects current data.
🎯 Exam Strategy

Likely phrasing: "After upgrading the embedding model, retrieval quality collapses," or "Deleted policies still appear in answers," or "How to keep a large index fresh cost-effectively?"

Eliminating distractors: If the trigger is a model change, the only correct answer is a full re-embed — options suggesting partial update are traps. If the trigger is a content change, favor incremental/delta re-indexing over full rebuilds.

Worked example. Q: "You switch from embedding-model v1 to v2 but only re-embed newly added documents. Search results become erratic. Why?"
Reason: New docs are in v2 space, old docs in v1 space — the two aren't comparable, so similarity scores are meaningless across them. The fix is to re-embed the entire corpus with v2. → Answer: full re-embedding after any model change.

47.6 Evaluating RAG Quality: Relevance, Faithfulness & Completeness

Concept Summary

You can't improve what you don't measure. RAG evaluation splits into retrieval quality and generation quality. On the retrieval side, context relevance/precision asks "are the retrieved chunks on-topic?" and context recall asks "did we retrieve everything needed to answer?". On the generation side, faithfulness (a.k.a. groundedness) asks "is the answer supported by the retrieved context, with no made-up claims?" and answer relevance/completeness asks "does the answer actually and fully address the question?". Evaluate the stages separately so you know which half to fix.

Key Terminology

Context precision / relevance
Share of retrieved chunks that are actually relevant — measures retrieval noise.
Context recall
Whether all information needed to answer was retrieved — measures retrieval completeness.
Faithfulness / groundedness
Degree to which answer claims are supported by the retrieved context (no hallucination).
Answer relevance
How directly the answer addresses the user's actual question.
Completeness
Whether the answer covers all parts the question requires.
Golden / evaluation set
A curated set of question → expected-answer/expected-source pairs used to measure quality over time.
LLM-as-judge
Using a strong model with a rubric to score faithfulness/relevance at scale; validate against human labels.

💡 Tips & Tricks
  • Build a small golden set early; measure before and after every change to prove impact.
  • Evaluate retrieval and generation separately — a low faithfulness score with good context points to the prompt/model, not retrieval.
  • Require citations; an uncited claim is a faithfulness red flag.
  • Use LLM-as-judge for scale, but spot-check against human labels to trust the scores.
  • Track metrics as a dashboard over time to catch regressions before users do.
⚠️ Common Pitfalls
  • Judging only the final answer and never inspecting whether retrieval supplied the right context.
  • Confusing faithfulness (grounded in context) with correctness (true in the real world) — an answer can be faithful to a wrong source.
  • Optimizing a single metric (e.g. recall) at the expense of another (precision).
  • Having no evaluation set at all, so "improvements" are guesswork.
🎯 Exam Strategy

Likely phrasing: "The retrieved context is correct but the answer adds facts not in the context — which metric is failing?" or "How would you diagnose whether a bad answer is a retrieval or generation problem?"

Eliminating distractors: Anchor on definitions. "Made-up claims despite good context" = faithfulness, not relevance. "Missed necessary info" = recall, not precision. Distractors swap these pairs — read the symptom carefully.

Worked example. Q: "Context contains the answer, but the model's response includes an extra statistic that appears nowhere in the retrieved text. Which metric is low?"
Reason: Retrieval was fine (context had the answer) → not a recall/precision issue. The problem is the answer isn't supported by context → that's faithfulness / groundedness. Fix = tighten prompt grounding + require citations. → Answer: faithfulness.

47.7 Hands-On: Building and Tuning a RAG Pipeline

Concept Summary

Building a RAG pipeline is iterative: stand up a baseline end-to-end, measure it against a golden set, then tune one variable at a time. The typical build order is: load & clean documents → choose a chunking strategy → pick an embedding model → select an index type → set retrieval (k, hybrid, rerank) → engineer a grounding prompt → evaluate → iterate. Because retrieval and generation are separable, you diagnose which stage is limiting quality and tune only that lever, re-measuring each time so you can attribute gains to specific changes.

Key Terminology

Baseline
The simplest working pipeline you measure everything else against.
Ablation / one-variable tuning
Changing a single parameter at a time so you can attribute quality changes to it.
Grounding prompt
Instruction that tells the model to answer only from provided context and to say "I don't know" if the context is insufficient.
Context assembly
How retrieved chunks are ordered/formatted/deduplicated into the final prompt.
Guardrail: cite-or-refuse
Require the model to cite sources or decline, curbing hallucination.

Visualization

Fig 47.7 — Build the baseline left-to-right, evaluate against a golden set, then loop back changing one lever at a time.
💡 Tips & Tricks
  • Ship a naive baseline first (fixed chunks, dense top-k, simple prompt) — you can't tune what you can't measure.
  • Tune one variable at a time and re-run evaluation to attribute the gain.
  • When retrieval metrics are the bottleneck, fix chunking/index/k before touching the generation model.
  • Add a cite-or-refuse instruction ("if the context doesn't contain the answer, say you don't know").
  • Log real queries + retrieved chunks to grow your golden set from actual usage.
⚠️ Common Pitfalls
  • Changing chunking, model, and prompt all at once — you can't tell what helped.
  • Optimizing the LLM prompt when the real problem is that retrieval never surfaced the answer.
  • No golden set, so "it feels better" replaces measurement.
  • Over-stuffing the context window, raising cost and triggering "lost in the middle".
🎯 Exam Strategy

Likely phrasing: "Answers are wrong; what do you tune first?", "How to isolate the cause of poor RAG quality?", or a step-ordering question ("place these build stages in order").

Eliminating distractors: The correct answer almost always starts with measure/diagnose before changing anything, and changes one lever at a time. Options that jump straight to fine-tuning the LLM, or that change several things at once, are distractors.

Worked example. Q: "Faithfulness is high but answers are frequently incomplete. Evaluation shows context recall is low. What should you tune first?"
Reason: Faithful but incomplete + low recall → the model is loyal to context, but the context is missing pieces. That's a retrieval recall problem, not a generation one. Levers: increase k, switch to hybrid search, or add query expansion — not prompt/model changes. → Answer: improve retrieval recall (hybrid/↑k) before touching the prompt.

One fact per sub-topic

  • 47.1 Architecture: RAG = two pipelines (ingestion + retrieval/generation) sharing one index; it updates knowledge without retraining and reduces hallucination only if retrieval + grounding both work.
  • 47.2 Chunking: Respect semantic boundaries; use 10–20% overlap for narrative text; the best answer pairs size + overlap + boundary, never size alone.
  • 47.3 Indexing: Vector = meaning, Keyword/BM25 = exact terms, Hybrid (+ RRF) = both and the production default for mixed queries.
  • 47.4 Retrieval: Match tool to symptom — redundancy → MMR, vague query → multi-query/HyDE, precision → rerank, chained facts → multi-hop; don't over-engineer simple queries.
  • 47.5 Freshness: Content change → incremental/delta re-index; embedding-model change → full re-embed of the entire corpus (never mix model spaces).
  • 47.6 Evaluation: Split retrieval (precision/recall) from generation (faithfulness/answer-relevance); "grounded in context" (faithfulness) ≠ "true in reality" (correctness).
  • 47.7 Hands-on: Baseline → measure against golden set → tune one variable at a time; fix retrieval before generation.

Quick decision tree — pick the retrieval strategy

▸ Query has exact IDs / codes / names  →  include keyword (BM25) → if also conceptual → hybrid + RRF

▸ Query is conceptual / paraphrased  →  dense vector top-k → if precision-critical → add cross-encoder rerank

▸ Results are relevant but repetitive  →  add MMR for diversity

▸ Query is vague / under-specified  →  multi-query or HyDE to boost recall

▸ Answer needs chained / multi-hop evidence  →  iterative multi-hop retrieval

▸ Mixed intent + production default  →  hybrid retrieval → rerank → assemble top few chunks

Quick decision tree — freshness & evaluation

▸ Source text changed  →  delta re-chunk + re-embed changed docs, upsert, tombstone deletes

▸ Embedding model changed  →  full re-embed of whole corpus, atomic cut-over

▸ Answer invents facts despite good context  →  low faithfulness → tighten grounding + citations

▸ Answer misses needed info  →  low context recall → ↑k / hybrid / query expansion

▸ Retrieved chunks off-topic  →  low context precision → rerank / better chunking / filters
