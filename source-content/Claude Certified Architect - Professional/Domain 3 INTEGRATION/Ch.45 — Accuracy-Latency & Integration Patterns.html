45.1Evaluating Accuracy-Latency Tradeoffs

Definition
Accuracy-latency tradeoff is the tension in LLM inference between how correct/complete a response is and how fast it is produced. Configuration choices that raise expected accuracy (larger model, more context, more reasoning tokens, self-consistency) generally increase latency and cost; choices that reduce latency (smaller model, tighter token budgets, streaming, caching) can reduce headroom for accuracy on hard tasks.

There is no single "best" configuration — only the best configuration for a stated requirement. The architect's job is to place the workload on the frontier deliberately rather than by accident.

Variables that affect latency

LLM inference latency has two mechanical phases: prefill (processing the input prompt, which sets Time-To-First-Token) and decode (autoregressive token-by-token generation, which dominates total latency because tokens are produced sequentially).

  • Model size / class — larger models (Opus-class) run more compute per token than mid (Sonnet-class) or small (Haiku-class) models, raising both TTFT and per-token time.
  • Output token budget (max_tokens & actual output length) — the single biggest controllable driver of total latency, because decode is sequential. Long outputs cost proportionally more wall-clock time.
  • Input / context length — longer prompts increase prefill work and TTFT. Prompt caching mitigates repeated prefixes.
  • Streaming vs batch — streaming (SSE) does not reduce total latency but dramatically improves perceived latency by emitting tokens as they are decoded. The Batch API trades higher throughput and lower cost for much higher, asynchronous latency.
  • Extended thinking / reasoning tokens — allocating a thinking budget adds decode work before the final answer, raising latency in exchange for accuracy on hard reasoning tasks.
  • Temperature & top-p — sampling parameters have negligible direct effect on latency; their role is on the accuracy axis.
🔴CRITICAL CONCEPT: Output length, not input length, usually dominates end-to-end latency. Decode is sequential and per-token; prefill is parallel. When a scenario complains about "slow responses," first suspect large max_tokens or verbose outputs before blaming model size.

Variables that affect accuracy

  • Model class — larger models generally handle harder reasoning, longer context, and more nuanced instructions better.
  • Context length & relevance — supplying the right grounding context (RAG, documents) raises accuracy; irrelevant or excessive context can dilute attention and hurt it.
  • Few-shot examples — well-chosen examples improve format adherence and task accuracy, at the cost of extra input tokens (latency/cost).
  • Prompt clarity & structure — explicit instructions, role framing, and output schemas reduce ambiguity-driven errors — cheap accuracy with no latency penalty.
  • Temperature / top-p — lower temperature reduces variance and improves consistency on deterministic tasks (extraction, classification); higher temperature aids creative breadth but can reduce factual reliability.
  • Extended thinking & self-consistency — giving the model room to reason (or sampling multiple answers and voting) raises accuracy on complex problems, with a direct latency/cost cost.
💡TIP: Lower temperature values (0.0–0.3) reduce output variance and improve factual consistency — ideal for classification and extraction tasks where accuracy outweighs creativity. Reserve higher temperatures for ideation and drafting.

📝 Quick Recall
  • Latency = prefill (TTFT) + decode; decode is sequential and usually dominates.
  • Output token budget is the biggest controllable latency lever.
  • Prompt clarity is the best accuracy-per-token lever — nearly free.
  • Streaming improves perceived, not actual, latency.
  • Pick the frontier point that meets the SLA; don't over-serve.

45.2Justifying Configuration Decisions with Data

Definition
A data-driven configuration decision replaces intuition ("Opus feels smarter") with measured evidence: run candidate configurations against a representative evaluation set, collect latency, quality, and cost metrics, and choose the configuration that meets the requirement at the lowest cost/latency.

Methodology for benchmarking Claude configurations

  1. Define the task & success criteria — what does "correct" mean? Exact match, rubric score, human preference, downstream task success?
  2. Build a representative eval set — real inputs that reflect production distribution, including hard/edge cases. Freeze it so comparisons are apples-to-apples.
  3. Enumerate candidate configs — vary one dimension at a time (model class, temperature, few-shot count, thinking budget) to attribute effects.
  4. Run under realistic conditions — same region, comparable concurrency, warm caches vs cold measured separately.
  5. Collect the full metric set (below) per request, not just averages — capture the distribution.
  6. Analyze & decide — compare on the axis your requirement cares about, subject to constraints on the others.

Key metrics to collect

MetricWhat it measuresWhy it matters
TTFT (Time To First Token)Latency until the first output token arrivesDrives perceived responsiveness in streaming UIs
Total latency (end-to-end)Request start → last tokenSLA / timeout budgeting
Output rate (tokens/sec)Decode throughputPredicts total time for long outputs
Accuracy / quality scoreTask-specific correctness (exact-match, rubric, pass rate)The whole point — the accuracy axis
Cost / requestInput + output tokens × price (± caching, batch)Unit economics at scale
Percentiles (p50/p95/p99)Tail latency, not just meanTails determine real user experience & SLAs
🔴CRITICAL CONCEPT: Report percentiles, not just averages. A config with great mean latency but a bad p95/p99 fails users at scale. Tail latency is where SLAs break.

Designing an A/B test for prompt configurations

  • Isolate one variable per arm (e.g. prompt A vs prompt B) so the effect is attributable.
  • Randomize assignment of inputs across arms to avoid distribution skew.
  • Hold everything else fixed — same model, region, time window, temperature.
  • Pre-register the metric & decision rule before looking at results, to avoid cherry-picking.
  • Run enough samples to detect the effect size you care about.
# Pseudocode: one-variable-at-a-time eval harness
for config in candidate_configs:          # vary model / temp / few-shot
    for item in frozen_eval_set:          # representative inputs
        r = call_claude(item.input, **config)
        record(config, latency=r.latency, ttft=r.ttft,
               tokens=r.usage, score=grade(r.output, item.gold),
               cost=price(r.usage, config.model))
report_percentiles_and_mean(per_config=True)

Statistical significance considerations

⚠️WARNING: LLM outputs are variable (sampling, non-determinism). A 2-point accuracy difference on 20 examples is noise. Use a large enough eval set, report confidence intervals, and treat small differences as ties. For latency, use percentiles over many runs — a single run's latency is meaningless.
  • Beware overlapping confidence intervals — if they overlap, you cannot claim one config is "better."
  • Control temperature during accuracy evals (lower = more stable, more reproducible measurements).
  • Separate cold vs warm cache latency; mixing them corrupts the comparison.
  • Watch for eval set contamination / overfitting — tuning prompts to a tiny fixed set can inflate scores that don't generalize.

🎯EXAM STRATEGY: Data-driven justification questions reward the answer that (1) names a specific metric tied to the stated requirement, and (2) acknowledges the tradeoff on the other axis. "Choose Opus because it's more accurate" is weak. "Benchmarks show Sonnet meets the p95 latency SLA with accuracy within 1% of Opus at 5× lower cost, so Sonnet is justified" is the pattern examiners want. Look for options that cite the right metric (TTFT for interactive, cost/request at scale, percentiles for SLA).
💡TIP: Common mistakes when citing data — quoting averages instead of percentiles; comparing configs measured under different conditions; drawing conclusions from too few samples; ignoring cost while optimizing accuracy; and confusing perceived (streaming) latency with total latency.
📝 Quick Recall
  • Freeze a representative eval set; vary one dimension at a time.
  • Collect TTFT, total latency, tokens/sec, quality score, cost/request — with percentiles.
  • Pre-register metric & decision rule; report confidence intervals.
  • Overlapping CIs = tie; don't over-claim from noise.
  • Justify with the metric that matches the requirement + name the tradeoff.

45.3Connection Protocols: MCP vs API/CLI vs Agent-to-Agent

Model Context Protocol (MCP)

Definition
MCP (Model Context Protocol) is an open, standardized protocol from Anthropic that connects LLM applications to external tools, data, and prompts through a uniform client-server interface. It lets a model "plug in" to context sources the way USB standardizes device connections — write a server once, reuse it across any MCP-compatible host.

Architecture: a host application (e.g. Claude Desktop, an IDE, a custom agent) runs one or more MCP clients, each maintaining a connection to an MCP server. Servers expose three primitives:

  • Tools — model-invokable functions (actions with side effects).
  • Resources — readable data/context (files, records) the host can load.
  • Prompts — reusable prompt templates surfaced to the user/model.

Transport layers: MCP messages use JSON-RPC 2.0 over a transport. The two standard transports are stdio (local subprocess — low latency, ideal for local servers) and streamable HTTP (remote servers, supports server-sent events for streaming). Use cases: standardized tool/resource abstraction, reusable connectors, decoupling integrations from any single app.

Direct API / CLI Integration

Definition
Direct API/CLI integration calls Claude straight through the Messages API over HTTPS (REST), via official SDKs (Python/TypeScript), or through command-line tooling. It is the lowest-overhead path: your code owns the request/response loop, tool definitions, and orchestration.
  • REST calls — POST to the Messages endpoint with model, messages, and parameters; JSON response.
  • SDK usage — typed clients that wrap auth, retries, streaming, and tool-use loops.
  • CLI tooling — command-line access (e.g. Claude Code) for scripting and developer workflows.
  • Streaming — server-sent events emit tokens incrementally for responsive UIs.
  • Tool use — you declare tools inline in the request; the model returns tool-use blocks you execute and feed back.

Agent-to-Agent Patterns

Definition
Agent-to-agent architectures coordinate multiple LLM agents to solve a task. A common pattern is orchestrator–subagent (worker): a lead agent decomposes a problem, delegates subtasks to specialized subagents that work in parallel with isolated context, then synthesizes their results.
  • Orchestrator–subagent — lead plans & delegates; workers execute focused subtasks with their own context windows, reducing context pollution.
  • Message passing — agents exchange structured task specs and results; the orchestrator owns final synthesis.
  • Trust boundaries — subagents should receive least-privilege tool access; validate/​sanitize inter-agent messages; the orchestrator is the authority that composes outputs.

📝 Quick Recall
  • MCP = open JSON-RPC client-server standard exposing tools, resources, prompts; transports = stdio & streamable HTTP.
  • Direct API/CLI = lowest overhead; your code owns the loop; best for simple, latency-sensitive integrations.
  • Agent-to-agent = orchestrator delegates to isolated subagents; highest capability, highest latency; mind trust boundaries.
  • Match keywords to protocol; don't over-engineer with multi-agent for simple tasks.

45.4Selecting the Appropriate Integration Mechanism

Definition
Integration mechanism selection is the structured process of mapping requirements (latency, accuracy, context complexity, security, team capability) onto the connection protocol and configuration that best satisfies them within constraints.

Selection framework (decision-tree logic)

  1. Latency requirement? Hard real-time → prefer direct API/CLI + streaming; async-tolerant → MCP or agent-to-agent acceptable.
  2. Accuracy requirement? High-stakes → larger model, thinking, structured output; routine → smaller model.
  3. Context complexity? Many heterogeneous sources / reusable tools → MCP; single tool → inline API tool use.
  4. Decomposability? Parallel specialized subtasks → agent-to-agent; linear task → single agent.
  5. Security posture? Strict least-privilege / auditable tool boundaries → MCP server boundary or explicit trust boundaries.
  6. Team expertise / time? Small team / fast delivery → simplest mechanism that meets requirements (usually direct API).

Accuracy on complex tasksDepends on configDepends on configBest (specialization)

Anti-patterns & failure modes

Anti-patternFailure mode

Decision tree (nested view)

  • Is the task latency-critical & simple?
    • Yes → Direct API/CLI (streaming, small model).
    • No → continue.
  • Do you need reusable tools/data across apps or many heterogeneous sources?
    • Yes → MCP.
    • No → continue.
  • Does the task decompose into parallel specialized subtasks?
    • Yes → Agent-to-Agent.
    • No → Direct API/CLI.
💡TIP — elimination strategy for MCQs: First delete over-engineered options (multi-agent for trivial tasks). Then delete options that violate a stated hard constraint (e.g. "must be real-time" kills agent-to-agent). Of what remains, pick the simplest mechanism that satisfies every stated requirement.
⚠️EXAM TRAP: Two mechanisms can look equally valid — e.g. "connect Claude to a database." Both direct API tool use and MCP work. The tiebreaker is in the qualifiers: if the question says "reused by multiple teams/apps" or "standardized," pick MCP; if it says "single service, lowest latency, simplest," pick direct API. Read the modifiers, not just the verb.
🎯EXAM STRATEGY: Mechanism-selection answers reward "simplest that meets all requirements." When two options satisfy the functional need, the constraint keywords (reuse, latency, security, team size) break the tie. The most powerful mechanism is rarely the correct answer for a simple scenario.
📝 Quick Recall
  • Filter by: latency, accuracy, context complexity, security, team expertise.
  • Simplest mechanism that meets all requirements wins.
  • Reuse/standardization → MCP; low latency + simple → direct API; decomposable → agent-to-agent.
  • Eliminate over-engineered and constraint-violating options first.

45.5Progressive Discovery vs Monolithic Context Strategy

Definition — Progressive Discovery
Progressive discovery builds context iteratively: the model starts with a minimal prompt and pulls in more context on demand through dynamic tool calls, lazy-loading only what each step needs. Context grows as the task reveals what's relevant.
Definition — Monolithic Context
Monolithic context pre-loads everything the model might need up front — full documents, complete instructions, all data — into a single large prompt, then answers in one (or few) shots with a static system prompt.

When each strategy is optimal

FactorProgressive DiscoveryMonolithic Context
Latency profileHigher per-task (multiple round-trips) but each call is smallSingle large call; big prefill/TTFT, no round-trips
Accuracy profileFocused context per step → less distraction on large corporaStrong when the full context fits & is all relevant
Token costPays only for context actually neededPays for all pre-loaded tokens every call
Best whenLarge/unknown corpus, tools available, unclear which context is neededSmall, bounded, fully-relevant context; simplicity prized
🔴CRITICAL CONCEPT: Stuffing a huge monolithic context is not free accuracy. Beyond relevance, irrelevant tokens can dilute attention and increase cost and TTFT. Progressive discovery trades extra round-trips for smaller, sharper context — often better on large corpora.

Hybrid approach

Real systems blend both: pre-load stable, always-relevant context (system prompt, core policies, cached prefix) monolithically, and discover volatile or large context progressively via tools/RAG. Prompt caching makes the stable prefix cheap on repeat calls, while progressive tool calls fetch only what each request needs.

💡TIP: Use prompt caching for the monolithic, unchanging portion (system prompt, long shared context) to cut TTFT, and reserve progressive tool calls for per-request, high-variance context. This captures the accuracy of focused context with the latency of a warm cache.

🎯EXAM STRATEGY: Scenario keywords decide it. "Large knowledge base / don't know which docs are relevant / cost-sensitive / tools available" → progressive discovery. 📝 Quick Recall
  • Progressive = lazy, iterative, tool-driven context; lower tokens/cost, higher latency, sharper on big corpora.
  • Monolithic = pre-load everything, one shot; lower latency, higher tokens, dilution risk.
  • Hybrid + prompt caching: monolithic stable prefix + progressive volatile context.
  • Big/unknown corpus → progressive; small/fixed/real-time → monolithic.

45.6Hands-On: Designing an Integration Architecture

Step-by-step methodology

  1. Capture requirements — functional (what it must do), non-functional (latency SLA, accuracy bar, throughput, cost ceiling, security/compliance).
  2. Identify constraints — data residency, existing systems, team skills, budget, deadlines.
  3. Choose model class per task against the accuracy-latency frontier (route easy tasks to small models, hard to large).
  4. Choose connection protocol(s) — MCP for reusable tools/data, direct API for latency-critical paths, agent-to-agent where decomposition helps.
  5. Choose context strategy — monolithic, progressive, or hybrid + prompt caching.
  6. Design the data/tool layer — RAG, tool definitions, permissions, trust boundaries.
  7. Add safety & fallback — timeouts, retries, guardrails, human escalation.
  8. Benchmark & justify — measure the chosen config (per §45.2) and document the tradeoffs.

Worked example — real-time customer support agent

Requirements: interactive latency (streaming, low TTFT), grounded answers from a knowledge base (RAG), ability to take actions via tools (order lookup, refunds) through a reusable connector, and escalation to a human for high-risk or low-confidence cases.

Design decisions:

  • Model: Sonnet-class default for quality within interactive latency; route trivial intents (greetings, FAQ tags) to a Haiku-class model.
  • Protocol: MCP server for order/refund tools (reused by web, mobile, and internal apps; centralized permissions) + direct streaming API for the conversational path.
  • Context strategy: hybrid — monolithic cached system prompt + policies (prompt caching for low TTFT) + progressive RAG retrieval per user question.
  • Safety: confidence/low-certainty and high-risk (refund > threshold, legal, complaint) → escalate to human; timeouts + retries; refund tool gated behind least-privilege permission.

Pre-deployment architecture review checklist

  • ☐ Latency SLA validated at p95/p99 under realistic load (not just mean).
  • ☐ Accuracy measured on a frozen, representative eval set with CIs.
  • ☐ Model routing verified (easy → small, hard → large).
  • ☐ Prompt caching configured for the stable prefix; cache-hit TTFT measured.
  • ☐ Tool permissions least-privilege; trust boundaries documented.
  • ☐ Timeouts, retries, and graceful degradation in place.
  • ☐ Human escalation path for low-confidence / high-risk cases.
  • ☐ Cost/request modeled at projected volume (incl. batch/caching savings).
  • ☐ Observability: log TTFT, total latency, tokens, cost, quality signals.
  • ☐ Fallback behavior if a tool/MCP server is unavailable.
🎯EXAM STRATEGY: For architecture-design scenario questions, structure your answer as requirements → constraints → chosen mechanisms → tradeoff justification. Always name the axis you optimized (latency vs accuracy), the protocol and why, the context strategy and why, and one safety/fallback measure. Answers that only pick a model without justifying protocol, context, and tradeoffs score lower.
💡TIP — common question formats & templates:
• "Design an architecture for X" → use the 4-part template (requirements → constraints → mechanisms → justification).
• "What's wrong with this architecture?" → scan for anti-patterns (over-engineering, wrong axis, no fallback, broad permissions).
• "Which change most improves latency/accuracy/cost?" → map the change to the axis via §45.1's matrix.

§Glossary — Chapter 45 Key Terms

Accuracy-Latency Tradeoff
The tension between response correctness/completeness and response speed; configuration choices move both axes.
Prefill
The phase where the model processes the input prompt; sets Time-To-First-Token. Parallelizable.
Decode
Autoregressive, token-by-token generation of the output; sequential and usually the dominant latency component.
TTFT
Time To First Token — latency until the first output token is emitted; key for perceived responsiveness.
Tokens/sec
Decode throughput; predicts total time for a given output length.
Streaming (SSE)
Server-Sent Events delivering tokens incrementally; improves perceived, not total, latency.
Batch API
Asynchronous, high-throughput, lower-cost processing for non-interactive workloads; higher latency.
Prompt Caching
Reusing a cached prompt prefix to reduce prefill work and TTFT on repeated stable context.
Extended Thinking
Allocating reasoning tokens before the final answer to raise accuracy on hard tasks, at a latency cost.
Temperature / Top-p
Sampling parameters controlling output randomness; affect accuracy/consistency, not latency directly.
MCP
Model Context Protocol — open JSON-RPC client-server standard connecting models to tools, resources, and prompts.
MCP Host / Client / Server
Host runs clients; each client connects to a server that exposes tools/resources/prompts.
stdio / Streamable HTTP
The two standard MCP transports — local subprocess and remote HTTP (with SSE) respectively.
Tools / Resources / Prompts
MCP primitives: invokable functions, readable context, and reusable prompt templates.
Direct API/CLI
Calling Claude straight through the Messages API/SDK/CLI; lowest overhead, app owns orchestration.
Agent-to-Agent
Multiple coordinating agents; common orchestrator–subagent pattern with delegation and synthesis.
Orchestrator–Subagent
Lead agent decomposes and delegates subtasks to specialized workers with isolated context.
Trust Boundary
The security perimeter between agents/components; enforce least-privilege tool access.
Progressive Discovery
Iterative, lazy context building via dynamic tool calls; sharper context, more round-trips.
Monolithic Context
Pre-loading all context into a single large prompt for one-shot answering.
Efficient Frontier
The curve of maximum accuracy achievable at each latency/cost budget.

§Chapter Summary — Top 10 Exam Takeaways

  1. There is no universally best config — place each workload deliberately on the accuracy-latency frontier for its stated requirement.
  2. Output token length is the biggest controllable latency driver; decode is sequential, prefill is parallel.
  3. Prompt clarity is the best accuracy-per-token lever; streaming improves perceived (not total) latency.
  4. Justify configs with the metric matching the requirement (TTFT for interactive, cost/request at scale) and report percentiles, not just means.
  5. Overlapping confidence intervals = a tie; don't over-claim tiny accuracy differences from small eval sets.
  6. MCP = open JSON-RPC client-server standard (tools/resources/prompts) over stdio or streamable HTTP — an abstraction choice, not an accuracy lever.
  7. Direct API/CLI = lowest overhead, best for simple, latency-critical integrations; agent-to-agent = highest capability & latency for decomposable tasks.
  8. Pick the simplest mechanism that meets all requirements; eliminate over-engineered and constraint-violating options first.
  9. Progressive discovery suits large/unknown corpora (lower tokens, sharper context); monolithic suits small, fixed, latency-critical context — hybrid + caching often wins.
  10. Design architectures as requirements → constraints → mechanisms → tradeoff justification, with least-privilege tools, fallbacks, and human escalation.

§Practice Questions

Click each question to reveal the explained answer.

Q1. A user-facing chat feature reports "slow responses." Which change most reliably reduces total latency?

Type: MCQ · §45.1

A. Increase temperature   B. Reduce max_tokens / output length   C. Add more few-shot examples   D. Switch to the Batch API

Correct: B.

Decode is sequential and per-token, so output length is the dominant controllable latency driver. Temperature (A) barely affects latency; more few-shot (C) adds input tokens; Batch API (D) increases latency and is for non-interactive workloads.

Q2. An architect claims "Opus is more accurate, so we should use it." Which critique is strongest?

Type: MCQ · §45.2

A. Opus is never more accurate   B. The claim lacks a measured metric tied to the requirement and ignores the latency/cost tradeoff   C. Accuracy can't be measured   D. Temperature should be raised instead

Correct: B.

Data-driven justification names a specific metric on a representative eval set and acknowledges the tradeoff. Blanket "more accurate" with no evidence or cost/latency consideration is exactly the weak pattern the exam flags.

Q3. You need a database connector that will be reused by web, mobile, and internal tools, with centralized permissions. Which mechanism?

Type: MCQ · §45.3 / §45.4

A. Direct API inline tool use   B. MCP   C. Agent-to-agent   D. Batch API

Correct: B (MCP).

"Reused by multiple apps" + "centralized permissions" + "standardized connector" are MCP keywords — write the server once, reuse across hosts. Inline API tool use (A) would duplicate code per app.

Q4. ⚠️ Trap: "Connect Claude to your CRM database." Both direct API tool use and MCP appear valid. What breaks the tie?

Type: Scenario · §45.4

Answer: The qualifying modifiers.

If the scenario says "reused by many teams / standardized / auditable permissions" → MCP. If it says "single service, lowest latency, simplest to ship" → direct API. Read the modifiers around the verb, not just "connect to a database." Choosing the more powerful option by default is the trap.

Q5. A research assistant must analyze hundreds of documents in parallel with specialized subtasks. Which pattern fits best?

Type: MCQ · §45.3

A. Monolithic single call   B. Direct API single agent   C. Agent-to-agent (orchestrator–subagents)   D. Batch API only

Correct: C.

"Parallel," "specialized subtasks," and "many documents" signal orchestrator–subagent decomposition with isolated contexts. Capability outweighs the higher latency here.

Q6. Your system re-sends the same 8k-token policy prompt on every request. Which change most reduces TTFT without hurting accuracy?

Type: MCQ · §45.1 / §45.5

A. Lower temperature   B. Enable prompt caching for the stable prefix   C. Increase max_tokens   D. Switch to agent-to-agent

Correct: B.

A stable, repeated prefix is the ideal prompt-caching target — cache hits cut prefill work and TTFT with no accuracy change. The other options don't address the repeated-prefix cost.

Q7. You have a very large, unfamiliar knowledge base and don't know which documents are relevant per query, and cost matters. Context strategy?

Type: Scenario · §45.5

Answer: Progressive discovery (with RAG).

Lazy, iterative retrieval loads only the context each step needs — lower tokens/cost and sharper context on a large corpus. Monolithic pre-loading would be costly and risk attention dilution.

Q8. Which statement about streaming is correct?

Type: MCQ · §45.1

A. Streaming reduces total latency   B. Streaming improves perceived latency but not total time   C. Streaming increases accuracy   D. Streaming replaces the need for caching

Correct: B.

Tokens are still decoded sequentially; the total wall-clock time is unchanged. Streaming just surfaces tokens as they're produced, improving responsiveness. A common exam distractor claims it cuts total latency.

Q9. For a high-volume, non-interactive ticket-classification job where cost matters most, which combination is best?

Type: MCQ · §45.2

A. Opus + streaming   B. Haiku-class + Batch API + temperature 0.0   C. Agent-to-agent + Opus   D. Sonnet + extended thinking

Correct: B.

Classification is easy, so a small model preserves accuracy; the Batch API cuts cost for async work; temperature 0.0 maximizes consistency. The others over-serve an easy task and raise cost/latency needlessly.

Q10. During architecture review, latency looks fine on average but users still complain. What did the review most likely miss?

Type: Scenario · §45.2 / §45.6

Answer: Tail latency (p95/p99).

A good mean can hide a bad tail. Real user experience and SLAs are governed by high percentiles, so the review should validate p95/p99 under realistic load, not just the average.

Q11. Which is an anti-pattern in integration mechanism selection?

Type: MCQ · §45.4

A. Direct API for a simple latency-critical call   B. MCP for a reusable multi-app connector   C. Agent-to-agent for a single trivial tool call   D. Hybrid context + caching for a repeated prefix

Correct: C.

Using a multi-agent orchestration for one trivial tool call adds latency, cost, and coordination complexity with no benefit — the classic over-engineering anti-pattern. The others are appropriate matches.

Q12. A medical-summary feature must be highly accurate and can tolerate a few seconds of latency. Best configuration direction?

Type: Scenario · §45.1

Answer: Accuracy-first.

"Medical" + "highly accurate" + latency-tolerant signal accuracy optimization: larger model class, temperature ≈ 0.0, structured output, possibly extended thinking, with quality validated on a representative eval set. Latency is a secondary constraint here.
