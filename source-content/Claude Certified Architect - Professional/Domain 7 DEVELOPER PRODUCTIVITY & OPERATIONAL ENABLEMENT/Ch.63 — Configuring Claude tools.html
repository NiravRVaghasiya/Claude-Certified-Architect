63.1 Claude Code Setup for Team Environments

🧭 Concept Overview

Claude Code is Anthropic's agentic coding tool that runs in the terminal/IDE. For an individual it "just works" with a login; for a team the challenge is consistency and governance — everyone should get the same context, the same guardrails, and the same tool access regardless of which machine they're on.

Definition — Settings Hierarchy Claude Code reads configuration from multiple settings.json layers that cascade and override one another. Team standardization works by pushing shared config into version-controlled project scope and locking policy into enterprise-managed scope, while leaving personal preferences at the user scope.

The four typical layers, from highest precedence to lowest:

  1. Enterprise managed policy — deployed by IT/admins; cannot be overridden by users.
  2. Command-line flags — per-invocation overrides.
  3. Project settings — .claude/settings.json (shared, committed) and .claude/settings.local.json (personal, git-ignored).
  4. User settings — ~/.claude/settings.json (applies to all your projects).

⚙️ Key Configuration

.claude/settings.json (shared, committed to the repo)
{
  "permissions": {
    "allow": ["Read", "Edit", "Bash(npm run test:*)"],
    "deny":  ["Read(./.env)", "Bash(rm -rf:*)"]
  },
  "env": {
    "NODE_ENV": "development"
  },
  "model": "claude-sonnet-4-5"
}
Typical repo layout for a team-ready project
my-service/
├── .claude/
│   ├── settings.json        # shared team config (committed)
│   ├── settings.local.json  # personal overrides (git-ignored)
│   ├── skills/              # team Agent Skills
│   └── commands/            # custom slash commands
├── .mcp.json                # shared MCP servers (committed)
├── CLAUDE.md                # shared project memory (committed)
└── src/

Higher in the chain wins. Enterprise policy is the only layer users cannot override — that's the lever admins use to enforce non-negotiable rules.

💡 Tips & Tricks

Best Practices
  • Commit .claude/settings.json, .mcp.json, and CLAUDE.md so every teammate inherits identical context on git clone.
  • Git-ignore .claude/settings.local.json — that's the escape hatch for personal preferences without polluting the shared config.
  • Use the enterprise managed settings file for anything security-critical (deny rules, blocked commands) — it is the only layer users can't loosen.
  • Pin the model in shared settings so results are reproducible across the team.
  • Onboard new hires with a single git clone → claude flow; avoid tribal "run these 12 setup steps" docs.

⚡ Exam Strategy

⚡ Exam Angle Expect precedence-ordering questions ("Which setting wins if project and enterprise conflict?") and scenario questions ("A user changed a deny rule locally but it's still blocked — why?").
  • Watch for distractors that reverse the hierarchy — enterprise policy is highest, user settings lowest.
  • Distinguish settings.json (shared, committed) from settings.local.json (personal, git-ignored). Swapping these two is a classic trap.
  • Mnemonic — "E-C-P-U": Enterprise → CLI → Project → User. "Every Company Prefers Uniformity."

63.2 Standardizing CLAUDE.md, Rules & Skills Across Teams

🧭 Concept Overview

Three artifacts shape how Claude behaves inside a repo. Standardizing them is what turns "everyone uses Claude differently" into "the whole team gets the same assistant."

Definition — The Three Standardization Layers
  • CLAUDE.md (Memory) — a Markdown file automatically loaded as context. Holds project purpose, tech stack, conventions, and frequently used commands.
  • Rules — behavioral directives (do / don't) expressed as instructions inside CLAUDE.md (e.g., "Always run tests before committing"). They are guidance, not hard-enforced security — enforcement lives in permissions (63.4).
  • Skills (Agent Skills) — packaged folders containing a SKILL.md plus optional scripts/resources that give Claude a reusable, invokable capability (e.g., deploy-staging).

Memory scopes mirror the settings hierarchy: a shared project ./CLAUDE.md (committed), and a personal ~/.claude/CLAUDE.md (applies to all your projects). CLAUDE.md files also support @path imports to pull in shared fragments, so teams can factor common conventions into one canonical file.

⚙️ Key Configuration / Syntax

CLAUDE.md — team template
# Team CLAUDE.md Template

## Project Context
- Purpose: Payments microservice (Node 20 + TypeScript)
- Tech stack: Express, Prisma, PostgreSQL
- Coding conventions: ESLint airbnb-base, 2-space indent

## Rules
- Always run `npm run test` before committing.
- Never modify `/infra` without a reviewer's approval.
- Prefer async/await over raw Promises.

## Common Commands
- Build:   `npm run build`
- Test:    `npm run test`
- Migrate: `npm run db:migrate`

## Shared conventions (imported)
@./docs/engineering-standards.md
.claude/skills/deploy-staging/SKILL.md — a shared Agent Skill
---
name: deploy-staging
description: Deploy the current branch to the staging environment.
  Use when the user asks to deploy, ship, or push to staging.
---

# Deploy to Staging

1. Confirm tests pass (`npm run test`).
2. Build the artifact (`npm run build`).
3. Run `./scripts/deploy.sh staging`.
4. Report the deployment URL back to the user.
Note — SKILL.md front-matter A Skill's name and description live in YAML front-matter. The description is the trigger signal — Claude reads it to decide when the skill is relevant, so write it in terms of when to use the skill, not just what it does.

💡 Tips & Tricks

Best Practices
  • Keep CLAUDE.md concise and specific — it's loaded into every context. Bloated memory wastes tokens and dilutes the important rules.
  • Factor common standards into one file and pull them in with @import instead of copy-pasting across repos.
  • Treat CLAUDE.md and skills as code: review changes in PRs so behavior shifts are intentional and visible.
  • Write skill description fields around triggers ("Use when…") so the right skill fires automatically.
  • Common misconfiguration: putting secrets or credentials in CLAUDE.md — it's plain text and committed. Keep secrets in env/secret managers.

⚡ Exam Strategy

⚡ Exam Angle Questions test whether you can match the artifact to the job: which of memory / rules / skills solves a given standardization problem.
  • Distractor to watch: conflating a "Rule" (guidance in CLAUDE.md) with a "permission deny rule" (hard-enforced in settings — 63.4). If the scenario needs enforcement, the answer is permissions, not CLAUDE.md text.
  • Remember Skills are folders with a SKILL.md; the description drives invocation.
  • Mnemonic — "M-R-S": Memory tells Claude what it knows, Rules tell it how to behave, Skills tell it what it can do.

63.3 MCP Server Configuration for Shared Infrastructure

🧭 Concept Overview

The Model Context Protocol (MCP) is an open standard for connecting Claude to external tools and data sources (databases, ticketing systems, internal APIs) through MCP servers. For teams, the goal is that everyone connects to the same shared infrastructure with the same configuration.

Definition — MCP Scopes MCP servers can be registered at three scopes, which determine who sees them and whether they're committed:
  • local — private to you, in the current project only (default). Not shared.
  • project — stored in a committed .mcp.json at the repo root; shared with everyone who clones the repo.
  • user — available to you across all your projects, but not shared with teammates.
For team infrastructure, project scope (.mcp.json) is the answer.

Servers connect over a transport: stdio (local subprocess), sse (Server-Sent Events, HTTP-based), or http (streamable HTTP). Remote/shared servers typically use sse or http.

⚙️ Key Configuration / Syntax

.mcp.json (project scope — committed, shared with the team)
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres",
               "postgresql://localhost/mydb"],
      "env": { "PGSSLMODE": "require" }
    },
    "internal-api": {
      "type": "http",
      "url": "https://mcp.internal.example.com/api",
      "headers": { "Authorization": "Bearer ${API_TOKEN}" }
    }
  }
}
CLI equivalents (adding servers by scope)
# Shared with the team (writes to .mcp.json)
claude mcp add --scope project postgres \
  npx -y @modelcontextprotocol/server-postgres postgresql://localhost/mydb

# Just for me, in this project (default scope)
claude mcp add --scope local scratch-tool ./run.sh

# Remote server over HTTP transport
claude mcp add --scope project --transport http internal-api \
  https://mcp.internal.example.com/api
Note — stdio vs http/sse servers A stdio server uses command + args (Claude launches it as a subprocess). A remote server uses type + url (and optional headers). Mixing these — e.g., putting a url on a command-style entry — is a common config error.

💡 Tips & Tricks

Best Practices
  • Never hard-code secrets in .mcp.json — it's committed. Use environment-variable expansion like ${API_TOKEN} and inject the real value at runtime.
  • Commit .mcp.json so a fresh clone connects to the same servers automatically.
  • Because project-scoped servers run code from the repo, Claude Code typically prompts each user to approve them the first time — this is a safety feature, not a bug.
  • Prefer http/sse transports for centrally hosted shared infrastructure; use stdio for local tooling.
  • Keep server names stable — permission rules and skills may reference them by name.

⚡ Exam Strategy

⚡ Exam Angle MCP questions frequently test which scope shares a server with the team and which fields are required for a given transport.
  • Distractor to watch: answers that swap scope values — user (all my projects, private) vs project (this repo, shared). If the scenario says "so the whole team gets it," the answer is project.
  • stdio → needs command/args; remote → needs type/url. Watch for entries that mismatch these.
  • Remember the file name: shared servers live in .mcp.json (not settings.json).
  • Mnemonic — "PUL" = Project(shared) · User(all-mine) · Local(here-only). "Publish to the team, User is universal-to-me, Local stays put."

63.4 Access Control and Permission Management

🧭 Concept Overview

Permissions govern what actions Claude may take without asking — reading files, editing code, running shell commands, calling MCP tools, fetching URLs. Team governance combines permission rules (allow/ask/deny per tool) with permission modes (the overall interaction posture) and enterprise-managed policy (admin-enforced, non-overridable).

Definition — Two Complementary Mechanisms
  • Permission rules — in settings.json under permissions, with allow, ask, and deny lists. Rules are patterns like Bash(npm run test:*) or Read(./.env). deny always wins.
  • Permission modes — the session posture: default (ask on first use), acceptEdits (auto-accept file edits), plan (read-only planning, no changes), and bypassPermissions (skip prompts — use with extreme caution).

⚙️ Key Configuration / Syntax

.claude/settings.json — permission rules
{
  "permissions": {
    "allow": [
      "Read",
      "Edit",
      "Bash(npm run test:*)",
      "Bash(git status)"
    ],
    "ask": [
      "Bash(git push:*)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./secrets/**)",
      "Bash(rm -rf:*)",
      "WebFetch"
    ],
    "defaultMode": "default"
  }
}
Precedence within permissions Evaluation order is deny → ask → allow. A deny match blocks the action outright even if an allow rule would also match. This is why security-critical restrictions belong in deny, ideally at the enterprise-managed layer where users can't remove them.

💡 Tips & Tricks

Best Practices
  • Least privilege: allow only the specific commands a team needs (e.g., Bash(npm run test:*)) rather than a blanket Bash(*).
  • Put hard security limits (deny secrets, deny destructive commands) in enterprise-managed settings so no local override can loosen them.
  • Use plan mode for code review / exploration where Claude should not change anything.
  • Reserve bypassPermissions for trusted, sandboxed CI contexts — never as a default for humans.
  • Use ask (not allow) for irreversible operations like git push or deploys, so there's a human checkpoint.

⚡ Exam Strategy

⚡ Exam Angle This is the most config-debugging-heavy topic. Expect "Claude did X even though we allowed it — how do we stop it?" (answer: add a deny, ideally in managed policy) and "why is a permitted command still blocked?" (answer: deny beats allow).
  • Golden rule: deny > ask > allow. If a question pits allow against deny, deny wins.
  • Distractors to watch: mode names — acceptEdits (auto-edits files) vs bypassPermissions (skips all prompts) vs plan (read-only). Don't confuse them.
  • Remember the enforcement boundary: Rules in CLAUDE.md are guidance; permission rules are enforcement.
  • Mnemonic — "DAA": Deny Ask Allow — evaluated top-down, deny first.

63.5 Hands-On: Setting Up Claude for a Development Team

🧭 Concept Overview

This section ties 63.1–63.4 into one end-to-end rollout. The scenario: a 6-person backend team wants every engineer to get identical context, shared tools, and enforced guardrails from a single git clone.

The rollout in one sentence Commit the shared config (CLAUDE.md + .claude/settings.json + .mcp.json + skills) into the repo, enforce the non-negotiables through enterprise-managed policy, and let individuals layer personal preferences via git-ignored local files.

⚙️ Key Configuration / Syntax

Step-by-step rollout commands
# 1. Create the shared team memory
$ cat > CLAUDE.md <<'EOF'
# Payments Service
## Rules
- Run `npm run test` before committing.
- Never touch /infra without review.
EOF

# 2. Commit shared permission rules
$ mkdir -p .claude
$ cat > .claude/settings.json <<'EOF'
{ "permissions": {
    "allow": ["Read","Edit","Bash(npm run test:*)"],
    "deny":  ["Read(./.env)","Bash(rm -rf:*)"] },
  "model": "claude-sonnet-4-5" }
EOF

# 3. Add a shared MCP server at project scope
$ claude mcp add --scope project postgres \
    npx -y @modelcontextprotocol/server-postgres $DB_URL

# 4. Add a shared skill
$ mkdir -p .claude/skills/deploy-staging
$ $EDITOR .claude/skills/deploy-staging/SKILL.md

# 5. Ignore personal overrides
$ echo ".claude/settings.local.json" >> .gitignore

# 6. Commit & push — teammates now inherit everything
$ git add CLAUDE.md .claude/settings.json .mcp.json .claude/skills
$ git commit -m "chore: standardize Claude Code for the team"
$ git push
managed-settings.json — deployed by admins (enterprise-enforced)
{
  "permissions": {
    "deny": ["Read(./secrets/**)", "Bash(curl:*)", "WebFetch"]
  }
}

💡 Tips & Tricks

Best Practices
  • Test the clean-clone path: clone into a fresh directory and confirm a new engineer gets working memory, servers, and guardrails with zero manual steps.
  • Roll config out through pull requests so changes to team behavior are reviewed like code.
  • Keep secrets in env vars / a secret manager; reference them as ${VAR} in .mcp.json.
  • Document the one-time MCP server approval prompt in onboarding so new hires aren't surprised.
  • Layer responsibilities: admins own managed policy, leads own repo config, engineers own their local overrides.

⚡ Exam Strategy

⚡ Exam Angle This section is tested as integrated scenarios: "A new engineer cloned the repo but isn't getting the team's deny rules — what's wrong?" or "Where should a non-negotiable security rule live?"
  • Consistency check: the permission model here must match 63.4 — deny wins, and enterprise-managed policy overrides everything (per 63.1).
  • Distractor to watch: putting a security guarantee in CLAUDE.md "Rules" (guidance only) instead of a deny permission or managed policy (enforcement).
  • If a shared server "doesn't work" for a teammate → likely the one-time approval prompt hasn't been accepted, or it was added at local/user scope instead of project.
  • Mnemonic — "Clone → Approve → Go": the three things a new teammate does to inherit the full environment.

Sample Exam Q&A

Original, illustrative questions for practice — not from any real Anthropic exam.

Q1 · 63.1 · MCQ A developer edits a deny rule in .claude/settings.json to permit a command, but Claude still refuses to run it. Enterprise IT deployed a managed policy denying that command. Which setting takes effect?
A. The project settings.json edit — project scope wins.
B. The user's settings.local.json.
C. The enterprise-managed policy deny rule.
D. Neither; the command runs by default.
Show answer & reasoning
Answer: C. Enterprise-managed policy is the highest layer in the precedence chain (E-C-P-U) and cannot be overridden by project or user settings. Additionally, deny wins over allow. Both principles point to the managed deny rule remaining in force.
Q2 · 63.3 · Scenario Your team wants every engineer to automatically get access to a shared PostgreSQL MCP server when they clone the repo. Which scope should you use, and where is it stored?
A. user scope, stored in ~/.claude/settings.json.
B. local scope, stored in local project state.
C. project scope, stored in a committed .mcp.json.
D. project scope, stored in .claude/settings.json.
Show answer & reasoning
Answer: C. Only project scope shares a server with everyone on the repo, and it is stored in a committed .mcp.json at the repo root. Distractor D swaps the file (MCP servers go in .mcp.json, not settings.json); A is private-to-user; B is private-to-you-in-this-project.
Q3 · 63.4 · Config-debug A team's permissions block lists Bash(git push:*) in both allow and deny. What happens when Claude tries to push?
A. It pushes — allow and deny cancel out to allow.
B. It is blocked — deny takes precedence over allow.
C. It prompts the user because of the conflict.
D. It errors and refuses to start the session.
Show answer & reasoning
Answer: B. Permission evaluation is deny → ask → allow ("DAA"). A matching deny rule blocks the action outright, regardless of any allow match. To require a checkpoint instead of a hard block, you'd remove the deny and place the pattern under ask.
Q4 · 63.2 / 63.4 · Scenario A lead adds "Never delete production data" to the ## Rules section of CLAUDE.md, but Claude still runs a destructive command in a session. What is the most robust fix?
A. Rephrase the rule in CLAUDE.md more forcefully.
B. Add the destructive command pattern to the deny list (ideally in enterprise-managed policy).
C. Move the rule to ~/.claude/CLAUDE.md.
D. Switch to acceptEdits mode.
Show answer & reasoning
Answer: B. CLAUDE.md "Rules" are behavioral guidance, not enforcement. Hard prevention requires a deny permission rule, and putting it in enterprise-managed policy ensures no local override can loosen it. This mirrors the 63.4 enforcement-vs-guidance distinction. (D is the opposite of safe — it auto-accepts edits.)
Q5 · 63.5 · Scenario A new engineer cloned the repo and started Claude, but the shared MCP servers appear unavailable. The .mcp.json is present and correct. What is the most likely cause?
A. MCP servers can never be shared via git.
B. The engineer hasn't approved the project-scoped servers on first use.
C. .mcp.json must be renamed to settings.json.
D. The servers were added at enterprise scope, which blocks engineers.
Show answer & reasoning
Answer: B. Project-scoped MCP servers run code defined in the repo, so Claude Code typically requires each user to approve them once before they activate — a deliberate safety feature. A is false (project scope is exactly how you share them), C is false (the file is correctly named), and "enterprise scope" for MCP servers is not a standard scope value.
