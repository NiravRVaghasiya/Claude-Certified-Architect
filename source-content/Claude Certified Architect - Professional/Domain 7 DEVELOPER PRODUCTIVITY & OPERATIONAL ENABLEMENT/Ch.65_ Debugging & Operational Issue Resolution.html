65.1 Debugging LLM-Powered Systems: Strategies and Tools

Debugging an LLM application differs from debugging traditional software in one crucial way: the model is non-deterministic and opaque. The same prompt can yield different outputs, and there is no stack trace inside the model. Effective debugging therefore focuses on everything around the model — inputs, context assembly, parameters, tool calls, and outputs — and treats the model as a probabilistic component you observe rather than step through.

A systematic debugging methodology

Follow a disciplined loop rather than randomly tweaking the prompt. The canonical cycle is Isolate → Reproduce → Hypothesize → Test → Fix → Verify, feeding back into monitoring.

  • Isolate — Determine which layer owns the bug: input/retrieval, prompt template, model parameters, tool execution, or output parsing. Narrow before you dig.
  • Reproduce — Capture the exact request (full messages array, system prompt, temperature, max_tokens, model version, tool definitions). Non-determinism makes this the hardest step — set temperature=0 and pin the model version to increase reproducibility.
  • Hypothesize — Form a single, testable theory (e.g., "the retrieved context is being truncated before it reaches the model").
  • Test — Change one variable at a time. Use an eval harness so results are measured, not eyeballed.
  • Fix & Verify — Apply the change and confirm against a regression set, not just the single failing case.

The debugging toolbox

  • Structured logging — Log the full request/response pair, token usage, latency, model version, and stop_reason. Never log raw secrets or full PII.
  • Tracing / observability — Distributed tracing (e.g., OpenTelemetry-style spans) around each API call, retrieval step, and tool invocation lets you see where latency and errors originate. Third-party LLM observability platforms (LangSmith, Langfuse, Arize Phoenix, etc.) specialize in capturing prompt/response traces.
  • Prompt inspection — Render and inspect the fully assembled prompt after template substitution and context injection — the bug is often in what actually reached the model, not the template.
  • Eval harnesses — Automated test suites that score outputs (exact-match, LLM-as-judge, rubric grading) against a curated dataset so you can measure regressions objectively.
  • Anthropic Console & token counting — Use the Console's Workbench to iterate on prompts interactively, and the token-counting endpoint to measure input size before sending.
💡 Tips & Tricks:
  • Set temperature=0 while debugging to make behavior as deterministic as possible, then restore production settings once fixed.
  • Always inspect stop_reason — "max_tokens" means the model was cut off (raise max_tokens or shorten the prompt), "end_turn" means it finished naturally.
  • Log a request ID with every call so a user complaint maps directly to a stored trace.
🎯 Exam Strategy: Questions here often present a symptom and ask for the first or best diagnostic step. The expected answer is almost always "reproduce with logging/tracing and inspect the assembled prompt," not "immediately rewrite the prompt." Watch for distractors that jump to a fix before isolating the cause. When you see "non-deterministic," the tie-breaker answer usually involves temperature=0 and pinning the model version.
⚠️ Common Pitfalls:
  • Judging a fix on a single lucky run — non-determinism means you must test across many runs / a dataset.
  • Debugging the prompt template instead of the fully-rendered prompt that the model actually received.
  • Logging secrets, API keys, or unredacted PII in your traces.

65.2 Common Operational Issues and Their Root Causes

Operational issues in Claude applications cluster into a handful of recurring categories. Recognizing the symptom → root cause → resolution chain quickly is the core skill this section tests.

Table 65.2 — Common operational issues, symptoms, root causes, and resolutions
IssueSymptomsRoot CauseResolution
Context window overflow Truncated or missing context; API returns an input-too-large error; earlier turns "forgotten" Total input tokens exceed the model's context window (e.g., 200K for Claude) Chunk, summarize, or window the conversation; use retrieval to inject only relevant context; count tokens before sending
Output truncation Response cut off mid-sentence; JSON that won't parse; stop_reason: "max_tokens" max_tokens set too low for the required output Raise max_tokens; ask for more concise output; stream and continue if needed
Rate limiting HTTP 429 rate_limit_error; bursts of failures under load Exceeding requests-per-minute (RPM) or tokens-per-minute (input/output TPM) limits Exponential backoff with jitter; honor retry-after header; queue/throttle; request a limit increase or use the Message Batches API for bulk work
Server overload HTTP 529 overloaded_error; intermittent failures The API is temporarily overloaded (transient, server-side) Retry with exponential backoff; degrade gracefully; consider a fallback model
High latency Slow responses; timeouts; poor UX Large input/output token counts, oversized context, or network/gateway bottleneck — not always the model Stream responses; trim context; use a smaller/faster model where adequate; enable prompt caching for repeated prefixes
Hallucination / inaccuracy Confident but wrong answers; fabricated facts, citations, or APIs Missing grounding context; ambiguous prompt; asking beyond model knowledge Ground with retrieval (RAG); instruct the model to say "I don't know"; request citations; add verification/eval checks
Cost spikes Unexpected bill increase; budget alerts firing Bloated prompts, redundant context on every call, retry storms, or a more expensive model than needed Enable prompt caching; trim/summarize context; route simple tasks to smaller models; cap retries; monitor token usage per request
Malformed structured output Invalid JSON; parser exceptions; downstream failures Free-form generation without constraints; truncation Use tool use / structured output; provide a schema and examples; validate and retry on parse failure
Auth / config errors HTTP 401/403; sudden total failure after a deploy Invalid/expired API key, wrong environment, or missing permissions Rotate/verify keys via secret manager; separate keys per environment; fail fast with a clear error
📌 Know your HTTP status codes: 400 invalid_request 401 authentication 403 permission 404 not_found 413 request too large 429 rate_limit 500 api_error 529 overloaded
💡 Tips & Tricks:
  • 429 vs 529: 429 means you hit a rate limit (back off + throttle); 529 means the server is overloaded (back off + retry). Both are retriable; 4xx like 400/401 are usually not.
  • Latency is frequently driven by output tokens — the model generates sequentially, so shorter outputs are faster. Trim before blaming the model.
  • Prompt caching dramatically cuts both latency and cost when a large, stable prefix (system prompt, docs) is reused across calls.
🎯 Exam Strategy: Expect "match the symptom to the root cause" and "which resolution is most appropriate" questions. Memorize the status-code semantics — especially the 429 (rate limit) vs 529 (overloaded) distinction, a classic trap. When a question says "cut off mid-response," the keyword is stop_reason: max_tokens. When it says "forgets earlier conversation," think context-window management.
⚠️ Common Pitfalls:
  • Assuming all latency is model-side — a gateway, network, or oversized retrieval step is often the real culprit.
  • Retrying 4xx errors (e.g., 400/401) — they won't succeed on retry and can cause retry storms.
  • Treating hallucination as a "model bug" rather than a grounding/prompting problem.

65.3 Incident Response for AI Systems

An incident is any unplanned degradation of service quality — including AI-specific degradations like a drop in answer quality that never throws an error. AI incident response follows the classic lifecycle but adds considerations unique to non-deterministic, model-driven systems.

The incident lifecycle

Detect→ Triage→ Contain→ Resolve→ Communicate→ Review
  • Detect — Alerts on latency, error rate, cost, and quality (eval scores, thumbs-down rate, guardrail triggers). AI systems need quality monitoring, not just uptime monitoring.
  • Triage — Assign a severity (SEV) based on user impact and scope. Designate an incident commander for higher severities.
  • Contain — Stop the bleeding before root-causing: roll back the last deploy, revert a prompt change, switch to a fallback model, or flip a feature kill-switch.
  • Resolve — Apply and verify the actual fix against a regression/eval set.
  • Communicate — Keep stakeholders and users informed throughout with status, impact, and ETA.
  • Review — Feed into a blameless post-mortem (Section 65.4).

AI-specific incident considerations

  • Model / config drift — Behavior can change when you upgrade the model version, edit the system prompt, or change retrieval data. Always pin model versions in production and treat prompt changes as deploys.
  • Non-determinism — Failures may be intermittent and hard to reproduce. Rely on aggregate metrics and captured traces, not one-off reproduction.
  • Silent failures — The most dangerous AI incidents throw no errors: the system returns confident, well-formed, wrong answers. Only quality evals and user feedback catch these — uptime dashboards stay green.
  • Upstream/data drift — Stale or corrupted retrieval sources degrade answers without any code change.
💡 Tips & Tricks:
  • Build a kill-switch and fallback path before you need them — a degraded static response beats an outage.
  • Because prompt and model changes are effective "deploys," version them and make them instantly revertible.
  • Contain first, root-cause later. Restoring service is the priority during an active incident.
🎯 Exam Strategy: Look for the ordering trap: the correct first action in an active incident is usually contain (rollback/mitigate), not "find the root cause." Root-causing belongs in the post-mortem. "Silent failure" and "model drift" are frequently the correct answers to "which AI-specific risk is described." Remember that AI monitoring must include quality signals, not just availability.
⚠️ Common Pitfalls:
  • Only monitoring uptime/latency and missing silent quality regressions.
  • Spending an active SEV1 hunting the root cause while users suffer, instead of rolling back first.
  • Not pinning the model version — an upstream model update silently changes behavior.

65.4 Post-Mortem Analysis and Continuous Improvement

A post-mortem (a.k.a. incident retrospective) is a structured, written analysis conducted after an incident is resolved. Its purpose is organizational learning and prevention — not assigning blame.

Post-mortem template

Table 65.4 — Standard blameless post-mortem structure
SectionWhat it captures
SummaryOne-paragraph plain-language description of what happened.
ImpactWho/what was affected, for how long, and by how much (users, requests, cost, quality drop).
TimelineTimestamped sequence: detection → key actions → resolution.
Root cause(s)The underlying cause(s), reached via techniques like the "5 Whys." Often more than one contributing factor.
Detection & responseHow it was found, how long detection took, what went well and poorly in the response.
Action itemsConcrete, owned, dated preventive tasks (tracked to completion).
Lessons learnedWhat the team now understands that it didn't before.

Blameless culture principles

  • Focus on systems, not individuals. Assume everyone acted reasonably with the information they had; ask "how did the system allow this?" not "who broke it?"
  • Psychological safety — People must feel safe reporting mistakes; blame drives incidents underground and prevents learning.
  • Actionable outcomes — Every post-mortem ends with owned, dated, tracked action items — otherwise the same incident recurs.
  • Share widely — Publish post-mortems so the whole org learns, not just the responders.

Feedback loop into the system

Continuous improvement means the learnings flow back into concrete safeguards:

Incident & Post-mortem→ New evals / regression tests→ Better monitoring & alerts→ Prompt / system fixes→ Fewer / smaller incidents
  • Into monitoring — Add an alert that would have caught this incident sooner.
  • Into evals — Turn the failing case into a permanent regression test so the bug can never silently return.
  • Into prompt engineering — Refine the system prompt or add guardrails/output validation.
  • Into system design — Add retries, fallbacks, caching, or better context management at the architecture level.
💡 Tips & Tricks:
  • The single most valuable post-mortem output is a new automated eval capturing the failure — it prevents silent regressions forever.
  • Use the "5 Whys" to push past the surface symptom to a systemic root cause.
  • Track action items in your normal issue tracker with owners and due dates — a post-mortem with no follow-through is theater.
🎯 Exam Strategy: "Blameless" is the keyword — the correct answer always favors systemic causes and psychological safety over individual fault. Watch for distractors that name a person or recommend discipline. A frequently-correct answer to "how do you prevent recurrence?" is "add a regression test / eval" and "improve monitoring." Remember post-mortems happen after resolution, not during the incident.
⚠️ Common Pitfalls:
  • Producing a post-mortem with no owned, dated action items (nothing changes).
  • Stopping at the proximate cause instead of the systemic root cause.
  • Assigning individual blame, which erodes the safety needed for honest reporting.

65.5 Hands-On: Debugging a Production Claude Application

Let's walk through a realistic incident end-to-end, applying the methodology from 65.1–65.4.

The scenario

A customer-support assistant built on the Claude Messages API begins intermittently returning truncated JSON that breaks the downstream parser. Users report "the bot froze." Error dashboards are mostly green; the failures are sporadic.

Step 1 — Reproduce & capture

Pull the traces for the failing request IDs. You notice every failure shares "stop_reason": "max_tokens" and a large retrieved-context payload. Uptime looked fine because the API calls succeeded (HTTP 200) — this is a classic silent failure: valid response, unusable content.

Step 2 — Hypothesize & isolate

Hypothesis: on long conversations, the assembled prompt is large and max_tokens is too low, so the model runs out of output budget mid-JSON. Confirm by inspecting the fully-rendered prompt token count and comparing failing vs passing requests.

Step 3 — Instrument, harden, and fix

Add structured logging, robust retry/backoff for transient 429/529 errors, explicit handling of the max_tokens stop reason, and JSON validation with a bounded retry. Example (Python-style, illustrative):

# Illustrative debugging + hardening for a Claude Messages API call
import time, json, logging, random

logging.basicConfig(level=logging.INFO)
log = logging.getLogger("support-bot")

def call_claude(client, messages, request_id):
    max_retries = 4
    for attempt in range(max_retries):
        try:
            resp = client.messages.create(
                model="claude-sonnet-4-5",   # pin the version
                max_tokens=2048,               # enough budget for full JSON
                temperature=0,                 # deterministic while debugging
                messages=messages,
            )
            # 1) Log the essentials for every call
            log.info(json.dumps({
                "request_id": request_id,
                "stop_reason": resp.stop_reason,
                "input_tokens": resp.usage.input_tokens,
                "output_tokens": resp.usage.output_tokens,
            }))

            # 2) Detect the silent failure explicitly
            if resp.stop_reason == "max_tokens":
                log.warning("Output truncated — raise max_tokens or trim context")
                raise ValueError("truncated_output")

            # 3) Validate structured output before trusting it
            text = resp.content[0].text
            return json.loads(text)          # raises on malformed JSON

        except (RateLimitError, OverloadedError) as e:   # 429 / 529 → retriable
            wait = (2 ** attempt) + random.random()      # backoff + jitter
            log.warning(f"Transient {e}; retry in {wait:.1f}s")
            time.sleep(wait)
        except (ValueError, json.JSONDecodeError) as e:
            log.error(f"Bad output ({e}); retrying with more budget")
            # optionally bump max_tokens / trim context here, then retry

    raise RuntimeError(f"Failed after {max_retries} attempts: {request_id}")

Step 4 — Verify & prevent recurrence

  • Verify against a dataset of long conversations, not just one request.
  • Contain immediately by raising max_tokens (or trimming/summarizing context) in production.
  • Add a regression eval that submits a long-context request and asserts valid JSON with stop_reason == "end_turn".
  • Add an alert on the rate of stop_reason == "max_tokens" so this silent failure is caught automatically next time.
  • Long-term: add context-window management (summarize old turns) so growth can't silently blow the budget.
📌 Note on names: Model identifiers and exact status codes evolve — always confirm the current model string and limits against the official Anthropic documentation. The patterns above (backoff on 429/529, checking stop_reason, validating structured output, adding a regression eval) are what the exam tests, and they remain stable.
💡 Tips & Tricks:
  • Retry only on retriable errors (429/529, transient network) — never blindly retry a 400/401.
  • Add jitter to exponential backoff to avoid a thundering-herd of synchronized retries.
  • Validate structured output at the boundary and fail loudly — don't pass malformed JSON downstream.
🎯 Exam Strategy: Code/scenario questions favor answers that show exponential backoff with jitter, honoring retry-after, checking stop_reason, and validating output. If a snippet retries on every exception, that's the wrong answer — good code distinguishes retriable (429/529) from non-retriable (4xx). Expect "what's wrong with this code?" items where the flaw is a missing backoff or retrying a non-retriable error.
⚠️ Common Pitfalls:
  • Ignoring stop_reason and treating a truncated 200 response as success.
  • Fixed-interval retries with no jitter, amplifying load during an outage.
  • No output validation, so malformed JSON silently corrupts downstream systems.

Chapter Summary / Quick Revision Checklist

Fast pre-exam recall for Chapter 65:

  • Debugging loop: Isolate → Reproduce → Hypothesize → Test → Fix → Verify. Use temperature=0 + pinned model version for reproducibility.
  • Toolbox: structured logging, tracing/observability, prompt inspection (rendered prompt!), and eval harnesses.
  • Status codes: 429 = rate limit (you), 529 = overloaded (server) — both retriable with backoff; 4xx like 400/401 are not.
  • stop_reason: "max_tokens" = truncated (raise budget / trim); "end_turn" = complete.
  • Context overflow: chunk, summarize, retrieve; count tokens before sending.
  • Latency: often output-token or network/gateway driven — not always the model; stream + prompt caching help.
  • Incident lifecycle: Detect → Triage → Contain → Resolve → Communicate → Review. Contain (rollback/fallback) before root-causing.
  • AI-specific risks: model/config drift, non-determinism, and silent failures (green dashboards, wrong answers) — monitor quality, not just uptime.
  • Post-mortems are blameless: systems over individuals; every one ends with owned, dated action items and a new regression eval.
  • Continuous improvement loop: incident → new evals + alerts → prompt/system fixes → fewer incidents.
  • Hardened API calls: exponential backoff + jitter on 429/529, honor retry-after, check stop_reason, validate structured output.
🎯 Final exam reminder: When two answers look correct, prefer the one that (a) contains before root-causing during an incident, (b) distinguishes retriable from non-retriable errors, (c) adds an eval/regression test to prevent recurrence, and (d) blames the system, not a person.
