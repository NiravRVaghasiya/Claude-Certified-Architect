40.1  Claude Model Family: Capabilities, Costs & Latency Profiles

The core architectural tradeoff: intelligence, cost, and speed pull against each other. Understanding the shape of each tier lets you place a workload where it belongs.

The three-tier mental model

Rather than memorizing version strings, reason in tiers. Each tier occupies a different point on the intelligence/cost/latency surface. A production system typically routes different tasks to different tiers rather than sending everything to the most capable model.

Model Tier Relative Capability Relative Cost Relative Latency Ideal Use Cases
Lightweight / Fast
(e.g. Haiku class)		 Good for well-scoped tasks; less depth on ambiguous, multi-step reasoning 💰 ⚡⚡⚡ lowest High-volume classification, extraction, routing, moderation, simple Q&A, real-time UX
Balanced
(e.g. Sonnet class)		 Strong general reasoning, coding, and instruction-following at moderate cost 💰💰 ⚡⚡ moderate Coding assistants, RAG chat, summarization, most agent steps, general-purpose workloads
Most Capable
(e.g. Opus class)		 Highest reasoning depth; best on ambiguous, long-horizon, high-stakes problems 💰💰💰 ⚡ highest Complex multi-step reasoning, hard agentic workflows, research, nuanced analysis, orchestration/planning

Reading the tableMore 💰 = more expensive per token. More ⚡ = faster (lower latency). Capability and cost tend to rise together, while speed moves in the opposite direction — that inverse relationship is the tradeoff you are architecting around.

Visualizing the tradeoff — Intelligence vs Cost-efficiency vs Speed

The radar plot shows why no single tier "wins." A larger area on one axis usually means a smaller area on another. Illustrative values

  • Lightweight / FastWide on speed & cost-efficiency, narrow on intelligence
  • BalancedThe compromise tier — solid on all three

Note: "Cost-efficiency" is drawn so that outward = cheaper. A tier that reaches far on this axis costs less per token.

💡 Tips & Tricks
  • Think in tiers, not names — model IDs change, but the fast / balanced / capable structure is stable and is what exam scenarios test.
  • Cost is driven by tokens × price-per-token. A cheaper tier that needs a longer prompt or more retries can end up costing more than a pricier tier that one-shots the task.
  • Latency has two parts: time-to-first-token (matters for streaming UX) and total generation time (matters for batch throughput). Optimize for the one your product actually feels.
🎯 Exam Strategy Expect questions that hand you a workload profile ("10M short support tickets/day, sub-second response needed") and ask for the right tier. Match on the dominant constraint first: high volume + latency-sensitive → fast tier; ambiguous reasoning + accuracy-critical → capable tier. Distractor answers usually flip the intelligence/cost relationship or quote a fake exact price — eliminate any option stating a precise dollar figure as if it were universal.

40.2  Selecting Models Based on Task Complexity and Budget

A repeatable selection framework beats intuition. Start from task complexity, then apply budget and latency as filters.

The decision framework

Work top-down. Anchor on what the task requires, then down-shift to a cheaper tier only if you can prove it still meets your quality bar via evaluation.

START: Characterize the task
Is the task well-defined with a narrow, verifiable output?
Does it need multi-step reasoning, planning, or tool orchestration?
Route toLightweight / Fast
Narrow, high-volume, latency-sensitive, easily verified
Route toBalanced
General reasoning, coding, RAG, typical agent steps
Route toMost Capable
Ambiguous, long-horizon, high-stakes, hard planning

Complexity → tier mapping

Task complexity signalRecommended starting tierBudget posture
Single-label output, deterministic-ish, easy to verifyLightweight / FastOptimize for throughput & cost
Open-ended generation, moderate reasoning, codingBalancedBalance cost vs quality
Chained reasoning, ambiguity, high cost-of-errorMost CapableAccept higher cost; error is expensive
Mixed pipeline (some steps easy, some hard)Route per step (heterogeneous)Cheapest tier that passes eval per step

Worked example — classification vs multi-step reasoning agent

Scenario A · Ticket classification

Task: Tag 2M incoming support emails/day into 12 categories, <500 ms budget, minor errors tolerable and correctable downstream.

Decision: Well-defined + verifiable + high-volume + latency-sensitive → Lightweight / Fast tier. Validate accuracy on a labeled eval set; the capable tier's extra reasoning adds cost without material benefit here.

Scenario B · Multi-step research agent

Task: An agent that reads a contract, plans sub-questions, calls tools, reconciles conflicts, and drafts a risk memo. Errors are costly; volume is low.

Decision: Ambiguous + long-horizon + high-stakes → Most Capable tier for the planning/reasoning steps. Consider a hybrid: capable tier plans, fast/balanced tier executes cheap sub-steps (extraction, formatting).

💡 Tips & Tricks
  • Down-shift, don't guess. Start on the tier the task obviously needs, then try the next-cheaper tier behind an eval gate. Keep it only if quality holds.
  • Budget is a filter applied after complexity, not the starting point. Picking the cheapest model first and hoping it's smart enough is the classic anti-pattern.
  • For agents, remember that a weaker model can loop — extra retries and longer trajectories can erase the per-token savings.
🎯 Exam Strategy The most common trap: a scenario leads with a tight budget to bait you into picking the cheapest tier for a task that clearly needs reasoning. Match task complexity first, then optimize cost/latency — never the reverse. If two options remain, prefer the one that proposes evaluating a down-shift over the one that asserts a tier without justification.

40.3  When to Use Smaller Models vs Larger Models

Smaller and larger models are not "worse" and "better" — they are different tools. The skill is knowing which job each one fits.

🐤 Smaller / Faster Models

Pros
  • Lowest cost per token — economical at scale
  • Lowest latency; great for real-time & streaming UX
  • Higher throughput / better rate-limit headroom
  • Ideal for narrow, well-specified tasks
Cons
  • Less robust on ambiguity & long reasoning chains
  • More sensitive to prompt quality; may need few-shot examples
  • Can require retries/guardrails that erode savings
Real-world fits
  • Intent / sentiment classification at volume
  • Structured field extraction from forms
  • Content moderation & routing
  • Autocomplete / inline suggestions
  • Cheap sub-steps inside a larger agent

🦅 Larger / More Capable Models

Pros
  • Deeper reasoning on ambiguous, multi-step problems
  • Stronger zero-/few-shot generalization
  • Better planning & tool orchestration in agents
  • Higher reliability where errors are costly
Cons
  • Highest cost per token
  • Higher latency — weaker fit for real-time UX at volume
  • Overkill (wasteful) on simple, verifiable tasks
Real-world fits
  • Multi-step research / analysis agents
  • Complex code generation & refactoring
  • Nuanced legal / financial / medical reasoning
  • Planning & orchestration ("the brain" of an agent)
  • High-stakes decisions with costly errors

The hybrid / routing pattern

Mature systems rarely pick one model. They route heterogeneously: a capable model handles planning and hard reasoning, while a fast model handles the high-frequency, low-difficulty steps. This captures most of the quality at a fraction of the cost — a frequent "best answer" on the exam.

💡 Tips & Tricks
  • Use a cascade: try the small model first, and only escalate to a larger model when a confidence check or validator fails.
  • A larger model can act as an offline teacher — use it to generate high-quality examples or labels that make a smaller model succeed on the same task.
  • Don't conflate "small model" with "bad output." Often the fix is a better prompt or a few examples, not a bigger model.
🎯 Exam Strategy When a question offers "use the largest model for everything" as an option, it is almost always a distractor — it's rarely cost-justified. Favor answers that match tier to task or propose routing/cascading. Watch for the reverse trap too: "use the smallest model for everything" fails on the reasoning-heavy items in the scenario.

40.4  Model Versioning and Migration Strategies

Models are versioned and eventually deprecated. A production architecture must migrate without regressing quality — treat a model swap like any other dependency upgrade.

Core concepts

  • Deprecation handling: Providers publish lifecycle/deprecation notices with retirement dates. Pin explicit model versions in code, subscribe to those notices, and plan migrations before the retirement date rather than reacting to a broken call.
  • Backward compatibility testing: A newer model version can change output style, formatting, or tool-use behavior even when it's "better" on average. Never assume drop-in compatibility — re-run your evaluation suite against the new version.
  • Canary rollouts: Shift a small percentage of traffic to the new model, monitor quality/latency/cost/error metrics, and ramp gradually. Keep the ability to roll back instantly.
  • Prompt regression testing: Maintain a versioned set of representative prompts with expected-quality checks (golden set + automated graders). Run it on every model or prompt change to catch regressions before users do.

Step-by-step migration checklist

  1. Pin & inventory. Confirm every place the old model ID/version is referenced (code, configs, prompts, agents).
  2. Read the deprecation & changelog. Note the retirement date, behavioral changes, and any new/renamed parameters.
  3. Build or refresh a golden eval set. Representative inputs with quality graders (accuracy, format adherence, safety, latency, cost).
  4. Run baseline vs candidate. Score the current model and the new version side-by-side on the same eval set.
  5. Regression-test prompts & tool use. Verify output format, structured/JSON schemas, and tool-calling still pass.
  6. Tune if needed. Adjust prompts, few-shot examples, temperature, or parsing to close any gaps the new version introduced.
  7. Canary deploy. Route a small % of live traffic to the candidate behind a feature flag; watch dashboards.
  8. Ramp gradually. Increase traffic in stages, comparing quality/cost/latency at each step, with rollback ready.
  9. Cut over & monitor. Promote to 100%, keep heightened monitoring, and set alerts on quality/cost drift.
  10. Decommission & document. Remove the old version, record the migration outcome, and archive the eval results.
💡 Tips & Tricks
  • Always pin explicit versions in production. "Latest"/alias references can silently change model behavior under you.
  • Version your prompts alongside your code — a prompt tuned for one model version may regress on the next.
  • Keep the old version reachable during canary so rollback is a config flip, not a redeploy.
  • Automate the golden-set eval in CI so every model/prompt change is gated the same way as code.
🎯 Exam Strategy Migration questions reward safety and reversibility. The correct answer almost always includes an eval/regression step before rollout and a gradual canary with rollback. Eliminate options that "immediately switch all production traffic to the newest model" or "assume the new version is a drop-in replacement" — both skip the regression gate.

40.5  Hands-On: Model Selection Decision Matrix

A decision matrix turns a fuzzy "which model?" into a scored, defensible choice. Use the template below, weight the criteria for your context, and total the columns.

The template (criteria × model options)

Score each model tier 1 (poor) – 5 (excellent) against each criterion for your task, multiply by the criterion weight, and sum. Higher total = better fit.

Worked example — sample business case

Business case A fintech wants an in-app support assistant that answers account questions over a RAG knowledge base. Volume is high (hundreds of thousands of chats/day), users expect fast streaming replies, answers must be accurate but questions are mostly routine, and a small tail of complex disputes needs deeper reasoning.

Weights chosen for this case: latency and cost matter a lot (high volume, real-time), quality matters but most queries are routine. Scores are illustrative, on a 1–5 scale (weight in parentheses).

Criterion (weight) Fast Balanced Capable
Task-complexity fit (×2)355
Output quality / accuracy (×3)345
Latency requirement (×3)542
Cost / budget (×3)532
Throughput / volume (×2)542
Cost-of-error / risk (×1)345
Weighted total 56 60 49

Interpretation: The Balanced tier wins overall (60) as the default handler — it clears the quality bar while staying reasonable on cost and latency. The Fast tier is close (56) and attractive for the routine majority. The Capable tier scores lowest here (49) despite top quality, because volume/cost/latency weigh against it.

Architect's move — hybrid routing: Serve the routine majority with the Fast tier for cost/latency, default ambiguous queries to Balanced, and escalate the complex-dispute tail to the Capable tier via a confidence/complexity check. The matrix informs the routing thresholds rather than forcing a single winner.

💡 Tips & Tricks
  • Set weights before scoring — deciding weights after you see the scores lets bias creep in.
  • A near-tie (e.g. 56 vs 60) is a strong signal to route/cascade rather than force one model.
  • Re-run the matrix after any major model release — a new version can shift a column enough to change the winner.
  • Keep the matrix in version control next to your eval set — it's living documentation of why a model was chosen.
🎯 Exam Strategy Matrix questions test whether you weight criteria to the scenario. If the prompt stresses volume and real-time UX, the "correct" choice should reflect heavy latency/cost weighting — not the highest raw-quality model. When the totals are close, the best answer typically proposes a hybrid/routing design. Beware options that ignore stated constraints (e.g. picking the capable tier when the scenario screams cost-sensitivity).

✦  Chapter Summary & Key Takeaways

Model selection is an exercise in placing each workload at the right point on the intelligence / cost / latency surface — and revisiting that choice as models evolve.

  • Reason in tiers. Fast, balanced, and most-capable classes are stable even as version names change.
  • Complexity first, budget second. Match the task's reasoning needs, then optimize cost/latency — never the reverse.
  • Down-shift behind an eval gate. Try the cheaper tier, but keep it only if quality holds.
  • Small ≠ worse. Smaller models win on cost, latency, and throughput for narrow, verifiable tasks.
  • Hybrid routing wins. Route hard steps to capable models and cheap steps to fast models — usually the best answer.
  • Migrate safely. Pin versions, regression-test prompts, canary-roll out, and keep rollback ready.
  • Use a decision matrix. Weight criteria to the scenario, score, and let close ties push you toward routing.
  • Distrust exact numbers. Treat precise prices/benchmarks as illustrative; verify against current official docs.
