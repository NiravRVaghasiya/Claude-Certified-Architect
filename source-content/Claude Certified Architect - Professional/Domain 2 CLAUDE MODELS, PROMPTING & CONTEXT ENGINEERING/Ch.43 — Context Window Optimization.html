43.1 Understanding Context Windows & Token Budgets

The context window is the fixed-size working memory of a single API request. Every optimization technique in this chapter exists to manage the pressure on this one finite resource.

Concept Overview

A context window is the maximum number of tokens a model can consider in a single request — both the input you send (system prompt, tools, conversation history, retrieved documents) and the output the model generates share that same budget. A token is a chunk of text roughly ¾ of a word in English; the exact count depends on the model's tokenizer.

As a general principle, current Claude models expose a large window — commonly 200K tokens as a baseline, with 1M-token windows available on newer models such as the Sonnet 4 generation and later. (Treat specific limits as version-dependent — always confirm against the model card for the exact model you deploy.)

Key Mechanics

  • Shared budget: input tokens + output tokens ≤ context window. If input consumes too much, you must reserve headroom for the response or generation gets truncated.
  • Max output is separate & smaller: models cap output tokens (e.g. an illustrative 64K–128K depending on model) independently of the window — you cannot spend the whole window on a single reply.
  • Token counting: use the SDK's token-counting endpoint/utility to measure a prompt before sending. Never eyeball character counts — code, JSON, and non-English text tokenize very differently from prose.
  • Everything counts: tool/function schemas, system prompt, few-shot examples, and prior turns all consume the window on every request — a growing conversation silently inflates cost.

Visualization — Context Window Budget

Real-World Use Case

A document-analysis assistant pastes a 150K-token contract into the prompt, then asks for a 10K-token summary. With a 200K window, that leaves only ~40K for the system prompt, tools, and any follow-up turns. By turn three the conversation overflows and the API rejects the request. The fix is a token budget: cap retrieved content and summarize prior turns so the running total stays comfortably under the limit.

Tips & Tricks

💡 Tip: Budget backwards. Decide your required output reserve first (e.g. 8K tokens), subtract it and your fixed system/tools overhead from the window, and treat the remainder as the ceiling for history + retrieved context.
💡 Tip: Count tokens programmatically before sending. A prompt that "looks short" can be token-heavy if it's JSON, code, or a non-Latin language.
⚠️ Pitfall: A bigger context window is not free performance. Larger prompts cost more per request and can increase latency — capacity is a ceiling, not a target to fill.

Exam Strategy

🎯 Exam Strategy: Questions here test whether you know the window is shared between input and output. If a scenario says "the response got cut off" or "the request was rejected as too large," the expected reasoning is insufficient output reserve / total-budget overflow — not a model quality issue. Eliminate answers that suggest "upgrade the model" when the real problem is budget management.

43.2 Progressive Summarization vs Full Context

When a conversation or task history outgrows the budget, you choose between carrying everything forward (full context) or carrying a compressed running summary (progressive summarization). Each trades fidelity against cost.

Concept Overview

Full context replays the entire history verbatim on every turn — maximum fidelity, but tokens (and cost/latency) grow linearly and eventually hit the window limit. Progressive summarization periodically compresses older turns into a compact summary, keeping only that summary plus the most recent verbatim turns — bounded token growth, at the cost of some detail loss.

Key Mechanics

  • Trigger: summarize when a threshold is crossed — e.g. running tokens exceed X% of the window, or every N turns.
  • Rolling window: keep the last k turns verbatim (recency matters most) and replace everything older with a summary block.
  • Summary as state: the summary becomes part of the system/context prefix; the model treats it as established facts.
  • Lossy by design: details dropped in a summary are gone unless preserved elsewhere (see 43.5 Scratchpads for durable facts).

Visualization — Full Context vs Progressive Summarization

Real-World Use Case

A multi-hour support chat would overflow if replayed verbatim. The app keeps the last 4 messages verbatim and maintains a running summary ("Customer: order #8842, requested refund, agent confirmed eligibility, awaiting bank details"). Token usage stays flat across a 60-turn session, and the model still "remembers" the key facts.

Tips & Tricks

💡 Tip: Keep recent turns verbatim, summarize only the tail. Recency carries the most conversational signal; over-summarizing the latest turn hurts quality most.
💡 Tip: Summarize into structured fields (entities, decisions, open items) rather than free prose — it compresses better and is less lossy for facts.
⚠️ Pitfall: Summarization is lossy and adds an extra model call. Don't summarize prematurely — if the whole session comfortably fits the window, full context is simpler and higher fidelity.

Exam Strategy

🎯 Exam Strategy: Watch for the fidelity vs. cost trade-off. If a question stresses "must not lose any detail / audit accuracy," lean full context (or scratchpad persistence). If it stresses "long-running / unbounded conversation" or "keep cost flat," lean progressive summarization. A distractor will often pitch summarization as loss-free — reject it.

43.3 Prompt Caching: Reducing Latency & Cost for Static Prefixes

When many requests share an identical, unchanging prefix (system prompt, tool defs, big reference doc), prompt caching lets the model reuse the already-processed prefix instead of paying to reprocess it every time.

Concept Overview

Prompt caching stores the encoded state of a prompt prefix up to a marked cache breakpoint. The first request writes the cache (a one-time premium); subsequent requests within the TTL that share the same prefix get a cache hit (read) at a large discount and lower latency, because the prefix does not need to be recomputed.

Key Mechanics

  • Prefix order: caching references the prompt in the order tools → system → messages, up to and including the block you mark with cache_control.
  • Immutability: the cache key is a cumulative hash of everything up to the breakpoint. Changing any earlier token — even one — produces a different hash and forces a full rewrite.
  • TTL: default 5-minute lifetime, with an optional 1-hour TTL. The clock starts at request start, and every hit refreshes the timer at no extra cost.
  • Pricing (per Anthropic docs, as multiples of base input price): 5-min write ≈ 1.25×, 1-hour write ≈ 2×, and a cache hit/read ≈ 0.1× (i.e. ~90% cheaper than uncached input; a few newer models read even cheaper).
  • Minimum size & breakpoints: prefixes must exceed a per-model minimum (illustratively ~1K tokens for larger models, higher for the smallest) to be cacheable; up to 4 breakpoints and a 20-block backward lookback apply.

Real-World Use Case

A coding assistant sends a 30K-token style guide + tool schema as a fixed prefix on every request. Marking that prefix with a cache breakpoint means the first request writes it (~1.25×), and the next thousand requests read it at ~0.1× — collapsing both the per-request token bill for the prefix and the time-to-first-token.

Tips & Tricks

💡 Tip: Treat prompt caching prefixes as immutable — even a single-token change (a timestamp, a request ID) invalidates the cache and forces a full reprocessing cost. Put volatile content after the breakpoint.
💡 Tip: Order prompts static → dynamic: tools and system instructions first (cached), user-specific query last (uncached). This maximizes the reusable prefix.
💡 Tip: Choose TTL by reuse cadence. Bursty traffic within minutes → 5-min TTL. Steady reuse over an hour → 1-hour TTL to avoid repeated write premiums.
⚠️ Pitfall: Caching a prefix that's below the minimum token threshold, or that changes every request, yields no hit — you pay the write premium for nothing.

Exam Strategy

🎯 Exam Strategy: When a question describes repeated identical system prompts / large static context across many requests, immediately think Prompt Caching before considering summarization. Key discriminators: caching helps when the prefix is static and reused; summarization helps when the history is growing. If the prompt changes every call, caching is the wrong answer — eliminate it.

43.4 Modular Prompts & Skills for Prompt Reuse

Instead of maintaining giant monolithic prompts, compose them from small, reusable, independently-versioned modules ("skills") that plug into a base template. Better maintainability — and a bigger, more stable cacheable prefix.

Concept Overview

Modular prompting decomposes a prompt into named components — role, guardrails, tool instructions, domain knowledge, output format — that are assembled per request. A skill is a packaged, reusable unit of instructions (and optionally examples/tools) that can be loaded on demand. This mirrors software modularity: write once, reuse everywhere, version independently.

Key Mechanics

  • Base template + slots: a stable scaffold defines slots ({{role}}, {{policies}}, {{format}}); modules fill them at assembly time.
  • On-demand loading: load only the skills relevant to the current task, keeping the assembled prompt lean rather than shipping every instruction every time.
  • Stable ordering → cache synergy: putting shared modules first, in a fixed order, produces a long, identical prefix — ideal for the caching in 43.3.
  • Independent versioning: update the "refund policy" module once and every prompt that includes it inherits the change.

Visualization — Modules Plugged Into a Base Template

Real-World Use Case

A company runs 12 different assistants (sales, support, HR…). All share the same "brand voice" and "safety policy" modules. When legal updates the safety policy, they edit one module; all 12 assistants update instantly — and because the shared modules lead every prompt, they form a cacheable common prefix across products.

Tips & Tricks

💡 Tip: Order modules most-shared first, most-specific last. This maximizes both reuse clarity and the length of the cacheable prefix.
💡 Tip: Load skills on demand. Injecting every possible instruction into every request wastes tokens; pull in the "refund" skill only when the task is about refunds.
⚠️ Pitfall: Over-modularization adds assembly complexity and can fragment context. If a module is used in exactly one place and never changes, inlining it is fine.

Exam Strategy

🎯 Exam Strategy: Modular-prompt questions usually reward maintainability + reuse + cache synergy. If a scenario mentions "duplicated instructions across many prompts" or "a policy that must update everywhere at once," pick modular prompts / skills. Note the link to 43.3: modularity's fixed ordering is what makes prefixes cacheable — questions may test that connection.

43.5 Scratchpad Files for Persistent Working Memory

A scratchpad is external storage — a file or datastore — the model reads from and writes to across turns and sessions. It offloads durable facts out of the context window, giving the app memory that survives summarization and even restarts.

Concept Overview

The context window is ephemeral: it vanishes when the request ends. A scratchpad file provides persistent working memory — the model (via tools) writes intermediate results, decisions, and facts to a file, and reads them back on later turns. This decouples "what must be remembered" from "what currently fits in the window."

Key Mechanics

  • File I/O via tools: the model uses read/write tools (or the app orchestrates them) to persist and retrieve state — e.g. append a decision, read the current task list.
  • Selective loading: only the relevant slice of the scratchpad is pulled into context per turn, keeping token usage low.
  • Survives compression: facts written to the scratchpad are safe even when conversation history is summarized (43.2) or the session restarts.
  • Structured state: works best as structured records (task list, key/value facts, running plan) rather than an unbounded log.

Visualization — Memory Persisting Across Turns

Real-World Use Case

An autonomous research agent works a multi-step task over dozens of turns. It writes findings and its running plan to progress.md after each step. When the context window fills and older turns are summarized, the agent still recovers exact figures and its to-do list by reading the file — no detail is silently lost.

Tips & Tricks

💡 Tip: Use the scratchpad as the source of truth for facts you cannot afford to lose (IDs, numbers, decisions). Summaries can drop detail; a file does not.
💡 Tip: Load only the relevant section of the scratchpad into context each turn. A 50K-token log defeats the purpose if you paste all of it back in.
⚠️ Pitfall: An ever-growing, unstructured scratchpad becomes its own context problem. Keep it structured and periodically compact it.

Exam Strategy

🎯 Exam Strategy: Scratchpad questions hinge on the word persistence. If a scenario says state must survive across sessions/restarts or "must not be lost when history is summarized," the answer is a scratchpad / external memory — not summarization (which is in-context and lossy) and not caching (which is a cost optimization, not memory). Eliminate any option that keeps critical state only inside the window.

43.6 Hands-On: Optimizing Token Usage for a High-Volume Application

Synthesis time. We take one realistic app hitting token, cost, and latency walls, and apply all four techniques (43.2–43.5) on top of the fundamentals (43.1) in a deliberate decision process.

The Scenario

A customer-support bot handles 50,000 conversations/day. Each conversation averages 8 turns. Every request ships:

  • A 18K-token system prompt (brand voice + full policy manual + tool schemas), sent verbatim every call.
  • The entire conversation history, replayed in full each turn (full-context strategy).
  • Growing latency as later turns re-send everything, plus a rising per-conversation token bill.

Symptoms: high cost per conversation, slow time-to-first-token on later turns, and occasional window-overflow errors on long chats.

Exam Strategy

🎯 Exam Strategy: Synthesis questions give you a messy scenario and ask for the best combination. Map each symptom to its technique: static repeated prefix → caching; growing history → summarization; must-not-lose facts → scratchpad; duplicated instructions → modular prompts; overflow/truncation → budgeting. The best answer usually layers techniques; single-technique answers to a multi-symptom problem are distractors.

? Self-Check Quiz

Eight questions across the whole chapter. Click each to reveal the answer and the reasoning.

Q1.The context window is best described as a budget shared between which two things?
Answer: Input tokens (system prompt, tools, history, retrieved context) and output tokens (the generated response). They draw from the same fixed limit, so you must reserve headroom for the response. 43.1
Q2.A 60-turn support chat keeps overflowing the window. Cost matters more than perfect recall. Which technique fits best?
Answer: Progressive summarization — keep the last few turns verbatim and compress older ones into a rolling summary to keep token growth flat. Full context would keep overflowing. 43.2
Q3.Roughly what are the cost multipliers for a 5-minute cache write, a 1-hour cache write, and a cache read, relative to base input price?
Answer: Per Anthropic's published pricing: 5-min write ≈ 1.25×, 1-hour write ≈ 2×, and a cache hit/read ≈ 0.1× (about 90% cheaper than uncached input; a few newer models read even cheaper). 43.3
Q4.Your cached prefix suddenly stops getting cache hits after you added a timestamp to the top of the system prompt. Why?
Answer: The cache key is a cumulative hash of everything up to the breakpoint. A changing timestamp alters the prefix on every request → a new hash → no hit, and you pay the write premium repeatedly. Fix: move volatile content after the cache breakpoint. 43.3
Q5.Twelve assistants share an identical safety policy that legal needs to update in one place. Which approach?
Answer: Modular prompts / skills — factor the policy into one versioned module included by all twelve. Bonus: placing it first creates a shared cacheable prefix. 43.4
Q6.An agent must remember exact order numbers across a session restart, even after old turns are summarized away. What do you use?
Answer: A scratchpad file (external persistent memory). Summarization is in-context and lossy; caching is a cost optimization, not memory. Only external persistence survives restarts. 43.5
Q7.In the high-volume support bot, which single change gives the biggest, lowest-risk win for the 18K static prompt, and why?
Answer: Prompt caching the static system+tools prefix. It's identical on every request, so cache reads cut that prefix's cost by ~90% and reduce latency — with essentially no fidelity loss. Apply it before summarization. 43.6
Q8.Which techniques are complementary rather than interchangeable, and give one pairing that matters?
Answer: All of them layer. Key pairing: summarization + scratchpad — summarization bounds token growth, while the scratchpad preserves the exact facts summarization would otherwise lose. Also modular prompts + caching — stable module ordering is what makes prefixes reliably cacheable. 43.6

! Common Misconceptions

High-frequency exam traps. Each is stated as the tempting-but-wrong belief, then corrected.

❌ "A bigger context window means I can stop optimizing."
✅ Reality: A larger window raises the ceiling, but bigger prompts still cost more per request and can add latency. Budgeting, caching, and summarization still matter. 43.1
❌ "Only the input I type counts against the context window."
✅ Reality: Tool schemas, the system prompt, few-shot examples, retrieved documents, and the reserved output all consume the same budget on every request. 43.1
❌ "Progressive summarization is lossless — it just makes things shorter."
✅ Reality: Summarization is inherently lossy. Details not captured in the summary are gone unless persisted elsewhere (e.g. a scratchpad). 43.2
❌ "Prompt caching is free savings — just turn it on everywhere."
✅ Reality: The first write costs a premium (~1.25× or ~2×). If the prefix isn't actually reused, or it changes each call, you pay the premium with no hit. Cache only stable, reused prefixes above the minimum size. 43.3
❌ "Prompt caching remembers my conversation for me."
✅ Reality: Caching is a cost/latency optimization for reprocessing a static prefix — it is not a memory feature. For durable memory, use a scratchpad. 43.3 / 43.5
❌ "A tiny edit to the system prompt is harmless for caching."
✅ Reality: Even a one-token change before the breakpoint invalidates the cache and forces a full rewrite. Keep cached prefixes immutable; put dynamic content after the breakpoint. 43.3
❌ "Modularizing prompts always saves tokens."
✅ Reality: Modularity improves maintainability and cache reuse, but if you load every module every time it can increase tokens. Load skills on demand. 43.4
