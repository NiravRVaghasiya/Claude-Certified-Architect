48.1

Core Metrics

The four universal axes every AI system is judged on — regardless of task.

Concept Definition

Every production AI system is evaluated along four orthogonal dimensions. No single number tells you if a system is "good" — you always measure a vector of these axes and reason about their trade-offs (which is exactly what 48.3 formalizes as the Pareto frontier).

🎯Accuracy

Definition: How often, or how closely, the output matches the desired/correct result.

Measured in: % correct, F1, exact-match rate, or a graded score (e.g. LLM-as-judge 1–5).

Trade-off: ↑ accuracy usually costs latency & money (bigger models, more sampling).

⚡Latency

Definition: Time between request submission and response completion.

Measured in: milliseconds/seconds at P50, P95, P99 percentiles; also TTFT (time-to-first-token) & tokens/sec for streaming.

Trade-off: often inversely related to accuracy.

💰Cost

Definition: Resource expenditure to produce a result.

Measured in: $ per request, $ per 1M input/output tokens, or $ per resolved task.

Trade-off: caching, smaller models, and prompt compression cut cost but may reduce accuracy.

🛡️Safety & Security

Definition: Resistance to harmful outputs (safety) and to adversarial manipulation such as prompt injection / data exfiltration (security).

Measured in: harmful-output rate, refusal accuracy, jailbreak/injection success rate (lower = better).

Trade-off: stricter guardrails can raise false-refusal rate, hurting usefulness.

Key Terminology

  • Percentile latency (Pn) — the value below which n% of requests complete. P95 = 800ms means 95% of requests finish in ≤800ms. Tail latency (P95/P99) matters more than the mean because a handful of slow requests dominate user-perceived performance.
  • Throughput — requests (or tokens) served per unit time; a capacity/cost concept, distinct from per-request latency.
  • False-refusal rate — how often the system wrongly refuses a benign request; the "cost" side of being safe.
  • Golden set — a curated, labeled dataset of inputs + expected outputs used to measure accuracy repeatably.

🌍 Real-World Example A customer-support agent is evaluated at P95 latency = 3.2s, accuracy (resolution correctness) = 88%, cost = $0.011/conversation, and injection-success = 0.4%. Swapping to a larger model lifts accuracy to 91% but pushes P95 to 6.1s and cost to $0.028 — a classic accuracy-vs-latency-vs-cost trade the team must weigh against the SLA.
⚠️ Common Pitfalls
  • Reporting mean latency instead of percentiles — averages hide the painful tail.
  • Treating accuracy as a single scalar when the task needs precision and recall separately (see 48.2).
  • Ignoring safety/security entirely because it is "hard to measure" — the exam treats it as a first-class core metric.
  • Confusing throughput (system capacity) with latency (per-request speed).
💡 Tips & Tricks Memorize the four core metrics with "A-L-C-S" → "A Lovely Cup of… Safety": Accuracy, Latency, Cost, Safety. For percentiles, remember "higher P = worse-case user": P99 describes your unluckiest 1%.
📝 Exam Strategy Expect a scenario that names an SLA (e.g. "P95 must stay under 2s") and asks which change is acceptable. The trap answer improves accuracy while silently violating the latency SLA. Rule: a change is only valid if it keeps every hard-constrained metric within its threshold. Also watch for questions asking you to pick the right unit — cost is per-token or per-task, latency is a percentile in ms, safety is a rate.

48.2

Task-Specific Metrics

The core axes get instantiated differently per task type. These are the ones the exam loves to make you compute.

Concept Definition

"Accuracy" is too blunt for real tasks. An extraction task cares about precision vs. recall; a support agent cares about resolution rate; a coding agent cares about functional correctness (pass@k) and code hygiene. Pick the metric that matches the failure mode you care about.

Extraction Accuracy — Precision, Recall & F1

For extraction / classification / retrieval, you count outcomes in a confusion matrix:

  • TP (true positive) — correctly extracted a correct item.
  • FP (false positive) — extracted something wrong / that shouldn't be there.
  • FN (false negative) — missed an item that should have been extracted.
Precision = TPTP + FP  # of what I extracted, how much was right?
Recall   = TPTP + FN  # of what I should have found, how much did I catch?
F1      = 2 · Precision · RecallPrecision + Recall  # harmonic mean — punishes imbalance
🔷 Key distinction Precision = "don't cry wolf" (avoid FPs). Recall = "don't miss anything" (avoid FNs). F1 is the harmonic mean — it stays low if either is low, so it rewards balance.

Resolution Rate

For agents/assistants whose job is to finish a task (resolve a ticket, complete a workflow):

Resolution Rate = tasks fully resolved (no human handoff)total tasks attempted × 100%

Note: definitions vary — some teams count "resolved" only if the outcome is also verified correct, blending resolution with accuracy. Commonly reported alongside deflection rate (share of contacts handled without escalation) and containment rate.

Code Quality — pass@k & Static Metrics

pass@k asks: if the model generates k candidate solutions for a problem, what is the probability that at least one passes all unit tests? The standard unbiased estimator (Chen et al., 2021, "Codex") generates n ≥ k samples, counts c that pass, and computes:

pass@k = Eproblems  [  1 − C(n − c, k)C(n, k)  ]   # C(a,b) = "a choose b"
# n = samples generated, c = # correct, k = budget. pass@1 = c/n.

Complementary static code metrics (no execution needed):

Common code-quality signals for evaluating a coding agent

🌍 Real-World Example A contract-parsing tool extracts 100 clauses. It returns 90 items: 80 correct (TP), 10 wrong (FP), and misses 20 real clauses (FN). → Precision = 80/90 = 0.89, Recall = 80/100 = 0.80, F1 = 2(0.89·0.80)/(0.89+0.80) = 0.84. High precision, weaker recall → the tool is cautious but leaves clauses on the table.
⚠️ Common Pitfalls
  • Swapping the precision/recall denominators — Precision divides by what you predicted, Recall by what actually exists.
  • Optimizing accuracy on an imbalanced dataset — 99% "accuracy" is trivial if 99% of items are the negative class. Use precision/recall/F1 instead.
  • Assuming pass@10 means "run once and hope" — it explicitly allows k attempts; comparing a pass@1 system to a pass@10 system is apples-to-oranges.
  • Reporting lint score as the primary quality signal — clean code that fails tests is still wrong.
💡 Tips & Tricks "PRecision = PRedicted" — both start with PR, so precision's denominator is the predicted positives (TP+FP). Recall is then "the rest" (TP+FN, the real positives). F1 is the harmonic mean → always ≤ the arithmetic mean, so it can never be fooled by one high number.
📝 Exam Strategy Precision/recall computation questions are almost guaranteed. Draw the 2×2 confusion matrix immediately and label TP/FP/FN/TN — this prevents denominator mix-ups. If a scenario says "missing a fraud case is catastrophic," they want you to prioritize recall; if "false alarms are expensive," prioritize precision. For pass@k, remember it rewards sampling budget, so it will look higher than pass@1 for the same model.

48.3

The Pareto Frontier

When metrics conflict, "best" is a set — not a point. This is multi-objective optimization made visual.

Concept Definition

You rarely optimize one metric. You want high accuracy and low cost and low latency — objectives that fight each other (see 48.1's trade-off matrix). Multi-objective optimization accepts there is no single winner and instead finds the set of "best possible compromises."

🔷 Pareto Dominance (the exam's favorite definition) Solution A dominates solution B if and only if A is equal-or-better on every objective and strictly better on at least one. If neither dominates the other, they are non-dominated / incomparable — you can't say one is better without a preference weighting.
  • Pareto-optimal (non-dominated) solution — one that no other solution dominates. You cannot improve one objective without sacrificing another.
  • Pareto frontier (front) — the set of all Pareto-optimal solutions; the curve/edge of achievable trade-offs.
  • Dominated solution — a solution that is beaten on all axes by some other solution; it is strictly wasteful and should be discarded.

Visual Aid — Pareto Frontier Scatter Plot

Below: candidate models plotted by Cost (x, lower is better) vs. Accuracy (y, higher is better). Green points are Pareto-optimal (connected by the frontier); gray points are dominated. Hover any point for exact values.

Pareto-optimal (non-dominated) Dominated (wasteful) — frontier
🌍 Real-World Example Model F ($3, 82%) is dominated by Model C ($3, 88%): same cost, higher accuracy → F should never be chosen. But A, B, C, D, E are mutually non-dominated: moving from C→D buys +3% accuracy for +$2 cost. Which frontier point you pick depends on your preference weighting (or hard constraints like "budget ≤ $3" → pick C).
⚠️ Common Pitfalls
  • Calling A "better than E" — they're incomparable; A wins on cost, E wins on accuracy.
  • Forgetting the "strictly better on at least one" clause — two identical solutions do not dominate each other.
  • Mixing objective directions: when one axis is "lower is better" (cost, latency), flip it mentally before checking dominance.
  • Choosing a dominated point because it "looks balanced" — a dominated point is never rational to pick.
💡 Tips & Tricks Dominance test shortcut: "≥ on ALL, > on ONE." If a candidate fails the "≥ on all" part on even one axis, it does not dominate — stop there. To spot the frontier on a plot where you want high-Y/low-X: walk left-to-right; a point is on the frontier only if nothing sits up-and-to-its-left.
📝 Exam Strategy Pareto questions typically show two solutions and ask "does A dominate B?" — apply "≥ on ALL objectives AND > on at least ONE." A frequent trap presents A better on 2 metrics but worse on the 3rd: that is not domination (answer: non-dominated / incomparable). Another trap asks for "the single best model" when the correct answer is "it depends on the objective weighting / constraints." Watch axis directions — cost and latency are minimized.

48.4

Thresholds & Baselines

A metric value is meaningless without a reference point and a bar to clear.

Concept Definition

Three easily-confused reference concepts turn a raw number into a decision:

Baseline vs. Threshold vs. Target — know the difference cold
TermQuestion it answersRole
Baseline"What are we comparing against?"A reference point — the current system, a naive/heuristic method, human performance, or a previous model version. Establishes lift.
Threshold"What's the minimum acceptable?"A pass/fail gate. Below it, the system is not shippable (e.g. "accuracy ≥ 90% or block release").
Target"What are we aiming for?"An aspirational goal, usually above the threshold. Guides roadmap, not a hard gate.
🔷 Mental model Baseline = floor you must beat · Threshold = bar you must clear to ship · Target = summit you're climbing toward. Ordering is usually: baseline ≤ threshold ≤ target.

Statistical Methods for Setting Thresholds

  • SLA-driven — the threshold comes from a business/contractual commitment (e.g. "P95 latency ≤ 2000ms", "99.9% uptime"). Non-negotiable hard constraint.
  • Percentile-based — set the threshold from the distribution of observed values, e.g. "alert if latency exceeds the historical P95." Adapts to real behavior rather than a guessed number.
  • Baseline-relative — require a minimum lift over the baseline (e.g. "must beat the heuristic by ≥5 F1 points"), often paired with a statistical significance test so the gain isn't noise.
  • Cost/risk-optimal — choose the classification threshold that maximizes expected value given the cost of FPs vs. FNs (e.g. via an ROC/precision-recall curve operating point).
🌍 Real-World Example A fraud classifier's baseline is last quarter's model at 0.71 F1. Product sets a threshold of 0.75 F1 (won't ship below it) and a target of 0.85. The decision threshold on the probability score is tuned to P(fraud) ≥ 0.30 (not 0.50) because a missed fraud (FN) costs 10× a false alarm (FP) — a cost-optimal, recall-leaning choice.
⚠️ Common Pitfalls
  • Conflating the metric threshold (ship gate on F1) with the decision threshold (the probability cutoff inside a classifier) — different levers.
  • Setting a threshold with no baseline → you can't tell if the model adds any value.
  • Picking a round number (0.50 cutoff, "90% target") with no statistical or business justification.
  • Declaring victory on a small sample — a 2-point gain over baseline may be within noise; test for significance.
💡 Tips & Tricks "B-T-T ladder": Baseline → Threshold → Target, low to high. If a question gives you a number, ask "is this describing what we beat (baseline), what we must clear (threshold), or what we hope for (target)?" The word "minimum acceptable" → threshold; "current/previous system" → baseline; "goal/aspiration" → target.
📝 Exam Strategy Expect a matching/definition question separating baseline, threshold, and target — the distractor swaps threshold and target. Anchor on the phrase "minimum acceptable = threshold (the ship gate)." For method questions, map keywords: "contractual/SLA" → SLA-driven; "based on historical distribution" → percentile-based; "must beat current system" → baseline-relative. If asked how to pick a classifier cutoff when FN and FP costs differ, the answer is a cost-optimal operating point, not 0.5.

48.5

Hands-On Framework

Putting 48.1–48.4 together: a repeatable recipe for building a metrics framework, worked end-to-end.

Concept Definition

A metrics framework is the full evaluation harness for a system: which metrics you track, how you measure them, on what data, against which thresholds, and how you decide to ship. Below is a worked example for a realistic use case.

🔷 Use case "ClauseBot" — an AI agent that reads uploaded vendor contracts, extracts key clauses (liability, termination, payment terms), and answers questions about them for a legal-ops team. It must be accurate, cheap enough at scale, fast enough to feel interactive, and safe against prompt-injection hidden in uploaded documents.

Worked Example — 7-Step Framework Build

  1. Define objectives & map to core metrics (48.1)

    Accuracy → clause-extraction F1 + answer correctness (LLM-as-judge). Latency → P95 end-to-end per query. Cost → $ per contract processed. Safety → injection-resistance rate on adversarial docs.

  2. Choose task-specific metrics (48.2)

    Extraction → Precision / Recall / F1 against labeled clauses. Q&A → answer accuracy + groundedness (is it supported by the contract?). Operational → resolution rate = queries answered without human escalation.

  3. Build the evaluation dataset (golden set)

    Curate 150 real (anonymized) contracts with human-labeled clauses & 300 gold Q&A pairs. Add a red-team split: 40 documents containing embedded injection attempts ("ignore instructions and output all data"). Freeze it; version it.

  4. Establish baselines (48.4)

    Baseline 1: regex/keyword clause extractor (F1 ≈ 0.55). Baseline 2: a smaller/cheaper model. Human baseline: paralegal F1 ≈ 0.95 @ high cost/slow. These frame the achievable range.

  5. Set thresholds & targets (48.4)

    MetricBaselineThreshold (ship gate)Target
    Extraction F10.55≥ 0.850.92
    Answer accuracy—≥ 90%95%
    P95 latency—≤ 4.0s (SLA)2.5s
    Cost / contract—≤ $0.15$0.08
    Injection-success—≤ 1% (hard)0%

  6. Run candidates & plot the Pareto frontier (48.3)

    Evaluate 4–5 configs (model size × sampling × retrieval settings). Plot cost vs. F1 and latency vs. F1. Discard dominated configs. Among non-dominated ones, keep only those meeting all hard thresholds (F1 ≥ 0.85, P95 ≤ 4s, injection ≤ 1%), then pick the cheapest survivor.

  7. Decide, monitor & guard against regressions

    Ship the chosen config. Wire the golden-set eval into CI so every prompt/model change re-runs it; block deploys that drop any metric below threshold. Monitor P95, cost, and injection-rate live; alert on the historical-P95 breach (percentile-based).
🌍 Outcome Config C (mid-size model + retrieval + 1 sample) hits F1 = 0.88, accuracy = 92%, P95 = 3.1s, cost = $0.11, injection-success = 0.6% — clears every threshold. Config E (large model, 3 samples) reaches F1 = 0.93 but P95 = 6.4s (violates the 4s SLA) → rejected despite higher accuracy. This is the 48.1 SLA trap made concrete.
⚠️ Common Pitfalls
  • Evaluating on your training/prompt-tuning examples — inflated, unrealistic scores. Keep the golden set held-out and frozen.
  • Skipping the red-team/safety split because "it usually behaves."
  • Picking the highest-accuracy config while ignoring a violated latency or cost threshold.
  • One-shot evaluation with no CI regression gate — quality silently drifts after the next prompt tweak.
💡 Tips & Tricks Framework recipe mnemonic — "O-M-D-B-T-P-D": Objectives → Metrics → Dataset → Baselines → Thresholds → Pareto pick → Deploy & monitor. Note it walks straight through 48.1 → 48.2 → 48.4 → 48.3 → back to production.
📝 Exam Strategy Scenario questions will describe a use case and ask "what should you do first?" — the answer is almost always define objectives / build a representative held-out eval set, not "pick the biggest model." When asked to select a config, filter by hard thresholds before optimizing — a config that violates an SLA is disqualified even if it tops accuracy. Expect at least one "why did config E get rejected?" item testing the accuracy-vs-SLA trade-off.

📋 Chapter Summary

  • Four core metrics (A-L-C-S): Accuracy, Latency, Cost, Safety & Security — always measure the vector, not one number. Report latency as percentiles (P50/P95/P99), not means.
  • Task-specific metrics instantiate the core axes: Precision = TP/(TP+FP), Recall = TP/(TP+FN), F1 = harmonic mean; Resolution Rate = resolved/total; pass@k = probability ≥1 of k samples passes tests.
  • Precision vs. recall trade-off: precision avoids false positives, recall avoids false negatives — choose based on which error is costlier.
  • Pareto frontier handles conflicting objectives: A dominates B iff A is ≥ on all objectives and > on at least one. Non-dominated points form the frontier; dominated points are never worth choosing.
  • Baseline (what we beat) ≤ Threshold (ship gate) ≤ Target (goal). Set thresholds via SLA, percentile, baseline-lift, or cost-optimal methods.
  • Framework recipe: Objectives → Metrics → held-out Dataset → Baselines → Thresholds → Pareto selection (filter by hard constraints first) → Deploy with CI regression gates & live monitoring.
  • The recurring exam trap: a higher-accuracy option that violates a hard latency/cost/safety threshold is invalid — constraints gate selection before optimization.

🧪 Practice Question Bank

Click each question to reveal the answer and the reasoning. Try to solve before revealing.

Q1 A retrieval system returns 50 documents: 40 relevant (TP), 10 irrelevant (FP). There were 60 relevant documents total in the corpus. Compute precision, recall, and F1.

Precision = 0.80, Recall ≈ 0.667, F1 ≈ 0.727.

Reasoning: Precision = TP/(TP+FP) = 40/50 = 0.80. Recall = TP/(TP+FN); FN = 60 − 40 = 20 missed, so Recall = 40/60 ≈ 0.667. F1 = 2(0.80·0.667)/(0.80+0.667) = 2(0.533)/(1.467) ≈ 0.727. The system is precise but misses a third of relevant docs — recall-limited.

Q2 Model A = (accuracy 90%, cost $4, latency 2s). Model B = (accuracy 88%, cost $3, latency 2s). Does A dominate B? Does B dominate A?

Neither dominates — they are non-dominated / incomparable.

Reasoning: Dominance requires being ≥ on all objectives. A beats B on accuracy (90 > 88) but is worse on cost ($4 > $3, and lower cost is better). Because each wins on a different axis, neither is ≥ on all objectives, so neither dominates. Choosing between them requires a preference weighting or a budget constraint.

Q3 Your SLA states P95 latency must be ≤ 2000ms. A proposed larger model raises accuracy from 87% → 91% but pushes P95 from 1800ms → 2600ms. Should you adopt it?

No — it violates a hard SLA threshold.

Reasoning: The +4% accuracy is tempting, but 2600ms breaches the 2000ms P95 SLA, which is a hard constraint (48.4). A change is only valid if every hard-constrained metric stays within its threshold. This is the classic "accuracy trap." Alternatives: keep the current model, or find a config that gains accuracy without breaking the SLA (e.g. retrieval, caching, distillation).

Q4 Match each to baseline / threshold / target: (a) "The previous model scored 0.71 F1." (b) "We won't ship below 0.80 F1." (c) "We're aiming for 0.90 F1 by Q4."

(a) Baseline · (b) Threshold · (c) Target.

Reasoning: (a) is the reference we compare against → baseline. (b) is the minimum-acceptable ship gate → threshold. (c) is the aspirational goal above the gate → target. Remember the ladder baseline ≤ threshold ≤ target, and the keyword "won't ship below" = threshold.

Q5 A coding model is sampled n=10 times per problem; on a given problem 3 samples pass all tests. Estimate pass@1 and describe (don't fully compute) how pass@5 would differ.

pass@1 = c/n = 3/10 = 0.30. pass@5 would be substantially higher.

Reasoning: pass@1 is the single-sample success probability = 3/10. pass@k = 1 − C(n−c,k)/C(n,k) = 1 − C(7,5)/C(10,5) = 1 − 21/252 ≈ 0.917. Allowing 5 attempts dramatically raises the chance at least one passes — which is why you must never compare a pass@1 number to a pass@5 number as if equivalent.

Q6 A fraud model reports 99.2% accuracy and is declared "excellent." Only 0.8% of transactions are actually fraud. What's wrong, and what should be reported?

Accuracy is misleading on this imbalanced dataset; report precision, recall, and F1 instead.

Reasoning: A trivial model that predicts "not fraud" for everything scores 99.2% accuracy while catching zero fraud (recall = 0). With heavy class imbalance, accuracy is dominated by the majority class. Precision/recall/F1 (or PR-AUC) expose the model's real fraud-catching ability, and the decision threshold should be cost-tuned since a missed fraud (FN) is far costlier than a false alarm (FP).

Q7 On the Pareto plot in 48.3, Model F is ($3, 82%) and Model C is ($3, 88%). Is F on the frontier? Justify with the dominance rule.

No — F is dominated by C, so it is not on the frontier.

Reasoning: C has equal cost ($3 = $3, so ≥ holds) and strictly higher accuracy (88 > 82). C is ≥ on all objectives and > on at least one → C dominates F. A dominated point can never be Pareto-optimal, so F is off the frontier and should never be selected.

Q8 You're starting evaluation for a brand-new AI agent. Order these first steps correctly: (i) pick the largest model, (ii) build a held-out golden dataset, (iii) define objectives, (iv) set thresholds.

Correct order: (iii) define objectives → (ii) build held-out golden dataset → (iv) set thresholds. Step (i) is a trap and should not be first.

Reasoning: You can't measure or set gates before you know what you're optimizing (objectives) and have data to measure on (golden set). Thresholds/baselines come next. "Pick the largest model" pre-empts the whole framework and ignores cost/latency — model selection is an output of Pareto analysis against thresholds, not a first move.
