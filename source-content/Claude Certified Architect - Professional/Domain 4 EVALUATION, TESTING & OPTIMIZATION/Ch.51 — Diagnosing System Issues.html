51.1  Prompt Failure Diagnosis: When the Model Misunderstands

Definition

A prompt failure occurs when Claude produces an unhelpful, off-target, or malformed response not because the model lacks capability, but because the instruction it received was ambiguous, under-specified, contradictory, or poorly structured. The model does exactly what it was told — the problem is that what it was told did not match what the architect intended. This is the most common and most fixable failure class, and it should always be ruled out first because it is cheap to test.

Root Causes

  • Ambiguous instructions — vague verbs ("analyze this", "make it better") with no success criteria or output shape.
  • Missing context — the model is asked to reason about data, a document, or a persona that was never supplied in the prompt.
  • Contradictory constraints — e.g. "be extremely concise" alongside "explain every step in full detail."
  • Unstructured input — instructions, data, and examples run together with no delimiters, so the model cannot tell the task from the material.
  • Format under-specification — no explicit output schema (JSON keys, headings, length), leaving the model to guess.
  • Role/system-prompt drift — the system prompt sets one persona or policy while the user turn implies another.
  • Negation-only instructions — telling the model only what not to do without stating the desired behavior.

Diagnostic Signals

  • Answers are generic or hedging ("It depends on many factors…") when a specific answer was expected.
  • Output format is inconsistent across otherwise similar requests (sometimes prose, sometimes a list, sometimes JSON).
  • The model asks for clarification or restates the task instead of doing it.
  • The model solves the wrong problem — a coherent, well-written answer to a question you did not ask.
  • Only part of a multi-part instruction is addressed.
  • Failures disappear when you rephrase the prompt manually — a strong tell that the prompt, not the model, is at fault.

Diagnostic Workflow

# Prompt-failure isolation (run before suspecting anything else)
Step 1: Re-read the prompt literally. Did the model do exactly what the words say?
        → YES and result is wrong  → the instruction is the bug, not the model. Go Step 2.
        → NO, it ignored instructions → check delimiters & instruction placement (Step 4).

Step 2: Is the desired output shape explicitly stated (schema, length, headings)?
        → NO  → add an explicit output contract + 1 example. Re-test.
        → YES → Step 3.

Step 3: Was all required context actually in the prompt/context window?
        → NO  → this is a context / retrieval gap → jump to Section 51.4.
        → YES → Step 4.

Step 4: Are instructions clearly separated from data (XML tags / headings)?
        → NO  → wrap data in delimiters, move instructions to a stable position. Re-test.
        → YES → Step 5.

Step 5: Are any two constraints in conflict?
        → YES → remove/re-rank the conflicting constraint. Re-test.
        → NO  → prompt is sound; escalate to model-mismatch (51.3) or hallucination (51.2).

Mitigation Strategies (ranked low→high effort)

  1. Low effort Add an explicit output contract — state format, length, and required fields. Often fixes the issue outright.
  2. Low effort Delimit structure — wrap supplied data in XML-style tags (e.g. <document>…</document>) so the model separates task from material. Claude responds particularly well to XML tags.
  3. Medium Add 1–3 few-shot examples showing an input and the exact desired output.
  4. Medium Move stable instructions into the system prompt; keep only the variable task in the user turn.
  5. Medium Ask Claude to reason step-by-step (or enable extended thinking) for multi-constraint tasks so intermediate logic is visible.
  6. Higher Prompt-test harness — a small eval set of representative inputs with expected outputs, run on every prompt change to catch regressions.
💡 Tips & Tricks
  • Put the long, stable material first, the instruction last. Claude follows the most recent instruction most reliably, and putting reusable content (documents, examples) at the top also makes it eligible for prompt caching.
  • Prefer positive instructions. "Respond in exactly two sentences" beats "don't be too long."
  • The 30-second manual test: paste the same prompt into a fresh chat and rephrase it yourself. If the rephrase fixes it, it was a prompt failure — no code change needed.
⚠️ Exam Strategy

Prompt-failure questions typically show you a prompt + a disappointing output and ask for the single best fix. The trap answer usually says "switch to a larger model" — but if the output is coherent and simply off-target, the model is fine and the prompt is the defect. Watch for keywords like "ambiguous," "no output format specified," "instructions and data mixed together." When a question emphasizes that the answer was well-written but wrong, choose the prompt-engineering fix, not a model upgrade.

51.2  Hallucination Detection and Mitigation

Definition

A hallucination is a confident, fluent, plausible-sounding output that is not grounded in the provided sources or in verifiable fact — a fabricated citation, invented statistic, non-existent API, or a claim the model cannot support. The danger is stylistic: hallucinations read exactly like correct answers. Unlike a prompt failure (wrong because of the instruction), a hallucination is wrong despite a reasonable instruction, because the model filled a knowledge gap with a probabilistically likely — but false — completion.

Root Causes

  • No grounding sources — the model is asked a factual question with nothing authoritative in context, so it draws on parametric memory that may be wrong or outdated.
  • Retrieved context is missing the answer — the model, primed to be helpful, "completes" the gap rather than admitting it (this overlaps with 51.4).
  • Leading or presuppositional prompts — "Summarize the three risks the report lists" when the report lists none pressures the model to invent three.
  • Long-context dilution — the relevant fact is buried among large amounts of loosely related text, weakening grounding.
  • High temperature / sampling — more randomness increases the chance of confident invention on factual tasks.
  • No permission to say "I don't know" — the instruction implicitly forbids uncertainty.

Diagnostic Signals

  • Fabricated references — citations, URLs, case numbers, or file names that do not exist in the sources.
  • Over-specific detail with no traceable origin (exact figures, dates, quotations not present in context).
  • Answer contradicts the supplied source when you check line by line.
  • Uniform confidence — the same assured tone for things it knows and things it cannot know.
  • Instability — re-running the same query yields different "facts" each time.
  • Named entities/APIs that don't exist in the domain.

Diagnostic Workflow

# Is this output grounded? Trace every load-bearing claim.
Step 1: List the factual claims in the answer.
Step 2: For each claim, can you point to a supporting span in the provided context?
        → YES for all → not a hallucination; may be a retrieval or prompt issue instead.
        → NO for some → those claims are ungrounded. Go Step 3.
Step 3: Was the supporting fact ever retrieved / supplied at all?
        → NO, it was never in context → the model invented it → 51.2 hallucination.
        → YES, it was in context but the model contradicted it → grounding/attention issue:
             tighten the prompt to "answer ONLY from the context; quote the source."
Step 4: Does the answer degrade at high temperature and stabilize at temp≈0?
        → YES → lower temperature for factual tasks.
Step 5: Add an explicit escape hatch ("If the answer is not in the context, say 'Not stated.'").
        Re-test: does the model now abstain instead of inventing?

Mitigation Strategies (ranked low→high effort)

  1. Low effort Grant permission to abstain — instruct the model to answer only from context and say "I don't know" / "Not stated" otherwise.
  2. Low effort Lower temperature to near 0 for factual/extraction tasks.
  3. Medium Ground with retrieval — supply authoritative source text (RAG) rather than relying on parametric memory.
  4. Medium Require inline citations / quotes — ask the model to quote the exact supporting span for each claim, making fabrication self-evident.
  5. Medium Ask it to reason first, answer second (extended thinking / "think step by step") so unsupported leaps are visible before the final answer.
  6. Higher Add a verification pass — a second Claude call that checks each claim in the draft against the sources and flags anything unsupported before the answer is returned.
💡 Tips & Tricks
  • "Quote-then-answer" is the cheapest anti-hallucination pattern. Force the model to first extract verbatim supporting quotes, then answer using only those quotes. If it can't find a quote, it can't fabricate one convincingly.
  • Ungrounded ≠ wrong-model. Upgrading to a larger model reduces but does not eliminate hallucination — grounding is the real fix.
  • Re-run at temp 0 twice. Identical answers suggest a deterministic (possibly grounded) response; wildly different "facts" scream fabrication.
⚠️ Exam Strategy

Hallucination questions almost always present a plausible-sounding but false Claude response — often with a fake citation. Scan the answer choices for the keywords "fabricated," "unverifiable," "not grounded in source," "no supporting evidence." The correct remediation on the exam is usually grounding + verification (retrieval, quote-then-answer, an "abstain" instruction), not "increase max tokens" or "raise temperature." If a scenario says the model invented a source, the answer is a grounding/citation control — never a creativity setting.

51.3  Model Mismatch: When the Wrong Model Is Deployed

Definition

Model mismatch is a configuration failure: the prompt and grounding are fine, but the deployed Claude variant is poorly matched to the task's difficulty, latency budget, or cost profile. The Claude family spans tiers — broadly, Haiku (fastest, cheapest, best for high-volume, simpler tasks), Sonnet (balanced general-purpose reasoning), and Opus (highest capability for the hardest reasoning). Deploying too small a model for a complex task yields shallow reasoning; deploying too large a model for a trivial, high-volume task wastes latency and cost. Mismatch also covers wrong configuration: truncated max output tokens, an unsuitable context window, or extended thinking left off for a task that needs deep reasoning.

Root Causes

  • Undersized model for a hard task — complex multi-step reasoning, nuanced code, or long-document synthesis routed to a lightweight tier.
  • Oversized model for a trivial task — simple classification or extraction on a top tier, hurting latency and cost with no quality gain.
  • Truncated max_tokens — the output limit cuts answers off mid-sentence (looks like a "capability" problem but is a config problem).
  • Context window too small for the input, forcing silent truncation of earlier content.
  • Extended thinking disabled on tasks that need deliberate reasoning, or enabled where it only adds latency.
  • Version drift — pinned to an older snapshot while newer, more capable versions exist; or an unpinned alias changing behavior underneath the app.
  • Uniform routing — one model for every request instead of routing by task complexity.

Diagnostic Signals

  • Quality ceiling — reasoning is consistently shallow or error-prone on hard cases even after prompt tuning (undersized).
  • Truncated / cut-off answers ending mid-sentence — check max_tokens and the stop reason.
  • Latency or cost out of line with task value — slow, expensive responses to trivial requests (oversized).
  • Inconsistent quality after a deploy with no prompt change — a version/alias changed underneath you.
  • Good on short inputs, degrades on long ones — likely context-window truncation.

Diagnostic Workflow

# Prompt & grounding already ruled out (51.1, 51.2). Now the model config.
Step 1: Did the response end mid-sentence / abruptly?
        → YES → check stop reason & max_tokens. If "max_tokens", raise the output limit. Done.
        → NO → Step 2.
Step 2: Is the input near or over the model's context window?
        → YES → earlier content was truncated → enlarge window or chunk/summarize input.
        → NO → Step 3.
Step 3: Is reasoning shallow on genuinely hard cases despite a clean prompt?
        → YES → upgrade one tier (Haiku→Sonnet→Opus) and/or enable extended thinking. Re-eval.
        → NO → Step 4.
Step 4: Is the task trivial but latency/cost high?
        → YES → downgrade a tier; consider routing simple traffic to Haiku.
Step 5: Did behavior shift with no code change?
        → YES → confirm the exact model version/snapshot; pin it to stop drift.

Mitigation Strategies (ranked low→high effort)

  1. Low effort Fix output limits first — raise max_tokens and confirm the stop reason before touching the model tier.
  2. Low effort Pin the model version to a specific snapshot to eliminate drift.
  3. Medium Right-size the tier — upgrade for hard reasoning, downgrade for trivial high-volume work.
  4. Medium Toggle extended thinking for deliberate reasoning tasks; disable it where it only adds latency.
  5. Higher Complexity-based routing — a cheap classifier sends simple traffic to Haiku and hard traffic to Sonnet/Opus, optimizing cost and quality together.
  6. Higher Tier A/B eval — run the same eval set across tiers to justify the choice with data rather than intuition.
💡 Tips & Tricks
  • Always check the stop reason before blaming the model. A cut-off answer with stop reason max_tokens is a config fix, not a capability upgrade — and far cheaper.
  • Bigger is not always better. On simple, high-volume tasks a smaller tier is often more reliable end-to-end because it's faster and cheaper, letting you add verification passes within the same budget.
  • Pin versions in production. Unpinned aliases can shift model behavior on their own schedule and produce "mystery regressions."
⚠️ Exam Strategy

Model-mismatch questions describe a working prompt whose output is either cut off, too shallow, or needlessly slow/expensive. First distinguish a truncation problem (raise max_tokens / enlarge context) from a capability problem (change tier). The classic trap: a truncated answer that looks like the model "couldn't finish" — the correct fix is the output-token limit, not a model upgrade. Watch for keywords "cut off," "mid-sentence," "stop reason," "latency," "cost per request," "shallow reasoning," "version/snapshot."

51.4  Retrieval Failures: Stale Chunks, Broken Indexes & Mismatched Embeddings

Definition

A retrieval failure occurs in a RAG system when the wrong context — or no useful context — is fed to Claude, so even a perfect prompt and a perfectly capable model produce a wrong answer. The generation step is only as good as what the retriever hands it: garbage in, confident garbage out. Retrieval failures are especially deceptive because the model's answer is fluent and grounded-looking — it simply grounds on the wrong material. This section covers the retrieval pipeline: chunking → embedding → indexing → query embedding → similarity search → (optional) reranking → context assembly.

Root Causes

  • Stale index — source documents changed but the vector store was never re-embedded, so old content is retrieved.
  • Embedding model mismatch — documents were embedded with one model and queries are embedded with a different one (or a new version), so vectors live in incompatible spaces and similarity is meaningless.
  • Broken / partial index — an ingestion job failed silently; some documents were never indexed (missing recall) or indexed twice (duplicates).
  • Poor chunking — chunks too large (diluted, off-topic context) or too small (answer split across chunk boundaries and never fully retrieved).
  • Dimension / metric mismatch — index configured with the wrong vector dimensionality or distance metric (cosine vs. dot vs. Euclidean).
  • Weak query — user query phrased very differently from source wording; pure vector search misses it (a lexical/hybrid signal would have caught it).
  • No reranking — top-k by raw similarity returns loosely related chunks ahead of the truly relevant one.
  • Metadata / access filters silently excluding the relevant documents.

Diagnostic Signals

  • Outdated answers despite correct, updated source docs — the hallmark of a stale index.
  • Confident answers grounded in the wrong document — retrieval returned irrelevant chunks.
  • "I couldn't find that" for content you know exists — missing from the index or filtered out.
  • Uniformly poor retrieval across all queries — a systemic cause: embedding mismatch, wrong metric, or empty/broken index.
  • Relevant chunk exists but ranks below junk — a reranking / chunking problem.
  • Similarity scores all near-identical or near-zero — a red flag for dimension/metric or embedding-space mismatch.

Diagnostic Workflow

# Inspect the RETRIEVED context directly — never diagnose from the final answer alone.
Step 1: Log & read the exact chunks retrieved for the failing query. Is the answer text present?
        → NO, correct chunk not retrieved → retrieval defect → Step 2.
        → YES, correct chunk WAS retrieved → not retrieval; revisit prompt (51.1) / hallucination (51.2).
Step 2: Does the source contain the up-to-date answer, but retrieval returns old text?
        → YES → STALE INDEX → re-embed & refresh the index. Done.
Step 3: Is retrieval bad for EVERY query (not just one)?
        → YES → systemic: verify query and docs use the SAME embedding model/version,
             and the index dimension & distance metric match that model. Fix & re-embed.
        → NO, only some queries → Step 4.
Step 4: Does the relevant chunk exist in the index but rank too low?
        → YES → improve chunking (size/overlap), add hybrid (keyword+vector) search, add a reranker.
        → NO, chunk absent entirely → ingestion gap → re-run indexing; check failed docs & filters.
Step 5: Are metadata/access filters excluding the doc?
        → YES → correct the filter scope. Re-test.

Mitigation Strategies (ranked low→high effort)

  1. Low effort Log & inspect retrieved chunks for failing queries — the single highest-value diagnostic step.
  2. Low effort Re-embed & refresh the index when sources change (fixes staleness); schedule regular re-indexing.
  3. Medium Guarantee embedding-model parity — pin one embedding model+version for both documents and queries; re-embed everything on any change.
  4. Medium Verify index config — dimensionality and distance metric must match the embedding model.
  5. Medium Tune chunking — right-size chunks with sensible overlap so answers aren't split across boundaries.
  6. Medium Add hybrid retrieval — combine keyword (lexical) with vector search to catch wording mismatches.
  7. Higher Add a reranker — re-score top-k candidates so the truly relevant chunk surfaces to the top.
  8. Higher Retrieval evals — measure recall@k / precision on a labeled query set to catch regressions before users do.
💡 Tips & Tricks
  • Never debug a RAG failure from the final answer. Print the retrieved chunks first. In >70% of "the model is wrong" RAG cases, the model was handed the wrong context.
  • "Bad for one query" vs. "bad for all" is the fastest split: all-queries-bad → systemic (embeddings/metric/empty index); one-query-bad → chunking/ranking/coverage.
  • Embedding parity is non-negotiable. If you upgrade the embedding model, you must re-embed the entire corpus — mixing spaces silently destroys similarity.
⚠️ Exam Strategy

Retrieval questions hinge on one tell: the docs are correct but the answer is outdated or off-base. "Outdated answers despite correct/updated documents" → stale index, re-embed. "Retrieval broke for all queries after we swapped the embedding model" → embedding mismatch, re-embed with a single aligned model. "The right passage exists but isn't retrieved" → chunking + reranking + hybrid search. Watch for "stale," "re-embed," "embedding mismatch," "index," "top-k," "cosine similarity," "chunk." The trap answer blames the model or prompt when the scenario clearly points to the retrieval pipeline.

51.5  Hands-On: Debugging a Failing Claude Application

This walkthrough applies the logic from 51.1–51.4 to a single realistic incident. Follow the reasoning, not just the fix — the exam tests whether you can isolate a failure, not merely recognize one.

The Scenario

System: "PolicyBot", an internal HR RAG assistant. It embeds HR policy PDFs into a vector store and answers employee questions with Claude Sonnet. It worked well at launch three months ago.

The complaint (ticket #4471): Since the company raised parental leave from 12 to 16 weeks last week, PolicyBot still tells employees the entitlement is 12 weeks — confidently, and it even cites "Section 4.2 of the HR Handbook."

Symptom capture

User: How many weeks of paid parental leave do I get?
PolicyBot: You are entitled to 12 weeks of paid parental leave,
          as stated in Section 4.2 of the HR Handbook.
# Ground truth (updated last week): 16 weeks. The answer is confident, fluent, and WRONG.

Step 1 — Rule out prompt failure (51.1)

The prompt is unchanged and previously produced correct answers. The output is well-formed and directly answers the question — it is simply factually wrong. A prompt failure would show as off-target or malformed output, not a confidently wrong fact. We manually re-ran the same prompt against the updated policy text pasted directly into context:

Prompt (manual test, policy pasted inline):
"Using ONLY the policy below, how many weeks of paid parental leave?
<policy> ...paid parental leave of 16 weeks... </policy>"
Claude: "16 weeks, per the provided policy."   # Correct when given the right context.

Conclusion: With the correct context, Claude answers correctly. The prompt and model are not the problem. → Move on.

Step 2 — Is it hallucination? (51.2)

It looks like one — a confident wrong number and a cited section. But hallucination means ungrounded invention. Here the "12 weeks / Section 4.2" claim is suspiciously specific and internally consistent, which suggests the model is grounded — just on the wrong (old) material. We confirm by inspecting what was actually retrieved rather than trusting the answer.

Step 3 — Inspect the retrieved chunks (51.4, Step 1)

# Logged retrieval for the query "paid parental leave weeks"
retrieved_chunks = [
  {
    "doc_id": "hr_handbook_v3.pdf",
    "chunk": "...eligible employees receive 12 weeks of paid parental leave (Section 4.2)...",
    "similarity": 0.91,
    "indexed_at": "2026-06-20"        # <-- three months old
  }
]
# The updated file hr_handbook_v4.pdf (16 weeks, ingested 2026-09-18) is NOWHERE in the results.

The retriever confidently returned the old handbook. Claude grounded on it faithfully and cited it accurately. This is not a hallucination — the model reported exactly what it was given. It is a retrieval failure.

Step 4 — Which retrieval failure? (51.4 workflow)

Following the 51.4 decision tree:

  • Is the source updated but old text returned? The updated PDF exists on disk (v4, 16 weeks), yet only v3 appears in the index. → Strong signal of a stale / broken index, not an embedding-space mismatch (retrieval is fine for other, unchanged queries, so it's not systemic).

We check the ingestion logs:

# ingestion.log
2026-09-18 02:00:11  INFO  Ingest start: hr_handbook_v4.pdf
2026-09-18 02:00:12  ERROR PDF parse failed: encrypted stream, 0 chunks produced
2026-09-18 02:00:12  WARN  hr_handbook_v4.pdf skipped; previous version retained
# Root cause surfaced: the new PDF was password-protected, parsing failed,
# the job skipped it silently, and the STALE v3 vectors were left serving traffic.

Step 5 — Root cause & fix

Root cause: A stale index caused by a silent ingestion failure. The updated policy PDF was encrypted; parsing produced zero chunks; the pipeline skipped it without alerting; the old 12-week vectors kept being retrieved. Claude was never wrong about its input — it faithfully reported stale context.

The fix (ordered):

  1. Decrypt / re-export hr_handbook_v4.pdf as a parseable file.
  2. Re-ingest and re-embed; verify the 16-week chunk now exists in the index and that v3 is removed or superseded.
  3. Re-run the failing query and confirm the correct chunk is retrieved (similarity + indexed_at current).
  4. Prevent recurrence: fail the ingestion job loudly on zero-chunk output (alert, don't silently skip); add a freshness check comparing source modified dates against indexed_at; add a retrieval eval that asserts the current parental-leave figure.
  5. Defense in depth: add an "answer only from retrieved context and cite the source date" instruction so a future stale hit is at least visibly dated.
# After re-embedding — verification run
User: How many weeks of paid parental leave do I get?
PolicyBot: You are entitled to 16 weeks of paid parental leave
           (HR Handbook v4, Section 4.2, effective 2026-09-18).   # Correct & current.

🔎 The meta-lesson

The most dangerous failures look like the wrong category. This one presented as a hallucination (confident, cited, wrong) but was a retrieval-pipeline defect. The disciplined move — inspect the actual retrieved context before blaming the model — is what separates a guess from a diagnosis.

⏱️ 5-Minute Review (last-minute exam prep)
  • Diagnose in order of cost: prompt (cheapest) → hallucination → model config → retrieval. Rule out the cheap cause before the expensive one.
  • Prompt failure = coherent but wrong-target. Fix with output contracts, delimiters (XML tags), and few-shot examples — not a bigger model.
  • Hallucination = confident + ungrounded. Fix with grounding, inline citations/quotes, an "abstain" instruction, and low temperature. A bigger model reduces but never eliminates it.
  • Model mismatch: a cut-off answer with stop reason max_tokens is a config fix (raise the limit), not a capability fix. Right-size the tier; pin versions to avoid drift.
  • Retrieval failure = right docs, wrong answer. Stale index → re-embed. All-queries-bad → embedding/metric mismatch. One-query-bad → chunking + hybrid search + reranker. Always read the retrieved chunks first.
  • Golden rule: never diagnose a RAG failure from the final answer — inspect the retrieved context. "Confident + cited" can still be a retrieval bug.
  • Keyword map: "ambiguous / no format" → 51.1 · "fabricated / unverifiable / not grounded" → 51.2 · "cut off / stop reason / shallow / latency" → 51.3 · "stale / re-embed / embedding mismatch / top-k" → 51.4.
⚠️ Exam-day meta-strategy

When a scenario question feels ambiguous, map its keywords to the table above and pick the fix that matches the signal, not the surface impression. The most common trap across all five sections is the tempting "upgrade the model" answer — correct only for genuine capability gaps (51.3), and wrong for prompt (51.1), grounding (51.2), and retrieval (51.4) problems.
