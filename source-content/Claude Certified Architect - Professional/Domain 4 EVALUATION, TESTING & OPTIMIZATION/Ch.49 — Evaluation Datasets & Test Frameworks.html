49.1 Designing Representative Evaluation Datasets

An evaluation dataset is only useful if it mirrors the distribution of real production inputs. A representative set lets a passing score on the eval predict a passing experience for users. If the eval over-samples easy or convenient inputs, the score becomes an optimistic illusion that masks real-world failure modes.

Key Concepts

  1. Sampling strategy. Prefer stratified sampling — partition production traffic by meaningful dimensions (intent, input length, language, user segment) and sample within each stratum so rare-but-important cases are not drowned out by high-volume ones.
  2. Use-case coverage. Enumerate the tasks the system must handle and confirm every task has enough examples to produce a statistically meaningful signal — not just the one or two flagship flows.
  3. Input diversity. Vary phrasing, formatting, length, tone, domain vocabulary, and language so the model is not evaluated on a single narrow style of prompt.
  4. Bias avoidance. Watch for selection bias (cherry-picking clean examples), survivorship bias (only successful past sessions), and temporal drift (last quarter's traffic no longer reflects today's).
  5. Label quality. Expected outputs / rubrics must be defined by someone who understands "good," with clear, reproducible criteria — ambiguous labels poison every downstream metric.

⚠️ Common Pitfalls
  • Convenience sampling: building the set from whatever logs are easiest to grab, skewing toward power users or one channel.
  • Over-representing the happy path: 95% easy inputs makes the eval score look great while production breaks on the tail.
  • Static forever: never refreshing the sample as traffic evolves, so the eval quietly stops representing reality (distribution drift).
  • Leaky examples: pulling eval items from the same data used to craft prompts/few-shots, inflating scores.
💡 Tips & Tricks
  • Start from a production traffic sample, then top up under-covered strata with hand-authored cases rather than the reverse.
  • Keep a coverage checklist (like the matrix above) and mark each dimension's example count — gaps become obvious.
  • Weight by risk × frequency, not frequency alone: a rare but high-impact failure deserves more eval mass than its raw share.
  • Version the dataset and record how it was sampled, so a reviewer can reason about what a score does and does not cover.
📌 How to Answer Exam Questions

Common patterns: "Your eval scores are high but users report failures — what is the most likely cause?" or "Which sampling strategy best ensures rare intents are represented?"

  • Watch for: "representative," "distribution," "stratified," "coverage," "bias." These flag this subtopic.
  • Elimination: answers that maximize quantity ("just add 10,000 random examples") are usually traps — representativeness beats raw volume.
  • If a scenario says the eval looks good but production is bad, favor the option about unrepresentative / biased sampling over options about model size or temperature.
  • "Stratified sampling" is almost always the correct choice when the stem stresses covering rare or minority cases.

49.2 Mixed Methodologies: Automated, Human & Hybrid Evaluation

No single evaluation method is best for everything. Mature evaluation stacks combine methods: cheap automated checks run on every change at scale, human review handles nuance and judgment, and hybrid approaches (including LLM-as-judge with human calibration) bridge the two. The architect's job is to route each quality question to the cheapest method that answers it reliably.

Key Concepts

  • Automated evaluation — deterministic checks (exact/regex match, schema validation, unit-test-style assertions) and metric scorers. Also includes LLM-as-judge, where a model grades outputs against a rubric. Fast and cheap, but only as trustworthy as its criteria.
  • Human evaluation — expert or crowd raters judge quality, tone, safety, and correctness. The gold standard for nuance, but slow, costly, and subject to rater variance.
  • Hybrid evaluation — automated scorers do the first pass at scale; humans review disagreements, low-confidence items, and a calibration sample. LLM-judges are validated against human labels before being trusted.

*Automated nuance accuracy depends entirely on the scorer: exact-match is objective but brittle; LLM-as-judge handles nuance better but must be validated against human labels first.

⚠️ Common Pitfalls
  • Trusting an LLM-judge blind: deploying it without measuring agreement with human labels — its errors then look like ground truth.
  • Over-relying on exact match for open-ended tasks: penalizing correct answers that are phrased differently.
  • Ignoring inter-rater reliability: humans disagree; a single unreliable rater is noise, not signal.
  • Using slow human review inside a fast CI loop, so testing becomes a bottleneck and gets skipped.
💡 Tips & Tricks
  • Match method to question: objective & high-volume → automated; subjective & high-stakes → human; scale + nuance → hybrid.
  • Always calibrate an LLM-judge against a human-labeled subset and report the agreement rate before relying on it.
  • Use humans where they are irreplaceable (tone, safety, edge judgment) and automate the rest to keep them focused.
  • Track inter-annotator agreement (e.g., percent agreement or a kappa statistic) to know how much to trust human labels.
📌 How to Answer Exam Questions

Common patterns: "Which evaluation method is most appropriate for [scenario]?" — where scenario stresses scale, cost, nuance, or safety.

  • Key terms: "at scale / every commit" ⇒ automated; "tone, empathy, safety, subjective" ⇒ human; "production readiness / best of both" ⇒ hybrid.
  • Elimination: "human review on every deploy" is usually a trap — too slow/expensive for CI. "LLM-judge, no validation" is a trap — must be calibrated.
  • If the stem mentions both large volume and subtle quality, the answer is almost always hybrid, not a single method.

49.3 Golden Datasets, Edge Cases & Adversarial Examples

Three complementary test-data types stress a system in different ways. A golden dataset is a curated, stable reference of inputs with verified expected outputs — the anchor for regression. Edge cases probe the boundaries of valid input. Adversarial examples are crafted to break the system: to induce unsafe, incorrect, or policy-violating behavior.

Key Concepts & Definitions

Test-data types, what they contain, and how they are built.
TypeDefinitionKey PropertyConstruction
Golden dataset Curated inputs paired with verified, high-confidence expected outputs / acceptance criteria. Static & version-controlled — changes are deliberate and reviewed, not constant. Expert-labeled, peer-reviewed, stored under version control with a changelog.
Edge cases Rare-but-valid inputs at the boundaries: empty input, maximum length, unusual formatting, ambiguous requests. Tests robustness to legitimate but uncommon input. Enumerate input boundaries; mine the long tail of real traffic; brainstorm "what breaks?"
Adversarial examples Inputs deliberately designed to elicit failure, unsafe output, or policy violations. Tests resilience under hostile pressure. Red-teaming, prompt-injection attempts, known jailbreak patterns, systematic perturbation.

Adversarial Prompt Categories

  • Prompt injection: embedded instructions that try to override the system prompt ("ignore previous instructions and…").
  • Jailbreak / role-play framing: attempts to bypass safety by reframing the request as fiction, hypothetical, or a persona.
  • Data exfiltration: attempts to extract the system prompt, hidden context, or other users' data.
  • Distraction / obfuscation: encoding, translation, or padding used to smuggle a disallowed request past filters.
  • Boundary probing: off-topic, out-of-scope, or nonsensical inputs to test graceful refusal and scope adherence.
⚠️ Common Pitfalls
  • Treating the golden set as living: constantly rewriting expected outputs destroys its value as a stable regression anchor.
  • No provenance for labels: golden outputs with no reviewer or rationale can't be trusted or defended.
  • Adversarial set that never grows: attackers evolve; a frozen red-team set gives false confidence.
  • Mixing categories carelessly: letting edge cases and adversarial cases blur so failures can't be attributed.
💡 Tips & Tricks
  • Keep the golden set small, high-quality, and stable; keep the adversarial set growing as new attack patterns emerge.
  • When a real incident occurs, distill it into a new adversarial or edge test case so the same failure can never regress silently.
  • Tag every case with its type and category — it makes failure triage and reporting far faster.
  • Change golden expected-outputs only through a reviewed, version-controlled process, never ad hoc.
📌 How to Answer Exam Questions

Common patterns: "What is the key property of a golden dataset?" or "Which category does [example prompt] belong to?"

  • Golden = static + version-controlled. Distractor answers say it should be "continuously updated," "auto-generated," or "the largest possible set" — these are traps.
  • Edge vs. adversarial: edge = valid but rare (robustness); adversarial = crafted to break (resilience/safety). If the input is hostile/malicious, it's adversarial.
  • Watch for: "ignore previous instructions" ⇒ prompt injection; "pretend you are…" ⇒ jailbreak framing.
  • Answers describing red-teaming or systematic perturbation point to adversarial construction.

49.4 Regression Testing for Prompt & Model Changes

Any change — a reworded prompt, a new few-shot example, a model version upgrade, a temperature tweak — can silently degrade behavior that used to work. Regression testing re-runs a fixed evaluation suite before and after a change and compares results, turning "seems fine" into a measured, gated decision to approve or roll back.

Key Concepts

  • Baseline: the recorded scores of the current, known-good configuration on the eval suite.
  • Candidate: the new prompt/model configuration under test.
  • Diff / comparison: per-case and aggregate deltas — crucially, catch per-case regressions even when the aggregate score is flat or improves.
  • Gate: an explicit pass/fail rule (e.g., "no critical case regresses AND aggregate ≥ baseline") that decides approve vs. rollback.
  • Rollback: reverting to the baseline configuration when the gate fails.

⚠️ Common Pitfalls
  • Aggregate-only comparison: a flat average can hide that 10 cases improved and 10 critical ones broke. Always inspect per-case deltas.
  • Moving the dataset with the change: if the eval set changes at the same time as the prompt, the comparison is meaningless.
  • Non-deterministic noise mistaken for regression: run enough samples (or fix seeds where possible) to separate real drops from sampling variance.
  • No gate defined up front: deciding "is this good enough?" after seeing results invites rationalizing a bad release.
💡 Tips & Tricks
  • Freeze the eval dataset and change one variable at a time so any delta is attributable.
  • Define the gate criteria before running — e.g., zero critical-case regressions, aggregate not below baseline minus tolerance.
  • Automate regression in CI so every prompt/model change is tested by default, not on request.
  • Store baseline results as an artifact; when you approve a candidate, promote its scores to the new baseline.
📌 How to Answer Exam Questions

Common patterns: "Aggregate score improved but users regressed — what did the process miss?" or "What must stay constant when regression testing a prompt change?"

  • Watch for: "baseline," "regression," "roll back," "gate," "per-case." The answer usually protects a stable baseline and a fixed dataset.
  • Elimination: options that change the dataset and the prompt together are wrong. Options relying only on the average metric are traps.
  • When the stem shows aggregate up but real quality down, choose the answer about inspecting per-case regressions.
  • "What stays constant?" ⇒ the evaluation dataset (and gate criteria). Only the change-under-test should vary.

49.5 Hands-On: Building an Evaluation Test Suite

This section assembles the previous four into a concrete, minimal test harness. The pattern mirrors software unit testing: load a versioned dataset of cases, run the system under test on each input, score the output with one or more scorers (automated assertions and/or an LLM-judge), aggregate, and compare against a baseline to gate the change.

Step-by-Step Walkthrough

  1. Define the dataset schema. Each case has an id, an input, an expected (or rubric), and metadata like category and critical.
  2. Store cases under version control (e.g., JSON/YAML). Golden cases are stable; add edge and adversarial cases over time.
  3. Implement scorers. Mix objective checks (exact/contains/schema) with a rubric-based LLM-judge for open-ended quality — after validating the judge against human labels.
  4. Run the system under test on every input, capturing outputs and any errors.
  5. Aggregate per-category and overall pass rates; flag any critical-case failure.
  6. Compare to baseline and apply the gate: approve and promote, or fail and roll back.
  7. Wire into CI so the suite runs on every prompt/model change.

Visualization — Sample Test Harness (Python-style pseudo-code)

# --- 1. Versioned dataset of eval cases (stored in git) ---
import json

def load_cases(path):
    return json.load(open(path))   # [{id, input, expected, category, critical}]

# --- 2. Scorers: objective + rubric-based judge ---
def exact_match(output, expected):
    return output.strip() == expected.strip()

def contains_required(output, keywords):
    return all(k.lower() in output.lower() for k in keywords)

def llm_judge(output, rubric):
    # Ask a model to grade output against rubric; return True/False or score.
    # NOTE: validate this judge against human labels before trusting it.
    return judge_model.grade(output, rubric)

# --- 3. Run system-under-test on each case ---
def run_case(case, system):
    output = system.generate(case["input"])
    if case.get("expected_type") == "exact":
        passed = exact_match(output, case["expected"])
    else:
        passed = llm_judge(output, case["rubric"])
    return {"id": case["id"], "passed": passed,
            "critical": case.get("critical", False), "output": output}

# --- 4. Aggregate results ---
def evaluate(system, cases):
    results = [run_case(c, system) for c in cases]
    total = len(results)
    passed = sum(r["passed"] for r in results)
    critical_fail = [r for r in results if r["critical"] and not r["passed"]]
    return {"pass_rate": passed / total, "critical_fail": critical_fail,
            "results": results}

# --- 5. Regression gate: compare candidate to baseline ---
def gate(candidate, baseline, tolerance=0.0):
    no_critical = len(candidate["critical_fail"]) == 0
    not_worse   = candidate["pass_rate"] >= baseline["pass_rate"] - tolerance
    return "APPROVE" if (no_critical and not_worse) else "ROLLBACK"

# --- 6. Wire together (this is what CI runs on every change) ---
cases    = load_cases("eval/cases.json")
baseline = json.load(open("eval/baseline.json"))
candidate = evaluate(current_system, cases)
decision  = gate(candidate, baseline)
print(decision, candidate["pass_rate"])
assert decision == "APPROVE", "Regression detected — blocking release"
⚠️ Common Pitfalls
  • No critical flag: treating a safety failure the same as a stylistic miss lets a dangerous regression pass the aggregate.
  • Hard-coding the baseline in the test: store it as a promotable artifact instead, so approvals update it cleanly.
  • Unvalidated LLM-judge: shipping the judge as ground truth without measuring its agreement with humans.
  • Non-reproducible runs: not recording model version, prompt version, and dataset version alongside results.
💡 Tips & Tricks
  • Keep the harness framework-agnostic: cases in, results out. Swap scorers without touching the runner.
  • Record version stamps (dataset, prompt, model) in every result file for reproducibility and audit.
  • Separate critical from non-critical gates so a minor style dip doesn't block a release and a safety break always does.
  • Make failures actionable: log the failing input and output so a human can triage without re-running.
📌 How to Answer Exam Questions

Common patterns: "What component makes a test suite gate a release?" or "Where should an LLM-judge be validated in this pipeline?"

  • Watch for: "gate," "baseline comparison," "critical case," "CI." The correct answer ties the pass/fail decision to a defined threshold vs. baseline.
  • Elimination: answers that "always approve if the average improved" ignore critical failures — trap. Answers that use an LLM-judge with no human validation — trap.
  • If asked what belongs in version control, choose the dataset, the baseline, and the prompt versions — not the raw model outputs alone.

Chapter Summary & Quick-Reference Recap

Evaluation is the discipline that turns "the model feels good" into a measured, defensible claim. Design data that represents reality, pick the cheapest reliable method per question, anchor on stable golden data while continuously growing adversarial coverage, and gate every change against a baseline using a repeatable test suite.

One-line recap of each subtopic and its single most exam-critical idea.

49.2 Mixed methodologies Automated for scale, human for nuance/safety, hybrid for production readiness. Trusting an LLM-judge without validating it against humans.
49.3 Golden / edge / adversarial Golden = static & version-controlled; edge = valid-but-rare; adversarial = crafted to break. Constantly rewriting the golden set (it's a stable anchor).
49.4 Regression testing Baseline → change → re-run → diff → gate (approve/rollback); inspect per-case deltas. Comparing aggregate only, or changing the dataset with the prompt.

📌 Exam-Day Mental Checklist
  • Representative beats large.
  • Golden = static; adversarial = growing.
  • Match method to the question (scale vs. nuance vs. safety).
  • An LLM-judge must be calibrated to humans before it's trusted.
  • Regression = fixed dataset + baseline + gate; watch per-case, not just the average.
