52.1 · Token Optimization Strategies

🧭Concept Overview

Token usage is the primary cost driver for LLM APIs — you pay per input and output token. Token optimization means sending fewer, smarter tokens (trimming), reusing already-processed tokens (caching), and amortizing overhead across many requests (batching). The goal is to cut spend without degrading answer quality.

🔧Key Techniques

  • Prompt / context pruning (trimming) — remove redundant instructions, boilerplate, and stale conversation turns. Why/when: long system prompts and unbounded chat history inflate every call; prune when context grows faster than it adds value.
  • Retrieval trimming (top-k + reranking) — inject only the most relevant retrieved chunks rather than dumping whole documents. Why/when: RAG pipelines where naive context stuffing balloons input tokens.
  • Prompt caching — cache a stable prompt prefix (system prompt, tool definitions, long documents) so repeated calls skip re-processing it. On the Claude API, cache reads cost ~10% of base input price; cache writes cost 1.25× base input for the 5-minute TTL (2× for the 1-hour TTL). Why/when: the single highest-leverage optimization when a large, unchanging prefix is reused across many calls.
  • Semantic caching — cache full responses keyed by embedding similarity of the request, returning a stored answer when a new query is "close enough." Why/when: high-repetition workloads (FAQs, support) where near-duplicate questions recur; requires a similarity threshold and staleness policy.
  • Request batching (Message Batches API) — submit many independent requests together for asynchronous processing at a 50% discount on input and output tokens. Why/when: bulk offline jobs where no user is waiting in real time.
  • Output trimming — constrain max_tokens and prompt for concise formats (JSON, short lists) so the model doesn't generate more than needed. Why/when: output tokens are typically the most expensive per token; useful when responses tend to over-explain.

💡Tips & Tricks

  • Place cacheable content at the start of the prompt (stable prefix first, variable user input last) — caching keys on the prefix, so any early change invalidates the cache.
  • Keep the cache warm: the 5-minute TTL refreshes on each read, so steady traffic avoids re-paying the write premium.
  • Combine batching with prompt caching for the largest offline savings — they stack.
  • Semantic caching needs a guardrail: too loose a similarity threshold returns wrong answers; log hit/miss rates and spot-check.
  • Measure before trimming — profile which calls carry the biggest token payloads instead of trimming blindly.

🎯Exam Strategy

"Questions on token trimming often present a scenario with a long system prompt reused across calls — the correct answer is usually 'implement prompt caching,' not 'reduce max_tokens.' Watch for distractors that optimize the wrong variable (cost vs. latency)."

Common trap: confusing prompt caching (reuses a repeated input prefix) with semantic caching (reuses a repeated output answer). Match the technique to what actually repeats — the prefix or the whole query.

52.2 · Latency Optimization

🧭Concept Overview

Latency is perceived speed. Two levers matter: time-to-first-token (TTFT, how fast output starts) and total completion time. You reduce both by streaming output as it's generated, doing independent work in parallel, and choosing a model whose speed matches the task's difficulty.

🔧Key Techniques

  • Streaming responses (stream=true / SSE) — tokens are sent as they're produced. Why/when: user-facing chat and long outputs; it slashes perceived latency even though total generation time is unchanged.
  • Parallel tool / request calls — fire independent API calls or tool invocations concurrently instead of sequentially. Why/when: agentic flows with multiple independent lookups; wall-clock time drops toward the slowest single call rather than the sum.
  • Model selection by tier — route to a smaller, faster model when the task allows. In the Claude family, Haiku-class models are the fastest and cheapest, Sonnet-class balances speed and capability, and Opus-class is the most capable but slowest and most expensive. Why/when: reserve the heaviest model for genuinely hard steps.
  • Prompt caching (latency side-effect) — cache hits skip the prefill of the cached prefix, lowering TTFT for prompts with large stable context. Why/when: large reused system prompts / documents.
  • Cap output length — generation time scales with output tokens, so a tight max_tokens bounds worst-case latency. Why/when: when responses can otherwise run long.

💡Tips & Tricks

  • Always stream in interactive UIs — it's the cheapest perceived-latency win and requires no model change.
  • Only parallelize independent calls; if Call B needs Call A's output, they must stay sequential.
  • Use a router: a cheap model (or rules) classifies difficulty, then dispatches to the right tier.
  • Distinguish TTFT from total latency when setting SLOs — streaming fixes the first, not the second.
  • Beware over-parallelizing into rate limits; concurrency should respect your account's request/token limits.

🎯Exam Strategy

"Latency questions usually describe a symptom — 'users wait too long before seeing any output' vs 'the full answer takes too long.' The first points to streaming; the second points to a smaller model or shorter output. Read the symptom, not just the fix."

Common trap: picking "upgrade to the largest model" to fix latency — larger models are generally slower. Also watch distractors that parallelize dependent calls, which is incorrect.

52.3 · Cost-Performance Tradeoff Analysis at Scale

🧭Concept Overview

At scale, small per-call inefficiencies multiply into large bills. Cost-performance analysis means quantifying spend with explicit per-token math, then deciding where accuracy is worth the money and where a cheaper/faster path is "good enough." The core idea: optimize the blended cost per successful task, not the price of a single token.

🔧Key Techniques

  • Per-token cost math — model total cost as cost = (input_tokens × in_price) + (output_tokens × out_price), priced per million tokens (MTok). Output tokens are usually priced higher than input. Why/when: foundational for any budgeting or forecast.
  • Cost per successful task — divide total spend by successful outcomes, including retries and failures. Why/when: a "cheap" model that needs 3 retries can cost more than one right answer from a stronger model.
  • Throughput vs accuracy tradeoff — smaller/faster models raise throughput and cut cost but may lower accuracy; quantify the accuracy loss against the savings. Why/when: high-volume pipelines where a small accuracy dip is tolerable (or not).
  • Model routing / cascades — try a cheap model first; escalate to a stronger model only when confidence is low. Why/when: mixed-difficulty traffic where most requests are easy.
  • Apply 52.1–52.2 levers to the math — factor in caching (reads ≈10% of input) and batching (50% off) when projecting scaled cost curves. Why/when: forecasting spend as volume grows.

💡Tips & Tricks

  • Always separate input and output pricing in models — they differ, and output usually dominates.
  • Track cost per successful task, not cost per call — retries hide in the gap.
  • Run an A/B on a cheaper model with an accuracy eval before switching; savings mean nothing if quality craters.
  • Cascades win when the easy fraction of traffic is large — measure that fraction first.
  • Re-derive the curve at each order of magnitude; what's negligible at 10K is budget-defining at 50M.

🎯Exam Strategy

"Cost questions at scale reward the answer that lowers total blended cost per outcome, not the one with the lowest sticker price per token. Expect a scenario where a cheap model's retry rate makes it more expensive overall."

Common trap: choosing the cheapest per-token model while ignoring accuracy/retry cost, or forgetting that output tokens are priced higher than input when doing the math.

52.4 · Monitoring & Alerting on Cost Metrics

🧭Concept Overview

You can't optimize what you don't measure. Cost monitoring instruments every call with token and spend telemetry, aggregates it by dimension (model, feature, customer, environment), and fires alerts when spend or usage crosses a threshold — so a runaway loop or prompt regression is caught in hours, not on the monthly invoice.

🔧Key Techniques

  • Track core metrics — input tokens, output tokens, cache read/write tokens, requests, cost, latency (TTFT & total), and error/retry rate. Why/when: these are the raw signals behind every cost anomaly.
  • Attribute cost by dimension — tag usage by model, feature/endpoint, tenant, and environment. Why/when: to answer "which feature or customer is driving the bill?" and to spot regressions.
  • Threshold & anomaly alerts — alert on absolute budget burn (e.g., daily spend cap), rate-of-change spikes, and cache-hit-rate drops. Why/when: to catch runaway agents, retry storms, or a change that broke caching.
  • Dashboards — the Anthropic Console provides a Usage & Cost view; teams also pipe API usage/response metadata into their own observability stack (e.g., Grafana, Datadog, CloudWatch) for custom dashboards. Why/when: for shared visibility and historical trend analysis.
  • Cache-hit-rate monitoring — track the ratio of cache-read to cache-write tokens. Why/when: a falling hit rate silently erodes your caching savings and signals a prefix that keeps changing.

💡Tips & Tricks

  • Log token counts from each API response's usage field (input, output, and cache tokens) rather than estimating.
  • Alert on rate of change, not just absolute totals — a 5× spike matters even below the monthly cap.
  • Set a hard budget guardrail (kill switch or throttle) for runaway-loop protection in agentic systems.
  • Break spend down by feature/tenant so you can attribute — and bill back — accurately.
  • Watch cache-hit-rate as a leading indicator: it drops before the bill spikes.

🎯Exam Strategy

"Monitoring questions typically ask which metric or alert would have caught a specific failure — e.g., a prompt change that quietly disabled caching. Map the symptom to the leading indicator (here, a falling cache-hit rate)."

Common trap: relying only on the end-of-month total (too late) instead of real-time rate-of-change alerts, or monitoring request count while ignoring the far more expensive output-token volume.

52.5 · Hands-On: Optimizing a High-Volume Production System CASE STUDY

🧭Concept Overview

This worked scenario applies 52.1–52.4 end-to-end. We take a support-automation system that is too slow and too expensive and optimize it in ordered passes, measuring after each. All numbers are illustrative to demonstrate method — not measured benchmarks.

📋The Scenario (baseline)

  • Workload: ~1,000,000 support requests / month, plus a nightly bulk job that summarizes 200,000 tickets.
  • Prompt: a 1,800-token system prompt (policies + tool defs) reused on every call; ~300 tokens of variable user input.
  • Model: a single large (Opus-class) model for everything.
  • Symptoms: high bill, users wait several seconds before any text appears, nightly job strains rate limits.

🔧Optimization Passes

  • Pass 1 — Trim (52.1): prune the system prompt of redundant boilerplate and cap max_tokens so answers stay concise. Fewer input and output tokens on every call.
  • Pass 2 — Cache the prefix (52.1): mark the stable 1,800-token prefix for prompt caching. Steady traffic keeps the cache warm (5-min TTL refreshes on read), so most calls pay ~10% of input price for that prefix instead of full price.
  • Pass 3 — Route by difficulty (52.2 / 52.3): classify each ticket; send simple/routing cases to a Haiku-class model and escalate only hard cases to Sonnet/Opus-class. Most traffic now runs on the cheap, fast tier.
  • Pass 4 — Stream + parallelize (52.2): stream responses in the agent UI to cut perceived latency, and run independent tool lookups concurrently to cut total time.
  • Pass 5 — Batch the nightly job (52.1): move the 200K-ticket summarization to the Message Batches API for a 50% discount; results return within 24 h, which is fine for an offline job, and it sidesteps live rate limits.
  • Pass 6 — Monitor & alert (52.4): instrument token/cost/latency/cache-hit metrics, dashboard them, and set alerts on daily spend, cache-hit-rate drop, and retry spikes so future regressions surface fast.

💡Tips & Tricks

  • Optimize in ordered passes and measure after each — don't change five things at once and lose attribution.
  • Sequence matters: trim first (smaller everything), then cache, then route, then batch offline work.
  • Keep an accuracy eval running while you route down-tier, so cost savings never silently degrade quality.
  • Batch only genuinely offline work; anything a user waits on stays synchronous + streamed.
  • Land monitoring before declaring victory — it's what keeps the win from regressing.

🎯Exam Strategy

"Case-study questions give a multi-symptom system and ask for the first or most impactful step. Map each symptom to its lever (reused prefix → caching; slow first token → streaming; offline bulk → batching) and pick the one that targets the stated bottleneck."

Common trap: applying an offline technique (batching) to a live user-facing path, or reaching for the largest model to 'fix' a latency/cost problem it actually worsens.
