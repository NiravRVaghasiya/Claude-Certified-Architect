38.1

When to Use Multi-Agent vs Single-Agent Architectures

Concept Overview

A single-agent system is one LLM-driven control loop that reasons, calls tools, and produces output — even if it has many tools. A multi-agent system splits work across two or more agents, each with its own role, prompt, tool set, and (critically) its own context window, coordinating toward a shared goal.

Why it matters at enterprise scale: adding agents is not free. Each agent is effectively an expensive, non-deterministic "thread" — it multiplies token cost, adds coordination latency, and introduces new failure modes (handoff errors, conflicting state). The architectural question is therefore not "how many agents can I use?" but "what is the smallest topology that meets the requirements?"

Key Principles

  • Start single, escalate deliberately. Default to one agent with tools; introduce additional agents only when a concrete constraint forces it.
  • Context isolation is a first-class reason to split. When one job would pollute or overflow another's context window, separate agents keep each context clean and focused.
  • Specialization — distinct system prompts, tools, or model sizes per role (e.g., a fast small model for routing, a stronger model for synthesis).
  • Parallelism — independent subtasks can run concurrently, cutting wall-clock time (fan-out/fan-in).
  • Fault isolation & security boundaries — a worker with narrow tool permissions limits blast radius; a failing worker need not crash the whole task.
  • Cost/latency tax — multi-agent systems typically consume substantially more tokens than a single chat turn because of duplicated context and inter-agent messaging. Budget for it.

DimensionSingle-AgentMulti-Agent

💡 Tips & Tricks
  • Mnemonic — reach for multi-agent when you have "S.P.I.C.E.": Specialization, Parallelism, Isolation (context), Containment (fault/security), Extensibility (independent scaling). No SPICE? Stay single.
  • Treat an agent like a thread: cheap to describe, expensive to run. Count the tokens before you count the agents.
  • Common pitfall: splitting a fundamentally sequential task into agents — you pay coordination cost for zero parallelism benefit.
🎯 Exam Strategy

These appear as "choose the most appropriate architecture" scenarios. Scan the stem for constraint keywords:

  • Points to multi-agent: "specialized," "parallel/concurrent," "independent subtasks," "isolate context," "different tool permissions," "long-horizon."
  • Points to single-agent: "low latency," "cost-sensitive," "simple," "tightly coupled steps," "easy to debug/maintain."

Elimination: if the task is linear and latency/cost-sensitive, eliminate every multi-agent option first. Beware distractors that add agents "for scalability" when no parallelism or specialization exists — that's the trap. Time tip: decide the constraint in the first read; don't re-read the whole stem for each option.

38.2

Orchestration Strategies for Enterprise Systems

Concept Overview

Orchestration is how agents coordinate: who decides what runs next, how work and state are passed between agents, and how results are aggregated. The topology you choose determines control flow, latency profile, cost, and how hard the system is to reason about.

At enterprise scale the orchestration layer is also where governance lives — rate limits, budgets, retries, approvals, and audit trails typically sit at the coordination boundary rather than inside individual agents.

Key Principles & Patterns

  • Orchestrator–Worker (supervisor): a central agent plans, delegates subtasks to workers, and synthesizes results. The most common enterprise default — clear control, easy auditing.
  • Sequential pipeline: agents chained stage-to-stage (A→B→C); each stage's output is the next stage's input. Deterministic, simple, but no parallelism and cumulative latency.
  • Parallel fan-out / fan-in: orchestrator dispatches independent subtasks concurrently, then aggregates. Best latency win when subtasks are truly independent.
  • Hierarchical: orchestrators of orchestrators — a supervisor delegates to sub-supervisors, each managing their own workers. Scales to large problem trees.
  • Peer / handoff (network): agents pass control laterally to whichever peer is best suited (decentralized routing). Flexible but harder to bound and audit.
  • Router / dispatcher: a lightweight classifier agent routes each request to the right specialist — often paired with a small, fast model.
  • Blackboard / shared state: agents read/write a shared workspace rather than messaging directly — useful for collaborative, evolving artifacts.

Control-flow axes to keep in mind: centralized vs decentralized control, deterministic vs dynamic (LLM-planned) routing, and stateless vs shared-state coordination.

💡 Tips & Tricks
  • Always define a fallback path. What happens if a worker times out, loops, or returns malformed output? Specify the default before you ship.
  • Bound everything: max steps, max delegation depth, and a token/cost budget per run. Unbounded orchestration is the #1 way multi-agent systems run away.
  • Contract at the boundary: give each agent a clear input/output schema so the orchestrator can validate, not guess.
  • Prefer orchestrator–worker as the default; reach for peer/handoff only when routing truly needs to be dynamic and decentralized.
⚠ Common Pitfall

Decentralized peer/handoff topologies can form infinite hand-off loops (A→B→A…) when no agent "owns" completion. If you must use handoffs, add a step budget, loop detection, and a designated terminator.

🎯 Exam Strategy

Expect pattern-matching questions: a scenario describes coordination needs and asks for the best orchestration strategy. Map keywords → pattern:

  • "central control / audit / delegate" → orchestrator–worker
  • "independent / concurrent / breadth-first" → parallel fan-out
  • "each stage transforms the previous" → sequential pipeline
  • "route to the right specialist" → router/dispatcher

Elimination: options that add decentralized handoffs without loop bounds are usually distractors on reliability grounds. If two answers seem right, prefer the one with clearer control & auditability — enterprise exams reward governance.

38.3

Decomposition Techniques for Complex Problem Solving

Concept Overview

Decomposition is the act of breaking a complex goal into subtasks that can be assigned, executed, and recombined. Good decomposition is what makes multi-agent systems work: it maximizes independence (so subtasks can parallelize and fail in isolation) while keeping interfaces clean enough to recombine reliably.

The engineering north star is borrowed from software design: high cohesion, low coupling. Each subtask should do one thing well and depend on as few others as possible.

Key Principles & Techniques

  • Functional decomposition: split by capability (retrieve / analyze / write). Maps naturally onto specialized agents.
  • Hierarchical / recursive: break a task into subtasks, then break those further — a task tree. Stop when a subtask is small enough for one agent to own.
  • Pipeline / stage-based: ordered transforms where each stage refines the artifact.
  • MapReduce-style: "map" identical work across many items in parallel, then "reduce"/aggregate. Ideal for batch document processing.
  • Plan-and-execute: a planner produces an explicit plan (often a DAG of steps), an executor runs it. Separates reasoning about the plan from doing the work.
  • Dependency-aware (DAG): model subtasks as a directed acyclic graph; anything not connected by an edge can run in parallel.

Quality tests for a decomposition: (1) Can subtasks run independently? (2) Are interfaces (inputs/outputs) explicit? (3) Is anything decomposed so finely that coordination cost exceeds the benefit? (4) Are there hidden cycles?

Table 38.3 — Choosing a decomposition technique
TechniqueStructureParallelizable?Use when…
FunctionalBy capabilityOftenDistinct skills needed (research vs code vs write)
Hierarchical / recursiveTask treeWithin levelsLarge problems that nest naturally
Pipeline / stageLinear chainNoEach step refines the previous artifact

💡 Tips & Tricks
  • Mnemonic — good subtasks are "C.L.E.A.R.": Cohesive, Loosely coupled, Explicit interfaces, Atomic (one owner), Recombinable.
  • Draw the dependency graph first. Edges = forced ordering; no edge = free parallelism. Fewer edges is almost always better.
  • Don't over-decompose. If a subtask's coordination overhead rivals its work, merge it back. Ten tiny agents can be slower and pricier than three sensible ones.
  • Give every subtask a written input/output contract — it doubles as the validation schema in 38.4.
🎯 Exam Strategy

Decomposition questions typically present a scenario and ask for the "most efficient" breakdown. The reliable heuristic:

  • Eliminate answers that create unnecessary inter-agent dependencies first — extra edges kill parallelism and add failure points.
  • Prefer breakdowns where independent subtasks are genuinely independent (can run concurrently) and a single, clear aggregation step recombines them.
  • Watch the trap of over-decomposition: an answer that splits into many micro-agents "for granularity" is usually wrong when coordination cost dominates.

Time tip: sketch a 3-node dependency graph in the margin; the answer with the fewest edges + one reducer is usually correct.

38.4

Cross-Cutting Concerns: Logging, Monitoring & Error Handling

Concept Overview

Cross-cutting concerns are the qualities that must hold across every agent rather than inside any one of them: observability (can you see what happened?) and reliability (does it keep working when things fail?). In non-deterministic LLM systems these are not optional — they're how you make an inherently variable system trustworthy in production.

The defining challenge at scale: a single user request may fan out across many agents and tool calls. Without a way to correlate those into one story, debugging is impossible.

Key Principles

  • Structured logging with correlation/trace IDs. Every agent and tool call carries a shared request ID (and a span ID) so the full path can be reconstructed. Log inputs, outputs, decisions, and tool results — as structured data, not free text.
  • Distributed tracing. Model the run as a trace of spans (one per agent step / tool call) to see latency, ordering, and where time is spent.
  • Metrics that matter for LLM systems: end-to-end latency, token usage & cost per run, task success rate, tool error rate, retry counts, and step counts. Alert on cost and step-count runaways.
  • Error-handling toolkit: timeouts, retries with exponential backoff + jitter, circuit breakers, fallbacks/graceful degradation, and idempotency so retries are safe.
  • Output validation / guardrails. Validate agent output against the subtask's schema (from 38.3) before passing it on; treat malformed output as a handled error, not a crash.
  • Human-in-the-loop escalation. Define when the system stops and asks a human (low confidence, repeated failure, high-stakes action).
  • Quality monitoring (evals). Because outputs are non-deterministic, monitor answer quality over time to catch regressions, not just infrastructure health.
Table 38.4 — Error-handling strategies at a glance
StrategyWhat it doesUse when…Watch out for
TimeoutCaps how long a step may runAny external/tool callToo short → false failures
Retry + backoff (jitter)Re-attempts transient failures with growing delaysFlaky/rate-limited dependenciesRequires idempotency; cap attempts
Circuit breakerStops calling a failing dependency to let it recoverRepeated downstream failuresNeeds a half-open probe to reset

💡 Tips & Tricks
  • Propagate the correlation ID everywhere — orchestrator → worker → tool. If one hop drops it, your trace breaks exactly where you need it most.
  • Idempotency first, retries second. Never enable retries on a non-idempotent action (e.g., "send payment") without a dedupe key.
  • Set a hard token/cost budget and a max-step ceiling per run, and alert when approached — this is your runaway-loop circuit breaker.
  • Log prompts and responses for debugging, but redact PII/secrets and mind retention policy.
⚠ Common Pitfall

Treating LLM output as always-valid. Non-deterministic agents will occasionally emit malformed JSON, hallucinated fields, or empty results. Validate at every handoff and define the retry-vs-escalate decision explicitly — don't let bad output flow silently downstream.

🎯 Exam Strategy

Reliability/observability questions lean on precise vocabulary. Memorize what each term solves:

  • Correlation/trace ID → follow one request across many agents.
  • Idempotency → makes retries safe.
  • Circuit breaker → protects a failing dependency (not the same as a retry).
  • Graceful degradation → partial-but-valid result under failure.

Elimination: distractors often swap definitions (e.g., calling a retry a "circuit breaker"). Match the mechanism to the problem it solves. If a scenario mentions "retrying a non-idempotent action," the correct answer usually adds idempotency/dedupe before retrying.

38.5

Hands-On: Architecting a Multi-Agent Enterprise Solution

Concept Overview

This section synthesizes 38.1–38.4 into a repeatable design method, then walks a worked example. The example is illustrative (not a real customer case) and is labeled as such.

A 6-step design method

  1. Clarify the goal & constraints — latency, cost, accuracy, compliance, volume. ↔ 38.1
  2. Decide single vs multi-agent using the SPICE test. Only escalate to multi-agent with a concrete justification. ↔ 38.1
  3. Decompose the goal into cohesive, loosely-coupled subtasks; draw the dependency DAG. ↔ 38.3
  4. Choose an orchestration topology that fits the DAG (fan-out for independent subtasks, pipeline for stage transforms). ↔ 38.2
  5. Design cross-cutting concerns — correlation IDs, tracing, metrics, timeouts/retries/circuit breakers, output validation, HITL escalation, budgets. ↔ 38.4
  6. Validate & iterate — evaluate quality (evals), watch cost/latency, and simplify anything that isn't earning its complexity.

Worked example — Enterprise "Market Intelligence Brief" generator (illustrative)

Goal: on demand, produce a cited market brief for a given company. High accuracy and traceability matter; some latency is acceptable. The subtasks (gather sources, extract facts, analyze, draft) are largely independent up front → multi-agent passes the SPICE test (specialization + parallelism + context isolation).

💡 Tips & Tricks
  • Design the reduce step first. Knowing exactly what the writer/validator needs tells you precisely what each worker must return — that defines the contracts.
  • Right-size the models per role: a fast, cheap model for routing/extraction; a stronger model for synthesis. Heterogeneous routing is a big cost lever.
  • Make the validator a real gate: if citations don't resolve, loop back to the retriever (bounded) rather than shipping an unverified brief.
  • Keep a "why more than one agent?" note in your design doc — if you can't answer it per agent, collapse that agent.
🎯 Exam Strategy

Hands-on/scenario questions ask you to assemble or critique an architecture. Approach:

  • Read the constraints before the options. The dominant constraint (latency vs accuracy vs cost) usually picks the answer.
  • Prefer designs that are as simple as the requirements allow — enterprise exams reward "no unjustified agents," clear control, and explicit failure handling.
  • For "what's wrong with this design?" items, scan for the usual defects: unbounded loops, missing fallback/validation, unnecessary dependencies, no observability, retrying non-idempotent actions.

Time tip: map each answer choice onto the 6-step method; the correct design satisfies all five concept areas without adding complexity that no constraint requires.

Chapter 38 — Key Exam Takeaways

Justify every agent

Default to single-agent; escalate to multi-agent only with a concrete reason (SPICE). "More agents = better" is the classic trap.

Match topology to control needs

Orchestrator–worker is the enterprise default. Fan-out for independent work, pipeline for stage transforms, router for intent.

Decompose for independence

High cohesion, low coupling (CLEAR). Fewest dependency edges + one reducer = the "most efficient" breakdown.

Correlate to observe

One trace/correlation ID across every agent and tool call. Track cost, steps, success — alert on runaways.

Know your reliability terms

Timeout ≠ retry ≠ circuit breaker ≠ fallback. Retries need idempotency. Validate every handoff.

Simplest design that meets constraints

Read constraints first; the dominant one usually picks the answer. Reward auditability and explicit failure handling.
