Core mental model for the whole chapter

Anthropic's central principle: find the simplest solution possible, and only increase complexity when needed. Complexity climbs in this order — single LLM call → Augmented LLM → Workflow → Agent. The exam repeatedly tests whether you can pick the least complex pattern that still solves the problem.

37.1 The Architecture Lifecycle

Every LLM-based system operates as a continuous cycle, not a one-shot pipeline. The four stages feed into one another, and the feedback loop is what turns a static prompt into an adaptive system.

The Four Stages

  • Input — the request enters the system: a user query, an event, a document, or upstream data. Includes any pre-processing (validation, guardrails, retrieval of context).
  • Processing — the LLM reasons over the input, optionally augmented by retrieval, tools, and memory. This is where the chosen pattern (workflow / agent) executes.
  • Output — a structured or natural-language result is produced, validated, and returned to the user or a downstream system.
  • Feedback Loops — signals (user corrections, tool results, evaluator scores, ground-truth comparisons) flow back to refine the next iteration. In agentic systems this loop is internal and automatic; in workflows it is often an explicit evaluator-optimizer step.

Real-world mapping: a support-ticket assistant

StageIn an LLM-based support system
InputCustomer message arrives; system retrieves the customer's order history + relevant KB articles (RAG).
ProcessingClaude reasons over the ticket + retrieved context, decides whether to answer directly or call a lookup_refund_status tool.
OutputA drafted reply is produced and checked against a guardrail (no PII leakage, correct tone).
FeedbackAgent rating / thumbs-down + escalation data feed evaluation, improving prompts and retrieval for future tickets.
💡 Tip — mnemonic

Remember the lifecycle as "I Prefer Our Feedback" → Input · Processing · Output · Feedback. If an exam diagram omits the loop back to Input, it's describing a pipeline, not a full lifecycle.

✅ Quick Recap — 37.1
  • Lifecycle = Input → Processing → Output → Feedback, running continuously.
  • Feedback loop distinguishes an adaptive system from a static pipeline.
  • Processing is where retrieval, tools, and memory augment the LLM.
  • In agents the loop is internal/automatic; in workflows it's often an explicit evaluator step.

37.2 Architectural Patterns

Anthropic draws a sharp architectural line between workflows and agents, both built on top of the foundational Augmented LLM.

  • Augmented LLM — the basic building block: a single LLM enhanced with retrieval, tools, and memory. No orchestration of multiple steps; the model uses these capabilities within one reasoning turn.
  • Workflows — systems where LLMs and tools are orchestrated through predefined code paths. The control flow is written by the developer; the LLM fills in steps.
  • Agents — systems where the LLM dynamically directs its own processes and tool usage, maintaining control over how it accomplishes a task, typically looping until a goal is met.
💡 Tip — the defining question

Ask: "Who decides the next step — the developer's code, or the model?" Predefined code path = Workflow. The model decides at runtime = Agent. One enhanced call, no looping = Augmented LLM.

Comparison table

PatternDescriptionBest Use CaseProsCons
Workflow Predefined sequence of LLM calls; deterministic control flow written in code (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer). Well-defined, repeatable tasks with known steps (e.g. document summarization pipeline, classify-then-route). Predictable, testable, easy to debug, lower cost/latency variance. Less flexible for novel inputs; developer must anticipate paths.
Agentic LLM autonomously decides which tools to call and what step comes next, looping on environment feedback until done. Open-ended tasks where steps can't be predicted in advance (e.g. research assistant, coding agent). Highly adaptable; handles novel, multi-step problems. Harder to control; higher cost & latency; needs guardrails, stopping conditions, and testing in a sandbox.
Augmented LLM Single LLM call enhanced with retrieval, tools, and/or memory — no autonomous multi-step looping. Q&A grounded in external knowledge (e.g. RAG chatbot), single tool-augmented response. Simple, fast, cheap, easy to reason about. Limited multi-step reasoning; can't decompose complex tasks alone.

Simple architecture diagrams

The five canonical workflow sub-patterns (know these by name)
  • Prompt chaining — decompose a task into a fixed sequence of steps, each LLM call feeding the next; optional "gate" checks between steps.
  • Routing — classify the input, then direct it to a specialized downstream prompt/model.
  • Parallelization — run subtasks simultaneously. Two flavours: sectioning (split into independent parts) and voting (run the same task multiple times for confidence).
  • Orchestrator-workers — a central LLM dynamically breaks down a task and delegates to worker LLMs, then synthesizes results.
  • Evaluator-optimizer — one LLM generates, another evaluates and gives feedback in a loop until quality passes.
⚠️ Common trap

Orchestrator-workers looks agentic, but it's still a workflow — the orchestration structure is predefined by the developer. It becomes an agent only when the LLM itself decides the overall process at runtime with no fixed path.

✅ Quick Recap — 37.2
  • Augmented LLM = foundational building block (retrieval + tools + memory), one call.
  • Workflow = LLMs orchestrated via predefined code paths.
  • Agent = LLM dynamically directs its own process & tool use in a loop.
  • Five workflow sub-patterns: chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer.

37.3 Selecting the Right Pattern

Anthropic's rule: start with the simplest option and only escalate when the task genuinely demands it. A single well-prompted LLM call solves more than people expect. Agents are the last resort — used when flexibility and model-driven decisions at scale are worth the added cost, latency, and reduced predictability.

Decision flowchart

Key evaluation criteria

CriterionPushes toward simpler (Augmented / Workflow)Pushes toward Agentic
Autonomy neededSteps are predictable & fixedSteps can't be enumerated up front
LatencyTight / real-time budgetTolerant of longer, variable runtimes
CostHigh volume, cost-sensitiveHigh-value tasks justify more tokens/loops
Predictability / controlMust be auditable & deterministicAcceptable to trade control for flexibility
Task complexitySingle-shot or linearOpen-ended, multi-step, novel

Worked examples

Example 1 — Invoice data extraction (high volume)

Scenario: Extract 6 fields from 50,000 invoices/day into JSON. Choose: Augmented LLM (single call with a tool/structured output + retrieval of the template). Why: steps are fixed, volume is huge and cost-sensitive, no dynamic decision-making — agentic looping would add cost and latency for zero benefit.

Example 2 — Support triage → specialized reply

Scenario: Classify a ticket (billing / technical / refund) then generate a tailored response. Choose: Workflow — routing. Why: the categories and downstream prompts are known in advance; a predefined routing path is predictable, cheap, and easy to debug. No need for the model to invent steps.

Example 3 — Autonomous coding assistant

Scenario: "Fix this failing test suite" — the fix requires exploring the repo, editing files, running tests, and iterating based on results. Choose: Agent. Why: the sequence of actions genuinely can't be predetermined; the model must observe tool/test output and decide next steps in a loop. Task is high-value, so added cost/latency is acceptable — pair with sandboxing and stopping conditions.

✅ Quick Recap — 37.3
  • Start simplest; escalate only when the tier below genuinely fails.
  • Criteria: autonomy, latency, cost, predictability, complexity.
  • Fixed steps → Workflow; unpredictable steps + acceptable risk → Agent.
  • Agents trade control/latency/cost for flexibility — justify the trade.

37.4 Designing for Scalability, Reliability & Maintainability

Production LLM architectures are judged on three pillars. Treat them separately, then verify with the checklists.

Pillar 1 — Scalability

Definition: the system's ability to handle growing load (requests, users, data) without degrading latency or cost-efficiency.

Key techniques

  • Right-size the model per task (route simple steps to smaller/faster models).
  • Caching — prompt caching for stable context; cache retrieval results and repeated tool outputs.
  • Batching & parallelization of independent subtasks (workflow parallelization pattern).
  • Streaming responses to improve perceived latency; asynchronous processing for long tasks.
  • Rate limiting & back-pressure to protect downstream tools/APIs.

Common pitfalls

  • Using an agentic loop where a single call would do — unbounded token/cost growth.
  • No caching → paying to re-process identical context repeatedly.
  • Ignoring tool/API rate limits until they throttle in production.

Pillar 2 — Reliability

Definition: the system produces correct, safe, consistent results and degrades gracefully when components fail.

Key techniques

  • Structured outputs + schema validation on every LLM response.
  • Guardrails: input validation, output filtering, PII checks, content safety.
  • Retries with backoff; fallbacks (smaller model, cached answer, human handoff).
  • Stopping conditions & max-iteration limits for agents to prevent runaway loops.
  • Evaluator-optimizer or explicit verification steps for high-stakes outputs.
  • Sandboxed tool execution — test agent actions in a safe environment.

Common pitfalls

  • Trusting free-text output without validation.
  • No stopping condition → an agent loops forever / burns budget.
  • No human-in-the-loop for irreversible or high-risk actions.

Pillar 3 — Maintainability

Definition: the ease with which the system can be understood, debugged, evaluated, and evolved over time.

Key techniques

  • Prefer the simplest pattern — simpler systems are easier to debug and maintain.
  • Observability: log every step, tool call, and decision; trace agent trajectories.
  • Evaluation suites / regression tests on representative inputs before shipping changes.
  • Modular, composable components with clear interfaces (documented tools, versioned prompts).
  • Keep the "ACI" (Agent-Computer Interface) — tool definitions & docs — clean and well-documented, just like a good API/human interface.

Common pitfalls

  • Over-engineering with frameworks that hide what's really happening under the hood.
  • Poorly documented / ambiguous tool definitions the model misuses.
  • No evals → can't tell if a prompt change improved or regressed behaviour.

Quick-review checklists

Scalability

  • Model right-sized per task; heavy steps not defaulting to the largest model
  • Prompt/result caching in place for stable context
  • Independent subtasks parallelized or batched
  • Streaming / async used for long-running work
  • Downstream rate limits respected with back-pressure

Reliability

  • Every LLM output validated against a schema/guardrail
  • Retries, backoff, and fallbacks defined for failures
  • Agents have max-iteration / stopping conditions
  • Human-in-the-loop for irreversible or high-risk actions
  • Tools execute in a sandbox before touching production

Maintainability

  • Simplest pattern that meets the requirement was chosen
  • Full logging/tracing of steps, tool calls, and decisions
  • Evaluation suite / regression tests exist and run on changes
  • Components are modular with documented interfaces
  • Tool definitions (ACI) are clear, tested, and unambiguous
💡 Tip — mnemonic "SRM = Scale, Recover, Read"

Scalability = handle more (scale). Reliability = recover from failure. Maintainability = a human can read/understand it later. If a question stresses "handles 10× traffic" → Scalability; "keeps working when the API fails" → Reliability; "another engineer can debug it in 6 months" → Maintainability.

✅ Quick Recap — 37.4
  • Three pillars: Scalability (load), Reliability (correct + graceful failure), Maintainability (understandable + evolvable).
  • Scale: right-size models, cache, parallelize, stream.
  • Reliability: validate outputs, guardrails, retries/fallbacks, stopping conditions, sandbox.
  • Maintainability: simplicity, observability, evals, clean tool interfaces (ACI).

37.5 Hands-On: Designing an End-to-End Architecture

Brief: Design a Research & Report Assistant — a user asks a business question ("How are our top competitors positioning on pricing?"), and the system returns a cited, structured brief.

Step-by-step design (applying 37.1–37.4)

  1. Frame the lifecycle (37.1). Input = the research question + scope. Processing = retrieval + multi-step reasoning. Output = a structured brief with citations. Feedback = user rating + fact-check pass that can trigger a re-run.
  2. Choose the pattern (37.2 & 37.3). The number and order of searches can't be predetermined (depends on what's found) → this is genuinely open-ended, so an Agent is justified for the research phase. But the final composition is a fixed step → wrap the agent inside an orchestrator-style workflow: an agentic research loop feeding a deterministic "compose + verify" workflow. (Hybrid — simplest thing that works.)
  3. Augment the LLM (37.2). Give it tools: web_search, read_url, a vector_retrieve over internal docs, and memory to accumulate findings.
  4. Add reliability (37.4). Max 8 research iterations (stopping condition); each claim must carry a source (schema validation); an evaluator-optimizer step fact-checks the draft before release; low-confidence → human review.
  5. Add scalability (37.4). Parallelize independent sub-queries; cache fetched pages; use a smaller model for classification/routing and Claude for synthesis.
  6. Add maintainability (37.4). Log every tool call and the agent's trajectory; version the compose prompt; run an eval set of 20 benchmark questions on any change.

Final architecture diagram

💡 Tip — what examiners look for in a design answer

Show that you chose the simplest pattern that works and justified any agentic component. A strong answer explicitly names the stopping condition, output validation, and feedback loop — these signal production maturity, not just a toy demo.

✅ Quick Recap — 37.5
  • Map the lifecycle first, then pick patterns per phase (hybrids are fine).
  • Agentic loop for unpredictable research; deterministic workflow for fixed compose step.
  • Bolt on reliability (stopping condition, validation, HITL) and scalability (parallelize, cache).
  • Always include observability + a feedback loop for maintainability.

🎯 Exam Strategy & Question-Pattern Recognition

How questions on this chapter are framed

  • Scenario-based (majority) — a paragraph describes a system's requirements and you pick the correct pattern or spot the design flaw. These reward the "simplest thing that works" instinct.
  • Definition-based — distinguish Workflow vs. Agent vs. Augmented LLM, or name a workflow sub-pattern from its description.
  • "Best/Most appropriate" choice — several options are technically possible; the correct one is the least complex that meets all stated constraints.

Time allocation

  • Definition/recall questions: ~45–60 seconds each — answer on sight, don't overthink.
  • Scenario questions: ~90 seconds — read the constraints twice, underline latency/cost/autonomy cues.
  • Flag long "design the system" scenarios and return after clearing quick wins; don't sink 5 minutes into one item early.

⚠️ Top traps to avoid
  • Over-picking "Agent." The tempting answer is often too complex. If steps are knowable, it's a Workflow.
  • Orchestrator-workers ≠ Agent. Predefined orchestration = still a Workflow.
  • "Augmented LLM" is a building block, not just RAG. Retrieval + tools + memory — any of these enhancements counts.
  • Terminology consistency: Anthropic says "Agentic / Agent," not "Autonomous." Don't let a distractor relabel it.
  • Forgetting stopping conditions. Any "what's missing from this agent design?" question — the answer is frequently a stopping condition, validation, or human-in-the-loop.
🎯 One-line exam reflex

When unsure between two patterns, pick the simpler one unless the scenario explicitly requires the model to make runtime decisions that code cannot predetermine. That single rule resolves the majority of scenario questions in this chapter.
