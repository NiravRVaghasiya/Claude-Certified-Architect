📌 A note on scope & accuracy

This chapter teaches the orchestrator–worker (coordinator–subagent) pattern as described in Anthropic's public engineering guidance on multi-agent research systems. The agent names used here — Coordinator, Web Search, Document Analysis, Synthesis — are role labels for this exam scenario, not fixed product SKUs. Anthropic's own documented system uses an orchestrator (lead) agent, parallel search subagents, and a dedicated citation step. Where an exact internal implementation detail is not publicly documented, this guide describes the concept generically and flags the assumption. No fabricated APIs or product names are asserted as fact.

32.1 — Scenario Overview & Architecture

The research use case

An organization needs to answer open-ended research questions that no single tool call can satisfy — e.g. "Compare the top three vendors in our RFP against current market analyst reports and our internal evaluation documents, and produce a cited summary." Such questions are:

  • Breadth-first — they fan out into many independent sub-questions that can be pursued in parallel.
  • Multi-source — answers live in live web content and internal documents.
  • Unpredictable in shape — the number and type of searches can't be hard-coded up front.
  • Citation-critical — the final answer must be traceable to its sources.

A single agent hits limits here: one context window fills up, searches run serially, and the model loses track of which finding came from where. The multi-agent orchestrator–worker pattern solves this by decomposing the task, parallelizing the work across subagents that each have their own context window, and synthesizing a single cited answer.

💡 Tip — when multi-agent actually wins

Multi-agent shines for breadth-first, parallelizable, heavy-search tasks where subtasks are loosely coupled. It is a poor fit for tightly-coupled, sequential work (e.g. most coding tasks where every step depends on the last) — there the coordination overhead and token cost outweigh the benefit. On the exam, "parallel," "independent sub-questions," and "broad search" signal multi-agent; "each step depends on the previous" signals a single agent.

High-level architecture

A Coordinator (a.k.a. lead / orchestrator agent) receives the user query, plans an approach, and delegates clearly-scoped subtasks to specialized subagents that run in parallel, each in its own isolated context window. Subagents return condensed findings (not raw dumps) to the coordinator, which routes document work and finally hands everything to a Synthesis step that composes the answer with preserved citations.

⚠️ Exam trap — the Coordinator does NOT search

A classic distractor claims the coordinator "performs the web searches and reads the documents itself." It does not. Its job is orchestration: planning, decomposition, delegation, and integration. The work is done by subagents. Answers that put retrieval work on the coordinator are wrong.

32.2 — Coordinator, Web Search, Document Analysis & Synthesis Subagents

Each agent has a distinct purpose, defined inputs/outputs, a set of tools, and characteristic failure modes. Study these role boundaries — most scenario questions test whether you can assign a responsibility to the correct agent.

32.2.1 Coordinator agent orchestrator / lead

  • Purpose: Turn an open-ended query into a plan; decompose it into clearly-scoped, non-overlapping subtasks; delegate them; then integrate the returns into a coherent whole. It also decides how many subagents to spawn (effort scaling).
  • Inputs: User query; conversation/context; available tool & subagent inventory; the persisted plan from memory.
  • Outputs: Explicit task specifications for each subagent (objective, expected output format, allowed tools, boundaries/scope), and a final integrated result routed to synthesis.
  • Tools used: Delegation / subagent-spawning capability; memory (write plan & task specs); typically not raw search/retrieval tools itself.
  • Failure modes:
    • Vague delegation — under-specified task descriptions cause subagents to duplicate work or drift off-scope.
    • Over-spawning — too many subagents → runaway token cost and diminishing returns.
    • Context overflow — trying to hold every raw finding itself instead of relying on condensed returns + memory.
    • Compounding errors — a flawed plan propagates to every subagent.
💡 Tip — the "OFTB" delegation checklist

A good coordinator task spec always defines O·F·T·B: Objective, output Format, Tools allowed, and Boundaries (scope). If an exam option describes a subagent doing the wrong thing, trace it back — usually the coordinator's task spec was missing one of these four.

32.2.2 Web Search subagent worker

  • Purpose: Gather evidence from live, external sources for its assigned sub-question, then return a condensed, source-tagged summary.
  • Inputs: A single scoped sub-question + boundaries from the coordinator.
  • Outputs: Key findings with source URLs/identifiers attached (provenance) — not a raw page dump.
  • Tools used: Web search / retrieval tools; optionally page-fetch tools.
  • Failure modes: Query drift (searching beyond scope), hallucinated or stale sources, returning raw un-condensed content that floods the coordinator, and dropping source references (breaks provenance downstream).

32.2.3 Document Analysis subagent worker

  • Purpose: Read and extract relevant information from internal or attached documents (PDFs, reports, knowledge bases) and summarize passages tied to the sub-question.
  • Inputs: Scoped sub-question + a document set / retrieval scope.
  • Outputs: Extracted facts and quotes with document + location references (file, page/section) for provenance.
  • Tools used: Document retrieval / RAG over the provided corpus; file readers.
  • Failure modes: Retrieving irrelevant chunks, mis-attributing a quote to the wrong document, exceeding context by loading whole documents instead of relevant passages, and losing page/section anchors needed for citations.

32.2.4 Synthesis subagent integrator

  • Purpose: Combine the condensed findings from all workers into one coherent, non-redundant answer; reconcile conflicts; and attach citations so each claim traces to its source.
  • Inputs: Condensed, source-tagged findings from every subagent + the provenance registry.
  • Outputs: The final cited answer/report.
  • Tools used: Reasoning/composition; a citation/attribution step that maps statements to the source registry.
  • Failure modes: Fabricating or mismatching citations (attaching the wrong source to a claim), silently dropping conflicting evidence, over-summarizing away important detail, and introducing claims not supported by any subagent finding.
⚠️ Exam trap — who owns citations?

Provenance is captured at the source by the workers (each finding carries its origin) and preserved/attached at synthesis time — ideally by a dedicated citation step. A tempting wrong answer says "the Synthesis agent invents citations after the fact." If sources weren't tagged when the evidence was gathered, synthesis has nothing truthful to cite. Provenance is a relay handed down the chain, not something conjured at the end.

💡 Tip — mnemonic "C-WDS"

Remember the pipeline order as C-WDS: Coordinator → Web search → Document analysis → Synthesis. Mental model: Coordinator is the editor-in-chief; Web & Doc subagents are reporters in the field (each with their own notebook = context window); Synthesis is the copy desk that fact-checks, merges, and footnotes the story.

32.3 — Context Passing & Provenance Tracking

How context moves between agents

Agents do not share one giant context window. Instead, context is passed through three disciplined channels:

  • Structured task messages (delegation): The coordinator sends each subagent a self-contained brief — objective, output format, allowed tools, boundaries (OFTB). This is the only context a fresh subagent starts with, keeping its window lean and focused.
  • Condensed return messages (fan-in): Subagents return compressed findings — key facts + source tags — not their raw working context. This prevents the coordinator's window from overflowing and keeps signal high.
  • Shared memory / state store: The plan, task specs, and a source registry live outside any single context window. Because a long research run can exceed a context window, the coordinator persists its plan to memory so work can continue after truncation/reset.
📌 Why isolation matters

Each subagent's separate context window is a feature, not a limitation: it isolates failures (one subagent's confusion doesn't poison others), enables true parallelism, and keeps each window focused on one sub-question. The cost is that agents can't "see" each other's raw context — so everything important must be explicitly passed via messages or memory.

Provenance tracking — why and how

Why it matters: A research answer is only trustworthy if each claim can be traced to a verifiable source. Provenance enables fact-checking, satisfies compliance/audit needs, lets users judge credibility, and prevents the confident-but-unsourced answers that erode trust.

How it's preserved across handoffs: Provenance is a relay. Each source is tagged at the moment of retrieval and that tag rides along with the finding through every handoff into a source registry. At synthesis, a dedicated citation step maps each statement in the draft back to the registry entry that supports it. If a tag is dropped at any hop, the citation is irrecoverable downstream — so provenance discipline is enforced at every step, not bolted on at the end.

⚠️ Exam trap — "shared context window"

Watch for options implying all agents "share the same context window / memory of each other's reasoning." They don't. Isolation + explicit message/memory passing is the whole point. The word shared applies to the memory/state store (plan + registry), not to the model context windows.

32.4 — Practice Questions & Walkthroughs

Multiple choice
Q1. In the multi-agent research system, what is the Coordinator agent's primary responsibility?
  • A) Perform all web searches and read all documents itself, then answer.
  • B) Plan and decompose the query, delegate scoped subtasks to subagents, and integrate their returns. ✅
  • C) Store the final answer in a database for auditing.
  • D) Rank web pages by relevance before any agent runs.
Show answer & walkthrough
Correct: B The coordinator is the orchestrator — it plans, decomposes, delegates, and integrates. The work (search, read) is done by subagents in parallel.
Why the others are wrong: A — this collapses the whole point of the pattern; the coordinator delegates rather than doing retrieval itself. C — persistence is a function of the memory/store, not the coordinator's defining role. D — page ranking is a retrieval concern handled within the Web Search subagent, not a coordinator responsibility.
Multiple choice
Q2. Why do subagents each run in their own context window rather than sharing one?
  • A) To force agents to talk to each other directly.
  • B) To isolate failures, enable parallelism, and keep each window focused on one sub-question. ✅
  • C) Because Claude cannot use tools inside a shared window.
  • D) To reduce the total token cost below that of a single agent.
Show answer & walkthrough
Correct: B Isolation contains errors, allows subagents to work simultaneously, and keeps each window lean and on-task.
Why the others are wrong: A — subagents don't communicate directly; the coordinator mediates. C — false; tool use isn't blocked by shared windows. D — a common misconception: multi-agent systems generally use more tokens than a single agent, not fewer. The benefit is capability/parallelism, not token savings.
Trick question
Q3. When the Synthesis subagent produces the final answer, how are citations obtained?
  • A) The Synthesis agent infers likely sources and generates plausible citations after drafting.
  • B) Sources are tagged at retrieval by the workers and preserved in a registry; synthesis maps each claim back to that registry. ✅
  • C) The Coordinator adds citations because only it can see all agents' context windows.
  • D) Citations are unnecessary because the model is trained on reliable data.
Show answer & walkthrough
Correct: B Provenance is captured at the source (retrieval) and relayed via the registry; synthesis verifies and attaches citations by mapping claims to registry entries.
Why the others are wrong — and why this is a trap: A is the tempting misconception from §32.2/§32.3: generating citations after the fact produces fabricated attributions, not real provenance. C — the coordinator does not see other agents' raw context windows; only condensed messages + shared memory flow between agents. D — verifiability is the whole reason provenance exists; "trust the model" is never the certified-architect answer.
Scenario
Q4. A research run produces an answer where two subagents clearly duplicated the same searches and one drifted into an unrelated topic. Which root cause and fix best matches?
  • A) The Coordinator's task specs were vague/overlapping — tighten decomposition with clear objectives and boundaries (OFTB). ✅
  • B) The context windows were shared — merge them into one window.
  • C) The Synthesis agent failed — retrain it on citations.
  • D) Too few subagents — spawn many more to cover the topic.
Show answer & walkthrough
Correct: A Duplicated work + scope drift are hallmark symptoms of poor delegation. The fix is at the coordinator: non-overlapping, well-bounded task specs (Objective, Format, Tools, Boundaries).
Why the others are wrong: B — merging windows removes isolation/parallelism and doesn't address delegation. C — the symptom is in search behavior, upstream of synthesis. D — adding subagents to a bad plan multiplies duplication and cost; over-spawning is itself a failure mode.
Scenario
Q5. Midway through a long research run, the Coordinator's context window is nearly full and it risks losing track of the overall plan. What design choice prevents work from being lost?
  • A) Ask the user to re-enter the query.
  • B) Persist the plan and task specs to shared memory so they survive context truncation. ✅
  • C) Delete subagent findings to free space.
  • D) Have each subagent hold the full plan in its own window.
Show answer & walkthrough
Correct: B Writing the plan to an external memory/state store lets the run continue past a single window's limit — a core reason memory exists in this architecture.
Why the others are wrong: A — disruptive and unnecessary; state should be engineered to persist. C — findings are the deliverable; deleting them defeats the purpose. D — bloats every subagent window and violates the lean, scoped-brief principle; the plan belongs in shared memory, not replicated everywhere.
Multiple choice
Q6. Which workload is the best fit for the multi-agent research pattern?
  • A) Refactoring a codebase where each change depends on the previous one.
  • B) Answering a broad question that fans out into many independent sub-questions across web and internal docs. ✅
  • C) A single fact lookup answerable by one tool call.
  • D) A strictly sequential, tightly-coupled multi-step calculation.
Show answer & walkthrough
Correct: B Breadth-first, parallelizable, multi-source research with loosely-coupled subtasks is the sweet spot.
Why the others are wrong: A and D are tightly-coupled/sequential — coordination overhead and token cost outweigh benefits; a single agent is better. C is trivial — multi-agent is overkill and wasteful for a one-shot lookup.
Multiple choice
Q7. What should a Web Search subagent return to the Coordinator?
  • A) The full raw HTML of every page it visited.
  • B) A condensed set of findings with source references attached. ✅
  • C) Only a yes/no answer with no sources.
  • D) Its entire internal chain-of-thought verbatim.
Show answer & walkthrough
Correct: B Workers compress findings and keep source tags — high signal, provenance intact.
Why the others are wrong: A floods the coordinator's window (context overflow failure mode). C strips the provenance needed for citations. D — dumping raw reasoning wastes context and provides no structured, source-tagged evidence.
Scenario
Q8. The final report contains a statistic attributed to the wrong document. Provenance tags were present in the registry. Where is the most likely defect?
  • A) The Web Search subagent — it never ran.
  • B) The memory store lost all tags.
  • C) The Synthesis citation step mismatched a claim to the wrong registry entry. ✅
  • D) The Coordinator refused to delegate.
Show answer & walkthrough
Correct: C Since tags existed in the registry, capture worked — the error is at the mapping/attachment stage during synthesis (claim ↔ source mismatch).
Why the others are wrong: A and D would prevent an answer or evidence from existing at all, contradicting the premise. B — the question states tags were present, so the store didn't lose them. This isolates the fault to the citation-mapping step.

Exam Strategy

Approaching scenario-based multi-agent questions

  1. Identify the agent under test first. Ask: is this about orchestration (coordinator), retrieval (web/doc worker), or integration/citation (synthesis)? Map the symptom to the correct layer before reading options.
  2. Trace the failure to its owner. Duplicated/off-scope work → coordinator delegation; stale/unsourced evidence → worker; wrong/missing citations → synthesis or a dropped tag upstream.
  3. Reject "single-brain" distractors. Any option that has the coordinator doing the searching, or all agents sharing one context window, is almost always wrong.
  4. Prefer the design fix over the brute-force fix. "Spawn more subagents" and "merge windows" are usually traps; tightening task specs or persisting to memory are usually correct.

Time management

  • ~60–75 seconds per scenario question. Read the last sentence (the actual ask) first, then re-read the stem for the specific symptom.
  • Eliminate two distractors fast using the "single-brain" and "brute-force" filters above — you can usually get to a coin-flip in 20 seconds.
  • Flag, don't stall. If a citation/provenance nuance isn't obvious, mark it and move on; these often clarify once you've answered related items.
  • Bank time on keyword questions. Direct "which agent does X" items should take <30 seconds — use the C-WDS mnemonic and the decoder table.
💡 Common exam wording patterns to watch
  • "Best," "most likely," "primary" → there may be several partially-true options; pick the one matching the agent's defining role.
  • "always / never / guarantees" → usually a red flag on an incorrect option (e.g. "multi-agent always reduces cost").
  • "shared context" → almost always the wrong choice for model windows; correct only when it refers to the memory/registry store.
  • "infers / generates citations" → provenance trap; real citations are captured at retrieval and verified, not invented.
