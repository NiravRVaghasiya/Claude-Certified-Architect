34.1

Scenario Overview & Pipeline Design

In this scenario, Claude Code runs as an automated agent inside a CI/CD pipeline rather than in an interactive terminal. The goal is to insert AI-assisted code review, test generation, and quality gates into the software delivery flow — automatically, on every pull request (PR) or commit — without a human invoking Claude by hand.

What makes CI/CD usage different from interactive Claude Code

Interactive Claude Code is a conversational REPL in your terminal. For pipelines you use headless (non-interactive) mode: you pass a single prompt with the -p / --print flag, Claude does its work and exits, and the pipeline reads the result. This makes it scriptable and deterministic enough to gate merges.

Headless invocation — the CI building block
# Non-interactive: run one prompt, print result, exit
claude -p "Review the staged diff for security issues" \
  --output-format json \
  --allowedTools "Read,Grep,Bash(git diff:*)" \
  --max-turns 8
Tip: Memorise the three flags that make Claude Code CI-safe: -p (headless), --output-format json (parseable result), and --max-turns (bounds cost & runtime). If a question describes "running Claude in a pipeline," these three are almost always the correct primitives.

Key architectural decisions

DecisionOptionsGuidance
Integration surface CLI (claude -p) vs. GitHub App (@claude mentions / Claude Code GitHub Action) Use the CLI in headless mode for custom pipelines and non-GitHub CI. Use the GitHub Action / app when you want @claude mentions and native PR comments with less scripting.
API vs. subscription auth Anthropic API key · Amazon Bedrock · Google Vertex AI CI runners authenticate via environment variables (e.g. ANTHROPIC_API_KEY) stored as pipeline secrets, never committed. Bedrock/Vertex are used for cloud-governed deployments.
Sync vs. async Blocking (gate waits for verdict) vs. non-blocking (comment posted later) Sync/blocking when Claude's result is a hard merge gate. Async when review is advisory — post comments without stalling the pipeline. Long jobs risk CI timeouts, so bound turns/time.
Rate limiting & concurrency Per-PR debounce, queueing, retry with backoff A burst of commits can trigger many runs. Debounce to the latest commit, cap concurrency, and retry API 429s with exponential backoff.
Tool permissions --allowedTools / --disallowedTools, permission mode Grant least privilege. A review job usually needs read/search only; avoid unrestricted Bash or write tools in an automated gate.
Context scope Full repo vs. changed files / diff only Scope to the diff / changed files for speed and cost. Add a CLAUDE.md for repo conventions Claude should honour.
Common pitfall: Committing the API key into the workflow file or echoing it in logs. Always inject credentials from the CI provider's secret store as environment variables, and never print them. A leaked key is the single most common CI security failure.
Exam strategy: When a scenario says "automated," "every pull request," "no human in the loop," or "merge gate," the intended answer is headless mode (-p) with a bounded, least-privilege configuration — not the interactive REPL. Watch for distractor answers that suggest a developer runs Claude manually.

34.2

Automated Reviews, Test Generation & PR Feedback

How Claude Code performs code reviews

Given a diff (or the changed files), Claude Code reasons over the code the way a senior reviewer would, then emits findings. In a CI job you steer it with a focused prompt and, ideally, ask for structured output so the pipeline can act on it. Typical review dimensions:

  • Style & conventions — naming, formatting, adherence to a CLAUDE.md or style guide, dead code.
  • Security — hardcoded secrets, injection risks, unsafe deserialization, missing input validation, insecure defaults.
  • Logic & correctness — off-by-one errors, unhandled edge cases, null/None handling, race conditions, incorrect error propagation.
  • Maintainability — complexity, duplication, missing docs/tests, unclear intent.
Focused review prompt for CI
claude -p "Review only the changed lines in the PR diff.
Report security, logic, and style issues. For each issue give
severity (high|medium|low), file, line, and a concrete fix.
Return JSON matching the review schema. Do not modify files." \
  --allowedTools "Read,Grep,Bash(git diff:*)" \
  --output-format json
Note (accuracy): Claude Code is a general-purpose coding agent, not a fixed rule-based linter. Its "checks" come from reasoning guided by your prompt and repo context — so review quality depends heavily on how specific your instructions and provided context are. Treat it as complementary to deterministic linters/SAST tools, not a replacement for them.

Test generation workflows

Claude Code can scaffold and write tests for changed code. Common patterns:

  1. Unit-test scaffolding — generate test files/skeletons for new functions using the repo's existing framework (pytest, Jest, JUnit, etc.), matching established patterns it finds in the codebase.
  2. Edge-case identification — enumerate boundary conditions (empty input, nulls, max/min, unicode, concurrency) and produce tests that exercise them.
  3. Coverage gap filling — given a coverage report, target untested branches.
  4. Regression tests — when a bug is described, write a failing test that reproduces it, then (in a fix workflow) implement the fix.
Tip: For deterministic CI test generation, tell Claude the exact framework, file naming convention, and where tests live (e.g. "use pytest, place in tests/, name test_<module>.py"). Vague prompts produce inconsistent scaffolding that fails to run.

Example PR feedback formats

A. Human-readable inline comment (posted on the PR)

## 🔎 Claude Code review — 2 issues found

B. Machine-readable summary (consumed by the gate — see 34.3)

Common pitfall: Posting a giant free-text review and also expecting the gate to parse it. Separate concerns — emit structured data for the machine gate and a readable comment for humans. Trying to regex severity out of prose is fragile and a frequent exam distractor.
Exam strategy: If a question contrasts "review comment for the developer" vs. "signal for the pipeline to block/allow," map them to two outputs: prose comment (human) and structured JSON (machine). The gate decision should key off a field like max_severity or status, never off prose.

34.3

Structured Output in CI Contexts

Why structured output matters

CI pipelines are programs, not people. A downstream step — a merge gate, a linter aggregator, a dashboard, a ticket creator — needs to parse the result and act on it deterministically. Free-form prose is ambiguous and brittle to parse; structured JSON/YAML is:

  • Parseable — a step can jq '.review_summary.max_severity' and branch on it.
  • Actionable — fields map directly to actions (block, comment, open ticket).
  • Stable — a fixed schema lets you validate and diff results across runs.
  • Composable — output of one stage feeds cleanly into the next.
Two distinct meanings of "structured output" — don't conflate them:

1. CLI transport format: --output-format json (or stream-json) wraps Claude's run in a JSON envelope with metadata (result text, session id, cost, duration, error flag). This is guaranteed valid JSON by the CLI.

2. The content schema you ask Claude to produce (e.g. the review issues array). This lives inside the result and is produced by the model following your prompt — so it is not guaranteed to be perfectly schema-valid every time. That gap is exactly why validation + fallbacks (below) matter.

Example schemas for structured review output

Full review result (the example schema)
{
  "pr_id": "1234",
  "review_summary": {
    "status": "changes_requested",     // approved | changes_requested | commented
    "max_severity": "high",
    "issue_count": 2,
    "issues": [
      {
        "severity": "high",             // high | medium | low
        "category": "security",
        "file": "auth.py",
        "line": 88,
        "issue": "Hardcoded API key detected",
        "suggested_fix": "Move to environment variable"
      },
      {
        "severity": "medium",
        "category": "logic",
        "file": "handlers.py",
        "line": 142,
        "issue": "records[0] on possibly empty result → IndexError",
        "suggested_fix": "Guard: if not records: return default"
      }
    ]
  }
}
Minimal single-finding schema (matches the syllabus example)
{ "severity": "high", "file": "app.py", "line": 42, "issue": "SQL built via string concat — injection risk" }
Consuming the result in a gate (bash + jq)
# CLI guarantees the envelope is JSON; extract the model's result text
result=$(claude -p "$PROMPT" --output-format json)
sev=$(echo "$result" | jq -r '.result | fromjson | .review_summary.max_severity')

if [ "$sev" = "high" ]; then
  echo "Blocking merge: high-severity issue"; exit 1
fi
Tip: Prefer an enum + numeric field the gate keys off (max_severity, issue_count) rather than making the gate walk the whole issues array. One scalar decision field keeps the gate logic trivial and testable.

Error handling & fallback strategies

Because the content schema is model-produced, a robust CI step must plan for malformed or missing structure. Layered strategy:

Failure modeMitigation
Invalid / non-parseable JSONValidate against a JSON Schema after each run. On parse failure, retry the prompt once with an explicit "return only valid JSON matching this schema" instruction.
JSON wrapped in prose / markdown fencesStrip ```json fences and extract the JSON object before parsing. Better: instruct "output only JSON, no prose." Prefer the CLI's --output-format json envelope so at least the transport is clean.
Missing required fieldsSchema validation flags it; apply defaults (e.g. treat missing severity as "medium") or fail the step explicitly rather than merging blind.
API error / rate limit (429)Retry with exponential backoff; cap attempts; surface a clear CI error if exhausted.
Timeout / runaway agentBound with --max-turns and a job-level timeout; on exceed, fail safe.
Ambiguous / advisory resultDecide the fail-open vs. fail-closed policy up front. Security gates should usually fail closed (block on uncertainty); advisory style checks may fail open.
Validate-then-fallback (Python pseudocode)
import json, jsonschema

def parse_review(raw, schema, retry_fn):
    try:
        data = json.loads(strip_fences(raw))
        jsonschema.validate(data, schema)
        return data                      # ✓ happy path
    except (json.JSONDecodeError, jsonschema.ValidationError):
        raw2 = retry_fn(strict=True)         # retry once, stricter prompt
        try:
            data = json.loads(strip_fences(raw2))
            jsonschema.validate(data, schema)
            return data
        except Exception:
            # fail CLOSED for a security gate
            return {"status": "error", "max_severity": "high",
                    "issues": [], "_note": "unparseable review; blocking"}
Common pitfall: Assuming the model's JSON is always valid and calling json.loads with no guard. A single malformed run then crashes the pipeline or, worse, silently merges bad code. Always validate; always define the fallback.
Exam strategy: Keywords like "parseable," "machine-readable," "downstream step," "automatically consume," "schema," or "gate on" signal that structured JSON with a defined schema is the intended answer — not markdown or plain text. And whenever an option mentions validating or a fallback, it is usually the more correct, production-minded choice.

Step-by-step walkthroughs (2 most complex questions)

Walkthrough — Q4 (structured-output resilience)

  1. Identify the real problem: the failure is intermittent, malformed content JSON — fences and missing fields. So the issue is content-schema reliability, not the transport format.
  2. Eliminate fail-unsafe options: A (assume valid) ignores the observed failures; D (merge on parse failure) is fail-open on a quality/security gate — dangerous. Both out.
  3. Eliminate over-corrections: B (drop JSON entirely) throws away machine-readability — the whole reason the gate exists. Regexing severity from prose is more fragile. Out.
  4. Confirm the layered answer: C handles each failure mode in order — strip fences (formatting), validate (structure), retry once (transient model error), fail closed (safety). This mirrors the 34.3 validate-then-fallback pattern.
  5. Answer: C. Keyword tells: "validate," "retry," "fallback," "fail-closed" are all production-minded signals the exam rewards.

Walkthrough — Q6 (rate limiting & concurrency)

  1. Extract the constraint: too many concurrent runs from one PR → hitting rate limits. The goal is to keep protective reviews while controlling request volume.
  2. Reject options that remove protection: A (remove the step) and D (review only after merge) both defeat the purpose of a pre-merge gate. Out.
  3. Reject the misdirection: C raises --max-turns, which increases work/cost per run — the opposite of relieving rate pressure. Out.
  4. Validate the multi-part fix: B attacks all three levers — debounce (only review the latest commit, not every intermediate push), cap concurrency (limit simultaneous runs), and backoff on 429 (graceful retry). These map directly to the 34.1 "rate limiting & concurrency" decision row.
  5. Answer: B. Exam tell: when one option bundles several sound mitigations and the others each break something, the bundle is usually correct.
