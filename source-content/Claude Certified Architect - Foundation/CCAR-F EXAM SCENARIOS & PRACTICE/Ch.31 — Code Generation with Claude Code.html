31.1 · Scenario Overview & Workflow Design

Claude Code is Anthropic's agentic command-line coding tool. Unlike a chat autocomplete, it operates in a loop: it reads your files, runs shell commands to explore, edits source, and verifies results — asking for permission according to the active mode. The "code generation" scenario tests whether you can design a context → plan → execute → verify workflow that is safe, repeatable, and grounded in real project context.

Key Details / Deep Dive

  • Agentic loop, not one-shot generation. Claude gathers context (files, grep/glob, shell output), proposes actions, acts, then checks its own work. Good workflow design front-loads context and back-loads verification (tests, git diff).
  • Context is the lever. Output quality is dominated by what Claude can see. The three durable context sources are: CLAUDE.md (persistent facts), skills / slash commands (reusable procedures), and explicit @file references you paste in.
  • Surfaces. The same engine runs in the CLI (terminal), the VS Code / JetBrains extensions, the desktop app, and via the Agent SDK. Permission behavior and mode selectors differ slightly per surface.
  • Design principle: match autonomy to blast radius. Exploratory or high-risk multi-file work → review first (Plan Mode). Small, well-scoped edits you'll review anyway → direct execution / acceptEdits.

💡 Tip: Think of the workflow as "context in, verification out." The two things you control most are what Claude sees before it starts (CLAUDE.md + references) and how it proves the change worked (tests / diff review). Everything in between is the agentic loop.
🎯 Exam Strategy: Questions here often describe a messy prompt with no project context and ask "what improves reliability most?" The best answer usually points to persistent, structured context (CLAUDE.md, a reusable command) rather than "write a longer prompt each time." Beware answers that treat Claude Code as a stateless autocomplete — that framing is the trap.

31.2 · Custom Slash Commands & CLAUDE.md Configuration

CLAUDE.md supplies persistent facts auto-loaded at session start (project conventions, architecture, "always/never" rules). Custom slash commands are reusable procedures you invoke on demand with /name. In current Claude Code, custom commands have been merged into Skills: a file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and behave the same — existing commands/ files keep working.

CLAUDE.md — the persistent memory file

  • Auto-loaded at session start — it is context Claude always has, so use it for facts, not one-off instructions.
  • Scope hierarchy (all layered together):
    LocationScopeTypical use
    ./CLAUDE.md (project root)Shared with the team (commit it)Architecture, conventions, build/test commands
    ./CLAUDE.local.mdPersonal, project-specific (git-ignored)Your local overrides & secrets-free notes
    ~/.claude/CLAUDE.mdGlobal (all your projects)Personal style & universal preferences
    Sub-directory CLAUDE.mdLoaded when Claude works in that folderModule-specific rules
  • Keep it lean. Everything in CLAUDE.md consumes context on every turn. When a section grows into a multi-step procedure, migrate it to a skill — a skill's body loads only when used, so long reference material costs almost nothing until needed.

Custom slash commands (skills)

  • Where they live: Project → .claude/commands/ or .claude/skills/; Personal → ~/.claude/commands/ or ~/.claude/skills/. The filename (or skill folder name) becomes the command you type.
  • Invocation: type /name explicitly, or let Claude load a skill automatically when its description matches the task. Set disable-model-invocation: true to keep it manual-only.
  • Dynamic substitution inside the command body:
    PlaceholderExpands to
    $ARGUMENTSAll arguments passed, as one string
    $ARGUMENTS[N]The N-th argument (0-based index)
    $NShorthand for $ARGUMENTS[N] (e.g. $0 = first arg)
    $nameA named arg declared in arguments: frontmatter
    !`command`Injects live shell output (e.g. !`git diff HEAD`) into the prompt
    @path/to/fileInjects the contents of a file as context

Example command file

---
description: Summarizes uncommitted changes and flags anything risky.
allowed-tools: Bash(git diff:*)
argument-hint: [base-branch]
---

## Current changes

!`git diff HEAD`

## Instructions
Summarize the changes above in two or three bullet points, then list
any risks you notice (missing error handling, hardcoded values,
tests that need updating). If the diff is empty, say so.

Saved to .claude/commands/review.md → invoke with /review. The !`git diff HEAD` line runs at invocation and feeds real output into the prompt.

Common frontmatter fields

FieldPurpose
descriptionHelps Claude decide when to auto-invoke the skill; shown in listings
allowed-toolsGrants tool permissions the command may use (goes through the normal permission flow)
argument-hintAutocomplete hint for expected args, e.g. [issue-number]
argumentsNamed positional args for $name substitution
disable-model-invocationtrue = user-only; Claude won't trigger it automatically
modelPin a specific model for this command
💡 Tip: The mental split is facts vs. procedures. If it's a stable truth Claude should always know → CLAUDE.md. If it's a repeatable multi-step action you trigger → a slash command / skill. A CLAUDE.md section that reads like a checklist is a sign it should become a skill.
⚠️ Misconception check: $ARGUMENTS is a substitution placeholder in the command body, not a shell/environment variable — and !`cmd` injects command output as context; it is distinct from allowed-tools, which grants Claude permission to run tools during the task.
🎯 Exam Strategy: Watch for "one-off instruction" bait. If a scenario describes a single temporary instruction, the correct answer is not "put it in CLAUDE.md" — CLAUDE.md is for persistent context. Also remember: custom commands are now skills; answers claiming ".claude/commands/ is deprecated and no longer works" are wrong — those files still work.

31.3 · Plan Mode vs Direct Execution in Practice

Permission modes decide what Claude can do without asking you first. You cycle them with Shift+Tab in the CLI (or a selector in VS Code / Desktop). Plan Mode makes Claude research and propose changes without editing source — reads and exploratory shell commands run, but edits stay blocked until you approve the plan. Direct execution (e.g. acceptEdits) applies edits immediately for speed.

The permission modes

ModeAllowed without promptBest for
default (a.k.a. Manual)Reads onlyReviewing every action; sensitive work
acceptEditsReads, file edits, common filesystem commands (mkdir, mv, cp…)Iterating on code you're actively reviewing
planReads + classifier-approved exploratory commands; no source editsExploring a codebase before changing it
autoEverything, with background safety checksLong tasks; reducing prompt fatigue Pro/Max/Team
dontAskReads + pre-approved tools; anything else is deniedLocked-down CI & scripts
bypassPermissionsEverythingIsolated containers / VMs only (needs a flag)

Cycling with Shift+Tab

defaultManual · reads only
⇥
acceptEditsedits applied
⇥
planpropose, don't edit
⇥
back to default

Optional modes (auto, dontAsk, bypassPermissions) slot in after plan only when enabled/available. Start a session directly in a mode with claude --permission-mode plan.

Plan Mode vs Direct Execution

AspectPlan ModeDirect Execution (default / acceptEdits)
What Claude doesReads, explores, writes a plan — no source editsReads and applies edits to files
Best forComplex, multi-file or unfamiliar changesSmall, well-defined tasks
Risk levelLow — review before anything is appliedHigher — changes land immediately
How to enterShift+Tab to plan, or --permission-mode planDefault on start, or Shift+Tab to acceptEdits
Exit / applyApprove the plan → switches to an executing modeN/A — already executing
💡 Tip: Use acceptEdits when you intend to review the result after the fact via git diff or your editor, rather than approving each edit inline. Use Plan Mode first when you're unsure of scope — you get a reviewable plan for free before a single line changes.
⚠️ Precision point: Plan Mode is not "read-only." Claude still runs exploratory shell commands to understand the code. What's blocked is editing your source until you approve the plan. Also: bypassPermissions approves everything and is intended for isolated/disposable environments only — it is not a general "go faster" setting, and writes to protected paths like .claude are still guarded.
🎯 Exam Strategy: If a question describes an irreversible or high-risk action, or a large change across many files, the correct answer usually favors Plan Mode over direct execution. If it emphasizes speed on a trusted, well-scoped edit, favor acceptEdits. Answers recommending bypassPermissions on a developer's real machine are almost always the distractor. Remember the cycle key is Shift+Tab (not a slash command).

31.4 · Practice Questions & Walkthroughs

Click each question to reveal the correct answer and full walkthrough. Questions integrate concepts from 31.1–31.3.

Q1 A teammate wants the whole team to always follow the repo's naming conventions and run pytest before commits, without re-typing it each session. Where should this go?
  1. A one-off message at the start of each session
  2. A project-root CLAUDE.md committed to the repository
  3. A personal ~/.claude/CLAUDE.md file
  4. The bypassPermissions mode flag
Correct: B — project-root CLAUDE.md, committed so the whole team shares it.
Walkthrough

These are persistent facts/conventions that should apply to every session and every teammate. CLAUDE.md is auto-loaded at session start, and placing it at the project root and committing it shares it with the team — exactly matching the requirement.

Why not the others: A defeats the "without re-typing" goal and isn't persistent. C is personal-only — it wouldn't reach teammates. D is a permission mode; it has nothing to do with sharing conventions.

Q2 You're about to refactor authentication across ~30 files in an unfamiliar codebase. Which approach best balances safety and effectiveness?
  1. Start in bypassPermissions so nothing interrupts the refactor
  2. Use acceptEdits and review the final git diff
  3. Enter Plan Mode, review the proposed plan, then approve to execute
  4. Paste the whole codebase into a single prompt and ask for the rewrite
Correct: C — Plan Mode first, review, then approve.
Walkthrough

A large, cross-cutting change in an unfamiliar codebase is high blast-radius. Plan Mode lets Claude read and explore, then produce a reviewable plan without touching source. You validate the approach before any edit lands — the safest effective path for complex multi-file work.

Why not the others: A is for isolated containers/VMs, never a real machine on a risky refactor. B applies edits immediately across 30 files before you've validated the strategy — riskier here. D ignores Claude Code's agentic file-exploration strengths and bloats context.

Q3 In a custom slash command file, what does the line !`git status` do when the command runs?
  1. Declares a named argument called git status
  2. Grants Claude permission to run git commands
  3. Executes git status and injects its live output into the prompt as context
  4. Prevents Claude from running that command
Correct: C — it runs the command and feeds the output into the prompt.
Walkthrough

The !`command` syntax performs shell injection at invocation: the command executes and its stdout becomes part of the prompt context. This is how commands pull in live state (diffs, status, test output) automatically.

Why not the others: A confuses it with arguments: frontmatter / $name. B is the job of allowed-tools, which grants permission but doesn't inject output. D is invented behavior.

Q4 Which statement about Plan Mode is accurate?
  1. Plan Mode is fully read-only; Claude cannot run any shell command
  2. Plan Mode lets Claude explore (reads + exploratory commands) but blocks source edits until you approve the plan
  3. Plan Mode is a paid add-on separate from the normal session
  4. You enter Plan Mode by typing /plan
Correct: B
Walkthrough

Plan Mode tells Claude to research and propose changes without making them: it reads files and runs shell commands to explore, writes a plan, but does not edit your source until you approve. This is the precise, exam-tested definition.

Why not the others: A is the classic trap — Plan Mode still runs exploratory commands; only edits are blocked. C is false — it's a mode, not a paid feature, and costs nothing extra. D is wrong — you cycle to it with Shift+Tab or start with --permission-mode plan, not a slash command.

Q5 A section of your CLAUDE.md has grown into a long, multi-step deployment checklist that only matters when you actually deploy. What's the best refactor?
  1. Leave it in CLAUDE.md so it's always loaded
  2. Move it into a skill / slash command (e.g. /deploy) that loads only when invoked
  3. Delete it and re-type the steps each deployment
  4. Convert it to bypassPermissions mode
Correct: B — migrate the procedure into a skill/slash command.
Walkthrough

CLAUDE.md is for facts loaded on every turn; a long procedure needed only occasionally wastes context. A skill's body loads only when used, so moving the checklist to /deploy keeps it out of the way until invoked — the documented "facts vs. procedures" guidance.

Why not the others: A keeps paying the context cost on every turn. C throws away reusability. D is a permission mode and unrelated to organizing content.
