30.1 — Scenario Overview & Architecture ↑ top

Concept Summary. The Customer Support Resolution Agent is a Claude-powered assistant that resolves customer issues by calling a small, well-defined set of MCP tools against back-end systems (CRM, order database, payments). Claude acts as the reasoning layer: it interprets the customer's request, decides which tool to call and in what order, inspects each structured result, and either resolves the issue at first contact or escalates to a human when rules or confidence thresholds are exceeded. The goal is to maximize safe first-contact resolution while routing genuinely risky or out-of-policy cases to people.

Key Details

  • Roles (real MCP). The host application embeds Claude (the MCP client); each back-end capability is exposed by an MCP server. Tools are advertised via tools/list and invoked via tools/call.
  • Tool schemas are JSON Schema. Each tool declares an inputSchema (typed parameters, required array). Claude must satisfy required parameters before calling.
  • Claude never touches data stores directly. All reads/writes go through tools — the model only produces tool calls and reasons over the returned results.
  • Ordered dependency. Identity → order → eligibility → action. Downstream tools depend on IDs returned by upstream tools (e.g. process_refund needs an order_id that lookup_order confirmed).
  • Two terminal states per turn: Resolved (first contact) or Escalated (handoff to human).
  • Escalation is a tool, not a failure. escalate_to_human is a legitimate, correct action whenever a trigger fires.

💡 Tips & Tricks. Memorize the pipeline with the mnemonic “VOTE” — Verify (get_customer) → Order (lookup_order) → Threshold/eligibility check → Execute (process_refund) or Escalate. Common pitfall: assuming Claude “knows” the customer or order without a tool call — it does not. Any fact about the customer/order must originate from a tool result in-context.
🎯 Exam Strategy — How this is typically tested. Questions describe a support conversation and ask for the architecturally correct next step or which component owns a responsibility. Answering approach: (1) identify what Claude currently knows from prior tool results, (2) find the first missing precondition in the VOTE order, (3) choose the tool that supplies it. Distractors usually skip a step (e.g. refund before verifying the order) or attribute data-store access to Claude directly.

30.2 — MCP Tools ↑ top

Concept Summary. The agent is equipped with exactly four tools. Each has a typed input schema, a structured return, and a defined place in the resolution pipeline. Mastery means knowing each tool's required parameters, its return fields, and — crucially — the precondition that must be true before you may call it. illustrative example parameter names/returns are scenario definitions.
Golden ordering rule. get_customer → lookup_order → (check refund_eligible & policy) → process_refund. escalate_to_human may be called at any point a trigger fires. Never call a downstream tool whose required inputs have not been produced upstream.

get_customer

Purpose: Verify the customer's identity and retrieve their account/contact profile so the agent can safely act on their behalf.

Input Parameters

get_customer — input schema illustrative example
NameTypeRequired?Description
customer_idstringConditional*Unique customer identifier (preferred lookup key).
emailstringConditional*Email used to resolve identity when customer_id is unknown.
verification_tokenstringNoOptional proof-of-identity token (e.g. OTP) to raise the verification level.

*At least one identifying key (customer_id or email) must be supplied.

Output / Return Schema

// structured tool result
{
  "customer_id": "CUST-10293",
  "name": "Jordan Lee",
  "verified": true,
  "tier": "standard",
  "open_tickets": 1
}

Example Invocation

{
  "name": "get_customer",
  "arguments": { "email": "jordan.lee@example.com" }
}

When to use vs. NOT use

  • Use: As the first tool in almost every flow — before any account-specific action.
  • Do NOT use: For anonymous, general-policy questions (“what is your return window?”) that need no identity; or to look up orders (that's lookup_order).
⚠️ Common exam trap. A returned record does not mean identity is proven — check the verified field. If verified: false, treat identity as unconfirmed and escalate (or request verification) before any refund. The distractor: “get_customer returned a record, so proceed to refund.”

lookup_order

Purpose: Retrieve an order's status, contents, and refund eligibility for a verified customer.

Input Parameters

lookup_order — input schema illustrative example
NameTypeRequired?Description
order_idstringYesUnique order identifier.
customer_idstringNoCross-check that the order belongs to the verified customer.

Output / Return Schema

{
  "order_id": "ORD-55871",
  "status": "delivered",
  "items": [ { "sku": "A-1", "qty": 1 } ],
  "total": 84.00,
  "currency": "USD",
  "refund_eligible": true,
  "days_since_delivery": 9
}

Example Invocation

{
  "name": "lookup_order",
  "arguments": {
    "order_id": "ORD-55871",
    "customer_id": "CUST-10293"
  }
}

When to use vs. NOT use

  • Use: After identity is verified, to confirm the order exists, belongs to the customer, and whether it's refund-eligible.
  • Do NOT use: Before verifying identity (you can't confirm ownership); or to issue a refund (that's process_refund).
⚠️ Common exam trap. Candidates forget that refund_eligible must be checked before calling process_refund. Issuing a refund on an ineligible order (refund_eligible: false) is the classic wrong-answer distractor. Also watch ownership: if customer_id doesn't match, treat as a mismatch (escalate).

process_refund

Purpose: Execute a monetary refund against an eligible order — a state-changing, side-effecting action.

Input Parameters

process_refund — input schema illustrative example
NameTypeRequired?Description
order_idstringYesOrder to refund (must be eligible).
amountnumberYesRefund amount; must be ≤ order total and ≤ auto-refund policy limit.
reasonstringYesReason code / note for the refund (audit trail).
customer_idstringNoRedundant ownership check for safety.
Policy threshold (scenario constant) illustrative example: the agent may auto-issue refunds up to $100. Any amount > $100 exceeds auto-authority and must be escalated, not processed.

Output / Return Schema

{
  "refund_id": "RF-33012",
  "order_id": "ORD-55871",
  "amount": 84.00,
  "status": "completed"
}

Example Invocation

{
  "name": "process_refund",
  "arguments": {
    "order_id": "ORD-55871",
    "amount": 84.00,
    "reason": "item_defective"
  }
}

When to use vs. NOT use

  • Use: Only when identity is verified, the order is found & owned, refund_eligible: true, and amount ≤ $100.
  • Do NOT use: On ineligible orders, unverified identity, amounts over the auto-limit, or when any escalation trigger has fired.
⚠️ Common exam trap. Because it moves money, process_refund is the most-tested “irreversible action.” The trap is calling it when any precondition is unmet. If a question stacks conditions (eligible order but amount $250), the correct action is escalate_to_human, not a partial/creative workaround.

escalate_to_human

Purpose: Hand the case to a human agent when the situation exceeds the agent's authority, confidence, or policy — creating a routed handoff with context.

Input Parameters

escalate_to_human — input schema illustrative example
NameTypeRequired?Description
reasonstring (enum)YesWhy escalation is needed — e.g. auth_failure, order_not_found, over_limit, policy_exception, customer_angry, repeated_failure.
summarystringYesConcise context for the human (what was tried, what's blocking).
prioritystringNolow | normal | high (default normal).
customer_idstringNoAttach known identity if available.

Output / Return Schema

{
  "ticket_id": "ESC-90781",
  "status": "queued",
  "assigned_queue": "tier2_billing"
}

Example Invocation

{
  "name": "escalate_to_human",
  "arguments": {
    "reason": "over_limit",
    "summary": "Verified customer, eligible order ORD-771, requested refund $250 > $100 auto-limit.",
    "priority": "high"
  }
}

When to use vs. NOT use

  • Use: Whenever a trigger fires — auth failure, order not found/ownership mismatch, over auto-limit, policy exception, detected anger/sentiment, or repeated tool failure.
  • Do NOT use: As a lazy default for routine, in-policy cases the agent is authorized to resolve (over-escalation lowers first-contact resolution and is also wrong on the exam).
⚠️ Common exam trap. Two opposite traps: (1) under-escalating a case that clearly meets a trigger (e.g. processing a $250 refund anyway), and (2) over-escalating a clean, in-policy refund. Also: escalation requires a meaningful reason + summary — “escalate with no context” is a weaker answer than “escalate with the specific trigger and summary.”

🎯 Exam Strategy — How this is typically tested. Expect “which tool would you call next?” items. Approach: scan the transcript for the last confirmed fact, then pick the tool that supplies the next missing precondition in VOTE order — unless a trigger has fired, in which case escalate_to_human overrides everything. 30.3 — First-Contact Resolution vs. Escalation ↑ top

Concept Summary. Every turn ends in one of two states: the agent resolves the issue itself, or it escalates to a human. Resolution is only permitted when a full set of criteria hold simultaneously; escalation is mandatory the moment any trigger fires. The logic is a short-circuit gate chain — the first failed condition determines the escalation reason.

Visualization — Resolution / Escalation Decision Flowchart

▼ Yes

No → escalate_to_human (policy_exception)
▼ Yes

No → escalate_to_human (over_limit)
▼ Yes
5 · No anger / repeated failure / policy flag?
Trigger fires → escalate_to_human (customer_angry / repeated_failure)
▼ All clear
✅ process_refund → Resolved at First Contact

Escalation Triggers (any one ⇒ escalate)

  • Auth failure: identity cannot be verified (verified: false or no valid key).
  • Order not found / ownership mismatch: no such order, or it doesn't belong to the verified customer.
  • Policy exception: refund_eligible: false (outside return window, non-refundable item, etc.).
  • Over auto-limit: requested/required refund > $100 illustrative example.
  • Sentiment / anger detected: customer is angry, threatens churn/legal, or explicitly demands a human.
  • Repeated failure: the same tool errored repeatedly, or the customer has contacted multiple times about the same unresolved issue.

First-Contact Resolution Criteria (ALL must hold)

  • Identity verified (get_customer.verified = true).
  • Order found and owned by the customer.
  • refund_eligible = true (within policy).
  • Refund amount ≤ $100 auto-limit.
  • No anger/sentiment flag and no repeated-failure condition.
Non-contradiction rule. Criteria and triggers are exact complements: resolution requires all criteria true; escalation requires any trigger true. A single failed criterion is, by definition, its matching trigger — there is no case that is both resolvable and escalatable.

🎯 Exam Strategy — How this is typically tested. When a question labels a customer “angry,” “frustrated,” mentions “third time contacting,” or a dollar figure, check triggers first before reasoning about tool mechanics — a sentiment/over-limit trigger can make a technically-eligible refund the wrong action. Read for the single disqualifying detail the question plants; that detail is the answer.

Q1MCQ · tool ordering

A verified customer says, “My order arrived broken, please refund it.” Claude has the customer_id and verified: true from get_customer, but has not yet touched the order. What is the correct next tool call?

  1. process_refund with the amount the customer stated
  2. lookup_order to fetch status and refund_eligible
  3. escalate_to_human because a refund was requested
  4. get_customer again to double-check identity
Show answer & walkthrough

Correct: B — lookup_order.

In VOTE order, identity is done; the next missing precondition is order information (status, ownership, eligibility). lookup_order supplies it.

  • A wrong: process_refund requires a confirmed, eligible order_id and an in-limit amount — none confirmed yet. Refunding now risks refunding an ineligible or non-existent order.
  • C wrong: No trigger has fired; a routine refund request is not itself grounds to escalate. Over-escalation.
  • D wrong: Identity is already verified: true; re-calling get_customer gathers no new precondition and wastes a step.
Q2Judgment · thresholds

Identity is verified, lookup_order returns refund_eligible: true and total: 250.00. The customer wants a full refund of $250. The auto-refund limit is $100. What should the agent do?

  1. Call process_refund for $250 — the order is eligible
  2. Call process_refund for $100 (the max it's allowed) and tell the customer that's all
  3. Call escalate_to_human with reason over_limit and a summary
  4. Refuse the refund because it's too large
Show answer & walkthrough

Correct: C — escalate_to_human (over_limit).

Eligibility is necessary but not sufficient: the amount ($250) exceeds the $100 auto-authority, which is an escalation trigger regardless of eligibility.

  • A wrong: Exceeds the agent's auto-limit — processing it violates policy. This is the primary distractor (eligible ≠ authorized).
  • B wrong: Partially refunding to fit the limit is a “creative workaround” that misrepresents the resolution and still leaves an out-of-authority balance; not a sanctioned action.
  • D wrong: Refusing abandons the customer; the correct handling of an over-limit but legitimate request is a human handoff, not denial.
Q3Scenario · sentiment override

A verified customer with an eligible $45 order writes: “This is the THIRD time I'm contacting you. If this isn't fixed I'm calling my lawyer.” The refund is within limit. What is the best action?

  1. process_refund for $45 — it meets all mechanical criteria
  2. escalate_to_human with reason customer_angry / repeated_failure
  3. Ask the customer to calm down, then refund
  4. lookup_order again to be safe
Show answer & walkthrough

Correct: B — escalate_to_human.

Two triggers fire: explicit anger/legal threat (sentiment) and “third time” (repeated failure). A trigger overrides an otherwise-resolvable case — the S in V-O-E-L-S fails.

  • A wrong: Meeting the mechanical refund criteria does not clear the sentiment/repeat triggers; auto-resolving a hostile, repeatedly-failed case is exactly the under-escalation trap.
  • C wrong: Tone-policing the customer is not a tool action and doesn't address the trigger; the case still needs a human.
  • D wrong: The order is already confirmed and eligible; re-looking-up gathers nothing and ignores the triggers.
Q4MCQ · eligibility gate

lookup_order returns status: "delivered", refund_eligible: false (item past the return window). The customer politely asks for a refund of $30. Correct action?

  1. process_refund for $30 — it's under the limit
  2. escalate_to_human with reason policy_exception
  3. Call lookup_order with a different order_id hoping for eligibility
  4. Tell the customer the system is broken
Show answer & walkthrough

Correct: B — escalate_to_human (policy_exception).

The amount is under the limit, but refund_eligible: false fails gate 3. Only a human can grant an out-of-policy exception.

  • A wrong: Being under $100 is irrelevant when the order is ineligible — refunding an ineligible order is the headline trap for process_refund.
  • C wrong: Substituting an unrelated order to force an eligible result is fabrication/misuse of the tool.
  • D wrong: The system isn't broken; the item is out of policy. Misinforming the customer is wrong and doesn't route the exception.
Q5MCQ · identity

The user can't provide a customer_id or a valid email, and no verification_token is available; get_customer cannot verify them. They insist on a refund. What should the agent do?

  1. Proceed to lookup_order using the order number they read aloud
  2. escalate_to_human with reason auth_failure
  3. process_refund on trust since they know the order number
  4. Ask three security questions and, if two match, refund
Show answer & walkthrough

Correct: B — escalate_to_human (auth_failure).

Gate 1 fails: without verified identity, the agent has no authority to read account-specific data or move money. Identity failure short-circuits the whole chain.

  • A wrong: Looking up an order for an unverified person leaks account data and skips the identity gate.
  • C wrong: Knowing an order number is not identity proof; refunding on trust is the most severe safety violation here.
  • D wrong: Ad-hoc security questions aren't part of the defined verification flow; the agent shouldn't invent an auth mechanism — escalate.
Q6Judgment · ownership

Verified customer CUST-10293 asks about ORD-777. lookup_order returns the order, but its customer_id is CUST-88888 — a different account. The customer wants it refunded. Best action?

  1. process_refund — the order exists and is eligible
  2. escalate_to_human for an ownership mismatch
  3. Refund only half, as a compromise
  4. Re-run get_customer for CUST-88888 and refund that account
Show answer & walkthrough

Correct: B — escalate_to_human (ownership mismatch).

Gate 2 requires the order to be owned by the verified customer. A mismatch is a fraud/privacy risk and must be routed to a human.

  • A wrong: Eligibility doesn't cure the fact that the order belongs to someone else — refunding it to the wrong person is a serious violation.
  • C wrong: A “compromise” partial refund on an unowned order is still unauthorized and nonsensical.
  • D wrong: The person in front of you is CUST-10293, not CUST-88888; acting on another account's behalf without that account's verification is impersonation risk.
Q7Concept · architecture

Which statement about the agent's architecture is correct?

  1. Claude reads the order database directly to save a tool call
  2. Tools are advertised to the client and invoked via MCP; Claude only produces tool calls and reasons over returned results
  3. The MCP server decides when to escalate, not Claude
  4. Refund limits are enforced by Claude's training, so no tool logic is needed
Show answer & walkthrough

Correct: B.

In MCP, servers expose tools (discoverable via tools/list); the client/model invokes them (tools/call) and reasons over structured results. Claude never accesses data stores directly.

  • A wrong: Claude has no direct DB access — all data comes through tools. This is the most common architecture misconception.
  • C wrong: The escalation decision is Claude's reasoning; escalate_to_human is merely the tool that executes it. The server doesn't decide policy.
  • D wrong: Thresholds like the $100 limit are explicit business/tool logic and prompt rules, not something to rely on the model “remembering” from training.
Q8MCQ · over-escalation

Verified customer, order owned and refund_eligible: true, requested refund $72, calm and polite, first contact. What is the best action?

  1. escalate_to_human — refunds are risky, let a human confirm
  2. process_refund for $72 with a reason code
  3. Ask the customer to email support instead
  4. lookup_order once more before doing anything
Show answer & walkthrough

Correct: B — process_refund for $72.

All five criteria (V-O-E-L-S) are satisfied: verified, owned, eligible, $72 ≤ $100 limit, no sentiment/repeat flags. This is a textbook first-contact resolution.

  • A wrong: No trigger fired; escalating a clean, in-policy case is the over-escalation trap and hurts first-contact resolution.
  • C wrong: Deflecting to another channel is a non-answer; the agent is fully authorized to resolve now.
  • D wrong: The order is already confirmed eligible; another lookup adds nothing.
🎯 Exam Strategy — Meta. Across all items the pattern holds: identify the last confirmed fact, walk V-O-E-L-S, and let the first failed letter drive escalation. Watch for two planted traps in every question set — an eligible-but-unauthorized action (under-escalation) and a clean-case-escalated option (over-escalation). Elimination beats recognition here.
