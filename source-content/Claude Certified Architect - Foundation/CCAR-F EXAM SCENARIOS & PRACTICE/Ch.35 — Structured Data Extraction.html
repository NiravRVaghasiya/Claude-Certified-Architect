35.1 Scenario Overview & Architecture

Structured data extraction is the task of turning unstructured or semi-structured input (documents, emails, logs, transcripts) into a predictable, machine-consumable structure (typically JSON) that a downstream system can trust. Claude is well suited to this because it can read messy real-world text and, when guided with tool use / structured output, emit a payload constrained to a schema you define.

Use case: automated invoice extraction into an ERP

Our running scenario: a finance operations team receives thousands of supplier invoices per month as PDFs and email bodies. Each must become a normalized JSON record — invoice_id, total_amount, currency, line_items[] — and be posted to an ERP (e.g. an accounts-payable API). The pipeline must be accurate, auditable, and resilient: a bad record must never silently corrupt the ledger.

System architecture diagram

Figure 35.1 — Four-stage pipeline. The validation layer is the trust boundary: nothing reaches the ERP until it passes schema + business-rule checks.

Key architectural decisions

Tool use vs. plain prompting

Prefer tool use (define a tool whose input_schema is your target schema). It constrains Claude to emit structured arguments and drastically reduces "prose around JSON" parsing errors versus asking for JSON in free text.

Temperature

Use low temperature (0–0.2) for extraction. You want deterministic, faithful transcription of what is in the document — not creativity. Higher temperature increases hallucinated/invented fields.

Streaming vs. batch

Batch suits high-volume back-office extraction (cost/throughput, async). Streaming helps interactive UIs where partial feedback matters — but you cannot validate a partial object, so validate only on the completed message.

Force the tool call

Set tool_choice to require your extraction tool so the model must return structured arguments rather than a chat reply. This makes the output shape predictable for the validation layer.

Idempotency

Carry a natural key (e.g. invoice_id) into the downstream write so retries don't create duplicates. The pipeline must be safe to run twice on the same input.

Observability

Log the raw model output, the parsed object, and the validation verdict for every record. Extraction quality is only measurable if you retain inputs, outputs, and outcomes.

💡 Tip: Treat the schema as the contract between the model and the downstream system. When both the model's input_schema and the validation layer reference the same schema definition, you eliminate an entire class of "the model and the validator disagree" bugs.
⚠️ Common pitfall: Assuming tool use guarantees a schema-valid payload. Tool use strongly biases the model toward your shape, but it is not a hard validator — the model can still omit a field, coerce a type, or invent a value. You must still validate. Skipping validation "because we used tool use" is the single most common design error in this scenario.

📋 35.1 Cheat sheet

  • Four stages: Input → Claude (tool use) → Validation → Downstream.
  • Validation is the trust boundary — validate before any downstream write.
  • Defaults: tool use + forced tool_choice + temperature 0–0.2 + batch for volume.
  • Design for idempotency, observability, and "fail closed."

35.2 JSON Schema Validation & Edge Case Handling

A JSON Schema is a declarative document that describes the allowed shape of a JSON value: which properties exist, their types, which are required, and constraints on values. In this scenario the schema plays two roles: (1) it is handed to Claude as the tool's input_schema to guide generation, and (2) it is enforced by a validator (e.g. jsonschema in Python, Ajv in Node, or Pydantic) before anything moves downstream.

Defining & enforcing the schema

JSON Schema — invoice contract 
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "invoice_id":   { "type": "string", "minLength": 1 },
    "currency":     { "type": "string", "pattern": "^[A-Z]{3}$" },
    "total_amount": { "type": "number", "minimum": 0 },
    "line_items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "additionalProperties": false,
        "properties": {
          "description": { "type": "string" },
          "quantity":    { "type": "integer", "minimum": 1 },
          "unit_price":  { "type": "number", "minimum": 0 }
        },
        "required": ["description", "quantity", "unit_price"]
      }
    }
  },
  "required": ["invoice_id", "currency", "total_amount", "line_items"]
}

Two clauses do most of the defensive work here:

  • "additionalProperties": false — rejects any field the model invents that you did not declare (a hallucinated tax_code, say). This is your primary defence against hallucinated fields.
  • "required": [...] — makes missing fields a hard failure rather than a silent null that reaches the ERP.
Enforcement — Python (jsonschema) 
from jsonschema import Draft202012Validator

validator = Draft202012Validator(INVOICE_SCHEMA)

def validate_extraction(payload: dict):
    errors = sorted(validator.iter_errors(payload), key=lambda e: e.path)
    if errors:
        return False, [f"{list(e.path)}: {e.message}" for e in errors]
    return True, []

# ok, problems = validate_extraction(claude_tool_input)
# if not ok: route to repair / DLQ  (see 35.3)
💡 Tip: Use iter_errors (collect all problems) rather than validate (raises on the first). Feeding the full error list back into a repair prompt lets Claude fix every issue in one retry instead of ping-ponging one error at a time.

Malformed output examples

The validator's job is to catch these three canonical failure modes before they escape:

❌ Missing required field (currency absent) 
{
  "invoice_id": "INV-2024-0912",
  "total_amount": 1480.50,
  "line_items": [
    { "description": "Widget A", "quantity": 10, "unit_price": 148.05 }
  ]
}
// → FAILS: 'currency' is a required property
❌ Wrong type (total_amount as string, quantity as float) 
{
  "invoice_id": "INV-2024-0912",
  "currency": "USD",
  "total_amount": "1,480.50",          // string, not number
  "line_items": [
    { "description": "Widget A", "quantity": 10.0, "unit_price": 148.05 }
  ]                                     // quantity 10.0 is not an integer
}
// → FAILS: '1,480.50' is not of type 'number'; 10.0 is not of type 'integer'
❌ Hallucinated field (discount_reason not in schema) 
{
  "invoice_id": "INV-2024-0912",
  "currency": "USD",
  "total_amount": 1480.50,
  "discount_reason": "loyal customer",   // never appeared in the document
  "line_items": [
    { "description": "Widget A", "quantity": 10, "unit_price": 148.05 }
  ]
}
// → FAILS: additional properties 'discount_reason' not allowed
⚠️ Common pitfall — silent coercion. If you parse with a permissive layer that auto-coerces types (e.g. turning "1,480.50" into a number, or silently dropping unknown keys), you can mask a real extraction error. Coercion is fine as an explicit, logged normalization step — never as an invisible side effect of your parser. Decide deliberately what you normalize vs. what you reject.

Edge case → detection method → recommended fix

Edge caseDetection methodRecommended fix
Missing required field required keyword fails during schema validation Repair prompt with the error; if truly absent from source, route to human review — do not fabricate.
Wrong type (e.g. string for number) type keyword mismatch Explicit, logged normalization (strip thousands separators, parse), then re-validate; reject if it still fails.
Hallucinated / extra field additionalProperties: false Strip if provably safe, but prefer to reject + retry — an invented field can signal broader hallucination.
Out-of-range value (negative total) minimum / maximum constraints Flag as business-rule violation; quarantine for review rather than clamping silently.
Empty array where data expected minItems constraint Retry with instruction to extract at least one line item; escalate if document genuinely has none.
Malformed / truncated JSON JSON parse fails before schema check (e.g. from a truncated stream) Check stop reason / increase max_tokens; retry. With tool use this is rare vs. free-text JSON.
Enum / format violation (bad currency code) pattern / enum / format Normalize against a known code list; reject unknown codes to human review.
Cross-field inconsistency (total_amount ≠ Σ line items) Business-rule check after schema passes (schema alone can't express it) Recompute and compare within tolerance; on mismatch, flag for review.
💡 Tip: JSON Schema validates structure and simple constraints. It cannot express "the total must equal the sum of line items." Layer a small set of business-rule checks after schema validation to catch semantic errors the schema is blind to.

📋 35.2 Cheat sheet

  • Schema = contract. Same definition feeds Claude's input_schema and your validator.
  • Two power clauses: required (catches missing) + additionalProperties:false (catches hallucinated).
  • Three canonical failures: missing field · wrong type · hallucinated field.
  • Collect all errors (iter_errors) for one-shot repair.
  • Schema + business rules — schema can't check cross-field math or "sum equals total."
  • Never fabricate a missing value; normalize explicitly and log it.

35.3 Downstream System Integration

Once a payload is validated, it must reach the system of record reliably. The core rule persists: validate before write. How you deliver the validated record depends on latency, volume, and coupling requirements.

Integration patterns

PatternWhen to useTrade-offs
Synchronous API call (POST to ERP/AP API) Low volume, need an immediate confirmation, tight coupling acceptable. Simple; but a slow/failing downstream directly stalls extraction. Needs timeouts + idempotency keys.
Message queue (SQS/Kafka/RabbitMQ) High volume, spiky load, want to decouple extraction from ingestion. Buffers bursts, enables independent scaling & retry; adds infra and eventual-consistency reasoning.
Direct database write You own the store and want the record persisted for later processing/audit. Fast, transactional; couples the pipeline to the schema of the store — use upserts keyed on the natural id.
💡 Tip: The queue-based pattern is usually the exam's "best" answer for high-volume, resilient extraction: it decouples the LLM step from the downstream, absorbs traffic spikes, and gives you retry + dead-letter semantics for free.

Retry / fallback flow when validation fails

Figure 35.3 — Retry/fallback loop. Bounded retries with a repair prompt, then a dead-letter queue that routes to human review. The pipeline never blocks and never writes bad data.

Error-handling strategies

  • Bounded retries with a repair prompt. On validation failure, re-invoke Claude with the original input plus the specific validation errors and an instruction to correct them. Cap attempts (e.g. 3) and use exponential backoff for transient/API errors.
  • Distinguish error classes. A transient error (429/5xx, timeout) warrants a plain retry with backoff. A validation error warrants a repair-prompt retry. A deterministic content error (data simply isn't in the document) should go straight to human review — retrying won't help.
  • Dead-letter queue (DLQ). After retries are exhausted, move the record (with its raw input, model output, and error trail) to a DLQ so it is preserved, auditable, and doesn't block throughput.
  • Human-in-the-loop. A reviewer inspects DLQ items, corrects or rejects them, and — ideally — those corrections feed back into prompt/schema improvements. This is your safety net for the long tail.
  • Idempotency & exactly-once effect. Use the natural key (invoice_id) as an idempotency key on the downstream write so retries never double-post.
  • Circuit breaking. If the downstream is down, stop hammering it — open a breaker, buffer in the queue, and drain when healthy.
⚠️ Common pitfall — retrying the same prompt unchanged. Re-sending the identical prompt after a validation failure usually reproduces the same failure and wastes tokens. Retries must be informed: feed the validation errors back so the model can actually correct them. And never retry indefinitely — bound it, then quarantine.
💡 Tip: Make the DLQ rich. Store the raw document, the exact model output, the schema version, and the ordered list of validation errors. A reviewer (or a debugging engineer) can resolve an item in seconds when the full context travels with it.

📋 35.3 Cheat sheet

  • Patterns: sync API (simple/low-volume) · queue (high-volume/decoupled — usually "best") · DB write (owned store, upsert on key).
  • Loop: extract → validate → (valid) write / (invalid) bounded repair-retry → DLQ → human.
  • Match the retry to the error: transient → backoff; validation → repair prompt; missing-in-source → human.
  • Always idempotent downstream writes; always bounded retries.
  • DLQ preserves & unblocks; human-in-the-loop is the long-tail safety net.

35.4 Practice Questions & Walkthroughs

Five scenario-style items in the pattern the exam favours. Read each stem for the qualifier — BEST, MOST, FIRST — before scanning options.

Q1
A downstream ERP system rejects a Claude-extracted JSON payload due to an unexpected null in a required field. What is the BEST architectural fix?
  • A) Increase model temperature so the field is filled more often.
  • B) Add schema validation with a default-value fallback (or repair step) before sending downstream.
  • C) Retry the same prompt indefinitely until the field is populated.
  • D) Disable the required-field constraint in the ERP.
✔ Correct: B. Validation is the trust boundary — catching the null before the write and applying a deliberate fallback (or repair retry) prevents the bad record from ever reaching the ERP.
‘A’ wrong: higher temperature increases hallucination, not correctness. ‘C’ wrong: unbounded identical retries loop and burn tokens. ‘D’ wrong: removing the constraint hides the defect and corrupts the ledger.
Q2
You want to minimise the chance that Claude returns prose wrapped around your JSON, forcing brittle string parsing. Which design choice helps MOST?
  • A) Ask for JSON in the system prompt and parse the first {...} you find with a regex.
  • B) Define an extraction tool with an input_schema and force tool_choice to that tool.
  • C) Raise max_tokens so the JSON is never truncated.
  • D) Increase temperature to make the model more flexible about formatting.
✔ Correct: B. Tool use makes the model emit structured arguments as tool input, and forcing tool_choice guarantees it calls your tool rather than replying in chat — removing the "prose around JSON" problem at the source.
‘A’ wrong: regex-scraping JSON from free text is exactly the brittleness you're trying to avoid. ‘C’ wrong: helps with truncation only, not formatting. ‘D’ wrong: higher temperature makes formatting less predictable.
Q3
Your schema passes, but finance reports that some invoices post with a total_amount that doesn't equal the sum of line items. What is the MOST appropriate fix?
  • A) Add additionalProperties: false to the schema.
  • B) Add a minimum constraint to total_amount.
  • C) Add a business-rule check after schema validation that compares the total to the summed line items within a tolerance.
  • D) Lower the temperature to 0.
✔ Correct: C. JSON Schema validates structure and simple per-field constraints but cannot express cross-field relationships like "total equals the sum of items." A business-rule check layered after schema validation is the right tool.
‘A’ wrong: blocks hallucinated fields, unrelated to arithmetic. ‘B’ wrong: only bounds the value, doesn't compare fields. ‘D’ wrong: may reduce errors marginally but doesn't detect the inconsistency.
Q4
Extraction volume is spiky — 10× spikes at month-end — and the ERP occasionally goes down for maintenance. Which integration pattern is BEST?
  • A) Synchronous POST from the extraction worker straight to the ERP.
  • B) A message queue between validation and the ERP, with retry + dead-letter semantics.
  • C) Write to a local file and email it to finance nightly.
  • D) Skip validation during spikes to keep up with volume.
✔ Correct: B. A queue decouples extraction from the ERP, absorbs the month-end spike, and lets the consumer retry (or dead-letter) while the ERP is down — nothing is lost and nothing blocks.
‘A’ wrong: a synchronous call stalls the whole pipeline when the ERP is unavailable. ‘C’ wrong: loses auditability and timeliness. ‘D’ wrong: never trade correctness for throughput — that's how bad data enters the ledger.
Q5
A validation failure occurs because a required tax_id is genuinely absent from the source document. What should the pipeline do FIRST?
  • A) Have Claude infer a plausible tax_id so the record can pass.
  • B) Retry the extraction three more times with the same prompt.
  • C) Route the record to human review (via the DLQ) rather than fabricate a value.
  • D) Delete the required constraint for tax_id.
✔ Correct: C. When data is truly not present in the source, no amount of retrying or prompting can honestly produce it. The correct move is to quarantine for human review — fabricating a value would corrupt the record and defeat the point of extraction.
‘A’ wrong: inventing data is the worst outcome — it's confidently wrong. ‘B’ wrong: retries can't extract what isn't there. ‘D’ wrong: weakening the contract lets incomplete records through system-wide.

🎯 Exam Strategy

  • Watch the qualifier. BEST / MOST / FIRST changes the answer. Several options may be "not wrong" — pick the one that best satisfies the qualifier.
  • Eliminate anti-patterns instantly. Options that increase temperature to fix correctness, retry indefinitely, disable a constraint, skip validation, or fabricate data are almost always distractors. Cross them out first — this often leaves one answer.
  • The recurring right answer in this scenario is "validate before write, then repair/retry with bounds, then human-in-the-loop." When in doubt, choose the option that protects the trust boundary.
  • Time management. For scenario items, budget roughly a minute each: ~15s to read the stem and spot the qualifier, ~25s to eliminate two distractors, ~20s to decide between the final two. Flag and move on rather than stalling — a hard item is worth the same as an easy one.
  • Read the last sentence of the stem twice. It usually contains the actual ask (the constraint or goal) that discriminates between the two plausible options.

📋 35.4 Cheat sheet

  • Default correct move: validate → repair-retry (bounded) → DLQ → human.
  • Instant distractors: raise temperature for correctness · retry forever · disable constraints · skip validation · fabricate data.
  • Cross-field logic → business rules, not schema. Prose-around-JSON → tool use + forced tool_choice.
  • Spiky volume + flaky downstream → message queue.
