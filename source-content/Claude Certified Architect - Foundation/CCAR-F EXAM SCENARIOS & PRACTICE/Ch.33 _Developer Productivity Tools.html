33.1 · Scenario Overview & Tooling

The scenario. A developer wants Claude to act as a productive engineering collaborator inside a real software project: exploring an unfamiliar codebase, reading and editing files, running tests, fetching documentation, and reaching into external systems (issue trackers, databases, internal APIs). Chapter 33 asks: which capability do you reach for, and why?

Claude's developer-productivity capabilities fall into two families, and the single most important skill this chapter tests is telling them apart:

  • Built-in tools — a fixed, Anthropic-defined set (e.g. bash, text_editor, code_execution, web_search, web_fetch, computer_use). You enable them by declaring the tool in the API request. They cover general coding and web operations.
  • MCP (Model Context Protocol) servers — an open, extensible integration layer. When you need Claude to talk to a specific or private system (Jira, GitHub, Postgres, an internal service), you connect an MCP server that exposes that system as callable tools/resources/prompts.

Rule of thumb: built-in tools answer "can Claude run code / read files / browse the open web?" MCP answers "can Claude interact with this particular external system in a governed, reusable way?" They are complementary, not competing — a real workflow often uses both.

Decision aid: which capability fits the need?

💡 Tips & Tricks
  • Read the target in the question, not the verb. "Query our internal service" ⇒ MCP. "Run this Python" ⇒ code_execution. "Read this public docs page" ⇒ web_fetch.
  • Keywords that scream MCP: private, internal, third-party, connect to, our database, our Jira, reusable across teams.
  • Keywords that scream built-in: run, execute, shell command, edit this file, browse the web, fetch this URL.
  • "Complementary, not either/or" is the most common correct framing — a workflow can use bash to run tests and an MCP server to update the ticket.
🎯 Exam Strategy
  • Selection questions almost always hinge on where the data/system lives. Classify first: open web, local execution, or a specific external system.
  • Distractors pair a plausible built-in tool with an external-system task (e.g. "use web_fetch to read Jira"). Reject built-in tools when the target is private/authenticated — web_fetch retrieves public URLs, not gated internal systems.
  • If two options seem valid, prefer the one that is reusable and governed for repeated organizational use (MCP) over a one-off command.

33.2 · Built-In Tools for Codebase Exploration

What they are. Built-in tools are Anthropic-defined tool types you enable in a Messages API request. For coding work the core set is bash, text_editor, code_execution, and the web tools web_search/web_fetch; computer_use extends Claude to GUI/desktop control.

The key architectural distinction — where does the tool run?

  • Client-side (you execute): bash, text_editor, computer_use. The API returns a tool_use block describing the requested action; your application executes it in your own environment and returns a tool_result. Anthropic never touches your filesystem — you are responsible for sandboxing and safety.
  • Server-side (Anthropic executes): code_execution, web_search, web_fetch. These run inside Anthropic-hosted infrastructure (e.g. a sandboxed Python environment for code execution) and return results directly — no local execution loop required.

How each tool supports codebase exploration

  • bash — run shell commands in a persistent session: grep -r/rg to search, ls/find to map structure, git log to inspect history, npm test/pytest to run suites. Session state (cwd, env) persists across calls.
  • text_editor — structured file viewing and editing via commands such as view (read a file or directory, optionally a line range), str_replace (surgical edit), create, and insert. Preferred over bash for precise reads/edits because it is targeted and less error-prone than stream editing.
  • code_execution — runs code (Python) in an Anthropic-hosted sandbox for analysis, quick computations, data processing, and validating snippets — without exposing your machine.
  • web_search / web_fetch — pull in public reference material: library docs, changelogs, error-message lookups, API references. web_search queries the open web; web_fetch retrieves the contents of a specific URL.
  • computer_use — screenshot-driven mouse/keyboard control of a GUI; used when a task requires a desktop app or browser UI rather than a shell. Runs in an environment you provide.

💡 Tips & Tricks
  • Editing? Default to text_editor for precision (str_replace/view). Use bash when you genuinely need a process (tests, git, package managers).
  • Isolation matters? code_execution = Anthropic sandbox (safe, disposable). bash = your machine (you own the risk). Exam distractors blur this.
  • web_fetch ≠ private data. It reads public URLs. For anything authenticated/internal, that's an MCP job (see 33.3).
  • Remember the loop: client-side tools require you to run the command and post a tool_result; forgetting this is a classic "why isn't it working" trap.
🎯 Exam Strategy
  • When a question stresses safety / isolation / "without touching my machine," the answer is the server-side option (code_execution), not bash.
  • When it stresses "exact edit to one function" or "view lines 40–60," choose text_editor over bash stream edits.
  • Watch for execution-locus traps: any option claiming bash runs "on Anthropic's servers" is wrong — bash/text_editor/computer_use execute in your environment.
  • computer_use is the answer only when there's no API/CLI path — i.e. a GUI-only task. If a shell or API works, prefer it.

33.3 · MCP Server Integration for Developer Workflows

What MCP is. The Model Context Protocol (MCP) is an open standard (open-sourced by Anthropic in late 2024) for connecting LLM applications to external tools and data sources through a uniform interface. Think of it as a universal adapter: instead of writing a bespoke integration for every model + every system, a system exposes an MCP server once, and any MCP-capable host can use it.

Architecture

  • Host — the LLM application (e.g. an IDE assistant, Claude Desktop, a custom agent). It manages one or more clients.
  • Client — lives inside the host and maintains a 1:1 connection to a single MCP server. If a host uses three servers, it runs three clients.
  • Server — a program that exposes capabilities (Tools, Resources, Prompts) for one system (GitHub, Postgres, a filesystem, an internal API).

Messages travel as JSON-RPC 2.0. The connection begins with an initialize handshake where host and server negotiate protocol version and capabilities; the client then discovers what the server offers by listing its tools/resources/prompts (e.g. tools/list) and invoking them (e.g. tools/call).

Transports — how client and server talk

Table 33.3a — MCP transports
TransportHow it worksTypical use
stdioClient launches the server as a local subprocess; messages flow over standard input/outputLocal servers on the same machine (e.g. a local filesystem or git server)
Streamable HTTP (supersedes the earlier HTTP + Server-Sent Events transport)Client connects to the server over HTTP; supports streaming responsesRemote / hosted servers, shared services, cloud deployments

The three server primitives

Table 33.3b — MCP primitives and who controls them
PrimitiveWhat it isControl modelDev-workflow example
ToolsExecutable functions the model can invoke (actions with effects)Model-controlled (the LLM decides to call)create_issue, run_query, open_pull_request
ResourcesRead-only data/context identified by a URIApplication-controlled (host decides what to load)A file's contents, a DB record, a doc referenced by URI
PromptsReusable templated messages/workflowsUser-controlled (user selects/triggers)A "review this PR" or "summarize incident" prompt template

Note: MCP also defines client features such as Sampling (a server can ask the host's model to generate a completion) and Roots (the host tells the server which files/directories are in scope). These are client-side capabilities, distinct from the three server primitives above.

Why MCP for developer workflows

  • Repo analysis: a GitHub/Git MCP server exposes issues, PRs, and file history as tools/resources — Claude can triage, summarize, or open PRs through governed actions.
  • CI/CD & internal services: wrap build systems, deployment APIs, or feature-flag services as MCP tools so agents can trigger or read pipeline state safely.
  • IDE integration: the IDE acts as the host; MCP servers give the in-editor assistant access to the project's real systems (tracker, DB, secrets-scoped services) without hardcoding integrations.
  • Reusability & governance: build the server once; every team/host reuses it. The server controls exactly what surface is exposed, centralizing auth and scoping.
💡 Tips & Tricks
  • Memorize the control-model triad: Tools = model-controlled, Resources = application-controlled, Prompts = user-controlled. This exact mapping is a favorite test point.
  • 1:1 client-to-server is a fact to lock in — "one client can manage many servers" is a classic wrong answer.
  • Transport picker: local subprocess → stdio; remote/hosted → Streamable HTTP.
  • MCP rides on JSON-RPC 2.0 — if an option says "REST-only" or "GraphQL protocol," it's wrong.
  • When a question says "real-time external data" or "third-party API," think MCP server — not a built-in tool.
🎯 Exam Strategy
  • Primitive questions: match the noun to the control model. "Read-only data by URI" ⇒ Resource; "action the model invokes" ⇒ Tool; "reusable user-triggered template" ⇒ Prompt.
  • Architecture questions: the safe answers are host contains clients, client:server is 1:1, JSON-RPC 2.0, and transports are stdio or HTTP.
  • Beware conflating Sampling/Roots (client features) with the three server primitives. If asked "which are the server primitives," the answer is Tools, Resources, Prompts only.
  • "Why MCP over a one-off integration?" ⇒ emphasize standardization, reusability, and governance, not raw speed.

33.4 · Practice Questions & Walkthroughs

Eight questions (MCQ + scenario). Reveal each answer to see the full walkthrough. At least one item explicitly tests the MCP vs. built-in-tool distinction (see Q1 and Q7).

Scenario

Q1. A developer wants Claude to query the team's private, authenticated Jira instance during a coding session and later create tickets from findings. Which approach is correct?

  1. Use the bash tool
  2. Use an MCP server connector for Jira
  3. Use web_fetch on the Jira URL
  4. Use code_execution
Answer & Walkthrough

Correct: B

Why: Jira is a specific, private, authenticated external system. MCP servers exist precisely to expose such systems as governed tools/resources — here, a Jira MCP server offers actions like create_issue and read access to tickets.

Why not the others: bash (A) runs local shell commands, not a governed Jira integration. web_fetch (C) retrieves public URLs and can't authenticate into a private instance. code_execution (D) runs code in a sandbox with no built-in Jira access.

Takeaway: private/third-party system ⇒ MCP.

MCQ

Q2. Which set correctly lists the three MCP server primitives?

  1. Tools, Resources, Prompts
  2. Tools, Sampling, Roots
  3. Clients, Servers, Transports
  4. Functions, Files, Sessions
Answer & Walkthrough

Correct: A

Why: The server exposes Tools (model-controlled actions), Resources (application-controlled read-only data by URI), and Prompts (user-controlled templates).

Trap: B mixes in Sampling and Roots, which are client features, not server primitives. C names architectural components, not primitives. D is invented.

MCQ

Q3. A developer needs Claude to run a Python snippet to validate an algorithm without executing anything on their own machine. Best choice?

  1. bash tool
  2. code_execution tool
  3. computer_use tool
  4. An MCP server
Answer & Walkthrough

Correct: B

Why: code_execution runs in an Anthropic-hosted sandbox (server-side), so nothing runs on the developer's machine — matching the "without executing on my machine" requirement.

Why not: bash (A) executes client-side on your environment. computer_use (C) drives a GUI you host. MCP (D) is for integrating external systems, not general code execution.

MCQ

Q4. In MCP, what is the relationship between a client and a server?

  1. One client connects to many servers simultaneously
  2. One client maintains a 1:1 connection with one server
  3. Servers connect to many clients in a mesh
  4. Clients and servers are the same component
Answer & Walkthrough

Correct: B

Why: Each MCP client holds a dedicated 1:1 connection to a single server. A host that needs multiple servers simply runs multiple clients.

Trap: A is the most tempting distractor — the host can use many servers, but it does so via many clients, one per server.

Scenario

Q5. Claude must make a surgical edit — replace one function body in service.py without disturbing the rest of the file. Which built-in tool is the best fit?

  1. bash with sed
  2. text_editor (str_replace)
  3. web_fetch
  4. code_execution
Answer & Walkthrough

Correct: B

Why: text_editor is purpose-built for precise reads/edits; its str_replace command targets an exact string, making it safer and more reliable than stream editing.

Why not: sed via bash (A) works but is error-prone for structured edits and is not the best fit. web_fetch (C) and code_execution (D) don't edit local files at all.

MCQ

Q6. A team wants an MCP server that a local host launches as a subprocess on the same machine. Which transport is most appropriate?

  1. Streamable HTTP
  2. stdio
  3. WebSockets-only
  4. FTP
Answer & Walkthrough

Correct: B

Why: stdio is the standard transport for local servers launched as a subprocess — messages flow over standard input/output. Remote/hosted servers use Streamable HTTP (A). C and D are not MCP transports.

Scenario

Q7. (MCP vs. built-in) A workflow needs to: (1) read the latest public release notes for a library, (2) run the project's test suite locally, and (3) update the status of a ticket in the company's internal tracker. Match each step to the right capability.

  1. (1) web_fetch/web_search · (2) bash · (3) MCP server
  2. (1) MCP server · (2) code_execution · (3) web_fetch
  3. (1) bash · (2) MCP server · (3) text_editor
  4. All three via a single MCP server
Answer & Walkthrough

Correct: A

Step (1) — public release notes: open-web content ⇒ built-in web_search/web_fetch.

Step (2) — run tests locally: process execution in the project environment ⇒ built-in bash.

Step (3) — internal tracker: a specific private system ⇒ MCP server.

Key insight: real workflows are mixed — built-in tools for open-web + local execution, MCP for private/external systems. Option D wrongly forces everything through MCP; MCP is not a general code runner or web browser.

MCQ

Q8. Which statement about MCP primitive control models is correct?

  1. Resources are model-controlled; Tools are user-controlled
  2. Tools are model-controlled; Resources are application-controlled; Prompts are user-controlled
  3. All three primitives are always model-controlled
  4. Prompts are model-controlled; Tools are application-controlled
Answer & Walkthrough

Correct: B

Why: Tools are invoked by the model (model-controlled); Resources are selected/loaded by the host application (application-controlled); Prompts are chosen/triggered by the user (user-controlled).

Trap: Options A, C, and D scramble the mapping. Memorize the triad exactly — it is a recurring test point.

Chapter summary. Developer-productivity work with Claude combines two capability families: built-in tools (bash, text_editor, code_execution, web_search/web_fetch, computer_use) for general code, file, and open-web operations, and MCP servers for governed, reusable integration with specific/private systems. The decisive skills are (a) classifying a task by where the target lives, (b) knowing each built-in tool's execution locus (client-side vs. Anthropic-hosted), and (c) mastering MCP's architecture (host → client 1:1 → server), transports (stdio, Streamable HTTP), and primitives (Tools/Resources/Prompts with their model/application/user control models).
