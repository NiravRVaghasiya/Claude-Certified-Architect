21.1 Retry-with-Error-Feedback: Appending Specific Validation Errors

Concept Explanation

Retry-with-error-feedback is a self-correction pattern: when a model’s output fails validation, you don’t just call the model again with the same prompt. Instead you construct a new prompt that includes (a) the original request, (b) the model’s failed output, and (c) the specific validation error that was raised. The model then repairs its own output using the concrete feedback.

The critical word is specific. “Your JSON was invalid” yields another random guess. “Field stated_total was a string \"250.00\" but must be a number” tells the model exactly what to fix.

How It Works

  1. Generate — model produces a structured response.
  2. Validate — run the output through schema + semantic checks.
  3. Capture — on failure, serialize a structured, human-readable error (field, expected, actual).
  4. Compose retry prompt — original instructions + the failed output + the exact error string.
  5. Regenerate — model returns a corrected response.
  6. Re-validate — pass ⇒ done; fail ⇒ loop until max_attempts.

Visualization — Retry Loop

Fig 21.1 — Error-feedback retry loop
Prompt→ Generate→ Validate?→ ✓ Return
↺ on failure: append error_message + offending value, increment attempt, regenerate
✗ Fail→ Build feedback prompt→ attempt < max?→ Generate (retry)
attempt ≥ max ⇒ escalate / abort

Code / Config Example

Retry prompt payload (attempt 2)
{
  "attempt": 2,
  "max_attempts": 3,
  "original_instruction": "Extract the invoice into the InvoiceSchema.",
  "previous_output": { "stated_total": "250.00", /* string, not number */ },
  "validation_error": {
    "field": "stated_total",
    "expected": "number",
    "actual": "string \"250.00\"",
    "error_message": "stated_total must be a JSON number, not a string. Return 250.00 (no quotes)."
  }
}
💡 Tip: Echo the offending value back verbatim in the retry prompt (“you returned \"250.00\"”). Models correct far more reliably when they can see their own mistake next to the rule they broke.
🎯 Exam Strategy: Distinguish a blind retry (same prompt, hope for a better sample) from an error-feedback retry (augmented prompt carrying the specific error). Distractors often propose “increase max_tokens” or “raise temperature” as the fix for a validation failure — those change sampling, not correctness. Example-style question: An extraction agent returns malformed JSON. Which change most directly improves the next attempt’s success? → Append the specific parser error and the offending fragment to the retry prompt.

21.2 When Retries Work (Format Mismatches) vs. When They Don’t (Absent Data)

Concept Explanation

Retries are powerful but not magic. They help when the information exists and only its form is wrong. They fail when the required information is simply not present in the source — no number of retries can invent data that was never there. Confusing these two cases is the most common (and most expensive) design mistake in retry logic.

How It Works — Classify Before You Retry

  1. On validation failure, ask: is the data present but mis-formatted, or is it absent?
  2. Present + mis-formatted → error-feedback retry (21.1). High success rate.
  3. Absent → short-circuit: do not retry. Escalate, request the missing input, or return a structured “needs human” result.

Visualization — Retry-Works vs. Retry-Fails

ScenarioRetry likely to succeed?Reason
Date MM/DD/YYYY expected, model returned DD-MM-YYYY✅ YesFormat mismatch — the value exists, model can reformat.
stated_total returned as string "250.00"✅ YesType coercion — data present, wrong JSON type.
Enum value "US-DOLLAR" instead of allowed "USD"✅ YesNormalisation — map to the permitted token.
Required customer_id not present anywhere in the source document❌ NoData absent — retrying invents/hallucinates a value.
Invoice has no line items, but a per-line breakdown is required❌ NoSource lacks the data — escalate, don’t loop.
Model must cite a statute the document never mentions❌ NoNo grounding — retry pressure increases hallucination risk.
⚠️ Anti-pattern: Looping on an absent-data failure doesn’t just waste tokens — it actively pushes the model toward hallucinating a plausible-looking value to satisfy the schema. A schema-valid hallucination is worse than an honest failure.
💡 Tip: Make your validator emit a machine-readable recoverable: true|false flag. Your retry controller reads that flag to decide retry vs. escalate — never leave the recover/abort decision to prompt vibes.
🎯 Exam Strategy: Watch for the “just try again” trap. If the stem says a required field is missing from the source, the correct answer is escalate / request input / return partial result — never “retry with higher temperature.” Key phrase: “data not present in the source.” Example-style question: An agent cannot find a mandatory customer_id in the uploaded PDF. Best action? → Short-circuit the retry loop and flag for human input.

21.3 Feedback Loop Design: Tracking Dismissal Patterns

Concept Explanation

There are two distinct loops. The retry loop (21.1) is synchronous and lives inside a single request. The feedback loop is asynchronous and lives across many requests: it observes how users react to the system’s output — especially dismissals (rejecting, overriding, or ignoring a suggestion) — and feeds that signal back to improve prompts, thresholds, and validators over time.

Every dismissal is a labelled data point: the system predicted “this is worth surfacing,” the human said “no.” Aggregating the detected_pattern behind dismissed items reveals systematic false positives.

How It Works — Dismissal Lifecycle

Tuning Job → Agent: raise tolerance / down-weight the noisy pattern; update prompt or threshold

Code / Config Example

Dismissal event record
{

  "detected_pattern": "rounding_mismatch",
  "conflict_detected": true,
  "delta": { "calculated_total": 245.00, "stated_total": 245.01 },
  "user_decision": "dismissed",
  "reason": "sub-cent rounding is acceptable for this vendor",
  "timestamp": "2026-09-23T10:14:02Z"
}
💡 Tip: Aggregate dismissals by detected_pattern. If one pattern is dismissed >80% of the time, it’s a systematic false positive — fix the rule (e.g. add a rounding tolerance), don’t just silence individual alerts.
⚠️ Watch out: A feedback loop that only suppresses alerts can silently hide true positives. Track dismissal reasons, not just counts, and keep a small human-audited sample to detect over-suppression drift.
🎯 Exam Strategy: The tested distinction is synchronous retry loop (fixes one output, now) vs. asynchronous feedback loop (improves the system, later). If a question mentions “over many sessions,” “aggregate,” or “tune thresholds,” it’s the feedback loop — not retry. Example-style question: Users repeatedly dismiss the same detected_pattern. What’s the right systemic response? → Aggregate dismissals offline and adjust the detection threshold / prompt.

21.4 Semantic vs. Schema Validation Errors

Concept Explanation

A schema (structural) error means the output has the wrong shape: malformed JSON, a missing required field, a wrong type, an out-of-range enum. A semantic (logical) error means the output is structurally perfect but meaningfully wrong: the totals don’t add up, a “ship date” precedes the “order date,” or two fields contradict each other. Schema validity is necessary but not sufficient.

How It Works — Two-Stage Gate

  1. Schema validation first (cheap, deterministic) — parse & type-check against the schema. Fail fast.
  2. Semantic validation second (more expensive) — run business rules only on shape-valid data. This is where conflict_detected is set.

Visualization — Schema vs. Semantic

🧱 Schema / Structural

  • Wrong shape
  • Malformed JSON, missing field, wrong type, bad enum
  • Caught by JSON Schema / Pydantic / type parser
  • Deterministic & cheap
  • Example: stated_total: "250" (string, not number)

🧠 Semantic / Logical

  • Right shape, wrong meaning
  • Totals mismatch, date order, cross-field contradiction
  • Caught by business-rule checks / recomputation
  • Often needs domain logic or a second model pass
  • Example: calculated_total ≠ stated_total ⇒ conflict_detected: true

Code / Config Example

Schema error (structural)
{
  "error_class": "schema",
  "field": "line_items",
  "error_message": "Expected array, got null. Field is required.",
  "recoverable": true
}
Semantic error (logical)
{
  "error_class": "semantic",
  "conflict_detected": true,
  "detected_pattern": "sum_mismatch",
  "calculated_total": 245.00,
  "stated_total": 250.00,
  "error_message": "Sum of line items (245.00) != stated_total (250.00)."
}
💡 Tip: Run schema validation before semantic validation. There’s no point recomputing a total on data that isn’t even parseable — and schema checks are orders of magnitude cheaper.
🎯 Exam Strategy: Watch for questions contrasting “schema-invalid” (structurally wrong) vs. “semantically-invalid” (structurally fine, logically wrong). A frequent distractor calls a totals mismatch a “schema error” — it isn’t; the JSON is well-formed, so it’s semantic. Example-style question: JSON parses cleanly and matches the schema, but the shipping date is before the order date. This is a ___ error. → Semantic.

21.5 Self-Correction Validation Flows: calculated_total vs stated_total

Concept Explanation

Language models are unreliable arithmeticians, so a robust extraction system never trusts a total the model reports. Instead it independently recomputes the value in code and compares:

  • stated_total — the figure the model/document asserts (untrusted).
  • calculated_total — the figure your code derives from the line items (authoritative).

If they disagree beyond a tolerance, set conflict_detected: true, label the detected_pattern, and route into self-correction.

How It Works — Recompute & Reconcile

Fig 21.5 — Self-correction flow
Extract line_items→ Σ items = calculated_total→ |calc − stated| ≤ ε ?
within tolerance ε ⇒ conflict_detected=false ⇒ accept
mismatch→ set conflict_detected=true
label detected_pattern→ error-feedback retry (re-extract items)→ resolved?
still mismatched after max attempts ⇒ flag for human review

Code / Config Example

Self-correction validation payload
{
  "field": "total_amount",
  "calculated_total": 245.00,
  "stated_total": 250.00,
  "conflict_detected": true,
  "detected_pattern": "rounding_mismatch",
  "error_message": "Stated total does not match calculated sum of line items."
}
💡 Tip: Always recompute in code and treat calculated_total as the source of truth. Add a small tolerance (ε) for currency rounding (e.g. ≤ 0.01) so legitimate sub-cent differences don’t trigger a conflict_detected storm.
⚠️ Trap: Retrying a totals mismatch only helps if the error is a mis-extracted line item (present-but-wrong). If the arithmetic genuinely doesn’t reconcile because a line item is missing from the source, that’s absent data (21.2) → escalate, don’t loop.
🎯 Exam Strategy: Know which value is authoritative: calculated_total (your code), not stated_total (the model). Distractors will suggest “trust the stated total, it came from the document.” Also: a mismatch is a semantic conflict (21.4), never a schema error. Example-style question: stated_total=250.00 but the line items sum to 245.00. What should the pipeline set? → conflict_detected: true with a categorising detected_pattern.

21.6 The detected_pattern and conflict_detected Fields

Concept Explanation

These two fields work as a pair and are frequently confused on the exam:

  • conflict_detected — a boolean gate. It answers one yes/no question: “Does a semantic conflict exist in this record?” It’s what your controller branches on.
  • detected_pattern — a categorical label. It answers “Which kind of conflict is it?” (e.g. rounding_mismatch, sum_mismatch, missing_line_item, duplicate_entry, currency_mismatch). It drives routing and analytics.

Rule of thumb: conflict_detected decides whether to act; detected_pattern decides how to act.

How It Works — Gate then Route

  1. Semantic validator sets conflict_detected = true when any rule fails.
  2. It classifies the failure into a detected_pattern.
  3. The controller routes on the pattern: some patterns → retry (recoverable), some → escalate (absent data), some → auto-tolerate (e.g. sub-cent rounding).
  4. Feedback loop (21.3) aggregates dismissals by pattern to tune the system.

Visualization — Pattern → Routing

detected_patternMeaningRecoverable by retry?Route
rounding_mismatchSub-cent / rounding difference✅ Often auto-tolerateAccept within ε or flag low-priority
sum_mismatchLine items don’t sum to stated total✅ Yes (re-extract items)Error-feedback retry
missing_line_itemA line item absent from source❌ NoEscalate / human review
duplicate_entrySame item counted twice✅ YesRetry with de-dup instruction
currency_mismatchMixed currencies in one total❌ NoEscalate — needs FX policy

Code / Config Example

Gate + label in one record
{
  "conflict_detected": true,          // GATE: branch on this
  "detected_pattern": "sum_mismatch",   // LABEL: route on this
  "calculated_total": 245.00,
  "stated_total": 250.00,
  "routing": "error_feedback_retry"
}
💡 Tip: Keep detected_pattern a controlled enum, not free text. A closed vocabulary is what makes routing rules and dismissal analytics (21.3) possible.
🎯 Exam Strategy: The classic distractor swaps the two: it describes conflict_detected as “the type of error” or detected_pattern as “whether an error occurred.” Remember: boolean gate = conflict_detected; categorical label = detected_pattern. Example-style question: Which field would you switch/branch your routing logic on? → detected_pattern (after conflict_detected gates in).

21.7 Hands-On: Implementing Validation and Retry Logic

Concept Explanation

This section assembles 21.1–21.6 into one working controller: schema → semantic → classify → decide (retry vs. escalate) → error-feedback retry → cap attempts. Every field name introduced earlier appears here consistently.

How It Works — Reference Implementation

validation_retry_controller.py (pseudocode)
def validate(record):
    # 1) SCHEMA first — cheap, deterministic
    schema_errors = schema_check(record)          # type/shape/required
    if schema_errors:
        return Result(ok=False, error_class="schema",
                      recoverable=True, errors=schema_errors)

    # 2) SEMANTIC second — recompute the total independently
    calculated_total = round(sum(li.amount for li in record.line_items), 2)
    stated_total     = record.stated_total
    conflict_detected = False
    detected_pattern  = None

    if abs(calculated_total - stated_total) > EPSILON:          # EPSILON = 0.01
        conflict_detected = True
        detected_pattern  = classify_mismatch(record,
                                calculated_total, stated_total)
        return Result(ok=False, error_class="semantic",
                      conflict_detected=conflict_detected,
                      detected_pattern=detected_pattern,
                      calculated_total=calculated_total,
                      stated_total=stated_total,
                      recoverable=is_recoverable(detected_pattern))
    return Result(ok=True)


def run_with_retry(prompt, max_attempts=3):
    attempt, output = 0, generate(prompt)
    while attempt < max_attempts:
        result = validate(output)
        if result.ok:
            return output                              # ✓ success
        if not result.recoverable:                       # 21.2: absent data
            return escalate(result)                     # short-circuit, no loop
        # 21.1: build error-feedback prompt with the SPECIFIC error
        prompt = augment(prompt, output, result.error_message)
        output = generate(prompt)
        attempt += 1
        log_attempt(result.detected_pattern, attempt)   # 21.3 feed
    return escalate(last_result)                        # attempts exhausted
📎 Trace it: schema check (21.4) → recompute calculated_total vs stated_total (21.5) → set conflict_detected + detected_pattern (21.6) → recoverable? retry with specific error (21.1) or escalate (21.2) → log for the feedback loop (21.3). Every subtopic maps to a line above.

🧪 Mini Practice Scenario

Scenario: An invoice agent returns valid JSON. Line items are [100.00, 45.00, 100.00] and stated_total is 250.00. The same 100.00 line appears twice, but the vendor’s original PDF lists it only once. What does the controller do — step by step?
Solution walkthrough
# Schema check → PASS (well-formed, correct types)
calculated_total = 100.00 + 45.00 + 100.00 = 245.00
stated_total     = 250.00
|245.00 - 250.00| = 5.00  > EPSILON(0.01)  # semantic conflict

conflict_detected = true
detected_pattern  = "duplicate_entry"   # 100.00 counted twice
recoverable       = true                # present-but-wrong, not absent

# → error-feedback retry (21.1): re-extract with de-dup instruction
augment(prompt, output,
  "Line item 100.00 appears twice but the source lists it once. "
  "Remove the duplicate; sum must equal stated_total 250.00 or flag mismatch.")

# Retry result: items = [100.00, 45.00, 105.00] → calc = 250.00
# conflict_detected = false → ✓ accept

Key teaching point: a duplicate_entry is recoverable (the data is present, just mis-structured), so the error-feedback retry is the correct route — contrast with missing_line_item, which is absent data and must escalate (21.2).

🎯 Exam Strategy: Hands-on questions test whether you can trace the ordering: schema → semantic → classify → recoverable-check → retry/escalate → cap. A common distractor reorders these (e.g. semantic before schema, or retry before checking recoverability). The recoverable check must gate the retry — that’s the 21.2 discipline enforced in code. Example-style question: In the controller, what prevents an infinite loop on absent data? → The recoverable=false short-circuit to escalate() plus the max_attempts cap.
