22.1  The Message Batches API — Cost Savings Mechanics & Processing Window

Core Concept

In plain language Instead of asking Claude one question at a time and waiting for each answer (synchronous), you hand Anthropic a big bag of requests at once and say "process these whenever you have spare capacity, I'll come back for the results." Because you're giving Anthropic scheduling flexibility, they charge you half price — but they only promise to finish within 24 hours.

Technically: The Message Batches API is Anthropic's asynchronous bulk-processing endpoint. You submit a list of independent Messages requests; the system creates a message_batch object, processes each request independently, and exposes results at a results_url once processing has ended. It trades immediate latency for cost efficiency and throughput.

Key Facts

PropertyValueNote
Cost discount50% offApplies to both input and output tokens (and special tokens), across all supported models.
Processing window (SLA ceiling)Up to 24 hoursMost batches finish in < 1 hour; the 24h figure is the guarantee ceiling, not the expectation.
Expiration24 hoursRequests not completed within 24h are marked expired (unbilled).
Result retention29 days from created_atMeasured from creation, not from processing end.
Batch size cap100,000 requests OR 256 MBWhichever limit is reached first. Oversized → 413 request_too_large.
ScopeWorkspaceBatches & results are isolated to the Workspace that created them.
Prompt-caching stacking✅ SupportedBatch discount and prompt-cache savings stack. Use the 1-hour cache duration for shared context.

💡 Tip: The "50% discount" is unconditional on batch usage — but the real savings multiplier comes from stacking prompt caching on shared context (e.g. a long system prompt reused across 50,000 rows). When you see a cost-optimization question mentioning a large shared prefix, the best answer usually combines both levers.
🎯 Exam Strategy: Watch for the classic trap that confuses the typical completion time (< 1 hour) with the guaranteed window (24 hours). For any SLA-safety question you must budget against the 24-hour ceiling, never the optimistic average. Also memorize that the 50% discount hits both input and output — a distractor answer will claim "input only."

22.2  When Batch Processing Is (and Isn't) Appropriate

Core Concept

In plain language Batch is for work you can wait on and want cheap. If a human or downstream system is blocking on the answer right now, batch is the wrong tool. If it's a big pile of independent work that can finish "sometime today," batch is ideal.

Technically: The decision hinges on three axes — latency tolerance, volume, and interaction shape. Batch wins when latency tolerance is high (minutes–hours), volume is large, and each unit of work is self-contained (no interactive round-trips).

Decision Framework — Real-Time vs. Batch

Interactive client-side tool loop✅ Natural fit⚠️ Not within one request (see §22.3)
ThroughputBounded by rate limits per callHigh — up to 100k requests/batch

💡 Tip: "Independent" is the keyword. If each item can be answered without the answer to another item, it batches cleanly. Cross-item dependencies (item B's prompt needs item A's output) mean you either sequence multiple batches or fall back to real-time orchestration.
🎯 Exam Strategy: Scenario questions here give you a workload and ask "batch or real-time?" Scan for latency verbs ("live", "immediately", "chat", "user waits") → real-time; and bulk nouns ("nightly", "10,000 documents", "backfill", "evaluation set") → batch. A single "the user is waiting" phrase overrides volume — it forces real-time regardless of size.

22.3  Batch API Limitations — Tool Calling & Why It Matters Architecturally

⚠️ Precision flag (read this carefully — commonly mis-stated): The blunt claim "the Batch API doesn't support tool calling or multi-turn" is outdated and imprecise. Current docs confirm batches accept multi-turn conversations, vision, extended thinking, and server-side tools (web search, web fetch, code execution, MCP connectors). The true limitation is structural, described below. Learn the precise version — exams reward it.

Core Concept

In plain language A batch request is "fire and forget." You send it once and pick up the answer later. That works great when Claude can finish the whole job on its own. It breaks down when the job needs a back-and-forth where your code has to run a tool mid-conversation and hand the result back — because there's no live connection to hand anything back to.

The Two Kinds of Tool Use — Know the Difference

Tool typeWho executes it?Works in a single batch request?
Server-side tools
(web search, web fetch, code execution, MCP connectors)		Anthropic, server-side, inside the agentic loop✅ Yes — the batch worker runs the same server-side loop.
Client-side (custom) tools
(your function that returns a tool_result)		Your application code, between turns⚠️ Not interactively — needs a live round-trip the async batch can't provide.

Why This Matters Architecturally

Because a batch is submitted once and processed asynchronously with no open connection:

  • A client-side tool loop (model asks for a tool → your code runs it → you return tool_result → model continues) requires multiple synchronous round-trips. You cannot inject a tool_result into an in-flight batch request.
  • If a server-tool turn doesn't finish, the result returns stop_reason: "pause_turn". You must resubmit the paused assistant content in a fresh request (batch or synchronous) to continue — i.e. multi-turn agentic flows become multiple sequential submissions, not one.
  • Unsupported params return validation errors: stream: true (results are a file, not a stream), speed / Fast mode (tunes sync latency), and max_tokens: 0 (cache pre-warming can't survive async delay).

💡 Tip: If a design needs an interactive client-side tool loop at scale, the correct pattern is a hybrid: run the interactive turns on the real-time Messages API, and batch only the independent, one-shot portions (e.g. batch the final summarization step). Alternatively, decompose an agentic flow into a pipeline of sequential batches, correlating stages by custom_id.
🎯 Exam Strategy: §22.3 questions typically present a scenario needing sequential client-side tool calls inside one batch request and ask for the fix. The correct answer: this interactive loop is not supported in a single batch → split into a real-time flow (or a multi-batch pipeline). Beware the trap distractor that says "batches don't support tools at all" — that's false; server-side tools do work. The precise limitation is the interactive client-side round-trip, plus pause_turn requiring re-submission.

22.4  The custom_id — Purpose, Uniqueness & Correlation Pattern

Core Concept

In plain language Results come back out of order. The custom_id is the name tag you staple to each request so you can match every answer back to the exact thing you asked about. No tag → no reliable way to know which answer belongs to which input.

Technically: Each request in a batch carries a client-supplied custom_id. Every result line in the returned .jsonl echoes that same custom_id. Since results can be returned in any order (and often are), custom_id is the only reliable correlation key between request and response.

Key Facts & Constraints

RuleDetail
UniquenessMust be unique within the batch. Duplicates cause errors / ambiguous correlation.
Length1 to 64 characters.
Allowed charactersAlphanumeric, hyphens, underscores only — regex ^[a-zA-Z0-9_-]{1,64}$.
Ordering guaranteeNone. Never rely on result order — always match by custom_id.
PurposeCorrelation of result → request; also the key for targeted failure resubmission (see §22.6).

Recommended Scheme — Encode Meaning

Design custom_id to be human-readable AND programmatically parseable, encoding the metadata you'll need to triage a failure without a lookup table:

{batch}-{entity}-{recordId}-{stage}
 e.g.  "b2026w38-invoice-000042-extract"
        │       │        │       └─ pipeline stage
        │       │        └────────── source record id
        │       └─────────────────── entity/type
        └─────────────────────────── batch identifier
💡 Tip: Always design your custom_id scheme to be human-readable AND programmatically parseable (e.g. "batch1-userid-1234") so failures can be triaged quickly without a lookup table. Keep it within 64 chars and stick to [a-zA-Z0-9_-] — a stray colon, slash, or space is a validation error.
🎯 Exam Strategy: Expect a question that quietly assumes results arrive in submission order — the correct move is to reject that assumption and correlate by custom_id. Also memorize the constraints: 1–64 chars, [a-zA-Z0-9_-] only, unique per batch. A distractor will offer a custom_id containing a period or slash (invalid) or claim results preserve order (false).

22.5  Calculating Batch Submission Frequency Based on SLA Constraints

Core Concept

In plain language If you promise results within X hours of an item arriving, you must submit often enough that even the slowest possible batch still lands inside X. The math is: your SLA has to cover both how long an item waits before you submit it plus how long the batch takes to process.

The Formula

TSLA  ≥  Isubmit  +  Wprocess

⟹   Imax = TSLA − Wprocess     f = 1 / Isubmit
  • TSLA — deadline: max time from item arrival to delivered result.
  • Wprocess — batch processing budget. For SLA safety, use the 24-hour ceiling (not the <1h typical) unless the SLA explicitly tolerates the tail risk.
  • Isubmit — interval between batch submissions (the max time an item waits to be picked up).
  • Imax — the largest allowable interval; submit at least this often.
  • f — submission frequency; batches per day = 24 / Isubmit.

Worked Example

Given: SLA = deliver results within 30 hours of an item arriving. Volume ≈ 20,000 items/day. Use the worst-case processing budget W = 24h.

Step 1 — Max interval:   Imax = TSLA − W = 30 − 24 = 6 hours.

Step 2 — Frequency:   submit every ≤ 6h → 4 batches/day (00:00, 06:00, 12:00, 18:00).

Step 3 — Size check:   20,000 / 4 ≈ 5,000 requests/batch — well under the 100k / 256 MB cap. ✅

Worst-case trace: an item arriving at 00:01 waits until the 06:00 submission (≈6h), then processes up to 24h → delivered by ≈30:00. Meets the 30h SLA.

0h ───────────── 6h ─────────────────────────── 30h (SLA deadline) ✅

Fig. 22.5 — SLA must absorb submission wait + worst-case processing window.
⚠️ Critical edge case: If TSLA ≤ 24h, then Imax ≤ 0 — the Batch API cannot guarantee the SLA against its own worst case, because a single batch may take the full 24h. Options: (1) use the real-time Messages API, (2) renegotiate the SLA above 24h, or (3) explicitly accept tail risk if the SLA permits (most batches finish <1h, but this is not guaranteed).
💡 Tip: If per-interval volume exceeds the 100,000-request / 256 MB cap, shard into multiple parallel batches for that window — the cap is per batch, not per account. Track shards with a batch-id prefix in the custom_id.
🎯 Exam Strategy: These are the calculation questions. The near-universal trap is plugging in the <1h typical time instead of the 24h worst case for W — always use 24h for SLA-safety math unless told otherwise. The second trap: an SLA tighter than 24h that the question expects you to flag as infeasible for batch alone. Show the subtraction I = T_SLA − W explicitly.

22.6  Handling Batch Failures — Resubmission Keyed on custom_id

Core Concept

In plain language When results come back, some items may have failed. You look at why each one failed, and only re-send the ones worth re-sending — reusing their name tags (custom_id) so the retry stays traceable. A failure of one item never breaks the others.

Technically: Each result carries a result.type. The request_counts object summarizes how many landed in each state. Your retry logic branches on the type — and you're not billed for errored, canceled, or expired requests.

The Four Result Types & Correct Response

Result typeMeaningBilled?Correct action
succeededMessage returned normally.YesPersist result, keyed by custom_id.
erroredRequest failed. Sub-cases below.NoBranch on error type (see below).
canceledUser canceled batch before this ran.NoResubmit in a fresh batch if still needed.
expiredHit 24h before being sent to the model.NoResubmit (consider smaller batches / better timing per §22.5).

Splitting the errored case

  • invalid_request_error — the request body is broken. Blind retry will fail again. Fix the payload first, then resubmit.
  • Server / internal errors — transient. Safe to retry directly (ideally with backoff).

Fig. 22.6 — Triage by result type; resubmit failures in a new batch, preserving custom_id for idempotent merging.
💡 Tip: Reuse the same custom_id on retries and treat your result store as a keyed upsert — the successful result overwrites the failed placeholder for that id. This makes the whole pipeline idempotent: re-running a retry batch can never create duplicates or lose the mapping. Track a retry counter as a suffix only if you need audit history (e.g. ...-extract-r2).
🎯 Exam Strategy: The signature §22.6 trap is treating all failures identically. The exam wants you to distinguish invalid_request_error (fix, don't blind-retry) from server errors (retry directly), and to know that errored/expired/canceled are not billed. Also remember: one failed request does not affect the others in the batch. The universal correct mechanism for resubmission is keying on custom_id.

22.7  Prompt Refinement on Sample Sets Before Large-Volume Processing

Core Concept

In plain language Don't spend money processing 100,000 items with a prompt you haven't proven works. Test on a small, representative sample first, fix the prompt until it's reliable, then scale up. A 2% error rate is trivial on 50 samples and expensive on 500,000 rows.

Technically: Because batches process asynchronously (feedback can be up to 24h away), the tight iterate-fix-iterate loop belongs on the synchronous Messages API against a curated sample — not on full-volume batches. Validating request shape synchronously also prevents mass validation errors, since batch param validation is asynchronous and only surfaces after the whole batch ends.

Fig. 22.7 — Refine synchronously on a sample; only commit to full-volume batch once quality & shape are proven.

Why sample first — the economics

  • Feedback latency: sync = seconds; batch = up to 24h. Iterating on batches wastes days.
  • Cost of a bad prompt at scale: even at 50% off, a flawed prompt over 500k rows is a large, avoidable spend — and you'd pay again to re-run.
  • Validation timing: batch param validation is asynchronous and reported only after the batch ends, so a shape bug can silently waste a whole window. A single synchronous dry-run catches it in seconds.
  • Representativeness: the sample must include known edge cases (empty fields, long inputs, unusual formats), not just easy rows.
💡 Tip: Lock a quantitative acceptance gate before scaling — e.g. "≥98% valid JSON schema and ≥95% field-level accuracy on the 150-row sample." Treat the sample like a mini eval set and version your prompt against it, so any future prompt change can be re-scored on the same rows.
🎯 Exam Strategy: Questions here reward the sequence sample → refine synchronously → dry-run shape → scale via batch. The trap answer skips refinement and submits the full batch immediately "to save time." Flag that as wrong: batch's async feedback makes iteration slow, and asynchronous validation means shape errors surface only after the window. The keyword "dry run a single request with the Messages API" is a documented best practice — recognize it.

22.8  Hands-On: Designing a Batch Extraction Workflow (End-to-End)

Scenario

Extract structured fields (vendor, date, total, line-items) from 40,000 scanned invoices/day as JSON. SLA: results within 36 hours of upload. Cost-sensitive. No human is blocked in real time.

Step-by-Step Design

① Validate fit (§22.2)

Bulk, self-contained, latency-tolerant (36h > 24h), cost-sensitive → Batch is the correct primitive.

② Refine on a sample (§22.7)

Take 150 representative invoices (include multi-page, low-quality scans, foreign currency). Iterate the extraction prompt on the synchronous Messages API until ≥98% valid JSON schema. Dry-run one request shape to confirm it validates.

③ Design the custom_id scheme (§22.4)

"inv-{yyyymmdd}-{shard}-{invoiceId}-extract"
 e.g. "inv-20260923-s01-000042-extract"   (≤64 chars, [a-zA-Z0-9_-] only)

④ Compute submission cadence (§22.5)

Imax = TSLA − W = 36 − 24 = 12 h  ⟹  submit every 12h → 2 batches/day

Per-batch volume ≈ 40,000 / 2 = 20,000 requests — under the 100k / 256 MB cap (verify total size; shard if > 256 MB, hence the {shard} field). Enable prompt caching on the shared extraction system prompt to stack savings.

⑤ Submit, poll, retrieve

# pseudocode
batch = client.messages.batches.create(requests=[...])   # status: in_progress
while client.messages.batches.retrieve(batch.id).processing_status != "ended":
    sleep(60)                                             # poll
for r in client.messages.batches.results(batch.id):      # stream .jsonl
    store[r.custom_id] = r.result                         # correlate by custom_id

⑥ Triage & resubmit failures (§22.6)

  • succeeded → upsert JSON into store keyed by custom_id.
  • errored / invalid_request_error → fix payload (e.g. oversized image) → retry.
  • errored / server → retry as-is with backoff.
  • expired → resubmit next window; if chronic, shrink batch size or add a window.
  • Resubmit in a new batch reusing the same custom_ids → idempotent merge.

⑦ Retrieve within retention (§22.1)

Download & persist results well within the 29-day window (measured from created_at). Persist to your own object storage; don't treat Anthropic's results_url as long-term storage.

💡 Tip: Make the store a keyed upsert from day one and stamp each custom_id with the shard + date. You get free idempotency, trivial failure re-runs, and a human-debuggable audit trail — all three exam themes (§22.4, §22.5, §22.6) satisfied by one well-designed id.
🎯 Exam Strategy: Hands-on questions ask you to sequence the steps correctly and to justify the cadence with the SLA formula. High-value points: (a) validate batch-fit against latency; (b) refine on sample synchronously; (c) cadence = T_SLA − 24h; (d) correlate/retry by custom_id; (e) retrieve within 29 days. Expect a "what's the first thing you'd do?" variant — the answer is validate fit / refine on a sample, never "submit the full batch."

✎  Practice Questions (Self-Check)

Focused on the trickiest concepts — §22.3, §22.5, §22.6. Click to reveal answers.

Q1 (§22.3). A design requires Claude to call your internal lookup_customer() function, use its result, then produce a summary — for 60,000 accounts. An engineer proposes doing it all in one Message Batch. What's wrong, and what do you recommend?

Answer: lookup_customer() is a client-side tool: the model requests it, your code must execute it and return a tool_result, then the model continues. That interactive round-trip needs a live connection, which an asynchronous, one-shot batch request does not maintain — so the loop cannot complete inside a single batch request.

Recommendation: Either run the interactive tool turns on the synchronous Messages API, or decompose into a multi-batch pipeline: Batch A resolves lookups (or pre-fetch the data yourself and inline it), then Batch B does the one-shot summarization on the enriched inputs, correlating stages by custom_id.

Trap avoided: Don't answer "batches don't support tools" — server-side tools (web search, code execution, etc.) do work in batches. The limit is specifically the interactive client-side loop.

Q2 (§22.5). Your SLA is "results within 20 hours of arrival." Can you meet it with the Batch API alone? Show the math.

Answer: I_max = T_SLA − W = 20 − 24 = −4 hours. A negative interval is impossible.

Because a single batch can take the full 24h worst case, the Batch API cannot guarantee a 20h SLA. Options: (1) use the real-time Messages API; (2) renegotiate the SLA to > 24h; or (3) explicitly accept tail risk if the SLA permits — most batches finish in <1h, but that is not contractually guaranteed.

Trap avoided: Plugging in the <1h typical time (giving a false "yes, submit ~every 19h"). SLA-safety math uses the 24h ceiling.

Q3 (§22.6). A batch of 10,000 returns: 9,600 succeeded, 300 errored (200 invalid_request_error, 100 server errors), 100 expired. How do you handle each, and what are you billed for?

Billing: You pay only for the 9,600 succeeded. errored, expired (and canceled) are not billed.

Handling:

  • 200 invalid_request_error — payload is broken; fix the request body (e.g. malformed content, oversized image) before resubmitting. Blind retry would just fail again.
  • 100 server errors — transient; retry directly (with backoff).
  • 100 expired — resubmit in the next window; if expiration is recurring, reduce batch size or improve submission timing (§22.5).

Build the retry set from the failed custom_ids, resubmit as a new batch reusing the same ids, and upsert into your keyed store so the merge is idempotent. Remember: one failed request never affects the others.

Q4 (§22.4 / §22.6). Why is correlating results by array index instead of custom_id a bug, even if your submission code is correct?

Answer: Batch results are returned in no guaranteed order — the .jsonl can (and routinely does) come back shuffled relative to submission. Positional/index matching therefore assigns answers to the wrong inputs. The custom_id echoed on each result line is the only reliable join key. This also underpins failure handling: retries reuse the same custom_id, so a keyed upsert stays correct across multiple batches.

Q5 (§22.5 sizing). You must process 350,000 items in a single 6-hour submission window. What constraint do you hit, and how do you handle it?

Answer: A single batch is capped at 100,000 requests OR 256 MB, whichever first. 350,000 > 100,000, so you shard into ≥ 4 parallel batches for that window (e.g. 4 × 87,500), also checking each shard stays under 256 MB. The cap is per batch, not per account, so parallel shards are fine. Encode the shard in the custom_id (e.g. ...-s01-...) so results across shards remain individually traceable and mergeable.
