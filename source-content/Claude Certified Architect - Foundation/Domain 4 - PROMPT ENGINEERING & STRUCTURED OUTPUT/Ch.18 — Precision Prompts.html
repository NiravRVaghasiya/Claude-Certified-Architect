18.1 Understanding False Positives in AI Code Review

A false positive is an issue the reviewer flags that is not actually a problem in context. In AI-assisted code review, false positives are the single biggest driver of developer distrust: a reviewer that cries wolf is quickly ignored, even when it is later right.

Deep Dive

Every classifier — human or model — trades off two error types. A false positive flags correct code as defective; a false negative misses a real defect. In code review these costs are asymmetric but not in the way beginners assume. A single missed critical bug is expensive, but a stream of spurious warnings is corrosive: it trains developers to dismiss the tool wholesale, at which point the false-negative rate effectively becomes 100% because nobody reads the output. This is why precision-oriented prompting matters — the goal is a reviewer whose signals are trusted enough to act on.

False positives arise because the model is reasoning under-constrained. When a prompt says "find problems," the model must silently invent a definition of "problem," a severity bar, and an assumption about surrounding context it cannot see. Each invented assumption is a chance to flag something that is fine — a deliberate style choice, a guard that exists two files away, a pattern that is idiomatic in the codebase. Reducing false positives is therefore mostly about removing the model's need to guess: supplying the definition, the bar, and the context explicitly.

🎯 Exam Strategy: Expect a definitional question distinguishing false positives from false negatives, and a scenario that asks why false positives are especially damaging in review workflows. The keyword to watch is "developer trust" — answers that connect false positives to erosion of trust (and therefore tool abandonment) score highest. Do not conflate "reduce false positives" with "flag less"; the correct framing is "flag only what is genuinely defective."

18.2 How Vague Prompts Cause False Positives

Vague instructions force the model to fill gaps with assumptions. Each unstated definition — of severity, scope, and context — becomes a place where the model over-flags. Ambiguity is the root cause; precision is the cure.

Deep Dive

Consider the instruction "Be thorough and catch all potential issues." Three words silently expand the model's flagging surface. "Thorough" rewards volume, so the model reports marginal observations to appear diligent. "All" removes any severity floor, so cosmetic nits sit beside real bugs. "Potential" invites speculation about code paths the model cannot verify from the diff alone. The result is a long list dominated by non-issues — a textbook false-positive cascade.

The mechanism is worth internalizing because it generalizes: a model resolves ambiguity in the direction the prompt seems to reward. A prompt that praises exhaustiveness biases toward recall (and false positives); a prompt that praises restraint biases toward precision. Vagueness also strips context — without knowing the file's role, the language's idioms, or which lines are new versus pre-existing, the model evaluates code against a generic ideal rather than the actual situation, flagging intentional trade-offs as mistakes. Removing the vagueness (see 18.3 and 18.4) is the direct antidote.

18.3 Scoping Prompts: Defining What to Flag and What to Ignore

Precision comes as much from stating what to ignore as what to catch. An explicit allow-list of concerns plus an explicit exclusion list bounds the model's attention, so it stops evaluating code against invisible, generic standards.

Deep Dive

Scoping works on a simple principle: a model will inspect whatever the prompt implies is in-bounds, so an unbounded prompt makes everything in-bounds. Two complementary levers narrow the frame. First, a positive scope — an explicit list of the concern categories that matter (e.g., correctness, security, resource safety). Second, a negative scope — an explicit exclusion list (e.g., "do not comment on formatting, import ordering, or subjective naming; assume the linter handles those"). The exclusion list is the one most engineers forget, and it is often the highest-leverage sentence in the entire prompt because it eliminates whole classes of noise at once.

Scope should also be pinned in space and time: tell the model to review only the changed lines in a diff, and to treat unchanged code and out-of-view files as correct rather than speculating about them. This prevents the classic false positive where the model "fixes" pre-existing code the author never touched, or invents a bug in a helper it cannot see. Well-scoped prompts convert an open-ended "judge this code" task into a closed checklist the model can actually satisfy.

18.4 Writing Specific Review Criteria by Category

Precise, per-category criteria (bugs, security, performance, style) reduce cross-category false positives by telling the model exactly what qualifies as an issue in each domain. A category with a concrete, verifiable definition is a category the model stops guessing about.

Deep Dive

Once scope (18.3) has named the in-bounds categories, each category still needs its own definition of a defect. "Check for security issues" is a category label, not a criterion — the model must still invent the bar. Replacing the label with enumerated, checkable conditions ("flag hardcoded secrets, unparameterized SQL, and missing auth on new endpoints") turns a fuzzy judgment into pattern-matching against a spec. This is why category-specific criteria are so effective at precision: the model can only flag what matches a listed condition, and everything else falls through as a true negative.

Specific criteria also prevent cross-category leakage — the tendency to report, say, a style preference under the banner of a "bug," or a theoretical performance concern as a "security" issue. When each category carries its own bar, the model classifies correctly and the severity stays honest. The practical craft is to phrase each criterion as something a reader could verify by pointing at a line: prefer "a resource opened without a corresponding close on the error path" over "possible resource issues." Verifiable phrasing is the difference between a criterion and a vibe.

Watch for the keyword "per-category" and for distractors that merge categories — the exam rewards keeping criteria and severities separated by domain.

18.5 Few-Shot Calibration with Positive and Negative Examples

Examples set the model's threshold more precisely than adjectives can. A few paired examples — one showing a true issue worth flagging, one showing similar-looking code that should not be flagged — calibrate the severity bar and teach the model where the line sits.

Deep Dive

Natural-language criteria still leave a gray zone: how bad must a bug be before it clears the bar? The most efficient way to communicate a threshold is by demonstration. A positive example shows code that should be flagged and the ideal terse comment. A negative example — the one engineers omit — shows code that looks suspicious but is actually correct, paired with the instruction "do not flag this." Negative examples are disproportionately powerful against false positives because they directly target the near-misses the model would otherwise report.

Good calibration examples are contrastive: the positive and negative should look similar so the model learns the discriminating feature, not a surface pattern. For instance, a SQL call built with string concatenation (flag) versus one using bound parameters (do not flag) teaches the model that parameterization, not the presence of SQL, is the signal. Keep the set small — three to five pairs usually suffice — and make sure they cover the boundary cases your team argues about, since those are exactly where the model's uncalibrated guesses become false positives.

A frequent question asks why adding negative examples reduces false positives — the answer is that they demonstrate the boundary of what counts, suppressing near-miss over-flagging. Distractor answers suggest adding only more positive examples or more rules; the stronger choice pairs positives with contrastive negatives.

18.6 Iterative Refinement and Measuring the False-Positive Rate

Precision prompting is empirical, not one-shot. You establish a labeled evaluation set, measure precision and recall, and feed each confirmed false positive back into the prompt as a sharpened criterion or a negative example. The loop is what turns a decent prompt into a trusted reviewer.

Deep Dive

You cannot reduce what you do not measure. The core metric is precision = true positives ÷ (true positives + false positives) — the fraction of the reviewer's flags that were genuinely worth raising. Track it against a held-out set of reviews that a human has labeled, so a prompt change's effect is visible rather than anecdotal. Pair it with recall (real issues caught ÷ real issues present) to guard against the trivial way to reach perfect precision: flag nothing. The tension between the two is captured by the F-score, but for review tooling teams usually weight precision higher because trust is the scarce resource (see 18.1).

Refinement is then a disciplined loop: run the prompt on the eval set, triage each flag as TP or FP, and for every false positive ask "what unstated assumption produced this?" The answer becomes a concrete edit — a tightened criterion (18.4), an added exclusion (18.3), or a new negative example (18.5). Change one thing at a time and re-measure, so you can attribute improvement (or regression) to a specific edit. This is ordinary regression testing applied to prompts: freeze the eval set, and treat a rise in false positives after an edit as a failing test.

Common Pitfalls

⚠️ Mistakes candidates make on this chapter's exam questions
  • Equating "reduce false positives" with "flag less." The goal is to flag only genuine defects, not to suppress volume indiscriminately — suppressing everything just trades false positives for false negatives.
  • Confusing false positives with false negatives. A false positive flags correct code; a false negative misses a real bug. Precision measures the former.
  • Forgetting the exclusion list. Candidates add more checks but never state what to ignore — yet negative scope (18.3) is often the highest-leverage fix.
  • Adding adjectives instead of criteria. "Check more carefully" is not precision; enumerated, verifiable conditions (18.4) are.
  • Only adding positive examples. Without contrastive negative examples (18.5), the model never learns the boundary of what not to flag.
  • Optimizing precision in isolation. Ignoring recall lets "flag nothing" look perfect; always report both, or F1.
  • Changing many prompt variables at once. You then cannot attribute the change in the false-positive rate to any single edit — refine one thing per iteration against a frozen eval set.
  • Assuming unseen code is broken. Instruct the model to treat unverifiable calls and unchanged lines as correct, or it will speculate and over-flag.
