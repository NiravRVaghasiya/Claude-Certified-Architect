20.1 Why Tool Use Is the Structured-Output Mechanism

Claude does not expose a dedicated "JSON mode" or "response format" object the way some other APIs do. Instead, the canonical way to force structured output is to define a tool and let Claude populate its inputs. A tool is a JSON object with three fields: name, description, and input_schema. The input_schema is a JSON Schema object describing the exact shape you want back. When Claude decides (or is forced) to call the tool, it emits a tool_use content block whose input field is a JSON object shaped by that schema.

The mental reframe for the exam: you are not really asking Claude to "run a function." You are using the tool's input_schema as a contract for the model's output. Even if you never execute any real code, defining a tool named record_extraction and forcing its use is the idiomatic pattern for guaranteed structured data.

Critically, Claude's schema adherence is best-effort, model-driven guidance — not hard-constrained decoding. The model is strongly steered toward valid output by the schema, but the API does not grammar-constrain every token. This single fact drives most of the chapter: because adherence is not guaranteed at the transport layer, you must validate client-side.

Anatomy of a tool definition and response

{
  "name": "record_contact",
  "description": "Save a structured contact record extracted from text.",
  "input_schema": {
    "type": "object",
    "properties": {
      "full_name": { "type": "string" },
      "email": { "type": "string" }
    },
    "required": ["full_name"]
  }
}

When invoked, Claude returns a message with stop_reason: "tool_use" and a content block like this:

{
  "type": "tool_use",
  "id": "toolu_01A9...",
  "name": "record_contact",
  "input": { "full_name": "Dana Lee", "email": "dana@acme.io" }
}

Terminology note

Anthropic documentation calls this tool use — the content block type is literally "tool_use". "Function calling" is a competitor's term; on the exam, the Claude-native vocabulary is tool_use, tool_result, and input_schema.

Comparison: free-text JSON vs. tool-use extraction

ApproachHow it worksReliabilityWhen to use

Tip: Put your extraction instructions inside the tool's description and each property's description, not only in the top-level prompt. Claude reads schema descriptions as guidance, so a well-described field ("ISO 8601 date; use null if absent") dramatically improves adherence.
Common Pitfall: Assuming there is a first-class "JSON mode" / response_format parameter on the Messages API. There is not. Selecting such an option on an exam question is a distractor — the mechanism is a defined tool plus tool_choice.
Exam Strategy: Questions here test whether you know the field names. Watch for distractors that swap input_schema for parameters (that is the other vendor's key). Keywords: "guaranteed structured output," "no first-class JSON mode," "schema as output contract."
Q: An architect needs Claude to reliably return an object with fixed keys and no surrounding prose. Which is the recommended mechanism?
A: Define a tool with an input_schema and read the resulting tool_use.input block. Why: it is the only approach that yields a schema-shaped object rather than a parsed string, and it avoids markdown/prose leakage.

20.2 tool_choice Options & Behavior

The tool_choice parameter controls whether and which tool Claude uses. For structured-output extraction you almost always move away from the default. There are four types, plus a modifier flag.

tool_choiceBehaviorCan emit leading text / chain-of-thought?Use case
{"type":"auto"}Model decides whether to call a tool at all (default when tools are present)YesGeneral assistants; optional tool use
{"type":"any"}Model must call one of the provided tools (its choice which)NoGuaranteed tool invocation, several valid tools
{"type":"tool","name":"x"}Model must call the one named toolNoSingle-purpose forced extraction
{"type":"none"}Model may not call any tool; text onlyYes (text only)Temporarily disable tools without removing definitions

The disable_parallel_tool_use boolean can accompany auto or any. Set it to true to force at most a single tool call per turn — useful when your pipeline expects exactly one structured object.

The "no leading text" nuance

When tool_choice is any or tool, Claude is compelled to open with the tool call, so it cannot produce a natural-language chain-of-thought before the call. With auto, it may reason in text first, then call. If your design relies on visible reasoning ahead of extraction, you must either use auto or add an explicit thinking field inside the schema.

# Forcing one specific extraction tool, single call only
tool_choice = { "type": "tool", "name": "record_contact" }
# On the request, alongside tools=[...]:
# "disable_parallel_tool_use": true  ->  guarantees exactly one tool_use block
Tip: For a deterministic extractor that returns exactly one object, combine {"type":"tool","name":"..."} with disable_parallel_tool_use: true. If you want a "thoughts first" pattern under a forced tool, add a "reasoning" string property to the schema so the model can still think — inside the JSON, not before it.
Common Pitfall: Choosing any when the scenario clearly needs one specific tool. any guarantees a tool runs but lets the model pick which; if only extract_invoice is acceptable, you need tool, not any. A second trap: expecting chain-of-thought text under any/tool — it is suppressed.
Exam Strategy: These questions hinge on "one specific" vs. "any of several." If the scenario names a single function that must run → forced tool. If it says "guarantee some tool is used but any of them is fine" → any. Watch the distractor that offers any for a single-tool requirement.
Q: A pipeline defines three tools but this request must invoke classify_ticket and nothing else, with no preamble text. Best config?
A: tool_choice = {"type":"tool","name":"classify_ticket"}. Why: only forced-tool guarantees that specific tool; it also suppresses leading text, satisfying the "no preamble" requirement.

20.3 Syntax vs. Semantic Validation Errors Chain-of-Thought

This is the most-tested conceptual distinction in the chapter. A structured output can fail in two independent layers:

  • Syntactic / schema errors — the data violates the JSON Schema itself: wrong type, missing a required field, a value outside an enum, or a string that fails a declared pattern. These are catchable by a JSON Schema validator.
  • Semantic errors — the data is fully schema-valid but wrong in meaning: a real-looking but impossible date, a total that does not equal the sum of line items, a country code that exists but is not the one in the source text. A schema validator passes these; only business-logic validation catches them.

The crux exam trap is the JSON Schema format keyword (e.g. "format": "date"). In standard JSON Schema, format is an annotation, not an enforced assertion by default. So a value can satisfy type: string + format: date and still be a nonexistent calendar date.

Chain-of-Thought Walkthrough: Why a malformed date fails validation but a logically-wrong date passes.
  1. Given schema: { "type": "string", "pattern": "^\\d{4}-\\d{2}-\\d{2}$" } for a ship_date.
  2. Candidate A — "March 5th": Run schema validation. It is a string (type OK) but does not match the pattern regex. → Fails at the syntactic layer. A validator rejects it immediately.
  3. Candidate B — "2026-02-31": It is a string, and 2026-02-31 does match ^\d{4}-\d{2}-\d{2}$. → Passes schema validation. The regex only checks digit grouping, not whether February has 31 days.
  4. Why the divergence: the pattern/format layer verifies shape, not real-world validity. Feb 31 is shape-correct but calendar-impossible — a semantic error.
  5. Conclusion: Candidate A is a syntax error (schema catches it); Candidate B is a semantic error (only a date parser — e.g. datetime.strptime — catches it). Therefore a robust pipeline needs both a schema validator and a semantic/business-rule check.

Error-layer comparison

Example valueSchema (type+pattern)Semantic checkError class
"March 5th"Fail (pattern)n/aSyntactic
"2026-02-31"PassFail (no such day)Semantic
total: "45" where type is numberFail (type is string)n/aSyntactic
total: 45 but line items sum to 50PassFail (arithmetic)Semantic
Tip: Layer your validation: (1) parse JSON, (2) validate against the schema with a real validator (e.g. Python jsonschema), (3) run domain checks (date parsing, sum reconciliation, cross-field rules). Never treat a passing schema check as proof of correctness.
Common Pitfall: Believing "format": "date" or "format": "email" is enforced. By default it is advisory metadata; most validators do not assert it unless format-assertion is explicitly enabled. Architects who rely on it ship semantic bugs.
Exam Strategy: The classic distractor pairs a schema-valid-but-nonsensical value with the claim "the schema guarantees this is correct." Keywords: "syntactically valid," "passes schema validation," "logically impossible," "format is advisory." If a value matches the shape but is impossible in reality → semantic error, and the schema will not catch it.
Q: Claude returns {"birth_date":"1990-13-02"} against a schema with type:string, format:date. Schema validation passes. Why, and what layer catches the bug?
A: It passes because format is advisory and the string is the right shape; month 13 is a semantic error caught only by an actual date parser / business rule, not the schema.

20.4 Designing JSON Schemas for Extraction

A good extraction schema is opinionated: it uses enum to constrain categoricals, marks the minimum viable set as required, allows null for genuinely-absent data, and writes a purposeful description on every field. Claude reads those descriptions as instructions, so schema design is prompt engineering.

Core keywords the exam expects you to know

KeywordPurposeEnforced by validator?
typeobject / string / number / integer / boolean / array / nullYes
propertiesDefines object fieldsYes (shape)
requiredFields that must be presentYes
enumRestricts to a fixed value setYes
patternRegex constraint on stringsYes
formatSemantic hint (date, email, uri)No (advisory by default)
descriptionGuidance to the model (and humans)No (guidance only)
enum + null / union typesAllow "absent" without breaking typeYes

Worked example — an invoice-line extraction schema

{
  "name": "record_invoice",
  "description": "Extract structured invoice fields from the supplied document text.",
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number": {
        "type": "string",
        "description": "Vendor invoice ID exactly as printed."
      },
      "issue_date": {
        "type": "string",
        "pattern": "^\\d{4}-\\d{2}-\\d{2}$",
        "description": "ISO 8601 date (YYYY-MM-DD). Validate the calendar day downstream."
      },
      "currency": {
        "type": "string",
        "enum": ["USD", "EUR", "GBP", "PLN"],
        "description": "ISO 4217 code. Use the closest match printed on the invoice."
      },
      "line_items": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "sku": { "type": "string" },
            "quantity": { "type": "integer" },
            "unit_price": { "type": "number" }
          },
          "required": ["sku", "quantity", "unit_price"]
        }
      },
      "total": {
        "type": "number",
        "description": "Grand total. Downstream must reconcile against sum(line_items)."
      }
    },
    "required": ["invoice_number", "currency", "line_items", "total"]
  }
}
Tip: Prefer enum over free-text for any categorical field — it converts an open-ended guess into a closed-set choice the schema can enforce. And keep required minimal: mark only fields that must exist, and allow null (via a union type) for optional data so Claude does not invent values to satisfy the schema.
Common Pitfall: Over-required-ing the schema. If you mark an optional field required but permit only string, Claude may hallucinate a plausible value rather than omit it — because omission would violate the contract. Give it a legal "escape" (null or an "unknown" enum) instead.
Exam Strategy: Expect "which keyword enforces X" matching questions. Remember the enforced set (type, required, enum, pattern) versus advisory (format, description). Keyword to watch: "constrain to a fixed set" → enum; "must be present" → required; "hint only" → format/description.
Q: You must guarantee status is one of exactly {open, closed, pending}. Which keyword?
A: enum: ["open","closed","pending"] — the only keyword that restricts to a fixed, validator-enforced value set.

20.5 Modeling Ambiguity: "other" / "unclear" + Detail Patterns Chain-of-Thought

Real documents contain values that do not fit your enum, or that are genuinely ambiguous. If the schema offers no legal way to say "I'm not sure," Claude is pushed to pick the least-wrong enum member — a silent, confident error. The fix is an escape-hatch enum value ("other", "unclear") paired with a conditional detail field that captures the free-text explanation.

The canonical pattern

{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["invoice", "receipt", "other", "unclear"],
      "description": "Document type. Use 'other' if it is a real type not listed; use 'unclear' if the text is too ambiguous to decide."
    },
    "category_detail": {
      "type": "string",
      "description": "REQUIRED when category is 'other' or 'unclear'. For 'other', name the actual type. For 'unclear', state what is missing to decide."
    }
  },
  "required": ["category"]
}

Note that category_detail is not in the top-level required array. JSON Schema can express conditional requirements via if/then, but Claude does not reliably enforce complex conditional subschemas at generation time. The robust approach is: describe the conditional rule in the field description (which steers the model), and enforce the "required-if" rule in your own validation code.

Chain-of-Thought Walkthrough: Why "other" and "unclear" are semantically different — and why you need both.
  1. Scenario 1 — a packing slip. It is a real, well-defined document type, just not in your enum {invoice, receipt}. If the only choices were those two, Claude would mislabel it. With "other", it can correctly signal "known type, not in your list," and put "packing slip" in category_detail. This is a confident classification into a residual bucket.
  2. Scenario 2 — a blurry, half-scanned page. Here the problem is not that the type is missing from the enum; it is that the evidence is insufficient. "unclear" expresses epistemic uncertainty, and category_detail should say what is missing ("header cut off, no totals visible").
  3. Why one value is not enough: collapsing both into a single "other" destroys information — downstream you cannot tell "route to a human because it's a new type" from "route to a human because the scan is bad." Two distinct values preserve that routing signal.
  4. Conclusion: provide "other" (out-of-taxonomy but known) and "unclear" (insufficient evidence), plus one detail field whose meaning is conditioned on which was chosen. Then enforce "detail required when either is selected" in code, since the schema alone will not guarantee it.
Tip: Always give the model a legal way to express uncertainty. An enum without an escape hatch is a hallucination generator: forced to choose, the model chooses confidently and wrongly. Pair the escape value with a required-in-code detail field so no information is lost.
Common Pitfall: Relying on JSON Schema if/then/dependentRequired to enforce "detail required when category is other." Claude will not reliably honor complex conditional subschemas during generation, and lightweight validators may skip them. Steer with descriptions; enforce the conditional in your application code.
Exam Strategy: Look for scenarios where a value "does not fit the categories" or is "ambiguous/insufficient." The right design adds an escape-hatch enum member plus a detail field — not "add every possible category" and not "let the model return free text." Keywords: "graceful uncertainty," "residual/other bucket," "conditional/required-if," "avoid forced misclassification."
Q: An extractor keeps mislabeling unfamiliar document types as the nearest enum value. Best schema fix?
A: Add "other" (and "unclear") to the enum plus a detail field, and enforce "detail required when other/unclear" in validation code. Why: it gives the model a correct, information-preserving way to decline a forced choice.

20.6 Production Patterns: Parallel Tools, Retries & Streaming

Beyond a single clean call, production extraction must handle multiple objects, malformed outputs, and latency. Three patterns dominate.

Parallel tool use

Under tool_choice: auto (or any), Claude may emit multiple tool_use blocks in one turn — for example calling record_line_item several times. If your pipeline expects exactly one object, set disable_parallel_tool_use: true. If you want the fan-out, iterate over every tool_use block in response.content and return one tool_result per tool_use_id.

The validate-and-retry loop

Because adherence is best-effort, wrap extraction in a bounded retry loop. On a schema or semantic failure, feed the validation error back to Claude as a tool_result with "is_error": true, and let it correct itself.

# Pseudocode — bounded self-correction loop
for attempt in range(MAX_RETRIES):        # cap retries to control cost/latency
    resp = client.messages.create(...)     # tool_choice forces the extractor
    block = first_tool_use(resp)            # pull the tool_use content block
    ok, errors = validate(block["input"])   # schema + semantic checks (20.3)
    if ok:
        return block["input"]               # clean, validated object
    # else: return the errors as a tool_result so Claude can fix them
    messages.append(tool_result(block["id"], errors, is_error=True))

Streaming tool inputs

Tool inputs stream as input_json_delta events — partial JSON fragments that you accumulate and parse only once the block completes. Do not attempt to json.loads a partial buffer mid-stream; wait for content_block_stop (or the final message) before validating.

Tip: Always bound your retry loop (e.g. 2–3 attempts) and pass the specific validation error text back in the tool_result. Vague "that was wrong" retries waste tokens; "field issue_date: 2026-02-31 is not a real calendar date" gives Claude exactly what to fix.
Common Pitfall: Parsing streamed input_json_delta fragments as if each were complete JSON. They are partial by design — accumulate first, parse once. A second trap: forgetting to return a tool_result for every tool_use block when parallel calls occur, which breaks the next turn.
Exam Strategy: Watch for "how do you handle a schema-invalid response" — the correct answer is a bounded retry that returns the error via tool_result with is_error: true, not "increase temperature" or "switch to JSON mode." For "exactly one object," the answer is disable_parallel_tool_use. Keywords: "self-correction," "partial JSON," "one tool_result per tool_use_id."
Q: Claude occasionally returns a schema-invalid object. What is the recommended production fix?
A: A bounded validate-and-retry loop that sends the validation errors back as a tool_result (is_error: true) so the model self-corrects — capped at a small number of attempts.

20.7 Hands-On: A Complete Extraction Pipeline

This section ties everything together: sample input, schema, request structure, expected output, and validation — each step annotated with why.

Step A — Sample input text

Support ticket #4471, opened 2026-09-18.
Customer: Dana Lee (dana@acme.io). Product: Aurora Dashboard.
"Exports keep failing with a 500 error since the last release."
Severity feels high — the whole reporting team is blocked.

Step B — Tool + JSON Schema definition

{
  "name": "record_ticket",
  "description": "Extract a structured support ticket. Use enum escape values when unsure.",
  "input_schema": {
    "type": "object",
    "properties": {
      "ticket_id":   { "type": "string",
                       "description": "ID as printed, without the '#'." },
      "opened_date": { "type": "string",
                       "pattern": "^\\d{4}-\\d{2}-\\d{2}$",
                       "description": "ISO date; verify the calendar day in code." },
      "customer_email": { "type": "string",
                          "description": "Contact email, or null if absent." },
      "severity": { "type": "string",
                    "enum": ["low", "medium", "high", "unclear"],
                    "description": "Use 'unclear' if severity is not stated or implied." },
      "severity_detail": { "type": "string",
                           "description": "REQUIRED (in code) when severity is 'unclear'." }
    },
    "required": ["ticket_id", "opened_date", "severity"]
  }
}

Why: enum closes the severity value set (20.4); "unclear" + severity_detail give a graceful uncertainty path (20.5); pattern catches malformed dates but the calendar check is deferred to code (20.3).

Step C — Request structure (forced, single tool)

{
  "model": "claude-3-7-sonnet",
  "max_tokens": 1024,
  "tools": [ /* record_ticket definition from Step B */ ],
  "tool_choice": { "type": "tool", "name": "record_ticket" },
  "disable_parallel_tool_use": true,
  "messages": [
    { "role": "user",
      "content": "Extract the ticket from the following text:\n" }
  ]
}

Why: forcing the named tool (20.2) guarantees exactly this extractor runs and suppresses any preamble; disable_parallel_tool_use guarantees a single object.

Step D — Expected structured output (the tool_use.input)

{
  "ticket_id": "4471",
  "opened_date": "2026-09-18",
  "customer_email": "dana@acme.io",
  "severity": "high",
  "severity_detail": "Reporter says the whole reporting team is blocked."
}

Why: severity is inferred as "high" from "the whole reporting team is blocked," not left "unclear", because the text implies impact. If it had said nothing about impact, "unclear" + a detail explaining the gap would be correct.

Step E — Validation pass (schema + semantic)

# 1. Schema validation — catches type/enum/pattern/required violations
jsonschema.validate(instance=tool_input, schema=input_schema)

# 2. Semantic validation — the schema cannot do these
datetime.strptime(tool_input["opened_date"], "%Y-%m-%d")   # real calendar day?
assert "@" in tool_input.get("customer_email", "@")        # plausible email
if tool_input["severity"] == "unclear":                     # conditional required-if
    assert tool_input.get("severity_detail"), "detail required when severity is unclear"

Why: step 1 enforces shape; step 2 enforces meaning and the required-if rule the schema cannot guarantee (20.3, 20.5). On failure, return the error via a tool_result with is_error: true and retry within a bounded loop (20.6).
