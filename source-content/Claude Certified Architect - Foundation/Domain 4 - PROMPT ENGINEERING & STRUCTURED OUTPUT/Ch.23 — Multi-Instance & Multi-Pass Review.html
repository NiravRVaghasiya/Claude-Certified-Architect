One principle threads the whole chapter: reliable review requires independence — separating the reviewer's context from the author's context, then structuring that review so scope (local → global) and confidence (auto → escalate) are handled by design, not by luck.

23.1Self-Review Limitations

Why asking the same session "are you sure?" rarely catches its own mistakes.

Definition — Self-review is when the same model instance that produced an artifact (code, a plan, a PR) is asked, within the same session and context window, to critique or verify that artifact. It fails systematically because the reviewer shares the author's state.

Why it matters

Self-review looks like verification but structurally it is the author re-reading their own work with the same assumptions loaded. Exam scenarios lean on this because teams naively bolt a "now double-check your answer" step onto a single agent and assume the problem is solved. It is not.

Mechanism — the three failure modes

  • Context contamination: the flawed reasoning trace is still in the context window. The model conditions its "review" on the very tokens that produced the bug, so the mistake is treated as an established premise rather than something to challenge.
  • Confirmation bias: having just committed to a solution, the model is primed to justify it. Generation and evaluation share an objective ("be consistent with what I just said"), so the review rationalizes instead of falsifies.
  • Shared blind spots: if the model lacks knowledge of an edge case (e.g., a race condition, a locale-specific date format), that gap is present in both the writing and the reviewing pass. You cannot catch an error you couldn't see in the first place.

Concrete example

An agent generates an auth handler and, in its reasoning, assumes tokens never expire mid-request. Asked "review this for bugs" in the same session, it re-reads its own note that "tokens are valid for the request lifetime," treats that as ground truth, and reports "no issues found." The expiry race survives review because the wrong assumption was inherited, not re-examined.

Fig 23.1 — Self-review is a closed loop: the reviewer never sees anything the author didn't.
⚠ Pitfalls
  • Mistaking "add a self-check step" for genuine QA — it raises confidence without raising coverage.
  • Longer chain-of-thought does not fix this; more tokens of the same context deepen the anchoring.
  • Temperature tweaks on the same instance are cosmetic — the contaminating context is unchanged.
💡 Tips & Tricks Remember the three failures with "C-C-S" — Contamination, Confirmation bias, Shared blind spots. Examiners test whether you can name why self-review fails structurally (shared state) rather than blaming "the model isn't smart enough." The magic phrase they look for is "the reviewer and author share context, so review is not independent."
🎯 Exam Strategy If a scenario says "the team added a self-verification prompt but bugs still ship," lead by diagnosing the shared-context root cause (name C-C-S), then prescribe the fix (independent instance, 23.2). Always state the problem class before the solution — graders reward the causal chain, not just the answer.

23.2Independent Review Instances

Fresh eyes, empty context: reviewing the artifact, not the author's story about it.

Definition — An independent review instance is a separate model invocation with a fresh context window that receives only the artifact under review (and its spec/requirements) — never the generator's reasoning trace, intermediate thoughts, or self-justifications.

Why it matters

This is the direct structural cure for 23.1. By denying the reviewer the author's context, you break all three failure modes at once: there is nothing to be contaminated by, no prior commitment to defend, and — crucially — a fresh instance may hold different blind spots, so overlap of gaps shrinks.

Mechanism

  • Context isolation: spin up a new session. The only inputs are the artifact + the original requirements/acceptance criteria — the "what should this do," not the "how I decided to do it."
  • Blind review: withhold the generator's chain-of-thought. If the reviewer never sees the rationalization, it cannot inherit the flawed premise.
  • Adversarial framing: instruct the reviewer to find defects (falsify), not to confirm correctness — the opposite objective to the author.
  • Optional diversity: vary the reviewer (different prompt/system role, or a different model) to further de-correlate blind spots.
Key rule to memorize: pass the reviewer the artifact + spec, never the author's reasoning. Independence is defined by what you withhold, not merely by "using a second call."

Concrete example

The auth handler from 23.1 is handed to a fresh instance that receives only the code and the requirement "handle expired tokens gracefully." With no note claiming tokens never expire, the reviewer reads the code on its own terms, spots that expiry mid-request is unhandled, and files a finding. Same model family — but independence surfaced the bug.

⚠ Pitfalls
  • Leaky isolation: passing the full conversation history "for convenience" re-creates self-review — the independence is an illusion.
  • Confusing "a second API call" with independence. Same context in the second call = still contaminated.
  • Over-diversifying (wildly different model with poor code skills) can add noise instead of coverage.
💡 Tips & Tricks Mnemonic: "FAB" — Fresh context, Artifact-only input, Blind to reasoning. If any of the three is missing, it is not a true independent instance. Examiners love the trap answer "just call the model twice" — reject it unless the context is reset.
🎯 Exam Strategy When proposing independent instances, always specify the inputs explicitly ("reviewer receives code + acceptance criteria only; generator CoT withheld"). Naming the withheld context is what distinguishes an A-grade answer from a vague "use a second agent." Mention 23.1's C-C-S and map each cure to it.

23.3Multi-Pass Review

Separate the questions "is each file correct?" from "do the files agree with each other?"

Definition — Multi-pass review decomposes review into distinct scopes run in sequence: a Pass 1 (local) that analyzes each file in isolation, then a Pass 2 (cross-file integration) that reasons over interfaces, contracts, and consistency across the whole change set.

Why it matters

A single "review the whole PR" prompt forces one context to hold every file and every relationship at once — attention is diluted and mid-file details get lost. Splitting by scope gives each concern its own focused pass, which is both more accurate and more token-efficient. This directly composes with 23.2: each pass runs on an independent, fresh-context instance.

Mechanism

  • Pass 1 — Local (per-file): for each file, a fresh reviewer instance checks correctness, style, and in-file logic in isolation. High recall on localized defects; deliberately blind to the rest of the PR.
  • Pass 2 — Cross-file integration: a reviewer receives the interface surface — function signatures, shared types, call graph, and each file's Pass-1 findings — and checks contract mismatches, broken callers, inconsistent assumptions, and duplicated/ conflicting logic between files.
  • Hand-off, not restart: Pass 2 consumes Pass 1's structured output (summaries + signatures), so integration reasoning is grounded without re-reading every full file.

Concrete example

In a 5-file PR, Pass 1 clears each file individually — api.py, db.py, etc. all look internally sound. Pass 2 then notices that api.py calls db.save(user, ttl) with three arguments while db.py's save(user) takes two. No single-file pass could catch this; it only exists between files.

Fig 23.3 — Fan-out for local depth, converge for global consistency.
⚠ Pitfalls
  • Skipping Pass 2 — the most dangerous defects (integration/contract breaks) live only between files.
  • Feeding Pass 2 every full file instead of the interface surface: you recreate the diluted-context problem and blow the token budget.
  • Ordering errors: cross-file reasoning before local passes have produced signatures leaves Pass 2 guessing.
💡 Tips & Tricks Mnemonic: "Local before Global" (L→G). Think "zoom in, then zoom out." Examiners test whether you know which class of bug each pass catches: local pass → in-file logic; integration pass → contract/interface mismatches. If asked "why not one big prompt?" answer with attention dilution + token budget + scope separation.
🎯 Exam Strategy Structure any multi-pass answer as Pass 1 (what & why) → hand-off artifact → Pass 2 (what & why). Explicitly name the hand-off (Pass-1 summaries + signatures) — that detail proves you understand passes are composed, not independent silos. Always tie each pass to an independent fresh instance (links 23.2).

23.4Confidence-Based Review Routing

Not every finding deserves the same treatment — let certainty decide the escalation path.

Definition — Confidence-based routing attaches a calibrated confidence score to each review finding (or verdict) and uses thresholds to decide its fate: auto-resolve, send to a secondary independent instance, or escalate to a human. It is the control plane that sits on top of 23.2/23.3.

Why it matters

Routing everything to humans doesn't scale; auto-approving everything is reckless. Confidence lets the system spend expensive attention (a second instance, or a person) only where uncertainty is high, keeping throughput high and risk low. This is where architects show they can balance cost, latency, and safety.

Mechanism

  • Score each finding: the reviewer emits a confidence value with each finding (e.g., "unhandled expiry — confidence 0.93"). Calibrate against known-labeled samples so the number is meaningful, not vibes.
  • Threshold bands: compare against configured cut-offs to pick an action.
  • Escalation targets that preserve independence: the "secondary reviewer" is another fresh independent instance (23.2) — often with a different prompt/model to de-correlate — never the same contaminated context.
  • Risk-weighting: multiply/adjust thresholds by blast radius. A low-confidence finding in auth or billing escalates faster than the same score in a doc string.

Concrete example

The cross-file reviewer reports the db.save arity mismatch at 0.95 confidence → auto-flagged as a blocking defect. A separate finding — "this retry loop might double-charge" — comes in at 0.72 → routed to a fresh secondary instance, which confirms it. A vague "naming feels off, unsure" at 0.4 → escalated to a human, who decides it's fine. Each finding consumed effort proportional to its uncertainty.

⚠ Pitfalls
  • Uncalibrated confidence: raw model self-reported certainty is often overconfident — routing on it blindly sends real bugs down the auto-approve path.
  • Ignoring risk: a 91% finding in payment code shouldn't auto-resolve just because it cleared the band.
  • Fake secondary review: routing the mid-band back to the same instance violates 23.2 — the "second opinion" is contaminated.
💡 Tips & Tricks Mnemonic: "A-S-E" — high→Auto, mid→Second instance, low→Escalate to human. Examiners test two traps: (1) that you calibrate confidence rather than trust it raw, and (2) that the mid-band reviewer is independent. If you forget the risk-weighting, you'll miss the "high-confidence in high-stakes code" gotcha.
🎯 Exam Strategy Present routing as a table of bands → actions → rationale (graders love the structure), then add one sentence on calibration and one on risk-weighting. Always state that the secondary path reuses the independent-instance mechanism from 23.2 — this proves cross-section consistency, which is exactly what Chapter-23 essay questions reward.

23.5Hands-On Design — a Multi-Pass Review System

Putting 23.1–23.4 together into one working pipeline for a real PR.

Step 1 — The problem

Design an automated review system for a 10-file pull request that touches an API layer, a data layer, and shared utilities. Requirements: catch both in-file bugs and cross-file contract breaks, minimize human load, and never auto-approve a risky change the system isn't sure about. A naive "one agent reviews the whole PR and self-checks" is explicitly disallowed (fails per 23.1).

Step 2 — Architecture

Fig 23.5 — End-to-end: fan-out (23.3 local) → converge (23.3 integration) → route (23.4), every reviewer independent (23.2), replacing self-review (23.1).

Step 3 — Walkthrough

  1. Pass 1 (local, parallel): 10 fresh independent instances each receive one file + the relevant spec — no generator reasoning (23.1/23.2). Each emits findings with confidence and a compact signature summary (exports, function signatures, assumptions).
  2. Pass 2 (cross-file): one fresh instance receives the 10 signature summaries + Pass-1 findings (not the full files) and checks the call graph and contracts. It discovers api.py calls db.save(user, ttl) while db.py defines save(user) — a break invisible to any local pass (23.3).
  3. Confidence routing: every finding flows through the router (23.4). See the decision table below for how each is handled.

⚠ Pitfalls in the build
  • Letting Pass 2 read all 10 full files (context blow-up) instead of signatures + Pass-1 findings.
  • Reusing the primary reviewer's session as the "secondary" — collapses independence back to self-review.
  • Trusting raw model confidence without calibration, and forgetting to risk-weight auth/billing findings.
💡 Tips & Tricks Recall the full pipeline as "Split → Local → Global → Route". If you can draw that four-stage flow and annotate each stage with the section it comes from (23.3, 23.3, 23.4) plus "every reviewer independent (23.2), never self-review (23.1)," you have the whole chapter in one diagram.
🎯 Exam Strategy For a "design a review system" question: (1) reject the naive single-agent design and say why (23.1); (2) draw the fan-out/converge/route diagram; (3) walk one finding of each confidence band through the pipeline; (4) close with calibration + risk-weighting. Present a decision table — it earns structure marks and demonstrates the routing logic concretely.

★Chapter Summary & Quick Revision

The whole chapter in seven cards — read these the night before.

23.1 Self-Review Limitations

Same-session review fails via C-C-S: Context contamination, Confirmation bias, Shared blind spots. Reviewer and author share state, so review isn't independent.

23.2 Independent Instances

FAB: Fresh context, Artifact-only input, Blind to reasoning. Independence is defined by what you withhold — the generator's chain-of-thought.

Local before Global. Pass 1 = per-file logic; Pass 2 = cross-file contracts via signatures + Pass-1 findings. Integration bugs live only between files.

Split → Local → Global → Route. 10 fresh local reviewers → one cross-file reviewer → confidence router with a decision table. Never self-review; secondary path stays independent.

Independence + scope separation + confidence gating. Every later section is a mechanism serving the independence principle introduced in 23.1.

✓Exam Answering Checklist

A repeatable order for any Chapter-23-style scenario or essay question.

  1. Diagnose before you prescribe. Name the root cause first — if self-review is in the scenario, state C-C-S (shared context) before offering any fix.
  2. Establish independence. Propose fresh-context instances and explicitly list the inputs (artifact + spec) and what's withheld (generator reasoning). Reject "just call the model twice."
  3. Separate scope into passes. Describe Pass 1 (local, per-file) then Pass 2 (cross-file), and name the hand-off artifact (signatures + Pass-1 findings). Say which bug class each pass catches.
  4. Add the confidence control plane. Present a bands → action → rationale table (auto / secondary independent instance / human). Confirm the secondary path is independent (ties to step 2).
  5. Address calibration & risk. State that confidence must be calibrated (not raw self-report) and thresholds risk-weighted for high-blast-radius code (auth, billing).
  6. Draw the diagram. Fan-out → converge → route. A labeled sketch earns structure marks and proves the sections compose consistently.
  7. Close with consistency. Explicitly note how 23.4 reuses 23.2 on 23.3's scopes — showing no contradiction across the chapter is exactly what graders reward.
