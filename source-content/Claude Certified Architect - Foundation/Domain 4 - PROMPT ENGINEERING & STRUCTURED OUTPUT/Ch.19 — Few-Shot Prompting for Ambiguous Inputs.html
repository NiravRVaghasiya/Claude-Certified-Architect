19.1  Creating Targeted Few-Shot Examples for Ambiguous Scenarios Core

📘 Concept Summary

An input is ambiguous when it can be reasonably interpreted in more than one way (e.g., "book a table" could mean a restaurant reservation or reserving furniture). Targeted few-shot examples are demonstrations chosen specifically to cover the confusing edge cases — not the easy, obvious ones — so the model learns your intended resolution for the hard cases. The examples do the disambiguating work that instructions alone struggle to convey.

💡 Why It Matters

Zero-shot instructions describe the rule in the abstract; ambiguous inputs are exactly where abstract rules break down. Without targeted examples the model defaults to the most statistically common interpretation, which may not match your domain. Targeted examples convert a vague policy ("classify support tickets correctly") into concrete, imitable boundaries for the cases that actually cause errors.

Worked Example

Task: Classify each message as ORDER, SUPPORT, or SALES.
Some messages are ambiguous — use the examples to resolve them.

Example 1 (ambiguous: sounds like sales but is support)
Message: "How much more do I pay to upgrade my current plan?"
Label: SUPPORT
(Existing customer asking about their account = SUPPORT, not SALES.)

Example 2 (ambiguous: mentions price but is a new prospect)
Message: "What does the Pro plan cost for a brand-new team?"
Label: SALES
(No existing account referenced; pre-purchase pricing = SALES.)

Example 3 (ambiguous: order-like but is a complaint)
Message: "I placed order #4412 yesterday and it still hasn't shipped."
Label: SUPPORT
(A problem with an existing order = SUPPORT, not ORDER.)

Now classify:
Message: "Can I add three more seats to our account today?"
Label: ?

Each example was picked because it sits on a boundary. The easy case ("I want to buy your product" → SALES) is omitted — it teaches the model nothing it didn't already know.

Visualization — Decision Tree: Should I add a targeted example?

✅ Tips & Tricks

  • Mine real failures. Build your example set from actual mislabeled inputs, not invented ones.
  • Cover the boundary, not the center. Choose examples near the decision line between two labels.
  • Pair look-alikes. Show two near-identical inputs that resolve to different labels so the discriminating feature is unmistakable.
  • Keep a short annotation in parentheses stating why — it reinforces the rule the example encodes.

⚠️ Common Pitfalls

  • Only showing easy cases. Examples of obvious inputs waste the context and don't reduce ambiguity.
  • Label imbalance. Ten examples of one class and one of another biases the model toward the majority.
  • Leaky examples. An example whose wording accidentally telegraphs the answer (e.g., always putting SUPPORT tickets last) teaches position, not meaning.
  • Contradictory examples — two similar inputs labeled inconsistently — actively degrade accuracy.

🎯 Exam Strategy Box

How questions are phrased: "A classifier works on clear inputs but fails on borderline cases. What is the most effective fix?" or "Which few-shot example set best reduces ambiguity?"

Keywords to watch: borderline, edge case, misclassified, both interpretations valid, works except when.

Eliminating wrong answers: Reject options that "add more general instructions" when the problem is specifically edge cases — the exam rewards targeted examples over more prose. Reject options that add many examples of the easy class. Prefer answers that show boundary cases with the correct resolution.

📝 Sample Q&A

Q. A ticket router correctly labels obvious tickets but confuses billing questions from existing customers (should be SUPPORT) with new-customer pricing questions (should be SALES). Which change most directly fixes this?

A. Add a longer system instruction defining SALES and SUPPORT.
B. Add few-shot examples of clearly-SALES and clearly-SUPPORT tickets.
C. Add paired few-shot examples of the two look-alike billing/pricing cases with contrasting labels and short reasons.
D. Increase temperature so the model considers more options.

Correct: C.

Why C is right: The failure is specifically on look-alike boundary cases. Paired contrasting examples encode the exact discriminating feature (existing account vs. new prospect), which is the highest-leverage fix.

Why the others are wrong: A restates abstract rules the model already fails to apply to edge cases. B demonstrates only easy cases and never shows the confusing boundary. D raises randomness, which makes ambiguous classification worse, not better.

19.2  Demonstrating Reasoning: Why One Action Was Chosen Over Alternatives Core

📘 Concept Summary

Beyond showing input → output, you can show input → reasoning → output, where the reasoning explicitly names the rejected alternative and states why it was rejected. This teaches the model a comparative decision procedure ("choose X over Y because…"), not just a mapping. It is few-shot chain-of-thought applied to disambiguation between competing choices.

💡 Why It Matters

Many ambiguous tasks are really "pick the best of several defensible answers." Showing only the final answer hides the trade-off, so the model can't generalize the trade-off to new inputs. Demonstrating the contrast ("Performance, not Bug, because the app still works") makes the decision boundary explicit and auditable — which also makes outputs easier for humans to verify.

Worked Example

Input: "Categorize this ticket: 'App crashes when I upload large files'"

Example 1
Ticket: "Page loads slowly on mobile"
Category: Performance
Reasoning: Chose "Performance" over "Bug" because no error/crash
occurs — the app functions, just slowly. This is a speed issue, not a defect.

Example 2
Ticket: "Login button does nothing when clicked"
Category: Bug
Reasoning: Chose "Bug" over "Feature Request" because expected
functionality (login) is broken, not missing.

Now categorize: "App crashes when I upload large files"
Category: ?

The model is expected to produce: Category: Bug — chose "Bug" over "Performance" because a crash is a functional failure, not a slowdown.

Visualization — Reasoning-Augmented vs. Answer-Only Examples

AspectAnswer-only exampleReasoning + contrast example
What it teachesInput → label mappingThe decision rule and the trade-off
Generalizes to new edge casesWeaklyStrongly
Human auditabilityLow — no rationaleHigh — rationale is visible
Token costLowerHigher (worth it for hard tasks)
Best forSimple, unambiguous mappingCompeting defensible answers

✅ Tips & Tricks

  • Name the loser. Always state the rejected alternative explicitly ("X over Y"), not just the winner.
  • Keep reasoning short and rule-shaped — one or two sentences that generalize, not a story about this one input.
  • Put reasoning before the final label in each example so the model imitates "think, then answer."
  • If you need a clean machine-readable output too, ask for reasoning in a separate field (or a <thinking> block) that you can strip later.

⚠️ Common Pitfalls

  • Post-hoc reasoning after the answer. If the label comes first, the "reasoning" becomes decoration and doesn't steer the decision.
  • Over-specific rationales that reference this exact input and don't transfer.
  • Inconsistent reasoning style across examples — the model imitates the surface pattern, so keep it uniform.
  • Contradiction between the reasoning and the chosen label — a fatal signal that confuses the model.

🎯 Exam Strategy Box

How questions are phrased: "The model picks a defensible-but-wrong category. How do you improve consistency?" or "Which example format best teaches the model to justify choices?"

Keywords: justify, rationale, chose X over Y, chain-of-thought, competing categories, defensible answer.

Eliminating wrong answers: Prefer options where reasoning precedes the answer and names the rejected option. Reject options that only add more categories, or that place reasoning after the label. Beware answers that say "chain-of-thought always increases accuracy" — the exam expects the nuance that it helps for reasoning-heavy/ambiguous tasks, not trivial mappings.

📝 Sample Q&A

Q. You want a model to reliably choose between "Performance" and "Bug" for support tickets and to make its choice auditable. Which few-shot design is best?

A. Examples with the label only.
B. Examples with the label, then a one-line reason after it.
C. Examples with a one-line reason that names the rejected category, then the label.
D. A single very long example with a five-paragraph analysis.

Correct: C.

Why C is right: Reasoning-before-answer makes the model deliberate before committing, and naming the rejected category ("Bug over Performance because…") encodes the trade-off it must generalize.

Why the others are wrong: A hides the decision rule. B puts the rationale after the decision, so it doesn't steer it. D is verbose, hard to imitate consistently, and burns tokens without improving the decision boundary.

19.3  Format Demonstration with Few-Shot Examples Core

📘 Concept Summary

Few-shot examples are the most reliable way to lock in an exact output format — JSON shape, key names, ordering, casing, delimiters, and how to render missing values. Instead of describing the schema in prose, you show two or three fully-formed outputs. The model imitates the surface form precisely, which is far more robust than "return valid JSON."

💡 Why It Matters

Downstream systems (parsers, databases, pipelines) fail on the smallest format drift — an extra prose sentence, a renamed key, a trailing comma. Demonstrated format examples dramatically cut this drift because the model has a concrete template to copy. This is the single highest-ROI use of few-shot for production integrations.

Worked Example

Extract fields as JSON exactly like the examples. Output JSON only — no prose.

Text: "Invoice #A-102 from Acme Corp, total $4,500, due 2026-03-01."
Output:
{"invoice_id": "A-102", "vendor": "Acme Corp", "total": 4500.00, "due_date": "2026-03-01"}

Text: "Receipt from Bolt Ltd for $89.99 (no invoice number)."
Output:
{"invoice_id": null, "vendor": "Bolt Ltd", "total": 89.99, "due_date": null}

Text: "Invoice #Z9 from Nimbus, amount 1200 EUR, payable immediately."
Output:

Notice the examples fix: key names, null for missing fields, numeric (not string) totals, and ISO dates. The prose instruction alone would leave all of those under-specified.

Visualization — Good vs. Bad Format Specification

ApproachResultReliability
"Return the data as JSON."Keys, types, null-handling all vary run to run; occasional prose preamble.❌ Low
Prose schema description (list every field + type)Better, but edge details (missing values, number vs. string) still drift.⚠️ Medium
2–3 complete worked output examples (incl. a null case)Model copies exact shape, key order, and missing-value convention.✅ High

✅ Tips & Tricks

  • Include an edge-case example in the format demo — especially one with a missing field — so the null convention is shown, not guessed.
  • Say "output JSON only, no prose" and back it with examples that contain only JSON.
  • Combine with a prefilled assistant turn (start the response with {) to suppress preambles when the API supports it.
  • Keep examples schema-identical — same keys in the same order every time.

⚠️ Common Pitfalls

  • Examples that disagree on format (one uses "total":"4500", another "total":4500) — the model will mix both.
  • No missing-value example, so the model invents a value or drops the key when a field is absent.
  • Prose mixed into example outputs ("Here is the JSON:") which the model faithfully copies into production.
  • Trailing commas or comments in example JSON that make it invalid and get imitated.

🎯 Exam Strategy Box

How questions are phrased: "Outputs are mostly valid JSON but occasionally include a sentence or rename a key. Best fix?" or "How do you guarantee a strict schema?"

Keywords: schema, strict format, parser fails, valid JSON, key names, missing field.

Eliminating wrong answers: Prefer "provide worked example outputs including a null case" and/or "prefill the assistant turn with the opening brace." Reject "ask more firmly for JSON" (prose-only fixes) and reject "lower max tokens" (truncates, doesn't format). Note: schema examples reduce but don't 100% guarantee validity — if an option promises absolute guarantees from prompting alone, be suspicious; true guarantees come from validation/tooling on top.

📝 Sample Q&A

Q. A pipeline breaks because ~5% of responses prepend "Sure, here's the JSON:" and sometimes omit the due_date key entirely. Which combination best fixes this?

A. Increase the temperature and retry on parse failure.
B. Add 2–3 example outputs (JSON only, one with due_date: null) and prefill the reply with {.
C. Add the instruction "Please only output JSON, thank you."
D. Switch to returning YAML.

Correct: B.

Why B is right: Worked examples fix key presence and the null convention; prefilling the opening brace removes the prose preamble. Together they attack both failure modes directly.

Why the others are wrong: A raises randomness (worse) and only reacts after failure. C is another prose plea that the 5% will still ignore. D changes the format without addressing why the model drifts.

19.4  Distinguishing Acceptable Code Patterns from Genuine Issues Applied

📘 Concept Summary

In AI-assisted code review, the same syntactic pattern can be perfectly fine in one context and a serious defect in another. Few-shot examples teach the model to judge by context and intent, not by surface pattern — flagging genuine issues while suppressing false positives on idiomatic, intentional code. This keeps review signal high and reduces alert fatigue.

💡 Why It Matters

A reviewer that flags every except: pass or every eval() becomes noise and gets ignored. A reviewer that never flags them misses real bugs. Context-aware few-shot examples calibrate the model to the middle ground your team actually wants — acceptable-vs-issue judgments that match your engineering standards.

Visualization — Same Pattern, Different Verdict

PatternAcceptable?Reasoning
except: pass in cleanup / best-effort teardown✅ YesIntentional silent cleanup; failure is non-critical
except: pass in payment / auth logic❌ NoHides critical failures; swallows errors that must surface
assert user.is_admin in a test✅ YesAssertions are the point of tests
assert user.is_admin as production access control❌ NoAsserts can be stripped with -O; not a security boundary
# TODO in a prototype / spike✅ YesExpected in exploratory code
# TODO: sanitize input before a DB write in prod❌ NoMarks a known, shipped security gap

Worked Example

Review the code. Flag GENUINE issues only. Acceptable intentional patterns
should be marked OK with a one-line reason.

Example 1:
Code:
  try:
      tmp_file.close()
  except Exception:
      pass          # best-effort cleanup on shutdown
Verdict: OK
Reason: Silent except is acceptable here — cleanup failure is non-critical.

Example 2:
Code:
  try:
      charge_customer(card, amount)
  except Exception:
      pass
Verdict: ISSUE (High)
Reason: Swallowing exceptions in payment logic hides failed charges.
Fix: Log, alert, and re-raise or handle explicitly.

Now review:
Code:
  try:
      audit_log.write(event)
  except Exception:
      pass
Verdict: ?

Expected: ISSUE (Medium) — silently dropping audit-log writes can violate compliance/traceability, even though it's "just logging."

✅ Tips & Tricks

  • Pair the same pattern in two contexts (one OK, one ISSUE) so the model learns that context decides the verdict.
  • Attach severity levels (Low/Medium/High) in examples to calibrate proportionate responses.
  • Always require a one-line reason and a fix for flagged issues — it forces genuine analysis over pattern-matching.
  • Include a "looks scary but is fine" example to suppress false positives on idiomatic code.

⚠️ Common Pitfalls

  • Only showing "bad" examples trains a flag-everything reviewer (false-positive storm).
  • Pattern-only examples with no context — the model can't learn the context-dependence you want.
  • Missing severity calibration, so trivial and critical issues get the same weight.
  • Treating style preferences as defects, eroding trust in the reviewer.

🎯 Exam Strategy Box

How questions are phrased: "An AI reviewer flags too many false positives on intentional patterns. How do you fix it?" or "Which examples best teach context-aware code review?"

Keywords: false positive, intentional pattern, context-dependent, alert fatigue, acceptable vs. defect, severity.

Eliminating wrong answers: Prefer options that show the same pattern in acceptable and unacceptable contexts. Reject "add more examples of bad code only" (worsens false positives) and "flag all instances of pattern X" (ignores context). Reject fine-tuning/temperature answers when a few-shot example set solves it more cheaply.

📝 Sample Q&A

Q. Developers complain that the AI reviewer flags every except: pass, including intentional cleanup code. What is the best fix?

A. Remove except: pass detection entirely.
B. Add few-shot examples showing except: pass as OK in cleanup and as an ISSUE in payment/auth, each with a reason.
C. Add more examples of dangerous except: pass usage.
D. Raise the temperature so the reviewer is less strict.

Correct: B.

Why B is right: Contrasting the same pattern across contexts teaches the model that intent/context — not the pattern itself — determines the verdict, cutting false positives while retaining true catches.

Why the others are wrong: A throws away a genuinely useful check. C pushes toward flagging more, worsening the false-positive problem. D makes behavior random and unreliable, not context-aware.

19.5  Handling Varied Document Structures: Citations, Bibliographies & Methodologies Applied

📘 Concept Summary

Real documents don't share one layout. Citations appear as APA, MLA, IEEE numeric, or footnotes; bibliographies may be labeled "References," "Works Cited," or unlabeled; methodology sections hide under many headings. Few-shot examples that span several structural variants teach the model to extract the same normalized fields regardless of surface format — turning heterogeneous documents into a consistent schema.

💡 Why It Matters

Extraction pipelines over academic papers, legal filings, or reports must be robust to layout diversity. If your examples only show one citation style, the model overfits to it and fails on the others. Deliberately varied examples build format-invariance, which is exactly what a real corpus demands.

Worked Example

Extract each cited work into: {authors, year, title}. Normalize across styles.

Example 1 (APA):
Text: "Smith, J. (2020). Deep learning for vision. Journal of AI, 12(3)."
Output: {"authors": ["Smith, J."], "year": 2020, "title": "Deep learning for vision"}

Example 2 (IEEE numeric):
Text: "[4] R. Lee and K. Osei, 'Robust extraction pipelines,' Proc. ICML, 2021."
Output: {"authors": ["R. Lee", "K. Osei"], "year": 2021, "title": "Robust extraction pipelines"}

Example 3 (footnote / no year in-line):
Text: "1. Chen et al., Methodology of Surveys (n.d.)."
Output: {"authors": ["Chen et al."], "year": null, "title": "Methodology of Surveys"}

Now extract from:
Text: "Garcia, M., & Patel, S. (2019). Scalable OCR. In Proc. CVPR."
Output: ?

Visualization — Variant Coverage Checklist

FieldStructural variants to demonstrateNormalized target
CitationsAPA, MLA, IEEE numeric [n], footnote, inline vs. reference-listUniform {authors, year, title}
Bibliography"References", "Works Cited", "Bibliography", unlabeled blockList of citation objects
Methodology"Methods", "Methodology", "Experimental Setup", "Approach", embedded in ResultsSingle methodology text field
Missing dataNo year ("n.d."), single author, "et al.", anonymousnull / graceful handling

✅ Tips & Tricks

  • One example per structural variant you expect in the wild — breadth beats depth here.
  • Normalize in the output, vary in the input. Keep the target schema identical across every example.
  • Show a heading-synonym case (e.g., "Experimental Setup" → methodology) so the model matches on meaning, not literal headings.
  • Include an "et al." and an "n.d." example to cover the most common real-world messiness.

⚠️ Common Pitfalls

  • Single-style overfitting — all examples in APA, then failure on IEEE/footnotes.
  • Literal heading matching that misses "Approach" or "Experimental Setup" as methodology.
  • Inconsistent author normalization (sometimes a string, sometimes a list) across examples.
  • Hallucinated years when the source says "n.d." — must map to null, not a guess (see 19.6).

🎯 Exam Strategy Box

How questions are phrased: "Extraction works on APA papers but fails on IEEE-numbered references. Best approach?" or "How do you make document extraction robust to layout?"

Keywords: varied formats, multiple citation styles, heterogeneous documents, works cited vs. references, robust extraction, normalize.

Eliminating wrong answers: Prefer "few-shot examples covering each structural variant with one normalized schema." Reject "add more APA examples" (deepens overfit) and "write a regex per style" (brittle; the exam favors example-driven normalization for varied natural-language layouts). Watch for the normalized-output nuance — the schema must stay constant.

📝 Sample Q&A

Q. A reference-extraction prompt (examples all in APA) returns good results on APA papers but garbage on papers using IEEE numeric citations and footnotes. What is the most effective fix?

A. Add several more APA examples for robustness.
B. Add one example each for IEEE numeric and footnote styles, all mapping to the same {authors, year, title} schema.
C. Instruct "handle all citation formats" without examples.
D. Reject non-APA documents.

Correct: B.

Why B is right: Demonstrating each variant with an identical normalized target teaches format-invariant extraction — exactly the failing dimension.

Why the others are wrong: A reinforces the single-style overfit. C is an abstract instruction with no concrete pattern to imitate for unfamiliar styles. D avoids the requirement instead of meeting it.

19.6  Addressing Empty/Null Extraction with Few-Shot Examples Core

📘 Concept Summary

When a requested field is genuinely absent from the source, the correct output is an explicit empty/null value — not a hallucinated or inferred one. Few-shot examples that include "not present" cases teach the model that "I don't see it" is a valid, expected answer, and show the exact token to emit (null, "", [], or a sentinel like "N/A").

💡 Why It Matters

The most dangerous extraction errors are confident fabrications — inventing a phone number, date, or amount that isn't in the document. Demonstrating null cases is the single most effective prompt-side defense against this: it gives the model explicit permission and a template for "absent," so it stops filling gaps with plausible guesses.

Worked Example

Extract {name, email, phone}. If a field is not present, use null. Do not guess.

Example 1 (all present):
Text: "Contact: Dana Ray, dana@acme.io, +1-202-555-0147"
Output: {"name": "Dana Ray", "email": "dana@acme.io", "phone": "+1-202-555-0147"}

Example 2 (phone missing):
Text: "Reach Dana Ray at dana@acme.io."
Output: {"name": "Dana Ray", "email": "dana@acme.io", "phone": null}

Example 3 (nothing extractable):
Text: "Please see the attached document for details."
Output: {"name": null, "email": null, "phone": null}

Now extract:
Text: "Questions? Email support@nimbus.co."
Output: ?

Expected: {"name": null, "email": "support@nimbus.co", "phone": null} — the model must not invent a person's name from a generic support address.

Visualization — Fabricate vs. Null Decision Flow

✅ Tips & Tricks

  • Always include at least one all-null example and one partial-null example.
  • State the convention explicitly ("use null if absent; do not guess") and demonstrate it — belt and suspenders.
  • Distinguish "absent" from "empty" if it matters (e.g., null = not mentioned vs. [] = mentioned as none).
  • Pick one sentinel and use it everywhere — don't mix null, "N/A", and "".

⚠️ Common Pitfalls

  • No null example, so the model fills gaps with confident hallucinations.
  • Inferring from context (guessing a name from an email domain) when the field isn't stated.
  • Inconsistent empty representations across examples confuse downstream parsers.
  • Punishing "null" implicitly — if every example has full data, the model learns that a non-null answer is always expected.

🎯 Exam Strategy Box

How questions are phrased: "The extractor invents plausible values for missing fields. How do you stop hallucination?" or "What must the few-shot set include for robust extraction?"

Keywords: missing field, hallucinated value, not present, return null, do not guess, empty result.

Eliminating wrong answers: The correct answer almost always includes demonstrating null/absent cases. Reject "instruct not to hallucinate" alone (no demonstration), "lower temperature only" (reduces but doesn't teach the null convention), and "add a required-field validator" (catches errors after the fact rather than preventing the fabrication).

📝 Sample Q&A

Q. An extractor returns a fabricated phone number whenever the document has none. Which single change most directly prevents this?

A. Add examples where the phone is missing and the output is "phone": null.
B. Add the sentence "do not hallucinate" with no examples.
C. Lower the temperature to 0.
D. Add a post-hoc validator that rejects malformed phone numbers.

Correct: A.

Why A is right: A demonstrated null case gives the model an explicit, imitable template for "absent," which is the core behavior that's missing.

Why the others are wrong: B is an instruction with nothing to imitate for the absent case. C reduces variability but a deterministic model can still confidently fabricate. D catches some bad values downstream but doesn't stop the model from inventing valid-looking ones.

19.7  Hands-On: Engineering Few-Shot Prompts Lab

📘 Concept Summary

This section is a repeatable workflow for building a few-shot prompt from scratch: define the task and schema, collect real inputs, select boundary examples, add reasoning/format/null demonstrations as needed, then test and iterate. It ties together 19.1–19.6 into one engineering loop.

💡 Why It Matters

Few-shot prompting is an empirical craft, not a one-shot write. Teams that follow a disciplined build-measure-iterate loop reach reliable prompts faster and can explain why each example is present — which is exactly the judgment the certification tests.

The 6-Step Engineering Loop

Worked Example — A Complete Prompt Assembled from the Loop

SYSTEM: You classify customer messages as ORDER, SUPPORT, or SALES and
return JSON only. If intent is unclear, choose the best fit and explain briefly.
Use the reasoning field to name the rejected alternative.

### Examples

Message: "How much to upgrade my current plan?"
{"label": "SUPPORT",
 "reason": "Existing customer account question — SUPPORT over SALES."}

Message: "What does Pro cost for a new team?"
{"label": "SALES",
 "reason": "Pre-purchase pricing, no existing account — SALES over SUPPORT."}

Message: "Order #4412 hasn't shipped."
{"label": "SUPPORT",
 "reason": "Problem with an existing order — SUPPORT over ORDER."}

Message: "..." (no discernible intent)
{"label": null,
 "reason": "No actionable intent present."}

### Now classify
Message: "Can I add three seats to our account today?"

This single prompt combines targeted boundary examples (19.1), reason-with-rejected-alternative (19.2), strict JSON format (19.3), and a null case for unclassifiable input (19.6).

Visualization — Iteration Log Template

IterationChange madeHeld-out accuracyFormat-valid %
v1 (zero-shot)Instruction only71%88%
v2+3 boundary examples (19.1)84%90%
v3+reasoning field (19.2)89%92%
v4+JSON format demo & null case (19.3/19.6)90%99%

✅ Tips & Tricks

  • Change one thing per iteration so you can attribute gains and losses.
  • Keep a held-out test set the examples never touch — measure on it, not on the examples.
  • Order matters: put the clearest, most canonical examples first; keep example format identical.
  • Stop adding examples when accuracy plateaus — more tokens then just cost money and latency.
  • Version and comment your prompts so each example's purpose is documented.

⚠️ Common Pitfalls

  • Testing on the same examples you put in the prompt — inflated, misleading accuracy.
  • Changing many things at once, so you can't tell what helped.
  • Endless example growth that bloats context and adds latency for no accuracy gain.
  • Ignoring format-validity while chasing label accuracy — a valid label in broken JSON still breaks the pipeline.

🎯 Exam Strategy Box

How questions are phrased: "You're iterating on a few-shot prompt. What's the correct methodology?" or "Which step comes next after v2 improves on the training examples but not on new inputs?"

Keywords: held-out set, iterate, one change at a time, plateau, overfitting to examples, evaluation.

Eliminating wrong answers: Prefer options that emphasize measuring on held-out data and changing one variable at a time. Reject "keep adding examples until 100%" (overfit/bloat) and "test on the prompt's own examples." Watch for the overfitting trap — improvement on the in-prompt examples is not evidence of generalization.

📝 Sample Q&A

Q. After adding examples, your prompt scores 100% on the messages that are in the prompt but only 74% on new messages. What is the best next step?

A. Add the failing new messages verbatim as more examples until new-set accuracy hits 100%.
B. Evaluate on a separate held-out set, then add a few representative boundary examples for the failure types and re-test.
C. Declare success — 100% on the in-prompt examples proves the prompt works.
D. Remove all examples and return to zero-shot.

Correct: B.

Why B is right: The gap between in-prompt and new-input accuracy is classic overfitting. Measuring on held-out data and adding representative (not memorized) examples for the failure categories improves generalization.

Why the others are wrong: A memorizes the test set and won't generalize. C mistakes in-prompt performance for real performance. D discards the gains few-shot already delivered.

✅ Final Exam Checklist — Must-Know Before the Exam

  • Targeted > more instructions: for edge-case failures, add boundary examples, not more prose.
  • Pair look-alikes with contrasting labels to encode the discriminating feature.
  • Reasoning goes before the answer and must name the rejected alternative.
  • Chain-of-thought helps ambiguous/reasoning tasks, not trivial mappings — know the nuance.
  • Format is taught by complete example outputs, including a missing-field/null case; prefilling the opening brace suppresses preambles.

  • Robust extraction = one example per layout variant → one normalized schema.
  • Demonstrate null cases to stop fabrication; pick one sentinel and use it consistently.
  • Balance classes and avoid contradictory or leaky examples.
  • Iterate on a held-out set, one change at a time; stop at the accuracy/format plateau.
  • Overfitting trap: high accuracy on in-prompt examples ≠ generalization.
  • Frame Claude behavior as general prompting best practice — no unverifiable proprietary claims.
