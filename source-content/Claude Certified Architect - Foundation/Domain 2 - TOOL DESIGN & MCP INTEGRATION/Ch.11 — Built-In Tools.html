Built-In Tools: Read, Write, Edit, Bash, Grep, Glob

Master Claude's six core built-in tools for filesystem interaction, shell execution, and codebase navigation. Understand when to use each tool, how to compose them into powerful workflows, and when to delegate to the Explore subagent for verbose discovery.

Learning Objectives

  • Define each of Claude's six built-in tools and articulate their purpose, inputs, outputs, and limitations
  • Apply systematic selection criteria to choose the right tool for any given task
  • Compose multi-tool workflows for efficient codebase exploration and modification
  • Evaluate when to use the Explore subagent versus direct tool calls
  • Demonstrate end-to-end codebase navigation using built-in tools in a realistic scenario

11.1 Overview of Built-In Tools and Their Purposes

Claude's agentic capabilities include six built-in tools — native functions available in agentic environments (such as Claude Code) that allow Claude to interact with the local filesystem and shell. These are not custom user-defined tools; they are part of Claude's core agentic toolkit and are always available when the model operates in tool-use mode within a coding environment.

Each tool is designed for a specific class of operation. Understanding the precise boundaries of each tool — what it can and cannot do — is fundamental to effective agentic workflows and a core exam topic.

Read (File Reader)

Definition: Reads and returns the contents of a file at a specified path.

AttributeDetails
Primary Use CaseViewing source code, configuration files, documentation, or any text file to understand its content before making decisions.
Inputfile_path (string, required) — absolute or relative path to the file. Optional: offset / limit to read specific line ranges.
OutputThe text content of the file (or specified line range). Includes line numbers for reference.
Side EffectsNone — strictly read-only. Does not modify the filesystem in any way.
Key LimitationCannot execute or interpret the file contents. Binary files produce garbled output. Very large files may need to be read in chunks using offset/limit parameters.
💡
Line-Range Reading

The Read tool supports reading specific line ranges (e.g., lines 50–80). This is essential for large files — reading an entire 5,000-line file wastes context window tokens when you only need a specific function. Always scope your reads when possible.

Write (File Writer)

Definition: Creates a new file or completely overwrites an existing file with the provided content.

AttributeDetails
Primary Use CaseCreating new files (source code, configs, documentation) or replacing the full content of an existing file.
Inputfile_path (string) — destination path. content (string) — the complete file content to write.
OutputConfirmation that the file was successfully written, including the number of bytes/lines.
Side EffectsDestructive — overwrites existing file content entirely. Creates intermediate directories if needed.
Key LimitationReplaces the entire file — unsuitable for small, targeted edits to existing files. Cannot append; writes are atomic and complete.
⚠️
Write Overwrites Everything

A common exam trap: using Write when you only need to change a few lines in a large file. Write replaces the entire file, which means you must include all unchanged content too. For targeted changes, always use Edit instead.

Edit (Surgical File Editor)

Definition: Makes precise, targeted modifications to an existing file using a search-and-replace mechanism (old_string → new_string).

AttributeDetails
Primary Use CaseModifying specific functions, fixing bugs, updating configuration values, or refactoring targeted code sections within existing files.
Inputfile_path (string), old_string (string — the exact text to find), new_string (string — the replacement text).
OutputConfirmation of the edit with a snippet of the surrounding context showing the change.
Side EffectsModifies the file in place — only the matched region is changed; all other content is preserved.
Key LimitationThe old_string must match exactly one location in the file. If it matches zero times (typo, wrong whitespace) or more than once (ambiguous match), the edit fails. Whitespace, indentation, and newlines must be exact.
ℹ️
The Uniqueness Constraint

Edit's requirement for a unique match is its most critical behavior. If a function signature appears twice in a file (e.g., in both the definition and a test), you must include enough surrounding context in old_string to disambiguate. Best practice: include 2–3 lines of context around the target change to ensure uniqueness.

Bash (Shell Command Executor)

Definition: Executes a shell command in a persistent bash session and returns stdout/stderr.

AttributeDetails
Primary Use CaseRunning tests, installing packages, executing build scripts, git operations, running linters, or any operation that requires shell access.
Inputcommand (string) — any valid shell command or pipeline.
OutputCombined stdout and stderr output from the command execution, plus the exit code.
Side EffectsHighly stateful and potentially destructive. Can modify files, install software, change directories, set environment variables, start processes. State persists across calls (working directory, env vars, shell history).
Key LimitationSecurity-sensitive — some commands may be restricted or require confirmation. Long-running commands can time out. Cannot handle interactive prompts (e.g., sudo password input). Non-deterministic: same command may produce different results.
🔴
Bash Is the "Power Tool" — Handle with Care

Bash can do everything the other tools can do (read files via cat, write via echo >, search via system grep), but using it for those purposes is an anti-pattern. Prefer the dedicated tools — they have better error handling, no side effects (for Read/Grep/Glob), and are more predictable. Use Bash only when you need shell capabilities (pipelines, git, test runners, package managers).

Grep (Pattern Searcher)

Definition: Searches for a regex pattern across files and returns matching lines with file paths and line numbers.

AttributeDetails
Primary Use CaseFinding function definitions, locating import statements, searching for string literals, identifying configuration values, and tracing symbol usage across a codebase.
Inputpattern (string — regex), optional: path (directory to search in), include (file glob filter, e.g. *.py).
OutputList of matches, each with: file path, line number, and the matching line content.
Side EffectsNone — strictly read-only.
Key LimitationPattern-based, not semantic — it matches text, not meaning. Cannot understand code structure (e.g., won't distinguish between a function definition and a comment mentioning the function name). Results can be noisy for common patterns.

Glob (File Path Matcher)

Definition: Returns a list of file paths matching a given glob pattern.

AttributeDetails
Primary Use CaseDiscovering project structure, finding files by extension or naming convention, locating configuration files, and scoping subsequent tool calls.
Inputpattern (string — glob pattern, e.g. src/**/*.ts, **/README.md).
OutputA flat list of file paths that match the pattern.
Side EffectsNone — strictly read-only.
Key LimitationReturns paths only, not file contents. Glob syntax is different from regex — * matches within a directory, ** matches recursively across directories. Cannot filter by file content.

Master Comparison Table

Tool Purpose Input Output Read-Only? Key Limitation
Read View file contents File path (+line range) File text with line numbers ✓ Yes No execution; binary files garbled
Write Create/overwrite files File path + full content Write confirmation ✗ No Replaces entire file; no partial writes
Edit Surgical file modifications File path + old_string + new_string Edit confirmation + context ✗ No old_string must match exactly once
Bash Execute shell commands Shell command string stdout + stderr + exit code ✗ No Stateful; side effects; security-sensitive
Grep Search file contents by pattern Regex pattern (+path +include filter) Matching lines + file paths + line numbers ✓ Yes Text matching only; not semantic
Glob Find files by path pattern Glob pattern List of matching file paths ✓ Yes Paths only; no content inspection

Side Effects Spectrum

Exam Strategy — 11.1 Tool Overview
Question Type: MCQ (identify the tool from a description) / True-False
Common Traps: ① Confusing Write (full overwrite) with Edit (surgical replace).
② Thinking Grep returns file paths only (that's Glob).
③ Assuming all tools have side effects (Read, Grep, Glob are read-only).
Answer Approach: For "which tool" questions: first classify the task as read vs. write vs. execute, then match to the tool's specific function.
Memory Hook: "RWEB-GG" = Read, Write, Edit, Bash, Grep, Glob — the six built-in tools, ordered from least to most powerful in terms of side effects.
Sample Question

"An agent needs to view the first 50 lines of a configuration file to determine the logging level. Which tool should it use?"

A) Bash (head -50 config.yaml)   B) Read (with line range)   C) Grep (search for 'log')   D) Glob

Answer: B

Read with offset/limit is the correct choice. While Bash with head would technically work, Read is the purpose-built tool for viewing file contents — it's read-only, has no side effects, and returns line numbers. Always prefer the most specific, least-powerful tool that gets the job done.

11.2 Selection Criteria: Choosing the Right Built-In Tool

Choosing the correct tool is not about capability — Bash can technically do everything. It's about precision, safety, and predictability. The exam tests your ability to select the most appropriate tool, which is always the most specific tool that satisfies the requirement with the fewest side effects.

Decision Factors

FactorQuestion to AskGuides You Toward
Task TypeAm I reading, writing, searching, or executing?Read/Grep/Glob vs. Write/Edit vs. Bash
ScopeAm I operating on one file, many files, or the system?Read/Edit (single file) vs. Grep/Glob (multi-file) vs. Bash (system)
Side EffectsDoes this operation modify anything?Read-only tools (Read, Grep, Glob) vs. mutating tools (Write, Edit, Bash)
PrecisionDo I need surgical accuracy or broad results?Edit (precise) vs. Write (whole file) vs. Bash (arbitrary)
StatefulnessDoes this depend on prior command state (cwd, env vars)?Bash (stateful) vs. all others (stateless per call)

Decision Flowchart

"When NOT to Use" Guide

Tool❌ Do NOT Use When…✅ Use This Instead
Read You only need to check if a pattern exists in a file (don't read the whole thing) Grep — pattern search is more efficient
Write You only need to change a few lines in an existing file Edit — surgical edits preserve the rest of the file
Edit The file doesn't exist yet (Edit requires an existing file to modify) Write — create the file first, then Edit if needed later
Bash A dedicated tool exists for the operation (reading files, searching, etc.) Use the dedicated tool — Bash is the fallback, not the default
Grep You need to find files by name/extension, not by content Glob — path-based matching is Glob's specialty
Glob You need to find files containing a specific string or pattern Grep — content search across multiple files

Exam Strategy — 11.2 Selection Criteria
Question Type: Scenario-Based MCQ (given a task, pick the tool)
Common Traps: ① Using Bash (cat file) when Read is the correct answer — Bash "works" but isn't the best choice.
② Using Write to "update" a file when only a small change is needed — Edit is more appropriate.
③ Confusing Grep (content search) with Glob (path search) — the names aren't intuitive for everyone.
Answer Approach: Three-step method: ① Classify the task (read / write / search / execute) → ② Scope it (single file / multi-file / system) → ③ Minimize side effects (pick the least-powerful tool that works).
Memory Hook: "Least Power Principle" — always escalate from read-only → targeted edit → full write → shell. The exam rewards the most specific tool, never the most powerful.
Sample Question

"An agent needs to check if a config value exists across 200 YAML files without modifying anything. Which built-in tool is MOST appropriate?"

A) Read each file and scan for the value   B) Bash (grep -r "value" *.yaml)   C) Grep   D) Glob

Answer: C

Grep is purpose-built for multi-file pattern search. Reading all 200 files wastes context tokens. Bash's grep would work but the built-in Grep tool is preferred (better integration, no side effects). Glob only returns paths, not content.

11.3 Combining Built-In Tools for Codebase Exploration

The true power of built-in tools emerges when they are composed into multi-step workflows. Each tool's output can inform or scope the next tool's input, creating efficient exploration and modification pipelines. Understanding these composition patterns is critical for the exam.

Workflow 1: "Find → Read → Edit" (Targeted Bug Fix)

Scenario: A bug report says the calculateDiscount() function uses the wrong rounding logic. Fix it.

Find → Read → Edit Pipeline
1
Grep Locate the function definition

Search for def calculateDiscount or function calculateDiscount across the codebase to find which file and line number contains the function.

2
Read View the function in context

Read the file at the identified path, focusing on the line range around the function to understand the current logic and surrounding code.

3
Edit Apply the surgical fix

Use old_string (the broken rounding line) → new_string (the corrected logic) to fix just the problematic code.

PSEUDOCODE
// Step 1: Grep — find the function
Grep(pattern="def calculateDiscount", include="*.py")
// → Result: src/pricing/discount.py:42

// Step 2: Read — view the function
Read(file_path="src/pricing/discount.py", offset=40, limit=60)
// → Returns lines 40-60, showing the full function body

// Step 3: Edit — fix the rounding
Edit(
  file_path="src/pricing/discount.py",
  old_string="return math.floor(price * discount_rate)",
  new_string="return round(price * discount_rate, 2)"
)
💡
Handoff Point

Grep's output (file path + line number) directly informs Read's input (which file and line range to view). Read's output (the actual code) informs Edit's old_string parameter. Each tool receives context from the previous step.

Workflow 2: "Glob → Grep → Read" (Dependency Audit)

Scenario: Audit the project to find all files that import a deprecated library (legacy_auth) and understand how each uses it.

Glob → Grep → Read Pipeline
1
Glob Discover all Python files

Use **/*.py to get a complete list of Python files in the project. This scopes the search space.

2
Grep Find files importing the deprecated library

Search for import legacy_auth or from legacy_auth across the identified Python files.

3
Read Deep-dive into each affected file

For each file that imports the deprecated library, read the relevant sections to understand the usage pattern and plan the migration.

PSEUDOCODE
// Step 1: Glob — discover all Python files
Glob(pattern="**/*.py")
// → Result: [src/auth/login.py, src/api/middleware.py, tests/test_auth.py, ...]

// Step 2: Grep — find deprecated imports
Grep(pattern="from legacy_auth|import legacy_auth", include="*.py")
// → Result:
//   src/auth/login.py:3:  from legacy_auth import verify_token
//   src/api/middleware.py:7:  import legacy_auth

// Step 3: Read — understand usage in each file
Read(file_path="src/auth/login.py")
Read(file_path="src/api/middleware.py")

Workflow 3: "Grep → Read → Edit → Bash" (Rename and Verify)

Scenario: Rename a function getUserData to fetchUserProfile across the codebase, then run tests to verify nothing broke.

Grep → Read → Edit → Bash Pipeline
1
Grep Find all occurrences

Locate every reference to getUserData across all source files — definitions, call sites, imports, and tests.

2
Read Verify context at each location

Read surrounding code at each occurrence to confirm it's a true reference (not a comment, string, or different scope) before editing.

3
Edit Rename at each location

Apply Edit with old_string="getUserData" → new_string="fetchUserProfile" in each file, ensuring unique matches.

4
Bash Run the test suite

Execute npm test or pytest to verify the rename didn't break anything. Check for compilation errors and test failures.

PSEUDOCODE
// Step 1: Find all references
Grep(pattern="getUserData", include="*.ts")
// → src/services/user.ts:15 (definition)
//   src/api/routes.ts:42 (call site)
//   src/api/routes.ts:87 (call site)
//   tests/user.test.ts:12 (test)

// Step 2: Verify each (Read the relevant lines)
Read("src/services/user.ts", offset=13, limit=20)
Read("src/api/routes.ts", offset=40, limit=50)

// Step 3: Edit each file (multiple Edit calls)
Edit("src/services/user.ts",
  old_string="export async function getUserData(",
  new_string="export async function fetchUserProfile(")
Edit("src/api/routes.ts",
  old_string="const data = await getUserData(userId)",
  new_string="const data = await fetchUserProfile(userId)")
// ... repeat for each occurrence

// Step 4: Verify with tests
Bash(command="npm test")

Pitfalls & Anti-Patterns

🔴
Anti-Pattern: "Bash Everything"

Using Bash("cat file.py") instead of Read("file.py"), or Bash("grep pattern *.py") instead of Grep("pattern"). While functional, this bypasses the safety and integration benefits of dedicated tools. The exam will penalize this approach.

🔴
Anti-Pattern: "Write-for-Edit"

Reading an entire file, modifying one line in the string, then using Write to replace the whole file. This is fragile — if the file was modified between the Read and Write, your changes will silently overwrite the intervening changes. Use Edit for targeted modifications.

🔴
Anti-Pattern: "Blind Edit"

Calling Edit without first using Read to verify the current state of the file. The old_string might not match due to prior changes, different formatting, or incorrect assumptions. Always Read before Edit.

⚠️
Anti-Pattern: "Glob Without Follow-Up"

Using Glob to find files but then not doing anything with the results. Glob is a scoping tool — its output is meant to feed into Grep, Read, or other tools. By itself, a file listing is rarely the answer.

Exam Strategy — 11.3 Combining Tools
Question Type: Scenario-Based (order the steps / identify the workflow)
Common Traps: ① Skipping the Read step before Edit (blind editing).
② Using Write when multiple Edit calls would be safer.
③ Not verifying changes with Bash (test execution) after modifications.
Answer Approach: Trace the data flow: What information does each step produce? and What does the next step need as input? The correct workflow has clear handoff points.
Memory Hook: "Scout → Study → Strike → Verify" = Grep/Glob (find) → Read (understand) → Edit/Write (change) → Bash (confirm). This is the canonical 4-phase workflow.
Sample Question

"An agent needs to update the API version string from 'v2.1' to 'v3.0' across all TypeScript files, then verify the build succeeds. What is the correct sequence?"

A) Edit → Bash   B) Grep → Edit → Bash   C) Grep → Read → Edit → Bash   D) Glob → Write → Bash

Answer: C

The correct workflow is: Grep (find all occurrences of 'v2.1' in *.ts files) → Read (verify each occurrence is a real API version, not a comment or unrelated string) → Edit (replace 'v2.1' → 'v3.0' at each location) → Bash (run the build/tests to verify). Skipping Read (option B) risks blind edits; Glob + Write (option D) is the wrong tool combination.

11.4 The Explore Subagent for Verbose Discovery

The Explore subagent is a specialized delegation mechanism in Claude Code that allows the primary agent to spawn a lightweight subagent for verbose, exploratory tasks — reading many files, searching broadly, and building a holistic understanding of a codebase — without consuming the primary agent's context window.

What Is the Explore Subagent?

When Claude Code encounters a task that requires extensive codebase exploration (e.g., "understand how authentication works in this project"), it can delegate that exploration to a subagent. This subagent:

  • Has access to the same built-in tools (Read, Grep, Glob — read-only tools only)
  • Operates in its own context window, so reading 20+ files doesn't consume the parent's tokens
  • Returns a synthesized summary to the parent agent, not the raw file contents
  • Cannot modify files — it is a read-only exploration agent
  • Is useful when the agent doesn't know where to look or what to look for yet

When to Use Explore vs. Direct Tool Calls

FactorDirect Tool Calls (Grep + Glob + Read)Explore Subagent
Use When You know exactly what you're looking for — a specific function, variable, file, or pattern You need to understand something broadly — how a system works, what a module does, how components connect
Scope Narrow: 1–5 files, specific patterns Wide: many files, exploratory, open-ended
Context Cost Every file read and search result consumes tokens in the main context window Only the summary comes back — raw exploration stays in the subagent's context
Speed Faster for targeted lookups — no subagent overhead Slightly slower (subagent initialization), but saves tokens on broad exploration
Modification Can chain into Edit/Write/Bash after reading Read-only — cannot modify files. Returns knowledge for the parent to act on
Example "Find where processPayment is defined" "Map the authentication flow from login to session management"
ℹ️
Key Insight: Context Window Efficiency

The Explore subagent's primary advantage is context window management. If understanding a feature requires reading 15 files, doing so directly would consume thousands of tokens. The subagent reads all 15, synthesizes the understanding, and returns a concise summary — perhaps 200 tokens — to the parent.

Worked Example: Exploring an Authentication System

Explore Subagent — Authentication Audit
1
Parent agent dispatches the Explore subagent

Task: "Explore the authentication and authorization system. Identify: entry points, middleware, token handling, session management, and any security concerns."

2
Glob Subagent discovers the project structure

**/auth*, **/middleware*, **/session* — identifies relevant files.

3
Grep Subagent searches for key patterns

Searches for jwt, session, authenticate, authorize, token across the codebase.

4
Read Subagent reads 12+ files in its own context

Reads auth controllers, middleware, models, config — building a complete picture without burdening the parent's context.

5
Subagent returns a synthesized summary

A structured report: auth flow diagram, key files, middleware chain, token lifecycle, identified concerns. Parent receives this compact summary.

CONCEPTUAL INVOCATION
// Parent agent dispatches exploration
dispatch_agent(
  task="Explore the authentication system in this project. "
     + "Map: entry points, middleware, token handling, sessions. "
     + "Identify security concerns.",
  tools=["Read", "Grep", "Glob"]  // read-only tools only
)
// → Returns: synthesized summary (~200 tokens)
// instead of raw content from 12+ files (~5000+ tokens)
Exam Strategy — 11.4 Explore Subagent
Question Type: Scenario-Based / True-False (when to delegate, what the subagent can/cannot do)
Common Traps: ① Thinking the Explore subagent can modify files (it cannot — read-only).
② Using Explore for a simple, targeted lookup that Grep handles in one call.
③ Forgetting that the subagent has its own context window — that's the whole point.
Answer Approach: Ask: "Is this exploration broad and open-ended, or narrow and targeted?" Broad → Explore. Narrow → direct Grep/Read. Also ask: "Will reading all this content blow up my context window?" If yes → Explore.
Memory Hook: "Explore = Scout, not Soldier" — it gathers intelligence (read-only) and reports back, but never fights (no modifications). Think of it as sending a reconnaissance drone.
Sample Question

"True or False: The Explore subagent can use the Edit tool to fix bugs it discovers during codebase exploration."

Answer: False

The Explore subagent is strictly read-only. It can use Read, Grep, and Glob to explore the codebase, but it cannot use Edit, Write, or Bash. If it finds a bug, it reports the finding back to the parent agent, which then decides how to act on it.

11.5 Hands-On: Navigating a Large Codebase with Built-In Tools

This section walks through a realistic end-to-end scenario where an agent navigates an unfamiliar 50,000-line microservices project. At each step, we explain the reasoning behind the tool choice — the same reasoning the exam expects you to demonstrate.

Scenario Setup

📁
Project: E-Commerce Order Service

A TypeScript microservice with ~50,000 lines across 200+ files. The task: "The /orders/refund endpoint is returning 500 errors in production. Diagnose and fix the issue."

Phase 1: Orientation — Understanding the Project

Reasoning: "I've never seen this codebase. Before debugging, I need to understand the project structure, entry points, and how the code is organized."

STEP 1 — GLOB
// Discover the top-level project structure
Glob(pattern="*")
// → [src/, tests/, package.json, tsconfig.json, docker-compose.yml, README.md, ...]

// Drill into the source directory
Glob(pattern="src/**/*.ts")
// → [src/index.ts, src/routes/orders.ts, src/routes/products.ts,
//    src/controllers/orderController.ts, src/services/refundService.ts,
//    src/models/order.ts, src/middleware/auth.ts, ...]

Tool choice rationale: Glob is the right starting tool because we need to understand the file structure, not file contents. It's read-only and returns paths quickly.

Phase 2: Targeting — Finding the Relevant Code

Reasoning: "The bug is in the /orders/refund endpoint. I need to trace from the route definition to the handler logic."

STEP 2 — GREP
// Find the route definition
Grep(pattern="/orders/refund|orders.*refund", include="*.ts")
// → src/routes/orders.ts:47:  router.post('/orders/refund', orderController.processRefund)
//   src/controllers/orderController.ts:89:  async processRefund(req, res) {
//   tests/orders.test.ts:156:  describe('/orders/refund', () => {

Tool choice rationale: Grep searches file contents across the entire codebase using a regex pattern. We know the string we're looking for (/orders/refund), making this a targeted content search — exactly what Grep excels at.

Phase 3: Deep Dive — Understanding the Code

Reasoning: "I found the controller method at line 89 in orderController.ts. Now I need to read the actual implementation to understand the logic."

STEP 3 — READ
// Read the controller method
Read(file_path="src/controllers/orderController.ts", offset=85, limit=130)
// → Shows the processRefund method:
//   89:  async processRefund(req: Request, res: Response) {
//   90:    const { orderId, reason } = req.body;
//   91:    const order = await this.orderService.getOrder(orderId);
//   92:    const refundResult = await this.refundService.process(order, reason);
//   93:    ...
//   95:  }

// Follow the chain — read the refund service
Read(file_path="src/services/refundService.ts")
// → Reveals the full refund logic, including a call to
//   an external payment API with error handling

Tool choice rationale: Read with line-range parameters lets us view exactly the function body without wasting context on the entire 500-line controller file. We read the controller first, then follow the call chain to the service layer.

Phase 4: Root Cause — Identifying the Bug

Reasoning: "In the refund service, I notice the error handler catches errors but re-throws without the correct status code. Let me also check the error logs with the test file."

STEP 4 — GREP + READ
// Search for error handling patterns in the refund service
Grep(pattern="catch|throw|Error", path="src/services/refundService.ts")
// → Line 34: } catch (error) {
//   Line 35:   throw new Error(error.message);  // ← BUG: loses status code!

// Read the test file to understand expected behavior
Read(file_path="tests/orders.test.ts", offset=156, limit=200)
// → Tests expect a RefundError with statusCode property

Phase 5: Fix — Applying the Correction

Reasoning: "The bug is clear: throw new Error(error.message) discards the original error's status code. I need to preserve it."

STEP 5 — EDIT
Edit(
  file_path="src/services/refundService.ts",
  old_string="    throw new Error(error.message);",
  new_string="    throw new RefundError(error.message, error.statusCode || 500);"
)

Tool choice rationale: Edit is the correct tool because we're making a surgical, single-line change to an existing file. The old_string is unique within the file. Using Write would require rewriting the entire service file — unnecessary and risky.

Phase 6: Verification — Confirming the Fix

Reasoning: "The fix is applied. Now I need to run tests and verify the build still passes."

STEP 6 — BASH
// Run the specific test suite
Bash(command="npx jest tests/orders.test.ts --verbose")
// → ✓ /orders/refund returns 400 for invalid order (45ms)
//   ✓ /orders/refund returns 200 for valid refund (82ms)
//   ✓ /orders/refund preserves error status codes (23ms)
//   All 12 tests passed.

// Run the full build to check for type errors
Bash(command="npx tsc --noEmit")
// → No errors.

Tool choice rationale: Bash is the only tool that can execute programs. Running tests and builds requires shell access — this is exactly what Bash is for.

Complete Workflow Summary

✅ Key Takeaways from the Walkthrough

  • Always start with orientation — Glob to understand the structure before diving into code
  • Narrow before deepening — use Grep to find relevant files, then Read to understand them
  • Read before editing — never Edit blind; verify the current state of the code first
  • Use line ranges — Read with offset/limit avoids wasting context on irrelevant code
  • Edit for surgical changes — one-line bug fixes should use Edit, not Write
  • Bash for verification only — in this workflow, Bash is the last step, not a substitute for dedicated tools
  • Follow the call chain — trace from route → controller → service to find the actual bug location
  • Each tool feeds the next — Glob's output scopes Grep, Grep's output targets Read, Read's output informs Edit

Answer: C

Option A (Edit without reading) is a "blind edit" anti-pattern. Option B uses Bash when Read is the dedicated tool. Option D (Write) would overwrite the entire file.

✅ Chapter Summary — 10-Bullet Master Recap

  1. Six built-in tools — Read, Write, Edit, Bash, Grep, Glob — provide Claude with filesystem and shell access in agentic environments. Three are read-only (Read, Grep, Glob) and three are mutating (Write, Edit, Bash).
  2. Read views file contents (optionally by line range); Write creates or fully overwrites files; Edit makes surgical search-and-replace changes with exact-match requirements.
  3. Bash executes shell commands in a persistent, stateful session — use it for tests, builds, git, and packages, never as a substitute for dedicated tools.
  4. Grep searches file contents by regex pattern; Glob searches file paths by glob pattern. They are complementary, not interchangeable.
  5. The Principle of Least Privilege governs tool selection: always choose the most specific, least-powerful tool that satisfies the requirement. Escalation order: Read/Grep/Glob → Edit → Write → Bash.
  6. Edit's uniqueness constraint is its defining behavior: old_string must match exactly once. Include surrounding context lines to ensure uniqueness.
  7. The canonical workflow is Orient → Target → Understand → Fix → Verify: Glob (structure) → Grep (locate) → Read (comprehend) → Edit (change) → Bash (test).
  8. The Explore subagent delegates verbose, read-only exploration to a separate context window — ideal for broad codebase understanding without consuming the parent's tokens.
  9. Key anti-patterns: "Bash everything," "Write-for-Edit," "Blind Edit," and "Glob without follow-up." Recognizing these is a frequent exam topic.
  10. Tool outputs chain naturally: Glob scopes Grep, Grep targets Read, Read informs Edit, Bash verifies Edit. Understanding this data flow is essential for scenario-based questions.

⚡ Tips & Tricks Panel

1️⃣
Read with Line Ranges Saves Tokens

In a 2,000-line file, reading lines 100–130 uses ~30 lines of context. Reading the whole file uses ~2,000 lines. Always scope your reads after Grep gives you a line number.

2️⃣
Edit's old_string Should Include Indentation

Whitespace is part of the match. If the code is indented with 4 spaces, your old_string must include those spaces. Copy-paste from Read output is the safest approach.

3️⃣
Grep's Include Filter Is Your Best Friend

Always use the include parameter to limit searches to relevant file types. Grep("TODO", include="*.py") is far more efficient than searching all files.

4️⃣
Glob Before Grep for Unknown Projects

In an unfamiliar codebase, start with Glob("*") and Glob("src/**") to understand the structure. Then use Grep to search within the relevant directories only.

5️⃣
Bash State Persists — Use It

After Bash("cd src && npm test"), the working directory remains src/ for subsequent Bash calls. You can cd once and run multiple commands in sequence.

6️⃣
Use Grep to Pre-Verify Edit Uniqueness

Before calling Edit, run Grep("your_old_string", path="the_file"). If it returns more than one match, you need to add more context to your old_string to make it unique.

7️⃣
Write Is for New Files and Complete Rewrites Only

The only valid uses for Write: (1) creating a file that doesn't exist, (2) completely replacing a file's content when >60% changes. Everything else should be Edit.

8️⃣
Explore Subagent ≠ "Read All Files"

The Explore subagent's value isn't just reading — it's synthesizing. It reads many files and returns a structured understanding. Direct multi-file reads dump raw content into your context; Explore returns distilled knowledge.

🎯 Mock Exam — 5 Scenario-Based Questions

Question 1 of 5

An agent is tasked with finding all files in a React project that contain unused imports. The agent should first find all .tsx files, then search for the pattern import.*unused within them. Which tool sequence is most appropriate?

A) Bash("find . -name '*.tsx'") → Bash("grep 'import.*unused' *.tsx")
B) Glob("**/*.tsx") → Grep("import.*unused", include="*.tsx")
C) Grep("import.*unused") → Read(each matched file)
D) Read(each .tsx file) → manually scan for unused imports

Answer: B

Glob discovers file paths by pattern; Grep searches content by regex. This is the correct pairing of path-search → content-search. Option A uses Bash for both, violating the Principle of Least Privilege. Option C skips the file discovery step (though Grep with include already handles this, making Glob optional — B is still more methodical). Option D is wildly inefficient.

Question 2 of 5

An agent needs to change the database port from 5432 to 5433 in a config file. The string 5432 appears in three places in the file: as the port value, in a comment, and in a connection string URL. How should the agent proceed?

A) Use Edit(old_string="5432", new_string="5433")
B) Use Write to replace the entire file with the port updated everywhere
C) Use Read to view the file, then Edit with enough context to match only the port declaration
D) Use Bash("sed -i 's/5432/5433/g' config.yaml")

Answer: C

Since 5432 appears three times, a simple Edit with just old_string="5432" will fail (multiple matches violate the uniqueness constraint). The correct approach: Read the file to see the context around each occurrence, then Edit with a longer old_string that includes surrounding context to uniquely identify the port declaration (e.g., old_string="port: 5432"). Option D blindly replaces all occurrences, which would break the connection string URL and modify the comment.

Question 3 of 5

True or False: The Explore subagent is the preferred approach when an agent needs to find the definition of a single function called validateInput in a known Python project.

Answer: False

The Explore subagent is designed for broad, open-ended exploration — not targeted lookups. Finding a single function definition is a narrow, targeted task perfectly suited for Grep(pattern="def validateInput", include="*.py"). Using the Explore subagent here adds unnecessary overhead (subagent initialization) and is slower than a direct Grep call.

Question 4 of 5

An agent is working in a large monorepo and needs to understand how the billing module interacts with the user module, the payment gateway, and the notification service. This requires reading 20+ files across 4 directories. What is the best approach?

A) Use Glob + Grep + Read to read all 20+ files directly
B) Use the Explore subagent to investigate the billing module's interactions
C) Use Bash to run tree and cat on all relevant files
D) Use Write to create a summary file, then Read it

Answer: B

This is exactly the Explore subagent's sweet spot: broad, multi-file, open-ended exploration across multiple modules. Reading 20+ files directly (option A) would overwhelm the parent's context window. The Explore subagent reads all the files in its own context and returns a synthesized summary of the billing module's interactions. Option C uses Bash when dedicated tools exist. Option D makes no sense — you can't write a summary before understanding the code.

Question 5 of 5

An agent has just finished renaming a function across 8 files using Edit. What should the agent do immediately after completing the edits?

A) Use Grep to verify the old function name no longer appears anywhere
B) Use Bash to run the test suite
C) Both A and B — Grep to verify the rename, then Bash to run tests
D) Nothing — the Edit tool guarantees correctness

Answer: C

After a multi-file rename, both verification steps are important. Grep confirms the old name no longer appears (catches missed occurrences — perhaps in files you didn't know about). Bash runs the test suite to catch any runtime issues the rename may have introduced (e.g., the function was referenced dynamically via a string). Edit guarantees each individual edit was applied correctly, but it does not guarantee you found all occurrences or that the codebase still works.
