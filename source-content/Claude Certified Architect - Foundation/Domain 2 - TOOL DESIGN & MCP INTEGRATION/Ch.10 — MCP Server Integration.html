10.1   Understanding Model Context Protocol (MCP)

📘 Core Concept

MCP (Model Context Protocol) is an open-source standard — created by Anthropic and now industry-adopted — that provides a universal interface for connecting AI applications to external systems (tools, data sources, workflows). It uses JSON-RPC 2.0 messages over stateful connections.

Why it exists: Before MCP, every AI-tool integration required a custom connector. MCP is the "USB-C for AI" — one protocol to replace N×M custom integrations with a standardized plug-in architecture.

Role in architecture: MCP defines the outer boundary of Claude's capability surface. Without MCP, Claude can only reason over text in its context window. With MCP, Claude gains access to live databases, APIs, file systems, and services.

🧠 Chain-of-Thought Breakdown

  1. First, an MCP Host (e.g., Claude Desktop, Claude Code, an IDE) starts up and reads its MCP configuration.
  2. Then, for each configured server, the host instantiates one MCP Client — a dedicated connector.
  3. Each client establishes a stateful connection to its MCP Server over a transport layer (stdio for local processes, Streamable HTTP for remote services).
  4. During discovery, the client sends a server/discover request (JSON-RPC). The server responds with its supported protocol versions, capabilities (tools, resources, prompts), and identity.
  5. At runtime, when Claude's reasoning determines it needs external data or action, it issues tool calls / resource reads via the appropriate MCP client, which routes them to the correct server.
  6. Results flow back through the same channel, enriching Claude's context for continued reasoning.

🔑 Key Takeaways
  • MCP follows a Host → Client → Server three-tier architecture
  • The protocol uses JSON-RPC 2.0 over stateful connections
  • Two transports: stdio (local) and Streamable HTTP (remote)
  • Discovery happens via server/discover — returns versions, capabilities, identity
  • MCP is protocol-only — it does not dictate how the host uses the LLM or manages context
💡 Tips & Tricks
  • Mnemonic — "HCS": Host Creates (multiple) clients; each Client Serves one Server
  • Pitfall: Don't confuse "MCP Server" with "runs on a remote server." Local stdio-based MCP servers run as subprocesses on the same machine.
  • Edge case: The server/discover request is optional — clients MAY send any request directly and handle version errors. But exam questions treat discovery as the "correct first step."
  • Sampling is deprecated (protocol version 2026-07-28). New implementations should integrate directly with LLM provider APIs instead.

10.2   MCP Tools vs MCP Resources: Actions vs Content Catalogs

📘 Core Concept

Tools are executable actions the AI model can invoke autonomously during reasoning (e.g., query a database, create an issue, send a message). Resources are read-only data sources the host application loads to provide context (e.g., file contents, database schemas, configuration).

Why the distinction: The critical design question is who controls invocation. Tools = model-controlled (the AI decides when to call). Resources = application-controlled (the host decides when to fetch). Getting this wrong causes either unnecessary model calls for static data, or an AI that can't act autonomously when it should.

Role in architecture: Together with Prompts (user-controlled templates), Tools and Resources form MCP's three server primitives — the capability surface a server exposes to clients.

🧠 Chain-of-Thought Breakdown

  1. First, ask: "Does this functionality perform an action or provide data?"
  2. If it performs an action (write, create, execute, send) → it's a Tool. Tools can have side effects.
  3. If it provides data (read-only context) → it's a Resource. Resources are identified by URIs and are side-effect-free.
  4. Then ask: "Who should control when this is used?" Model decides → Tool. Application decides → Resource. User explicitly picks → Prompt.
  5. The model sees tool descriptions + input schemas and decides autonomously when calling a tool would help.
  6. Resources are fetched by the host before or during conversation to enrich context — the model doesn't "call" them.

🔑 Key Takeaways
  • Tools = model-controlled actions; Resources = application-controlled data; Prompts = user-controlled templates
  • Tools can have side effects; Resources are always read-only
  • Resources use URI addressing (config://project, db://schema)
  • Discovery methods: tools/list, resources/list, prompts/list
  • The decision framework: "Who controls invocation?" is the #1 question
💡 Tips & Tricks
  • Mnemonic — "TAP": Tools (AI), App-Resources, Prompts (User) — ordered by autonomy level
  • Common pitfall: Implementing a read-only data fetch as a Tool instead of a Resource. This wastes model reasoning and token budget on something the host should load automatically.
  • Edge case: A search_docs function looks like it "just reads data" — but because the model decides when and what to search, it's correctly a Tool, not a Resource.
  • Resource Templates allow dynamic URIs (e.g., users://{userId}/profile) — but the application still controls when they're fetched.

10.3   The .mcp.json Configuration File

📘 Core Concept

.mcp.json is the project-scoped configuration file placed at the repository root. It declaratively defines which MCP servers a project uses, their transport types, commands, arguments, environment variables, and headers. It is the "configuration as code" artifact for MCP — version-controllable, shareable, and reviewable.

Why it exists: Without it, every developer must manually claude mcp add each server. With .mcp.json, cloning a repo brings the entire tool configuration along. Teammates get prompted to approve the servers automatically.

Role in architecture: .mcp.json is the bridge between human-authored config and the MCP runtime. Claude Code reads it at session start, instantiates clients, and connects to each defined server.

🧠 Chain-of-Thought Breakdown

  1. First, a developer adds a server with claude mcp add --scope project, which writes to .mcp.json at the repo root.
  2. Alternatively, developers can hand-edit the JSON file directly.
  3. The file contains a top-level "mcpServers" object. Each key is the server alias.
  4. Each server entry specifies: type (transport), plus transport-specific fields (command/args for stdio, url for HTTP).
  5. When a teammate clones the repo, Claude Code detects the .mcp.json and prompts for approval before starting any servers — a security gate.
  6. Changes to .mcp.json require a session restart to take effect — the file is read once at startup.

📊 Annotated Configuration

// .mcp.json — placed at project root, committed to version control
{
  "mcpServers": {
    "filesystem": {            // ← Server alias (your chosen name)
      "type": "stdio",          // ← Transport: "stdio" | "http" | "streamable-http"
      "command": "npx",         // ← Executable to run
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/project"],
      "env": {                   // ← Environment variables passed to the process
        "NODE_ENV": "production"
      }
    },
    "sentry": {                 // ← Remote HTTP server
      "type": "http",
      "url": "https://mcp.sentry.dev/sse",
      "headers": {              // ← Custom headers (auth tokens, etc.)
        "Authorization": "Bearer ${SENTRY_TOKEN}"  // ← Env var expansion!
      }
    }
  }
}

File Structure Rules

RuleDetail
LocationProject root (.mcp.json), same level as .git/
type fieldMandatory. Without it, Claude Code defaults to stdio and may silently fail for HTTP servers.
streamable-httpAlias for http — the spec's official name. Claude Code accepts both.
Approval gateOn first load, users must approve project-scoped servers before they start.

🔑 Key Takeaways
  • .mcp.json lives at project root and is committed to version control
  • Top-level key: "mcpServers" — each child key is a server alias
  • The type field is required — omitting it causes silent failures for HTTP servers
  • Changes require a session restart; the file is read once at startup
  • Never commit raw secrets — use ${VAR} environment variable expansion (see 10.4)
💡 Tips & Tricks
  • Common pitfall: Forgetting the type field on an HTTP server. The entry gets parsed as stdio, the URL is ignored, and the server silently fails with "connection error."
  • Pitfall #2: Editing .mcp.json and expecting changes immediately — you must restart the Claude Code session.
  • If servers don't appear after editing, open /mcp panel and look for parse warnings. Also check if you rejected the approval prompt earlier — reset with claude mcp reset-project-choices.
  • Correct file names: .mcp.json (project root) or ~/.claude.json (user/local). NOT ~/.claude/mcp.json, ~/.claude/.mcp.json, or %APPDATA%\Claude\mcp.json.
🎯 Exam Strategy

Question Type: Code-reading MCQ (identify what's wrong in a config)

Trigger phrase: "Given the following .mcp.json…" / "Which file should contain…"

Answer direction: Look for missing type field, wrong file location, or raw secrets in config.

10.4   Environment Variable Expansion in MCP Config

📘 Core Concept

MCP configuration files support environment variable expansion using the syntax ${VAR_NAME} or ${VAR_NAME:-default_value}. This enables storing secrets (API keys, tokens, connection strings) in the environment rather than hardcoded in config files, keeping .mcp.json safe to commit.

Why it exists: Project-scoped config must be version-controlled, but secrets must never be committed. Env var expansion bridges this gap — the shape of the config is in the repo, the secrets are in each developer's environment.

Role in architecture: This is the security mechanism for MCP configuration. It works across command, args, env, url, and headers fields.

🧠 Chain-of-Thought Breakdown

  1. First, the developer writes ${API_KEY} in a config field instead of the raw value.
  2. At startup, Claude Code's config parser scans string values for ${...} patterns.
  3. For each match, it looks up the variable name in the process environment.
  4. If found, the value is JSON-escaped and substituted — quotes and braces in the value won't break the config structure.
  5. If not found and a default is specified (${VAR:-fallback}), the fallback is used.
  6. If not found and no default exists, the literal ${VAR} text remains — the file still loads, but the connection fails at runtime. Claude Code warns in claude mcp list.

📊 Syntax Reference

// Expansion syntax variants

"api_key": "${MY_API_KEY}"                    // ← Plain substitution
"base_url": "${API_URL:-https://api.example.com}"  // ← With default fallback
"auth": "Bearer ${TOKEN}"                     // ← Inline expansion within a string

// Works in ALL string fields:
//   command, args[], env{}, url, headers{}

// ⚠️ Unterminated placeholder "${VAR" → parse error
// ⚠️ Unset var without default → literal "${VAR}" remains → fails at connect

Complete Example

{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    },
    "db-server": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "db-mcp-server"],
      "env": {
        "DB_CONNECTION": "${DATABASE_URL}",
        "DB_POOL_SIZE": "${POOL_SIZE:-5}"
      }
    }
  }
}
🔑 Key Takeaways
  • Syntax: ${VAR} for plain substitution, ${VAR:-default} for fallback
  • Expansion works in: command, args, env, url, headers
  • Values are JSON-escaped during substitution — safe for secrets with special characters
  • Unset variables without defaults → literal text remains, connection fails at runtime
  • Unterminated ${ (no closing }) → parse error (deliberately vague to protect secrets)
💡 Tips & Tricks
  • Always use defaults for non-secret values like base URLs: ${API_URL:-https://prod.example.com}
  • Desktop app gotcha: The Claude Desktop app has no shell in its launch path, so there's no easy way to inject env vars. This pushes users toward plaintext tokens — flag this as a known limitation.
  • Debugging: If claude mcp list shows a server as failed, check for unset env vars first — it's the #1 cause of "works on my machine" issues.
  • Never commit .env files either. Use .env.example with placeholder names (no values) in the repo.
🎯 Exam Strategy

Question Type: Syntax identification / Security best-practice MCQ

Trigger phrase: "How should an API key be stored in .mcp.json…" / "What happens if the environment variable is not set…"

Answer direction: Always pick ${VAR} syntax over hardcoded values. Know the fallback syntax.

Sample Question

10.5   Project-Scoped vs User-Scoped MCP Servers

📘 Core Concept

MCP servers in Claude Code have three configuration scopes that determine visibility, storage location, and shareability. The scope controls which projects "see" a server and whether teammates get it automatically.

Why it exists: Different servers have different sharing needs. A project's database connector should travel with the repo; a personal API key integration shouldn't leak to every project; an experimental server shouldn't follow you everywhere.

Role in architecture: Scoping is the access-control model for MCP configuration. It determines the blast radius of each server definition and implements the principle of least privilege.

🧠 Chain-of-Thought Breakdown

  1. Local scope (default): Private to you in the current project. Stored in ~/.claude.json under the project's path key. Use for experiments and credential-bearing servers.
  2. Project scope: Shared with the team via version control. Written to .mcp.json at project root. Use for servers the whole team needs.
  3. User scope: Available to you across all projects. Stored in ~/.claude.json top-level mcpServers. Use for personal utilities you want everywhere.
  4. Precedence rule: When the same server name exists at multiple scopes: local > project > user > plugin > claude.ai connectors.
  5. Critical detail: The winning entry is used whole — configurations are never merged across scopes.

Scope Hierarchy Diagram

🔑 Key Takeaways
  • Three scopes: Local (default, private, per-project), Project (shared via git), User (global, private)
  • Precedence: local > project > user > plugin > claude.ai
  • Configs are never merged — the winning scope's entry is used whole
  • Scope is fixed at add-time. To change scope: remove + re-add.
  • Only .mcp.json (project scope) is shareable through version control
💡 Tips & Tricks
  • Biggest gotcha: "User-scoped" sounds restrictive/personal but is actually BROADER in reach — it loads in all projects. This is the #1 exam distractor.
  • Decision rule: Has a credential? → Local. Whole team needs it? → Project. You want it everywhere? → User.
  • "My server disappeared": Almost always a scope mismatch. Local scope is tied to the exact directory where you ran claude mcp add. If you cd elsewhere, it's gone.
  • No merge = no combining: A URL in project scope and a header in local scope for the same name will NOT combine. The local entry wins entirely, with no header from project.
🎯 Exam Strategy

Question Type: Scenario-based MCQ

Trigger phrase: "A team wants server X only for Project A, not globally…" / "available across ALL projects…"

Answer direction: "Only for this project" → project or local. "All projects for me" → user.

Distractor warning: "User-scoped" sounds personal/restrictive but is the BROADEST personal scope. "Global-scoped" and "Team-scoped" are NOT valid MCP scope terms — they're distractors.

10.6   Multi-Server Simultaneous Access

📘 Core Concept

Claude Code supports connecting to multiple MCP servers simultaneously. The host creates one MCP Client per server, each maintaining an independent connection. Claude's reasoning layer can draw on tools and resources from any connected server within a single conversation.

Why it exists: Real-world workflows require multiple data sources — a project might need a database server, a monitoring server, a file system server, and a CI/CD server all at once. Multi-server access enables this without swapping connections.

Role in architecture: This is what makes MCP composable. Servers are independent modules; the host is the orchestrator that presents a unified capability surface to the LLM.

🧠 Chain-of-Thought Breakdown

  1. First, Claude Code reads all configured servers (from all scopes) and deduplicates by name using the precedence rule.
  2. Then, it instantiates one MCP Client per surviving server and connects them in parallel.
  3. Tool search is on by default — tool definitions load on demand rather than all at once, preventing context window bloat.
  4. At runtime, when Claude needs a tool, it searches across all connected servers' tool registries.
  5. Each tool call is routed to the specific server that owns that tool — the client handles routing transparently.
  6. Claude can invoke tools from multiple servers in a single reasoning turn (e.g., read from DB server + post to Slack server).

📊 Multi-Server Topology

┌──────────────── Claude Code Host ────────────────────┐ │ │ │ Claude LLM ──► Tool Router ──┬──► Client A ──► DB Server │ │ ├──► Client B ──► GitHub │ │ ├──► Client C ──► Sentry │ │ └──► Client D ──► Playwright │ │ │ │ Tool Search: loads definitions on demand │ │ Context: tools from ALL servers available │ └───────────────────────────────────────────────────────┘
🔑 Key Takeaways
  • One MCP Client per server — connections are independent and parallel
  • Tool search is on by default — definitions load on demand, not all at startup
  • Claude can invoke tools from multiple servers in a single turn
  • Name collision: If two servers define a tool with the same name, the one from the higher-precedence server wins
  • Removing unused servers is still worthwhile — each server's tool names still load into session context
💡 Tips & Tricks
  • Naming discipline matters: Use distinct server aliases to avoid name collisions in the tool registry.
  • Performance note: stdio servers start as subprocesses — many heavy servers can slow session startup. Consider which really need to be stdio vs remote HTTP.
  • On-demand loading: Tool search means adding many servers no longer eats your context window — but each server's metadata still has a small cost.
🎯 Exam Strategy

Question Type: Architecture MCQ

Answer direction: One client per server, independent connections, tool search on demand.

10.7   Integrating MCP Servers into Claude Code

📘 Core Concept

Claude Code provides a comprehensive CLI (claude mcp) for adding, removing, inspecting, and authenticating MCP servers. Integration follows a structured workflow: add → verify → authenticate (if needed) → use. Understanding each step and the failure modes at each stage is essential.

Why it exists: The CLI abstracts away the complexity of JSON config editing, transport negotiation, and credential management. It provides guardrails, feedback, and debugging tools.

Role in architecture: The CLI is the developer's primary interface for MCP lifecycle management in Claude Code.

🧠 Chain-of-Thought Breakdown

  1. Add a server: claude mcp add [options] <name> [-- command args...]
  2. Verify connection: claude mcp list — must show ✔ Connected
  3. Authenticate (if needed): claude mcp login <name> or via /mcp panel in session
  4. Use the tools: Start a session, name the server in your prompt, approve tool calls on first use
  5. Manage: claude mcp get, claude mcp remove, claude mcp reset-project-choices

📊 CLI Command Reference

claude mcp remove <name>Remove a server (use --scope to target specific scope)

claude mcp logout <name>Clear stored OAuth tokens

🔑 Key Takeaways
  • Integration workflow: Add → Verify → Authenticate → Use
  • claude mcp add is a write receipt, not a connection test — always verify with claude mcp list
  • Two auth models: OAuth (interactive sign-in) vs static token (passed via --header)
  • The -- separator is critical for stdio servers — everything after it is the server command
  • /mcp in-session panel provides status, reconnect, and authenticate actions
💡 Tips & Tricks
  • Flag ordering trap: --env KEY=value consumes all following KEY=value pairs. If the server name comes right after --env, it's parsed as an env pair. Put another flag between them.
  • stdio first-run timeout: npx downloads packages on first run, which can exceed the 30s default timeout. Set MCP_TIMEOUT=60000 claude to increase.
  • "Failed" with a header token: Claude Code reports this as failed, NOT as "needs authentication." A failed status on a server with an Authorization header almost always means a bad token.
  • SSE transport: Deprecated but some servers still use it. Use --transport sse if an HTTP endpoint doesn't work.

10.8   Hands-On: Configuring and Using an MCP Server

📘 Core Concept

This section synthesizes all prior knowledge into a complete, end-to-end workflow for configuring and using MCP servers in Claude Code. It covers both the CLI-based approach and the config-file approach, plus troubleshooting patterns.

Why it matters: The exam tests practical knowledge. Understanding the theory is necessary but not sufficient — you must know the exact commands, file locations, and debugging steps.

🧠 End-to-End Workflow

  1. Identify the server — Remote HTTP endpoint? Local stdio package? What credentials does it need?
  2. Choose scope — Private experiment → local. Team standard → project. Personal utility → user.
  3. Add the server — CLI (claude mcp add) or hand-edit .mcp.json
  4. Verify connection — claude mcp list must show ✔ Connected
  5. Authenticate — OAuth: claude mcp login. Token: passed at add-time via --header
  6. Use in session — Name the server in your first prompt. Approve tool calls. Verify tool call carries server name.
  7. Debug if needed — Check status → check URL/command → check env vars → check scope → restart session

📊 Quick-Reference: Adding Servers

# ═══ Remote HTTP server ═══
claude mcp add --transport http --scope user sentry https://mcp.sentry.dev/sse

# ═══ Local stdio server ═══
claude mcp add playwright -- npx -y @playwright/mcp@latest

# ═══ stdio with env vars ═══
claude mcp add --env AIRTABLE_API_KEY=xxx --transport stdio airtable \
  -- npx -y airtable-mcp-server

# ═══ Verify ═══
claude mcp list              # Must show ✔ Connected
claude mcp get sentry        # Full config for one server

# ═══ Auth ═══
claude mcp login sentry      # OAuth flow
claude mcp logout sentry

# ═══ Remove ═══
claude mcp remove sentry --scope user

# ═══ Scope change (must remove + re-add) ═══
claude mcp remove explain --scope local
claude mcp add --scope user --transport http explain https://example.com/mcp

Troubleshooting Decision Tree

Problem: MCP Server Not Working │ ▼ Run claude mcp list │ ┌─────┼──────────────────────────────────────┐ ▼ ▼ ▼ No servers ✘ Failed ✔ Connected shown / Error but no tools │ │ │ ▼ ▼ ▼ Wrong For HTTP: curl -I <url> Open /mcp panel scope For stdio: run command manually Check env vars/keys or wrong Check: URL, type field, → Missing API key file path transport, -- separator is #1 cause
🔑 Key Takeaways
  • Complete workflow: Identify → Scope → Add → Verify → Auth → Use → Debug
  • The -- separator is mandatory for stdio servers with arguments
  • Scope change requires remove + re-add (cannot be changed in-place)
  • Troubleshooting order: status first → then URL/command → then env vars → then scope
  • MCP_TIMEOUT=60000 environment variable extends the 30s default startup timeout
💡 Tips & Tricks
  • Always test with claude mcp list before opening a session — it's the cheapest diagnostic.
  • "Added" ≠ "Connected": The add command is a file-write confirmation, not a connectivity test.
  • For SSH/no-browser machines: Use --no-browser with claude mcp login to get a printable auth URL.
  • Import from Desktop: claude mcp add-from-claude-desktop migrates your existing Claude Desktop MCP config.

📄 Rapid-Review Cheat Sheet

MCPModel Context Protocol — open standard for connecting AI apps to external systems via JSON-RPC 2.0
HostAI application that coordinates multiple MCP Clients (e.g., Claude Code, Claude Desktop)
ClientComponent in the Host that maintains a 1:1 connection to an MCP Server
ServerProgram that exposes tools, resources, and/or prompts to MCP Clients
ToolModel-controlled action (verb) — AI decides when to invoke. Can have side effects.
ResourceApplication-controlled data (noun) — read-only, identified by URI, no side effects.
PromptUser-controlled template — reusable message structure the user explicitly selects.
stdio transportLocal subprocess communication via stdin/stdout. Default transport. No network overhead.
Streamable HTTPRemote transport using HTTP POST + optional SSE. Supports OAuth, bearer tokens, headers.
.mcp.jsonProject-scoped config file at repo root. Declares MCP servers for version-controlled sharing.
~/.claude.jsonUser config file. Holds local (project-keyed) and user (top-level) server definitions.
${VAR}Environment variable expansion — substitutes the value, JSON-escaped. Fails at connect if unset.
${VAR:-default}Expansion with fallback — uses default if VAR is unset.
Local scopePrivate, current project only. Stored in ~/.claude.json under project key. Default scope.
Project scopeShared via git, current project. Stored in .mcp.json. Requires teammate approval.
User scopePrivate, ALL projects. Stored in ~/.claude.json top-level. Broadest personal scope.
Precedencelocal > project > user > plugin > claude.ai. Entire entry wins — no merging.
server/discoverJSON-RPC method for version negotiation and capability discovery. Optional but recommended.
Tool searchOn-demand loading of tool definitions. On by default. Prevents context window bloat.
claude mcp listShows all servers + connection status. The #1 diagnostic command.
/mcpIn-session interactive panel for status, reconnect, authenticate, and tool inspection.
ElicitationServer-initiated request for user input through the client. Replaces deprecated Sampling.

⚠️ Top 10 Exam Traps

1. "User-scoped" sounds restrictive but is the broadest personal scope — it loads in ALL projects.
2. "Global-scoped" and "Team-scoped" are NOT valid MCP scope terms — they're distractors.
3. claude mcp add does NOT verify connectivity. It's a write receipt only. Always follow with claude mcp list.
4. Omitting the type field in .mcp.json defaults to stdio — an HTTP server entry without type: "http" silently fails.
5. Resources CANNOT have side effects. Any option claiming resources can modify state is wrong.
6. Scope configs are NEVER merged. A URL from project scope + a header from local scope for the same name won't combine. The winning scope's entry is used whole.
7. "MCP Server" ≠ "remote server." Local stdio servers running on the same machine are still MCP Servers.
8. Unset env vars with no default → literal ${VAR} text remains. The file loads successfully, but the connection fails at runtime with no clear error about the variable.
9. A bad auth token shows as "Failed," NOT "Needs authentication." Claude Code only shows "Needs authentication" for servers expecting OAuth flow — a rejected header token shows as a generic failure.
10. Sampling is deprecated (protocol version 2026-07-28). Any option listing Sampling as a current client primitive is outdated.

🧩 Practice Scenario

Multi-Part Scenario

Context: Your team is building a customer support tool. You need Claude Code to:

  • Query a PostgreSQL database for ticket data (requires DATABASE_URL credential)
  • Post updates to a Slack channel (remote HTTP MCP server at https://mcp.slack.dev/sse)
  • Read the project's README and API schema for context

The team has 5 developers. The database and Slack servers should be available to all of them. Each developer has their own DATABASE_URL.

Questions

Part A (Sections 10.2, 10.5): Which MCP primitive should expose the database query capability? Which should expose the README and API schema? What scope should each server use?

Part B (Sections 10.3, 10.4): Write the .mcp.json entry for the database server. How should the DATABASE_URL be handled?

Part C (Section 10.7): A new developer clones the repo. They run claude mcp list and the database server shows ✘ Failed to connect. The Slack server shows ⏸ Pending approval. Diagnose both.

🔑 Model Answer

Part A:

  • Database query → Tool. The AI model decides when to query based on conversation context. It's an action with potential side effects (even SELECTs hit the DB).
  • README + API Schema → Resources. Read-only context data the host loads to enrich Claude's understanding. URIs like docs://readme, db://schema.
  • Scope: Both servers should be project-scoped (via .mcp.json) so all 5 developers get them automatically when cloning the repo. Individual credentials (DATABASE_URL) stay in each developer's environment, not in the config file.

Part B:

{
  "mcpServers": {
    "support-db": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@mcp/postgres-server"],
      "env": {
        "DATABASE_URL": "${DATABASE_URL}"
      }
    },
    "slack": {
      "type": "http",
      "url": "https://mcp.slack.dev/sse"
    }
  }
}

DATABASE_URL uses ${DATABASE_URL} expansion — each developer sets it in their own environment. The credential never enters version control.

Part C:

  • Database ✘ Failed: The new developer hasn't set the DATABASE_URL environment variable. The ${DATABASE_URL} placeholder resolved to the literal string, causing a connection failure. Fix: Set DATABASE_URL in their shell environment and restart the session.
  • Slack ⏸ Pending approval: This is the security gate working correctly. Project-scoped servers require approval before starting. Fix: Open the /mcp panel in a Claude Code session and approve the Slack server.
