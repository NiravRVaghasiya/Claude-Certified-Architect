Section 7.1

The Role of Tool Descriptions in Model Reasoning

This section establishes the foundational truth of tool design: the model cannot execute code, peek at implementations, or test endpoints. Its entire understanding of what a tool does, when to invoke it, and what to expect comes from the schema you provide — the name, description, and parameter definitions. Tool descriptions are not documentation for humans; they are executable reasoning context for the model.

Core Concept Summary

When Claude encounters a user message that may require tool use, it follows a multi-step internal reasoning process. First, it evaluates the user's intent. Then it scans all available tool definitions to find a match. The description field is the primary signal Claude uses to decide which tool to invoke — not the tool name, and not the parameter names alone. The description acts as a contract: it tells the model (1) what the tool does, (2) when to use it, and (3) when not to use it. Poorly written descriptions lead to incorrect tool selection, hallucinated parameters, or failure to use tools at all.

The model does not have access to the implementation behind the tool. It cannot infer behavior from code. Every assumption it makes is derived from the text you wrote. This means ambiguous or incomplete descriptions lead to ambiguous or incorrect tool calls — there is no runtime safety net.

Key Definitions

TermDefinition
Tool SchemaThe JSON object provided to Claude describing a tool's name, purpose, and input parameters. It follows JSON Schema conventions.
Tool SelectionThe model's internal reasoning step where it decides which tool (if any) to invoke based on the user's query and available schemas.
GroundingThe degree to which a model's tool-use decision is supported by explicit information in the schema, as opposed to inferred or hallucinated.
Description ContractThe implicit agreement that the description fully specifies the tool's capabilities, constraints, and appropriate usage scenarios.
Negative GuidanceExplicit instructions in a description about when not to use the tool (e.g., "Do NOT use for real-time data").

Common Misconceptions

❌ Misconception 1: "The model reads my API implementation"

Claude has zero visibility into what happens after a tool call. It cannot inspect endpoints, read source code, or observe side effects. Your description is the only interface.

❌ Misconception 2: "Tool names are enough — descriptions are optional details"

While names help, the model weights the description far more heavily for tool selection. A well-named tool with a vague description will still cause errors. Descriptions are not optional — they are the core mechanism.

❌ Misconception 3: "More tools = better capability"

Adding too many tools without clear, differentiated descriptions causes selection confusion. The model may pick the wrong tool or oscillate between similar options. Fewer, well-described tools outperform many poorly described ones.

Exam Tips

💡 Exam Tip 7.1a

If a question asks "why did the model fail to invoke the correct tool?", check the description first. In 80%+ of exam scenarios, the root cause is a missing, vague, or overlapping description — not a naming issue.

💡 Exam Tip 7.1b

Questions about "negative guidance" (telling the model when NOT to use a tool) are common. Remember: negative constraints in descriptions reduce false-positive tool calls. Look for answers that include "Do not use for…" phrasing.

Section 7.2

Writing Clear, Unambiguous Tool Descriptions

A description is not a comment. It is a precise specification that the model uses as its sole source of truth about a tool's purpose, scope, and limitations. This section covers the formula for writing descriptions that minimize ambiguity and maximize correct tool selection.

Core Concept Summary

Effective tool descriptions follow a predictable structure: they state what the tool does, what it returns, when to use it, and when not to use it. The best descriptions are written as if you're briefing a competent colleague who has never seen your codebase — specific enough to act on, concise enough to process quickly. Avoid jargon unless the model needs it, and always include boundary conditions (what the tool can't do or shouldn't be used for).

The model processes all tool descriptions simultaneously when making a selection decision. This means descriptions must be mutually differentiable — each tool should occupy a clearly distinct semantic space. If two descriptions overlap in scope, the model will struggle to choose.

The Description Formula

The 4-Part Description Formula

① WHAT it does

"Retrieves the current weather forecast for a specified city, including temperature, humidity, and 5-day outlook."

② WHAT it returns

"Returns a JSON object with fields: temp_celsius, humidity_percent, conditions, and forecast_days[]."

③ WHEN to use it

"Use when the user asks about current weather, temperature, or forecasts for a specific location."

④ WHEN NOT to use it

"Do NOT use for historical weather data — use get_historical_weather instead."

Common Misconceptions

❌ Misconception: "Shorter descriptions are always better"

While you should avoid unnecessary verbosity, omitting critical scope or boundary information to save tokens actively harms tool selection accuracy. A 2-sentence description that's vague is worse than a 4-sentence description that's precise. Aim for complete and concise, not just short.

❌ Misconception: "Parameter descriptions compensate for a weak top-level description"

The model uses the top-level description field for tool selection. Parameter descriptions only matter after the tool is chosen. If the top-level description is vague, the model might never select the tool in the first place.

Exam Tips

💡 Exam Tip 7.2a

When a question presents two tool schemas and asks "which is better?", apply the 4-part formula: does it say WHAT / RETURNS / WHEN / WHEN NOT? The answer with more of these elements is almost always correct.

💡 Exam Tip 7.2b

Look for questions about overlapping descriptions. If two tools' descriptions both say "searches for information", that overlap is the bug. The fix is always to add differentiating scope (e.g., "searches internal KB" vs. "searches the public web").

Section 7.3

Splitting vs. Consolidating Tools: Granularity Tradeoffs

One of the most consequential architectural decisions in tool design is how many tools to expose and how coarse-grained each one should be. Too many fine-grained tools causes selection confusion; too few mega-tools causes parameter overload. This section teaches you to find the right granularity.

Core Concept Summary

The granularity spectrum ranges from one-tool-per-action (maximum splitting) to one-tool-for-everything (maximum consolidation). Neither extreme is ideal. The optimal point depends on three factors: (1) how semantically distinct the actions are, (2) whether the actions share input parameters, and (3) the total number of tools in the set. Claude performs best when it has 5–20 well-differentiated tools. Beyond ~20 tools, selection accuracy degrades even with perfect descriptions.

The golden rule: split tools along intent boundaries, not implementation boundaries. If two operations serve different user intents (e.g., "create an order" vs. "cancel an order"), they should be separate tools even if they hit the same API. If two operations serve the same intent but take slightly different parameters (e.g., "search by name" vs. "search by ID"), they can often be consolidated.

Decision Matrix

✂️ Split Into Separate Tools When…

  • Actions serve different user intents (create vs. delete vs. query)
  • Actions have non-overlapping parameters
  • Actions have different side effects (read-only vs. mutating)
  • Mixing them would require a complex action_type enum
  • Users would never invoke both in the same conversational turn

🔗 Consolidate Into One Tool When…

  • Actions share most parameters
  • They represent variations of the same intent (search by name vs. ID)
  • Splitting would create near-identical descriptions
  • The total tool count is approaching the 20-tool threshold
  • A single optional parameter can differentiate the variations

Code Example — Consolidation Done Right

// Instead of 4 separate search tools, consolidate with a "search_type" param
{
  "name": "search_customers",
  "description": "Searches the customer database by name, email, or customer ID. Returns matching customer records with contact info and account status. Use when the user needs to find or look up a specific customer.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "The search term: a name, email address, or customer ID."
      },
      "search_type": {
        "type": "string",
        "enum": ["name", "email", "customer_id"],
        "description": "The type of search to perform. Defaults to 'name' if omitted."
      }
    },
    "required": ["query"]
  }
}

Common Misconceptions

❌ Misconception: "Every REST endpoint should map to one tool"

Tool design should be driven by user intent, not API structure. Two endpoints that serve the same user need (e.g., GET /users?name=X and GET /users?email=X) should often become a single tool with a search_type parameter. Conversely, one endpoint with multiple modes (GET /data?type=report vs. GET /data?type=export) may need to be split.

❌ Misconception: "More tools always means more flexibility"

There is an empirical performance cliff. Beyond ~20 tools, Claude's selection accuracy drops measurably. The solution is not to add more tools but to consolidate related tools and use parameters to differentiate.

Exam Tips

💡 Exam Tip 7.3

When a question describes a system with 25+ tools and asks "how to improve reliability", the answer is almost always consolidate related tools. Look for the option that reduces total tool count while keeping intents distinct. Also remember: read vs. write operations should almost always be separate tools — never consolidate a mutation with a query.

Section 7.4

Tool Naming Strategies to Reduce Ambiguity

While descriptions carry the primary selection weight, tool names serve as fast semantic anchors that help the model quickly narrow its search space. A good naming convention makes the tool set scannable and predictable, reducing the cognitive load on the model during selection.

Core Concept Summary

Tool names should follow a consistent verb_noun pattern that immediately signals both the action and the resource. Names like get_order_status are far more useful than orderStatus or check. Consistency is key: if one tool is create_order, the next should be cancel_order — not orderCancellation or remove_order. The model uses naming patterns to infer relationships between tools. A consistent namespace (e.g., all order tools starting with order_ or ending with _order) creates a mental grouping.

Naming Patterns

Common Misconceptions

❌ Misconception: "Name is more important than description"

The name is a heuristic shortcut. The description is the authoritative specification. If forced to choose between a perfect name with a vague description or a mediocre name with a perfect description, always optimize the description first.

❌ Misconception: "CamelCase or snake_case doesn't matter"

While the model can handle both, mixing conventions across tools in the same set degrades pattern recognition. Pick one and stick with it. Anthropic examples use snake_case — this is the safest default.

Exam Tips

💡 Exam Tip 7.4

Naming questions often present a set of 4–5 tools and ask "which naming scheme causes the least ambiguity?" The winning answer is almost always the one with: (1) consistent verb_noun pattern, (2) no synonymous verbs (e.g., not both "get" and "fetch"), and (3) no abbreviations. Eliminate any option that mixes conventions.

Section 7.5

Parameter Design: Required vs. Optional, Enums & Defaults

After the model selects a tool, it must populate the parameters correctly. Poorly designed parameter schemas cause the model to hallucinate values, omit required fields, or pass invalid types. This section covers the rules that make parameters foolproof.

Core Concept Summary

Claude's tool-use system validates parameters against JSON Schema. The schema defines parameter types, constraints (enums, min/max), required vs. optional status, and descriptions. Required parameters must appear in the required array — the model treats absence of a parameter from this array as meaning it's optional. Default values should be documented in the description, not just in backend code, because the model needs to know whether it should provide a value or let the backend default take over.

Enums are one of the most powerful constraint tools. When a parameter has a finite set of valid values, always use enum. This prevents the model from hallucinating invalid values (e.g., sending "electronics_dept" when the valid value is "electronics"). Every constrained parameter should document its options in both the enum array and the description.

Parameter Type System

TypeJSON SchemaBest PracticeWatch Out For
string "type": "string" Add format hints in description ("ISO 8601 date", "UUID") Model may hallucinate formats without guidance
integer "type": "integer" Include min/max in description when bounded Model may pass 0 or negative values if unconstrained
number "type": "number" Specify units in description ("price in USD", "weight in kg") Ambiguous units cause incorrect values
boolean "type": "boolean" Describe the effect of true vs. false explicitly Model may guess wrong default if not documented
enum "enum": [...] Always use for finite, known value sets Missing valid values from enum causes silent failures
array "type": "array", "items": {...} Always specify items type and describe array contents Model may pass single value instead of array without guidance
object "type": "object", "properties": {...} Nest sparingly — prefer flat parameters when possible Deep nesting increases hallucination risk

Full Schema Example — Rich Parameter Design

{
  "name": "create_support_ticket",
  "description": "Creates a new customer support ticket in the helpdesk system. Returns the created ticket ID and estimated response time. Use when a customer reports an issue or requests help that cannot be resolved in this conversation.",
  "input_schema": {
    "type": "object",
    "properties": {
      "subject": {
        "type": "string",
        "description": "Brief summary of the issue, max 120 characters."
      },
      "description": {
        "type": "string",
        "description": "Detailed description of the customer's issue, including steps to reproduce if applicable."
      },
      "priority": {
        "type": "string",
        "enum": ["low", "medium", "high", "critical"],
        "description": "Ticket priority. Use 'critical' only for service outages affecting multiple users. Defaults to 'medium' if omitted."
      },
      "category": {
        "type": "string",
        "enum": ["billing", "technical", "account", "feature_request"],
        "description": "The category that best matches the issue type."
      },
      "customer_email": {
        "type": "string",
        "description": "Customer's email address for ticket notifications."
      },
      "attachments": {
        "type": "array",
        "items": { "type": "string" },
        "description": "Optional list of attachment URLs (screenshots, logs). Max 5 items."
      }
    },
    "required": ["subject", "description", "category", "customer_email"]
  }
}
🔑 Key Principle: Document Defaults in the Description, Not Just in Code

If priority defaults to "medium" in your backend, the model has no way to know this unless you state it in the parameter description. Without this, Claude may always explicitly pass a priority value, or worse, hallucinate a wrong default. Write: "Defaults to 'medium' if omitted."

Common Misconceptions

❌ Misconception: "Enums are just nice-to-have"

Enums are a critical constraint mechanism. Without them, the model may invent plausible-sounding but invalid values. A model given "type": "string" for a priority field might generate "urgent", "P1", "top_priority", or "ASAP" — none of which match your backend. Always use enums for closed value sets.

❌ Misconception: "All parameters should be required to prevent the model from skipping them"

Over-requiring parameters forces the model to hallucinate values it doesn't have. If the user hasn't mentioned a priority, marking it required will cause the model to guess. Only require parameters that are truly necessary for the tool to function.

Exam Tips

💡 Exam Tip 7.5a

When a question shows a schema where the model is "hallucinating parameter values," look for: (1) missing enum constraints on bounded fields, (2) parameters marked required that the user hasn't provided, or (3) missing default documentation. These are the top three hallucination causes.

💡 Exam Tip 7.5b

Remember that required is a schema-level array, not a property-level flag. A parameter is required only if its name appears in "required": ["param1", "param2"]. This is a JSON Schema convention that exam questions may test directly.

Section 7.6

Hands-On: Designing a Tool Interface Suite

This section synthesizes everything from 7.1–7.5 into a complete, production-grade tool suite design exercise. The exam heavily weights this section because it tests whether you can apply all principles simultaneously under realistic constraints.

Core Concept Summary

A tool interface suite is a coordinated set of tools that together serve a domain (e.g., e-commerce, customer support, content management). Designing a suite requires balancing naming consistency, description differentiation, parameter reuse, granularity, and total tool count. The hallmark of a well-designed suite is that every tool is clearly distinguishable from every other tool, and the model can reliably select the correct tool for any user intent within the domain.

The design process follows three phases: (1) Intent mapping — enumerate all user intents the suite must cover; (2) Tool boundary drawing — group intents into tools using the split/consolidate framework; (3) Schema authoring — write names, descriptions, and parameters using all the patterns from earlier sections.

Common Misconceptions

❌ Misconception: "The hands-on section is just practice — it won't be on the exam"

Section 7.6 is the highest-weight topic in Chapter 7. Exam questions frequently present a scenario and ask you to evaluate, critique, or design a tool suite. You will need to apply all principles simultaneously — not just recall them in isolation.

❌ Misconception: "If the suite works in testing, the design is good"

A suite can produce correct results in happy-path testing while still having design flaws that surface under edge cases. The exam tests design quality, not just functional correctness. Look for naming inconsistencies, missing negative guidance, and over-required parameters even when the output looks right.

Exam Tips

💡 Exam Tip 7.6a

Scenario-based questions in 7.6 often present a tool suite with 2–3 deliberate flaws and ask "which improvement would most increase reliability?" Apply the 10-point checklist mentally — the answer is the fix for the most critical violation. Priority order: overlapping descriptions (#3) > missing enums (#5) > naming inconsistency (#1).

💡 Exam Tip 7.6b

If asked to "add a new tool to an existing suite," first check: (1) does an existing tool already cover this intent? (2) would the new tool push the count above 20? (3) can the intent be served by adding a parameter to an existing tool? The best answer often involves modifying an existing tool rather than adding a new one.

📋 Chapter 7 — Exam Strategy

1. Question Pattern Recognition

Chapter 7 questions fall into four predictable patterns:

Pattern A: "Why did the model pick the wrong tool?"

Root cause is almost always overlapping or vague descriptions. Look for the answer that improves description specificity or adds negative guidance.

Pattern B: "Which schema is better?"

Apply the 4-part description formula and check for enums, documented defaults, and correct required usage. The answer with more of these elements wins.

Pattern C: "How many tools should this system have?"

Map intents first. Count distinct user intents. Each intent → one tool (unless they share 80%+ parameters). Total should be 5–20.

Pattern D: "What's wrong with this tool suite?"

Apply the 10-point checklist. The most common planted flaws are: overlapping descriptions, missing enums, mixing read/write in one tool, and over-requiring parameters.

2. Elimination Strategies for Distractors

  • Eliminate answers that suggest adding more tools when the suite already has 15+ — consolidation is more likely correct
  • Eliminate answers that prioritize naming over descriptions — the description is always more impactful
  • Eliminate answers that mark all parameters as required — this causes hallucination; only essentials should be required
  • Eliminate answers that mix read and write in one tool — this is almost never the right design
  • Eliminate answers using generic verbs like "process" or "handle" — these are ambiguity red flags

3. High-Priority Last-Minute Review Topics

  1. The 4-part description formula (WHAT / RETURNS / WHEN / WHEN NOT) — most questions trace back to this
  2. Enum usage — know when and why to constrain values
  3. Required vs. optional tradeoffs — over-requiring causes hallucination
  4. The ~20-tool threshold — know what happens above it and how to fix it
  5. The 10-point checklist — memorize it for scenario questions
  6. Negative guidance pattern ("Do NOT use for X — use Y instead")

⚡ Chapter 7 — Quick-Reference Card

📝 Description Formula

  1. WHAT the tool does
  2. RETURNS — what the output looks like
  3. WHEN to use it (trigger conditions)
  4. WHEN NOT to use it (+ alternative tool)

🏷️ Naming Rules

  • verb_noun pattern (e.g., get_order)
  • Consistent casing — prefer snake_case
  • No synonyms across tools (pick one verb)
  • No abbreviations or internal jargon

✂️ Split vs. Consolidate

  • Split: different intents, different side effects
  • Consolidate: shared params, same intent with variants
  • Threshold: aim for 5–20 tools total
  • Never: mix read & write in one tool

⚙️ Parameter Design

  • Required: only if tool can't function without it
  • Enums: always for bounded value sets
  • Defaults: document in description text
  • Descriptions: include format, units, and examples

🎯 Top 3 Exam Traps

  1. Overlapping descriptions → model picks wrong tool
  2. Missing enums → model hallucinates values
  3. Over-requiring params → model guesses values

✅ 10-Point Suite Checklist

① Naming consistency  ② Description completeness  ③ No overlaps  ④ Read/write separation  ⑤ Enums used  ⑥ Defaults documented  ⑦ Required minimized  ⑧ Param descriptions  ⑨ ≤20 tools  ⑩ Cross-references
