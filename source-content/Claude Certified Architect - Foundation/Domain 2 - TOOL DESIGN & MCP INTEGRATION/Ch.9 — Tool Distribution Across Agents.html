9.1 — Distributing Tools Appropriately Across Agents

Concept Overview

Tool distribution is the practice of assigning specific tools to specific agents in a multi-agent system so that each agent has access only to the capabilities it needs to fulfil its designated role. It applies the Principle of Least Privilege (PoLP) to LLM-based tool use: an agent should never have more tools than its task requires.

This matters in production Claude deployments because indiscriminate tool assignment creates security risks (a research agent that can delete files), performance degradation (the model wastes reasoning on irrelevant tools), and reliability failures (the model selects the wrong tool from an overcrowded set).

Key Terminology

  • Tool — A structured function definition (name, description, input schema) exposed to Claude via the API's tools parameter.
  • Agent — A Claude invocation configured with a system prompt, a set of tools, and (optionally) other agents it can delegate to.
  • Orchestrator — The top-level agent that decomposes a task and routes subtasks to specialized subagents.
  • Subagent — A downstream agent invoked by the orchestrator to perform a scoped piece of work.
  • Tool Surface Area — The total set of tools visible to a single agent at invocation time.
  • Domain Alignment — Matching tool assignments to the semantic domain of the agent's role (e.g., a "database agent" gets query tools, not file-system tools).
  • Principle of Least Privilege (PoLP) — A security design principle stating that each component should have exactly the permissions it needs — no more.

Core Principles / Rules

  1. Assign tools by role, not by availability. Start from the agent's responsibility, then determine which tools it needs — never start from the full tool list and ask "which agent might use this?"
  2. One domain per agent. Group tools that belong to the same operational domain (file I/O, database, web, communication) and assign each group to a dedicated agent.
  3. Dangerous tools need isolation. Tools that perform irreversible or high-impact operations (delete, execute code, send messages) should be restricted to agents with explicit authorization flows.
  4. The orchestrator delegates, not executes. The orchestrator should ideally carry zero or minimal tools itself. Its job is task decomposition and routing, not tool execution.
  5. Read vs. Write separation. When feasible, separate read-only tools from write/mutate tools across different agents. This limits the blast radius of misuse.
  6. Tool descriptions are part of the distribution. A well-written tool description helps the model select correctly — poorly described tools cause cross-agent confusion even when distribution is correct.
  7. Validate distribution against the task graph. Every leaf task in the decomposition must have at least one agent with the tools to accomplish it. No tool should be assigned to an agent that never needs it.

💡 Tip — The "Shopping Cart" Mnemonic

Think of tool assignment like packing shopping bags: you wouldn't put raw chicken in the same bag as fresh bread. Group tools by what they affect (reads vs. writes, internal vs. external, safe vs. dangerous) and assign each group to the agent that specializes in handling that category.

⚠️ Common Pitfalls / Anti-Patterns
  • "Give all tools to the orchestrator" — This creates a monolithic agent that violates PoLP, increases error rates, and makes debugging impossible. The orchestrator should delegate, not execute.
  • "Copy every tool to every subagent just in case" — Redundant tool assignment inflates context, confuses tool selection, and negates the purpose of decomposition.
  • Ignoring tool risk classification — Not all tools are equal. A read_file and a delete_file should never be treated as interchangeable assignments.
  • Distributing by tool count instead of domain — Splitting tools 50/50 between agents without considering domain coherence produces worse results than an unbalanced but logically aligned split.

9.2 — Configuring allowedTools to Limit Subagent Scope

Concept Overview

allowedTools is an API-level mechanism for explicitly whitelisting which tools an agent is permitted to use during a given invocation. Even if many tools are defined in the tools array, the allowedTools parameter restricts the model to only selecting from the specified subset.

This is critical in multi-agent architectures because it provides hard enforcement — unlike system prompt instructions ("do not use tool X"), which are probabilistic, allowedTools is enforced by the API and cannot be bypassed by the model's reasoning.

Key Terminology

  • allowedTools — An API parameter that specifies the subset of defined tools the model is permitted to invoke. Acts as a whitelist.
  • Hard enforcement — The API blocks tool calls not in the allowed list; the model cannot override this via reasoning or prompt injection.
  • Prompt-level guardrail — A system-prompt instruction attempting to restrict tool use (e.g., "Never call delete_file"). This is soft enforcement — the model may still call the tool.
  • Tool definition scope — The full set of tools defined in the tools parameter. allowedTools filters this set at invocation time.
  • Dynamic scoping — Changing allowedTools between turns or between subagent invocations based on task context.
  • Tool type filter — allowedTools supports type-based entries that match categories of tools (e.g., all computer-use tools, all MCP server tools).

Core Principles / Rules

  1. allowedTools is a whitelist, not a blacklist. You specify what IS allowed. If a tool is not listed, it is inaccessible — period. There is no deniedTools API parameter (though you may use it conceptually in your architecture design).
  2. API enforcement > prompt enforcement. Always use allowedTools for security-critical restrictions. Never rely solely on system prompt instructions to prevent dangerous tool use.
  3. allowedTools filters, it does not define. Tools must still be defined in the tools array. allowedTools creates a view over the defined set.
  4. Dynamic scoping is a power feature. You can change allowedTools between conversation turns to implement state-based access control (e.g., allow write_file only after a review step).
  5. Supports type-based matching. Entries in allowedTools can match tool types — useful for allowing all tools from a specific MCP server or all built-in tools of a category without enumerating each one.
  6. Empty allowedTools = no tools. If you pass an empty array, the model cannot use any tools in that turn. This is useful for "think-only" or "summarize-only" turns.
  7. Omitting allowedTools = all tools. If you do not include the parameter at all, all defined tools are available. This is the default behavior.

Basic allowedTools configuration

# Research agent — read-only tool access
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    system="You are a research assistant. Find and summarize information.",
    tools=[
        web_search_tool,
        read_file_tool,
        write_file_tool,     # defined but...
        delete_file_tool,    # ...will be blocked
    ],
    messages=messages,
    tool_choice={"type": "auto"},
    # ↓ HARD ENFORCEMENT: only these tools are actually usable
    allowed_tools=[
        {"type": "tool", "name": "web_search"},
        {"type": "tool", "name": "read_file"},
    ],
)

Type-based filtering (allow all tools from an MCP server)

# Allow all tools served by a specific MCP server
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    tools=all_defined_tools,
    messages=messages,
    allowed_tools=[
        {"type": "mcp_server", "name": "research_server"},  # all tools from this server
        {"type": "tool", "name": "summarize"},               # plus one specific tool
    ],
)

Dynamic scoping between turns

# Turn 1: Research phase — read-only
turn1_response = client.messages.create(
    tools=all_tools,
    allowed_tools=[{"type": "tool", "name": "web_search"},
                   {"type": "tool", "name": "read_file"}],
    messages=messages,
)

# Turn 2: After human approval — unlock write
messages.append(turn1_response.content)
messages.append({"role": "user", "content": "Approved. Please write the report."})

turn2_response = client.messages.create(
    tools=all_tools,
    allowed_tools=[{"type": "tool", "name": "read_file"},
                   {"type": "tool", "name": "write_file"}],   # ← now permitted
    messages=messages,
)
💡 Tip — The "Bouncer" Mental Model

Think of allowedTools as a nightclub bouncer with a guest list. The tools array is everyone who applied for entry. The allowedTools list is who the bouncer actually lets in. No amount of persuasion (prompt injection) can get past the bouncer — it's server-enforced.

Memory aid: "allowedTools = hard wall, prompt = suggestion."

⚠️ Common Pitfalls / Anti-Patterns
  • Relying on prompt-only tool restriction for security — "My system prompt says 'never use delete_file'" is NOT a security control. The model can still call it. Use allowedTools.
  • Defining tools you never intend to allow — If a tool should never be used by an agent, don't include it in the tools array at all. allowedTools is for dynamic or conditional filtering, not for permanently blocking tools that shouldn't be defined.
  • Forgetting that omitting allowedTools means "all" — A common bug: the developer forgets to pass allowedTools for a subagent, inadvertently giving it full access.
  • Confusing allowedTools with tool_choice — tool_choice controls whether the model must/can/cannot use tools at all. allowedTools controls which specific tools are available. They are independent parameters.

9.3 — Tool Overload: Why Too Many Tools Hurts Performance

Concept Overview

Tool overload occurs when an agent is given significantly more tools than it needs for its task. Each tool definition consumes context window tokens (name + description + parameter schema), and the model must reason over all available tools when deciding which one to call. As the tool count grows, selection accuracy drops, latency increases, and costs escalate.

This is not merely an efficiency concern — it is a reliability problem. Anthropic's research and guidance consistently shows that agents with fewer, well-described tools outperform agents with large, unfocused tool sets on the same tasks.

Key Terminology

  • Tool overload — The condition where an agent's tool set is large enough to measurably degrade its performance.
  • Context budget — The finite context window shared between system prompt, conversation history, tool definitions, and reasoning. Tools compete for this space.
  • Tool token cost — The token count consumed by a single tool's definition (name + description + JSON schema of parameters). Typically 100–500+ tokens per tool.
  • Selection confusion — When the model selects the wrong tool because similar or overlapping tools exist in the set.
  • Semantic overlap — When two or more tools have similar names, descriptions, or capabilities, making it hard for the model to distinguish between them.
  • Tool description tax — The cumulative context and reasoning cost of including tool definitions the model never uses.

Core Principles / Rules

  1. Every tool has a non-zero cost. Even unused tools consume context tokens and add cognitive overhead. Tool definitions are not free.
  2. Performance degrades non-linearly. Going from 5 to 10 tools causes less degradation than going from 20 to 25 tools. The marginal cost of each additional tool increases.
  3. Anthropic recommends limiting tool count. For best results, keep each agent's tool set focused and minimal. Ideally under ~20 tools per agent; performance begins to degrade noticeably beyond this range.
  4. Semantic overlap is worse than high count. Ten clearly distinct tools outperform eight tools with two semantically overlapping pairs. Overlap causes selection errors.
  5. Tool descriptions are part of the prompt. Verbose, redundant, or poorly written descriptions compound the overload problem. Descriptions should be concise, distinct, and action-oriented.
  6. The fix is decomposition, not truncation. The solution to tool overload is distributing tools across specialized subagents (see §9.1), not trimming tool descriptions.
  7. Measure tool utilization. Track which tools are actually called. Tools with near-zero utilization should be removed or reassigned.

Code / Configuration Example

Measuring tool token cost

import anthropic, json

client = anthropic.Anthropic()

def estimate_tool_tokens(tools: list) -> int:
    """Estimate token count consumed by tool definitions."""
    # Tool definitions are serialized as structured content;
    # a rough proxy is the JSON character count / 4
    tool_json = json.dumps(tools)
    return len(tool_json) // 4  # approximate tokens

# Example: 5 well-defined tools
lean_tools = [search_tool, read_tool, summarize_tool, calc_tool, format_tool]
print(f"Lean set: ~{estimate_tool_tokens(lean_tools)} tokens")
# → Lean set: ~800 tokens

# Example: 40 tools (kitchen-sink approach)
bloated_tools = lean_tools + [tool_6, tool_7, ..., tool_40]
print(f"Bloated set: ~{estimate_tool_tokens(bloated_tools)} tokens")
# → Bloated set: ~6,400 tokens  ← 8x more context consumed

Refactoring overlapping tools

# ❌ BEFORE: Two tools with semantic overlap
tools_before = [

    },

💡 Tip — The "Toolbox Weight" Rule

Imagine carrying a physical toolbox. Every tool you add makes the box heavier and slower to search through. A carpenter doesn't carry a plumber's wrench. Apply the same discipline: if the agent won't use it in >10% of invocations, remove it.

Quick heuristic: For each tool, ask: "If I remove this tool, can the agent still complete its primary task?" If yes, remove it.

⚠️ Common Pitfalls / Anti-Patterns
  • "More tools = more capable" — The most dangerous misconception. Adding tools beyond what's needed actively degrades the agent's core abilities.
  • Copy-paste tool sets across agents — Reusing the same 30-tool set for every agent because "it works" ignores the performance tax each agent pays.
  • Verbose tool descriptions — A 200-word description for a simple tool wastes tokens and drowns out other tools. Keep descriptions under 2–3 concise sentences.
  • Similar tool names — search_web, web_search, find_on_web in the same set guarantees confusion. One tool, one name, one purpose.
  • Ignoring parameter schemas — Complex parameter schemas (deeply nested objects, many optional fields) add token cost. Flatten and simplify where possible.

9.4 — Focused Subagents vs Swiss-Army-Knife Agents

Concept Overview

This section addresses the fundamental architectural choice: should you build focused subagents (each with a narrow set of tools and a clear domain) or swiss-army-knife agents (a single or few agents with broad tool access)?

Focused subagents follow the Unix philosophy ("do one thing well") and yield higher reliability, easier debugging, and better security isolation. Swiss-army-knife agents offer simpler architectures, fewer coordination costs, and faster prototyping. The right choice depends on the task's complexity, risk profile, and production maturity.

Key Terminology

  • Focused subagent — An agent with a narrow, well-defined role and a small, domain-aligned tool set (typically 3–10 tools).
  • Swiss-army-knife agent — A single agent given a broad set of tools spanning multiple domains.
  • Specialization — The degree to which an agent's tools and system prompt are optimized for a specific task type.
  • Coordination overhead — The latency, token cost, and complexity added by orchestrating multiple subagents vs. running one agent.
  • Blast radius — The scope of damage if an agent misbehaves. Focused agents have small blast radii; swiss-army agents have large ones.
  • Fan-out pattern — An orchestrator dispatching tasks to multiple focused subagents in parallel.
  • Monolith pattern — A single agent handling all aspects of a workflow end-to-end.

Core Principles / Rules

  1. Default to focused subagents in production. Anthropic's multi-agent guidance recommends specialized agents for production systems due to higher reliability and security.
  2. Swiss-army agents are acceptable for prototyping. During development and iteration, a single broad agent can help discover the right tool set before decomposing.
  3. The decision depends on task heterogeneity. If the task requires tools from many domains in a single reasoning chain, a swiss-army agent avoids inter-agent communication overhead. If the task naturally decomposes into independent subtasks, focused agents are superior.
  4. Focused agents are easier to test. Each subagent has a clear contract: given input X and tools Y, produce output Z. This enables unit-testing at the agent level.
  5. Focused agents are easier to debug. When something goes wrong, you know which agent and which tool set caused the issue. With a monolith, fault isolation is difficult.
  6. Coordination cost is real but manageable. Multi-agent systems add orchestration complexity. Use structured handoff protocols and clear interfaces to minimize this cost.
  7. Hybrid approaches work. You can have a mostly-focused architecture with one slightly broader "utility" agent for cross-cutting concerns. Purity is less important than pragmatism.

💡 Tip — The "Restaurant Kitchen" Analogy

A busy restaurant doesn't have one chef do everything. The sous chef preps, the grill cook grills, the pastry chef bakes, and the head chef orchestrates. Each station has exactly the equipment it needs. A grill cook doesn't need a stand mixer; a pastry chef doesn't need a grill.

Exam shortcut: When comparing patterns, remember: "Focused = production, Swiss-army = prototype." If the question mentions production, security, or reliability, the answer involves focused subagents.

⚠️ Common Pitfalls / Anti-Patterns
  • "Specialization means exactly one tool" — Focused doesn't mean singular. A research agent with 5 retrieval tools is still focused. Specialization is about domain coherence, not tool count = 1.
  • "Swiss-army is always wrong" — This is an overcorrection. For simple, low-risk tasks or rapid prototyping, a single-agent approach is perfectly valid.
  • Over-decomposition — Creating 15 subagents each with 1 tool adds massive coordination overhead. Find the right granularity — typically 3–5 subagents for most workflows.
  • Forgetting the orchestrator's cost — The orchestrator itself is an API call. If the task is simple enough to handle in one call, adding an orchestrator layer just adds latency and cost with no benefit.

9.5 — Hands-On: Designing Agent-Tool Architectures

Concept Overview

This section provides a systematic design methodology for mapping business requirements to agent-tool architectures. The process moves from requirements gathering → task decomposition → tool identification → agent assignment → validation → iteration.

Mastering this process is essential because the exam tests not just knowledge of principles (§9.1–9.4) but the ability to apply them in realistic scenarios. Design questions typically present a use case and ask candidates to identify the best architecture, spot flaws in a proposed design, or optimize an existing setup.

Key Terminology

  • Task decomposition — Breaking a complex objective into independent, assignable subtasks.
  • Tool inventory — The complete catalog of available tools before distribution.
  • Agent contract — The specification of an agent's inputs, outputs, tools, and responsibilities.
  • Handoff protocol — The structured mechanism by which one agent passes work to another (output format, context transfer, error handling).
  • Validation matrix — A mapping that verifies every required capability is covered by exactly one agent and no tool is assigned without purpose.
  • Architecture review checklist — A systematic set of questions to verify the design meets security, performance, and reliability requirements.

Core Principles / Rules

  1. Start from requirements, not from tools. The design process begins with "what does the system need to do?" not "what tools do we have?"
  2. Decompose before assigning. First identify all subtasks, then map tools to tasks, then group tasks into agents. Do not assign tools to agents before understanding the task structure.
  3. One agent = one responsibility. Each agent should have a clear, single responsibility expressible in one sentence ("This agent researches topics using web search").
  4. Design handoffs explicitly. How does the orchestrator pass context to a subagent? What format does the subagent return? What happens on failure? These must be specified.
  5. Validate with the matrix. After design, verify: (a) every task has an agent, (b) every agent has only needed tools, (c) no tool is unassigned, (d) no tool is duplicated without reason.
  6. Plan for iteration. The first design is rarely perfect. Build observability (logging tool calls, tracking accuracy) to inform optimization.

💡 Tip — The "Napkin Test"

If you can't sketch the entire architecture on a napkin in under 60 seconds, it's too complex. Production multi-agent systems typically have 3–5 agents, not 15. If you're designing more, look for agents that can be merged without violating PoLP.

Exam shortcut for design questions: Draw the diagram first (orchestrator at top, subagents below). Then verify: (1) each subagent has a one-sentence role, (2) tools are domain-aligned, (3) read/write are separated, (4) allowedTools is used. If all four hold, the design is correct.

⚠️ Common Pitfalls / Anti-Patterns
  • Designing bottom-up (tools first) — Starting from "here are 30 tools, how do we distribute them?" leads to incoherent agents. Always start from requirements and tasks.
  • No validation step — Shipping a design without verifying coverage and isolation. The validation matrix takes 5 minutes and prevents hours of debugging.
  • Static design with no iteration plan — The first architecture is a hypothesis. Without monitoring and feedback loops, you can't improve it.
  • Ignoring handoff contracts — If subagents don't have clear input/output specs, the orchestrator can't reliably route information. This is the #1 cause of multi-agent system failures.
  • Over-engineering simple tasks — Not every task needs an orchestrator. If a task only requires 3–5 tools in a single domain, one agent is sufficient.

Master Tips Sheet — Top 10 Last-Minute Takeaways

🏁 Final Review — Memorize These
  1. allowedTools = hard wall, system prompt = suggestion. For security-critical restrictions, always use allowedTools.
  2. Fewer tools = better performance. Every tool has a non-zero context and reasoning cost. Aim for under 15–20 per agent.
  3. Focused subagents for production, swiss-army for prototyping. This is the default recommendation — deviate only with justification.
  4. The orchestrator delegates, not executes. Give the orchestrator routing tools only. Execution tools go to subagents.
  5. Separate reads from writes. Read-only agents should never have write/delete/send tools.
  6. Semantic overlap kills accuracy. Two similar tools in the same agent cause random selection. Deduplicate or differentiate descriptions.
  7. Omitting allowedTools = all tools accessible. An empty array [] = no tools. Know the difference.
  8. Validate with the matrix. After design, verify: every task covered, every tool justified, read/write separated, allowedTools configured.
  9. 3–5 subagents is the sweet spot. More than ~7 agents usually indicates over-decomposition. Fewer than 2 often means under-decomposition for complex tasks.
  10. Design methodology: Requirements → Decompose → Inventory → Assign → Validate → Iterate. Never skip the validation step.
