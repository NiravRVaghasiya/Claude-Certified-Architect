Section 8.1

Structured Error Context: Failure Type, Attempted Query & Partial Results

📘 Concept Overview

In the Model Context Protocol, an MCP tool is expected to communicate failure with the same structural discipline as success. A bare "Something went wrong" string is never enough. Structured error context gives the LLM coordinator (Claude, or any orchestrating model) the information it needs to decide what to do next — without hallucinating reasons or retrying blindly.

Structured error context consists of three pillars returned together whenever a tool fails:

The Three Pillars of Structured Error Context
① Failure Type
+
② Attempted Query
+
③ Partial Results
Together, these give the coordinator enough signal to recover, reroute, or report.

📖 Key Definitions

Failure Type
A machine-readable category (e.g., "transient", "business_rule", "permission_denied") that classifies why the tool call failed. This replaces opaque error strings with actionable categories.
Attempted Query
An echo of exactly what the tool tried to do — the parameters, filters, and resource identifiers it used. This allows the coordinator to understand what was attempted without re-parsing its own prior request.
Partial Results
Any data the tool was able to retrieve before the failure occurred. For example, a database tool may return 3 of 5 requested rows before a timeout. Partial results prevent unnecessary re-fetching of already-available data.
Error Context Object
The composite JSON structure within the MCP tool response that bundles all three pillars alongside the isError: true flag.

🎨 Visual: Anatomy of a Structured Error Response

// MCP Tool Response with structured error context
{
  "content": [
    {
      "type": "text",
      "text": "{\"error\": {\"type\": \"transient\", \"message\": \"Database connection timed out after 30s\", \"attempted_query\": {\"table\": \"orders\", \"filters\": {\"status\": \"pending\"}, \"limit\": 50}, \"partial_results\": {\"rows_fetched\": 12, \"data\": [...]}, \"retry_after_seconds\": 5}}"
    }
  ],
  "isError": true
}
💡 Tips & Tricks
  • Always serialize error context as JSON within the text content — MCP content items are text or image; structured error metadata goes inside the text body as parseable JSON.
  • Echo parameters faithfully. Don't summarize the attempted query — return the exact parameters. The coordinator may use them to construct a follow-up call.
  • Include timestamps. Adding "timestamp" and "duration_ms" to the error object helps the coordinator gauge transient vs. persistent failure.
  • Partial results should include a progress indicator (e.g., "fetched": 12, "expected": 50) so the coordinator knows how much is missing.
🎯 Exam Strategy — Section 8.1
  • Question type: Scenario-based MCQ — "Given this tool failure, which error context fields are essential?"
  • Watch for: Distractors that include HTTP status codes or transport-layer headers as part of MCP error context. MCP error context lives inside the response body, not in protocol headers.
  • Common distractor: Options suggesting that the coordinator should infer the failure type from the error message string. The correct answer always involves an explicit, machine-readable type field.
  • Memory anchor: "Three pillars: What failed (type), what was tried (query), what survived (partial)."
  • Likely format: MCQ and "select all that apply"
Section 8.2

The isError Flag in MCP Tool Responses

📘 Concept Overview

Every MCP tool invocation returns a CallToolResult object. This object contains a content array (with one or more text/image items) and a boolean flag called isError. This flag is MCP's application-level error signal — it tells the coordinating LLM whether the tool call succeeded or failed, regardless of how the data was transported.

isError is not analogous to HTTP status codes. A tool call can arrive successfully over the transport layer (HTTP 200, stdio stream intact) yet still carry isError: true because the tool's business logic encountered a problem. Conversely, a transport-layer failure (network error, process crash) produces a protocol-level error, which is handled differently from a tool-level isError.

📖 Key Definitions

CallToolResult
The MCP response schema returned by every tool invocation. Fields: content (array of content items) and isError (optional boolean, defaults to false).
isError: true
Signals that the tool executed but the operation it attempted failed. The content array describes what went wrong. The coordinator should treat this as an error to be handled, not data to present to the user.
isError: false
The default. Indicates the tool succeeded. Content represents the requested result. May be omitted (absence ≡ false).
Protocol-level error
A JSON-RPC error (e.g., method not found, invalid params, internal error) that occurs at the transport/protocol layer. These are separate from tool-level errors and don't use isError — they use the JSON-RPC error object with numeric codes.

# CallToolResult schema (simplified)
class CallToolResult:
    content: list[TextContent | ImageContent | EmbeddedResource]
    isError: bool = False   # Optional, defaults to False

# How the coordinator should interpret it
def process_tool_result(result: CallToolResult):
    if result.isError:
        # Content describes the error — parse and route to recovery
        error_info = json.loads(result.content[0].text)
        return handle_error(error_info)
    else:
        # Content is the actual result — use it
        return use_result(result.content)
💡 Tips & Tricks
  • isError is optional and defaults to false. If a tool response has no isError field, treat it as a success.
  • Don't confuse isError with JSON-RPC errors. A JSON-RPC error object (code + message) means the protocol failed. isError means the tool ran but its operation didn't succeed.
  • Content is always present. Even when isError: true, the content array is populated — it describes the error. Tools should never return an empty content array on error.
  • Think of isError as an in-band signal. It travels inside the successful response envelope, not as a separate error mechanism.
🎯 Exam Strategy — Section 8.2
  • Question type: Scenario-based MCQ — "A tool returns HTTP 200 with isError: true. What should the coordinator do?"
  • Watch for: Distractors that conflate isError with HTTP 4xx/5xx codes. The exam tests whether you understand the two-layer model.
  • Common trap: "If isError is absent, the tool failed silently." — Wrong. Absent means false (success).
  • Memory anchor: "isError is MCP's internal signal — it lives INSIDE the response body, not in the transport layer."
  • Likely format: MCQ, true/false
Section 8.3

Transient Errors vs Business Errors vs Permission Errors

📘 Concept Overview

Not all errors are equal. MCP tool implementations should classify errors into distinct categories because the correct recovery strategy differs radically between them. An error taxonomy allows the coordinator to take immediate, appropriate action rather than applying a one-size-fits-all retry or giving up entirely.

The three canonical error categories in MCP tool design are:

⏳ Transient Errors
Temporary infrastructure or capacity failures that are expected to self-resolve.

Examples: Network timeouts, rate limits, database connection pool exhausted, service temporarily unavailable.

Key signal: The same request, sent again later, is likely to succeed.
🚫 Business Errors
The request was well-formed but violates a business rule, validation constraint, or domain logic.

Examples: Invalid date range, referenced entity not found, exceeding a balance limit, conflicting parameters.

Key signal: Retrying the exact same request will always fail. The input needs to change.
🔒 Permission Errors
The caller lacks the authorization or scope to perform the requested operation.

Examples: Expired OAuth token, insufficient scope, IP-restricted resource, role-based access denied.

Key signal: The request itself is valid, but the caller's identity or credentials are insufficient.

📖 Key Definitions

Transient Error
An error caused by temporary infrastructure conditions. Retry with exponential backoff is the standard recovery.
Business Error
An error caused by invalid input or violated domain rules. Recovery requires modifying the request, not retrying it.
Permission Error
An error caused by insufficient authorization. Recovery requires credential refresh, scope escalation, or user intervention.
Retry Budget
The maximum number of retries the coordinator should attempt for transient errors before escalating. Typically 2–3 retries with exponential backoff.
Exponential Backoff
A retry strategy where the wait time between attempts increases exponentially (e.g., 1s → 2s → 4s) to avoid overwhelming recovering services.

⚠️ Common Confusion: Rate Limits

Rate limit errors (429 Too Many Requests) are transient, not business errors. They are caused by temporary capacity constraints and will resolve when the rate window resets. Many candidates incorrectly classify them as business errors because "the server rejected the request." The litmus test: would the same request succeed later without changing anything? If yes → transient.

💡 Tips & Tricks
  • Error type is a tool-design decision. The MCP spec doesn't mandate specific type strings — it's the tool author's responsibility to include a clear, machine-readable classification. Best practice: use a consistent enum like "transient" | "business" | "permission".
  • Include a human-readable message AND a machine-readable type. The coordinator needs the type; the message is for fallback or user-facing output.
  • For business errors, suggest a fix. A "suggestion" field (e.g., "Try a date range ≤ 90 days") lets the coordinator self-correct without user intervention.
  • Permission errors should specify exactly what's needed — e.g., "required_scope": "calendar:write" — so the coordinator or user can request precisely the missing permission.
🎯 Exam Strategy — Section 8.3
  • Question type: Classification scenarios — "Given this error message, what type is it?"
  • Watch for: Rate limit traps (transient, not business). Also: token expiry is permission not transient, even though it "happens temporarily."
  • Key distinction: Retryability. The exam loves testing: "Should the coordinator retry?" If the same identical request can succeed later → transient. If the request must change → business. If credentials must change → permission.
  • Memory anchor: "Transient: wait and retry. Business: fix the input. Permission: fix the credentials."
  • Likely format: MCQ, classification matching
Section 8.4

Enabling Intelligent Coordinator Recovery Decisions

📘 Concept Overview

The purpose of structured error responses is to enable the coordinator (Claude) to make intelligent recovery decisions autonomously. Rather than immediately escalating every failure to the user, a well-structured error response gives the coordinator a decision tree: Can I retry? Can I adjust the parameters? Should I try a different tool? Do I need user input?

This section maps out the coordinator's decision logic when it receives an isError: true response, and explains how each field in the structured error context feeds into that logic.

📖 Key Definitions

Coordinator
The orchestrating LLM (e.g., Claude) that invokes MCP tools and processes their results. It decides what to do next based on the tool response.
Recovery Strategy
The action the coordinator takes after a tool error: retry, adjust parameters, try an alternative tool, ask the user, or gracefully degrade.
Graceful Degradation
Presenting partial results or a helpful explanation to the user when full recovery is impossible, rather than showing a raw error.
Fallback Tool
An alternative MCP tool that can serve the same purpose via a different mechanism (e.g., a cached search tool when the live API is down).
Retry Budget
Maximum retries before the coordinator gives up on transient errors. Prevents infinite retry loops.

📐 How Error Fields Map to Recovery Decisions
  • error.type → Selects the recovery branch (retry / adjust / re-auth)
  • error.retry_after_seconds → Determines backoff duration for transient errors
  • error.suggestion → Provides parameter correction for business errors
  • error.required_scope → Identifies missing permission for permission errors
  • error.attempted_query → Allows coordinator to modify and re-submit without re-inferring parameters
  • error.partial_results → Enables graceful degradation when full recovery is impossible
💡 Tips & Tricks
  • Every field in the error object should map to a coordinator action. If a field doesn't help the coordinator decide what to do, it's noise. Keep error payloads actionable.
  • Partial results are the coordinator's safety net. When all retries are exhausted, presenting partial data with a caveat ("Here's what I found before the timeout; 12 of 50 rows were retrieved") is far better than "An error occurred."
  • Chain-of-thought matters. The coordinator should reason through the error type → available fields → best recovery action step by step. This is how Claude processes errors in practice.
🎯 Exam Strategy — Section 8.4
  • Question type: Scenario-based — "A tool returns a transient error with partial results. What should the coordinator do first?"
  • Watch for: Distractors suggesting immediate user notification for transient errors. The correct answer is almost always: retry first, notify only if budget exhausted.
  • Key pattern: The exam tests the priority order of recovery strategies. Memorize: Retry → Fallback → Partial → Notify. Business: Adjust → Ask → Explain. Permission: Refresh → Alternative → Escalate.
  • Memory anchor: "The coordinator's job is to exhaust all autonomous recovery options before bothering the user."
  • Likely format: Scenario-based MCQ, ordering/priority questions
Section 8.5

Access Failures vs Valid Empty Results

📘 Concept Overview

One of the most critical — and most commonly confused — distinctions in MCP error design is the difference between:

  • Access Failure: The tool could not reach the data (permission denied, service down, auth expired)
  • Valid Empty Result: The tool successfully queried the data source and found zero matching records

These produce radically different coordinator behaviors. Conflating them is a serious design flaw that leads the coordinator to either (a) report "no results found" when it actually couldn't access the data, or (b) trigger error recovery when there truly are just no matching records.

  }],

✅ Valid Empty Result Response

{
  "content": [{
    "type": "text",
    "text": "{\"results\": [], \"total_count\": 0, \"query\": {\"table\": \"orders\", \"status\": \"pending\"}, \"message\": \"No pending orders found for the specified criteria.\"}"
  }],
  "isError": false  // ← Signals success (query worked, just no matches)
}

📖 Key Definitions

Access Failure
The tool was unable to execute its query against the data source. No reliable information about the result set exists. isError: true.
Valid Empty Result
The tool successfully queried the data source and the result set is genuinely empty. This is not an error — it is a successful operation that returned zero records. isError: false.
False Negative
When an access failure is misrepresented as an empty result, causing the user to believe no data exists when in fact the data was unreachable. This is the most dangerous consequence of conflating the two.
⚠️ The Dangerous Anti-Pattern

Never return isError: false with empty results when the data source was unreachable. This creates a false negative — the coordinator tells the user "there are no matching records" when it simply couldn't check. In high-stakes domains (medical, financial, safety), this can lead to harmful decisions.

Rule of thumb: If the tool didn't successfully complete its query, isError must be true — even if the failure was silent or partial.

💡 Tips & Tricks
  • Include "total_count": 0 in empty results. This explicitly confirms the query ran and found nothing. It disambiguates from cases where count is unknown.
  • Echo the query in both cases. For empty results, the query field helps the coordinator suggest alternative parameters. For access failures, it helps with retry construction.
  • Use distinct response schemas. Access failures should always include error.type. Empty results should always include total_count or results: []. If you see both patterns in the same response, it's a design smell.
  • Semantic clarity test: Ask yourself — "If I showed only the content to a coordinator with no other context, could it tell whether the data source was reached?" If not, your response is ambiguous.
🎯 Exam Strategy — Section 8.5
  • Question type: Scenario-based — "A tool returns zero results. Which response is correct?"
  • Watch for: The exam loves presenting a scenario where a database is unreachable and asking whether isError should be true or false. The answer is always true when the data source wasn't reached, regardless of what data was returned.
  • Trap question: "An empty array [] with isError: false always means no data exists." — Correct only if the query actually executed.
  • Memory anchor: "Couldn't look → error. Looked and found nothing → success with zero results."
  • Likely format: MCQ, true/false, scenario classification
Section 8.6

Hands-On: Implementing Error-Handling Strategies

📘 Concept Overview

This section bridges theory and practice. You will see production-grade code patterns for implementing structured error responses in MCP tool servers, and for writing coordinator-side logic that consumes them intelligently. The focus is on two perspectives: tool author (producing errors) and coordinator (consuming errors).

📖 Key Definitions

Tool Author
The developer implementing an MCP tool server. Responsible for catching exceptions, classifying errors, and returning structured CallToolResult responses.
Error Schema
A consistent JSON structure used across all tools for error payloads, enabling the coordinator to parse errors uniformly regardless of which tool produced them.
Error Boundary
A try/except wrapper at the tool handler level that catches all exceptions and converts them to structured MCP responses rather than allowing raw crashes.

💻 Code Example 1: Tool-Side — Producing Structured Error Responses

This example shows how to implement a robust MCP tool handler that classifies exceptions into the three error categories and returns consistent, structured error context.

import json
from datetime import datetime
from typing import Any, Optional

# ──────────────────────────────────────────────────────────────
# 1. Define a consistent error schema used by ALL tools
# ──────────────────────────────────────────────────────────────
def build_error_context(
    error_type: str,        # "transient" | "business" | "permission"
    message: str,            # Human-readable error description
    attempted_query: dict,   # Echo of what the tool tried to do
    partial_results: Optional[dict] = None,
    suggestion: Optional[str] = None,
    retry_after: Optional[int] = None,
    required_scope: Optional[str] = None,
) -> dict:
    """Build a standardized error context object."""
    error = {
        "type": error_type,
        "message": message,
        "timestamp": datetime.utcnow().isoformat() + "Z",
        "attempted_query": attempted_query,
    }
    # Include optional fields only when relevant to the error type
    if partial_results:
        error["partial_results"] = partial_results
    if suggestion and error_type == "business":
        error["suggestion"] = suggestion     # Only for business errors
    if retry_after and error_type == "transient":
        error["retry_after_seconds"] = retry_after  # Only for transient errors
    if required_scope and error_type == "permission":
        error["required_scope"] = required_scope  # Only for permission errors
    return {"error": error}

# ──────────────────────────────────────────────────────────────
# 2. MCP tool handler with error boundary pattern
# ──────────────────────────────────────────────────────────────
async def handle_query_orders(params: dict) -> dict:
    """MCP tool: query_orders — fetch orders by status and date range."""
    attempted = {"tool": "query_orders", "params": params}

    try:
        # ── Validate input (catches business errors early) ──
        if params.get("days_back", 0) > 90:
            return {
                "content": [{
                    "type": "text",
                    "text": json.dumps(build_error_context(
                        error_type="business",
                        message="Date range cannot exceed 90 days",
                        attempted_query=attempted,
                        suggestion="Use days_back ≤ 90, or paginate with date windows"
                    ))
                }],
                "isError": True
            }

        # ── Execute the query ──
        results = await db.query_orders(
            status=params["status"],
            days_back=params.get("days_back", 30)
        )

        # ── Success: return results (even if empty — NOT an error) ──
        return {
            "content": [{
                "type": "text",
                "text": json.dumps({
                    "results": results,
                    "total_count": len(results),
                    "query": attempted
                })
            }],
            "isError": False
        }

    except TimeoutError as e:
        # ── Transient: timeout is temporary, can retry ──
        return {
            "content": [{
                "type": "text",
                "text": json.dumps(build_error_context(
                    error_type="transient",
                    message=f"Query timed out: {e}",
                    attempted_query=attempted,
                    retry_after=5
                ))
            }],
            "isError": True
        }

    except PermissionError as e:
        # ── Permission: caller lacks required access ──
        return {
            "content": [{
                "type": "text",
                "text": json.dumps(build_error_context(
                    error_type="permission",
                    message=f"Access denied: {e}",
                    attempted_query=attempted,
                    required_scope="orders:read"
                ))
            }],
            "isError": True
        }

💻 Code Example 2: Coordinator-Side — Consuming Errors Intelligently

This example shows how a coordinator (or orchestration framework) processes structured error responses to make recovery decisions.

import json
import asyncio

# ──────────────────────────────────────────────────────────────
# Coordinator-side error handler with full recovery logic
# ──────────────────────────────────────────────────────────────
class MCPErrorHandler:
    def __init__(self, max_retries: int = 3):
        self.max_retries = max_retries
        self.attempt_count: dict[str, int] = {}  # Track retries per tool call

    async def handle_tool_response(
        self,
        tool_name: str,
        response: dict,
        call_tool_fn  # async callable to re-invoke the tool
    ) -> dict:
        """Process a tool response, handling errors with appropriate strategy."""

        # ── Happy path: tool succeeded ──
        if not response.get("isError", False):
            return {"status": "success", "data": response["content"]}

        # ── Parse the structured error ──
        error_text = response["content"][0]["text"]
        error_ctx = json.loads(error_text).get("error", {})
        error_type = error_ctx.get("type", "unknown")

        # ── Route to the correct recovery strategy ──
        if error_type == "transient":
            return await self._handle_transient(
                tool_name, error_ctx, call_tool_fn
            )
        elif error_type == "business":
            return self._handle_business(error_ctx)
        elif error_type == "permission":
            return self._handle_permission(error_ctx)
        else:
            # Unknown error type — cannot recover autonomously
            return {
                "status": "escalate",
                "reason": f"Unknown error type: {error_type}",
                "original_error": error_ctx
            }

    async def _handle_transient(self, tool_name, error_ctx, call_tool_fn):
        """Retry with exponential backoff for transient errors."""
        call_key = f"{tool_name}:{json.dumps(error_ctx.get('attempted_query', {}))}"
        attempts = self.attempt_count.get(call_key, 0)

        if attempts >= self.max_retries:
            # Budget exhausted — degrade gracefully
            partial = error_ctx.get("partial_results")
            if partial:
                return {
                    "status": "partial",
                    "data": partial,
                    "warning": "Retries exhausted; returning partial results."
                }
            return {"status": "escalate", "reason": "Transient error persisted after max retries."}

        # Wait, then retry
        wait = error_ctx.get("retry_after_seconds", 2 ** attempts)
        await asyncio.sleep(wait)
        self.attempt_count[call_key] = attempts + 1
        # Re-invoke with original parameters
        new_response = await call_tool_fn(error_ctx["attempted_query"]["params"])
        return await self.handle_tool_response(tool_name, new_response, call_tool_fn)

    def _handle_business(self, error_ctx):
        """Route business errors — suggest fix or escalate to user."""
        suggestion = error_ctx.get("suggestion")
        if suggestion:
            return {
                "status": "adjust_and_retry",
                "suggestion": suggestion,
                "original_query": error_ctx.get("attempted_query")
            }
        return {
            "status": "escalate",
            "reason": error_ctx.get("message", "Business rule violation")
        }

    def _handle_permission(self, error_ctx):
        """Route permission errors — identify what's needed."""
        return {
            "status": "auth_required",
            "required_scope": error_ctx.get("required_scope", "unknown"),
            "message": error_ctx.get("message")
        }
📐 Design Principles for Error Handling in MCP Tools
  1. Fail structured, not raw. Never let an unhandled exception escape. Wrap every tool handler in an error boundary that catches all exceptions and converts them to structured CallToolResult responses.
  2. Classify at the source. The tool — not the coordinator — should determine the error type. The tool knows whether an exception represents a timeout (transient), an invalid parameter (business), or a denied scope (permission).
  3. Be generous with context. Include the attempted query, partial results, timing info, and actionable suggestions. More context = better coordinator decisions.
  4. Idempotent retries. Transient error handlers assume the original request can be safely re-sent. Tool operations should be idempotent (or clearly documented when they aren't).
  5. Consistent schema across all tools. If every tool on the server uses the same error schema, the coordinator can use a single parsing strategy rather than tool-specific handling.
💡 Tips & Tricks
  • Test error paths, not just happy paths. Write integration tests that verify your tool returns correct isError, proper error types, and parseable JSON for every failure mode.
  • Log error responses server-side. Even though the coordinator processes errors, the tool server should log them for observability and debugging.
  • Version your error schema. Include a "schema_version" field so coordinators can adapt if the error format evolves.
  • Don't leak sensitive info. Error messages should be informative but never expose internal stack traces, database connection strings, or API keys.

Q1. An MCP tool returns HTTP 200 with the following body: {"content": [{"type": "text", "text": "Rate limit exceeded"}], "isError": true}. What type of error is this, and should the coordinator retry?

  1. Business error — do not retry
  2. Transient error — retry with exponential backoff
  3. Permission error — refresh credentials
  4. Protocol error — the tool never executed
Show Answer
B. Transient error — retry with exponential backoff.
Rate limiting is a temporary capacity constraint. The same request will succeed once the rate window resets. HTTP 200 confirms the transport layer succeeded; isError: true is the application-level error signal. Option D is wrong because protocol errors use JSON-RPC error objects, not isError.

Q2. A database tool encounters a connection timeout but managed to fetch 12 of 50 requested rows before failing. What should the structured error response include?

  1. Only isError: true and a generic error message
  2. isError: true, error type "transient", attempted query, and partial results (12 rows)
  3. isError: false with the 12 rows (since some data was retrieved)
  4. isError: true with the 12 rows returned as a successful result in a separate field
Show Answer
B. The response should include all three pillars of structured error context: failure type ("transient"), attempted query (the parameters used), and partial results (the 12 rows). This gives the coordinator enough information to decide between retrying for the remaining 38 rows or presenting the 12 partial rows. Option C is wrong because the operation didn't complete — isError must be true.

Q3. True or False: If the isError field is absent from a CallToolResult, the coordinator should treat the response as an error because the tool forgot to set it.

  1. True
  2. False
Show Answer
B. False. The isError field is optional and defaults to false. Its absence indicates success, not a missing field. This is by design in the MCP specification — tools only need to set isError when reporting a failure.

Q4. A tool attempts to query a customer's order history but the customer database is completely unreachable. The tool returns: {"content": [{"type": "text", "text": "{\"results\": [], \"total_count\": 0}"}], "isError": false}. What is wrong with this response?

  1. Nothing — zero results is a valid response when the database is empty
  2. It creates a false negative — the coordinator will tell the user "no orders found" when it actually couldn't check
  3. The total_count should be null instead of 0
  4. The content should be an image, not text
Show Answer
B. This is the "false negative" anti-pattern. The database was unreachable, so the tool doesn't know whether orders exist. Returning isError: false with empty results makes the coordinator believe the query ran successfully and found nothing. The correct response would be isError: true with error type "transient" (or appropriate type), indicating the data source was not reached.

Q5. A coordinator receives a business error with a "suggestion" field: "Try a date range ≤ 90 days". What is the coordinator's first action?

  1. Retry the exact same request with exponential backoff
  2. Adjust the parameters based on the suggestion and re-call the tool
  3. Immediately ask the user to re-enter their request
  4. Refresh OAuth credentials and retry
Show Answer
B. Adjust the parameters based on the suggestion and re-call the tool.
Business errors are not retryable with the same input. The suggestion field provides a specific, machine-readable hint for how to fix the request. The coordinator should modify the parameters accordingly and re-call the tool — this is autonomous recovery without user intervention. Option A is wrong because retrying the same request will always fail for a business error. Option C is the secondary action (only if no suggestion is available). Option D applies to permission errors, not business errors.
