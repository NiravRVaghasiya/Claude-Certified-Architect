How this chapter fits together

In a multi-agent system, a coordinator (orchestrator) delegates work to specialized subagents. Things fail: tools time out, permissions are denied, payloads come back empty. The chapter teaches one coherent error-handling lifecycle:

26.1 RepresentCapture failures as structured error context, not raw strings.
26.2 DistinguishSeparate "couldn't check" (access failure) from "checked, nothing found" (valid empty).
26.3 ContainLet the subagent self-heal locally before it bothers the coordinator.
26.4 RecoverCoordinator retries, tries alternatives, or degrades gracefully.
26.5 ApplyWire it all together end-to-end in a worked example.

Keep this progression in mind — represent → distinguish → contain → recover → apply — because exam questions frequently test whether you know which layer owns which responsibility.

26.1 Structured Error Context for Intelligent Recovery

Concept Overview

When a subagent fails, how it reports the failure decides whether the system can recover intelligently. A bare string like "Error: request failed" tells the coordinator almost nothing — it cannot decide whether to retry, switch tools, or give up. Structured error context replaces that string with a machine-readable object carrying the facts a recovery policy needs: what failed, who failed, what was being attempted, what (if anything) was already produced, and how many times it has been tried.

The "why" is decision-making. Recovery is a routing decision, and routing needs typed inputs. Structured context turns error handling from guesswork ("does this string contain the word 'timeout'?") into deterministic policy ("if error_type == ACCESS_FAILURE and retry_count < max, retry").

Key Terminology

Structured Error Context
A typed object describing a failure, designed to be consumed by recovery logic rather than read by a human.
Error Type
A categorical label (e.g. ACCESS_FAILURE, VALIDATION_ERROR, EMPTY_RESULT) that drives the recovery branch taken.
Source Agent
The identifier of the subagent (and ideally the tool) where the failure originated — essential for targeted retries and observability.
Attempted Action
The operation being performed (query, tool name, parameters) so the coordinator can reproduce or substitute it.
Partial Results
Any usable output gathered before the failure, so work already done is not thrown away.
Retry Count
How many attempts have already occurred — the guard that prevents infinite retry loops.

Code / Pseudocode Example

from dataclasses import dataclass, field
from enum import Enum

class ErrorType(Enum):
    ACCESS_FAILURE   = "access_failure"   # couldn't complete the operation
    EMPTY_RESULT     = "empty_result"     # completed, nothing matched (NOT an error)
    VALIDATION_ERROR = "validation_error" # bad input / schema mismatch

@dataclass
class ErrorContext:
    error_type: ErrorType
    source_agent: str
    attempted_action: dict
    retry_count: int = 0
    partial_results: list = field(default_factory=list)
    message: str = ""

# Producing structured context instead of a raw string:
try:
    data = subagent.fetch(query)
except TimeoutError as e:
    return ErrorContext(
        error_type=ErrorType.ACCESS_FAILURE,
        source_agent="research_subagent",
        attempted_action={"tool": "web_search", "query": query},
        retry_count=1,
        message=f"web_search timed out: {e}",
    )
💡 Tips & Tricks
  • Make error_type a closed enum, not a free string — this is what makes recovery logic exhaustive and testable.
  • Always populate partial_results when any work completed; discarding it forces needless re-computation and blocks graceful degradation (26.4).
  • Keep message for humans/logs only. The moment your recovery code parses message with string matching, you've reintroduced the fragility structured context was meant to remove.
  • Include the tool name inside attempted_action, not just the query — the coordinator often recovers by swapping the tool, not the input.
⚠️ Common Pitfall

Returning None or an empty list on failure. This collapses two very different situations — "it broke" and "it found nothing" — into one ambiguous value, which is exactly the confusion 26.2 warns against.

🎯 Exam Strategy

Questions here test whether you know why structure beats strings. Look for stems like "the coordinator cannot decide how to recover" or "error handling is brittle / relies on string matching."

  • Keywords to spot: "intelligent recovery," "typed / categorized error," "retry budget," "machine-readable."
  • Elimination tactic: Reject any answer that logs a nicely-formatted string but returns it as the sole signal — presentation ≠ structure.
Trap answer: "Wrap the error in a detailed human-readable message." Detail is good for logs but is not structured context — the recovery layer still can't branch on it reliably.

26.2 Access Failures (Timeouts) vs Valid Empty Results

Concept Overview

This is the single most tested distinction in the chapter. Two outcomes look superficially similar — both leave you with "no data" — but they mean opposite things:

Access failure = "I couldn't check." The operation never completed (timeout, connection reset, permission denied). The truth is unknown. The correct response is to retry or escalate.

Valid empty result = "I checked, and there's nothing." The operation completed successfully and authoritatively returned an empty payload (e.g. [], 0 rows). The truth is known: nothing exists. The correct response is to proceed / conclude.

Conflating them produces two dangerous bugs. Treating an access failure as empty → a false negative ("no security vulnerabilities found" when the scanner actually crashed). Treating a valid empty as a failure → wasted retries, escalation storms, and silent stalls.

Key Terminology

Access Failure
The operation did not complete; the result is unknown. Signalled by an exception, timeout, or non-2xx transport error.
Valid Empty Result
The operation completed successfully and the authoritative answer is "nothing." Signalled by a successful response with an empty payload.
False Negative
Reporting "nothing found" when in fact the check never ran — the most damaging failure mode of conflation.
Silent Failure
An error that produces no visible signal because it was quietly coerced into a benign-looking empty value.

Visualization

The core distinction table — memorize this
ScenarioSignalCorrect InterpretationWrong Interpretation
API call times out Exception / no response Access failure — status unknown; retry or escalate ❌ Treating as "no data exists"
Query returns [] Successful (2xx) response, empty payload Valid empty result — status known; proceed ❌ Treating as a system failure
Permission denied (403) Error response, no data Access failure — escalate (retry won't help) ❌ Reporting "user has no records"
Search returns 0 results 2xx with count: 0 Valid empty — conclude "none match" ❌ Retrying indefinitely

Code / Pseudocode Example

# Distinguish at the boundary: exceptions => access failure;
# successful-but-empty => valid empty result.
def fetch_records(client, query):
    try:
        resp = client.search(query, timeout=5)      # may raise TimeoutError
    except (TimeoutError, ConnectionError) as e:
        return ErrorContext(                         # "COULDN'T CHECK"
            error_type=ErrorType.ACCESS_FAILURE,
            source_agent="records_subagent",
            attempted_action={"tool": "search", "query": query},
            message=f"{type(e).__name__}: {e}",
        )
    except PermissionError:
        return ErrorContext(                         # also access failure; retry is futile
            error_type=ErrorType.ACCESS_FAILURE,
            source_agent="records_subagent",
            attempted_action={"tool": "search", "query": query},
            message="permission denied",
        )

    # Reached here => the call SUCCEEDED. Empty is a real answer.
    if resp.count == 0:
        return {"status": "empty", "data": [], "checked": True}   # "CHECKED, NOTHING"
    return {"status": "ok", "data": resp.items, "checked": True}
💡 Tips & Tricks
  • Draw the line at the transport boundary: an exception/timeout is an access failure; a successful response is authoritative even when empty.
  • Carry a checked: true flag on empty results so downstream agents can trust that "empty" really means "verified empty."
  • 403 / auth errors are access failures, not empties — but note that retrying them is usually pointless, so route them straight to escalation (26.3/26.4).
  • Never coerce exceptions into [] or None "to keep the pipeline running." That is how false negatives become invisible.
🎯 Exam Strategy

Watch for scenario questions describing a subagent returning "no results" after a network exception — the correct answer treats this as an access failure, not a valid empty result.

  • Keywords that mean access failure: "timed out," "connection reset," "exception," "403 / denied," "no response."
  • Keywords that mean valid empty: "returned successfully," "200 OK," "empty list," "zero rows," "no matches found."
  • Elimination tactic: If the stem mentions any exception or timeout, eliminate every option that says "report no data / conclude none exist."
Trap answer: "The scan finished with no vulnerabilities, so mark the system secure" — when the stem said the scanner crashed / timed out. That's a false negative, not a clean bill of health.

26.3 Subagent Local Recovery Before Coordinator Escalation

Concept Overview

Good multi-agent systems contain failures at the lowest level that can resolve them. Before a subagent escalates to the coordinator, it should attempt inexpensive local recovery: a bounded retry (ideally with backoff) for transient errors, then a fallback tool or alternative strategy. Escalation is the last resort — it costs coordinator attention, may pause other work, and loses local context.

The guiding principle is self-heal vs. escalate: retry what is transient, fall back on what is tool-specific, and escalate what is structural (permissions, exhausted budgets, unrecoverable validation errors). A valid empty result is not a failure and should simply be returned — never retried or escalated.

Key Terminology

Local Recovery
Recovery attempted inside the subagent, invisible to the coordinator, before any escalation.
Bounded Retry
Retrying a transient failure a fixed maximum number of times, typically with exponential backoff, guarded by retry_count.
Fallback Tool
An alternative tool/data source the subagent tries when the primary one fails (e.g. cached index when the live API is down).
Escalation
Returning a structured ErrorContext up to the coordinator because local recovery is exhausted or inappropriate.
Transient vs. Structural Error
Transient = likely to succeed on retry (timeout, rate limit). Structural = will not (403, schema mismatch, budget exhausted) → escalate.

Code / Pseudocode Example

def subagent_run(action, max_retries=2):
    retry_count = 0
    while retry_count <= max_retries:
        try:
            return primary_tool(action)          # success (empty is fine) -> return
        except RateLimitError, TimeoutError:      # TRANSIENT -> self-heal
            retry_count += 1
            sleep(backoff(retry_count))          # exponential backoff
        except PermissionError as e:            # STRUCTURAL -> escalate now
            return ErrorContext(ErrorType.ACCESS_FAILURE, "sub",
                       action, retry_count, message="denied")

    # Retries exhausted: try a fallback before giving up
    if has_fallback(action):
        try:
            return fallback_tool(action)         # alternative source
        except Exception:
            pass

    # Local recovery exhausted -> escalate with full context
    return ErrorContext(ErrorType.ACCESS_FAILURE, "sub",
               action, retry_count, message="primary+fallback failed")
💡 Tips & Tricks
  • Use exponential backoff with jitter for retries to avoid synchronized retry storms across subagents.
  • Do not retry structural errors (403, malformed schema) — you'll burn the retry budget and delay escalation. Fail fast, escalate clearly.
  • Keep the retry budget small at the subagent (2–3). Deep retry loops hide latency and mask real outages from the coordinator.
  • When you escalate, send the final retry_count and any partial_results so the coordinator doesn't restart from zero.
🎯 Exam Strategy

These questions test where recovery should happen. The best answers keep transient recovery local and reserve escalation for structural failures or exhausted budgets.

  • Keywords to spot: "before escalating," "self-heal," "fallback," "who should handle," "lowest level."
  • Elimination tactic: Eliminate answers that escalate a first transient timeout straight to the coordinator (skips cheap local retry) and answers that retry a 403 forever (never escalates a structural error).
Trap answer: "Immediately escalate every error to the coordinator for centralized handling." Centralizing all errors defeats containment and floods the coordinator.

26.4 Coordinator Recovery Strategies: Retry, Alternative Approaches & Graceful Degradation

Concept Overview

Once a failure escalates, the coordinator chooses among three recovery strategies. They form an escalating ladder: try the cheapest, most faithful option first, and only trade fidelity for resilience as options run out.

  1. Retry — attempt the same action again (usually with backoff). Best for transient access failures the subagent couldn't clear alone.
  2. Alternative approach — achieve the same goal a different way: a different subagent, tool, data source, or decomposition. Best when the primary path is structurally blocked but the goal is still reachable.
  3. Graceful degradation — return a reduced-but-useful result (using partial_results), clearly flagged as incomplete. Best when the goal is not fully reachable but partial value still helps the user.

Key Terminology

Retry (coordinator-level)
Re-issuing the failed action, often to a fresh subagent instance, bounded by a global retry budget.
Alternative Approach
Substituting the path to the goal — different tool, agent, or strategy — while keeping the goal fixed.
Graceful Degradation
Delivering a partial or lower-fidelity result with an explicit "incomplete / some sources failed" annotation instead of failing entirely.
Retry Budget
A system-wide cap on retries that prevents cost blow-ups and cascading load.

Visualization — Strategy Comparison

Choosing among the three coordinator strategies
StrategyWhen to useProsCons / Risk of overuse
Retry Transient access failure (timeout, rate limit); action is idempotent. Simple; preserves full fidelity; often succeeds. Useless on structural errors; overuse → latency, cost, retry storms, duplicate side effects if not idempotent.
Alternative approach Primary path blocked (tool down, permission denied) but goal reachable another way. Recovers full or near-full result; resilient to single-path outages. More complex; alternative may be slower/less accurate; overuse hides that the primary path is chronically broken.
Graceful degradation Goal not fully reachable; partial results still valuable; deadline pressure. Always returns something useful; honest about gaps; good UX under partial outage. Reduced fidelity; overuse normalizes incomplete answers and can mask systemic failures if not flagged.

Code / Pseudocode Example

def coordinator_recover(err: ErrorContext, goal):
    # 1) RETRY — cheap, full fidelity, only for transient + within budget
    if err.error_type == ErrorType.ACCESS_FAILURE and err.retry_count < GLOBAL_BUDGET \
       and is_transient(err):
        return retry(err.attempted_action)

    # 2) ALTERNATIVE — same goal, different path (structural block, goal reachable)
    alt = pick_alternative(err.attempted_action, goal)
    if alt is not None:
        return dispatch(alt)                     # different tool / subagent

    # 3) GRACEFUL DEGRADATION — return partial, clearly flagged
    return {
        "status": "partial",
        "data": err.partial_results,
        "note": f"{err.source_agent} unavailable; result is incomplete",
    }
💡 Tips & Tricks
  • Enforce a global retry budget at the coordinator that spans subagent retries — otherwise local + global retries multiply into runaway cost.
  • Only retry idempotent actions blindly; for non-idempotent ones (writes, payments), prefer an alternative or require a deduplication key.
  • Graceful degradation must be labelled. An unlabelled partial result is indistinguishable from a complete one — and reintroduces the false-negative risk from 26.2.
  • Log which strategy fired. If "alternative" or "degradation" fires constantly, that's a signal the primary path needs fixing — don't let resilience mask rot.
🎯 Exam Strategy

Scenario questions give you a failure and ask "what should the coordinator do?" Map the error nature to the strategy: transient → retry; structural-but-goal-reachable → alternative; goal-unreachable-but-partial-value → degrade.

  • Keywords → retry: "temporary," "timeout," "rate limited," "transient."
  • Keywords → alternative: "primary tool unavailable," "another data source," "different agent," "still need the full answer."
  • Keywords → degrade: "deadline," "return what we have," "3 of 4 sources responded," "partial results acceptable."
Trap answer: "Keep retrying until it succeeds." No retry budget = infinite loop / cost blow-up. Also a trap: degrading silently without flagging the result as partial.

26.5 Hands-On: Implementing Error Propagation in a Multi-Agent System

Concept Overview

This worked example wires together 26.1–26.4. A coordinator dispatches two subagents in parallel to answer a compliance question:

  • Subagent A (regulatory feed) — its live API times out → this is an access failure (26.2). It self-heals with a bounded retry (26.3); the retry also fails → it escalates a structured ErrorContext (26.1).
  • Subagent B (internal records) — it completes successfully but the query matches nothing → a valid empty result (26.2). It returns cleanly, no retry, no escalation.

The coordinator receives one escalation and one clean empty. It applies the strategy ladder (26.4): retry the transient failure once more, then fall back to an alternative source; if that also fails, it degrades gracefully, returning B's verified-empty finding plus an explicit note that the regulatory source was unreachable — never claiming "no regulations found."

Key Terminology (reused, defined once earlier)

All terms below are used exactly as defined above: ErrorContext (26.1), access failure / valid empty result (26.2), local recovery / escalation (26.3), retry / alternative approach / graceful degradation (26.4).

Code / Pseudocode Walkthrough

# ---------- Shared types (26.1) ----------
# ErrorType, ErrorContext as defined in 26.1

# ---------- Subagent A: regulatory feed (will time out) ----------
def subagent_A(query, max_retries=2):
    retry_count = 0
    while retry_count <= max_retries:
        try:
            return {"status": "ok", "data": regulatory_api.get(query)}
        except TimeoutError:                     # 26.2: access failure, not empty
            retry_count += 1                     # 26.3: bounded local retry
            sleep(backoff(retry_count))
    return ErrorContext(                        # 26.1 + 26.3: escalate with context
        error_type=ErrorType.ACCESS_FAILURE,
        source_agent="regulatory_subagent",
        attempted_action={"tool": "regulatory_api", "query": query},
        retry_count=retry_count,
        message="regulatory_api timed out after retries",
    )

# ---------- Subagent B: internal records (succeeds, empty) ----------
def subagent_B(query):
    resp = records_db.search(query)             # completes successfully
    if resp.count == 0:
        return {"status": "empty", "data": [], "checked": True}  # 26.2 valid empty
    return {"status": "ok", "data": resp.items, "checked": True}

# ---------- Coordinator: orchestrate + recover (26.4) ----------
def coordinator(query):
    a = subagent_A(query)
    b = subagent_B(query)

    findings = {}

    # Handle B: a valid empty result is a REAL, trustworthy answer
    if b["status"] in ("ok", "empty"):
        findings["internal_records"] = {"data": b["data"], "verified": True}

    # Handle A: only an ErrorContext means it truly failed
    if isinstance(a, ErrorContext):
        recovered = coordinator_recover(a, goal=query)   # retry -> alt -> degrade
        if recovered.get("status") == "partial":
            # 26.4 graceful degradation: keep B's verified finding,
            # explicitly flag the regulatory gap — never claim "none found".
            findings["regulatory"] = {
                "data": None,
                "verified": False,
                "note": "regulatory source unreachable — result INCOMPLETE",
            }
        else:
            findings["regulatory"] = {"data": recovered["data"], "verified": True}
    else:
        findings["regulatory"] = {"data": a["data"], "verified": True}

    return summarize(findings)   # honest: verified-empty + flagged gap
💡 Tips & Tricks
  • Notice the asymmetry: B's empty flows straight into findings as verified; A's failure is an ErrorContext that triggers the recovery ladder. Same "no data," completely different handling — that's the whole chapter in one function.
  • The final summary must distinguish "internal records: verified none" from "regulatory: unknown / unreachable." Merging them into "no regulations apply" would be the exact false negative 26.2 forbids.
  • Run subagents concurrently, but collect structured results — never a mix of exceptions and values — so the coordinator's branching stays clean.
🎯 Exam Strategy

Integration questions describe a multi-subagent scenario and ask for the "correct final behavior." The right answer (a) treats the timeout as an access failure, (b) treats the empty query as a valid finding, and (c) degrades gracefully with an explicit incompleteness flag.

  • Elimination tactic: Discard any option that reports a single fused "nothing found," or that retries the valid-empty subagent, or that fails the whole request because one subagent errored.
Trap answer: "Since neither subagent returned data, report that no regulations apply." This ignores that A never actually checked — a textbook false negative.

Quick-Reference Cheat Sheet

Last-Minute Revision

  • Structured context fields: error_type · source_agent · attempted_action · partial_results · retry_count (+ message for logs only).
  • Access failure = "couldn't check" → status unknown → retry/escalate. Signalled by exception/timeout/403.
  • Valid empty result = "checked, nothing" → status known → proceed. Signalled by 2xx + empty payload.
  • Golden rule: exception ⇒ access failure; successful-but-empty ⇒ valid empty. Never coerce an exception into []/None.
  • Subagent order: bounded retry (transient) → fallback tool → escalate (structural / exhausted). Never retry a valid empty.
  • Coordinator ladder: Retry → Alternative approach → Graceful degradation.
  • Retry only idempotent actions blindly; always enforce a global retry budget.
  • Graceful degradation must be flagged — an unlabelled partial = a hidden false negative.
  • Cardinal sin: reporting "none found" when the check never completed (false negative).

Self-Check Questions

Five exam-style questions covering all sub-topics. Click each to reveal the answer and rationale.

Q1 (26.1). A subagent catches an exception and returns the string "failed to fetch: timeout". The coordinator's recovery logic is described as "brittle." What is the best fix?
  • A. Add more detail to the error string.
  • B. Return a typed ErrorContext with error_type, source_agent, attempted_action, and retry_count.
  • C. Return None so the coordinator knows it failed.
  • D. Log the error and continue with an empty list.

Answer: B.

Brittleness comes from string-matching. A typed object lets recovery branch deterministically. A is presentation, not structure; C and D destroy information and cause the false-negative confusion of 26.2.

Q2 (26.2). A vulnerability scanner subagent throws a TimeoutError, and the wrapper returns []. The coordinator reports "no vulnerabilities found." What went wrong?
  • A. Nothing — an empty list correctly means no vulnerabilities.
  • B. The timeout is an access failure; coercing it to [] produced a false negative. It should be reported as ACCESS_FAILURE and retried/escalated.
  • C. The scanner should have retried forever until it succeeded.
  • D. The coordinator should have degraded silently.

Answer: B.

The scan never completed, so "empty" is unknown, not verified. Reporting a clean result is a dangerous false negative. (C = no budget; D = unflagged degradation — both also wrong.)

Q3 (26.3). A subagent's primary tool returns a RateLimitError on its first call. What should it do first?
  • A. Immediately escalate an ErrorContext to the coordinator.
  • B. Retry with exponential backoff (bounded), then try a fallback tool, then escalate if still failing.
  • C. Return an empty result.
  • D. Retry indefinitely with no backoff.

Answer: B.

Rate limiting is transient — the subagent should self-heal locally before escalating. A skips cheap local recovery; C hides the failure; D causes retry storms and ignores the retry budget.

Q4 (26.4). A subagent escalates because its primary data source is permanently decommissioned (permission revoked), but an equivalent source exists. Which coordinator strategy is most appropriate?
  • A. Retry the same action repeatedly.
  • B. Alternative approach — dispatch to the equivalent source.
  • C. Graceful degradation with a partial result.
  • D. Fail the entire request.

Answer: B.

The failure is structural (retry is futile, so A is out) but the goal is still fully reachable via another path, so an alternative approach recovers full fidelity. Degradation (C) needlessly sacrifices completeness when a full answer is attainable.

Q5 (26.5 integration). Subagent A times out (after local retries) and escalates; Subagent B completes and returns 0 rows. Retry and alternative both fail for A. What is the correct final coordinator behavior?
  • A. Report "no results" for the whole request.
  • B. Fail the entire request because A errored.
  • C. Return B's result as a verified empty finding and flag A's portion as unreachable/incomplete (graceful degradation).
  • D. Retry A until it eventually succeeds.

Answer: C.

B's empty is authoritative and should be reported as verified; A's outcome is unknown and must be flagged as an incomplete gap — never fused with B into a single "none found." A is a false negative, B discards a valid finding, D ignores the retry budget.
