Chapter Overview

Every Claude interaction is stateless under the hood: the model has no memory between API calls, so the entire conversation — system prompt, all prior turns, tool results, and documents — must be re-sent inside a finite context window on every request. As a long-running agent accumulates turns, that window fills, forcing architects to decide what to keep, what to compress, and what to offload. Get this wrong and the agent silently forgets critical facts, contradicts itself, slows down, and burns cost linearly with history length.

This chapter walks the problem chain (24.1 budgets → 24.2 overflow → 24.3 degraded recall), then the mitigation toolkit (24.4 summarization, 24.5 structured state, 24.6 tool-output trimming, 24.7 external retrieval), and finishes with a hands-on lab (24.8) that applies every technique to a real support transcript. Mastering context management is the single highest-leverage skill for building reliable, affordable, long-horizon Claude agents.

24.1 Context Windows & Token Budgets Problem · Foundations

Definition / Concept

A context window is the maximum number of tokens a model can process in a single request — it holds the input (system prompt + full history + tool results + documents) and reserves room for the output. A token budget is the architect's plan for how that fixed capacity is divided among competing consumers.

Key idea: Tokens are sub-word units (roughly ~3–4 English characters, or ~0.75 words each). The window is a hard ceiling shared by input and output — every token spent on stale history is a token unavailable for reasoning or the answer.

Why It Happens / Root Cause

  • Transformers are fixed-context: self-attention computes relationships across all positions at once, so the architecture defines a maximum sequence length it was trained/served to handle.
  • Statelessness: the API resends the whole conversation each turn, so token usage grows with cumulative history — not just the latest message.
  • Cost & latency scale with input tokens: longer prompts mean more compute per call; attention cost grows roughly quadratically with sequence length, and price is billed per input/output token.

Real-World Example

A coding agent starts a session with a 1,500-token system prompt and pastes an 18,000-token file. After 30 turns of back-and-forth plus verbose tool logs, the "input" alone approaches the window ceiling. The next tool result is rejected because there is no room left for the model to actually respond.

Tips & Tricks

  • Always reserve output headroom explicitly (e.g., leave 10–20% for max_tokens) — never plan to fill the window with input.
  • Instrument a live token counter per turn; track input growth, not just message count.
  • Treat the system prompt as fixed overhead — keep it lean; it is paid on every single call.
  • Estimate early: ~4 chars ≈ 1 token for English; code and JSON are token-dense.

Common Pitfalls

  • Assuming a "big" window means you never have to manage it — cost and latency still scale linearly with what you send.
  • Counting turns instead of tokens; one pasted document can equal 100 chat turns.
  • Forgetting that the window is shared by input and output — a full input can leave no room to reply.

Exam Strategy

Expect calculation / allocation MCQs: "Given a system prompt of X tokens, a Y-token document, and Z tokens reserved for output, how many tokens remain for conversation history?" Also "why did the request fail?" scenarios where the answer is input+output exceeded the window. Approach: subtract fixed consumers (system, docs, output reserve) from the window first, then reason about what's left for history.

Quick Recall: The context window is a single fixed token budget shared by input and output; because Claude is stateless, cumulative history is re-sent every turn — manage tokens, not turns.

24.2 Context Overflow & Truncation Problem · Hard Loss

Definition / Concept

Overflow is what happens when the assembled prompt exceeds the window. Truncation is the crude fix: dropping tokens — usually the oldest turns (a sliding window) — so the request fits. This is hard, irreversible information loss: dropped content is simply gone from the model's view.

Key idea: Truncation is silent by default. The model doesn't announce "I forgot turn 3" — it just answers as if that content never existed.

Why It Happens / Root Cause

  • Fixed ceiling met by growing history: once cumulative tokens exceed the window, something must be removed or the call errors.
  • Naive eviction policy: the common default is FIFO (drop the earliest messages), which often evicts the most important setup facts (customer ID, original goal, constraints stated up front).
  • System-prompt pinning gaps: if the framework doesn't protect key content, it can be evicted alongside chit-chat.

Real-World Example

In turn 1 a customer gives order ID #88213 and a refund amount $129.99. Twenty turns later the sliding window has evicted turn 1. The agent, asked to "process the refund we discussed," now has no order ID — it hallucinates a plausible-looking one or asks the customer to repeat information they already gave, eroding trust.

Tips & Tricks

  • Never rely on raw truncation for anything that must persist — extract facts to a pinned block (see 24.5) before they can be evicted.
  • Prefer compaction/summarization (24.4) over blind eviction so early context survives in condensed form.
  • Pin the system prompt and a "case facts" region so the eviction policy can't touch them.
  • Set a proactive threshold (e.g., compact at ~70% window) instead of waiting for a hard overflow error.

Common Pitfalls

  • Believing "the model still remembers earlier turns" after truncation — it cannot see what was removed.
  • Letting FIFO eviction quietly delete the original task goal or key identifiers.
  • Only handling overflow reactively (after an error) rather than compacting ahead of the ceiling.

Exam Strategy

Look for "identify the flaw" and root-cause scenarios: an agent "forgets" a detail after many turns — the correct diagnosis is truncation/eviction, and the correct fix is fact extraction or summarization before eviction, not "use a bigger model." Beware distractors that blame the model's intelligence rather than the context pipeline.

Quick Recall: Overflow forces truncation; default FIFO eviction silently drops the oldest turns — which often hold setup facts. Extract or summarize before the window fills.

24.3 Attention Dilution & "Lost in the Middle" Problem · Soft Loss

Definition / Concept

Even when content fits in the window, the model may not use it well. "Lost in the middle" describes the empirically observed pattern where models retrieve information placed at the beginning and end of a long context more reliably than information buried in the middle. Attention dilution is the broader effect: as context grows, relevant signal competes with more distractors.

Key idea: This is soft loss — the facts are present but under-weighted. Position and signal-to-noise ratio matter, not just presence.

Why It Happens / Root Cause

  • Positional effects: primacy/recency-like biases mean edges of the context are attended to more strongly than the middle (documented by Liu et al., 2023, "Lost in the Middle").
  • Signal dilution: softmax attention spreads weight across many tokens; a needle fact competes with a large haystack of low-value tokens.
  • Distraction: irrelevant but topically-similar content can pull attention away from the truly relevant span.

Real-World Example

An agent is given 40 pages of policy plus the user question. The exact clause needed sits on page 20 (the middle). The model answers using a more prominent clause from page 1, producing a confidently wrong response — despite the correct text being "in context."

Illustrative pattern: recall is a "U-shape" — strong at the edges, weak in the middle.

Tips & Tricks

  • Position matters: place the most critical facts and the actual instruction at the start or the very end of the prompt.
  • Put the question after the documents (or restate it at the end) so the ask sits in a high-recall position.
  • Reduce the haystack: retrieve only relevant chunks (24.7) instead of dumping everything.
  • Use structured highlighting (headers, a "CASE FACTS" block) to make key spans stand out.

Common Pitfalls

  • Assuming "if it's in the window, the model will use it" — presence ≠ reliable retrieval.
  • Burying the actual instruction in the middle of a huge context.
  • Stuffing more context to "be safe," which increases dilution and lowers accuracy.

Exam Strategy

Scenario MCQs will show a correct answer that exists in the provided context yet the agent got it wrong; the tested insight is positional recall / dilution, with the fix being reduce & reposition (retrieve relevant chunks, put key facts at edges) rather than "add more context." Watch for the trap answer "increase the context window."

Quick Recall: Fitting ≠ using. Models recall edges better than the middle ("lost in the middle"); keep contexts lean and put critical facts and the instruction at the start or end.

24.4 Progressive Summarization & Compaction Mitigation

Definition / Concept

Progressive summarization (a.k.a. compaction) replaces older raw turns with a running condensed summary, so the conversation's meaning survives at a fraction of the token cost. It's the primary defense against overflow while preserving continuity.

Key idea: Trade fidelity for capacity — condense what happened so the window keeps room for what happens next.

Why It Happens / Root Cause (why it's needed & how it works)

  • Mechanism: when history nears a threshold, the older segment is fed to the model with a "summarize this" instruction; the raw turns are then replaced by the summary in subsequent prompts.
  • Lossy compression: summarization is inherently lossy — it keeps gist and can drop exact specifics (numbers, IDs, dates) unless explicitly told to preserve them.
  • Rolling vs. hierarchical: you can summarize on a rolling basis (summary + last N raw turns) or hierarchically (summaries of summaries) for very long sessions.

Real-World Example

A 60-turn planning session is compacted every 20 turns into a 300-token "state so far" block. The agent stays coherent about decisions made hours ago — but the first naive summary dropped the exact budget figure $47,500, which had to be re-anchored via a structured facts block (24.5).

Tips & Tricks

  • Use a structured summary template (Goal / Decisions / Open items / Key facts) — free-form summaries drift and drop specifics.
  • Extract critical facts first (24.5), then summarize the prose — protect IDs, amounts, and dates from lossy compression.
  • Keep the last N turns verbatim so fine-grained recent detail (needed for the next reply) isn't blurred.
  • Summarize on a threshold (e.g., ~70% window), not every turn — over-summarizing wastes calls and compounds loss.

Common Pitfalls

  • Summarizing exact figures/IDs into vague prose ("a refund was discussed") — losing the data the task needs.
  • Summaries-of-summaries drifting further from the truth each cycle (compounding error).
  • Compacting the most recent turn and losing the immediate detail needed to answer.

Exam Strategy

Expect "what did summarization risk losing?" and "best-practice ordering" questions. The high-scoring answer usually pairs summarization with structured fact extraction and keeps recent turns raw. A classic distractor: "summarize everything including the latest turn" — wrong, because recent detail must stay verbatim.

Quick Recall: Compaction condenses old turns into a running summary to save tokens — but it's lossy; extract exact facts first and keep the last few turns verbatim.

24.5 Structured Fact Extraction & Persistent State Mitigation

Definition / Concept

Instead of hoping key data survives summarization, explicitly extract critical facts into a compact, structured block that is pinned to the top of every prompt. This persistent state / "case facts" block is the source of truth for identifiers, decisions, and constraints.

Key idea: Facts that must not be lost should live in a durable, structured region — not scattered across evictable prose.

Why It Happens / Root Cause (why it's needed)

  • Complements summarization: 24.4 preserves gist; 24.5 guarantees exact specifics that summarization would blur.
  • Placement leverages 24.3: pinning the block near the top (a high-recall position) makes the model attend to it reliably.
  • Machine-updatable: a structured schema (key: value) is easy to update, deduplicate, and validate across turns.

Real-World Example

The support agent maintains a pinned block updated each turn. When the conversation is later compacted, the order ID and amount remain exact because they live in the facts block, not in the summarized prose.

CASE FACTS (pinned, updated each turn):
- Customer ID:   88213
- Order Date:    2024-03-14
- Issue:         Refund not processed
- Amount:        $129.99
- Status:        Escalated to Tier 2 (turn 4)

Visualization — State Block vs. Summary Roles

Content typeWhere it livesGuarantee
Exact IDs, amounts, dates, decisionsStructured facts block (pinned, top)Lossless, high-recall
Narrative "what happened" gistRolling summary (24.4)Lossy but compact

Tips & Tricks

  • Define a fixed schema up front (IDs, dates, amounts, status, open actions) and update it every turn.
  • Pin it near the top of the prompt so it sits in a high-recall position and survives eviction.
  • Keep it terse — key:value lines, not paragraphs — so it stays cheap.
  • Have the model update the block explicitly as part of each turn's output, then feed it back next turn.

Common Pitfalls

  • Letting the facts block grow unbounded (append-only) until it becomes bloat itself — deduplicate and prune stale entries.
  • Storing prose instead of structured key:value pairs, reintroducing ambiguity.
  • Extracting facts but then forgetting to re-inject the block on subsequent turns.

Exam Strategy

MCQs frame this as the correct fix when a scenario shows lost exact data: "how do you guarantee the order ID survives 50 turns of summarization?" → maintain a pinned structured facts block. Recognize it as the complement to summarization, not an alternative.

Quick Recall: Extract must-keep specifics (IDs, amounts, dates, decisions) into a compact pinned key:value block — lossless, high-recall, and immune to summarization drift.

24.6 Tool-Output Management & Selective Retention Mitigation

Definition / Concept

Tool/API calls often return large, verbose payloads (full JSON, HTML, logs). Tool-output management means trimming, parsing, and selectively retaining only the fields the agent actually needs before those results re-enter the context on future turns.

Key idea: Raw tool output is frequently the single biggest, least-valuable consumer of the window. Keep the signal, drop the wrapper.

Why It Happens / Root Cause

  • APIs are verbose: a single response can be thousands of tokens of metadata, pagination, and nesting — most irrelevant to the task.
  • Accumulation: in an agentic loop, every tool call's full output can persist in history, multiplying bloat across turns.
  • Token density: JSON/HTML is token-heavy (braces, quotes, keys), so raw payloads cost disproportionately.

Real-World Example

An order-lookup tool returns a 2,000-token JSON object. The agent only needs 5 fields (status, amount, date, ID, ETA). Retaining the full blob across 10 turns would waste ~20,000 tokens; retaining a 5-field digest costs ~50 tokens per turn.

Visualization — Before vs. After Trimming

Tips & Tricks

  • Parse then persist: extract the needed fields outside the model and inject only the digest, not the raw payload.
  • Summarize large results (e.g., long documents returned by a tool) before they enter history.
  • Keep the full raw output only for the current turn if needed, then collapse it to a digest afterward.
  • Store bulky results externally (24.7) and pass a reference/ID instead of the payload.

Common Pitfalls

  • Dumping raw JSON straight into context and leaving it there every subsequent turn.
  • Over-trimming — removing a field the next step actually needs, forcing a re-call.
  • Ignoring tool output as a context consumer because it "isn't chat" — it counts against the same window.

Exam Strategy

Expect before/after token-math questions and "which change most reduces context growth?" — trimming verbose tool output is often the highest-impact single lever. Distractors suggest summarizing chat while ignoring the far larger tool payloads.

Quick Recall: Verbose tool/API output is often the biggest context hog — parse it down to the few needed fields (or an external reference) before it re-enters history.

24.7 Retrieval-Augmented Context / External Memory Mitigation

Definition / Concept

Retrieval-Augmented Generation (RAG) and external memory move the bulk of knowledge out of the context window and into a store (vector DB, database, files). At each turn, only the most relevant chunks are retrieved and injected — turning "keep everything in context" into "fetch what's needed, when it's needed."

Key idea: The window becomes a working set, not a warehouse. Long-term memory lives externally and is queried on demand.

Why It Happens / Root Cause (how it works)

  • Embedding + similarity search: documents/turns are embedded into vectors; a query embedding retrieves the top-k most similar chunks.
  • Decouples knowledge from window size: a store can hold gigabytes; only a few relevant chunks enter the prompt.
  • Directly fights dilution (24.3): retrieving only relevant chunks raises signal-to-noise and improves recall.

Real-World Example

A support agent embeds the full 500-page product manual once. When a user asks about "warranty on refurbished units," it retrieves the 3 relevant paragraphs (~600 tokens) instead of stuffing the whole manual — cheaper, faster, and more accurate.

Tips & Tricks

  • Chunk thoughtfully: right-sized, semantically coherent chunks retrieve better than arbitrary splits.
  • Tune top-k: too few misses context, too many reintroduces dilution — retrieve the minimum that answers.
  • Use metadata filters (date, source, customer) to narrow before similarity search.
  • Combine with a facts block (24.5): RAG for knowledge, structured state for session-specific identifiers.

Common Pitfalls

  • Retrieving too many chunks and recreating the very dilution RAG was meant to solve.
  • Poor chunking/embeddings → retrieving irrelevant passages (garbage in, garbage out).
  • Treating RAG as a replacement for session state — it retrieves knowledge, not the live conversation's exact IDs.

Exam Strategy

Questions contrast "put it all in context" vs. "retrieve on demand" for large/static knowledge bases — RAG is the scalable answer. Also expect "why did RAG return a wrong passage?" (chunking/embedding quality) and "RAG vs. structured state" distinctions (knowledge vs. session facts).

Quick Recall: RAG keeps bulk knowledge in an external store and injects only the top-k relevant chunks per turn — the window becomes a working set, not a warehouse.

24.8 Hands-On: Optimizing a Multi-Turn Support Session Lab

Definition / Concept

This lab applies the full mitigation toolkit (24.4–24.7) to a realistic support session that suffers growing context bloat. You'll see a Before (verbose, unoptimized) transcript, an After (optimized) version, and a per-turn walkthrough of what technique was applied and why.

Scenario

A customer contacts support about a failed refund. The agent must look up the order (tool call), escalate, check policy (knowledge base), and confirm resolution — across ~7 turns. Watch the token cost diverge.

BEFORE — Unoptimized (context grows every turn)

[SYSTEM] You are a support agent... (1,500 tokens)

[T1 User] Hi, my refund for order #88213 ($129.99, ordered 2024-03-14) hasn't come through.
[T1 Agent] Let me look that up.
→ TOOL get_order(88213) returns FULL 2,000-token JSON (all fields, metadata, history) — kept verbatim in context

[T2 User] Any update?
[T2 Agent] Checking payment status...
→ TOOL get_payment(88213) returns ANOTHER 1,800-token JSON — kept verbatim

[T3 User] Is it a policy issue?
[T3 Agent] Let me check the refund policy.
→ ENTIRE 40-page refund policy pasted into context (~30,000 tokens)

[T4 User] So what now?
[T4 Agent] Escalating to Tier 2.  (all prior raw turns + 2 huge JSONs + full policy still present)

[T5 User] Can you confirm my order number again?
[T5 Agent] ...order #88213 has now been EVICTED by truncation — agent asks user to repeat it ✖

RESULT: context near ceiling by T4; by T5 the earliest turn (with the order ID) is truncated.
Cost balloons every turn; recall of the key ID is lost (24.2) and the needed policy clause is
"lost in the middle" of 30k tokens (24.3).

[T1 Agent] Looking it up.

[T2 User] Update?

[T3 User] Policy issue?
[T3 Agent] → RAG retrieves ONLY the 2 relevant clauses (~500 tokens) from the policy store (24.7)
Per policy §4.2, card refunds take 5–7 business days; yours is day 8 → eligible for manual push.

[T4 User] So what now?
[T4 Agent] Escalating to Tier 2.  → updates CASE FACTS: Status = "Escalated T2 (T4)" (24.5)
→ Turns 1–2 raw exchanges COMPACTED into 1-line summary (24.4): "Looked up order+payment; refund pending, gateway OK."

[T5 User] Confirm my order number?
[T5 Agent] Order #88213, $129.99 — still exact, read from pinned CASE FACTS ✔ (survives — 24.5)

[T6 User] Great, when will I see it?
[T6 Agent] Manual refund pushed; 1–2 business days per §4.2 (retrieved clause still available). ✔

RESULT: context stays flat and small. Order ID never lost; policy answer accurate;
cost per turn ~constant instead of exploding.

Tips & Tricks

  • Layer the techniques — facts block + digests + RAG + compaction compound; no single one suffices.

  • Compacting the most recent turn and losing detail needed to answer the next message.
