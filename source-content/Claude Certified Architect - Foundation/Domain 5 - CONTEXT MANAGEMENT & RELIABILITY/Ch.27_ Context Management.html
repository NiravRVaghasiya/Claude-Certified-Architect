27.1 Subagent Delegation for Isolating Verbose Exploration Output

Concept Overview

Exploring a large codebase generates a lot of low-signal, high-volume output — directory listings, grep hits, full file contents, dependency trees. If all of that lands in the main conversation, it crowds out the reasoning space you actually need. Subagent delegation pushes that noisy work into a separate agent with its own context window, so the parent only ever sees the conclusion.

Key Mechanics

  • Separate context window. A subagent (spawned via the Task tool / general-purpose agent) runs with its own fresh context. Conceptually, the tokens it burns reading files do not accumulate in the parent's window.
  • Only the final message returns. The parent receives the subagent's final summary text — not its intermediate tool calls, file dumps, or scratch reasoning.
  • One-way, stateless hand-off. The subagent cannot see the parent's future turns and typically cannot ask follow-up questions mid-task. You brief it once with a clear objective; it reports back once.
  • Parallelizable. Independent exploration tasks (e.g. "map the auth module" and "map the billing module") can be dispatched to multiple subagents at once, each isolating its own output.

💡 Tips & Tricks
  • Delegate when the output is bulky but the answer is small — that gap is exactly what a subagent collapses.
  • Give the subagent a crisp deliverable ("return the file paths and the function that handles retries"), not a vague verb ("look around").
  • Common mistake: delegating a task that needs tight back-and-forth. Subagents can't easily interrogate you mid-run — use them for self-contained investigation, not interactive design.
  • Don't delegate trivially small lookups — the round-trip overhead isn't worth it for a single-file read.
🎯 Likely Question Pattern: "An agent must inspect 200 files but the user only needs one answer. What keeps the main context window from filling up?"
Answer Approach: Keywords "many files" + "main context window" → Subagent Delegation (27.1). The correct answer isolates verbose work in a subagent's separate context and returns only the final summary. Distractors that mention "read all files into the main agent" or "increase temperature" are wrong.
🧠 If you remember only 3 things
  1. A subagent has its own context window — its verbose output never touches the parent.
  2. Only the subagent's final message returns to the main agent.
  3. Delegate when output is large but the answer is small.
Practice

Scenario: Your agent needs to find every place a deprecated LegacyLogger class is instantiated across a 600-file repo. Reading each match inflates the conversation. What's the context-optimal move?

Show reasoning & answer

Delegate the search to a subagent and ask it to return only a list of file:line locations plus a one-line note on how each is used.

Reasoning: The raw grep output and surrounding code could be thousands of tokens, but the useful result is a compact list. Isolating the search inside a subagent means those thousands of tokens are spent in the subagent's window; the parent receives only the distilled inventory it needs to plan the refactor.

27.2 The Explore Subagent: Returning Summaries to Preserve Main Context

Concept Overview

27.1 established why to delegate. The Explore subagent is the concrete pattern for how: a read-only investigator whose sole job is to explore an area of the codebase and hand back a structured summary. Its value is entirely in the shape of what it returns — a good Explore subagent answers "what did you find and where," not "here is everything I saw."

Key Mechanics

  • Read-only by convention. An Explore subagent investigates and reports; it doesn't edit files. Keeping it read-only makes its output predictable and safe to run in parallel.
  • Summary contract. You specify the return format up front: key files, entry points, data flow, and open questions — not raw file contents.
  • Context asymmetry. The subagent may read tens of thousands of tokens internally, yet return only a few hundred. This asymmetry is the entire point — it's a lossy-but-lossless-on-signal compressor.
  • Pointers over payloads. A well-designed summary returns references (file paths, symbol names, line ranges) so the parent can pull exact detail later only if needed.

Visualization

💡 Tips & Tricks
  • Dictate the summary schema in your delegation prompt: "Return: (1) relevant files, (2) entry point, (3) data flow in ≤5 bullets, (4) anything ambiguous."
  • Ask for pointers, not payloads — file paths and symbol names let you fetch detail precisely later.
  • Common mistake: letting the subagent "be helpful" by dumping full snippets. That silently re-imports the verbosity you delegated away. Explicitly forbid raw file dumps.
  • Request an "open questions" field — it surfaces gaps to explore next instead of hiding them.
🎯 Likely Question Pattern: "A subagent explored a module and returned the full contents of every file it opened. What went wrong, and what should it return instead?"
Answer Approach: The failure is that the subagent re-imported verbosity into the parent, defeating the purpose. Correct answer: return a structured summary with pointers (files, entry points, data flow, open questions). Watch for distractors praising "completeness" — in context management, completeness of raw output is a bug, not a feature.
🧠 If you remember only 3 things
  1. The Explore subagent's job is the return shape: summary, not dump.
  2. Return pointers (paths/symbols), not payloads — fetch detail later on demand.
  3. Specify the summary schema in the prompt, and forbid raw file contents.
Practice

Scenario: You dispatch an Explore subagent to understand a payments module. It returns 4,000 tokens — mostly pasted source. Your main context is now 60% consumed after one delegation. What do you change?

Show reasoning & answer

Re-run with an explicit summary contract: ask for a ≤300-token structured report — key files, the charge entry point, the flow in bullets, and open questions — and explicitly instruct it not to paste file contents.

Reasoning: The subagent isolated the reading correctly, but its return broke the contract. Context preservation depends on the summary being small and signal-dense. Constraining the output shape (and forbidding payload dumps) restores the asymmetry that makes the Explore pattern worthwhile.

27.3 Progressive Context Building: Start Narrow, Expand as Needed

Concept Overview

Rather than front-loading the whole repository, progressive context building starts with the smallest useful slice — one file, one function, one entry point — and expands only where evidence says to. Context is spent lazily, guided by discovered gaps, so the window fills with relevant signal instead of speculative bulk.

Key Mechanics

  • Narrow first. Begin at a single anchor (the file the user mentioned, the failing test, main). Understand it before widening.
  • Gap-driven expansion. Each step reveals what you don't yet know — an imported module, an unseen caller. Those gaps, not a checklist, decide the next read.
  • Delegate the wide sweeps. When expansion means touching many files, hand that breadth to a subagent (27.1/27.2) so only its summary re-enters your window.
  • Synthesize, then stop. Expand only until you can act. "Enough to answer" is the terminal condition — not "read everything."

Visualization

Start Narrow (single file) → Identify Gaps → Expand Scope (module) → Delegate Deep Dive (subagent) → Synthesize Summary

Narrow → gap → expand → delegate → synthesize. Each arrow is justified by a discovered gap, never by "just in case."

💡 Tips & Tricks
  • Treat context budget like money: spend on the file in front of you, not on hypothetical files you might need.
  • After each read, ask "what's the smallest next thing that unblocks me?" — let the answer drive scope.
  • Common mistake: "read the whole repo first, then think." This exhausts context before reasoning begins and buries signal under noise.
  • Pair with delegation: progressive building decides what to look at next; subagents keep the wide steps from bloating your window.
🎯 Likely Question Pattern: "Which strategy uses the context window most efficiently when debugging an unfamiliar service?" with options ranging from "load all files upfront" to "start from the failing test and expand as gaps appear."
Answer Approach: Efficiency + unfamiliar + debugging → Progressive Context Building (27.3). Choose the option that starts narrow and expands on evidence. Reject any "load everything first" option — bulk-loading is the canonical wrong answer in context-management questions.
🧠 If you remember only 3 things
  1. Start narrow at one anchor; understand it before widening.
  2. Let discovered gaps — not a checklist — drive each expansion.
  3. Stop at "enough to act," and delegate the wide sweeps.
Practice

Scenario: A user reports a bug in checkout. You could (A) read the entire /checkout directory immediately, or (B) start at the failing test, follow its imports, and widen only where the trace leads. Which is more context-disciplined, and why?

Show reasoning & answer

Option B — start at the failing test and expand along the actual code path.

Reasoning: Option A spends context on files that may be irrelevant to this bug, filling the window with noise before any reasoning happens. Option B is gap-driven: each file you open is justified by the trace, so the context accumulates only relevant signal. If the trace fans out into many files, delegate that breadth to a subagent so only the summary returns.

27.4 Hands-On: Exploring a Legacy Codebase with Context Discipline

Concept Overview

This lab stitches 27.1–27.3 together on a realistic target: a sprawling, poorly documented legacy repo where a single "add a feature" request could naïvely consume your entire context. The discipline is to combine progressive building (what to look at) with delegated exploration (how to look without bloating the window).

Key Mechanics — the disciplined walkthrough

  1. Anchor narrow. Start from the one artifact you were given — a ticket, a stack trace, a function name. Read just that.
  2. Map before diving. Delegate a read-only Explore subagent to return the repo's high-level structure: top-level modules, entry points, and where the relevant subsystem lives — as pointers, not contents.
  3. Expand on the gap. Using the map, identify the single module that matters and pull just that into the main context.
  4. Delegate the deep dive. For the verbose "trace every caller / every dependency" step, dispatch another subagent; take back only its structured summary.
  5. Synthesize & act. Now the main context holds a clean picture: anchor + map + targeted detail. Make the change with room to reason.

Visualization — end-to-end context flow

Ticket / stack trace → Explore sub: repo map → Pull target module → Explore sub: caller trace → Synthesize & implement

Two subagent hops carry all the verbose reading; the main context only ever holds the anchor, the map, and the targeted detail.

💡 Tips & Tricks
  • In legacy code, map before you dive — a subagent-produced overview prevents you from wandering (and burning context) in the wrong subsystem.
  • Keep a running mental index of pointers (paths/symbols) in the main context; fetch bodies only at the moment of editing.
  • Common mistake: opening files "to get oriented." Orientation is a delegated job — a subagent orients and reports; the parent stays clean.
  • If the main context still bloats, you're returning payloads somewhere — audit each subagent's return shape (27.2).
🎯 Likely Question Pattern: "Given a 500-file legacy repo and a feature request, which sequence minimizes context-window usage?" — often an ordering / multi-select question.
Answer Approach: Keywords "legacy," "large codebase," "minimize context" → combine Subagent Delegation (27.1) + Explore summaries (27.2) + Progressive Building (27.3). The correct sequence is anchor narrow → delegate a map → expand to the target → delegate the deep dive → synthesize. Any answer that begins with "read/index all 500 files into the main agent" is the trap.
🧠 If you remember only 3 things
  1. Map before you dive — delegate the repo overview first.
  2. Every wide step is a subagent hop; the parent holds pointers + targeted detail only.
  3. The techniques compose: progressive decides what, delegation controls how much comes back.
Practice

Scenario: You must add a rate-limit header to responses in a 500-file legacy API with no docs. Outline the context-disciplined sequence, and name the technique behind each step.

Show reasoning & answer

Anchor → map → expand → delegate → synthesize:

  1. Anchor on the response/middleware entry point you were given (Progressive, 27.3).
  2. Delegate a repo map to an Explore subagent — where does response handling live? Return pointers (27.2).
  3. Pull just the middleware module into main context (Progressive expand, 27.3).
  4. Delegate a caller/usage trace for that middleware; take back a summary (Delegation, 27.1).
  5. Synthesize and add the header with a clean context.

Reasoning: No single step dumps hundreds of files into the parent. Breadth is always delegated; the main window only ever grows by small, justified, signal-dense additions.
