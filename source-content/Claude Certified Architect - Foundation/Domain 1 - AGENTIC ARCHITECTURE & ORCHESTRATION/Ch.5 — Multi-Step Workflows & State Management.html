5.1 Designing Multi-Step Workflows with Intermediate Verification

🔵 Core Concept

Multi-step workflows decompose a complex AI task into discrete, bounded stages, where each stage produces an explicit intermediate artifact that can be independently verified before the next stage begins. The fundamental principle is: never let an error in Step N propagate silently into Step N+1. This pattern trades a small amount of latency for dramatically higher reliability, debuggability, and user trust.

Why Decompose?

Large, monolithic prompts that attempt an entire complex task in a single pass suffer from three failure modes the exam will test you on:

  1. Error Compounding — A subtle mistake in early reasoning poisons all downstream output, with no way to isolate the failure point.
  2. Opaque Debugging — When a single-pass output is wrong, there is no intermediate state to inspect; you must re-run everything from scratch.
  3. Wasted Compute — If Step 8 out of 10 fails, a monolithic pipeline forces you to redo Steps 1–7, even though they were correct.

Key Principles of Decomposition

PrincipleDescriptionExam Relevance
Single Responsibility Each step should do exactly one thing — parse, transform, validate, generate, or review Questions may present a step that does too much and ask you to identify the violation
Explicit Artifact Boundary Every step must produce a named, typed output artifact (e.g., a structured JSON object, a file, a validated record) Distinguish from implicit state (context window contents) vs. explicit state (persisted artifact)
Verifiability The artifact produced by each step must be checkable against defined criteria before the next step consumes it Core to Sections 5.1 and 5.2 — the interplay between these is heavily tested
Idempotency Re-running a step with the same input must produce the same output (or at minimum, not corrupt state) Critical for crash recovery (5.4) — expect questions about what breaks when a step is not idempotent
Loose Coupling Steps communicate only through their explicit artifacts, never through shared mutable state or side channels Trap answers often introduce hidden dependencies between steps

How It Works — Step-by-Step

┌─────────────────────────────────────────────────────────────────────┐ │ MULTI-STEP WORKFLOW ANATOMY │ └─────────────────────────────────────────────────────────────────────┘ [ Input ] │ ▼ ┌──────────────────┐ artifact_0 │ Step 1: Parse │────────▶ { structured_input } └──────────────────┘ │ ▼ ◆ Verify: schema valid? ── FAIL ──▶ Halt & Report │ PASS │ ▼ ┌──────────────────┐ artifact_1 │ Step 2: Enrich │────────▶ { enriched_data } └──────────────────┘ │ ▼ ◆ Verify: completeness? ── FAIL ──▶ Retry / Remediate │ PASS │ ▼ ┌──────────────────┐ artifact_2 │ Step 3: Generate │────────▶ { final_output } └──────────────────┘ │ ▼ ◆ Verify: quality check │ PASS │ ▼ [ Output Delivered ]

Design Heuristics for Step Boundaries

Where should you place step boundaries? Look for these natural seams:

  • Data format changes — If the representation changes (e.g., raw text → JSON → SQL), that is a step boundary.
  • Domain transitions — If the task crosses domains (e.g., parsing → reasoning → code generation), each domain is a step.
  • Risk boundaries — If a sub-task is expensive, external-facing, or irreversible (API call, database write, email send), isolate it as its own step with a preceding verification gate.
  • Review points — If a human or model review is desirable, place a step boundary there.
🔴 Common Pitfall

Over-decomposition: Splitting a task into too many tiny steps introduces excessive latency and checkpoint overhead. The exam may present a 15-step pipeline and ask which steps should be merged. The answer: merge steps that share the same domain, have no useful verification between them, and always succeed or fail together.

Implicit state leakage: Candidates often forget that the LLM's context window is implicit state. If you rely on the model "remembering" an artifact from 3 turns ago without explicitly passing it, you have created a hidden dependency that breaks on context overflow.

💡 Exam Tip — Section 5.1

When a question asks "what is the PRIMARY benefit of multi-step decomposition," the answer is intermediate verification and error isolation, NOT "parallel execution" or "reduced token usage." While those may be secondary benefits in some cases, the architectural motivation is always fault isolation.

5.2 Verification Gates Between Workflow Steps

🔵 Core Concept

A verification gate is a programmatic or model-driven checkpoint positioned between workflow steps that validates the output of the preceding step against defined criteria. Gates enforce a pass/fail contract: execution proceeds only on pass; on fail, the system halts, logs, and triggers a remediation strategy (retry, fallback, or escalation). Gates are the immune system of the pipeline — without them, corrupted data flows silently downstream.

Key Terminology

TermDefinitionExam Tip
Verification Gate A checkpoint that validates the output of Step N before Step N+1 begins execution Often tested in "what happens if X fails" scenarios — the gate determines the response
Structural Validation Checks that the artifact conforms to an expected schema, type, or format (e.g., JSON schema validation) Cheapest and fastest gate type — always apply first before more expensive checks
Semantic Validation Uses a second LLM call (or judge model) to evaluate whether the content is logically correct, coherent, or aligned with intent More expensive but catches errors structural checks miss — exam tests when to use which
Constraint Validation Checks domain-specific business rules (e.g., "total must not exceed budget," "all referenced IDs must exist") Often the right answer for "which validation catches X" questions involving business logic
Gate Disposition The action taken on gate failure: HALT, RETRY, FALLBACK, or ESCALATE Know all four — questions may ask which disposition is correct for a given scenario
Retry Budget A finite limit on how many times a failed step may be retried before escalation or halt Without a retry budget, you risk infinite loops — the exam expects you to know this

Gate Types & When to Use Them

╔══════════════════════════════════════════════════════════════════╗ ║ VERIFICATION GATE SELECTION MATRIX ║ ╚══════════════════════════════════════════════════════════════════╝ Level 1: STRUCTURAL (always first, zero LLM cost) ├── Schema validation (JSON Schema, Pydantic, Zod) ├── Type checking (expected fields exist, correct types) ├── Length / size constraints (min/max tokens, array bounds) └── Format adherence (regex for dates, emails, IDs) Level 2: CONSTRAINT (domain logic, usually deterministic) ├── Business rules (total ≤ budget, deadline in future) ├── Referential integrity (all IDs resolve to real entities) ├── Uniqueness / deduplication checks └── Cross-field consistency (start_date < end_date) Level 3: SEMANTIC (most expensive, uses LLM or judge model) ├── Coherence check (does the output make logical sense?) ├── Completeness check (are all requested components present?) ├── Alignment check (does the output match the original intent?) └── Quality scoring (rubric-based evaluation by a judge model)

Retry Strategies

StrategyWhen to UseImplementation
Simple Retry Non-deterministic failures (LLM variance, transient API errors) Re-invoke the same step with identical input, up to max_retries
Retry with Feedback The output was wrong but fixable (e.g., missing a field, wrong format) Append the failure reason to the prompt: "Previous attempt failed because: {reason}. Fix and retry."
Retry with Escalation A simpler model failed; a more capable model may succeed Re-invoke with a higher-tier model (e.g., Haiku → Sonnet → Opus)

🔴 Common Pitfall

"Silent continue" trap: The #1 wrong answer pattern in verification gate questions is an option that says "log the error and continue to the next step." The correct answer almost always includes halting execution before remediation. Skipping the halt means corrupted data reaches downstream steps.

Unbounded retries: Any retry mechanism without a finite retry budget is a defect. Exam answers that propose "retry until success" without a limit are always wrong.

💡 Exam Tip — Section 5.2

When a question asks "what should happen when a verification gate fails," look for the answer that includes all three components: halt → log → remediate. If an option skips the logging step, it's a trap. If an option skips the halt, it's a trap. The correct answer is the one with the complete protocol.

For "which gate type" questions, apply the cheapest-first heuristic: structural before constraint before semantic. An answer that jumps straight to LLM-based semantic validation when a JSON schema check would suffice is the wrong answer.

5.3 Explicit State Persistence: Progress Manifests & Checkpoint Files

🔵 Core Concept

In a multi-step workflow, explicit state persistence is the practice of writing the workflow's progress and intermediate results to durable storage after each successful step. This is achieved through two complementary mechanisms: the progress manifest (a high-level ledger of which steps completed) and checkpoint files (granular snapshots of each step's output data). Together, they form the foundation for crash recovery (5.4) and session management (5.5).

Key Terminology

TermDefinitionExam Tip
Progress Manifest A persistent metadata record tracking which workflow steps have completed, their status, timestamps, and any error information. Acts as the pipeline's "table of contents." Distinguish from checkpoint files: the manifest tracks status; checkpoints store data
Checkpoint File A durable snapshot of a single step's output artifact, written to storage upon successful verification. Contains the actual data needed to resume. Granularity matters: one checkpoint per step, not one per workflow
Explicit State State that is intentionally serialized and persisted to storage (files, DB, object store) — as opposed to implicit state held only in memory or context window The exam contrasts explicit vs. implicit state frequently
Implicit State State that exists only in transient memory: LLM context window, in-process variables, unwritten buffers Implicit state is lost on crash — a core vulnerability the chapter addresses
Atomic Write A write operation that either completes fully or not at all — no partial/corrupted files Critical for checkpoint integrity; the write-then-rename pattern is the standard technique
State Schema Versioning Including a version number in checkpoint/manifest format so older checkpoints can be migrated or rejected when the pipeline code changes Often overlooked by candidates — expect a question about what happens when pipeline code changes

How Manifests & Checkpoints Work Together

┌──────────────────────────────────────────────────────────────────┐ │ MANIFEST + CHECKPOINT INTERACTION MODEL │ └──────────────────────────────────────────────────────────────────┘ Progress Manifest Checkpoint Files (status ledger) (data snapshots) ┌─────────────────────┐ ┌─────────────────────┐ │ step_0: completed │───────────────▶│ step_0_parse.json │ │ step_1: completed │───────────────▶│ step_1_enrich.json │ │ step_2: failed │ (no checkpoint — step failed) │ step_3: pending │ │ step_4: pending │ └─────────────────────┘ └─────────────────────┘ Recovery reads manifest → finds last "completed" → loads its checkpoint → resumes from step_2 with step_1's output data as input

Atomic Write Pattern

Checkpoint corruption is a real risk if the process crashes mid-write. The standard solution is the write-then-rename (or write-to-temp-then-move) pattern:

def save_checkpoint(step_id, data, checkpoint_dir):
    # 1. Write to a TEMPORARY file (incomplete data lives here)
    tmp_path = f"{checkpoint_dir}/{step_id}.tmp"
    with open(tmp_path, 'w') as f:
        json.dump(data, f)
        f.flush()
        os.fsync(f.fileno())   # Force write to disk

    # 2. Atomically RENAME to the final path
    #    (rename on same filesystem is atomic on POSIX)
    final_path = f"{checkpoint_dir}/{step_id}.json"
    os.rename(tmp_path, final_path)

    # 3. Update the manifest AFTER the checkpoint is safely written
    update_manifest(step_id, status="completed", checkpoint_ref=final_path)
🔴 Common Pitfall

Confusing manifest and checkpoint scope: The manifest answers "which steps are done?"; the checkpoint answers "what did that step produce?" They are complementary, not interchangeable. Candidates who treat the manifest as the checkpoint (or vice versa) will misdiagnose recovery scenarios.

Ignoring schema versioning: If the pipeline code changes between runs (e.g., Step 2 now expects an extra field), old checkpoints become incompatible. Without a schema_version field, the system may silently load stale data and produce wrong results.

💡 Exam Tip — Section 5.3

Any exam question about "what is lost when a process crashes" is testing your understanding of explicit vs. implicit state. The answer is: everything not yet written to a checkpoint is lost. Context window state, in-memory variables, partial outputs — all gone. Only completed, persisted checkpoints survive.

If a question asks about the order of operations when completing a step, the correct sequence is: (1) write checkpoint file atomically, (2) update manifest to "completed." Never the reverse — if you update the manifest first and crash before writing the checkpoint, the manifest says "done" but the data is missing.

5.4 Crash Recovery Using Checkpoint-Based Resumption

🔵 Core Concept

Crash recovery is the process of detecting that a workflow was interrupted (crash, timeout, resource exhaustion) and resuming execution from the last known good state rather than restarting from scratch. The recovery system reads the progress manifest to find the last completed step, loads its checkpoint data, and re-enters the pipeline at the next step. This requires that every step is either idempotent (safe to re-run) or skip-safe (the checkpoint proves it already completed).

Key Terminology

TermDefinitionExam Tip
Resumption Point The step index where execution resumes after recovery — always the first step whose status is NOT "completed" in the manifest Questions test: the resumption point is the failed or pending step, not the last completed step
Idempotent Step A step that produces the same result when executed multiple times with the same input, with no harmful side effects Essential for safe retries and recovery — the exam expects you to identify non-idempotent operations
Side-Effect Isolation Ensuring that steps with external side effects (API calls, DB writes, emails) are guarded so they don't double-fire on retry The classic "sent the email twice" scenario — know how to prevent it
Stale Checkpoint Detection Identifying when a checkpoint was written by an older version of the pipeline code and may be incompatible Schema version mismatch is the signal; the correct response is to invalidate and re-run, not silently proceed

Recovery Algorithm — Step by Step

┌──────────────────────────────────────────────────────────────────┐ │ CRASH RECOVERY ALGORITHM │ └──────────────────────────────────────────────────────────────────┘ [Pipeline Start / Restart] │ ▼ 1. Does a progress manifest exist? │ │ YES NO ──▶ Start fresh from Step 0 │ ▼ 2. Is schema_version compatible? │ │ YES NO ──▶ Invalidate all checkpoints │ ──▶ Start fresh from Step 0 ▼ 3. Find LAST step with status "completed" │ ▼ 4. Verify its checkpoint file exists & is intact │ │ YES NO ──▶ Walk backward until valid checkpoint found │ ▼ 5. Load checkpoint data as input │ ▼ 6. Resume execution at step (last_completed + 1)

Handling Non-Idempotent Steps

Some steps have external side effects that must not be repeated:

PatternMechanismExample
Idempotency Key Include a unique request ID; the external system deduplicates Payment API: include idempotency_key: "wf-a3b8-step3-attempt1"
Effect Log Before performing a side effect, check a local log of already-executed effects Before sending email, check: effects_log["send_email_to_user_42"] — if present, skip
Two-Phase Commit First "prepare" the side effect (reserve, draft), then "commit" only after verification Create email as draft → verify contents → send only on explicit commit
🔴 Common Pitfall

Resuming at the wrong step: A common mistake is resuming at the last completed step instead of the next step. If Steps 0–2 are completed and Step 3 is "failed," the resumption point is Step 3, not Step 2. Re-running Step 2 wastes compute (and risks non-idempotent side effects).

Assuming all steps are idempotent: LLM inference calls are idempotent (re-calling produces possibly different but valid output). But API calls, database writes, and message-sends are NOT inherently idempotent. The exam tests whether you can identify which steps need idempotency protection.

💡 Exam Tip — Section 5.4

If a question describes a pipeline that crashes after completing Steps 1–3 and asks "which component determines where execution resumes," the answer is the progress manifest / checkpoint file — NOT the session token (which tracks identity, not progress) and NOT the verification gate log (which records pass/fail results but doesn't store resumption state).

For questions about "what can go wrong during recovery," the top answers are: (1) stale/incompatible checkpoints, (2) missing checkpoint files, and (3) non-idempotent steps being re-executed.

5.5 Session State, Resumption & Forking (fork_session, Named Sessions)

🔵 Core Concept

Session state encapsulates the full context of a workflow execution: conversation history, accumulated artifacts, manifest state, and configuration. Session resumption reloads a previously suspended session to continue where it left off. Session forking (fork_session) creates a divergent copy of an active session — both the original and the fork continue independently from the same point, enabling parallel exploration, A/B testing, and what-if analysis. Named sessions give human-readable identifiers to sessions for easy retrieval and management.

Key Terminology

TermDefinitionExam Tip
Session State The complete snapshot of a workflow's execution context: conversation history, progress manifest, all checkpoint data, config, and metadata Broader than a checkpoint — session state = manifest + all checkpoints + context + config
Session Resumption Reloading a suspended or interrupted session and continuing execution from where it paused Resumption continues the same session; forking creates a new one — know the difference
fork_session An operation that creates a new, independent session by deep-copying the state of an existing session at a specific point in time The fork and the original are fully independent after the fork point — changes in one do NOT affect the other
Named Session A session identified by a human-readable label (e.g., "quarterly-report-v2") rather than only a system-generated UUID Named sessions enable explicit retrieval and management — important for long-running workflows
Fork Point The exact moment/state from which a fork diverges — both branches share all history up to this point Forks share the same history before the fork point and diverge after
Session Lineage The parent-child relationship between a forked session and its origin, enabling traceability Important for auditing and debugging — know that lineage metadata is preserved

Resumption vs. Forking — Comparison

DimensionSession ResumptionSession Forking
Intent Continue the same task from where it stopped Explore an alternative path without losing the original
Sessions After 1 session (the same one, extended) 2 sessions (original + fork, both active)
State Relationship Appends to existing state Deep-copies state; branches are independent
Use Case Crash recovery, pause/resume, context reload A/B testing, what-if analysis, parallel strategy exploration
Side Effect Risk Low — continuing a known path Higher — forked branches may repeat side effects if not guarded

Fork Architecture

┌──────────────────────────────────────────────────────────────────┐ │ SESSION FORKING MODEL │ └──────────────────────────────────────────────────────────────────┘ Session "main-report" ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Step 0 Step 1 Step 2 Step 3 ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ │ Parse │────▶│ Enrich │────▶│Analyze │────▶│Generate│ └────────┘ └────────┘ └────────┘ └────────┘ │ fork_session() │ ┌────┘ ▼ Session "main-report-aggressive" (Named fork) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ (Inherits Step 0–2 state) Step 3' Step 4' ┌────────┐ ┌────────┐ │Analyze │────▶│Generate│ │(alt. │ │(alt. │ │ params)│ │ output)│ └────────┘ └────────┘ Both sessions are now independent: • "main-report" continues with original parameters • "main-report-aggressive" explores alternative approach • Neither affects the other's state or checkpoints

Named Session Best Practices

  • Use descriptive, hierarchical names: "project-alpha/report/v3" is better than "session_12345"
  • Include intent in fork names: "report-conservative-tone" vs. "report-aggressive-tone" — makes A/B comparison legible
  • Set TTL (time-to-live): Named sessions should have expiration policies to avoid unbounded storage growth
  • Track lineage: Always record which session a fork originated from, and at which step
🔴 Common Pitfall

Confusing fork and resume: Resumption continues the same session (same ID, same lineage). Forking creates a new session (new ID, parent lineage reference). The exam will present scenarios where one is appropriate and the other is not — for example, "the client wants to see two different report styles" → fork, not resume.

Shared mutable state after fork: If two forked sessions write to the same external resource (database table, file, API endpoint) without coordination, they can create race conditions and data corruption. Forks must have isolated effect scopes.

💡 Exam Tip — Section 5.5

When a question asks about the difference between fork_session and session resumption, focus on two axes: (1) number of sessions after the operation (resume = 1, fork = 2) and (2) independence (resume = same path, fork = divergent paths). If the scenario involves exploring alternatives or parallel strategies, the answer is fork. If the scenario involves continuing interrupted work, the answer is resume.

For named session questions, the key insight is human-readable retrieval. Without named sessions, you need the system-generated UUID to find a session. Named sessions solve the "which session was the good one?" problem.

5.6 Hands-On: Building a Resilient Multi-Step Pipeline

🟢 Hands-On Section

This section applies every concept from 5.1–5.5 into a complete, annotated implementation of a resilient multi-step pipeline. The scenario: a document analysis pipeline that parses, enriches, analyzes, and generates a final report — with full verification gates, checkpoint persistence, crash recovery, and session support.

Complete Annotated Pseudocode Pipeline

# ═══════════════════════════════════════════════════════════════════
# RESILIENT MULTI-STEP PIPELINE — Complete Implementation
# Demonstrates: decomposition, verification gates, checkpoints,
#               crash recovery, idempotency, and session management.
# ═══════════════════════════════════════════════════════════════════

import json, os, time, hashlib
from datetime import datetime, timezone
from pathlib import Path

# ─── CONFIGURATION ───────────────────────────────────────────────
SCHEMA_VERSION  = 2          # Increment when step I/O contracts change
MAX_RETRIES     = 3          # Finite retry budget per step
CHECKPOINT_DIR  = "./checkpoints"
MANIFEST_PATH   = "./progress_manifest.json"


# ═══════════════════════════════════════════════════════════════════
# 1. MANIFEST & CHECKPOINT MANAGEMENT (Section 5.3)
# ═══════════════════════════════════════════════════════════════════

class WorkflowState:
    """Manages the progress manifest and checkpoint persistence.
    
    WHY: Explicit state persistence ensures that progress survives
    crashes. Without this, every failure restarts from zero.
    """

    def __init__(self, workflow_id: str, steps: list[str]):
        self.workflow_id = workflow_id
        self.steps = steps
        self.manifest = self._load_or_create_manifest()

    def _load_or_create_manifest(self) -> dict:
        """Load existing manifest (for recovery) or create a fresh one.
        
        WHY: On startup, we check for existing state to enable
        crash recovery (Section 5.4). A missing manifest means
        this is a fresh run.
        """
        if Path(MANIFEST_PATH).exists():
            manifest = json.loads(Path(MANIFEST_PATH).read_text())
            # CRITICAL: Validate schema version compatibility
            if manifest.get("schema_version") != SCHEMA_VERSION:
                print("⚠ Schema version mismatch — invalidating old state")
                return self._create_fresh_manifest()
            return manifest
        return self._create_fresh_manifest()

    def _create_fresh_manifest(self) -> dict:
        return {
            "workflow_id": self.workflow_id,
            "schema_version": SCHEMA_VERSION,
            "created_at": datetime.now(timezone.utc).isoformat(),
            "steps": [
                {"step_id": sid, "index": i, "status": "pending",
                 "checkpoint_ref": None, "retries": 0, "error": None}
                for i, sid in enumerate(self.steps)
            ]
        }

    def save_checkpoint(self, step_index: int, data: dict):
        """Atomically persist step output using write-then-rename.
        
        WHY: The atomic write pattern (Section 5.3) prevents
        corrupted checkpoint files from crashes during the write.
        """
        step = self.manifest["steps"][step_index]
        os.makedirs(CHECKPOINT_DIR, exist_ok=True)

        # Phase 1: Write to temp file
        tmp_path = f"{CHECKPOINT_DIR}/{step['step_id']}.tmp"
        with open(tmp_path, 'w') as f:
            json.dump(data, f, indent=2)
            f.flush()
            os.fsync(f.fileno())

        # Phase 2: Atomic rename
        final_path = f"{CHECKPOINT_DIR}/{step['step_id']}.json"
        os.rename(tmp_path, final_path)

        # Phase 3: Update manifest AFTER checkpoint is safe
        step["status"] = "completed"
        step["checkpoint_ref"] = final_path
        step["completed_at"] = datetime.now(timezone.utc).isoformat()
        self._persist_manifest()

    def load_checkpoint(self, step_index: int) -> dict:
        """Load the persisted output of a completed step."""
        ref = self.manifest["steps"][step_index]["checkpoint_ref"]
        if ref and Path(ref).exists():
            return json.loads(Path(ref).read_text())
        raise FileNotFoundError(f"Checkpoint missing for step {step_index}")

    def find_resumption_point(self) -> int:
        """Find the first non-completed step (Section 5.4).
        
        WHY: This is the core of crash recovery. We walk the
        manifest to find where to resume, NOT where we stopped.
        """
        for step in self.manifest["steps"]:
            if step["status"] != "completed":
                return step["index"]
        return len(self.manifest["steps"])  # All complete

    def _persist_manifest(self):
        self.manifest["updated_at"] = datetime.now(timezone.utc).isoformat()
        Path(MANIFEST_PATH).write_text(json.dumps(self.manifest, indent=2))


# ═══════════════════════════════════════════════════════════════════
# 2. VERIFICATION GATES (Section 5.2)
# ═══════════════════════════════════════════════════════════════════

class GateFailure(Exception):
    """Raised when a verification gate rejects step output."""
    def __init__(self, step_id: str, reason: str):
        self.step_id = step_id
        self.reason = reason
        super().__init__(f"Gate failed at {step_id}: {reason}")


def verify_structural(data: dict, required_keys: list[str]) -> bool:
    """Level 1 gate: cheapest check — schema/structure validation.
    
    WHY: Always run structural checks FIRST (cheapest-first heuristic).
    No LLM cost, millisecond execution.
    """
    return all(k in data for k in required_keys)


def verify_constraints(data: dict, rules: list[callable]) -> tuple[bool, str]:
    """Level 2 gate: domain-specific business logic checks.
    
    WHY: Catches semantic errors that structure checks miss,
    without the cost of an LLM call.
    """
    for rule in rules:
        ok, msg = rule(data)
        if not ok:
            return False, msg
    return True, ""


def verify_semantic(data: dict, criteria: str, llm_client) -> tuple[bool, str]:
    """Level 3 gate: LLM-based quality/coherence check.
    
    WHY: Most expensive gate — use only when structural and
    constraint checks cannot catch the class of errors you need
    to detect (e.g., logical coherence, completeness of reasoning).
    """
    response = llm_client.evaluate(
        prompt=f"Evaluate if this output meets: {criteria}\n\nOutput: {data}",
        response_format={"pass": bool, "reason": str}
    )
    return response["pass"], response.get("reason", "")

# 4. PIPELINE ORCHESTRATOR (Ties everything together)
# ═══════════════════════════════════════════════════════════════════

class ResilientPipeline:
    """Orchestrates multi-step execution with full resilience.
    
    Integrates: decomposition (5.1), gates (5.2), checkpoints (5.3),
    crash recovery (5.4), and session management (5.5).
    """

    def __init__(self, workflow_id: str, session_name: str = None):
        self.steps_config = [
            {
                "id": "parse",
                "fn": step_parse,
                "gate": lambda d: verify_structural(d, ["title", "sections"]),
                "gate_type": "structural",
            },
            {
                "id": "enrich",
                "fn": step_enrich,
                "gate": lambda d: verify_structural(d, ["enrichments"]),
                "gate_type": "structural",
            },
            {
                "id": "analyze",
                "fn": step_analyze,
                "gate": lambda d: verify_semantic(d, "complete analysis", llm),
                "gate_type": "semantic",
            },
            {
                "id": "generate",
                "fn": step_generate,
                "gate": lambda d: verify_structural(d, ["report", "summary"]),
                "gate_type": "structural",
            },
        ]
        step_ids = [s["id"] for s in self.steps_config]
        self.state = WorkflowState(workflow_id, step_ids)
        self.session_name = session_name or workflow_id

    def run(self, initial_input):
        """Execute the pipeline with crash recovery support.
        
        WHY: The resumption point check (Section 5.4) means this
        method handles both fresh runs AND recovery runs identically.
        """
        start_index = self.state.find_resumption_point()

        if start_index > 0:
            print(f"♻ Resuming from step {start_index} (recovered)")
            # Load the last completed step's output as input
            current_data = self.state.load_checkpoint(start_index - 1)
        else:
            print("▶ Starting fresh pipeline run")
            current_data = initial_input

        for i in range(start_index, len(self.steps_config)):
            step = self.steps_config[i]
            print(f"\n── Step {i}: {step['id']} ──")

            success = False
            for attempt in range(MAX_RETRIES):
                try:
                    # Execute the step
                    result = step["fn"](current_data)

                    # Run verification gate (Section 5.2)
                    gate_result = step["gate"](result)
                    if isinstance(gate_result, tuple):
                        passed, reason = gate_result
                    else:
                        passed, reason = gate_result, ""

                    if not passed:
                        raise GateFailure(step["id"], reason)

                    # Gate passed — persist checkpoint (Section 5.3)
                    self.state.save_checkpoint(i, result)
                    current_data = result
                    success = True
                    print(f"  ✓ Step {step['id']} completed (attempt {attempt+1})")
                    break

                except GateFailure as gf:
                    # HALT → LOG → REMEDIATE (retry with feedback)
                    print(f"  ✗ Gate failed: {gf.reason} (attempt {attempt+1})")
                    self.state.manifest["steps"][i]["retries"] = attempt + 1
                    self.state.manifest["steps"][i]["error"] = gf.reason
                    self.state._persist_manifest()

                    if attempt == MAX_RETRIES - 1:
                        print(f"  ✗ Retry budget exhausted — ESCALATING")
                        self.state.manifest["steps"][i]["status"] = "failed"
                        self.state._persist_manifest()
                        raise  # Escalate to caller

            if not success:
                break

        print("\n✅ Pipeline completed successfully")
        return current_data

    def fork(self, new_session_name: str) -> "ResilientPipeline":
        """Create a divergent copy of this pipeline (Section 5.5).
        
        WHY: fork_session enables exploring alternative strategies
        without losing the original execution path. Both branches
        continue independently.
        """
        import copy
        forked = ResilientPipeline(
            workflow_id=f"{self.state.workflow_id}-fork-{new_session_name}",
            session_name=new_session_name
        )
        # Deep copy current state — branches are independent after this
        forked.state.manifest = copy.deepcopy(self.state.manifest)
        forked.state.manifest["forked_from"] = self.state.workflow_id
        forked.state.manifest["fork_point"] = self.state.find_resumption_point() - 1
        forked.state._persist_manifest()
        return forked

Developer Checklist — Building a Resilient Pipeline

  • Decompose the task into steps with single responsibilities and explicit artifact boundaries
  • Define the output schema for each step — typed, versioned, documented
  • Add verification gates between every pair of adjacent steps (structural → constraint → semantic)
  • Set a retry budget for every step — no unbounded retries
  • Implement atomic checkpoint writes using the write-then-rename pattern
  • Design the progress manifest with schema_version, step status, timestamps, and checkpoint refs
  • Write the recovery algorithm — load manifest → find resumption point → load checkpoint → resume
  • Handle non-idempotent steps — use idempotency keys, effect logs, or two-phase commit
  • Validate schema version on recovery — reject incompatible checkpoints
  • Support named sessions — assign human-readable names for retrieval and management
  • Implement fork support — deep-copy state with lineage tracking for parallel exploration
  • Test the failure paths — simulate crashes at every step boundary and verify correct recovery
  • Add observability — log every gate result, retry attempt, and recovery event
💡 Exam Tip — Section 5.6

Hands-on questions typically present a pipeline with a deliberate flaw and ask you to identify it. Common flaws to watch for:

  • Missing verification gate between two steps
  • Checkpoint written after manifest update (wrong order)
  • No schema version in the manifest
  • Retry without a budget limit
  • Non-idempotent step without side-effect protection
  • Fork that shares mutable state with the original

Exam Strategy for Chapter 5

💡 Master Strategy

Chapter 5 questions revolve around failure handling and architectural decision-making. The exam writer's goal is to test whether you understand not just what happens on the happy path, but what happens when things go wrong — and which recovery mechanism addresses which failure mode.

Question Types to Expect

TypePatternStrategy
Scenario-Based "A pipeline crashes at Step 3. Which component determines where to resume?" Map the scenario to the specific section: crash recovery → 5.4. The answer involves manifests and checkpoints, not session tokens or gate logs.
Best Practice "What is the recommended approach for handling a gate failure?" Apply the complete protocol: Halt → Log → Remediate. Any answer missing a step is incomplete.
"Which Approach?" "Should you use session resumption or fork_session for X?" Two-axis test: (1) continuing vs. exploring, (2) one session vs. two sessions. Match the scenario to the axis.
Debugging "A recovered pipeline produces wrong data. What is the most likely cause?" Top causes: stale checkpoints (schema version mismatch), non-idempotent side effects, wrong resumption point.

Memory Aids & Mnemonics

🧠 Mnemonics

HLR — Gate failure protocol: Halt → Log → Remediate. Never skip a letter.

SCS — Gate type order: Structural → Constraint → Semantic. Cheapest first.

"Checkpoint = Data, Manifest = Status" — Repeat this distinction until it's automatic. The checkpoint stores what was produced; the manifest stores whether it was produced.

"Write checkpoint, THEN manifest" — The correct ordering. Think of it as: "prove the work exists before marking it done."

"Fork = 2, Resume = 1" — Number of sessions after the operation. Fork creates 2 independent sessions; resume continues the 1 existing session.

CRISP — Five properties of a well-designed step: Checked (verified), Recoverable (checkpointed), Idempotent (safe to retry), Single-purpose, Persisted (explicit state).

Practice Questions

Practice Question 1 — Crash Recovery
A pipeline completes Steps 0–2 successfully before crashing during Step 3. On restart, which component determines where execution resumes?
  • A) The session token
  • B) The verification gate log for Step 3
  • C) The progress manifest / checkpoint files ✅
  • D) The fork_session identifier
Explanation: The progress manifest records the completion status of each step, and the checkpoint files store the actual data. On restart, the recovery algorithm reads the manifest to find the first non-completed step (Step 3), loads Step 2's checkpoint as input, and resumes at Step 3. The session token tracks identity (not progress), the gate log records pass/fail verdicts (not resumption state), and fork_session is for creating divergent branches (not recovery).
Practice Question 2 — Verification Gate Failure
A verification gate detects that Step 2's output is missing a required field. What is the correct response protocol?
  • A) Log the error and proceed to Step 3 with a warning flag
  • B) Retry Step 2 indefinitely until the field appears
  • C) Halt execution, log the failure reason, then retry Step 2 with feedback (up to the retry budget) ✅
  • D) Skip Step 2 and use Step 1's output for Step 3 instead
Explanation: The correct protocol is Halt → Log → Remediate (HLR). Option A skips the halt — corrupted data reaches Step 3. Option B has no retry budget — risks infinite loops. Option D skips a required step — violates the pipeline's data contract. Option C correctly halts, logs, and remediates with bounded retries and feedback to help the model self-correct.
Practice Question 3 — State Persistence
A developer writes the progress manifest update BEFORE the checkpoint file. The system crashes between the two writes. What is the consequence?
  • A) No consequence — the system is designed to handle this
  • B) The step is silently skipped on recovery
  • C) On recovery, the manifest says the step completed, but the checkpoint data is missing — causing a recovery failure or silent data loss ✅
  • D) The checkpoint is automatically regenerated from the manifest
Explanation: The manifest now says "completed" for the step, but no checkpoint file exists. On recovery, the system believes the step is done and tries to load a checkpoint that doesn't exist — this either throws a FileNotFoundError or causes silent data loss if the system proceeds without the data. This is why the correct order is checkpoint first, manifest second. The manifest is never auto-generated from the checkpoint or vice versa.
Practice Question 4 — Fork vs. Resume
A product team has completed Steps 0–3 of a report generation pipeline. They now want to explore two different formatting strategies for the final step while keeping the original execution intact. Which operation should they use?
  • A) Resume the session twice with different parameters
  • B) Fork the session into two named branches, each with different formatting parameters ✅
  • C) Create a new verification gate for each formatting strategy
  • D) Roll back to Step 2 and re-run with both strategies sequentially
Explanation: The requirement is to explore alternatives while keeping the original intact — this is the textbook use case for fork_session. Resuming twice would mutate the same session (you can't resume into two parallel paths). Verification gates validate output, not explore alternatives. Rolling back wastes the work already done in Steps 2–3. Forking creates two independent named sessions that share the Steps 0–3 history and diverge at Step 4.
Practice Question 5 — Gate Selection
A pipeline step generates a JSON response containing financial calculations. You need to verify that: (1) the JSON has all required fields, (2) no total exceeds the approved budget, and (3) the executive summary is coherent and complete. In what order should these checks be applied?
  • A) Semantic → Constraint → Structural
  • B) Constraint → Structural → Semantic
  • C) Structural → Constraint → Semantic ✅
  • D) All three simultaneously for efficiency
Explanation: The cheapest-first heuristic (SCS: Structural → Constraint → Semantic) dictates the order. (1) Structural validation checks JSON schema conformance — instant, zero cost. If it fails, there's no point running more expensive checks. (2) Constraint validation checks budget limits — fast deterministic logic. (3) Semantic validation (LLM-based) evaluates the executive summary — most expensive, only run when the data is structurally and logically sound. Running them simultaneously wastes LLM calls when the JSON doesn't even parse correctly.
