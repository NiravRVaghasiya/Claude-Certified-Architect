3.1   Hub-and-Spoke Architecture: The Coordinator Pattern

Concept Overview

The hub-and-spoke (or coordinator) pattern is the foundational architecture for multi-agent systems built with Claude. A single coordinator agent sits at the center and is the only agent that communicates directly with the user. It receives the user's request, decomposes it into subtasks, dispatches those subtasks to specialized subagents, collects their results, and synthesizes a final response. Subagents never talk to each other or to the user — they only talk to the coordinator.

Key Terminology

  • Coordinator (Hub/Orchestrator) — The central agent responsible for task planning, delegation, and result aggregation. It maintains the conversation state with the user.
  • Subagent (Spoke/Worker) — A specialized agent that receives a scoped task from the coordinator, executes it, and returns a result. Stateless between invocations.
  • Hub-and-Spoke Topology — A network topology where all communication flows through a central node (the hub); spokes do not communicate laterally.
  • Orchestration Layer — The application code that manages the lifecycle of subagent calls — spawning, monitoring, timeout, aggregation.
  • Fan-out / Fan-in — The pattern of dispatching multiple subtasks (fan-out) and collecting their results (fan-in).

Deep Dive

In multi-agent systems using Claude, the hub-and-spoke pattern is the strongly recommended default. Here's why:

  1. Single point of coherence. The coordinator holds the "big picture" — it understands the user's intent and can make trade-offs across subtask results. Subagents, by design, have narrow scope.
  2. Clear responsibility boundaries. Each subagent has a well-defined specialty (research, code generation, summarization). This allows you to tune system prompts, temperature, and tool access per subagent without cross-contamination.
  3. Simplified error handling. The coordinator is the single place where you handle subagent failures, retries, and fallback logic.
  4. Conversation continuity. Only the coordinator maintains the multi-turn conversation with the user. Subagents are invoked for a single turn and are discarded.

How it works mechanically: The coordinator is a Claude API call with its own system prompt. When it decides to invoke a subagent, your orchestration code makes a new, separate Claude API call with the subagent's system prompt and the scoped task as the user message. The subagent's response is returned to the orchestration code, which feeds it back into the coordinator's context. The coordinator then continues its reasoning with the subagent result available.

Critically, subagents are implemented as tool calls from the coordinator's perspective. The coordinator decides to use a "tool" (e.g., research_agent), the orchestration layer intercepts this, makes the subagent API call, and returns the result as a tool result. This keeps the coordinator's conversation flow clean.

🟡 Tip — Tool-Based Subagent Invocation

Model subagents as tools in the coordinator's tool definitions. For example, define a tool called research_agent(query: str). When the coordinator calls this tool, your application code routes the call to a dedicated Claude instance with a research-focused system prompt. This pattern leverages Claude's native tool-use capabilities for clean orchestration.

🔴 Common Mistake — Peer-to-Peer Agent Communication

A frequent anti-pattern is allowing subagents to call each other directly (mesh topology). This leads to unpredictable execution paths, circular dependencies, and makes debugging nearly impossible. Always route communication through the coordinator. If Subagent B needs information from Subagent A, the coordinator should invoke A first, extract relevant data, and pass it to B.

Exam Strategy

🟢 Exam Strategy — 3.1

Questions on this topic test whether you understand why centralized coordination is preferred over peer-to-peer. Look for scenarios describing multi-step tasks — the correct answer will involve a coordinator that delegates and aggregates. Watch for distractors that describe agents "passing messages to each other" or "sharing a conversation" — these describe mesh patterns that violate hub-and-spoke.

3.2   Subagent Context Isolation — Why Subagents Don't Inherit History

Concept Overview

When a coordinator spawns a subagent, the subagent starts with a completely fresh context. It does not automatically receive the coordinator's conversation history, previous subagent results, or any accumulated state. Each subagent invocation is an independent Claude API call with its own system prompt and a user message that contains only what the orchestration layer explicitly provides. This is a deliberate architectural choice, not a limitation.

Key Terminology

  • Context Isolation — The principle that each subagent operates in its own context window, independent of all other agents.
  • Context Window — The maximum amount of text (system prompt + messages) a single Claude call can process. Each subagent has its own window.
  • Context Injection — The practice of explicitly inserting relevant information into a subagent's prompt so it has the data it needs.
  • Context Pollution — When irrelevant information from other tasks "leaks" into a subagent's context, degrading its performance and focus.
  • Minimum Viable Context — The smallest amount of context a subagent needs to successfully complete its specific subtask.

Deep Dive

Context isolation exists for three critical reasons:

  1. Focus and precision. A subagent tasked with "analyze this code for security vulnerabilities" performs better when its context contains only the code and the analysis instructions — not 20 turns of unrelated conversation about project timelines.
  2. Context window efficiency. Claude has a finite context window. If every subagent inherited the full coordinator history, you'd waste significant token budget on irrelevant context, leaving less room for the actual task.
  3. Security and data segmentation. In enterprise systems, different subagents may handle data with different sensitivity levels. Isolation ensures a "public summary" subagent never accidentally sees data intended only for an "internal analysis" subagent.

What this means in practice: When you invoke a subagent via a Claude API call, the messages array for that call starts fresh. The only content the subagent sees is:

  • Its own system prompt (specialized for its role)
  • The user message you construct — which should contain the subtask description and any necessary context extracted from the coordinator's state

Real-world analogy: Think of the coordinator as a project manager and subagents as contractors. When you hire a plumber (subagent), you don't hand them the entire project file for a house renovation. You give them the plumbing-specific plans, access to the relevant area, and the scope of work. That's context injection — providing exactly what's needed, nothing more.

🔵 Core Concept — Explicit Context Transfer

If a subagent needs information from the coordinator's conversation history or from a previous subagent's result, the coordinator must explicitly extract and pass that information. This is typically done by constructing a structured prompt that includes relevant data snippets. There is no automatic, implicit, or inherited context sharing.

🔴 Common Mistake — Assuming Context Inheritance

New architects often assume subagents "see" the coordinator's history. This leads to subagent prompts like: "Continue the analysis from earlier." The subagent has no idea what "earlier" refers to. The correct approach: "Analyze the following data for trend X. The data was collected from [source] and shows [key observations]. Here is the data: ..."

🟢 Exam Strategy — 3.2

This is one of the most frequently tested concepts. Questions will describe a scenario where a subagent "needs to know" something from a previous turn or another subagent's result. The correct answer always involves explicitly passing context in the subagent's prompt. Distractor trap: Any option that suggests subagents "automatically receive," "inherit," or "share" the coordinator's conversation history is always wrong.

Q1: A coordinator agent has gathered research results in Turn 3. In Turn 5, it needs a subagent to summarize those results. How should the results be made available to the summarization subagent?
A) The subagent automatically receives the coordinator's full conversation history including Turn 3
B) The coordinator stores the results in a shared memory space that the subagent reads from
✅ C) The coordinator extracts the relevant research results and includes them in the subagent's prompt as context
D) The subagent makes an API call back to the coordinator to request the Turn 3 results
Rationale: C is the only correct approach. A violates context isolation. B implies a shared memory system that doesn't exist in Claude's standard architecture. D implies subagent-to-coordinator communication, which is not how the pattern works.
Q2: Which of the following is NOT a benefit of subagent context isolation?
A) Prevents irrelevant information from degrading subagent performance
B) Allows different security levels for different subagents
✅ C) Eliminates the need to think about what context each subagent requires

3.3   Task Decomposition, Delegation & Result Aggregation

Concept Overview

Task decomposition is the coordinator's most critical responsibility: breaking a complex user request into well-scoped subtasks that individual subagents can handle independently. Delegation is the act of assigning each subtask to the appropriate specialized subagent. Result aggregation is the synthesis of subagent outputs into a coherent, complete response that addresses the original user request. Together, these three steps form the core loop of multi-agent orchestration.

Key Terminology

  • Task Decomposition — Breaking a complex request into independent, well-scoped subtasks.
  • Subtask — A discrete unit of work that can be completed by a single subagent in a single invocation.
  • Delegation — The act of assigning a subtask to a specific subagent based on its specialization.
  • Result Aggregation — Combining subagent outputs into a unified response, resolving conflicts and filling gaps.
  • Decomposition Strategy — The method used to break down tasks (by domain, by step, by data partition, etc.).
  • Atomic Subtask — A subtask that cannot be meaningfully subdivided further for a single agent.

Deep Dive

Decomposition Strategies

There are four primary decomposition strategies, and the right one depends on the task:

StrategyWhen to UseExample
By DomainTask spans multiple knowledge areasSecurity + Cost + Performance analysis
By StepTask is inherently sequentialResearch → Analyze → Write → Review
By Data PartitionSame analysis on different data chunksAnalyze each of 5 documents separately
By PerspectiveTask benefits from multiple viewpointsEvaluate from user, developer, business perspectives

Principles of Good Decomposition

  • Independence: Subtasks should be as independent as possible. Minimize dependencies between subagent tasks.
  • Completeness: The union of all subtasks should fully cover the original request. No gaps.
  • Specificity: Each subtask should have clear success criteria. "Look into security" is too vague; "List the top 3 security risks of X and mitigations for each" is specific.
  • Right-sizing: Each subtask should be substantial enough to warrant a separate agent but focused enough for a single invocation.

Aggregation is Not Concatenation

A critical architect-level insight: aggregation is not simply appending subagent results together. The coordinator must:

  • Resolve contradictions — If the security subagent recommends Lambda but the cost subagent recommends ECS, the coordinator must acknowledge and reason through the trade-off.
  • Fill gaps — If no subagent addressed a cross-cutting concern (e.g., operational complexity), the coordinator should identify and address it.
  • Enforce coherence — The final response should read as a unified analysis, not three separate reports stitched together.
  • Add meta-level insight — The coordinator can see patterns across subagent results that no individual subagent could see.
🟡 Tip — Structured Output for Easier Aggregation

Instruct subagents to return results in a consistent structured format (e.g., JSON with predefined keys like findings, confidence, caveats). This makes the coordinator's aggregation step dramatically easier and more reliable than parsing free-form text from different agents.

Exam Strategy

🟢 Exam Strategy — 3.3

Exam questions will present a complex task and ask which decomposition strategy is best. Focus on the dependencies: if subtasks have no dependencies, they can be parallel (by-domain or by-data). If they must happen in order, it's by-step. Also watch for questions about aggregation — the answer that involves "synthesizing and resolving conflicts" beats "concatenating results" every time.

Q1: A user asks: "Research competitor X, draft a blog post about our advantages, and create social media snippets." The coordinator should decompose this as:
A) Three parallel subtasks dispatched simultaneously to different subagents
✅ B) A sequential pipeline: research first, then pass results to the blog writer, then pass the blog to the snippet creator
C) A single subtask given to one generalist subagent
D) Two parallel subtasks (research + blog) followed by snippet creation
Rationale: B is correct because each step depends on the previous one's output. The blog post needs research results; the snippets need the blog post. A is wrong because of these dependencies. C loses the benefit of specialization. D misidentifies the dependency chain.
Q2: During result aggregation, the security subagent rates a design as "high risk" while the performance subagent rates the same design as "optimal." What should the coordinator do?
A) Return both results verbatim and let the user decide
B) Prioritize the security finding since security always trumps performance
✅ C) Acknowledge the trade-off, explain the tension between security and performance, and provide a recommendation based on the user's stated priorities
D) Re-run both subagents with additional context to resolve the conflict
Rationale: C reflects the coordinator's responsibility to synthesize and add meta-level insight. A abdicates the coordinator's role. B applies a rigid rule without considering context. D wastes resources when the coordinator already has enough information.

3.4   Risks of Overly Narrow Task Decomposition

Concept Overview

While decomposition is essential, over-decomposition — splitting a task into too many tiny subtasks — is a common anti-pattern that degrades system performance. When subtasks are too narrow, each subagent lacks sufficient context to produce meaningful output, the coordinator's aggregation burden skyrockets, and the system incurs unnecessary latency and cost. The architect's challenge is finding the right granularity: coarse enough for each subagent to do meaningful work, fine enough for specialization to add value.

Key Terminology

  • Over-Decomposition — Splitting a task into subtasks that are too small or too narrow to be independently meaningful.
  • Context Fragmentation — When over-decomposition causes each subagent to receive only a tiny slice of context, losing the holistic view needed for quality output.
  • Aggregation Overhead — The increased coordinator effort required to stitch together many tiny results into a coherent response.
  • Granularity Sweet Spot — The optimal level of decomposition where subtasks are focused but self-contained.
  • Single-Agent Sufficiency — The recognition that not every task benefits from multi-agent orchestration; some are better handled by a single well-prompted agent.

Deep Dive

Over-decomposition manifests in several concrete problems:

1. Context Fragmentation

When you split "Write a market analysis report" into "Write the introduction," "Write section 1," "Write section 2," etc., each subagent lacks the full picture. The introduction subagent doesn't know what sections 1–3 will say. Section 2 doesn't know what Section 1 concluded. The result is a disjointed report with repetitions, contradictions, and no narrative flow.

2. Compounding Latency and Cost

Each subagent invocation is a separate API call. Ten tiny subtasks running sequentially mean 10× the API round-trip latency. Even in parallel, you pay for 10 separate API calls when 2–3 would have sufficed.

3. Aggregation Complexity Explosion

Aggregating 3 well-structured results is manageable. Aggregating 15 tiny fragments — some overlapping, some with gaps, some contradicting — requires the coordinator to essentially re-do the work of understanding the full problem.

4. Loss of Emergent Insight

Claude produces its best work when it can see enough context to draw connections. A subagent analyzing only one paragraph of a document cannot identify themes that span multiple paragraphs. Over-decomposition eliminates the possibility of emergent, cross-cutting insights.

The Right-Sizing Heuristic

Ask: "Can this subtask be meaningfully completed in isolation, with the context I plan to provide, and produce a result that is useful on its own?" If the answer is no, the subtask is too narrow.

🟡 Tip — The 2–5 Subtask Rule of Thumb

For most tasks, 2–5 subtasks is the sweet spot. If you find yourself creating more than 5 subtasks for a single user request, step back and ask whether some subtasks should be merged. If you have only 1 subtask, you probably don't need multi-agent orchestration at all — just use a well-prompted single agent.

🔴 Common Mistake — Decomposing by Paragraph or Section

Never decompose a writing task by assigning each paragraph or section to a different subagent. Writing is inherently holistic — each section must be aware of the others for coherence. Instead, decompose by research vs. writing vs. review (by step), or have one writing agent produce the full draft and a separate review agent critique it.

Exam Strategy

🟢 Exam Strategy — 3.4

The correct answer typically involves merging subtasks or using fewer, more capable subagents. Watch for scenarios where latency, cost, or incoherent output is described — these are signals of over-decomposition.

3.5   Dynamic Subagent Selection Based on Query Complexity

Concept Overview

Not every user query requires the full multi-agent apparatus. A well-designed coordinator should dynamically assess query complexity and choose the appropriate execution strategy: handling simple queries directly, using a single specialized subagent for focused tasks, and deploying multiple subagents only for genuinely complex, multi-faceted requests. This adaptive routing minimizes cost and latency while maximizing quality where it matters most.

Key Terminology

  • Complexity Classification — The coordinator's assessment of how complex a query is, which determines the orchestration strategy.
  • Direct Response — The coordinator answers the query itself without invoking any subagents (for simple queries).
  • Single-Agent Routing — Dispatching the entire query to one specialized subagent (for moderately complex, single-domain queries).
  • Multi-Agent Fan-Out — Dispatching multiple subtasks to multiple subagents (for complex, multi-faceted queries).
  • Routing Logic — The decision-making process (in the coordinator's system prompt or application code) that determines which path to take.

Deep Dive

Dynamic selection can be implemented at two levels:

1. Prompt-Based Classification (Coordinator Decides)

Include complexity classification instructions in the coordinator's system prompt:

# In the coordinator's system prompt:
Before responding, classify the query complexity:
- SIMPLE: Factual question, definition, or straightforward request
  → Answer directly without subagents
- MODERATE: Requires specialized expertise in one domain
  → Delegate to the appropriate specialist subagent
- COMPLEX: Requires multiple domains, comparison, or synthesis
  → Decompose into subtasks and delegate to multiple subagents

This approach leverages Claude's reasoning ability to make the routing decision. The coordinator classifies the query and then acts accordingly.

2. Code-Based Classification (Application Logic Decides)

Use a lightweight classifier (could be a cheaper/faster model or even heuristics) in your application code to route before the coordinator is even invoked:

def route_query(query):
    complexity = classify_complexity(query)  # fast classifier
    if complexity == "simple":
        return single_agent_response(query, model="haiku")
    elif complexity == "moderate":
        specialist = select_specialist(query)
        return single_agent_response(query, agent=specialist, model="sonnet")
    else:
        return full_orchestration(query, model="opus")  # coordinator + subagents

Model Tiering

An important optimization: not all subagents need the same model tier. A research subagent that aggregates information might use Haiku (fast, cheap). A reasoning-heavy analysis subagent might need Sonnet. The coordinator, which handles the most complex reasoning, might use Opus. This tiered approach optimizes cost without sacrificing quality where it matters.

🟡 Tip — Start Simple, Scale Up

Default to the simplest execution path. Most production systems find that 60–70% of queries can be handled by a single agent. Reserve multi-agent orchestration for the 20–30% of queries that genuinely need it. Premature multi-agent design is a common waste of engineering effort and API budget.

🟢 Exam Strategy — 3.5

✅ C) Implement query complexity classification so simple queries are answered directly by the coordinator without spawning subagents

Rationale: C addresses the root cause — unnecessary orchestration for simple queries. A reduces latency but doesn't fix the architectural waste. B is limited to exact matches. D is arbitrary.
Q2: In a multi-agent system, which model selection strategy best optimizes cost while maintaining quality?
A) Use the most capable model (Opus) for all agents to ensure quality
B) Use the cheapest model (Haiku) for all agents to minimize cost
✅ C) Use a tiered approach: lighter models for simple subtasks, more capable models for complex reasoning and coordination
D) Alternate between models randomly to balance cost and quality
Rationale: C applies model tiering — the correct cost optimization strategy. A wastes budget. B sacrifices quality. D is not a strategy.

3.6   Passing Structured Context Between Coordinator and Subagents

Concept Overview

Since subagents don't inherit context (Section 3.2), the coordinator must explicitly construct the context for each subagent invocation. The quality of this context directly determines the quality of the subagent's output. Structured context passing — using well-defined schemas, clear formatting, and the principle of minimum viable context — is the architect's primary lever for controlling multi-agent system quality.

Key Terminology

  • Context Packet — The structured block of information assembled by the coordinator and passed to a subagent.
  • Minimum Viable Context (MVC) — The smallest set of information needed for a subagent to complete its task effectively.
  • Context Schema — A predefined format (JSON, XML, or structured text) for organizing context passed between agents.
  • Context Injection Point — Where in the subagent's prompt the context is inserted (typically in the user message).
  • Output Contract — The agreed-upon format for subagent responses, enabling reliable parsing by the coordinator.

Deep Dive

Constructing Effective Context Packets

A well-constructed context packet has four components:

1. Task Description — What the subagent should do. Be specific and include success criteria.

# Bad:  "Look at this code."
# Good: "Identify the top 3 security vulnerabilities in the following Python code.
         For each, provide: (a) vulnerability type, (b) affected line(s),
         (c) severity (Critical/High/Medium/Low), (d) recommended fix."

2. Relevant Context — Background information the subagent needs but wouldn't know from the input data alone (language, framework, deployment environment, user preferences stated earlier in the conversation).

3. Input Data — The actual content to process, clearly delimited. Use XML tags (<code>...</code>, <document>...</document>) for unambiguous boundaries.

4. Output Contract — The format the subagent must use for its response. This makes the coordinator's parsing step deterministic.

Formatting Best Practices

FormatBest ForExample Use
XML tagsSeparating data types within a prompt<task>...</task><context>...</context>
JSONOutput contracts, structured input dataSubagent returns {"findings": [...]}
MarkdownHuman-readable context with hierarchyMulti-section briefings for subagents
Numbered listsSequential instructions or criteria"Evaluate against these 5 criteria: 1. ..."
🔵 Core Concept — Minimum Viable Context (MVC)

Pass only what the subagent needs to complete its specific subtask. Extra context wastes tokens and can distract the subagent. If a subagent is analyzing code for security issues, it doesn't need to know the project's business requirements or the user's name. The MVC principle is about relevance filtering — the coordinator selects and extracts only the pertinent information from its broader context.

🔴 Common Mistake — Dumping the Full Coordinator Context

Passing the coordinator's entire conversation history to a subagent "just in case" is a common anti-pattern. It wastes context window capacity, increases cost, and introduces noise that can degrade the subagent's focus. A 50,000-token coordinator context should become a 2,000-token context packet for a focused subagent.

Exam Strategy

🟢 Exam Strategy — 3.6

Questions on this topic test whether you understand what should be in a context packet and what should not. The correct answer will include a well-structured prompt with task, context, data, and output format. Distractors include: passing the full conversation, passing no context, or having the subagent "figure it out" from the data alone.

Q1: A coordinator delegates a code review subtask to a subagent. Which context packet is most effective?

B) The coordinator's full conversation history + the code file
✅ C) A structured prompt with the task description, the language/framework, the code, the specific review criteria, and the desired output format
D) The code file + "Return your analysis as a JSON object"
Rationale: C provides all four components of an effective context packet. A is too vague. B violates MVC by dumping irrelevant history. D specifies output format but lacks task specificity and context.
Q2: What is the purpose of XML tags like <code>...</code> or <document>...</document> in a subagent's prompt?

✅ B) They create clear, unambiguous boundaries between the task instructions and the input data, helping the model distinguish what to analyze from how to analyze it

3.7   Handling Subagent Failures and Partial Results

Concept Overview

In production multi-agent systems, subagents will fail. API calls time out, rate limits are hit, subagents produce malformed output, or they return low-confidence results. A robust coordinator must handle these failures gracefully: retrying when appropriate, using fallback strategies, and delivering the best possible response even when some subtasks fail. Graceful degradation — returning a partial but useful response rather than a complete failure — is a hallmark of well-architected multi-agent systems.

Key Terminology

  • Graceful Degradation — Returning a useful (if incomplete) response when some subagents fail, rather than failing entirely.
  • Retry Strategy — The logic for re-attempting failed subagent calls (with/without backoff, with/without modified prompts).
  • Fallback Agent — A backup subagent (often simpler or more general) invoked when the primary specialist fails.
  • Timeout Policy — Maximum time to wait for a subagent response before considering it failed.
  • Partial Result Aggregation — Combining available results while clearly indicating which subtasks didn't complete.
  • Circuit Breaker — A pattern that stops sending requests to a consistently failing subagent to avoid cascading failures.

The Decision Tree for Failure Handling

subagent_failed:
  if retries_remaining > 0:
    if failure_type == "timeout":
      retry with reduced context  # maybe subagent was overloaded
    elif failure_type == "malformed_output":
      retry with stricter output instructions
    elif failure_type == "rate_limit":
      wait(exponential_backoff) then retry
    else:
      retry as-is
  else:
    if fallback_agent_available:
      invoke fallback_agent
    elif subtask_is_critical:
      return error to user with explanation
    else:
      proceed with partial results + transparency note

Partial Result Aggregation

When aggregating partial results, the coordinator should be transparent:

# Coordinator aggregation prompt (with partial results):
"""
You have results from 2 of 3 analysis subtasks.
- Security analysis: [available - see results below]
- Cost analysis: [UNAVAILABLE - subagent timed out after retries]
- Performance analysis: [available - see results below]

Synthesize the available results into a coherent response.
Clearly note that cost analysis could not be completed and
suggest the user request it separately if needed.
"""
🔵 Core Concept — Transparency Over Silence

When a subagent fails and partial results are returned, the coordinator must tell the user what's missing. A response that silently omits the cost analysis (because the subagent failed) is worse than one that says "I was unable to complete the cost analysis due to a processing issue. Here are the security and performance findings. Would you like me to retry the cost analysis?"

🔴 Common Mistake — Infinite Retry Loops

Without a retry limit and circuit-breaker, a failing subagent can cause the entire system to hang. Always set: (1) a maximum retry count (typically 1–2), (2) a per-subagent timeout, and (3) a total orchestration timeout. If a subagent is consistently failing, stop calling it for a period (circuit breaker).

Exam Strategy

🟢 Exam Strategy — 3.7

Questions will describe a subagent failure scenario and ask for the best response. The answer that involves graceful degradation with transparency (return what you have + tell the user what's missing) is almost always correct. Answers that suggest "fail completely" or "silently omit the failed result" are typically wrong.

Q2: A subagent returns output that doesn't match the expected JSON schema. What is the best immediate retry strategy?

✅ B) Retry with a more explicit output format instruction and an example of the expected schema

Rationale: B addresses the likely cause (unclear output instructions) with a targeted fix. A might produce the same error. C is a heavy change for a prompt issue. D is fragile and unreliable.

3.8   Parallel vs Sequential Subagent Execution

Concept Overview

When the coordinator dispatches multiple subtasks, they can be executed in parallel (simultaneously) or sequentially (one after another). The choice depends on dependency relationships between subtasks. Independent subtasks should run in parallel for speed. Dependent subtasks — where one needs another's output — must run sequentially. Hybrid patterns (some parallel, some sequential) are common in production systems.

Key Terminology

  • Parallel Execution — Running multiple subagent calls concurrently (e.g., using asyncio.gather or threads).
  • Sequential Execution — Running subagent calls one at a time, where each call may use the previous call's output.
  • Pipeline Pattern — A sequential chain where each stage's output feeds the next stage's input.
  • Fan-Out / Fan-In — Dispatch multiple parallel subtasks (fan-out) and collect all results (fan-in) before proceeding.
  • DAG (Directed Acyclic Graph) — A dependency graph that defines which subtasks depend on others, enabling maximum parallelism.
  • Barrier / Join Point — The point in execution where you wait for all parallel subtasks to complete before continuing.

Deep Dive

When to Use Parallel Execution

  • Subtasks are independent — no subtask needs another's output
  • Example: Analyzing a document for security, cost, AND performance (three independent lenses)
  • Benefit: Total latency = time of slowest subtask (not sum of all)
  • Cost: Same total API cost, but you need concurrent API call capacity

When to Use Sequential Execution

  • Subtasks have data dependencies — output of one feeds into the next
  • Example: Research → Outline → Write → Review (pipeline)
  • Benefit: Each subsequent subagent builds on refined input
  • Cost: Total latency = sum of all subtask latencies

The Hybrid / DAG Pattern

Most real systems have a mix of independent and dependent subtasks. Model this as a DAG (Directed Acyclic Graph):

import asyncio

async def orchestrate(query):
    # Level 1: Independent research tasks (parallel)
    research_a, research_b = await asyncio.gather(
        research_agent(query, "security"),
        research_agent(query, "cost")
    )
    # Level 2: Depends on both research results (sequential)
    analysis = await analysis_agent(research_a, research_b)

    # Level 3: Independent post-processing (parallel)
    summary, visuals = await asyncio.gather(
        summary_agent(analysis),
        visualization_agent(analysis)
    )
    return combine(summary, visuals)

Decision Framework

FactorChoose ParallelChoose Sequential
DependenciesNo dependencies between subtasksOutput of A needed by B
Latency PrioritySpeed is criticalAccuracy over speed
Error HandlingFailures are independentEarly failure should abort later tasks
Context BuildingEach subtask has all needed contextContext is progressively enriched
Cost ImpactSame total cost, burst capacity neededSame total cost, spread over time
🟡 Tip — Identify the Critical Path

In a hybrid execution, the critical path is the longest chain of sequential dependencies. This determines the minimum possible latency. To optimize, focus on shortening the critical path — parallelize as many of its subtasks as possible. Everything off the critical path is already optimized by virtue of being parallel.

🔴 Common Mistake — Forcing Sequential When Parallel Is Possible

New architects sometimes default to sequential execution "to be safe." If subtasks A and B are genuinely independent (B doesn't need A's result), running them sequentially doubles the latency for no benefit. Always analyze dependency relationships before choosing the execution pattern.

Exam Strategy

🟢 Exam Strategy — 3.8

Questions will describe a set of subtasks with implicit dependency relationships. You must identify which can be parallelized and which must be sequential. Key signal: If the question says "Subtask B requires the output of Subtask A," B cannot start until A finishes. If subtasks are described as "independent analyses" or "different aspects," they can be parallel. Look for the answer that maximizes parallelism while respecting dependencies.

Q1: A coordinator must: (A) research a topic, (B) fact-check the research, and (C) write a summary based on the fact-checked research. What is the optimal execution strategy?
A) All three in parallel
✅ B) Sequential: A → B → C (each depends on the previous result)
C) A and C in parallel, then B
D) A and B in parallel, then C
Rationale: B is correct — B needs A's output (to fact-check it), and C needs B's output (to summarize fact-checked research). A is wrong because B can't run without A's result. C and D misidentify the dependencies.
Q2: A coordinator must: (A) analyze code security, (B) analyze code performance, (C) analyze code readability, and (D) produce a unified report from A+B+C. What is the optimal execution pattern?
A) A → B → C → D (fully sequential)
B) (A || B) → C → D (partial parallel)
✅ C) (A || B || C) → D (fan-out/fan-in: A, B, C in parallel, then D)
D) All four in parallel
Rationale: C maximizes parallelism. A, B, C are independent analyses that can run simultaneously. Only D depends on all three. D is wrong because the report can't be written without the analysis results.
Q3: In a fan-out/fan-in pattern with 5 parallel subagents, what determines the total latency of the parallel phase?
A) The average response time of all 5 subagents
B) The total sum of all response times
✅ C) The response time of the slowest subagent
D) The response time of the fastest subagent
Rationale: In parallel execution, you must wait for all tasks to complete (the barrier/join point). The total time is determined by the slowest task. This is a fundamental property of parallel execution.

import asyncio, json, anthropic

# ──────────────────────────────────────────────────────────

SUBAGENTS = {

              "title": "...", "description": "...", "suggestion": "..."}],
  "quality_score": 85,
  "summary": "One-paragraph quality assessment"
}""",
        "model": "claude-sonnet-4-20250514",   # Needs deeper reasoning
        "timeout": 45,
    },
    "summary_writer": {
        "system": """You are a technical writer. Produce an executive summary from
analysis results. Return JSON:
{
  "title": "Document Analysis Report",
  "executive_summary": "2-3 paragraph overview",
  "key_recommendations": ["...", "...", "..."],
  "priority_actions": ["...", "..."]
}""",
        "model": "claude-sonnet-4-20250514",   # Needs quality writing
        "timeout": 30,
    }
}

# ──────────────────────────────────────────────────────────
# SUBAGENT INVOCATION (with retry & timeout)
# ──────────────────────────────────────────────────────────

async def invoke_subagent(
    name: str,
    task_prompt: str,
    max_retries: int = 1
) -> Optional[dict]:
    """Invoke a subagent with timeout and retry logic."""
    config = SUBAGENTS[name]

    for attempt in range(max_retries + 1):
        try:
            # Each subagent gets a FRESH context (Section 3.2)
            # Only the task_prompt is passed — no coordinator history
            response = await asyncio.wait_for(
                asyncio.to_thread(
                    client.messages.create,
                    model=config["model"],
                    max_tokens=2048,
                    system=config["system"],     # Specialized system prompt
                    messages=[{"role": "user", "content": task_prompt}]
                ),
                timeout=config["timeout"]
            )

            # Parse structured output (Section 3.6 — output contract)
            result = json.loads(response.content[0].text)
            return {"status": "success", "agent": name, "data": result}

        except asyncio.TimeoutError:
            if attempt < max_retries:
                continue  # Retry (Section 3.7)
            return {"status": "timeout", "agent": name, "data": None}
        except json.JSONDecodeError:
            if attempt < max_retries:
                task_prompt += "\n\nIMPORTANT: Return ONLY valid JSON."
                continue
            return {"status": "parse_error", "agent": name, "data": None}
        except Exception as e:
            return {"status": "error", "agent": name, "data": str(e)}

# ──────────────────────────────────────────────────────────
# COORDINATOR
# ──────────────────────────────────────────────────────────

async def coordinator(document: str) -> str:
    """
    Coordinator agent: decomposes, delegates, aggregates.

    Architecture Decisions:
    - Security & Quality run in PARALLEL (independent)   [Section 3.8]
    - Summary runs SEQUENTIALLY after (needs their output) [Section 3.8]
    - Each subagent gets minimum viable context             [Section 3.6]
    - Failures produce partial results, not total failure  [Section 3.7]
    """

    # ── Step 1: DECOMPOSE (Section 3.3) ──
    # Two independent analysis tasks + one dependent summary task

    # ── Step 2: DELEGATE — Phase 1: Parallel analysis ──
    # Security and Quality are independent → run in parallel
    security_task = invoke_subagent(
        "security_analyzer",
        # Context packet: task + input data (Section 3.6)
        f"Analyze the following document for security vulnerabilities:\n"
        f"<document>\n{document}\n</document>"
    )
    quality_task = invoke_subagent(
        "quality_reviewer",
        f"Review the following document for quality issues:\n"
        f"<document>\n{document}\n</document>"
    )

    # Fan-out: both run concurrently
    security_result, quality_result = await asyncio.gather(
        security_task, quality_task
    )

    # ── Step 2b: DELEGATE — Phase 2: Sequential summary ──
    # Summary depends on analysis results → runs after Phase 1
    available_results = []
    missing_components = []

    for r in [security_result, quality_result]:
        if r["status"] == "success":
            available_results.append(r)
        else:
            missing_components.append(
                f"{r['agent']} ({r['status']})"
            )

    # Build context packet for summary agent (Section 3.6)
    summary_context = "Synthesize these analysis results into an executive summary:\n"
    for r in available_results:
        summary_context += f"\n<{r['agent']}_results>\n"
        summary_context += json.dumps(r["data"], indent=2)
        summary_context += f"\n</{r['agent']}_results>\n"

    if missing_components:
        summary_context += f"\nNote: These analyses were unavailable: "
        summary_context += ", ".join(missing_components)
        summary_context += "\nAcknowledge this gap in your summary."

    summary_result = await invoke_subagent("summary_writer", summary_context)

    # ── Step 3: AGGREGATE (Section 3.3) ──
    return aggregate_final_report(
        security_result, quality_result, summary_result, missing_components
    )

def aggregate_final_report(security, quality, summary, missing) -> str:
    """Combine all results into a coherent final report."""
    report = "# Technical Document Analysis Report\n\n"

    if summary["status"] == "success":
        report += f"## Executive Summary\n{summary['data']['executive_summary']}\n\n"

    if security["status"] == "success":
        report += "## Security Analysis\n"
        for f in security["data"]["findings"]:
            report += f"- **[{f['severity']}]** {f['title']}: {f['description']}\n"

    if quality["status"] == "success":
        report += f"\n## Quality Review (Score: {quality['data']['quality_score']}/100)\n"
        for i in quality["data"]["issues"]:
            report += f"- **[{i['category']}]** {i['title']}: {i['suggestion']}\n"

    # Transparency: report missing components (Section 3.7)
    if missing:
        report += f"\n---\n⚠️ **Note:** The following analyses could not be completed: "
        report += ", ".join(missing)
        report += "\nPlease retry these components if needed.\n"

    return report

Implementation Best Practices Checklist

  • Define each subagent with a specialized system prompt and output contract
  • Model subagents as tools in the coordinator's tool definitions
  • Use minimum viable context — pass only what the subagent needs
  • Use XML tags to delimit input data in subagent prompts
  • Implement timeout policies for every subagent call
  • Add retry logic with modified prompts for parse errors
  • Design for graceful degradation — return partial results when subagents fail
  • Be transparent about missing components in the final output
  • Run independent subtasks in parallel, dependent ones sequentially
  • Use model tiering — match model capability to task complexity
  • Keep coordinator logic in application code, not in a single mega-prompt
  • Validate subagent outputs against the expected schema before aggregation
  • Log all subagent calls and results for debugging and observability
  • Test with injected failures — verify degradation behaves as expected
🟡 Tip — Tool-Based vs Code-Based Orchestration

There are two main implementation patterns: (1) The coordinator uses Claude's native tool-use to "call" subagents — your orchestration code intercepts tool calls and routes them to subagent API calls. This is more natural but the coordinator has less explicit control over execution order. (2) The coordinator is pure application code that calls Claude API for each subagent independently — this gives you full control over parallel/sequential execution, timeouts, and retries. Pattern 2 is recommended for production systems where reliability and control matter most.

B) There is no error handling

D) The code uses the wrong programming language

Q2: In the Technical Document Analyzer example, why is the summary_writer subagent invoked after security_analyzer and quality_reviewer, rather than in parallel with them?
A) Because the summary_writer uses a more expensive model
B) Because running 3 subagents in parallel would exceed the API rate limit
✅ C) Because the summary_writer needs the results from the other two subagents as input — it has a data dependency
D) Because sequential execution is always more reliable than parallel
Rationale: C correctly identifies the dependency. The summary cannot be written until the analyses it summarizes are available. A and B are not the determining factors. D is false.

📋 Chapter Summary — 10 Critical Takeaways

  1. Hub-and-spoke is the default. Use a central coordinator that delegates to specialized subagents. No peer-to-peer communication between subagents.
  2. Subagents are context-isolated. Every subagent starts with a blank context. Nothing is inherited — everything must be explicitly passed.
  3. Decomposition is the coordinator's #1 job. Break complex tasks into independent, well-scoped subtasks with clear success criteria.
  4. Aggregation ≠ concatenation. The coordinator must synthesize, resolve conflicts, fill gaps, and add meta-level insight.
  5. Over-decomposition kills quality. 2–5 subtasks is typical. If subtasks can't produce meaningful results independently, they're too narrow.
  6. Not every query needs multi-agent orchestration. Use complexity classification to route simple queries directly, moderate ones to a single specialist, and only complex ones to full orchestration.
  7. Structured context packets are essential. Pass: task description + relevant context + input data + output contract. Apply the Minimum Viable Context principle.
  8. Plan for failure. Implement timeouts, retries, and graceful degradation. Return partial results with transparency about what's missing.
  9. Parallel when independent, sequential when dependent. Analyze the dependency DAG to maximize parallelism while respecting data flow.
  10. Model tiering optimizes cost. Use lighter models (Haiku) for simple subtasks, more capable models (Sonnet/Opus) for complex reasoning and coordination.

Glossary

Aggregation Overhead
The extra coordinator effort needed when combining many subagent results, especially from over-decomposed tasks.
Atomic Subtask
A subtask that cannot be meaningfully subdivided further for a single agent to execute.
Barrier / Join Point
The synchronization point where the coordinator waits for all parallel subagent calls to complete before proceeding.
Circuit Breaker
A pattern that automatically stops sending requests to a consistently failing subagent for a cooldown period.
Complexity Classification
The coordinator's assessment of query difficulty, used to determine whether to respond directly, use one subagent, or invoke full orchestration.
Context Fragmentation
Loss of holistic understanding caused by splitting a task too finely, depriving each subagent of sufficient context.
Context Injection
Explicitly inserting relevant information into a subagent's prompt so it has the data it needs to complete its task.
Context Isolation
The design principle that each subagent operates in its own independent context window with no inherited state.
Context Packet
The structured block of information (task + context + data + output contract) assembled by the coordinator for a subagent.
Context Pollution
When irrelevant information leaks into a subagent's context, degrading its focus and output quality.
Coordinator / Hub / Orchestrator
The central agent that manages user interaction, task decomposition, subagent delegation, and result aggregation.
DAG (Directed Acyclic Graph)
A dependency graph showing which subtasks depend on others, used to determine maximum parallelism.
Decomposition Strategy
The method used to break down tasks: by domain, by step, by data partition, or by perspective.
Direct Response
When the coordinator answers a simple query itself without invoking any subagents.
Fan-Out / Fan-In
Dispatching multiple parallel subtasks (fan-out) and collecting all results at a join point (fan-in).
Graceful Degradation
Returning a useful partial response when some subagents fail, with transparency about what's missing.
Hub-and-Spoke Topology
A network pattern where all communication flows through a central node; spokes never communicate directly.
Minimum Viable Context (MVC)
The smallest set of information a subagent needs to complete its specific subtask effectively.
Model Tiering
Using different Claude model tiers (Haiku/Sonnet/Opus) for different subtasks based on complexity requirements.
Orchestration Layer
The application code that manages the lifecycle of subagent calls: spawning, monitoring, timeout, retry, and aggregation.
Output Contract
The agreed-upon format (typically JSON schema) that a subagent must use for its response.
Over-Decomposition
Splitting a task into subtasks that are too small or narrow, leading to context fragmentation and aggregation overhead.
Pipeline Pattern
A sequential chain where each stage's output feeds the next stage's input.
Single-Agent Sufficiency
The recognition that some tasks are better handled by one well-prompted agent than by multi-agent orchestration.
Subagent / Spoke / Worker
A specialized, stateless agent that receives a scoped task, executes it, and returns a result to the coordinator.
Task Decomposition
Breaking a complex user request into independent, well-scoped subtasks for individual subagent execution.
Tool Definition
The JSON schema registered with the coordinator's API call, representing a subagent as a callable tool.
