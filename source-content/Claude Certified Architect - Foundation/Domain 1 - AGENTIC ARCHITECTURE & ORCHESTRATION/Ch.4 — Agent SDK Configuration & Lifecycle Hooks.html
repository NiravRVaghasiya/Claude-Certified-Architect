4.1 The allowed_tools Configuration: Restricting Subagent Capabilities 🔥 HIGH exam frequency
📘 Core Concept

allowed_tools is the primary mechanism for capability scoping in the Claude Agent SDK. It specifies an explicit allowlist of tool names that an agent (or a spawned subagent) is permitted to invoke. When set, it overrides the default behavior where an agent inherits all tools registered in its parent's runner context. Think of it as a firewall rule: anything not on the list is silently blocked — the agent never even sees the tool in its available tool list, so it cannot attempt to call it.

This is the foundational building block for least-privilege multi-agent design. By restricting each subagent to only the tools it needs, you limit blast radius if the agent behaves unexpectedly, reduce token waste from unnecessary tool descriptions, and enforce security boundaries between trust zones.

🔑 Key Terms
  • allowed_tools — A list of tool name strings passed at agent construction or subagent spawn time. Only these tools are visible to the agent.
  • Tool Visibility — An agent can only see (and therefore call) tools in its allowed set. Unallowed tools are excluded from the system prompt's tool list entirely.
  • Scope Isolation — The principle that a subagent's tool access is decoupled from its parent's access. No implicit inheritance.
  • Least Privilege — Grant the minimum tool access required for the agent's task. Core security principle tested heavily on the exam.
  • Allowlist Model — A positive security model: specify what IS allowed, rather than what is blocked. Safer than a blocklist approach.
💻 Code Example

Define an agent with a restricted tool set — only web_search and read_file are available:

from agents import Agent, Runner, function_tool

@function_tool
def web_search(query: str) -> str:
    """Search the web and return results."""
    return search_engine.query(query)

@function_tool
def read_file(path: str) -> str:
    """Read a local file."""
    return open(path).read()

@function_tool
def execute_code(code: str) -> str:
    """Execute arbitrary code (dangerous)."""
    return exec_sandbox(code)

# ─── Restricted agent: can search and read, but CANNOT execute code ───
researcher = Agent(
    name="researcher",
    instructions="You are a research assistant. Find and summarize information.",
    tools=[web_search, read_file, execute_code],   # All tools registered…
    allowed_tools=["web_search", "read_file"],   # …but only these two are visible
)

# execute_code is NEVER visible to 'researcher', even though it's in tools[].
# The agent's system prompt will only describe web_search and read_file.

⚠️ Common Pitfalls
  1. Assuming Inheritance: The most common exam mistake. Subagents do not automatically inherit the parent's tools. If you spawn a subagent without specifying allowed_tools, the subagent gets its own tools list — not the parent's allowed_tools. Each agent's scope is configured independently.
  2. Confusing tools vs. allowed_tools: tools registers tool functions with the agent. allowed_tools filters which of those registered tools are actually visible. If a tool name is in allowed_tools but not in tools, it is simply ignored — no error, no tool available.
  3. Using Blocklists Instead: There is no denied_tools parameter. The SDK uses an allowlist model only. Exam distractors often offer blocklist-based answers.
💡 Tips & Tricks
  • Mnemonic — "ATF" (Allowlist at Task-level Filtering): Remember that allowed_tools acts like a bouncer at the door — it checks the list, and only lets listed tools through.
  • Pattern: When you see "restrict", "limit", "scope", or "least privilege" in an exam question, immediately think allowed_tools.
  • Omitting allowed_tools: If you don't specify it, all tools in the tools list are visible. This is the "wide-open" default — the exam tests whether you know that explicitly setting an allowlist is required for restriction.

A) Set denied_tools=["file_read", "execute_code"] on the subagent

4.2 Configuring Tool Access at the Agent Level 🔥 MEDIUM exam frequency
📘 Core Concept

Beyond allowed_tools, the Agent SDK provides several levers for configuring what tools an agent can use and how. The tools parameter on the Agent class accepts a list of tool objects (functions decorated with @function_tool, built-in SDK tools, or custom Tool subclasses). This list defines the universe of capabilities available — allowed_tools then optionally narrows it.

Key insight: tool configuration is declarative and static at agent construction time. Once an Agent is instantiated, its tool set is fixed. To change it, you create a new Agent instance. This immutability is intentional — it makes the security model auditable and predictable.

🔑 Key Terms
  • tools parameter — List of tool objects passed to Agent(). Defines the full tool universe for that agent.
  • @function_tool decorator — Converts a Python function into a tool the agent can call. Automatically extracts the function signature for the tool schema.
  • Tool base class — For advanced tools that need custom serialization, async execution, or stateful behavior. Subclass Tool and implement run().
  • Tool Schema — JSON Schema auto-generated from the function's type hints and docstring. This is what Claude sees in its system prompt.
  • Immutable Configuration — Once constructed, an Agent's tool set cannot be modified at runtime.
💻 Code Example

Three patterns for registering tools — decorator, class-based, and combined with allowed_tools:

from agents import Agent, Tool, function_tool
from typing import Any

# ─── Pattern 1: Decorator-based (simplest, most common) ───
@function_tool
def get_weather(city: str) -> str:
    """Get current weather for a city. Returns temperature and conditions."""
    return weather_api.get(city)

# ─── Pattern 2: Class-based (for advanced / stateful tools) ───
class DatabaseQuery(Tool):
    """Execute a read-only SQL query against the analytics database."""
    name = "database_query"
    description = "Run a SQL SELECT query."

    async def run(self, query: str) -> str:
        # Validate: only SELECT allowed (security guardrail)
        if not query.strip().upper().startswith("SELECT"):
            raise ValueError("Only SELECT queries are permitted")
        return await db.execute(query)

# ─── Pattern 3: Combined registration with allowed_tools filter ───
analyst = Agent(
    name="data_analyst",
    instructions="Analyze data and report findings.",
    tools=[get_weather, DatabaseQuery()],    # Both tools registered
    allowed_tools=["database_query"],          # Only DB queries allowed
)
# Result: analyst sees ONLY database_query. get_weather is registered but hidden.

⚠️ Common Pitfalls
  1. Mutating after construction: Attempting agent.tools.append(new_tool) after instantiation. The SDK treats tool configuration as immutable. Create a new Agent instance instead.
  2. Mismatched names: allowed_tools uses string names, not function references. If your function is named get_weather but you write allowed_tools=["weather"], the tool is silently excluded.
  3. Schema from docstrings: The tool's description in Claude's system prompt comes from the function's docstring, not the function name. A vague docstring = a poorly-used tool. Exam questions may test whether you know where the description is sourced from.
💡 Tips & Tricks
  • Naming convention: Use snake_case for tool function names — the decorator extracts the function name as the tool's identifier. Keep names descriptive and unique across the agent's tool set.
  • Type hints drive the schema: @function_tool reads your Python type hints to generate the JSON Schema. Use str, int, float, bool, list[str], Optional[str] for clean schemas.
  • Exam signal: When the question mentions "immutable", "fixed at creation", or "agent construction" — it's testing Agent-level config, not runtime modification.
🎯 Exam Strategy — 4.2 Agent-Level Tool Config

WHAT'S BEING TESTED: The difference between tool registration (tools=[]) and tool filtering (allowed_tools=[]), plus immutability of agent configuration.

SAMPLE QUESTION STEM:

A developer registers tools [A, B, C] on an Agent and sets
allowed_tools=["A", "D"]. Which tools can the agent use?

A) A, B, C (allowed_tools is ignored if a name doesn't match)
B) A only (D is not in tools, so it's ignored; B, C are filtered out)
C) A and D (allowed_tools always takes precedence)
D) Error: D is not a registered tool

Rationale: allowed_tools is an intersection filter. "D" is in allowed_tools but not registered in tools[], so it's silently ignored (no error). Only "A" passes both gates.

4.3 The Task Tool for Subagent Spawning 🔥 HIGH exam frequency
📘 Core Concept

The Task tool (also referred to as the agent handoff mechanism) is the SDK's built-in way for one agent to delegate work to another agent — spawning it as a subagent within the same Runner execution. The orchestrator agent calls the Task tool just like any other tool, passing the input and receiving the subagent's final output as the tool result.

Critically, each Task tool wraps a specific target agent with its own configuration. When the orchestrator lists the Task in its tools, the Runner knows how to spawn the child agent, enforce its allowed_tools, and return results. The subagent runs in an isolated turn cycle — it does not share conversation history with the parent unless explicitly passed context.

🔑 Key Terms
  • Task tool — A built-in tool type that wraps a target Agent, enabling one agent to invoke another as part of its tool-calling flow.
  • Orchestrator Agent — The parent agent that decides when and how to delegate work to subagents via Task tools.
  • Subagent — A child agent spawned by a Task tool. It runs with its own instructions, model, and tool scope.
  • Handoff — The act of transferring execution from the orchestrator to the subagent. The subagent runs to completion, then returns results to the orchestrator.
  • Turn Isolation — Subagent conversation history is separate from the orchestrator's. The orchestrator only sees the subagent's final output.
💻 Code Example

Orchestrator with two specialized subagents — each with different tool scopes:

from agents import Agent, Runner, function_tool

# ─── Define specialized tools ───
@function_tool
def web_search(query: str) -> str:
    """Search the web."""
    return search(query)

@function_tool
def write_file(path: str, content: str) -> str:
    """Write content to a file."""
    open(path, "w").write(content)
    return f"Written to {path}"

@function_tool
def send_email(to: str, body: str) -> str:
    """Send an email."""
    return email_client.send(to, body)

# ─── Define subagents with scoped tools ───
research_agent = Agent(
    name="research_agent",
    instructions="Research the given topic and return a summary.",
    tools=[web_search],                      # Can ONLY search
)

writer_agent = Agent(
    name="writer_agent",
    instructions="Write a report based on the provided research.",
    tools=[write_file],                       # Can ONLY write files
)

# ─── Orchestrator delegates via agent references in its tools list ───
orchestrator = Agent(
    name="orchestrator",
    instructions="""You coordinate research reports.
    1. Delegate research to research_agent.
    2. Pass findings to writer_agent for the final report.
    Do NOT search or write files yourself.""",
    tools=[
        research_agent.as_tool(              # Exposes research_agent as a callable tool
            tool_name="delegate_research",
            tool_description="Delegate a research task to the research specialist.",
        ),
        writer_agent.as_tool(
            tool_name="delegate_writing",
            tool_description="Delegate report writing to the writing specialist.",
        ),
        send_email,                          # Orchestrator can email directly
    ],
)

# ─── Run the orchestrator ───
result = await Runner.run(orchestrator, input="Research AI trends and write a report.")

⚠️ Common Pitfalls
  1. Thinking subagents share conversation: By default, a subagent does NOT see the orchestrator's prior conversation. It receives only the input passed to the Task tool. If you need context, you must include it in the tool input explicitly.
  2. Over-permissioning the orchestrator: If the orchestrator has send_email and delegates to subagents, the subagents cannot send email unless you also give them that tool. Tool access does not cascade.
  3. Ignoring the as_tool() pattern: To use an agent as a tool in another agent, you must explicitly convert it using .as_tool() (or equivalent handoff mechanism). Simply passing the agent object in the tools list is incorrect.
💡 Tips & Tricks
  • Mnemonic — "Spawn + Scope": Every spawn = new scope. Parent scope ≠ child scope.
  • Design Pattern: Orchestrators should generally have no direct data tools — only Task/handoff tools and communication tools (email, Slack). This forces all data access through specialized subagents with proper guardrails.
  • Exam trick: Questions may describe a chain: Agent A → Agent B → Agent C. Each agent's tools are independent. Don't assume cascading.

4.4 Agent SDK Hooks: on_tool_end for Tool Call Interception 🔥 HIGH exam frequency
📘 Core Concept

Lifecycle hooks are callback methods that the Agent SDK invokes at specific points during an agent's execution cycle. They give you interception points — moments where your code runs between the agent's decision to use a tool and the actual execution, or after the tool returns its result. The two primary tool-related hooks are:

  • on_tool_start — fires before a tool executes (Pre-Tool hook)
  • on_tool_end — fires after a tool returns its result (Post-Tool hook)

The on_tool_end hook (Post-Tool) is especially powerful because it receives both the tool call arguments and the result. This lets you log, transform, redact, or validate tool outputs before they're returned to the agent. The hook can modify the result, raise an exception to signal failure, or silently record metrics.

🔑 Key Terms
  • Lifecycle Hook — A user-defined callback attached to an agent that fires at a specific phase of the execution loop.
  • RunHooks — The base class for defining hooks that apply to the entire Runner execution (across all agents in a run).
  • AgentHooks — The base class for defining hooks scoped to a specific agent instance.
  • on_tool_start(context, agent, tool_call) — Pre-execution hook. Called with the tool name and arguments before the tool runs.
  • on_tool_end(context, agent, tool_call, tool_result) — Post-execution hook. Called with the tool name, arguments, and result after the tool completes.
  • RunContext — An object passed to all hooks carrying the run's metadata, state, and configuration.
💻 Code Example

Implementing a post-tool hook that logs every tool result:

from agents import Agent, AgentHooks, RunContext, ToolCallInfo, ToolResult
import logging

logger = logging.getLogger("agent_tools")

class LoggingHooks(AgentHooks):
    """Hooks that log every tool call and result."""

    async def on_tool_start(
        self,
        context: RunContext,
        agent: Agent,
        tool_call: ToolCallInfo,
    ) -> None:
        # Fires BEFORE the tool executes
        logger.info(
            f"[PRE]  Agent '{agent.name}' calling '{tool_call.name}' "
            f"with args: {tool_call.arguments}"
        )

    async def on_tool_end(
        self,
        context: RunContext,
        agent: Agent,
        tool_call: ToolCallInfo,
        tool_result: ToolResult,
    ) -> None:
        # Fires AFTER the tool returns
        logger.info(
            f"[POST] Agent '{agent.name}' tool '{tool_call.name}' "
            f"returned: {tool_result.output[:200]}"  # Truncate for log safety
        )

# ─── Attach hooks to an agent ───
agent = Agent(
    name="monitored_agent",
    instructions="You are a helpful assistant.",
    tools=[web_search, read_file],
    hooks=LoggingHooks(),                    # ◄── Attach hooks here
)

⚠️ Common Pitfalls
  1. Confusing RunHooks vs. AgentHooks: AgentHooks are scoped to a single agent. RunHooks apply to the entire run (all agents). Exam questions test whether you know which to use for per-agent vs. global interception.
  2. Blocking in on_tool_end: By the time on_tool_end fires, the tool has already executed. You can modify or log the result, but you cannot prevent the execution. To block, use on_tool_start.
  3. Forgetting async: Hook methods are async. Forgetting the async keyword causes the SDK to skip the hook silently in some implementations — a subtle bug that's hard to debug.
💡 Tips & Tricks
  • Mnemonic — "Start blocks, End logs": on_tool_start = gate/approval (can prevent execution). on_tool_end = observe/transform (execution already happened).
  • Hook ordering: If both RunHooks and AgentHooks define the same method, RunHooks fires first (global before local).
  • Exam pattern: "Where should you add logging?" → on_tool_end (you want to see results). "Where should you add approval?" → on_tool_start (before execution).
🎯 Exam Strategy — 4.4 Hooks

SAMPLE QUESTION STEM:

A developer wants to redact PII from tool results BEFORE the agent

A) on_tool_start — redact the arguments before execution

4.5 Intercepting Sensitive Operations (PII Redaction, Approval Gates) 🔥 HIGH exam frequency
📘 Core Concept

Hooks enable two critical enterprise patterns: PII redaction (sanitizing sensitive data from tool outputs before the agent processes them) and approval gates (requiring human or system approval before certain high-risk tools execute). These patterns transform the Agent SDK from a development tool into an enterprise-grade framework with compliance and governance built into the execution pipeline.

PII Redaction uses on_tool_end — the tool's raw output is scanned for patterns (emails, SSNs, phone numbers) and replaced with placeholders before the agent sees the data. Approval Gates use on_tool_start — before a sensitive tool (e.g., database write, email send) executes, the hook pauses execution and requests approval from a human or automated system.

🔑 Key Terms
  • PII Redaction — Replacing personally identifiable information (names, emails, SSNs) with anonymized tokens (e.g., [REDACTED_EMAIL]) in tool outputs.
  • Approval Gate — A checkpoint in on_tool_start that blocks tool execution until an external authority (human or system) approves the action.
  • Human-in-the-Loop (HITL) — Architecture pattern where a human must approve agent actions before execution. Implemented via approval gate hooks.
  • Guardrail — Any mechanism that constrains agent behavior within acceptable bounds. Hooks are the SDK's primary guardrail enforcement point.
  • Sensitive Tool — A tool whose execution has irreversible or high-impact side effects (send email, delete record, transfer funds).
💻 Code Example — PII Redaction Hook
import re
from agents import AgentHooks, RunContext, Agent, ToolCallInfo, ToolResult

# ─── PII patterns ───
PII_PATTERNS = {
    "email":  (re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "[REDACTED_EMAIL]"),
    "ssn":    (re.compile(r"\b\d{3}-\d{2}-\d{4}\b"), "[REDACTED_SSN]"),
    "phone":  (re.compile(r"\b\d{3}[-.]?\d{3}[-.]?\d{4}\b"), "[REDACTED_PHONE]"),
}

class PIIRedactionHooks(AgentHooks):
    """Scrub PII from all tool results before the agent sees them."""

    async def on_tool_end(
        self,
        context: RunContext,
        agent: Agent,
        tool_call: ToolCallInfo,
        tool_result: ToolResult,
    ) -> None:
        # Redact all PII patterns from the tool output
        cleaned = tool_result.output
        for pii_type, (pattern, replacement) in PII_PATTERNS.items():
            matches = pattern.findall(cleaned)
            if matches:
                logger.warning(f"Redacted {len(matches)} {pii_type} instance(s)")
                cleaned = pattern.sub(replacement, cleaned)
        tool_result.output = cleaned      # ◄── Mutate result in-place
💻 Code Example — Approval Gate Hook
class ApprovalGateHooks(AgentHooks):
    """Block sensitive tools until human approval is received."""

    SENSITIVE_TOOLS = {"send_email", "delete_record", "transfer_funds"}

⚠️ Common Pitfalls
  1. Redacting in on_tool_start: PII exists in the result, not the arguments. Redacting arguments is usually wrong — the tool needs the real arguments to function (e.g., a name to query).
  2. Approval gate in on_tool_end: By the time on_tool_end fires, the email is already sent, the record already deleted. Approval gates must be in on_tool_start.
  3. Forgetting to re-assign: When redacting PII, you must mutate tool_result.output in-place or re-assign the cleaned value. Simply computing a cleaned string without assigning it back does nothing.
💡 Tips & Tricks
  • Mnemonic — "Before = Block, After = Clean": on_tool_start = can block (approval). on_tool_end = can clean (redact).
  • Combine patterns: In production, you often implement BOTH on the same agent — approval gate on on_tool_start for writes AND PII redaction on on_tool_end for reads.
  • Exam tell: If the question mentions "irreversible action" or "side effect" → approval gate → on_tool_start. If it mentions "sensitive data in output" → redaction → on_tool_end.

4.6 Adding Logging, Metrics & Guardrails via Hooks 🔥 MEDIUM exam frequency
📘 Core Concept

Beyond security (approval gates) and compliance (PII redaction), hooks are the primary extension point for observability and operational guardrails. Three enterprise-critical patterns built on hooks:

  • Structured Logging: Emit structured JSON logs for every tool call, including timing, agent name, tool name, arguments, and result summary. Enables audit trails and debugging.
  • Metrics Collection: Track tool call counts, latency percentiles, error rates, and token usage. Feed into monitoring dashboards (CloudWatch, Datadog, etc.).
  • Guardrails: Enforce runtime invariants — e.g., rate-limit how many times an agent can call a tool, cap output size, or enforce argument constraints beyond what the tool schema allows.
🔑 Key Terms
  • Structured Logging — JSON-formatted log events with consistent fields (timestamp, agent_name, tool_name, duration_ms, status). Machine-parseable for log analytics.
  • Observability — The ability to understand an agent's internal state from its external outputs (logs, metrics, traces).
  • Rate Limiting — Guardrail that caps how many times a tool can be called per run or per time window.
  • Output Guardrail — Validation on tool results (e.g., max size, required format, no forbidden content).
  • Input Guardrail — Validation on tool arguments (e.g., SQL injection prevention, path traversal checks).
💻 Code Example — Combined Logging + Rate Limiting
import time, json, logging
from collections import defaultdict
from agents import AgentHooks, RunContext, Agent, ToolCallInfo, ToolResult

logger = logging.getLogger("agent.audit")

class ObservabilityHooks(AgentHooks):
    """Structured logging, latency tracking, and rate limiting."""

    def __init__(self, max_calls_per_tool: int = 10):
        self.call_counts: dict[str, int] = defaultdict(int)
        self.max_calls = max_calls_per_tool
        self._start_times: dict[str, float] = {}

    async def on_tool_start(
        self, context: RunContext, agent: Agent, tool_call: ToolCallInfo,
    ) -> None:
        # ── Rate limiting guardrail ──
        self.call_counts[tool_call.name] += 1
        if self.call_counts[tool_call.name] > self.max_calls:
            raise ToolExecutionError(
                f"Rate limit exceeded: '{tool_call.name}' called "
                f"{self.call_counts[tool_call.name]} times (max: {self.max_calls})"
            )
        # ── Start timer ──
        self._start_times[tool_call.id] = time.monotonic()

    async def on_tool_end(
        self, context: RunContext, agent: Agent,
        tool_call: ToolCallInfo, tool_result: ToolResult,
    ) -> None:
        # ── Calculate latency ──
        start = self._start_times.pop(tool_call.id, None)
        duration_ms = (time.monotonic() - start) * 1000 if start else 0

        # ── Structured log event ──
        log_event = {
            "event": "tool_call_complete",
            "agent": agent.name,
            "tool": tool_call.name,
            "duration_ms": round(duration_ms, 2),
            "output_length": len(tool_result.output),
            "call_count": self.call_counts[tool_call.name],
        }
        logger.info(json.dumps(log_event))

# ─── Usage ───
agent = Agent(
    name="guarded_agent",
    tools=[web_search, database_query],
    hooks=ObservabilityHooks(max_calls_per_tool=5),  # Max 5 calls per tool
)

⚠️ Common Pitfalls
  1. Logging sensitive arguments: When logging tool call arguments in structured logs, be careful not to log PII or secrets. Combine your logging hook with redaction logic, or exclude argument values from production logs.
  2. Stateful hooks without thread safety: If the same hook instance is shared across concurrent agent runs, mutable state (like call_counts) can race. Use asyncio.Lock or per-run state isolation.
  3. Over-guardrailing: Setting rate limits too low causes the agent to fail legitimate multi-step workflows. Tune guardrails based on expected usage patterns, not arbitrary numbers.
💡 Tips & Tricks
  • Pattern recognition: Exam questions about "audit trail" or "compliance logging" → structured logging in on_tool_end. Questions about "preventing abuse" or "limiting calls" → rate limiting in on_tool_start.
  • Combine, don't duplicate: Implement one Hooks class per agent with all concerns (logging, metrics, guardrails). Don't try to attach multiple hook instances — the SDK uses a single hooks parameter.
  • Timer pattern: Start in on_tool_start, stop in on_tool_end, keyed by tool_call.id. This is the standard latency measurement pattern — memorize it.

4.7 Hands-On: Implementing Tool Call Interception 🔥 HIGH exam frequency
📘 Core Concept

This section synthesizes all prior concepts into a production-ready interception pipeline. In practice, you combine approval gates, PII redaction, structured logging, and rate limiting into a single cohesive hook class that acts as the agent's "middleware layer." The key architectural insight: hooks form a pipeline of concerns, executed in a predictable order, providing a single enforcement boundary for all cross-cutting requirements.

The exam tests your ability to read a complete hook implementation and identify: (1) what each section does, (2) whether hook methods are in the correct phase, and (3) what happens when edge cases occur (e.g., approval denied, PII found in arguments vs. results, rate limit hit mid-conversation).

🔑 Key Terms
  • Hook Pipeline — The sequential execution of hook methods forming a middleware-like chain around tool execution.
  • Cross-Cutting Concern — Functionality (logging, security, metrics) that spans across all tools rather than belonging to any single tool.
  • Middleware Pattern — Hooks acting like middleware in web frameworks — each request (tool call) passes through layers of processing.
  • Error Propagation — When a hook raises an exception, the tool does not execute and the agent receives an error result. Subsequent hooks in the same phase are skipped.
  • Graceful Degradation — Hooks should handle their own exceptions (e.g., logging service down) without breaking the agent's core flow.
💻 Code Example — Complete Production Hook Pipeline

A single hook class combining all four enterprise patterns:

import re, time, json, logging
from collections import defaultdict
from agents import (
    Agent, Runner, AgentHooks, RunContext,
    ToolCallInfo, ToolResult, ToolExecutionError, function_tool,
)

logger = logging.getLogger("agent.production")

# ═══════════════════════════════════════════════
#  PRODUCTION HOOK PIPELINE
# ═══════════════════════════════════════════════
class ProductionHooks(AgentHooks):
    """
    Combined pipeline:
      on_tool_start → [1] Rate Limit → [2] Approval Gate → [3] Start Timer
      on_tool_end   → [4] PII Redact → [5] Log Event    → [6] Metrics
    """

    SENSITIVE_TOOLS = {"send_email", "delete_record"}
    PII_PATTERNS = [
        (re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "[EMAIL]"),
        (re.compile(r"\b\d{3}-\d{2}-\d{4}\b"), "[SSN]"),
    ]

    def __init__(self, max_calls: int = 20):
        self.counts = defaultdict(int)
        self.max_calls = max_calls
        self.timers = {}
        self.metrics = {"total_calls": 0, "total_latency_ms": 0, "errors": 0}

    # ─── PRE-TOOL: Rate Limit → Approval Gate → Timer ───
    async def on_tool_start(
        self, context: RunContext, agent: Agent, tool_call: ToolCallInfo,
    ) -> None:
        # [1] RATE LIMIT — checked first (cheapest check)
        self.counts[tool_call.name] += 1
        if self.counts[tool_call.name] > self.max_calls:
            self.metrics["errors"] += 1
            raise ToolExecutionError(f"Rate limit hit for {tool_call.name}")

        # [2] APPROVAL GATE — only for sensitive tools
        if tool_call.name in self.SENSITIVE_TOOLS:
            approved = await request_approval(tool_call.name, tool_call.arguments)
            if not approved:
                self.metrics["errors"] += 1
                raise ToolExecutionError("Approval denied")

        # [3] START TIMER
        self.timers[tool_call.id] = time.monotonic()

    # ─── POST-TOOL: PII Redact → Log → Metrics ───
    async def on_tool_end(
        self, context: RunContext, agent: Agent,
        tool_call: ToolCallInfo, tool_result: ToolResult,
    ) -> None:
        # [4] PII REDACTION
        cleaned = tool_result.output
        pii_found = False
        for pattern, replacement in self.PII_PATTERNS:
            if pattern.search(cleaned):
                cleaned = pattern.sub(replacement, cleaned)
                pii_found = True
        tool_result.output = cleaned

        # [5] STRUCTURED LOG
        duration = (time.monotonic() - self.timers.pop(tool_call.id, time.monotonic())) * 1000
        logger.info(json.dumps({
            "agent": agent.name, "tool": tool_call.name,
            "duration_ms": round(duration, 2),
            "pii_redacted": pii_found,
            "output_chars": len(cleaned),
        }))

        # [6] METRICS
        self.metrics["total_calls"] += 1
        self.metrics["total_latency_ms"] += duration

# ═══════════════════════════════════════════════
#  WIRE IT UP
# ═══════════════════════════════════════════════
@function_tool
def query_customers(filter: str) -> str:
    """Query the customer database."""
    return db.query(filter)

@function_tool
def send_email(to: str, body: str) -> str:
    """Send an email to a customer."""
    return email_service.send(to, body)

agent = Agent(
    name="customer_service",
    instructions="Help resolve customer issues.",
    tools=[query_customers, send_email],
    hooks=ProductionHooks(max_calls=20),    # ◄── All guardrails in one class
)

result = await Runner.run(agent, input="Look up customer #1234 and email them a refund confirmation.")

⚠️ Common Pitfalls
  1. Order matters in on_tool_start: Rate limiting should come before approval gates. Checking rate limits is cheap; requesting human approval is expensive. If the rate limit is already exceeded, don't waste time requesting approval.
  2. Swallowing exceptions in hooks: If a hook's logging code fails (e.g., logger connection timeout), it should catch that exception internally and not propagate it. Crashing the agent because the logging service is down is worse than missing a log entry.
  3. Testing hook interactions: When multiple concerns are in one hook class, test each concern in isolation AND test the combined flow. A PII pattern might inadvertently match a tool argument in on_tool_end that's also used for rate counting.
💡 Tips & Tricks
  • Mnemonic — "RAS-PLM" (Racecar): on_tool_start = Rate-limit → Approval → Start-timer. on_tool_end = PII-redact → Log → Metrics.
  • Exam shortcut: If a code snippet asks "what's wrong?", look for: (1) wrong hook phase, (2) missing async, (3) mutating result without re-assigning, (4) approval gate in on_tool_end.
  • Production best practice: Wrap all hook internals in try/except with fallback logging. Never let hook failures crash the agent run.

Q5 — A ProductionHooks class implements: rate limiting, approval gates, PII redaction, and structured logging. In what order should these execute in on_tool_start?

CORRECT ANSWER Rate limit → Approval gate → Start timer. (PII redaction and logging are in on_tool_end, not on_tool_start.)

Explanation: In on_tool_start: check rate limits first (cheapest operation — just a counter). If the rate limit is exceeded, there's no point requesting human approval (expensive, blocks execution). Then check the approval gate for sensitive tools. Then start the latency timer. PII redaction happens in on_tool_end because it operates on the tool's output. Structured logging also happens in on_tool_end because you need the duration and result to log.
