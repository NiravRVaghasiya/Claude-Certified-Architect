for Complex Workflows

⏱ Estimated Study Time: 75–90 min 📈 Difficulty: Intermediate–Advanced ⚖️ Exam Weight: ~15%

📋 Chapter Overview

This chapter covers the architect's core competency: knowing when and how to break complex tasks into manageable units of work that Claude can execute reliably. Task decomposition is the bridge between a vague user intent and a structured agentic pipeline. You will learn to assess complexity, choose the right decomposition strategy (top-down or bottom-up), design iterative refinement loops that improve subagent outputs, and balance breadth against depth when decomposing research-oriented workflows. The chapter concludes with a fully worked hands-on example that ties all concepts together.

Mastering these strategies is essential because Claude's effectiveness scales directly with how well tasks are scoped. An overly broad prompt produces shallow results; an overly narrow one creates coordination overhead. The architect's job is to find the decomposition that maximizes output quality while minimizing token cost and latency.

6.1

Complexity Assessment: When to Decompose

📘 Core Concept

Not every task needs decomposition. An architect's first skill is recognizing the inflection point where a single Claude call becomes insufficient and a multi-step workflow becomes necessary. Decomposing too early adds unnecessary coordination overhead—extra prompts, latency, token cost, and potential for propagation errors between steps. Decomposing too late produces outputs that are shallow, incoherent, or incomplete because a single context window cannot hold all the required reasoning.

Complexity assessment is a structured evaluation of four dimensions: cognitive breadth (how many distinct knowledge domains does the task span?), depth of reasoning (how many sequential inference steps are required?), output length and structure (will the output exceed what a single response can produce with quality?), and dependency structure (are there subtasks whose inputs depend on the outputs of other subtasks?).

When evaluating a task, an architect should apply the "single-prompt test": mentally draft the prompt you would send to Claude for this task. If the prompt requires more than two distinct instruction blocks (e.g., "first do X, then analyze Y, then format as Z, then validate against W"), the task likely benefits from decomposition. Another reliable heuristic is the context budget check: estimate how much of the context window the instructions, reference data, and expected output would consume. If the total approaches 60–70% of the model's context window, decomposition becomes necessary to ensure quality—Claude's output quality degrades when operating near context limits because it must allocate attention across too many competing objectives.

The key output of complexity assessment is a decomposition decision: either "proceed with a single call" (with optional output format constraints) or "decompose into N subtasks with specified dependencies." This decision should be documented in the system architecture and revisited as task requirements evolve.

🔑 Key Terms

Reasoning DepthThe number of sequential, dependent inference steps needed to reach a conclusion. Deep reasoning chains are fragile in single calls.

💡 Tips & Tricks
  • The 60% Rule: When context usage exceeds 60% of the window (instructions + data + expected output), Claude's quality drops measurably. This is a hard trigger for decomposition, not a guideline—treat it as a constraint.
  • Watch for hidden domains: A seemingly simple "write a market analysis" task actually spans data interpretation, competitive intelligence, financial modeling, and business writing—four domains. List the required skills explicitly before making your decomposition decision.
  • Cost the coordination overhead: Before decomposing, estimate the extra token cost and latency. If the overhead exceeds 30% of a single-call cost but quality improvement is marginal, stay single-call and add output constraints instead.
  • Document the decision, not just the result: In production architectures, record why you chose to decompose (or not). When requirements change, this record tells you whether the original decision still holds.
  • Prototype before architecting: Run the task as a single prompt first. If the output is 80%+ acceptable, optimize the prompt rather than decomposing. Decomposition is a structural change; prompt refinement is a tuning change.

✅ Quick-Check Questions
Q1: A task requires Claude to analyze financial data, write a narrative summary, and produce a formatted HTML report. Does this require decomposition?
Not necessarily. While the task has three sub-objectives, they form a single output pipeline (analyze → narrate → format) with low cognitive breadth overlap. Apply the context budget check: if all reference data, instructions, and expected output fit within 60% of the context window, a well-structured single prompt with clear section instructions can handle this. Decompose only if the financial data alone consumes a large portion of the context, or if the formatting step requires specialized tooling (like code execution).
Q2: What distinguishes "reasoning depth" from "cognitive breadth" in complexity assessment?
Reasoning depth measures the length of the inference chain (Step A's conclusion feeds Step B's premise, which feeds Step C). Cognitive breadth measures the number of parallel knowledge domains required (e.g., law + medicine + statistics). A task can be deep but narrow (multi-step mathematical proof) or broad but shallow (summarize documents from five departments). Each dimension independently triggers decomposition at its own threshold.
Q3: Why is 60% of the context window used as the threshold rather than, say, 90%?
Claude's output quality degrades well before the hard context limit because the model must allocate attention across instructions, reference data, in-progress reasoning, and the output itself. At 60%, there is still sufficient "headroom" for the model to maintain coherent reasoning and generate structured output. Beyond 60%, the model increasingly drops details, shortens reasoning chains, and produces less accurate summaries. The 60% figure is an empirically derived guideline for maintaining high-quality output, not a theoretical limit.
6.2

Top-Down vs Bottom-Up Decomposition

📘 Core Concept

Once you have decided to decompose, the next question is direction of decomposition. Two fundamental strategies exist, each suited to different scenarios. Top-down decomposition starts from the high-level goal and recursively breaks it into smaller subgoals until each subgoal is simple enough for a single Claude call. Bottom-up decomposition starts from known atomic capabilities—things Claude can do well in a single call—and composes them into a larger workflow that achieves the overall objective.

Top-down decomposition is the natural choice when the goal is well-defined but the path to achieving it is unclear. For example, "produce a competitive analysis report for Company X" has a clear deliverable, but the architect must decide how to structure the research, analysis, and formatting steps. The architect starts with the final output and works backward: what sections does the report need? What data feeds each section? What analysis produces that data? Each question yields a subtask.

Bottom-up decomposition excels when the capabilities are well-understood but the goal is emergent or loosely specified. For example, "build a workflow that helps users understand their codebase" is vague, but the architect knows Claude can summarize files, extract function signatures, generate dependency graphs, and answer questions about code. The architect composes these known capabilities into a pipeline that achieves the broad objective. Bottom-up is also the preferred strategy when integrating Claude into existing tool chains where each tool's input/output contract is fixed.

In practice, most production architectures use a hybrid approach: top-down for the overall structure (defining the workflow stages), then bottom-up within each stage (selecting and composing specific Claude capabilities to fulfill that stage). The exam tests your ability to identify which strategy is primary for a given scenario and to recognize when hybrid is the correct answer.

🔑 Key Terms
TermDefinition
Top-DownDecomposition starting from the goal, recursively splitting into subgoals until each is atomic. Best when the deliverable is clearly defined.
Bottom-UpDecomposition starting from known atomic capabilities, composing them into progressively larger functional units. Best when capabilities are fixed.
HybridUsing top-down for the macro workflow structure and bottom-up for the micro capability selection within each stage.
Atomic TaskA task simple enough to be completed in a single Claude call with high reliability and no further splitting needed.
Recursive SplittingThe process of taking a non-atomic task and dividing it into two or more subtasks, repeating until all subtasks are atomic.

💡 Tips & Tricks
  • Default to top-down for exam scenarios: When the question gives you a specific deliverable (report, analysis, plan), top-down is almost always the primary strategy. The exam uses "vague goal + known tools" as the signal for bottom-up.
  • The "leaf test" for top-down: Stop recursing when a subtask can be described in one sentence and executed reliably with a single prompt. If you need a paragraph to describe a leaf task, it is not atomic yet.
  • Bottom-up guardrail: After composing a bottom-up pipeline, run a "coverage check" by comparing the pipeline outputs against the stated goal's requirements. Each requirement should map to at least one module. Missing mappings reveal gaps.
  • Hybrid is usually the real answer: When the exam offers both top-down and bottom-up as answer choices alongside hybrid, and the scenario involves both a clear goal and existing tooling, choose hybrid. The exam rewards nuanced over absolute answers.
  • Watch for the over-decomposition trap: If your decomposition results in subtasks that are individually trivial (e.g., "extract the title from a document"), you have gone too far. Merge trivial adjacent subtasks into a single call.

Question Type: Scenario-based MCQ, "which approach is MOST appropriate?"

✅ Quick-Check Questions
Q1: A company has a suite of Claude-powered tools (summarizer, classifier, extractor) and wants to "improve customer support quality." Which decomposition approach is primary?
Bottom-up. The goal ("improve support quality") is loosely defined and emergent, but the capabilities (summarizer, classifier, extractor) are well-understood. The architect should compose these existing tools into a workflow—for example: classify incoming ticket → extract key entities → summarize prior interactions → draft response. Each module is a known capability being wired together.
Q2: An architect must produce a 50-page regulatory compliance report. The deliverable's sections, formatting, and data sources are all specified. Which approach?
Top-down. The goal is crystal clear: a 50-page report with specified sections. The architect starts with the report outline and decomposes each section into data-gathering, analysis, and formatting subtasks. There is no ambiguity about what needs to be produced—only about how to produce it. Bottom-up would be incorrect because the "what" is defined; it is the "how" that needs structuring.
Q3: When should an architect merge subtasks during top-down decomposition?
Merge subtasks when two or more adjacent leaves are trivially simple (each can be described in a single short sentence), share the same context (they need the same input data), and produce tightly coupled outputs (the output of one is immediately consumed by the next with no branching). Merging reduces coordination overhead without sacrificing quality. The "leaf test" applies: if the merged task is still describable in one sentence and executable in one call, the merge is valid.
6.3

Iterative Refinement Loops for Subagent Outputs

📘 Core Concept

Decomposition alone does not guarantee quality. Each subagent (a Claude call assigned to a subtask) produces an output that may be incomplete, imprecise, or misaligned with the downstream requirements. Iterative refinement loops address this by introducing a generate → evaluate → refine cycle where a subagent's output is assessed against explicit criteria, and the subagent is re-invoked with targeted feedback until the output meets a quality threshold. This pattern is sometimes called "self-critique" or "verifier-refinement" in the literature.

A refinement loop has four essential components. First, the generator: the subagent that produces the initial output. Second, the evaluator: a separate Claude call (or the same call with a different prompt) that scores the output against predefined criteria. The evaluator may be a structured rubric prompt that returns a score and a list of specific deficiencies. Third, the feedback injector: the mechanism that takes the evaluator's assessment and injects it into the generator's next prompt as context. Fourth, the convergence criterion: the condition that terminates the loop—typically a score threshold, a maximum iteration count, or a "no new feedback" condition.

The critical design decision is what the evaluator checks. Vague evaluation ("is this output good?") produces vague feedback and slow convergence. Effective evaluators use dimensional scoring: accuracy, completeness, formatting compliance, tone alignment, and logical coherence are scored independently on a numeric scale. This gives the generator actionable feedback ("accuracy: 8/10, completeness: 5/10 — missing sections on pricing and timeline") rather than subjective impressions.

A common architectural mistake is using unlimited refinement loops. Without a hard iteration cap, a loop can cycle indefinitely—especially when the evaluator and generator disagree on interpretation. Best practice is to set a maximum of 2–3 refinement iterations. If the output hasn't converged by then, the issue is likely in the task specification or decomposition, not in the generation quality. Escalate to a human reviewer or restructure the subtask.

TermDefinition

Convergence CriterionThe condition that stops the loop: a score threshold, a max iteration count, or a "no new deficiencies" condition.

💡 Tips & Tricks
  • Separate evaluator from generator: Using the same prompt to both generate and evaluate creates confirmation bias—Claude will rate its own output more generously. A separate evaluator call with a dedicated rubric produces more honest scoring and faster convergence.
  • Make feedback structural, not editorial: "Section 3 is missing a pricing comparison table" is actionable feedback. "Section 3 could be better" is not. Structure your evaluator's output as a list of {dimension, score, specific_deficiency} objects.
  • Cap at 3 iterations: Research and practice show that LLM refinement loops produce diminishing returns after 2–3 rounds. If quality hasn't converged, the issue is upstream: the task spec is ambiguous, the decomposition is wrong, or the reference data is insufficient.
  • Cost check: multiply by N: Each refinement iteration roughly doubles the token cost for that subtask (generator + evaluator calls). A 3-iteration loop costs ~6x a single call. Budget accordingly and only apply refinement to high-stakes outputs.
  • Use "delta feedback" in later iterations: In iteration 2+, only include the new deficiencies found, not the full evaluation. This focuses the generator on unresolved issues and prevents regression on already-fixed items.
🎯 Exam Strategy
Question Type: Component identification, ordering, and "what's missing from this loop?" diagnostic questions
Likely Stem: "A refinement loop is producing diminishing quality improvements after each iteration. Which component is MOST likely misconfigured?"
Common Trap: Confusing iterative refinement (section 6.3) with iterative decomposition (breaking tasks further). Refinement improves a fixed subtask's output; decomposition changes the task structure. The exam will offer "decompose further" as a distractor when the correct answer is "improve the evaluator."
Answer Framework: IDENTIFY the failing component (generator, evaluator, feedback injector, convergence criterion) → DIAGNOSE the symptom (e.g., vague feedback = evaluator issue; looping forever = convergence issue) → PRESCRIBE a targeted fix.
✅ Quick-Check Questions
Q1: A refinement loop runs for 5 iterations without converging. What is the MOST likely root cause?
The most likely root cause is that the evaluator's criteria are too vague or conflicting, causing it to generate feedback that the generator cannot act on effectively. Alternatively, the convergence criterion may be set unrealistically high (e.g., requiring 10/10 on all dimensions). The fix is to audit the evaluator's rubric for actionability and adjust the score thresholds. A secondary cause is that the task itself may be under-specified—no amount of refinement can fix a bad decomposition. The hard cap (3 iterations) should have prevented running 5 iterations; its absence signals a missing architectural safeguard.
Q2: Why should the evaluator be a separate Claude call rather than part of the generator's prompt?
Separation eliminates confirmation bias. When Claude generates and evaluates in the same call, it has cognitive incentive to rate its own output favorably—it has already committed to a reasoning path. A separate call with a dedicated evaluation rubric approaches the output as a fresh assessor, producing more objective scores. Additionally, separate calls allow the evaluator to use a different system prompt optimized for critique rather than generation, and they enable independent tuning of each component.
Q3: What is "delta feedback" and when is it used?
Delta feedback means including only the new or unresolved deficiencies in the feedback injection, rather than the full evaluation from all prior iterations. It is used from iteration 2 onward. The purpose is twofold: (1) it focuses the generator's attention on remaining issues rather than re-processing already-fixed items, and (2) it reduces token usage in the feedback portion of the prompt. Without delta feedback, the generator may regress on fixed issues while addressing new ones, creating an oscillation pattern that prevents convergence.
6.4

Balancing Breadth and Depth in Research Decomposition

📘 Core Concept

Research-oriented tasks present a unique decomposition challenge: how much of the problem space should each subagent cover, and how deeply should it investigate? This is the breadth-versus-depth tradeoff. Allocating too many subagents to broad coverage produces a report that mentions everything but explains nothing. Allocating too few, deeply focused subagents produces a report with blind spots—critical topics are never investigated because no subagent was assigned to them.

The architect's tool for managing this tradeoff is the research decomposition matrix. This is a two-dimensional grid where one axis lists the topics or dimensions that must be covered (breadth), and the other axis defines the investigation depth levels for each topic—from surface-level scanning (identify that the topic exists and note key facts) to deep analysis (multi-source synthesis, quantitative evaluation, and expert-level assessment). Each cell in the matrix is assigned a depth level, and this assignment determines the subagent's scope.

A common pattern is the "T-shaped" research strategy: assign broad, shallow coverage (Level 1: surface scan) to all topics, then assign deep investigation (Level 3: full analysis) to only 2–3 high-priority topics identified by the stakeholder or the task specification. This ensures no important topic is missed entirely while concentrating analytical effort where it matters most. The "T" shape comes from the visual: a wide horizontal bar (broad coverage) with a narrow vertical drop (deep focus on select topics).

Resource allocation directly follows from the matrix. Each depth level has a known token budget profile: Level 1 (surface scan) may require 500–1,000 tokens of output and minimal reference data; Level 2 (moderate analysis) requires 1,500–3,000 tokens and may need retrieval-augmented context; Level 3 (deep analysis) requires 3,000–6,000+ tokens with extensive source material and potentially multiple calls with chain-of-thought prompting. The architect maps these profiles to the matrix to estimate total cost and latency, then adjusts the distribution if the budget is constrained. This is a core architectural skill: making explicit tradeoffs between coverage quality and resource consumption.

💡 Tips & Tricks
  • Start with the matrix, not the prompts: Building the research decomposition matrix before writing any prompts forces you to make breadth/depth tradeoffs explicitly. Architects who skip this step tend to create lopsided decompositions—deeply researching the first topic they think of and rushing through the rest.
  • Use L1 results to decide L3 targets: A two-phase approach works well: run all topics at L1 first, then use the results to decide which topics warrant L3. This is an "adaptive T" strategy that avoids over-investing in topics that turn out to be less important than initially assumed.
  • Budget for synthesis: The matrix allocates resources to individual topics, but the final deliverable also needs a synthesis step that integrates findings across topics. Budget 15–20% of total tokens for this cross-cutting synthesis subagent.
  • Flag coverage gaps visually: After filling the matrix, any row with no checkmarks at any depth level is a coverage gap. These are easy to miss when working from a flat task list but immediately visible in a matrix format. Review for gaps before executing.
  • Parallelize within depth levels: All L1 scans can run in parallel (no dependencies). L3 deep dives may also parallelize if they cover independent topics. Only the synthesis step requires all prior outputs, making it the serialization bottleneck.

Question Type: Resource allocation scenarios, "which configuration optimizes the tradeoff?" analysis
Likely Stem: "A research task must cover 8 topics within a fixed token budget. The stakeholder marks 2 topics as critical. Which allocation strategy BEST balances coverage and depth?"
Common Trap: Choosing "deep analysis on all topics" when the budget is constrained. The exam penalizes answers that ignore resource constraints. Also, confusing the T-shaped strategy with simple prioritization—T-shaped always includes broad L1 coverage, not just deep dives on the priorities.
Answer Framework: LIST the topics → MAP each to a depth level based on priority and budget → VERIFY no coverage gaps → ALLOCATE remaining budget to synthesis. The answer that does all four steps is correct.
✅ Quick-Check Questions
Q1: What is the risk of assigning ALL topics to Level 3 (deep analysis)?
Three risks: (1) Budget overrun—L3 costs ~10x more tokens than L1 per topic; with 8 topics at L3, you may exceed the total budget. (2) Latency—even with parallelization, L3 tasks take significantly longer, and the synthesis step must wait for all of them. (3) Diminishing returns—many topics simply don't have enough substance to justify deep analysis; you'll spend tokens producing padded content. The T-shaped strategy avoids all three by reserving L3 for genuinely complex priority topics.
Q2: How does the "adaptive T" strategy differ from a standard T-shaped strategy?
In a standard T, the priority topics for L3 are chosen upfront—before any research is done—based on stakeholder input or task specification. In an adaptive T, all topics first receive L1 (surface scan) treatment. The L1 results are then evaluated to determine which topics have the most complexity, controversy, or data richness, and those are assigned to L3 in a second phase. This is more expensive (two-phase execution) but more accurate because depth allocation is based on evidence rather than assumption.
Q3: Why should an architect budget 15–20% of tokens for a synthesis step?
Individual topic subagents produce findings in isolation—they don't see each other's outputs. The synthesis step is a dedicated subagent that receives all topic outputs and integrates them into a coherent deliverable: identifying cross-cutting themes, resolving contradictions, creating a unified narrative, and ensuring the final output addresses the original research question holistically. Without this step, the deliverable reads as a collection of independent summaries rather than a cohesive analysis. 15–20% is the typical allocation because synthesis requires reading all prior outputs (context) and generating a substantive integrative section (output).
6.5

Hands-On: Decomposing a Complex Research Query

📘 Core Concept

This section integrates all prior concepts into a fully worked example. You will see the complete process: starting with a complex, real-world research request; running it through complexity assessment; choosing a decomposition strategy; building the research matrix; designing refinement loops for critical outputs; and producing a final execution plan with subagent specifications.

The worked example matters for the exam because Section 6.5 questions are typically multi-step scenario questions where you must apply concepts from sections 6.1–6.4 in sequence. You cannot answer these questions by knowing only one section—they test integrated understanding. The example below follows the exact reasoning pattern the exam expects.

Our example query: "Analyze the competitive landscape of large language model API providers (OpenAI, Anthropic, Google, Meta, Mistral) across pricing, performance benchmarks, developer experience, enterprise features, and regulatory compliance posture. Produce a recommendation for a mid-size SaaS company choosing a primary LLM provider." This is representative of exam scenario complexity—it has breadth (5 providers × 5 dimensions = 25 cells), requires depth on key dimensions, and demands a synthesized recommendation.

📘 Worked Example — Step-by-Step Decomposition
Step 1 — Complexity Assessment (Section 6.1)
Apply the four-gate decision tree

Gate 1 — Cognitive Breadth: The task spans pricing analysis, performance benchmarking, UX evaluation, enterprise feature comparison, and legal/regulatory analysis. That's 5 distinct domains. ≥ 3 → DECOMPOSE. (Already triggered.)
Gate 2 — Reasoning Depth: The recommendation requires analyzing each provider across each dimension, synthesizing across all 25 cells, and weighing tradeoffs. That is ≥ 4 sequential reasoning steps. → DECOMPOSE.
Gate 3 — Context Budget: 5 providers × 5 dimensions, each requiring sourced data = massive reference context. Easily > 60% of even a 200K context window if done properly. → DECOMPOSE.
Gate 4 — Dependencies: The recommendation depends on all 25 analysis cells being complete. → DECOMPOSE.
Decision: Decompose. All four gates triggered.

Step 2 — Choose Decomposition Strategy (Section 6.2)
Top-down, because the deliverable is clearly defined

The deliverable is a competitive analysis report with a recommendation. This is a well-defined goal → top-down decomposition is the primary strategy. We will also use bottom-up within the data-gathering phase to compose known retrieval capabilities (web search, document analysis, structured extraction).

Top-level decomposition:
Stage 1: Data Gathering (per-provider, per-dimension) → parallel
Stage 2: Analysis & Scoring (per-dimension comparison) → depends on Stage 1
Stage 3: Synthesis & Recommendation → depends on Stage 2

Step 3 — Build the Research Matrix (Section 6.4)
Apply T-shaped strategy with stakeholder priorities

The mid-size SaaS company cares most about pricing (budget-constrained) and developer experience (small team, needs fast integration). These get L3 depth. The remaining three dimensions get L1–L2.

Step 4 — Design Refinement Loops (Section 6.3)
Apply refinement to the two critical outputs

Two outputs are high-stakes: the pricing analysis (errors here directly affect the recommendation) and the final recommendation (this is the deliverable the stakeholder reads first). Each gets a refinement loop:

Pricing Analysis Loop: Generator produces per-provider cost comparison → Evaluator scores on accuracy (are the numbers current?), completeness (are all pricing tiers covered?), and comparability (is the comparison using the same units?). Convergence: all scores ≥ 8/10, max 2 iterations.

Recommendation Loop: Generator synthesizes all analyses into a recommendation → Evaluator scores on evidence linkage (does each claim trace to an analysis?), balance (are all 5 dimensions weighted?), and actionability (can the SaaS company act on this?). Convergence: all scores ≥ 8/10, max 3 iterations.

Step 5 — Build the Execution Plan
Define the dependency DAG and orchestration sequence

The final execution plan specifies three phases. Phase 1 (parallel): all 25 data-gathering subagents run simultaneously—no dependencies between them. Phase 2 (5× parallel): each dimension's comparison subagent runs once all 5 providers' data for that dimension are complete. Phase 3 (serial): the synthesis subagent runs once all 5 comparison outputs are ready, then enters its refinement loop. Total latency = max(Phase 1 latency) + max(Phase 2 latency) + Phase 3 latency × (1 + refinement iterations).

💡 Tips & Tricks
  • On the exam, draw the DAG mentally: Scenario questions in 6.5 test whether you can identify which phases parallelize and which serialize. The critical path (longest path through the DAG) determines total latency—that's usually what the question asks about.
  • Watch the subagent count: If your decomposition produces > 40 subagent calls, question whether you've over-decomposed. The worked example has ~31 calls before refinement and ~37 after—this is at the upper end of practical for a single orchestration run.
  • Don't forget the synthesis budget: A common exam mistake is accounting for all data-gathering and comparison costs but forgetting the synthesis step. The synthesis subagent consumes the outputs of all prior steps as input—its context can be very large.
  • Adapt the worked example pattern: The exam won't use the same query, but the structure is always the same: assess → choose strategy → build matrix → add refinement → plan DAG. Memorize this five-step sequence.
🎯 Exam Strategy
Question Type: Multi-step scenario requiring you to apply concepts from 6.1–6.4 in sequence. May ask "what is the NEXT step?" or "which phase has the highest latency?"
Likely Stem: "Given the following research query and constraints, an architect has completed Steps 1–3. What should Step 4 address?"
Common Trap: Jumping to execution details (prompt writing, API parameters) before completing the architectural plan. The exam rewards structured planning over implementation speed. Another trap: selecting "add more subagents" when the correct answer is "add a refinement loop to existing subagents."
Answer Framework: Follow the five-step sequence: (1) Assess complexity → (2) Choose strategy → (3) Build matrix → (4) Add refinement → (5) Plan DAG. If the question asks "what's next?" after step N, the answer is step N+1. If it asks "what's wrong?" about a plan, check which step was skipped.
✅ Quick-Check Questions
Q1: In the worked example, what is the critical path that determines total latency?
The critical path is: longest Phase 1 data-gathering task → longest Phase 2 comparison task (with refinement) → Phase 3 synthesis (with refinement). Specifically: one of the L3 data-gathering tasks (pricing or DevEx, since they produce the most output) → Pricing Comparison + 2 refinement iterations → Synthesis + 3 refinement iterations. This is the longest sequential chain. Parallelization helps within phases but cannot shorten this critical path. Latency optimization would focus on reducing Phase 3 refinement iterations (the largest serial bottleneck).
Q2: If the token budget is cut by 40%, which adjustment to the matrix is MOST appropriate?
The most appropriate adjustment is to downgrade L2 tasks (Performance benchmarks) to L1 and reduce L3 refinement iterations from 2 to 1. This preserves the T-shaped structure (pricing and DevEx remain L3 as stakeholder priorities) while cutting the moderate-depth and refinement costs. Downgrading priority topics from L3 to L2 would be worse because it directly reduces quality on the dimensions the stakeholder cares about most. Cutting topics entirely (removing a provider) would create coverage gaps and a less useful deliverable.
Q3: An architect skips building the research matrix and goes directly from "decompose" to writing prompts. What problems are likely to emerge?
Three problems: (1) Uneven coverage—without a matrix, the architect likely over-invests in whichever topic they write first and under-invests in later topics as they realize the budget is running low. (2) Hidden coverage gaps—without a systematic grid, entire dimensions may be accidentally omitted (e.g., regulatory compliance is easy to forget). (3) No basis for tradeoff decisions—when the budget constrains, the architect has no structured framework for deciding what to cut; decisions become ad hoc. The matrix is the architect's planning artifact—skipping it is like writing code without a design.
