Agentic Loops — Autonomous Task Execution

Master the architecture of autonomous Claude agents: the request-inspect-execute-return lifecycle, stop_reason-driven control flow, correct tool result management, and the anti-patterns that derail production systems. This chapter is the foundation of every agentic system built on Claude.

📌
Chapter Overview

An agentic loop is a while loop that repeatedly calls the Claude API, inspects the stop_reason field to decide what to do next, executes any requested tools, appends results back into the conversation, and repeats — until Claude signals it's done. This single pattern underlies every Claude-powered agent, from simple tool-calling assistants to multi-step autonomous planners.

2.1 The Agentic Loop Lifecycle

Every agentic loop follows a four-phase lifecycle: Request → Inspect → Execute → Return. Understanding the precise responsibility of each phase — and the data that flows between them — is non-negotiable for the exam and for building reliable agents.

Phase Definitions

1
REQUEST — Send the message to Claude

Pack the full conversation history (system prompt, all prior user/assistant/tool messages) plus the list of available tools into an API call via client.messages.create(). Claude receives the complete context and generates a response.

Data in: messages array, tools array, model, max_tokens
Data out: API response object

2
INSPECT — Check stop_reason

Read response.stop_reason. This is the only reliable signal for what the model wants to happen next. If it's "tool_use", the model is requesting tool execution. If it's "end_turn", the model considers the task complete.

Data in: response object
Data out: control flow decision (continue loop / exit loop / handle error)

3
EXECUTE — Run the requested tools

Extract every tool_use content block from the response, execute each corresponding function with the provided input arguments, and collect results. A single response can contain multiple tool_use blocks — all must be executed and returned.

Data in: tool_use blocks (name, id, input)
Data out: tool results with matching IDs

4
RETURN — Append results & loop back

Append Claude's assistant message (the full response content) and a new user message containing tool_result blocks to the conversation history. Then return to phase 1 for the next API call. Claude will see the tool outputs and decide what to do next.

Data in: tool execution results
Data out: updated messages array → back to phase 1

Lifecycle Diagram

Failure Modes at Each Transition

Transition Failure Mode Impact Mitigation
Request → Inspect API error (rate limit, auth, network) Loop never starts or stalls Retry with exponential backoff; raise after N retries
Inspect → Execute Unrecognized stop_reason Undefined behavior; silent data loss Treat unknown values as errors; raise ValueError
Execute → Return Tool execution failure (exception, timeout) Missing result breaks Claude's context Catch exceptions; return error message as tool result
Return → Request Malformed message history (wrong roles, missing IDs) API rejects the request; loop crashes Validate message structure before each API call

Minimal Code: The Complete Lifecycle

# The four-phase agentic loop in its simplest form
import anthropic

client = anthropic.Anthropic()
messages = [{"role": "user", "content": "What's the weather in London?"}]
tools = [weather_tool_definition]  # defined elsewhere

while True:
    # PHASE 1: REQUEST
    response = client.messages.create(
        model="claude-sonnet-4-20250514",
        max_tokens=4096,
        tools=tools,
        messages=messages
    )

    # PHASE 2: INSPECT
    if response.stop_reason == "end_turn":
        break  # Model is done — exit the loop
    elif response.stop_reason == "tool_use":
        # PHASE 3: EXECUTE
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result
                })

        # PHASE 4: RETURN
        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})
    else:
        raise ValueError(f"Unexpected stop_reason: {response.stop_reason}")
PYTHON
💡
Key Insight

The agentic loop is not an AI concept — it's a while loop with a structured exit condition. The model doesn't "run" tools; your code does. Claude only requests tool execution by setting stop_reason to "tool_use". Your code is the executor, the model is the decision-maker.

⚠️
Common Mistake

Forgetting to append both the assistant message (with tool_use blocks) and the user message (with tool_result blocks) before looping back. If you skip the assistant message, Claude loses context of what it asked for. The conversation history must always alternate correctly: user → assistant → user → assistant.

🎯
Exam Tip

When a question asks "what are the phases of an agentic loop," the canonical answer is exactly four: Request, Inspect, Execute, Return. Don't add "Plan" or "Decide" as separate phases — planning and deciding happen within the model during the Request phase. The loop structure is about your code's control flow, not the model's internal reasoning.

🔗
Connection

This lifecycle is the foundation for Chapter 3 (Multi-Turn Tool Orchestration) and Chapter 5 (Error Recovery Strategies). The four-phase structure remains identical in complex agents — what changes is the sophistication of the Execute and Return phases.

2.2 Understanding stop_reason

The stop_reason field is the single most critical signal in an agentic loop. It's a structured, machine-readable indicator that tells your code exactly why the model stopped generating. Every loop iteration must inspect this field — and only this field — to decide what happens next.

Definitive Values

Value Meaning Your Code Should
"end_turn" The model has finished its response and does not need any tools. It considers the current task complete (or has provided its final answer). Exit the loop. Extract the final text from response.content and return it to the user.
"tool_use" The model wants to call one or more tools. The response's content array contains tool_use blocks specifying which tools to call and with what arguments. Execute tools & continue the loop. Run each requested tool, build tool_result messages, append to history, and make another API call.
"max_tokens" The response was truncated because it hit the max_tokens limit. The model was still generating when cut off. Handle as a special case. You may either increase max_tokens and retry, or treat as a partial response. Never silently ignore this.
"stop_sequence" The model hit a custom stop sequence defined in the API call parameters. Handle per your application logic. This is rarely used in agentic loops but may appear in constrained output scenarios.

Decision Flowchart

What Happens When You Get It Wrong

Mistake What Happens Severity
Treat "tool_use" as "end_turn" Loop exits prematurely. Claude asked for a tool but never gets the result. The user receives an incomplete response (often just the model's reasoning, not the answer). Critical
Treat "end_turn" as "tool_use" Code tries to extract tool_use blocks from a text-only response. Crashes or produces empty tool results. May cause infinite loop if the code re-sends. Critical
Ignore "max_tokens" Truncated response is treated as complete. Partial JSON, broken instructions, or missing data propagates downstream silently. High
No handler for unexpected values If Anthropic adds a new stop_reason in the future, the code silently drops into an unhandled state — potentially infinite-looping. High

Correct Pattern: Exhaustive Handling

# ✅ CORRECT: Handle every possible stop_reason
if response.stop_reason == "end_turn":
    # Task complete — extract and return the final text
    final_text = "".join(
        block.text for block in response.content
        if hasattr(block, "text")
    )
    break

elif response.stop_reason == "tool_use":
    # Model wants tools — execute and continue
    tool_results = process_tool_calls(response)
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": tool_results})

elif response.stop_reason == "max_tokens":
    # Response was truncated — handle explicitly
    logger.warning("Response truncated at max_tokens")
    raise RuntimeError("Max tokens reached; increase max_tokens or simplify the task.")

else:
    # Future-proof: reject unknown stop_reasons loudly
    raise ValueError(f"Unhandled stop_reason: {response.stop_reason}")
✅ CORRECT
💡
Key Insight

stop_reason is a structural signal, not a content signal. It tells you about the structure of the response (does it contain tool calls or not?), not about the meaning of the text. This distinction is why checking text content for phrases like "I'm done" is always wrong.

⚠️
Common Mistake

Checking response.content[0].text to decide if the loop should continue. The content array may contain both text blocks and tool_use blocks in the same response. The model often "thinks out loud" before requesting a tool. Only stop_reason tells you what the model actually wants your code to do.

🎯
Exam Tip

If a question shows code that checks if "tool_use" in str(response.content) or if response.content[-1].type == "tool_use", those are wrong — even if they'd work in some cases. The exam tests for the canonical pattern: response.stop_reason == "tool_use". Don't be tricked by "technically works" alternatives.

🔗
Connection

stop_reason handling is the direct prerequisite for Section 2.5 (Loop Control Flow) and Section 2.6 (Anti-Patterns). Every anti-pattern in Section 2.6 is, at its core, a failure to use stop_reason correctly.

2.3 Appending Tool Results to Conversation History

The conversation history is the shared memory between your code and Claude. After executing tools, you must append the results in a very specific format. Getting the structure, ordering, or role assignments wrong will cause API errors or — worse — silently corrupt Claude's understanding of what happened.

The Exact Message Structure

After Claude responds with stop_reason: "tool_use", you must append two messages:

# Message 1: The assistant's response (including tool_use blocks)
{
    "role": "assistant",
    "content": [
        {
            "type": "text",
            "text": "Let me check the weather for you."
        },
        {
            "type": "tool_use",
            "id": "toolu_01A09q90qw90lq917835lq9",
            "name": "get_weather",
            "input": {"city": "London"}
        }
    ]
}

# Message 2: The tool results (as a "user" message)
{
    "role": "user",
    "content": [
        {
            "type": "tool_result",
            "tool_use_id": "toolu_01A09q90qw90lq917835lq9",
            "content": "Partly cloudy, 18°C, humidity 72%"
        }
    ]
}

Critical Rules

  1. Role assignment: The assistant's response uses "role": "assistant". Tool results use "role": "user". This is counter-intuitive but mandatory — your code sends tool results, so they're a "user" message from the API's perspective.
  2. ID matching: Every tool_result block's tool_use_id must exactly match the id of the corresponding tool_use block. Mismatched IDs cause API errors.
  3. All tools answered: If Claude requested 3 tools in one turn, you must return 3 tool_result blocks. Missing results cause the API to reject your next call.
  4. Order within the user message: All tool_result blocks go in a single user message, not separate messages. The order within that message doesn't matter as long as IDs match.
  5. Content serialization: The content of a tool_result must be a string (or an array of content blocks). If your tool returns JSON, serialize it to a string first.

Edge Cases

Failed Tool Execution

# When a tool throws an exception, return the error as a tool result
# with is_error=True — do NOT skip the result entirely
{
    "type": "tool_result",
    "tool_use_id": "toolu_01AAA",
    "content": "Error: Connection timeout after 30s. The weather API is unavailable.",
    "is_error": True
}
TOOL ERROR FORMAT

Setting is_error: true tells Claude the tool failed. Claude can then decide to retry, use an alternative approach, or inform the user — all without your code needing to hardcode recovery logic.

Empty / Null Tool Results

# A tool that returns nothing (e.g., a "send_email" action)
{
    "type": "tool_result",
    "tool_use_id": "toolu_01CCC",
    "content": "Success: email sent."
}
# Even for void actions, always return a confirmation string.
# Never pass content: null or content: ""
✅ CORRECT

Multiple Tools in One Turn — Implementation

                "tool_use_id": block.id,

Key Insight

Tool results are sent as a "user" message — not as an "assistant" message and not as a separate role. This is because tool results represent new information entering the conversation from outside the model. The API models them as user-provided input, even though they were generated by your tool execution code.

⚠️
Common Mistake

Sending tool results as separate user messages instead of one combined message. If Claude requested 3 tools, you must return one user message with 3 tool_result blocks — not 3 user messages with 1 block each. Multiple consecutive user messages violate the API's alternation requirement.

🎯
Exam Tip

If a question asks "what role do tool results use?", the answer is "user". This is a high-frequency trick question because it feels wrong — your infrastructure code produces the results, not the human user. But from the API's perspective, any non-model input enters as a user message. Watch for answer options that say "tool" or "system" — both are wrong.

🔗
Connection

The is_error: true pattern connects directly to Chapter 5 (Error Recovery). When Claude receives an error tool result, it uses its own judgment to decide next steps — retry, use a different tool, or report the failure. This is model-driven decision-making in action (Section 2.4).

2.4 Model-Driven Decision-Making vs Pre-Configured Decision Trees

A fundamental architectural choice in every agentic system is: who decides what to do next — the model or your code? Both approaches have legitimate use cases, but the Claude ecosystem strongly favors model-driven decision-making as the default. Understanding why — and when to deviate — is critical for both the exam and production systems.

Definitions

Model-Driven Pre-Configured Decision Tree
Who decides Claude determines which tools to call, in what order, and when to stop — based on the system prompt, available tools, and conversation context. Your code hardcodes the sequence of actions. The model fills in parameters or generates text, but the control flow is predetermined.
Loop control stop_reason drives the loop. Your code merely executes what Claude asks for. Your code decides when to call Claude, which tools to offer at each step, and when to terminate.
Adaptability High — Claude can handle unexpected inputs, change plans mid-task, and recover from tool failures autonomously. Low — the system only handles cases you explicitly coded for. Novel situations cause failures or incorrect behavior.
Predictability Lower — the model may take unexpected paths or call tools in unexpected orders. High — execution follows the exact sequence you designed.
Security Requires guardrails: tool-level permissions, input validation, output filtering. The model could potentially misuse powerful tools. Inherently more constrained: only the tools you explicitly offer at each step are accessible.
Best for Open-ended tasks, research, complex reasoning, multi-step problem solving, user-facing agents. Compliance workflows, safety-critical pipelines, batch processing, predictable data transformations.

Model-Driven Approach

        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": results})

        raise ValueError(f"Unexpected: {response.stop_reason}")

    tools=[calculator_tool], # Only calculator available
    messages=[{"role": "user", "content": f"Calculate growth from: {search_data}"}]

calculation = extract_result(step2)

# Step 3: Email (force the model to send)

    model="claude-sonnet-4-20250514",

    tools=[email_tool],      # Only email available
    messages=[{"role": "user", "content": f"Email this summary: {calculation}"}]

Decision Criteria: When to Use Each

Criterion Use Model-Driven Use Pre-Configured
Task complexity Open-ended, ambiguous, multi-step reasoning Well-defined, repeatable, deterministic
Tool risk Low-risk tools (read-only, reversible) High-risk tools (payments, deletions, external systems)
User trust Interactive agent with human in the loop Batch automation with no human oversight
Error tolerance Retry/recovery is acceptable Errors are costly (compliance, financial)
Exam default Model-driven is the expected default answer unless the question specifies constraints that require pre-configuration.
💡
Key Insight

The model-driven approach is not "letting the AI run wild." It's delegating the decision graph to the model while your code enforces the execution boundaries. You still validate inputs, cap iterations, authenticate tools, and handle errors. The model just decides which tools to call and in what order.

⚠️
Common Mistake

Building a pre-configured pipeline and then wondering why the agent can't handle edge cases. If you hardcode "Step 1: Search, Step 2: Calculate, Step 3: Email," what happens when the search returns nothing? With model-driven design, Claude would naturally adapt; with a decision tree, you need explicit error branches for every possible failure.

🎯
Exam Tip

When the exam asks "what is the recommended approach for agentic task execution," the answer is model-driven. The pre-configured approach is only correct when the question explicitly mentions constraints like "safety-critical," "compliance," or "must follow exact sequence." If in doubt, model-driven is the default.

2.5 Implementing Loop Control Flow

A production-grade agentic loop needs more than just a while True + stop_reason check. You need entry guards, continuation logic, safe exit conditions, iteration limits, timeouts, and graceful error recovery. This section shows the complete, annotated implementation.

Complete Annotated Loop

import anthropic
import time
import logging

logger = logging.getLogger(__name__)

class AgenticLoop:
    """Production-grade agentic loop with full control flow."""

    def __init__(self, client, model, tools, system_prompt,
                 max_iterations=10, timeout_seconds=300):
        self.client = client
        self.model = model
        self.tools = tools
        self.system_prompt = system_prompt
        self.max_iterations = max_iterations   # Safety cap — not an exit signal
        self.timeout = timeout_seconds
        self.tool_registry = self._build_registry(tools)

    def run(self, user_message: str) -> str:
        """Execute the full agentic loop and return the final response."""
        messages = [{"role": "user", "content": user_message}]
        iteration = 0
        start_time = time.time()

        while True:
            # ── GUARD: Check iteration limit ──
            iteration += 1
            if iteration > self.max_iterations:
                logger.warning(f"Max iterations ({self.max_iterations}) reached")
                raise RuntimeError(
                    f"Agent exceeded {self.max_iterations} iterations. "
                    "Possible infinite loop — task may be too complex."
                )

            # ── GUARD: Check timeout ──
            elapsed = time.time() - start_time
            if elapsed > self.timeout:
                logger.warning(f"Timeout after {elapsed:.1f}s")
                raise TimeoutError(
                    f"Agent timed out after {self.timeout}s"
                )

            # ── PHASE 1: REQUEST ──
            try:
                response = self.client.messages.create(
                    model=self.model,
                    max_tokens=4096,
                    system=self.system_prompt,
                    tools=self.tools,
                    messages=messages
                )
            except anthropic.APIError as e:
                logger.error(f"API error on iteration {iteration}: {e}")
                raise

            # ── PHASE 2: INSPECT ──
            if response.stop_reason == "end_turn":
                # ✅ Normal exit: model is finished
                return self._extract_text(response)

            elif response.stop_reason == "tool_use":
                # ── PHASE 3: EXECUTE ──
                tool_results = self._execute_tools(response)

                # ── PHASE 4: RETURN ──
                messages.append({
                    "role": "assistant",
                    "content": response.content
                })
                messages.append({
                    "role": "user",
                    "content": tool_results
                })
                # Loop continues → back to PHASE 1

            elif response.stop_reason == "max_tokens":
                logger.warning("Response truncated at max_tokens")
                raise RuntimeError("Response exceeded max_tokens limit")

            else:
                raise ValueError(
                    f"Unexpected stop_reason: {response.stop_reason}"
                )

    def _execute_tools(self, response):
        """Execute all tool_use blocks and return tool_result list."""
        results = []
        for block in response.content:
            if block.type == "tool_use":
                try:
                    fn = self.tool_registry[block.name]
                    output = fn(**block.input)
                    results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": str(output)
                    })
                except Exception as e:
                    results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": f"Error: {e}",
                        "is_error": True
                    })
        return results

    def _extract_text(self, response):
        """Extract text content from the final response."""
        return "".join(
            block.text for block in response.content
            if hasattr(block, "text")
        )

    def _build_registry(self, tools):
        """Map tool names to callable functions."""
        # Implementation depends on your tool setup
        return {}

Control Flow Summary

Mechanism Purpose Implementation
Entry condition Ensure the loop starts with valid state Non-empty messages list, valid tools, authenticated client
Continuation logic Decide whether to loop again stop_reason == "tool_use" → continue

Key Insight

The iteration cap is a safety net, not a control mechanism. Your loop should almost never hit the cap — if it does regularly, you have a design problem (bad tools, unclear system prompt, or overly complex tasks). The cap exists to catch infinite loops, not to define normal exit behavior.

⚠️
Common Mistake

Using for i in range(5) as the loop structure. This treats the iteration cap as the primary loop control instead of stop_reason. It also masks the distinction between "the model finished" and "we ran out of iterations" — critical information for debugging and user experience.

🎯
Exam Tip

If a question asks "how should an agentic loop terminate normally," the answer is always stop_reason == "end_turn". Iteration limits, timeouts, and error handlers are abnormal termination paths. The exam distinguishes between the model's chosen exit (normal) and your code's forced exit (safety).

2.6 Common Anti-Patterns

These are the three most dangerous mistakes developers make when building agentic loops. Each one seems reasonable at first glance but introduces subtle, hard-to-debug failures. The exam tests these directly — you must be able to identify each anti-pattern and explain why it's wrong.

Anti-Pattern #1: Natural Language Signals

What It IsUsing the text content of Claude's response (e.g., "I'm done," "Here's your answer," "No more tools needed") as a signal to exit the loop.
Why It's WrongClaude's text output is natural language — it varies with phrasing, context, and model version. The model might say "I'm done" while also requesting a tool call, or it might rephrase its completion signal in infinite ways. Text is unreliable; stop_reason is definitive.
Correct ApproachAlways use response.stop_reason == "end_turn" for loop termination. Never inspect response.content text for control flow decisions.
# ❌ ANTI-PATTERN: Checking text content for exit signals
while True:
    response = client.messages.create(**params)

    # WRONG: Model phrasing is infinitely variable
    if "I'm done" in response.content[0].text:
        break
    if "final answer" in response.content[0].text.lower():
        break
    # What if Claude says "Here's what I found" instead?
    # What if content[0] is a tool_use block, not text?
    # This approach fails silently in both cases.
❌ WRONG
# ✅ CORRECT: Structural stop_reason check
while True:
    response = client.messages.create(**params)

    if response.stop_reason == "end_turn":
        break  # Definitive, machine-readable exit signal
    elif response.stop_reason == "tool_use":
        results = execute_tools(response)
        append_to_history(messages, response, results)
    else:
        raise ValueError(f"Unexpected: {response.stop_reason}")
✅ CORRECT

Anti-Pattern #2: Arbitrary Iteration Caps as Exit Conditions

What It IsUsing a fixed iteration count (e.g., for i in range(3)) as the primary mechanism for loop termination, rather than as a safety backstop.
Why It's WrongIt decouples termination from the model's actual state. A 3-iteration cap means the agent stops mid-task if it needs 4 tool calls, or wastes iterations if it finishes in 1. The model's stop_reason == "end_turn" is the semantically correct exit signal. A cap should only be a safety fallback.
Correct ApproachUse while True with stop_reason as the exit condition. Add an iteration counter as a safety cap that raises an error when exceeded — this is an abnormal termination, not a normal one.
# ❌ ANTI-PATTERN: Fixed iteration count as the loop structure
for i in range(3):   # WRONG: Why 3? What if the model needs 4 steps?
    response = client.messages.create(**params)
    if response.stop_reason == "tool_use":
        results = execute_tools(response)
        append_to_history(messages, response, results)
    else:
        break
# After the loop: no distinction between "model finished"
# and "we ran out of iterations." Both silently exit.
❌ WRONG
# ✅ CORRECT: stop_reason drives exit; iteration cap is a safety net
MAX_ITERATIONS = 25  # Generous cap — should rarely be hit

for iteration in range(1, MAX_ITERATIONS + 1):
    response = client.messages.create(**params)

    if response.stop_reason == "end_turn":
        break  # Normal exit: model decided it's done
    elif response.stop_reason == "tool_use":
        results = execute_tools(response)
        append_to_history(messages, response, results)
    else:
        raise ValueError(f"Unexpected: {response.stop_reason}")
else:
    # for-else: this runs only if the loop exhausted all iterations
    raise RuntimeError(f"Agent hit safety cap of {MAX_ITERATIONS} iterations")
✅ CORRECT

Anti-Pattern #3: Text-Content Checks for Tool Detection

What It IsInspecting the content of the response to determine if tools were called — e.g., checking if response.content[-1].type == "tool_use" or searching the content array manually instead of using stop_reason.
Why It's WrongA response's content array can contain both text blocks and tool_use blocks. The last element might be text even when tools were requested. The content structure is for payload extraction, not control flow. Only stop_reason is designed to signal the model's intent.
Correct ApproachUse response.stop_reason for control flow. Only iterate over response.content blocks after confirming stop_reason == "tool_use", and only to extract the tool call details.
# ❌ ANTI-PATTERN: Inspecting content structure for control flow
while True:
    response = client.messages.create(**params)

    # WRONG: Content structure doesn't reliably indicate intent
    has_tool = any(b.type == "tool_use" for b in response.content)
    if has_tool:
        results = execute_tools(response)
        append_to_history(messages, response, results)
    else:
        break  # Assumes no tool_use block = done. Fragile!
❌ WRONG
# ✅ CORRECT: stop_reason for control; content for data extraction
while True:
    response = client.messages.create(**params)

    # Control flow: stop_reason is the definitive signal
    if response.stop_reason == "end_turn":
        break
    elif response.stop_reason == "tool_use":
        # Data extraction: now iterate content safely
        tool_calls = [b for b in response.content if b.type == "tool_use"]
        results = [execute_single_tool(tc) for tc in tool_calls]
        append_to_history(messages, response, results)
    else:
        raise ValueError(f"Unexpected: {response.stop_reason}")
✅ CORRECT

💡
Key Insight

All three anti-patterns share a common root: using the wrong signal for control flow. The response content (text and content blocks) is data. The stop_reason field is the control signal. Mixing data-plane and control-plane information is a classic systems design error — and it's exactly what the exam tests for.

⚠️
Common Mistake

Thinking "well, checking for tool_use blocks in the content array works in practice." It might — until it doesn't. The Anthropic API contract is that stop_reason is the authoritative signal. If a future API version changes how content blocks are ordered (or adds new block types), your text-content check breaks. Building on stop_reason is forward-compatible; building on content structure is not.

Train yourself to scan for three things: (1) string matching on response text, (2) for i in range(N) as the main loop, (3) content inspection for control flow. If any of these appear in an answer choice, it's almost certainly wrong.

2.7 Hands-On: Building Your First Agentic Loop

Let's build a complete, runnable agentic loop from scratch. This example implements a simple agent with two tools — a calculator and a unit converter — demonstrating every concept from sections 2.1 through 2.6 in working code.

Step 1: Define the Tools

import anthropic
import json

# ── Tool implementations ──
def calculator(expression: str) -> str:
    """Evaluate a mathematical expression safely."""
    try:
        # Restrict to safe math operations
        allowed = set("0123456789+-*/.() ")
        if not all(c in allowed for c in expression):
            return "Error: Expression contains invalid characters."
        result = eval(expression)  # Safe after character validation
        return str(round(result, 6))
    except Exception as e:
        return f"Calculation error: {e}"

def unit_converter(value: float, from_unit: str, to_unit: str) -> str:
    """Convert between common units."""
    conversions = {
        ("km", "miles"): 0.621371,
        ("miles", "km"): 1.60934,
        ("kg", "lbs"): 2.20462,
        ("lbs", "kg"): 0.453592,
        ("celsius", "fahrenheit"): lambda v: v * 9/5 + 32,
        ("fahrenheit", "celsius"): lambda v: (v - 32) * 5/9,
    }
    key = (from_unit.lower(), to_unit.lower())
    if key not in conversions:
        return f"Unsupported conversion: {from_unit} → {to_unit}"
    factor = conversions[key]
    if callable(factor):
        result = factor(value)
    else:
        result = value * factor
    return f"{value} {from_unit} = {round(result, 4)} {to_unit}"

# ── Tool registry: maps tool names to Python functions ──
TOOL_FUNCTIONS = {
    "calculator": calculator,
    "unit_converter": unit_converter,
}

Step 3: The Complete Agentic Loop

def run_agent(user_message: str, max_iterations: int = 10) -> str:
    """
    Run a complete agentic loop with calculator and unit converter tools.

    Args:
        user_message: The user's natural language request.
        max_iterations: Safety cap to prevent infinite loops.

    Returns:
        The agent's final text response.
    """
    client = anthropic.Anthropic()
    messages = [{"role": "user", "content": user_message}]
    iteration = 0

    print(f"🚀 Agent started | Task: {user_message}")
    print("─" * 60)

    while True:
        iteration += 1

        # ── Safety cap check ──
        if iteration > max_iterations:
            raise RuntimeError(
                f"Safety cap reached: {max_iterations} iterations"
            )

        print(f"\n📡 Iteration {iteration} — Calling Claude API...")

        # ── PHASE 1: REQUEST ──
        response = client.messages.create(
            model="claude-sonnet-4-20250514",
            max_tokens=1024,
            system="You are a helpful assistant with access to a calculator and unit converter. Use tools when needed to answer questions accurately.",
            tools=TOOLS,
            messages=messages,
        )

        print(f"   stop_reason: {response.stop_reason}")

        # ── PHASE 2: INSPECT ──
        if response.stop_reason == "end_turn":
            # ✅ Normal exit — extract final text
            final_text = "".join(
                block.text for block in response.content
                if hasattr(block, "text")
            )
            print(f"\n✅ Agent finished in {iteration} iteration(s)")
            print(f"📝 Response: {final_text}")
            return final_text

        elif response.stop_reason == "tool_use":
            # ── PHASE 3: EXECUTE ──
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    print(f"   🔧 Tool call: {block.name}({json.dumps(block.input)})")

                    # Look up and execute the tool function
                    tool_fn = TOOL_FUNCTIONS.get(block.name)
                    if tool_fn is None:
                        result = f"Error: Unknown tool '{block.name}'"
                        is_error = True
                    else:
                        try:
                            result = tool_fn(**block.input)
                            is_error = False
                        except Exception as e:
                            result = f"Error: {e}"
                            is_error = True

                    print(f"   📤 Result: {result}")

                    tool_result = {
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": str(result),
                    }
                    if is_error:
                        tool_result["is_error"] = True
                    tool_results.append(tool_result)

            # ── PHASE 4: RETURN ──
            messages.append({
                "role": "assistant",
                "content": response.content
            })
            messages.append({
                "role": "user",
                "content": tool_results
            })
            # Loop continues...

        elif response.stop_reason == "max_tokens":
            raise RuntimeError("Response truncated — increase max_tokens")

        else:
            raise ValueError(
                f"Unexpected stop_reason: {response.stop_reason}"
            )

Elimination Rules for Multiple Choice

Immediately eliminate any option that:
• Checks .text or .content for loop control decisions
• Uses role: "tool" or role: "system" for tool results

📝 Top 10 Likely Exam Questions

Q1 What are the four phases of an agentic loop, and what is the responsibility of each?
1. Request — Send the conversation history and tool definitions to the Claude API via messages.create().
2. Inspect — Check response.stop_reason to determine what the model wants: "end_turn" (done), "tool_use" (needs tools), or other values (handle/error).
3. Execute — If "tool_use", extract all tool_use blocks from response.content, execute each tool function, and collect results.
4. Return — Append the assistant message and a user message with tool_result blocks to the conversation history, then loop back to phase 1.
Q2 What is the only reliable signal for determining whether to continue or exit an agentic loop?
The response.stop_reason field. Specifically: "end_turn" means exit, "tool_use" means continue. Never use text content, content block types, or iteration counts as the primary exit signal.
Q3 What role should tool results be sent under, and why?
Tool results must use "role": "user". This is because the API models any non-model input as coming from the user side. Even though your infrastructure code generates the results, from the API's perspective, they are new information entering the conversation — which is always a user message. There is no "tool" or "system" role for this purpose.
Q4 What two messages must be appended to conversation history after executing tools?
First: An assistant message containing the full response.content (which includes the tool_use blocks Claude generated).
Second: A user message containing an array of tool_result blocks, one per tool call, each with a matching tool_use_id.
Both must be appended in this order. Skipping the assistant message or sending results as the assistant role will cause API errors or corrupt the model's context.
Q5 How should a tool execution error be communicated back to Claude?
Return the error as a normal tool_result block with "is_error": true and a descriptive error string in the "content" field. Do not skip the result, throw an exception in the loop, or silently retry. By receiving the error, Claude can autonomously decide to retry, try a different approach, or inform the user — enabling model-driven error recovery.
Q6 Why is checking response.content[0].text for "I'm done" an anti-pattern?
Three reasons: (1) The model's phrasing is non-deterministic — it might say "I'm done," "Here's your answer," or nothing at all. (2) content[0] may not have a .text attribute — it could be a tool_use block, causing an AttributeError. (3) The model might include "I'm done" in text while also requesting tool calls in the same response. stop_reason is the only authoritative signal for the model's intended control flow.
Q7 What is the difference between using an iteration cap as a safety net vs. as a primary exit condition?
Safety net (correct): The loop exits normally via stop_reason == "end_turn". The iteration cap exists only to prevent infinite loops — hitting it raises an error because it indicates abnormal behavior.
Primary exit (anti-pattern): The loop is structured as for i in range(N), where reaching N is the normal way the loop ends. This decouples termination from the model's actual state, making it impossible to distinguish "task complete" from "ran out of iterations."
Q8 When is a pre-configured decision tree preferable to model-driven decision-making?
Pre-configured trees are preferable when: (1) the task is safety-critical (financial transactions, compliance workflows); (2) the execution order must be deterministic and auditable; (3) you need to restrict which tools are available at each step for security; (4) the task is a well-defined pipeline with no ambiguity in the sequence. In all other cases — especially open-ended tasks, user-facing agents, and complex reasoning — model-driven is the recommended default.
Q9 If Claude requests three tool calls in a single response, how should the results be returned?
All three results must be returned in a single user message containing an array of three tool_result blocks. Each block's tool_use_id must match the id of the corresponding tool_use block. Sending them as three separate user messages violates the API's message alternation requirement (user → assistant → user). The order of results within the single message doesn't matter as long as IDs match.
Q10 What should your code do when it encounters an unexpected stop_reason value?
Raise an explicit error (e.g., ValueError) with the unexpected value. Do not silently continue the loop, ignore the response, or default to "end_turn" behavior. Unknown stop_reason values could indicate API changes, new features, or edge cases that your code isn't equipped to handle. Raising an error makes these cases visible immediately rather than causing silent data corruption or infinite loops.
