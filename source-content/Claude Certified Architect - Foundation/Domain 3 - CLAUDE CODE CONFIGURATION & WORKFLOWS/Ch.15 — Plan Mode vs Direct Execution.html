15.1 When to Use Plan Mode: Complex, Multi-File, Architectural Tasks
Concept

Plan Mode (toggled via Shift+Tab in Claude Code) instructs Claude to analyze, reason, and propose a structured plan before executing any file modifications. In Plan Mode, Claude reads the codebase, identifies affected files, maps dependencies, and outputs a step-by-step implementation proposal — but does not write or edit any files until the user explicitly approves and switches to execution. This is the "think before you act" paradigm for agentic coding.

Plan Mode is designed for situations where the blast radius of a change is large, the interactions between components are non-obvious, or the developer needs confidence that the AI understands the full scope before committing.

Key Principles
  • Multi-file awareness: Plan Mode forces Claude to map out all files that need to change — interfaces, implementations, tests, imports, configs — before touching any single file.
  • Dependency chain analysis: Claude traces call graphs, import trees, and type hierarchies to identify cascading impacts. A rename in a base class ripples through dozens of consumers.
  • Architectural coherence: Plans maintain consistency across the change set. Without planning, sequential edits can create intermediate broken states that are hard to diagnose.
  • Human-in-the-loop gate: The plan is presented to the developer for review. The user can refine, reject, or redirect before any code is written — reducing wasted work and wrong-direction edits.
  • Higher token cost, lower error cost: Plan Mode consumes more tokens (analysis + plan text + eventual execution) but drastically reduces the risk of producing an inconsistent, half-finished change set.
  • Explicit scope declaration: The plan enumerates exactly what will change and what won't, making the change auditable before it happens.

Real-World Example

Scenario: Migrating a REST API from Express to Fastify

A developer asks Claude to migrate a Node.js backend from Express to Fastify. The project has 40+ route handlers, custom middleware, error handlers, and integration tests. In PLAN mode, Claude:

  1. Reads the Express app entry point, middleware stack, and route files
  2. Maps the middleware dependency graph (auth → rate-limit → logging → routes)
  3. Identifies Fastify equivalents for each Express pattern (middleware → hooks/plugins, req.body → schema validation)
  4. Produces a 12-step plan: install Fastify deps → convert app bootstrap → migrate middleware → convert routes (grouped by domain) → update tests → update Docker config
  5. Flags risk: "Express res.locals pattern used in 8 handlers — Fastify uses request.decorators; requires manual verification"

The developer reviews, adjusts step ordering, then approves. Only then does Claude begin writing code — in the planned sequence.

Tips & Tricks
  • Memory aid — "Plan = Map the Minefield": Think of Plan Mode as sending a reconnaissance drone before deploying troops. You want the full terrain map (dependency graph, interface contracts, test coverage) before any boots hit the ground.
  • Toggle shortcut: In Claude Code, Shift+Tab toggles between Plan and Act modes. The mode indicator appears in the input bar. If you forget which mode you're in, check the UI label.
  • Plan quality correlates with context quality: Plans are only as good as the codebase context Claude can access. Ensure CLAUDE.md, architecture docs, and relevant files are accessible.
Exam Strategy — 15.1

Trigger words in questions: "multi-file", "refactor", "architecture", "cascading changes", "unknown codebase", "migration", "restructure", "large-scale"

→ These almost always signal: choose Plan Mode.

Common distractor: "Plan Mode is always the safest choice." This is false — Plan Mode has higher token cost, latency overhead, and is overkill for trivial changes. The exam tests whether you know when Plan Mode is appropriate, not whether you default to it.

Key distinction: Plan Mode = read-only analysis → user approval → execution. Direct Execution = immediate tool use. If a question describes a workflow where files are edited before a plan is shown, that's Direct Execution regardless of what the question claims.

15.2 When to Use Direct Execution: Simple, Well-Scoped Changes
Concept

Direct Execution (also called "Act Mode") is Claude's default operating mode where it immediately reads, writes, and modifies files in response to a request without producing an intermediate plan. Claude uses tools — Read, Write, Edit, Bash — as soon as it determines the appropriate action. This is optimal for tasks where the scope is clear, the risk is low, and the overhead of a formal plan would slow down an otherwise fast operation.

Direct Execution trusts that the task is well-understood and the changes are either trivially correct, easily reversible (via git), or confined to a small surface area.

Key Principles
  • Low-ceremony, high-speed: No planning phase means faster turnaround. Ideal for the "just do it" class of tasks — bug fixes, typo corrections, adding an import, writing a utility function.
  • Single-file or tightly scoped: Best when the change affects one file, or a small cluster of files with no ambiguous cross-dependencies.
  • Git as safety net: Direct Execution relies on version control as the undo mechanism. Every edit is recoverable via git diff, git stash, or git checkout.
  • Lower token cost: No separate planning pass means fewer total tokens consumed. For simple tasks, Plan Mode can spend more tokens on the plan than the actual edit.
  • Iterative correction: If Claude's first attempt isn't quite right, the developer can give feedback and Claude iterates — still faster than a full plan-approve-execute cycle for simple fixes.
  • Appropriate trust level: Use Direct Execution when you know the answer space is small. "Add a --verbose flag to the CLI" has a narrow, predictable implementation.
Signal Direct Execution? Rationale
Fix a typo in a docstring ✅ Yes Single-line, zero-risk, no dependencies
Add an import statement ✅ Yes Single-file change, well-defined action
Write a new unit test for an existing function ✅ Yes Additive (new file), doesn't modify existing code
Rename a variable used across 15 files ❌ Use Plan Multi-file, cascading — needs dependency mapping
Add a CLI flag with 2-line implementation ✅ Yes Small scope, predictable outcome
Restructure module hierarchy ❌ Use Plan Architectural change, import rewiring needed
Real-World Example

Scenario: Adding a Validation Check

A developer says: "Add input validation to the createUser function — check that email is non-empty and matches a basic regex."

This is a textbook DIRECT execution task:

  • One function, one file
  • Clear acceptance criteria (non-empty + regex)
  • No cross-file dependencies — the function's callers don't change
  • Easily tested: run the existing test suite

Claude reads the file, adds the validation logic at the function entry point, and runs the tests. Total time: seconds. A planning phase would add latency with zero safety benefit.

Tips & Tricks
  • Memory aid — "SWAT": Direct Execution is for Single-file, Well-scoped, Additive or Trivial tasks. If the task passes the SWAT test, go direct.
  • Watch for scope creep: A task that starts simple can reveal unexpected complexity mid-execution. If Claude discovers during a Direct Execution pass that 8 more files need changes, it should signal this — and the developer should consider switching to Plan Mode.
  • "Additive" is generally safe: Creating a new file (test, utility, config) is almost always safe for Direct Execution because it doesn't modify existing behavior.
Exam Strategy — 15.2

Trigger words: "simple", "one file", "quick fix", "add a test", "typo", "straightforward", "well-defined"

→ These signal: choose Direct Execution.

Trap question pattern: "A developer needs to rename a single utility function used in one file. Which mode?" — Answer: Direct Execution. The key is "used in one file." If the question said "used across 12 files," it would be Plan Mode. Read the scope carefully.

Anti-distractor: The answer "always use Plan Mode for safety" is never correct. The exam rewards nuanced judgment, not risk aversion.

15.3 Safe Codebase Exploration Before Committing to Changes
Concept

Safe codebase exploration is the practice of performing read-only investigation of a project's structure, conventions, dependencies, and patterns before making any modifications. This is a pre-requisite discipline — not a mode per se, but a behavioral pattern — where Claude (or the developer directing Claude) invests upfront time in understanding the terrain. The principle: never commit to changes in a codebase you don't yet understand.

In Claude Code, exploration uses read-only tools: Read (file contents), Bash (for grep, find, git log), ListFiles, and search commands — none of which modify the filesystem.

Key Principles
  • Read before write — always: Even in Direct Execution mode, Claude should read the target file and understand its context before applying edits. Blind writes cause regressions.
  • Project structure first: Start with high-level exploration: ls, tree, README, package.json/pyproject.toml, architecture docs. Understand the project's shape before diving into individual files.
  • Convention detection: Identify naming patterns, error-handling conventions, import styles, test structure. Changes should conform to the project's existing patterns, not the AI's defaults.
  • Dependency tracing: Use grep and import analysis to trace who calls the function/class you're about to change. This determines the true blast radius.
  • CLAUDE.md and config files: If the project has a CLAUDE.md, .clinerules, or similar configuration, reading it first provides critical context about project conventions, forbidden patterns, and preferred approaches.
  • Exploration is cheap; mistakes are expensive: Reading 10 files costs tokens but no risk. Editing 1 file blindly can break the build, fail tests, and require debugging — costing far more tokens and time.

Real-World Example

Scenario: Fixing a Bug in an Unfamiliar Codebase

A developer joins a new project and asks Claude: "Fix the null pointer exception in processOrder()." Instead of jumping to the fix, Claude explores first:

  1. Reads the file containing processOrder() — finds it calls getCustomer() which can return null
  2. Greps for all callers of processOrder() — discovers it's called from 3 route handlers and 1 background job
  3. Reads the test file — finds no test for the null case
  4. Checks getCustomer() — confirms it returns null when customer is deleted
  5. Now, with full context, applies the fix (null check + appropriate error response) and adds the missing test

Without exploration, Claude might have added a bare null check without understanding why the null occurs — producing a band-aid rather than a correct fix.

Tips & Tricks
  • Memory aid — "Scout then Strike": Military operations don't begin without reconnaissance. Coding operations shouldn't either. Scout (explore) before strike (edit).
  • Exploration has a stopping rule: You don't need to read the entire codebase. Explore until you can confidently answer: "What will change, what won't, and what might break?"
  • git log --oneline -10 <file> is an underused exploration tool — it reveals who last modified the file and why, giving valuable contextual clues.
Exam Strategy — 15.3

Trigger words: "unfamiliar codebase", "before making changes", "investigate first", "understand the structure", "read-only"

→ These signal: exploration phase required before any mode selection.

Key exam insight: Exploration is not a separate "mode" — it's a best practice that can occur within Plan Mode, before Direct Execution, or via a dedicated Explore Subagent (see 15.4). If a question asks "what should Claude do first in an unknown codebase?" — the answer is always explore, never start editing.

Watch for: Questions where exploration reveals that a "simple" task is actually complex. The correct answer is to escalate to Plan Mode — not to forge ahead with Direct Execution.

15.4 The Explore Subagent for Isolating Verbose Discovery
Concept

The Explore Subagent is a child agent spawned by the main Claude session specifically for read-only codebase investigation. It operates with restricted permissions (no file writes, no destructive commands) and is designed to perform verbose, wide-ranging exploration — reading many files, running search commands, analyzing directory structures — without polluting the main conversation's context window. The subagent returns a concise summary of its findings, keeping the parent context lean and focused.

This is particularly valuable for large codebases where exploration might involve reading 30+ files. Doing that in the main session would consume the context window with file contents that are only needed for analysis, not for the final answer.

Key Principles
  • Context window preservation: The #1 benefit. The main conversation retains its context budget for the actual task — planning, coding, iterating — without being filled with exploration output.
  • Read-only isolation: The Explore subagent cannot modify files, ensuring that exploration is truly safe. It can read, search, list, and run non-destructive commands.
  • Summarized output: The subagent returns a structured summary — key findings, relevant patterns, dependency maps — not raw file dumps. This is curated intelligence, not raw data.
  • Spawned on demand: Not every task needs an Explore subagent. It's most valuable when the exploration scope is large or when the main context is already partially consumed.
  • Parallelizable: In advanced workflows, multiple subagents can explore different parts of the codebase simultaneously (e.g., one explores the backend, another the frontend).
  • Explicit boundary: The subagent completes and returns before the main agent takes action. There's a clean handoff: explore → summarize → return → plan/execute.

Real-World Example

Scenario: Understanding a Monorepo Before Refactoring

A developer asks: "Refactor the authentication module to support OAuth2 in addition to JWT." The project is a monorepo with 200+ files across api/, web/, shared/, and infra/.

The main agent spawns an EXPLORE subagent with the directive: "Map the authentication module: find all auth-related files, trace the middleware chain, identify where JWT tokens are issued/validated, list all consumers of the auth module, and check for existing OAuth2 references."

The subagent reads 35 files, runs grep -r "jwt\|auth\|token", traces imports, and returns:

  • Auth module files: 6 core files + 3 middleware + 2 utility
  • JWT is issued in auth/token-service.ts, validated in auth/middleware.ts
  • 14 route handlers depend on the auth middleware
  • No existing OAuth2 code — greenfield addition
  • Test coverage: 72% on auth module

The main agent receives this summary (consuming ~500 tokens of context vs ~15,000 if it had read all files directly) and proceeds to create a Plan.

Tips & Tricks
  • Memory aid — "Send a Scout, Keep Your Map Clean": The Explore subagent is the scout. It goes deep into enemy territory (the codebase), gathers intelligence, and reports back concisely — so the general (main agent) can make decisions with a clean operational picture.
  • When to spawn vs. explore in-session: If you need to read ≤5 files, just do it in the main session. If exploration will touch 10+ files or involve extensive grep/search, spawn a subagent.
  • Subagent directives matter: Give the Explore subagent a specific investigation mandate, not "look around." A focused question yields a focused answer.
Exam Strategy — 15.4

Trigger words: "large codebase", "context window", "verbose output", "read-only investigation", "isolate discovery", "monorepo"

→ These signal: Explore Subagent is the best-fit answer.

Key exam distinction: Explore Subagent ≠ Plan Mode. Plan Mode is the main agent thinking before acting. Explore Subagent is a separate agent doing read-only investigation. They can be used together (explore → plan → execute) but are different mechanisms.

Trap: "Why not just use Plan Mode for exploration?" — Plan Mode includes exploration as a step, but if the exploration is verbose (reading many files), it fills the main context window. The subagent specifically solves the context pressure problem.

15.5 Combining Plan Mode Investigation with Direct Execution
Concept

Combined Mode is the pragmatic workflow where developers use Plan Mode for the investigation and design phase, then switch to Direct Execution for the implementation phase. This is not a formal "mode" — it's a workflow pattern that leverages both approaches in sequence. The developer toggles between Shift+Tab states: plan the complex architecture first, then execute changes step-by-step with Direct Execution for each well-defined sub-task.

This hybrid approach captures the safety benefits of planning (scope analysis, dependency mapping, change ordering) while maintaining the speed and iterative flexibility of Direct Execution for the actual coding.

Key Principles
  • Phase separation: Investigation/planning and execution are distinct phases. Mixing them (editing mid-plan) creates inconsistency. Complete the plan, review it, then execute.
  • Plan decomposes into atomic tasks: A good plan breaks the work into steps small enough that each step is suitable for Direct Execution. Each step should be self-contained and verifiable.
  • Checkpoint after each step: After executing each planned step, verify it works (run tests, check compilation) before proceeding. This prevents error cascade across steps.
  • Plan is a living document: If execution of step 3 reveals that step 5 needs adjustment, update the plan. Plans are guidance, not contracts — they should adapt to reality.
  • Mode switching is low-cost: Toggling Shift+Tab between Plan and Act is instant. There's no penalty for switching modes mid-task — it's the expected workflow for complex work.
  • Optimal token economics: Plan Mode tokens are spent once (on analysis). Each Direct Execution step is small and focused, avoiding the token overhead of re-analyzing the entire project for each edit.

Real-World Example

Scenario: Adding a Caching Layer to a Web Application

Task: "Add Redis caching to the product catalog API endpoints."

Phase 1 — Plan Mode:

  1. Claude explores: identifies 4 API endpoints, the data access layer, existing response shapes
  2. Produces a plan: (a) Add Redis client config, (b) Create cache utility module, (c) Add cache middleware to product routes, (d) Add cache invalidation on product updates, (e) Update tests, (f) Add Redis to Docker Compose
  3. Developer reviews — adjusts TTL strategy, approves

Phase 2 — Direct Execution (per step):

  1. Step (a): Claude creates config/redis.ts → developer runs tsc → passes ✅
  2. Step (b): Claude creates utils/cache.ts with get/set/invalidate → passes ✅
  3. Step (c): Claude adds caching middleware to routes → runs tests → 1 failure (cache key collision) → Claude fixes → passes ✅
  4. Steps (d)–(f): Executed in sequence, each verified

The combined approach took less total time than pure Plan Mode (no waiting for a monolithic execution) and was safer than pure Direct Execution (no risk of forgetting cache invalidation).

Tips & Tricks
  • Memory aid — "Architect then Bricklayer": Plan Mode is the architect drawing blueprints. Direct Execution is the bricklayer following them. You need both roles, but at different times.
  • Feedback loop: Each executed step provides new information. Use it. If step 3 reveals that the planned approach for step 5 won't work, toggle back to Plan and revise. This adaptability is the superpower of the combined approach.
  • Commit between steps: Use git commit between planned steps. This gives you atomic rollback points — if step 4 goes wrong, you can revert to the state after step 3 without losing earlier work.
Exam Strategy — 15.5

Trigger words: "phased approach", "plan then execute", "step-by-step implementation", "iterative with oversight", "complex task broken into stages"

→ These signal: Combined Plan + Direct Execution workflow.

Key exam insight: The exam may present scenarios where neither pure Plan nor pure Direct is the best answer. The combined approach is often the "best practice" answer for medium-to-high complexity tasks. Look for answer options that describe a two-phase workflow.

Trap: "Combined mode is slower than Direct Execution." — True for simple tasks (overhead of planning), but false for complex tasks where unplanned Direct Execution leads to rework that costs more time than the planning phase saved.

15.6 Hands-On: Choosing the Right Execution Mode
Concept

Choosing the right execution mode is a judgment call that depends on multiple interacting factors: task complexity, codebase familiarity, risk tolerance, available context budget, and reversibility. This section synthesizes the heuristics from 15.1–15.5 into an actionable decision framework. The goal is not to memorize rules but to develop the architectural intuition to rapidly assess a task and select the optimal approach.

An experienced architect's hallmark is not always choosing Plan Mode for safety — it's choosing the right mode for the situation, accepting appropriate risk when the payoff is speed, and demanding rigor when the cost of errors is high.

Decision Factors
  • File count: 1 file → Direct. 2–4 related files → Direct (with caution) or Plan. 5+ files → Plan.
  • Familiarity: You know the codebase well → more Direct. New codebase → Explore + Plan.
  • Reversibility: Git-committed, test-covered code → more Direct (easy rollback). Database migrations, config changes, deployed infra → Plan (hard to undo).
  • Blast radius: Change affects only caller → Direct. Change affects interface consumed by many → Plan.
  • Context budget: Context window nearly full → Explore Subagent for investigation. Plenty of context → can explore in-session.
  • Time pressure: Urgent hotfix for a known bug → Direct. Strategic refactor with no deadline → Plan.
Factor → Direct Execution → Plan Mode → Explore Subagent

Codebase familiarity High Low–Medium Very Low
Task complexity Low (well-defined) High (architectural) Unknown (needs discovery)
Risk of error Low (easily reversible) High (cascading effects) Unknown
Context budget Any Sufficient Constrained (offloads to child)
Token cost Lowest Highest Medium (separate context)

Tips & Tricks
  • The "5-second rule": If you can describe the complete change in one sentence and it touches ≤2 files → Direct. If you need a paragraph to explain it → Plan.
  • When in doubt, start with exploration: You can always escalate from exploration to planning to execution. You can't easily de-escalate from a botched Direct Execution.
  • Mode selection is itself a skill: The exam tests your ability to choose, not just to know the definitions. Practice by mentally mode-selecting for every coding task you encounter in your daily work.
Exam Strategy — 15.6

This subtopic is the synthesis. Questions from 15.6 will present a scenario and ask you to choose the best mode — testing whether you can apply the heuristics from 15.1–15.5 in concert.

Strategy: Read the scenario for these signals: (1) How many files? (2) How familiar is the codebase? (3) What's the blast radius? (4) Is it reversible? Score each factor, then select the mode that matches the majority signal.

Multi-step answer pattern: Some questions have answer options like "Explore, then Plan, then Execute." These are often correct for complex scenarios. Don't dismiss multi-step options as "too complicated" — they reflect real professional practice.

Ultimate trap: "Which mode is best?" — There is no universally "best" mode. The correct answer is always the one that matches the task's characteristics. Reject any answer that claims one mode is universally superior.

Q1 — Scenario
A developer asks Claude Code to refactor a monolithic Express application into separate microservices. The codebase has 120 files across 8 domains. Which execution approach is most appropriate?
A) Direct Execution — start splitting files immediately
B) Plan Mode — analyze dependencies, propose service boundaries, then execute after approval
C) Explore Subagent to map the codebase, then Plan Mode for the migration strategy, then Direct Execution per step ✅
D) Direct Execution with frequent git commits for safety
Answer: C. This is a large, architectural task in a complex codebase. The three-phase approach (Explore → Plan → Execute) is the gold standard for this class of problem. Option B is incomplete — it skips the exploration phase, which is critical for a 120-file monolith where the main agent's context would be overwhelmed. Option D underestimates the architectural complexity — git commits don't prevent wrong-direction work.
Q2 — Scenario
A developer asks Claude to add a createdAt timestamp field to the User model in a Django application. The model is used in 3 views and has 2 serializers. Which mode is best?
A) Explore Subagent — need to understand the full codebase first
B) Plan Mode — the change cascades through model, migration, views, serializers, and tests ✅
C) Direct Execution — it's just adding a field
D) Combined approach — plan the model change, direct-execute each step
Answer: B. Although "add a field" sounds simple, in Django it triggers a migration, requires serializer updates, may affect view logic (e.g., filtering/ordering), and needs test updates. That's 5+ files with dependency ordering (migration must be generated after model change). Plan Mode ensures all affected files are identified and changes are ordered correctly. Option C is a trap — it underestimates the cascade. Option D is also reasonable but B is the most accurate single-mode answer for this scope.
Q3 — Scenario
A developer asks Claude to rename a single utility function formatDate() that is used only within the file where it's defined. No other file imports it. Which execution mode is most appropriate?
A) Plan Mode — to map all dependencies first
B) Direct Execution — task is simple and well-scoped ✅
C) Explore Subagent — to isolate verbose output
D) Combined Mode — to ensure safety
Answer: B. Renaming a function used only within one file is a textbook Direct Execution task: single file, zero dependencies, trivially reversible. Plan Mode (A) adds unnecessary overhead. The Explore Subagent (C) is for large investigation tasks, not single-file edits. Combined Mode (D) is overkill.
Q4 — Concept
What is the primary benefit of using an Explore Subagent instead of exploring directly in the main Claude session?
A) The Explore Subagent has write access that the main session lacks
B) The Explore Subagent is faster at reading files
C) The Explore Subagent preserves the main session's context window by keeping verbose exploration output in a separate context ✅
D) The Explore Subagent can access external APIs that the main session cannot
Answer: C. The Explore Subagent's defining advantage is context window preservation. Verbose exploration (reading 30+ files, running multiple search commands) fills the main context, leaving less room for planning and execution. The subagent absorbs this cost and returns only a concise summary. Option A is the opposite of truth — the subagent has restricted (read-only) access. Options B and D are fabricated benefits.
Q5 — Best Practice
During Direct Execution, Claude discovers that a "simple" bug fix actually requires changes to 8 files due to a shared interface. What should happen next?
A) Continue with Direct Execution — the changes are already started
B) Abort and ask the user to re-state the task more clearly
C) Pause, communicate the discovered complexity to the user, and suggest switching to Plan Mode ✅
D) Complete the current file's changes, then use Plan Mode for the remaining 7
Answer: C. Discovering unexpected complexity during Direct Execution is the classic escalation trigger. The correct response is to stop, communicate, and escalate to Plan Mode. Option A is dangerous — continuing without a plan across 8 files risks inconsistency. Option D creates a hybrid mess — some files changed ad-hoc, others planned. Option B is too extreme — the task itself is fine; only the approach needs adjustment.
Watch Out For — Common Misconceptions
  • "Plan Mode is always safer than Direct Execution" — False. Plan Mode is safer for complex tasks, but it has higher token cost and latency. For simple tasks, it adds unnecessary overhead without improving safety.
  • "Direct Execution means no exploration" — False. Claude should always read the target file before editing, even in Direct Execution. The mode determines whether a formal plan is produced, not whether reading occurs.
  • "Explore Subagent = Plan Mode" — False. They are different mechanisms. Plan Mode is the main agent analyzing and proposing changes. The Explore Subagent is a separate child agent performing read-only investigation. They can be used together.
  • "You should always use the Combined approach for maximum safety" — False. The Combined approach is optimal for medium-to-high complexity tasks. For trivial tasks, it's unnecessarily slow.
  • "Plan Mode prevents all errors" — False. Plans can be wrong. The value is the human review gate, not the plan's infallibility. A bad plan that gets approved still produces bad code.
  • "Explore Subagent has write access" — False. The Explore Subagent is explicitly read-only. This is a safety feature, not a limitation — it guarantees exploration can't accidentally modify the codebase.
  • "Token cost doesn't matter in mode selection" — False. In real-world usage, token cost is a practical constraint. Plan Mode on a trivial task wastes budget that could be spent on actual coding.

Chapter 15 — 20-Point Cheat Sheet

  1. Plan Mode = analyze → propose → user approves → execute. No files modified until approval.
  2. Direct Execution = immediate read/write. Default mode. Best for simple, well-scoped tasks.
  3. Explore Subagent = read-only child agent for verbose investigation. Preserves main context window.
  4. Toggle: Shift+Tab switches between Plan and Act (Direct) in Claude Code.
  5. SWAT rule: Single-file, Well-scoped, Additive, Trivial → Direct Execution.
  6. Multi-file + cascading dependencies → Plan Mode.
  7. Unfamiliar codebase → Explore first, always. Then decide Plan vs. Direct.
  8. 10+ files to read during investigation → use Explore Subagent to avoid context bloat.
  9. Combined approach: Plan the strategy → Execute each step with Direct Execution → Verify between steps.
  10. Git is the safety net for Direct Execution. Commit between steps in Combined workflows.
  11. Plans should decompose into atomic, verifiable steps — each suitable for Direct Execution.
  12. Plans are living documents — update them when execution reveals new information.
  13. Exploration has a stopping rule: stop when you can answer "what will change, what won't, what might break."
  14. Additive changes (new files) are almost always safe for Direct Execution.
  15. Token cost order: Direct (lowest) < Explore Subagent (medium) < Plan Mode (highest).
  16. Latency order: Direct (fastest) < Explore (medium) < Plan (slowest, includes approval gate).
  17. Risk mitigation order: Plan (safest for complex) > Combined > Direct > Explore (N/A, read-only).
  18. Escalation trigger: If Direct Execution reveals unexpected complexity → pause → switch to Plan.
  19. No mode is universally "best" — the correct mode depends on the task's specific characteristics.
  20. The exam tests judgment, not defaults. Read every scenario's signals: file count, blast radius, familiarity, reversibility.
