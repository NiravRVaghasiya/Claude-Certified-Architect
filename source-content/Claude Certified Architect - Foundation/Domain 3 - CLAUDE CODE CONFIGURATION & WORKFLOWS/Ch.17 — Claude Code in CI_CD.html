17.1

The -p / --print Flag for Non-Interactive Mode

▼

Concept Overview

The --print flag (shorthand -p) switches Claude Code from its interactive REPL into a single-shot batch invocation: it reads a prompt, runs to completion, prints the response to stdout, and exits. This is the foundational mechanism for all CI/CD, scripted, and automated usage of Claude Code — without it, headless execution is impossible.

Think of -p as the difference between a chat window (interactive) and a Unix command-line tool (batch). With -p, Claude Code behaves like grep or jq — it takes input, produces output, and exits with a status code.

Key Mechanics

  • Syntax: claude -p "your prompt here"
  • Exit codes: 0 on success, non-zero on failure — enabling if/else branching in shell scripts
  • Stdin piping: cat file.py | claude -p "review this" — reads stdin up to a 10 MB cap
  • Stdout output: Result goes to stdout; errors go to stderr
  • No TTY needed: Fully headless — no terminal, no user interaction
  • Combinable flags: Works with --output-format, --allowedTools, --max-turns, --model, --continue, --resume
  • Incompatible flags: Rejects --bg; rejects --cloud with a task description
  • --bare mode: Skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md — recommended for CI for deterministic, fast startup

Visual Aid

┌─────────────────────────────────────────────────────────────────┐ │ CI Runner Environment (no TTY available) │ │ │ │ ┌───────────┐ ┌────────────────┐ ┌──────────────────┐ │ │ │ Trigger │───▶│ claude -p │───▶│ stdout → parse │ │ │ │ (PR open, │ │ "review this" │ │ exit(0) → pass │ │ │ │ push, │ │ --output json │ │ exit(N) → fail │ │ │ │ cron) │ │ --max-turns 10 │ │ │ │ │ └───────────┘ └────────────────┘ └──────────────────┘ │ │ │ │ │ ┌─────┴─────┐ │ │ │ stdin pipe │ │ │ │ (optional) │ │ │ │ ≤ 10 MB │ │ │ └───────────┘ │ └─────────────────────────────────────────────────────────────────┘ Figure 17.1 — The -p flag turns Claude Code into a batch CLI tool

⚠️ Exam Tips & Tricks

Distractor Alert: Exams may offer --silent, --batch, --headless, or --non-interactive as alternatives. None of these exist. Only -p / --print enables headless mode.

Key fact: -p is required for any CI/CD usage. Without it, Claude Code opens an interactive REPL and hangs waiting for input.

Tricky scenario: "What happens if you run claude without -p in a CI runner?" → It hangs or times out because there's no TTY for the REPL.

❌ Common Pitfalls

Pitfall 1: Assuming Claude Code works interactively in CI — it will hang indefinitely waiting for keyboard input.

Pitfall 2: Feeding prompts that ask follow-up questions ("let me know if you want…") — there's nobody to answer. Write self-contained, complete prompts.

Pitfall 3: Piping more than 10 MB via stdin — Claude Code rejects it with an error, not a silent truncation.

Pitfall 4: Forgetting --bare in CI — without it, the session loads hooks, plugins, and CLAUDE.md from the working directory, which may pull in unintended configuration.

⚡ Quick-Recall Summary

  • -p = --print = non-interactive, headless, stdout output
  • Required for all CI/CD integrations — no exceptions
  • Supports stdin piping (≤ 10 MB cap) and stdout redirection
  • Returns standard exit codes (0 = success, non-zero = failure)
  • --bare = skip auto-discovery → faster, deterministic startup for CI
17.2

Output Formats & Structured Output

▼

Concept Overview

The --output-format flag controls the shape of what -p prints. It determines whether the output is human-readable prose, a single structured JSON object, or a real-time stream of newline-delimited JSON events. Choosing the right format is critical for building reliable pipelines — text is for humans; JSON is for machines.

Key Mechanics — The Three Formats

ValueShapeBest For
text (default) Plain text — what you'd read in a terminal Human-readable logs; no machine decision depends on it
json One structured JSON object with result, session_id, total_cost_usd, and metadata Pipeline parses the outcome after the run finishes
stream-json Newline-delimited JSON (JSONL) — one object per event, emitted in real-time Live UIs, streaming logs, real-time event processing

JSON Output Structure

bash# Get a single JSON object with the result
claude -p "Summarize this project" --output-format json

# Extract specific fields with jq
claude -p "Review auth.py" --output-format json | jq -r '.result'
claude -p "Review auth.py" --output-format json | jq -r '.session_id'
claude -p "Review auth.py" --output-format json | jq -r '.total_cost_usd'

Stream-JSON Event Types

jsonl# system/init — first event: session metadata
{"type":"system","subtype":"init","session_id":"...","model":"...","tools":["Read","Grep"]}

# assistant — model reasoning / tool calls
{"type":"assistant","message":{"content":[{"type":"text","text":"Reviewing the diff..."}]}}

# system/api_retry — emitted before retrying a transient API error
{"type":"system","subtype":"api_retry","attempt":1,"max_retries":3,"error":"rate_limit"}

# result — terminal event with final outcome
{"type":"result","result":"No regressions found.","session_id":"..."}

Stream-JSON Requires Additional Flags

  • --verbose — Required to emit the full turn-by-turn stream
  • --include-partial-messages — Optional; adds token-level deltas for real-time display
bash# Full streaming with token-level deltas
claude -p "Explain recursion" \
  --output-format stream-json \
  --verbose \
  --include-partial-messages

Visual Aid — Parsing Pipeline

┌──────────────────┐ claude -p │ --output-format │ "review..." ──▶ │ json │ ──▶ Single JSON Object │ stream-json │ ──▶ JSONL Stream (line-by-line) │ text │ ──▶ Plain text string └──────────────────┘ │ ┌─────┴─────┐ │ jq parse │ ←── Use jq, not grep/sed! └─────┬─────┘ │ ┌────────┴────────┐ │ .result │ → final text │ .session_id │ → for --resume │ .total_cost_usd │ → cost tracking │ .structured_output │ → when --json-schema used └─────────────────┘ Figure 17.2 — Output format selection and JSON field extraction
⚠️ Exam Tips & Tricks

Common question pattern: "Which --output-format should you use when building an automated CI pipeline that needs to branch on the result?" → json (single structured object, easy to parse).

Distractor: stream-json is NOT required for basic CI — it's for real-time streaming UIs. Most CI jobs should use json.

Key field: The final text lives in .result — not .text, not .output, not .response.

Cost tracking: total_cost_usd is an estimate and may differ from your actual bill. The exam may test this distinction.

❌ Common Pitfalls

Fatal mistake: Parsing text output with grep/sed to extract structured data. The wording changes between runs. Always use --output-format json + jq.

Forgotten flag: Using --output-format stream-json without --verbose — you'll get a minimal stream without full turn-by-turn events.

⚡ Quick-Recall Summary

  • text = default, human-readable — never parse programmatically
  • json = single JSON object — use for CI pipeline decisions
  • stream-json = JSONL real-time stream — needs --verbose
  • Key JSON fields: .result, .session_id, .total_cost_usd
  • Always parse with jq, never with grep/sed
17.3

CI/CD Pipeline Integration

▼

Concept Overview

Claude Code integrates into any CI/CD system that can execute a shell command. For GitHub specifically, there's an official action (anthropics/claude-code-action@v1). For all other systems (GitLab CI, Jenkins, CircleCI, etc.), you run claude -p directly. The pattern is always: trigger → authenticate → guardrailed claude -p → parse output → act on result.

Key Mechanics

Universal CI Pattern (Any System)

  1. Install Claude Code: npm install -g @anthropic-ai/claude-code
  2. Set ANTHROPIC_API_KEY as a secret environment variable
  3. Run claude -p with guardrail flags
  4. Parse the structured JSON output

GitHub Actions — Official Action

yamlname: PR Review
on:
  pull_request:
    types: [opened, synchronize]
permissions:
  contents: read
  pull-requests: write

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Review this pull request for correctness and security.
            Comment on specific lines. Do not modify files.
          claude_args: |
            --max-turns 12
            --model sonnet
            --allowedTools "Read,Grep,Glob"

GitHub Actions — Direct CLI

yaml- name: Install Claude Code
  run: npm install -g @anthropic-ai/claude-code

- name: Review PR diff
  env:
    ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
  run: |
    git diff origin/main...HEAD | claude -p \
      "Review this PR diff. Flag bugs and security issues." \
      --max-turns 3 \
      --output-format json > review.json

GitLab CI

yamlclaude_review:
  image: node:22
  variables:
    ANTHROPIC_API_KEY: $ANTHROPIC_API_KEY
  script:
    - npm install -g @anthropic-ai/claude-code
    - |
      claude -p "Review the changes in this MR." \
        --max-turns 10 --model sonnet \
        --allowedTools "Read,Grep,Glob" \
        --output-format json > review.json
    - jq -r '.result' review.json
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

Jenkins

groovypipeline {
  agent any
  environment { ANTHROPIC_API_KEY = credentials('anthropic-api-key') }
  stages {
    stage('Review') {
      when { changeRequest() }
      steps {
        sh '''
          npm install -g @anthropic-ai/claude-code
          claude -p "Review this change for bugs." \
            --max-turns 10 --model sonnet \
            --allowedTools "Read,Grep,Glob" \
            --output-format json > review.json
        '''
        sh 'jq -r .result review.json'
      }
    }
  }
}

Authentication Methods for CI

ProviderEnvironment VariablesBest Practice

Amazon Bedrock CLAUDE_CODE_USE_BEDROCK=1, AWS_REGION, AWS credentials Use OIDC role assumption — no long-lived keys

⚠️ Exam Tips & Tricks

Official Action name: anthropics/claude-code-action@v1 — exams may test the exact name. Note: anthropics (with an 's'), not anthropic.

Scenario question: "Which authentication method avoids storing long-lived secrets?" → OIDC (Bedrock) or Workload Identity Federation (Vertex AI).

Cross-CI universality: The pattern is identical everywhere — only the YAML/Groovy dialect changes. The exam may present an unfamiliar CI system and ask if Claude Code works there → Yes, any system that runs shell commands works.

❌ Common Pitfalls

Never put the API key directly in the workflow YAML. Always use the CI's secret store.

Never let secrets end up in the prompt, transcript, or committed diff.

Pick exactly one credential path — mixing (e.g., ANTHROPIC_API_KEY + OAuth) invites confusing precedence bugs.

⚡ Quick-Recall Summary

  • Official GitHub Action: anthropics/claude-code-action@v1
  • Universal pattern: install → auth → claude -p → parse → act
  • Three auth paths: API key, Bedrock (OIDC), Vertex AI (WIF)
  • Prefer OIDC/WIF over stored keys to avoid secret leakage
  • Works on any CI system — GitHub, GitLab, Jenkins, CircleCI, etc.
17.4

Session Management & Isolation

▼

Concept Overview

A single -p run is stateless from the caller's perspective, but Claude Code can continue prior conversations for multi-step automated workflows that share context. Session management controls whether each run is isolated or part of a conversation chain, and how to safely handle concurrency in scheduled jobs.

Key Mechanics — Session Flags

FlagPurposeUse Case
--continue / -c Resume the most recent conversation in the current directory Multi-step reviews: "review" → "now focus on DB queries" → "summarize"
--resume <session_id> / -r Resume a specific session by ID Pipeline stage 2 picks up exactly where stage 1 left off
--session-id <UUID> Run under a caller-chosen session ID Deterministic naming for idempotent/addressable jobs
--fork-session Branch a new session from an existing one (with --resume/--continue) Try a follow-up without mutating the original transcript

Multi-Step Pattern

bash# Step 1: Start review, capture session ID
session_id=$(claude -p "Start a review of the auth module." \
  --output-format json | jq -r '.session_id')

# Step 2: Continue the same conversation
claude -p "Now focus on the database queries." \
  --resume "$session_id"

# Step 3: Generate summary from full context
claude -p "Generate a summary of all issues found." \
  --resume "$session_id"

Session Isolation in CI

Each CI job run creates an isolated environment. Key isolation concepts:

  • Ephemeral environments: Docker containers and CI runners are disposable — sessions don't persist across job runs unless you explicitly save the session ID
  • --bare mode: Prevents loading ambient configuration (hooks, plugins, CLAUDE.md) from the workspace, ensuring identical behavior across machines
  • Concurrency locks: Use flock or CI concurrency groups to prevent overlapping scheduled runs

Visual Aid — Session Decision Tree

Start │ ┌──────┴──────┐ │ Need prior │ │ context? │ └──────┬──────┘ ╱ ╲ Yes No │ │ ┌──────┴──────┐ ┌─┴──────────────┐ │ Same dir as │ │ Fresh run with │ │ last session?│ │ claude -p only │ └──────┬──────┘ └────────────────┘ ╱ ╲ Yes No / specific │ │ ┌──────┴──────┐ ┌───┴───────────┐ │ --continue │ │ --resume │ │ (latest in │ │ <session_id> │ │ this dir) │ │ │ └─────────────┘ └───────────────┘ │ ┌──────┴──────┐ │ Want to │ │ fork? │ └──────┬──────┘ ╱ ╲ Yes No │ │ ┌──────┴──────┐ ┌──┴──────────┐ │--fork-session│ │ Mutates │ │ (new branch) │ │ original │ └─────────────┘ └─────────────┘ Figure 17.4 — Session flag decision tree

Preventing Overlapping Scheduled Runs

bash# Use flock to prevent concurrent runs
flock -n /tmp/claude-nightly.lock -c '
  claude -p "Nightly refactor sweep." \
    --max-turns 15 --model sonnet --output-format json
' || echo "Previous run still in progress; skipping."
yaml# GitHub Actions: cancel overlapping scheduled runs
concurrency:
  group: nightly-docs
  cancel-in-progress: true
⚠️ Exam Tips & Tricks

Exam scenario: "A pipeline has two stages that need shared context. How do you connect them?" → Capture .session_id from JSON output, then --resume in the next stage.

Trick question: "--continue resumes any session anywhere." → False. It resumes the most recent session in the current directory.

Key distinction: --fork-session creates a new branch; --resume mutates the original.

⚡ Quick-Recall Summary

  • --continue = resume latest session in current directory
  • --resume <id> = resume specific session by ID
  • --session-id <UUID> = deterministic, idempotent session naming
  • --fork-session = branch without mutating original
  • Use flock or CI concurrency groups to prevent overlap
17.5

Guardrails & Permission Management

▼

Concept Overview

In interactive mode, the human IS the guardrail — approving each risky action. In CI/CD, there's no human, so you must encode all safety decisions in advance using three layers: tool restrictions (--allowedTools / --disallowedTools), permission modes (--permission-mode), and hooks (deterministic veto scripts).

This is the most exam-critical section — the difference between responsible and reckless automation.

Key Mechanics

Layer 1: Tool Restrictions

FlagPurposeExample
--allowedTools Whitelist tools that may run without prompting --allowedTools "Read,Grep,Glob" (read-only)
--disallowedTools Blacklist specific tools or tool invocations --disallowedTools "Bash(rm *)" 
bash# Read-only reviewer: can search and read, nothing else
claude -p "Review this diff for bugs." \
  --allowedTools "Read,Grep,Glob"

# Allow git inspection but block destructive commands
claude -p "Summarize recent history." \
  --allowedTools "Bash(git log *)" "Bash(git diff *)" "Read" \
  --disallowedTools "Bash(rm *)"

# Auto-commit with specific git commands allowed
claude -p "Commit staged changes with a descriptive message." \
  --allowedTools "Bash(git diff *),Bash(git log *),Bash(git status *),Bash(git commit *)"
ℹ️ Important Detail — Prefix Matching

Bash(git diff *) — the trailing * with a space before it enables prefix matching. Without the space, Bash(git diff*) would also match git diff-index. The exam may test this nuance.

Layer 2: Permission Modes

ModeBehaviorCI Suitability
default Standard interactive prompting ❌ Hangs in CI — no one to answer
auto Classifier reviews most actions instead of human ⚠️ Usable with --permission-prompts none
acceptEdits Auto-approves file writes + common filesystem commands ✅ For code-changing jobs
dontAsk Auto-denies everything not pre-approved ✅ The CI-shaped mode — fully non-interactive
bypassPermissions Disables ALL permission checks — every tool call executes 🔴 ONLY in disposable sandboxes

--dangerously-skip-permissions

Shorthand for bypassPermissions. Disables all permission prompts. Refuses to run as root on Linux/macOS. Use ONLY in ephemeral, sandboxed environments where there's nothing valuable to damage.

bash# ✅ SAFE: dontAsk mode with tight tool restrictions
claude -p "Review src/ for bugs." \
  --permission-mode dontAsk \
  --allowedTools "Read,Grep,Glob"

# ⚠️ SANDBOXED ONLY: bypass all permissions in a disposable container
docker run --rm -e ANTHROPIC_API_KEY node:20-slim bash -c '
  npm install -g @anthropic-ai/claude-code &&
  claude -p "Fix the failing tests." \
    --dangerously-skip-permissions \
    --max-turns 5
'

Layer 3: Hooks (Deterministic Veto)

A PreToolUse hook is a shell script that runs before every tool execution. It can block an action by exiting non-zero — a deterministic veto that doesn't depend on the model's judgment.

  • Encoded in .claude/settings.json
  • Exit 0 = allow, exit non-zero = deny
  • Sees the full proposed action — can inspect and decide programmatically
  • Holds even if the prompt is adversarial or the model misbehaves

Visual Aid — Permission Decision Flow

Tool Call Proposed │ ┌────────▼────────┐ │ PreToolUse Hook │ │ (if defined) │ └────────┬────────┘ ╱ ╲ exit(0) exit(N) Allow BLOCKED ✗ │ ┌───────▼────────┐ │ --allowedTools │ │ match? │ └───────┬────────┘ ╱ ╲ Yes No │ │ EXECUTE ┌────▼──────────┐ ✓ │ Permission │ │ Mode decides │ └────┬──────────┘ │ ┌──────────┼──────────┐ │ │ │ dontAsk acceptEdits bypass │ │ │ AUTO-DENY IS EDIT? EXECUTE ✗ ╱ ╲ ✓ Yes No │ │ EXECUTE AUTO-DENY ✓ ✗ Figure 17.5 — How hooks, allow-lists, and permission modes compose

The Write/Commit/Push Boundary

Authority LevelAgent Can DoPipeline DoesGuardrails
Read-only (review) Read files, search, analyze Post comments --allowedTools "Read,Grep,Glob"
Write-to-tree (fix/refactor) Edit files in working tree Open PR if tests pass --permission-mode acceptEdits
Full auto (sandboxed) Everything — Only in disposable containers
⚠️ Exam Tips & Tricks

High-weight topic: Expect 2–3 questions on guardrails/permissions. The exam loves testing which permission mode is appropriate for which scenario.

"Which mode for CI?" → dontAsk is the safe default answer unless the question specifically describes a disposable sandbox.

Tricky distractor: --dangerously-skip-permissions is NOT required for CI. You can (and should) use --permission-mode dontAsk + --allowedTools instead.

Hook fact: Hooks run before the allow-list check. A hook can block something that's on the allow-list.

❌ Common Pitfalls

Over-permissioning: Using --dangerously-skip-permissions against a real repo because it was easier. An automated agent can push, delete, or call external APIs.

Confusing "allow" vs "approve": --allowedTools skips the permission prompt, but a hook can still veto.

Forgetting turn limits: Without --max-turns, a looping agent bills indefinitely.

⚡ Quick-Recall Summary

  • Three guardrail layers: tools → permission mode → hooks
  • --allowedTools = whitelist; --disallowedTools = blacklist
  • dontAsk = the CI permission mode (auto-deny unapproved)
  • --dangerously-skip-permissions = sandbox-only, refuses to run as root
  • Hooks = deterministic veto via PreToolUse shell scripts
17.6

CLAUDE.md in CI/CD Context

▼

Concept Overview

CLAUDE.md is a special Markdown file that provides Claude Code with project-specific context — coding conventions, architecture decisions, tool preferences, and team practices. In CI/CD, it determines what context the agent has about your codebase, but also introduces a risk: ambient configuration that may not be appropriate for automated runs.

Key Mechanics

CLAUDE.md Hierarchy (Resolution Order)

LocationScopeLoaded in -p?Loaded in --bare?
~/.claude/CLAUDE.mdGlobal — all projects✅ Yes❌ No
<parent-dirs>/CLAUDE.mdParent directories (monorepo)✅ Yes❌ No
<project-root>/CLAUDE.mdProject-level — shared with team✅ Yes❌ No
<project-root>/.claude/CLAUDE.mdSame as above (alternative path)✅ Yes❌ No
ℹ️ Critical CI Distinction

--bare mode skips ALL CLAUDE.md files. This is the recommended mode for CI because it ensures deterministic behavior. Without --bare, a teammate's ~/.claude/CLAUDE.md or a project's uncommitted configuration can change agent behavior unpredictably.

What Goes in CLAUDE.md for CI

If you intentionally want CI runs to use project context (without --bare), include:

  • Coding conventions: "We use pnpm, not npm" / "Tests go next to the source file"
  • Architecture notes: "src/auth/ handles all authentication"
  • CI-specific instructions: "When reviewing PRs, focus on security and API contracts"
  • Tool restrictions: "Never modify files in the config/ directory"
markdown# CLAUDE.md

## Project Conventions
- Package manager: pnpm (never npm or yarn)
- Tests: colocated with source files (*.test.ts)
- Import style: absolute paths with @/ alias

## CI Review Instructions
When reviewing pull requests:
- Focus on security vulnerabilities, type safety, and API contracts
- Check for proper error handling in async functions
- Verify new endpoints have corresponding tests
- Do NOT suggest style changes — the linter handles those

## Architecture
- src/auth/ — Authentication and authorization
- src/api/ — REST API routes
- src/db/ — Database models and migrations

Alternative: --append-system-prompt

Instead of relying on CLAUDE.md, you can inject context directly via CLI flags:

bash# Add security review context without CLAUDE.md
gh pr diff "$1" | claude -p --bare \
  --append-system-prompt "You are a security engineer. Review for vulnerabilities." \
  --output-format json
⚠️ Exam Tips & Tricks

Key exam question: "How do you ensure identical Claude Code behavior across all CI machines?" → Use --bare mode, which skips all ambient CLAUDE.md files, hooks, plugins, and auto-memory.

Scenario: "Agent behaves differently on two developers' CI forks." → Likely cause: different ~/.claude/CLAUDE.md files being loaded. Fix: add --bare.

Alternative injection: --append-system-prompt adds to default behavior; --system-prompt fully replaces it.

⚡ Quick-Recall Summary

  • CLAUDE.md = project context file read at session start
  • --bare skips ALL CLAUDE.md + hooks + plugins — use for deterministic CI
  • --append-system-prompt = add context without CLAUDE.md files
  • --system-prompt = fully replace default system prompt
  • Without --bare, CI loads ambient config from the workspace and home dir
17.7

JSON Schema Validation (--json-schema)

▼

Concept Overview

The --json-schema flag constrains Claude Code's output to conform to a specific JSON Schema definition. Instead of hoping the model returns parseable data from free-text prose, you get schema-validated structured output in the structured_output field of the JSON response. This is what turns a brittle "grep the prose" pipeline into a robust, typed data pipeline.

Key Mechanics

  • Requires: --output-format json must be used together with --json-schema
  • Schema format: Standard JSON Schema (passed as a JSON string or file reference)
  • Output location: Validated output in .structured_output field (not .result)
  • Validation: If the schema is invalid, Claude exits with Error: --json-schema is not a valid JSON Schema and a diagnostic
  • format keyword: Accepted but treated as an annotation only — NOT enforced (e.g., "format": "email" won't validate emails)

Example: Extracting Function Names

bashclaude -p "Extract the main function names from auth.py" \
  --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "functions": {
        "type": "array",
        "items": { "type": "string" }
      }
    },
    "required": ["functions"]
  }' \
| jq '.structured_output'

Example: Bug Report Extraction

bashclaude -p "Analyze this code for bugs and report findings." \
  --output-format json \
  --json-schema '{
    "type": "object",
    "properties": {
      "bugs": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "file": { "type": "string" },
            "line": { "type": "integer" },
            "severity": { "type": "string", "enum": ["critical","high","medium","low"] },
            "description": { "type": "string" }
          },
          "required": ["file", "line", "severity", "description"]
        }
      },
      "summary": { "type": "string" }
    },
    "required": ["bugs", "summary"]
  }'

⚠️ Exam Tips & Tricks

Critical distinction: With --json-schema, the structured result is in .structured_output, NOT .result. The exam will test this.

Trap question: "Does --json-schema work with --output-format text?" → No. It requires --output-format json.

Format keyword: The "format": "email" annotation is accepted but not enforced. Before v2.1.205, schemas containing format were treated as invalid entirely.

When to use: Whenever a downstream pipeline step branches on the agent's output. Prefer schema over parsing free text.

❌ Common Pitfalls

Wrong field: Reading .result when you should read .structured_output.

Invalid schema: Passing malformed JSON Schema — Claude exits with an error. Always validate your schema before deploying.

Over-reliance on format: Assuming "format": "uri" validates URIs — it doesn't; it's annotation-only.

⚡ Quick-Recall Summary

  • --json-schema + --output-format json = schema-validated structured output
  • Validated result lives in .structured_output (not .result)
  • Invalid schema → error exit with diagnostic message
  • format keyword = accepted as annotation, NOT enforced
  • Use whenever downstream steps branch on agent output

Complete Workflow File

yamlname: Claude Code PR Review
on:
  pull_request:
    types: [opened, synchronize]

permissions:
  contents: read          # Read repo, but cannot push
  pull-requests: write    # Post review comments

concurrency:
  group: claude-review-${{ github.event.pull_request.number }}
  cancel-in-progress: true

jobs:
  review:
    runs-on: ubuntu-latest
    timeout-minutes: 10     # Wall-clock safety net

    steps:
      # Step 1: Checkout with full history for diff
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      # Step 2: Install Claude Code
      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      # Step 3: Run the review with full guardrails
      - name: Review PR
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          git diff origin/main...HEAD | claude -p \
            --bare \
            --max-turns 12 \
            --model sonnet \
            --permission-mode dontAsk \
            --allowedTools "Read,Grep,Glob" \
            --output-format json \
            --json-schema '{
              "type": "object",
              "properties": {
                "issues": {
                  "type": "array",
                  "items": {
                    "type": "object",
                    "properties": {
                      "file": {"type":"string"},
                      "line": {"type":"integer"},
                      "severity": {"type":"string","enum":["critical","high","medium","low"]},
                      "description": {"type":"string"}
                    },
                    "required": ["file","line","severity","description"]
                  }
                },
                "summary": {"type":"string"},
                "risk_level": {"type":"string","enum":["none","low","medium","high"]}
              },
              "required": ["issues","summary","risk_level"]
            }' \
            "Review this pull request for bugs, security issues, and correctness. \
             Be concise — one issue per finding with file:line reference." \
          | tee review.json

      # Step 4: Parse and log results
      - name: Parse results
        run: |
          echo "## Review Summary" >> $GITHUB_STEP_SUMMARY
          jq -r '.structured_output.summary' review.json >> $GITHUB_STEP_SUMMARY
          echo "Risk: $(jq -r '.structured_output.risk_level' review.json)"
          echo "Issues: $(jq '.structured_output.issues | length' review.json)"
          echo "Cost: $(jq -r '.total_cost_usd' review.json)"
          echo "Session: $(jq -r '.session_id' review.json)"

Tricky Distractor Patterns to Watch

Golden Rules for This Chapter

  1. No -p, no CI. Every unattended invocation requires --print.
  2. Parse JSON, not text. Always use --output-format json + jq.
  3. Least privilege. --allowedTools + --permission-mode dontAsk is the safe default.
  4. Always cap cost. --max-turns + timeout + model selection.
  5. Schema for structure. --json-schema → read .structured_output.
  6. Bare for determinism. --bare ensures identical behavior across all machines.

Q1
Which flag is required to run Claude Code non-interactively in a CI pipeline?
  1. --batch
  2. --headless
  3. -p / --print
  4. --ci-mode

✅ C) -p / --print

The --print flag (shorthand -p) is the ONLY flag that switches Claude Code into non-interactive batch mode. Options A, B, and D are fabricated flags that do not exist in Claude Code.

Q2
When using --output-format json with --json-schema, where does the schema-validated output appear in the response?
  1. .result
  2. .structured_output
  3. .schema_result
  4. .validated_json

✅ B) .structured_output

When --json-schema is used, the validated output is placed in the .structured_output field, NOT .result. The .result field contains the free-text response. This is a critical distinction for building reliable pipelines.

Q3
A team wants their CI job to review PRs without any ability to modify files. Which combination is the MOST appropriate?
  1. --dangerously-skip-permissions --allowedTools "Read,Write,Edit"
  2. --permission-mode dontAsk --allowedTools "Read,Grep,Glob"
  3. --permission-mode bypassPermissions --allowedTools "Read,Grep"
  4. --permission-mode acceptEdits --allowedTools "Read,Grep,Edit"

✅ B) --permission-mode dontAsk --allowedTools "Read,Grep,Glob"

dontAsk auto-denies anything not pre-approved, and the allow-list contains ONLY read-only tools. Option A uses the dangerous bypass with write access. Option C uses bypassPermissions unnecessarily. Option D includes Edit which allows file modifications.

Q4
What does the --bare flag skip when running claude -p? (Select ALL that apply)
  1. CLAUDE.md files from the project and home directory
  2. Hooks defined in .claude/settings.json
  3. The ANTHROPIC_API_KEY environment variable
  4. MCP servers, plugins, and auto-memory

✅ A, B, and D

--bare skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, CLAUDE.md files, and OAuth/keychain credentials. It does NOT skip ANTHROPIC_API_KEY from the environment — that's the intended auth method for bare mode.

Q5
A pipeline has two stages. Stage 1 analyzes code; Stage 2 needs Stage 1's context to generate tests. How should Stage 2 access Stage 1's conversation?
  1. Stage 2 uses --continue to resume the latest session
  2. Stage 1 saves .session_id from JSON output; Stage 2 uses --resume <session_id>
  3. They share context automatically because they're in the same CI job
  4. Stage 2 passes --shared-context stage1

✅ B) Capture .session_id and use --resume

The reliable pattern: extract .session_id from the JSON output of Stage 1, then pass it to --resume in Stage 2. Option A works but is less reliable (what if they run in different directories?). Option C is false — there's no automatic sharing. Option D is a fabricated flag.

Q6
Which authentication method avoids storing long-lived secrets in a GitHub Actions CI environment for Amazon Bedrock?
  1. Hard-coded AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in the workflow file
  2. OIDC role assumption via aws-actions/configure-aws-credentials with id-token: write
  3. ANTHROPIC_API_KEY stored as a GitHub secret
  4. Service account JSON key stored in repository settings

✅ B) OIDC role assumption

OIDC federation mints short-lived credentials at job runtime — no static secret is stored anywhere. The job requests id-token: write permission, assumes an IAM role, and receives temporary credentials scoped to that role. Option A hard-codes secrets (worst practice). Option C is for direct Anthropic API, not Bedrock. Option D is a GCP concept.

Q7
True or False: --dangerously-skip-permissions is required for running Claude Code in any CI/CD pipeline.
  1. True — CI has no human to approve, so all permissions must be skipped
  2. False — you should use --permission-mode dontAsk with --allowedTools instead

✅ B) False

--dangerously-skip-permissions is NOT required for CI. The recommended approach is --permission-mode dontAsk combined with --allowedTools to whitelist only what the task needs. The dangerous flag should only be used in disposable sandboxed environments. It refuses to run as root as an additional safety measure.

Q8
Which of these are valid cost controls for unattended Claude Code runs? (Select ALL that apply)
  1. --max-turns N to cap agentic iterations
  2. --max-budget-usd N to set a hard dollar ceiling
  3. --cost-limit N to restrict per-token pricing
  4. --model sonnet to use a cheaper model for routine tasks
  5. CI timeout-minutes as a wall-clock safety net

✅ A, B, D, and E

The five valid cost controls are: --max-turns (iteration cap), --max-budget-usd (dollar ceiling), model selection (cheaper models for routine work), concurrency groups (prevent parallel job explosion), and wall-clock timeouts. Option C (--cost-limit) is a fabricated flag that does not exist.
