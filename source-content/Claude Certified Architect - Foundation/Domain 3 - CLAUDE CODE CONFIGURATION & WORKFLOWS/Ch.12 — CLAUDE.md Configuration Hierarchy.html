Chapter 12: CLAUDE.md Configuration Hierarchy Claude Certified Architect — Foundations & Professional

This chapter covers how Claude Code uses CLAUDE.md files to carry persistent context across sessions. You will learn the four-scope hierarchy, file discovery mechanics, modular configuration with @import directives and the .claude/rules/ directory, and the complementary auto-memory system. Mastering this chapter is essential for exam scenarios involving configuration precedence, monorepo setups, and debugging "Claude ignores my instructions" situations.

⚠️ Critical Misconception Alert
CLAUDE.md files are concatenated, not overridden. There is no "cascade" where a more specific file replaces a broader one. All files are loaded additively into the context window. The phrase "most specific wins" is the single most expensive assumption you can carry into this exam domain.

12.1 — What Is CLAUDE.md?

Concept Summary

CLAUDE.md is a plain-text Markdown file that Claude Code reads at the start of every session. It provides persistent instructions — coding standards, build commands, project architecture, naming conventions — so that you don't have to re-explain context every time. Claude Code loads its contents as a user message after the system prompt. It is advisory context, not enforced configuration; Claude tries to follow the instructions, but compliance is not guaranteed, especially for vague or conflicting rules.

Key Terms

TermDefinitionExample / Notes
CLAUDE.md A markdown configuration file read by Claude Code to give persistent context to the session. Placed at project root, user home, managed policy path, or subdirectories.
Advisory Context Instructions Claude reads and tries to follow — not a hard enforcement layer. Adherence is estimated at ~80%. For guaranteed behavior, use hooks.
Session Context Window The finite token budget for a Claude Code conversation, consumed by CLAUDE.md content. Longer files = more tokens consumed = less room for conversation.
Hooks Shell commands executed at fixed lifecycle events (e.g., PreToolUse, PostCommit) — deterministic, not advisory. Use when a rule must fire every time (linting, formatting, blocking writes).
/init Slash command that auto-generates a starter CLAUDE.md by analyzing the codebase. If a file already exists, /init suggests improvements instead of overwriting.
/memory Slash command that lists every CLAUDE.md, CLAUDE.local.md, and rules file in context. First debugging step for "Claude ignores my rule" problems.
/context Slash command that shows exactly which memory files loaded into the current session. Verifies files are actually visible to Claude.

Visual Aid — CLAUDE.md vs. Hooks Decision Model

┌─────────────────────────────────┐ │ "Does this rule MUST fire │ │ every single time?" │ └──────────────┬────────────────────┘ │ ┌────────────┴────────────┐ ▼ ▼ YES → Use a Hook NO → Use CLAUDE.md (deterministic shell (advisory context; command; ~100% ~80% adherence; enforcement) Claude tries) Examples: Hook: "Run eslint --fix after every edit" Hook: "Block writes to /prod/ directory" CLAUDE.md: "Prefer 2-space indentation" CLAUDE.md: "Use TypeScript strict mode"

Annotated Code Example

<!-- CLAUDE.md — Project Root -->

# Project: invoice-api

## Build & Test
- Run `pnpm build` to compile        <!-- Command Claude can't guess -->
- Run `pnpm test:unit` before committing  <!-- Specific enough to verify -->
- IMPORTANT: prefer single test files, not the full suite

## Code Style
- Use ES modules (import/export), not CommonJS
- 2-space indentation                  <!-- Differs from default -->
- Destructure imports when possible

## Architecture
- API handlers: `src/api/handlers/`
- Shared types: `src/types/`
- Never use `any` type              <!-- Concrete, verifiable -->

Deep Dive — Edge Cases & Gotchas

  • Not part of the system prompt: CLAUDE.md content is loaded as a user message after the system prompt. It is not injected into the system prompt. This distinction matters for override semantics.
  • Size limit: A single CLAUDE.md file can be up to 4 MiB. Files larger than 4 MiB are silently skipped — no error, no warning.
  • Recommended size: Target under 200 lines per file. Longer files degrade adherence because important rules drown in noise.
  • HTML comments are stripped: Block-level <!-- ... --> comments are removed before injection into context — they cost zero tokens. Use them for maintainer notes.
  • Survives /compact: The project-root CLAUDE.md is re-read from disk after /compact. Subdirectory files and path-scoped rules reload on demand.
  • Pruning test: For each line, ask: "Would removing this cause Claude to make mistakes?" If no — delete it.
💡 Tips & Tricks
  • Use IMPORTANT or YOU MUST emphasis for 2–3 critical rules. If you bold everything, you've bolded nothing.
  • Use /init to bootstrap, then prune ruthlessly with the pruning test.
  • Don't include information Claude can derive from reading the code — file trees, dependency lists, architecture overviews are noise.
  • A rule that tells Claude to do what it already does by default wastes tokens.
🎯 Exam Strategy — Section 12.1
  • Typical question angle: "Is CLAUDE.md enforced or advisory?" — Answer: advisory context, ~80% adherence.
  • Trap: Options that describe CLAUDE.md as "system prompt configuration" — it loads as a user message, not system prompt.
  • Trap: "CLAUDE.md files over 200 lines are rejected" — they're not rejected; the 200-line target is a recommendation. The hard limit is 4 MiB.
  • Key differentiator: CLAUDE.md (advisory) vs. Hooks (deterministic) vs. Managed Settings (enforced by client).

12.2 — The Four-Scope Hierarchy

Concept Summary

CLAUDE.md files exist at four distinct scopes, loaded from broadest to most specific. All scopes are concatenated into context additively — nothing overrides anything else. Instructions closer to where you launched Claude are read last. The mental model is a stack of context, not a cascade of overrides.

Scope Table — The Definitive Reference

Scope Location Purpose Shared With Can Be Excluded?
1. MANAGED POLICY macOS: /Library/Application Support/ClaudeCode/CLAUDE.md
Linux/WSL: /etc/claude-code/CLAUDE.md
Windows: C:\Program Files\ClaudeCode\CLAUDE.md 		Org-wide rules deployed by IT/DevOps All users on machine NO — cannot be excluded by claudeMdExcludes
2. USER ~/.claude/CLAUDE.md Personal preferences across all projects Just you (all projects) Yes
3. PROJECT ./CLAUDE.md or ./.claude/CLAUDE.md Team-shared project instructions (committed to source control) Team via VCS Yes
4. LOCAL ./CLAUDE.local.md Personal project-specific preferences (gitignored) Just you (this project) Yes
⚠️ Gotcha — "Most Specific Wins" Is Wrong
Scopes are additive/concatenated, not cascading overrides. If the managed policy says "use tabs" and your project CLAUDE.md says "use spaces," both instructions appear in context and Claude may pick either one arbitrarily. The only "precedence" is read order: later context may have slightly higher salience, but this is an emergent behavior of the LLM, not a deterministic rule engine.

USER INSTRUCTIONS │ │ ~/.claude/CLAUDE.md │ │ ~/.claude/rules/*.md (no paths: field) │ └──────────────────────┬──────────────────────┘ │ concatenated ↓ ┌──────────────────────┴──────────────────────┐ │ 3. PROJECT INSTRUCTIONS │ │ ./CLAUDE.md OR ./.claude/CLAUDE.md │ ← Committed to git │ ./.claude/rules/*.md │ └──────────────────────┬──────────────────────┘ │ concatenated ↓ ┌──────────────────────┴──────────────────────┐ │ 4. Deep Dive — Edge Cases & Gotchas

  • Two project-level locations: ./CLAUDE.md and ./.claude/CLAUDE.md are both valid. If both exist, both are loaded.
  • Managed policy has two delivery mechanisms: A standalone CLAUDE.md file at the OS-specific path, or the claudeMd key inside managed-settings.json. Both have the same precedence.
  • The claudeMd key only works in managed/policy settings. Setting it in user, project, or local settings has no effect — this is an exam trap.
  • CLAUDE.local.md is worktree-specific: In git worktrees, a gitignored local file only exists in the worktree where you created it. To share personal instructions across worktrees, use an @import pointing to your home directory.
  • Settings vs. CLAUDE.md separation: Managed settings (permissions.deny, sandbox.enabled) are enforced by the client. Managed CLAUDE.md is still advisory context. Don't confuse the two.
💡 Tips & Tricks
  • Start with the project file committed to git — it's the highest-leverage scope.
  • Use the user file only for genuinely personal preferences (commit style, verbosity) that have no business in a shared repo.
  • Use CLAUDE.local.md for sandbox URLs, personal test data, custom MCP servers — anything you'd .gitignore.
🎯 Exam Strategy — Section 12.2
  • Favorite trap: "Which scope takes precedence?" — The answer is none; they're concatenated. If forced to pick, "read last" = slightly higher salience, but this is not deterministic.
  • Watch for: Questions that claim the claudeMd key in settings.json works at all scopes — it only works in managed/policy settings.
  • Watch for: Options that say managed policy can be excluded — it cannot.
  • Recall anchor: M-U-P-L = Managed → User → Project → Local (load order, broadest to most specific).

12.3 — File Discovery & Loading Mechanics

Concept Summary

Claude Code doesn't just read the CLAUDE.md in your current directory — it walks the entire directory tree from the filesystem root down to your CWD, loading every CLAUDE.md and CLAUDE.local.md it finds along the way. Subdirectory files below CWD are loaded lazily (on demand) when Claude reads files in those directories. This walk-up + lazy-load model is the core discovery mechanism.

The Walk-Up Algorithm

How it works at launch

  1. Claude Code starts at the filesystem root and walks down to your CWD.
  2. At each directory level, it loads CLAUDE.md, then CLAUDE.local.md (if present).
  3. Content is ordered: root-most first → CWD last. Within each directory, local is appended after project.
  4. Managed policy and user-level files load before the directory walk.

Visual Aid — Walk-Up Discovery Example

Scenario: You run `claude` in /home/dev/monorepo/packages/api/ Discovery order (launch): 1. Managed policy: /etc/claude-code/CLAUDE.md 2. User: ~/.claude/CLAUDE.md 3. Walk-up root level: /CLAUDE.md (if exists) 4. Walk-up: /home/CLAUDE.md (if exists) 5. Walk-up: /home/dev/CLAUDE.md (if exists) 6. Walk-up: /home/dev/monorepo/CLAUDE.md ✓ exists 7. Walk-up: /home/dev/monorepo/CLAUDE.local.md (if exists) 8. Walk-up: .../monorepo/packages/CLAUDE.md (if exists) 9. CWD: .../packages/api/CLAUDE.md ✓ exists 10. CWD local: .../packages/api/CLAUDE.local.md ✓ exists Result: All discovered files are CONCATENATED into context. Monorepo root → packages → api → api.local

Subdirectory Lazy Loading

BehaviorWhen It HappensKey Detail
Walk-up (eager) Session launch CWD and every directory above CWD — loaded immediately
Subdirectory (lazy) When Claude reads files in that subdirectory Directories below CWD — loaded on demand only
After /compact Context compaction event Project-root CLAUDE.md is re-read from disk. Subdirectory files reload only when Claude touches matching files again.

Deep Dive — Edge Cases & Gotchas

  • claudeMdExcludes: Glob patterns in .claude/settings.local.json that skip specific CLAUDE.md files. Patterns match against absolute file paths. Arrays merge across settings layers. Managed policy files cannot be excluded.
  • --add-dir flag: Gives Claude access to additional directories. CLAUDE.md files from these dirs are NOT loaded by default. Set CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 to include them.
  • Monorepo pitfall: In large monorepos, ancestor CLAUDE.md files from other teams get picked up by the walk-up. Use claudeMdExcludes to skip irrelevant ones.
  • Conversation-only instructions vanish: Instructions given only in chat (not written to CLAUDE.md) disappear after /compact. Add them to the file to persist.
✅ Best Practice — Verify What Loaded
Run /context at the start of any debugging session. It lists every memory file Claude can see. If your CLAUDE.md isn't listed, Claude literally cannot see it. This explains most "ignored rule" complaints.
🎯 Exam Strategy — Section 12.3
  • Common question: "In which order are files loaded when CWD is X?" — Walk from root down, listing every CLAUDE.md + CLAUDE.local.md pair.
  • Trap: "Subdirectory CLAUDE.md files load at session start" — they do NOT; they load lazily.
  • Trap: "After /compact, all CLAUDE.md files reload" — only the project-root file re-reads from disk. Subdirectory files require Claude to touch files there again.
  • Recall anchor: Walk-up = eager. Walk-down = lazy.

12.4 — @imports & Modular Rules

Concept Summary

As projects grow, CLAUDE.md files can be split into modular fragments using two mechanisms: @import directives (inline file inclusion) and the .claude/rules/ directory (topic-specific rule files). Both help with organization, but neither reduces token usage — imported content and unconditional rules still load into the context window at launch. Path-scoped rules are the exception: they load on demand when Claude touches matching files.

@import Syntax

Key Rules

RuleDetail
Syntax @path/to/file — bare, outside code fences or backtick spans
Path resolution Relative paths resolve relative to the file containing the import, not the CWD
Absolute paths Allowed — e.g. @/home/user/shared-rules.md
Recursive imports Imported files can import other files, up to a maximum depth of 4 hops
Escaping Wrap in backticks to prevent import: `@README` stays literal. Fenced code blocks also suppress imports.
External imports An import resolving outside CWD triggers an approval dialog on first encounter.
Token impact Imported files still load into context at launch — imports help organization, not token savings.

Annotated Code Example — @import

<!-- CLAUDE.md — Project Root -->

# invoice-api

See @README.md for project overview.          <!-- Imports README content -->
Check @package.json for available scripts.    <!-- Imports package.json -->

## Shared Standards
@docs/coding-standards.md                     <!-- Relative to this file -->
@docs/security-rules.md                       <!-- Max 4 hops of recursion -->

## Cross-Reference (not imported)
See `@AGENTS.md` for other tools' config.       <!-- Backticks = literal -->

## Bridge AGENTS.md
@AGENTS.md                                    <!-- Imports AGENTS.md -->
⚠️ Gotcha — @import ≠ Token Savings
Splitting CLAUDE.md into @imported fragments is organizational, not a token optimization. All imported content loads at launch. To genuinely reduce context consumption, use path-scoped rules that load on demand.

The .claude/rules/ Directory

Visual Aid — Directory Structure

your-project/
├── .claude/
│   ├── CLAUDE.md            # Main project instructions
│   ├── settings.json        # Project settings
│   └── rules/
│       ├── code-style.md    # Always loaded (no paths: field)
│       ├── testing.md       # Always loaded
│       ├── security.md      # Always loaded
│       ├── api-rules.md     # Path-scoped → loaded on demand
│       └── frontend/
│           └── react.md     # Path-scoped → loaded on demand
├── CLAUDE.md                # Alternative project-root location
└── CLAUDE.local.md          # Personal, gitignored

Rules behavior

  • Rules without a paths frontmatter field load unconditionally at launch, same priority as .claude/CLAUDE.md.
  • Rules with a paths field load on demand when Claude reads files matching the glob patterns.
  • Rules are discovered recursively in subdirectories of .claude/rules/.
  • Symlinks are supported — circular symlinks are detected gracefully.
  • User-level rules in ~/.claude/rules/ apply to every project on your machine, loaded before project rules.

Path-Scoped Rules — The Key to Token Efficiency

# .claude/rules/api-rules.md
---
paths:
  - "src/api/**/*.ts"
  - "src/api/**/*.tsx"
---

# API Development Rules

- All API endpoints must include input validation
- Use the standard error response format
- Include OpenAPI documentation comments
- IMPORTANT: Never expose internal error messages to clients

Glob pattern reference

PatternMatches
**/*.tsAll TypeScript files in any directory
src/**/*All files under src/
*.mdMarkdown files in the project root only
src/components/*.tsxReact components in a specific directory
src/**/*.{ts,tsx}Brace expansion — matches both .ts and .tsx
✅ Best Practice — When to Use Each Mechanism
MechanismUse WhenToken Impact
CLAUDE.md (single file)Small projects, <200 linesAlways loaded
@importOrganization; shared fragments across filesAlways loaded
.claude/rules/ (no paths)Topic modularity; file >200 linesAlways loaded
.claude/rules/ (with paths)Genuine token savings; rules for specific parts of codebaseOn demand only
Skills (.claude/skills/)Task-specific workflows, not needed every sessionOn demand (invoked)

Deep Dive — Edge Cases & Gotchas

  • Brace expansion limit: A rule's entire paths list shares a budget of 1,000 expanded patterns and 4 MiB. Exceeding this causes the pattern to be used unexpanded (literal braces match nothing).
  • Bracket syntax: [ starts a bracket expression. A pattern like photos [2024/** is invalid and matches nothing. Escape as photos \[2024/**.
  • Symlinked rules outside CWD behave like external imports — they require approval and only non-path-scoped rules load.
  • Path-scoped rules trigger on file reads, not on every tool use. Claude must actually read a file matching the glob.
🎯 Exam Strategy — Section 12.4
  • Favorite trap: "@import reduces token usage" — it does NOT. Content is expanded at launch.
  • Trick question: "What is the maximum import depth?" — 4 hops.
  • Key distinction: Rules without paths: = always loaded. Rules with paths: = on demand = token savings.
  • Path resolution: Imports resolve relative to the file containing the import, not CWD. This is tested frequently.
  • Watch for: Code in backticks is NOT imported — `@README` is literal text.

12.5 — Auto Memory, Debugging & Best Practices

Concept Summary

Claude Code has two complementary memory systems: CLAUDE.md files (written by you) and auto memory (written by Claude). Auto memory lets Claude accumulate knowledge across sessions without manual effort. It stores four kinds of notes: user preferences, feedback/corrections, project context, and reference information. Understanding the interaction between these two systems — and knowing when to use hooks instead of either — is the capstone of this chapter.

Auto Memory System

Comparison: CLAUDE.md vs. Auto Memory

DimensionCLAUDE.mdAuto Memory
Who writes itYou (the developer)Claude (automatically)
ContentInstructions and rulesLearnings, corrections, patterns
ScopeProject, user, or orgPer repository (shared across worktrees)
Loaded intoEvery session (full file, up to 4 MiB)Every session (first 200 lines or 25 KB of MEMORY.md)
StorageIn the project directory or user home~/.claude/projects/<project>/memory/
ShareableYes — commit to gitNo — machine-local only
Topic filesN/ALoaded on demand (not at startup)

Auto Memory Directory Structure

~/.claude/projects/<project>/memory/
├── MEMORY.md              # Index — first 200 lines loaded each session
├── user_role.md           # Topic file — loaded on demand
├── feedback_testing.md    # Topic file — loaded on demand
└── project_deadlines.md   # Topic file — loaded on demand

Memory Types (Frontmatter type field)

TypeWhat Claude RecordsExample
userYour role, expertise, working preferences"Senior backend engineer, prefers verbose tests"
feedbackCorrections you give, approaches you confirm"Always use pnpm, not npm"
projectOngoing work, deadlines, decisions"API migration deadline: March 15"
referenceWhere to find information outside the project"Issue tracker: Linear board 'backend'"
⚠️ Gotcha — MEMORY.md Size Limits
  • Only the first 200 lines or 25 KB (whichever is reached first) of MEMORY.md is loaded at session start.
  • Content beyond the threshold is silently dropped.
  • This limit applies only to MEMORY.md. CLAUDE.md files can be up to 4 MiB.
  • Topic files (e.g., user_role.md) are NOT loaded at startup — Claude reads them on demand.

The Pruning Test

For each line in your CLAUDE.md, ask: "Would removing this cause Claude to make mistakes?"
If the answer is no — delete the line. Run this test every time the file grows.

The Three-Tier Enforcement Model

┌──────────────────────────────────────────────────────┐ │ TIER 1: MANAGED SETTINGS │ │ ✓ Enforced by the client, deterministic │ │ → permissions.deny, sandbox.enabled, env vars │ └────────────────────────┬─────────────────────────────┘ │ ┌────────────────────────┴─────────────────────────────┐ │ TIER 2: HOOKS │ │ ✓ Shell commands at lifecycle events, deterministic │ │ → PreToolUse, PostCommit — run regardless of Claude │ └────────────────────────┬─────────────────────────────┘ │ ┌────────────────────────┴─────────────────────────────┐ │ TIER 3: CLAUDE.md / AUTO MEMORY │ │ ~ Advisory context, Claude tries (~80% adherence) │ │ → Coding standards, conventions, preferences │ └──────────────────────────────────────────────────────┘

Debugging "Claude Ignores My Rule"

  1. Run /context — verify the file is listed under Memory files.
  2. Run /memory — browse all memory files and open for editing.
  3. Check conflicting instructions — if two files disagree, Claude picks arbitrarily.
  4. Make instructions more specific — vague rules are unreliable.
  5. Check if the rule should be a hook — if it must fire every time, prose isn't enough.
  6. Check after /compact — nested/subdirectory files may not have reloaded yet.
💡 Tips & Tricks
  • Use the InstructionsLoaded hook to log exactly which instruction files are loaded, when, and why.
  • "Remember X" told to Claude saves to auto memory. "Add X to CLAUDE.md" edits the CLAUDE.md file. Know the difference.
  • Auto memory is machine-local and never committed to git. Worktrees of the same repo share one memory directory.
  • The /init trim check (v2.1.206+) proposes pruning for checked-in CLAUDE.md files automatically.
🎯 Exam Strategy — Section 12.5
  • Key distinction tested: CLAUDE.md (written by you, instructions) vs. auto memory (written by Claude, learnings). The exam loves switching these.
  • Trap: "Auto memory is shared via git" — it is NOT. It's machine-local.
  • Trap: "MEMORY.md loads completely" — only first 200 lines / 25 KB.
  • Favorite scenario: "A rule must always execute. Where do you put it?" — Answer: a hook, not CLAUDE.md.
  • Recall anchors: 200 lines (MEMORY.md limit), 4 MiB (CLAUDE.md max), 4 hops (import depth), ~80% (adherence estimate).

  • claudeMdExcludes arrays merge across settings layers
  • --add-dir does NOT load CLAUDE.md from additional dirs by default
  • Set CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 to include them
  • After /compact: root CLAUDE.md re-reads; subdirectory files reload on next file touch
  • Conversation-only instructions disappear after /compact

12.4 — @imports & Modular Rules

  • @path/to/file syntax imports content inline
  • Paths resolve relative to the importing file, not CWD
  • Maximum recursive import depth: 4 hops
  • Backticks (`@path`) and code fences suppress imports
  • External imports (outside CWD) trigger an approval dialog
  • Imports do NOT reduce token usage — content loads at launch
  • .claude/rules/ files are discovered recursively
  • Rules without paths: = always loaded (unconditional)
  • Rules with paths: = loaded on demand (genuine token savings)
  • Brace expansion budget: 1,000 expanded patterns / 4 MiB per rule
  • Symlinked rules outside CWD behave like external imports (approval required)
  • User-level rules (~/.claude/rules/) load before project rules

12.5 — Auto Memory & Best Practices

  • CLAUDE.md = written by you (instructions); auto memory = written by Claude (learnings)
  • Auto memory is on by default; toggle via /memory or autoMemoryEnabled setting
  • Storage: ~/.claude/projects/<project>/memory/
  • MEMORY.md index: first 200 lines or 25 KB loaded each session
  • Topic files are loaded on demand, not at session start
  • Auto memory is machine-local — not shareable via git
  • Four memory types: user, feedback, project, reference
  • Claude skips info it can derive from the codebase or CLAUDE.md already says
  • Three-tier enforcement: Managed Settings → Hooks → CLAUDE.md/Memory
  • Debugging flow: /context → /memory → check conflicts → increase specificity → consider hooks
  • Write instructions specific enough to verify: concrete > vague
  • IMPORTANT emphasis on 2–3 critical rules maximum

✅ Correct: B

Imported files can recursively import other files up to a maximum depth of 4 hops. Beyond that, imports are not expanded.

🪤 Trap in D: While cycle detection exists, there is a hard limit of 4 hops. Unlimited recursion is not allowed even without cycles.

Q18. Which of the following PREVENTS @README from being interpreted as an import?

✅ Correct: B

Import parsing skips code spans (backticks) and fenced code blocks. Writing `@README` keeps the text literal. Headings, spaces, and backslashes do not suppress the import behavior.
