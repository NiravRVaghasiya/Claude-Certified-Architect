Chapter Thesis: Prompt engineering is not a one-shot activity — it is an iterative, feedback-driven process analogous to software development. Chapter 16 teaches that the highest-quality Claude interactions emerge from a disciplined cycle of specifying expectations concretely (via input/output examples), validating outputs systematically (via test-driven iteration), uncovering hidden requirements proactively (via the interview pattern), and choosing the right fix granularity (single message vs. sequential). Mastering these patterns transforms prompt engineering from ad-hoc experimentation into a repeatable, measurable, production-grade discipline. The unifying theme is: define "done" before you start, then converge on it through structured feedback loops.
Section 16.1

Concrete Input/Output Examples for Transformation Requirements

Concept Overview

Instead of describing a transformation in abstract prose, you show Claude exactly what you want by providing concrete input→output pairs inside the prompt. This technique eliminates ambiguity, reduces back-and-forth, and gives Claude a precise specification to pattern-match against. Think of each example as a unit test embedded in the prompt — it defines the contract the output must satisfy.

Key Definitions

  • Transformation Requirement — A task that takes an input in one form and produces an output in another, e.g., parsing unstructured text into JSON, reformatting dates, or translating domain-specific notation.
  • Example Pair — A concrete (input, expected_output) tuple embedded in the prompt to demonstrate the desired behavior.
  • Boundary Example — An example deliberately chosen to illustrate edge cases, ambiguous inputs, or limit conditions.
  • Progressive Complexity — Ordering examples from simple to complex so Claude infers the generalization gradient.
  • Few-Shot Prompting — Providing 2–5 example pairs to establish a pattern (distinct from zero-shot, which gives no examples).
  • Canonical Form — The exact structure/format you expect in the output (e.g., specific JSON schema, date format, field ordering).

Core Principles

  1. Show, don't tell. A single concrete example is worth a paragraph of abstract description. Ambiguity in natural language disappears when you demonstrate the expected behavior.
  2. Cover the edges. Select examples that expose edge cases: empty inputs, malformed data, boundary values, multi-line content, special characters. Claude generalizes from your examples — if edge cases aren't shown, behavior is undefined.
  3. Order matters — simple first. Start with a straightforward example that establishes the basic pattern, then layer in complexity. This helps Claude build an internal model incrementally.
  4. Match format exactly. If you want JSON output, your examples must show exact JSON. If you want markdown tables, show a markdown table. The example's output format IS the specification.
  5. Keep examples representative, not exhaustive. 3–5 well-chosen examples outperform 20 random ones. Each example should teach Claude something the previous ones didn't.
  6. Annotate the "why" sparingly. If a transformation rule is non-obvious, a brief comment next to the example (e.g., // edge case: empty array returns null) helps Claude understand the intent.

Detailed Explanation

The fundamental challenge of prompt engineering is specification transfer: the mental model in your head must be translated into instructions Claude can execute reliably. Natural language is inherently ambiguous — the phrase "extract the date" could mean extract as ISO 8601, as a Unix timestamp, as a human-readable string, or as separate year/month/day fields. Concrete examples resolve this ambiguity completely.

How Claude processes examples: When Claude encounters input/output pairs in a prompt, it performs in-context learning — treating the examples as a form of implicit instruction. Each pair constrains the output space. The model identifies structural patterns (format, field names, transformations applied) and behavioral patterns (how edge cases are handled, what is omitted, what is added). With 3+ examples, Claude can reliably generalize to unseen inputs of similar structure.

The Example Selection Strategy: Think of examples as a spanning set for your input space. Each example should cover a distinct region:

  • Base case — the simplest, most typical input.
  • Variation case — a different structure within the same family (e.g., different number of fields).
  • Edge case — boundary conditions: empty input, missing fields, unexpected types.
  • Negative case (optional) — what the transformation should NOT do, or how to handle invalid input.

Example placement: In Claude's API, examples work best when placed inside the system prompt or early in the user message, using clear delimiters (XML tags like <example>, or markdown headers). Placing them after the task instruction but before the actual input creates a natural "here's the pattern → now apply it" flow.

Concrete Examples

❌ Before: Vague Instruction (Prone to Drift)

# Prompt (vague)
"""
Extract dates from the text and format them nicely.
"""

# Input
"The meeting is on 3/15/2026 and the deadline is March 20th."

# Possible outputs (all "valid" interpretations):
# → "March 15, 2026 and March 20, 2026"
# → "2026-03-15, 2026-03-20"
# → ["3/15/2026", "March 20th"]
# → {"dates": ["2026-03-15T00:00:00Z", ...]}

✅ After: Example-Driven Specification (Unambiguous)

# Prompt with concrete examples
"""
Extract all dates from the text. Return a JSON array of objects.

<example>
Input: "Meeting on 1/5/2026, review by Jan 12."
Output: [
  {"original": "1/5/2026", "iso": "2026-01-05", "display": "January 5, 2026"},
  {"original": "Jan 12", "iso": "2026-01-12", "display": "January 12, 2026"}
]
</example>

<example>
Input: "No dates here, just a regular sentence."
Output: []
</example>

<example>
Input: "Fiscal year ends 12/31."
Output: [
  {"original": "12/31", "iso": null, "display": "December 31 (year unknown)"}
]
</example>

Now extract dates from the following text:
"""

Notice how the three examples cover: (1) a base case with two dates in different formats, (2) the empty-input edge case, and (3) an ambiguous year situation. Claude now has an unambiguous specification for format, structure, and edge case handling.

💡 Tips & Tricks — 16.1

Mnemonic → "BVEN" — Base, Variation, Edge, Negative. Pick one example from each category for optimal coverage with minimal tokens.

Use XML delimiters: Wrapping examples in <example> tags makes them structurally distinct from instructions and actual input, reducing confusion for Claude.

Copy real data: Use sanitized versions of your actual production data as examples, not synthetic toy inputs. This ensures your examples are representative of real-world complexity.

Format the output yourself: Don't ask Claude to "figure out" the format. Manually write the exact output you expect in each example — this is the specification.

📝 Exam Strategy — Section 16.1

Question Types: Scenario-based ("Which prompt revision best reduces output ambiguity?"), best-practice ("How many examples are recommended for a transformation task?").

Signal Words: "concrete examples", "input/output pairs", "transformation", "specification", "edge case", "few-shot".

Strategy: Prefer answers that include specific examples over those that rely on verbose natural-language instructions. Eliminate choices that provide only abstract descriptions without concrete demonstrations.

Watch For: Distractors suggesting "more examples is always better" — quality and coverage beat quantity. Also beware answers that mix instructions inside examples (polluting the pattern).

⚠️ Common Pitfalls — 16.1
  • Redundant examples: Providing 5 examples that all demonstrate the same basic case wastes tokens without improving coverage.
  • Inconsistent formatting between examples: If example 1 returns {"date": "..."} and example 2 returns {"Date": "..."}, Claude won't know which casing to follow.
  • Omitting edge cases: If you don't show how to handle missing/null fields, Claude will improvise — and its improvisation may not match your expectations.
  • Overfitting to examples: If all examples are about dates, Claude may struggle with a different entity type. Ensure examples represent the actual input variety.

📌 Section 16.1 Summary

  • Concrete input/output examples eliminate ambiguity more effectively than natural-language descriptions.
  • Select 3–5 examples using the BVEN strategy: Base, Variation, Edge, Negative.
  • Format examples exactly as you expect the output — the example IS the specification.
  • Use XML delimiters (<example>) to separate examples from instructions and actual input.
  • Quality of examples matters far more than quantity — each should teach Claude something new.
Section 16.2

Test-Driven Iteration: Write Tests First, Then Iterate

Concept Overview

Borrowing from Test-Driven Development (TDD) in software engineering, test-driven prompt iteration means defining your success criteria as automated checks before you start refining the prompt. You write assertions about what the output must contain, what format it must follow, and what constraints it must satisfy — then iterate on the prompt until all tests pass. This turns subjective "does this look right?" evaluations into objective, repeatable, binary pass/fail signals.

Key Definitions

  • Prompt Test — An automated assertion that evaluates Claude's output against expected criteria (structural, semantic, or exact-match).
  • Test Suite — A collection of prompt tests covering multiple input scenarios and evaluation dimensions.
  • Red-Green-Refine Cycle — (1) RED: A test fails against the current prompt's output. (2) GREEN: Refine the prompt until the test passes. (3) REFINE: Generalize the fix so it works across all cases without regressing.
  • Regression — When a prompt change that fixes one test case breaks a previously passing case.
  • Evaluation Function (Eval) — A programmatic function that scores or validates Claude's output, ranging from simple string checks to LLM-based grading.
  • Golden Dataset — A curated set of (input, expected_output) pairs used as the ground truth for testing.
  • Eval Harness — The infrastructure that runs prompts against test cases and reports results systematically.

Core Principles

  1. Define "done" before you start. Write the tests first. If you can't articulate what good output looks like as a test, you don't yet understand your requirements well enough.
  2. Automated over manual. Every prompt change should be validated against the full test suite automatically. Manual spot-checking misses regressions.
  3. Test at multiple granularities. Combine exact-match tests (format, field names), structural tests (JSON validity, required keys), semantic tests (LLM-graded relevance), and constraint tests (word count, language, tone).
  4. One fix per iteration. Change one thing in the prompt per cycle. If you change multiple things and a test flips, you won't know which change caused it.
  5. Track every version. Keep a prompt changelog: what changed, which test it targeted, and whether regressions occurred. This history is invaluable for debugging.
  6. Regressions are information. When a new fix breaks an old test, it reveals a tension in your requirements or an over-specific patch. Address the root cause, not the symptom.

Detailed Explanation

Prompt engineering without tests is like coding without a compiler — you're flying blind. The Red-Green-Refine cycle provides the discipline:

Phase 1: RED — Write failing tests. Before touching the prompt, define what success looks like. This could be:

  • Format assertions: assert output.startswith("{") — Is it valid JSON?
  • Key presence: assert "summary" in json.loads(output) — Does it have the required field?
  • Content constraints: assert len(output.split()) < 200 — Is it within the word limit?
  • Semantic checks: Use a second Claude call to grade: "Does this output correctly answer the question? Return YES or NO."
  • Negative assertions: assert "I cannot" not in output — Does it avoid refusal patterns?

Phase 2: GREEN — Refine the prompt. Make a targeted change to the prompt aimed at fixing exactly one failing test. Common refinement moves:

  • Adding a concrete example that demonstrates the expected behavior.
  • Adding an explicit constraint: "Your response must be valid JSON."
  • Reordering instructions to put the most critical requirement first.
  • Adding a negative instruction: "Do NOT include explanations outside the JSON."

Phase 3: REFINE — Check for regressions and generalize. Run the full test suite. If the fix is too narrow (works for one case but breaks others), look for a more general solution. Often this means replacing a specific patch with a broader principle or a well-chosen example.

Types of evaluation functions:

Eval Type Method Best For Limitation
Exact Match output == expected Deterministic formats, codes Brittle to whitespace/ordering
Structural JSON schema validation, regex Format compliance Doesn't check content quality
Contains/Excludes Substring checks Required/forbidden phrases Coarse — misses paraphrases
LLM-Graded Second LLM evaluates output Semantic accuracy, tone, quality Non-deterministic, adds latency & cost
Human Rubric Manual scoring on a rubric Subjective quality, final sign-off Doesn't scale; inter-rater variance

Concrete Examples

Building a Prompt Test Suite (Python)

import json

# Golden test cases: (input, assertions)
test_cases = [
    {
        "input": "Summarize: AI is transforming healthcare...",
        "assertions": [
            lambda out: len(out.split()) < 100,         # concise
            lambda out: "healthcare" in out.lower(),     # on-topic
            lambda out: not out.startswith("I "),       # no first-person
        ]
    },
    {
        "input": "Summarize: ",                         # edge: empty
        "assertions": [
            lambda out: "insufficient" in out.lower()
                        or "no content" in out.lower(),
        ]
    },
]

# Run tests (pseudo-code)
for i, case in enumerate(test_cases):
    output = call_claude(prompt_template, case["input"])
    for j, assertion in enumerate(case["assertions"]):
        result = assertion(output)
        print(f"Case {i}, Assert {j}: {'✅ PASS' if result else '❌ FAIL'}")

💡 Tips & Tricks — 16.2

Mnemonic → "RED-GREEN-REFINE"
RED = Test fails (expected output not met)
GREEN = Test passes after prompt refinement
REFINE = Generalize the fix across all cases

Start with 5 tests. You don't need 100 tests on day one. Start with 5 that cover format, content, edge cases, constraints, and a negative case. Expand as you discover new failure modes.

Use temperature 0 for testing. Set temperature=0 during test runs to maximize reproducibility. Non-determinism at higher temperatures makes test results unreliable.

Version your prompts alongside tests. Store them in the same repository or file. A prompt without its test suite is undocumented; a test suite without its prompt is useless.

📝 Exam Strategy — Section 16.2

Question Types: Process-ordering ("What is the correct first step in iterative refinement?"), best-practice ("Which evaluation method is most appropriate for…?"), scenario-based ("A prompt passes 4/5 tests after a change. What should the engineer do next?").

Signal Words: "test-driven", "regression", "evaluation", "assertion", "iterate", "validate".

Strategy: The correct answer almost always involves (1) running the full test suite after every change, and (2) changing only one thing at a time. Eliminate answers that suggest skipping regression checks or making multiple simultaneous changes.

Watch For: Distractors that confuse "automated testing of prompts" with "asking Claude to test itself." Self-evaluation is a separate technique — TDD here means external, programmatic validation.

⚠️ Common Pitfalls — 16.2
  • Skipping the red phase: Writing the prompt first, then tests, biases your tests toward what the prompt already does — not what it should do.
  • Testing only the happy path: If all test cases are "normal" inputs, you'll miss failures on edge cases that appear in production.
  • Over-reliance on exact match: LLM outputs are non-deterministic; tests that require exact string equality will be flaky. Use structural/semantic checks instead.
  • Ignoring regressions: "It's fine, the other tests still mostly pass" is how production failures start. Every regression demands investigation.
  • Multiple changes per iteration: If you change the system prompt, add an example, AND adjust temperature in one step, you can't isolate which change helped or hurt.

📌 Section 16.2 Summary

  • Define success criteria as automated tests before writing or refining the prompt.
  • Follow the Red-Green-Refine cycle: fail → fix → regression check → generalize.
  • Use multiple evaluation types: exact match, structural, semantic (LLM-graded), and constraint-based.
  • Change only one thing per iteration and run the full test suite after every change.
  • Maintain a prompt changelog to track what changed, why, and what it affected.
Section 16.3

The Interview Pattern: Having Claude Surface Considerations

Concept Overview

The Interview Pattern inverts the typical human→Claude instruction flow. Instead of specifying everything upfront (which risks missing requirements), you ask Claude to interview you — asking clarifying questions, surfacing edge cases, and identifying considerations you may not have thought of. This two-phase approach (discovery → execution) produces higher-quality outcomes because the requirements are more complete before Claude begins the actual task.

Key Definitions

  • Interview Pattern — A prompting technique where Claude is instructed to ask the user clarifying questions before executing the task, ensuring requirement completeness.
  • Discovery Phase — The first phase where Claude asks questions and surfaces considerations. No task execution occurs.
  • Execution Phase — The second phase where Claude performs the task using the answers gathered during discovery.
  • Requirement Elicitation — The process of drawing out implicit requirements that the user hasn't stated.
  • Consideration Surfacing — Claude proactively identifies trade-offs, edge cases, assumptions, and dependencies the user should decide on.
  • Bounded Interview — Constraining the discovery phase to a specific number of questions or categories to prevent endless back-and-forth.

Core Principles

  1. You don't know what you don't know. The interview pattern's power is in surfacing unknown unknowns — requirements you wouldn't have thought to specify.
  2. Separate discovery from execution. Never let Claude start executing while still gathering requirements. The phases must be distinct.
  3. Bound the interview. Without constraints, Claude may ask dozens of questions. Specify: "Ask me up to 5 critical questions before proceeding" or "Focus your questions on [specific dimension]."
  4. Claude's questions are diagnostic. The quality of Claude's questions reveals how well it understands the task. Poor questions signal a poor task description.
  5. Answers become specifications. Your answers to Claude's questions should be fed back into the prompt as explicit constraints for the execution phase.
  6. Use for complex, ambiguous, or high-stakes tasks. Don't use the interview pattern for simple, well-defined tasks — it adds unnecessary latency.

Detailed Explanation

The interview pattern addresses the cold-start specification problem: when you begin a complex task, you often don't know all the requirements upfront. In traditional prompt engineering, this leads to a lengthy back-and-forth cycle of "generate → review → correct → regenerate." The interview pattern front-loads this discovery.

How to implement the interview pattern:

Step 1 — Frame the task and trigger the interview: 

"I want to build an API rate limiter. Before you write any code,
ask me the questions you'd need answered to design this correctly.
Limit yourself to your 5 most important questions."

Step 2 — Claude surfaces considerations: Claude might ask about request volume, rate limit algorithm (token bucket vs. sliding window), scope (per-user vs. global), storage backend, and how to handle bursting. These are the exact design decisions that, if unspecified, would lead to wrong assumptions.

Step 3 — You answer, providing specifications: Your answers become the requirement document. Claude now has explicit, user-confirmed constraints.

Step 4 — Claude executes with full context: With the interview answers in context, Claude produces output that is aligned with your actual needs, not its default assumptions.

Variants of the pattern:

Variant Description When to Use
Open Interview Claude asks any questions it deems relevant Exploratory tasks, brainstorming
Bounded Interview Fixed number of questions (e.g., "ask up to 5") Time-sensitive tasks, clear scope
Categorized Interview Questions organized by dimension (technical, business, UX) Multi-stakeholder projects
Assumption-Check Claude lists its assumptions and asks you to confirm/correct When you have a partial spec already
Devil's Advocate Claude challenges your stated requirements and surfaces risks High-stakes decisions, architecture review

Concrete Examples

Example: Bounded Interview for a Data Pipeline

# User prompt:
"""
I need to build a data pipeline that processes customer feedback.
Before designing anything, ask me up to 5 critical questions that
would affect the architecture. Format each as:

Q[n]: [question]
Why it matters: [brief explanation]
Default assumption if unanswered: [what you'd assume]
"""

# Claude's response:
"""
Q1: What is the expected volume of feedback per day?
Why it matters: Determines batch vs. stream processing architecture.
Default assumption if unanswered: <1000/day → batch is sufficient.

Q2: Do you need real-time sentiment scores or is daily aggregation OK?
Why it matters: Real-time requires streaming + low-latency ML inference.
Default assumption if unanswered: Daily aggregation is acceptable.

Q3: What downstream systems consume the processed data?
Why it matters: Affects output format (JSON API, database writes, S3 parquet).
Default assumption if unanswered: Results go to a PostgreSQL database.

Q4: Is PII present in the feedback? Any compliance requirements?
Why it matters: PII handling affects storage, encryption, and data retention.
Default assumption if unanswered: No PII; standard security practices.

Q5: What is your team's infrastructure stack (AWS/GCP/Azure, K8s, etc.)?
Why it matters: Solution should use tools your team can maintain.
Default assumption if unanswered: AWS-based, serverless preferred.
"""

Notice the "Default assumption" field — this is a power technique. It lets the user skip questions where the default is acceptable, while making Claude's assumptions transparent and correctable.

💡 Tips & Tricks — 16.3

Mnemonic → "ASK before ACT" — Always Surface Knowledge before Acting on the Task.

Request "default assumptions": Ask Claude to state what it would assume if you don't answer. This makes implicit assumptions explicit and correctable.

Combine with 16.1: After the interview phase, ask Claude to produce example input/output pairs based on your answers — this validates that Claude understood your requirements correctly before execution begins.

Use for system prompt design: The interview pattern is especially powerful when designing system prompts for agents or chatbots — Claude can surface all the behavioral edge cases you need to specify.

📝 Exam Strategy — Section 16.3

Question Types: Scenario-based ("A developer needs to build a complex workflow but has vague requirements. What technique should they use?"), comparison ("How does the interview pattern differ from iterating on outputs?").

Signal Words: "clarifying questions", "surface considerations", "requirements gathering", "unknown unknowns", "before starting".

Strategy: When the scenario involves ambiguity, incomplete requirements, or a complex task where the user doesn't know all the constraints — the interview pattern is almost certainly the correct answer. Eliminate answers that jump straight to execution.

Watch For: Distractors suggesting "ask Claude to figure it out on its own" — the interview pattern is collaborative (Claude asks, human answers), not autonomous.

⚠️ Common Pitfalls — 16.3
  • Unbounded interviews: Without a limit, Claude may ask 15+ questions, exhausting the user. Always cap it (e.g., "up to 5 questions").
  • Mixing phases: If Claude starts executing partway through the interview, the output will be based on incomplete information. Enforce phase separation.
  • Using it for simple tasks: Asking Claude to interview you about "What's 2+2?" is overhead without value. Reserve the pattern for genuinely complex/ambiguous tasks.
  • Ignoring the answers: If you collect interview answers but don't feed them back explicitly into the execution prompt, Claude may not use them consistently.

📌 Section 16.3 Summary

  • The interview pattern front-loads requirement discovery by having Claude ask clarifying questions before executing.
  • Separate Discovery Phase (questions) from Execution Phase (task work) — never mix them.
  • Bound the interview: specify the number of questions or focus categories.
  • Ask Claude to state default assumptions — makes implicit decisions transparent and correctable.
  • Best suited for complex, ambiguous, or high-stakes tasks where missing requirements would be costly.
Section 16.4

Single Message vs Sequential Fixes: Interacting vs Independent Problems

Concept Overview

When Claude's output has multiple issues, you face a choice: fix them all in one message (batch), or fix them one at a time (sequential). The correct strategy depends on whether the problems are independent (fixing one doesn't affect the others) or interacting (fixing one changes the context for the others). Choosing the wrong strategy wastes tokens, introduces confusion, or causes cascading regressions.

Key Definitions

  • Independent Problems — Issues that exist in isolation; fixing one has no effect on the others. Example: a formatting error in section A and a factual error in section B.
  • Interacting Problems — Issues where fixing one changes the context, content, or validity of another. Example: restructuring the document outline (fix 1) affects the content of every section (fix 2+).
  • Batch Fix — Sending all corrections in a single message. Efficient for independent problems.
  • Sequential Fix — Sending one correction at a time, waiting for the result before sending the next. Necessary for interacting problems.
  • Fix Ordering — The deliberate sequencing of fixes from structural/high-level to granular/low-level to prevent rework.
  • Cascading Regression — When a fix to one issue inadvertently creates or changes another issue downstream.

Core Principles

  1. Classify before fixing. Before sending corrections, categorize each issue as independent or interacting. This determines your strategy.
  2. Independent problems → batch. If issues don't interact, fix them all in one message. This is token-efficient and faster.
  3. Interacting problems → sequential, high-level first. Fix structural/architectural issues before content/detail issues. Each fix changes the landscape for subsequent fixes.
  4. When in doubt, go sequential. Sequential fixes are always safe (if slower). Batching interacting problems can cause Claude to resolve conflicts unpredictably.
  5. Be specific about which text to change. Whether batching or sequencing, reference the exact location of each issue (line number, section header, quoted text). Vague instructions like "fix the error in the middle" invite mistakes.
  6. The fix hierarchy: Structure → Logic → Content → Style. Always fix in this order. Structural changes (reorganization, adding/removing sections) invalidate lower-level fixes.

Detailed Explanation

This section addresses a practical problem every prompt engineer faces: multi-issue correction. After Claude generates a response, it's rare that only one thing needs fixing. The question is: how do you communicate multiple corrections effectively?

The Dependency Test: For each pair of issues (A, B), ask: "If I fix A, does that change what B's fix looks like?" If yes, they interact — sequence them. If no, they're independent — batch them.

Concrete Examples

✅ Independent Issues → Batch Fix (Correct)

# All three issues are independent — batch is efficient
"""
Please make these three corrections to the report:

1. In the Executive Summary (paragraph 2), change "Q3 2025" to "Q3 2026"
2. In Section 3.1, the table header says "Reveue" — fix to "Revenue"
3. In the Conclusion, add a bullet point: "• Expand to APAC in Q1 2027"

All other content should remain unchanged.
"""

✅ Interacting Issues → Sequential Fix (Correct)

# Message 1: Structural fix first
"""
Reorganize the report: merge Sections 2 and 3 into a single
"Market Analysis" section, and move Section 5 to come before
the new Section 3. Keep all existing content.
"""

# Wait for output...

# Message 2: Content fix (depends on new structure)
"""
Good. Now in the new "Market Analysis" section, the competitive
landscape data is outdated. Replace it with: [new data].
Also update all section cross-references to match the new numbering.
"""

# Wait for output...

# Message 3: Style fix (lowest priority)
"""
Finally, change the tone of the Executive Summary from academic
to conversational. Use shorter sentences and active voice.
"""

❌ Anti-Pattern: Batching Interacting Issues

# WRONG — these issues interact, but are batched
"""
1. Restructure the document into 4 sections instead of 6
2. Rewrite the introduction to reference the new structure
3. Update all cross-references
4. Add a new conclusion summarizing the new sections
"""
# Problem: Claude must resolve #1 before it can do #2-#4,
# but it's processing them "simultaneously" in one pass.
# Result: inconsistent cross-references, wrong section numbers.
💡 Tips & Tricks — 16.4

Mnemonic → "SLCS" (Structure → Logic → Content → Style) — fix in this order whenever issues interact.

The "Pair Test": For every pair of fixes, ask: "If I do A, does B change?" If yes → sequential. If no → batchable. This is a O(n²) check, but with typical 3-5 issues, it takes seconds.

Quote the exact text: Instead of "fix the error in paragraph 3", say Change "the company's reveue" to "the company's revenue" in paragraph 3. Precision prevents misapplied corrections.

End with "All other content should remain unchanged": This anchoring instruction prevents Claude from making unrequested changes while applying your fixes.

📝 Exam Strategy — Section 16.4

Question Types: Scenario-based ("An output has three issues: a structural reorganization, a factual correction, and a typo. What is the best fix strategy?"), classification ("Which of these issue pairs are independent?").

Signal Words: "single message", "sequential", "interacting", "independent", "batch", "fix order", "dependency".

Strategy: Look for the dependency relationship between the issues described. If any fix changes the context for another fix, the answer should involve sequential processing. Structural fixes always come first.

Watch For: Distractors suggesting "always fix one at a time" or "always batch for efficiency." The correct answer is context-dependent — it depends on whether problems interact.

⚠️ Common Pitfalls — 16.4
  • Defaulting to batch for everything: Token-efficient but risky when issues interact — causes inconsistencies and cascading errors.
  • Defaulting to sequential for everything: Safe but wasteful when issues are independent — costs unnecessary API calls and latency.
  • Wrong fix ordering: Fixing style before structure means the style fix gets overwritten. Always fix top-down: structure → logic → content → style.
  • Vague references: "Fix the second issue" is ambiguous when the document has changed. Always quote specific text or use section identifiers.

📌 Section 16.4 Summary

  • Classify issues as independent (fix doesn't affect others) or interacting (fix changes context for others).
  • Independent problems → batch fix in a single message. Interacting problems → sequential fix.
  • Follow the SLCS hierarchy: Structure → Logic → Content → Style.
  • Use the Pair Test ("Does fixing A change B?") to classify dependencies.
  • Always reference fixes with exact text quotes or section identifiers, not vague descriptions.
Section 16.5

Hands-On: Applying Iterative Refinement

Concept Overview

Section 16.5 is the practical synthesis of all preceding patterns. It walks through an end-to-end iterative refinement workflow: starting from a vague task, using the interview pattern to clarify requirements, encoding those requirements as concrete examples, building a test suite, and applying the correct fix strategy (batch vs. sequential) as you converge on a production-quality prompt. This section transforms theoretical knowledge into a repeatable, practical methodology.

Key Definitions

  • Iterative Refinement Workflow — The full end-to-end process: Interview → Specify → Test → Refine → Validate → Ship.
  • Convergence — The process of each iteration getting closer to the desired output, measured by test pass rate.
  • Prompt Maturity Levels — The stages a prompt goes through: Draft → Tested → Refined → Production → Monitored.
  • Refinement Velocity — How quickly each iteration improves the test pass rate. Declining velocity signals diminishing returns or a fundamentally misaligned approach.
  • Production Readiness — A prompt that passes all tests, handles edge cases, and has been validated against real-world input variety.

Core Principles

  1. The workflow is sequential, not optional. Skipping steps (e.g., jumping to testing without examples, or to execution without interviewing) degrades quality predictably.
  2. Each pattern feeds the next. Interview answers become example pairs (16.3 → 16.1). Example pairs become test assertions (16.1 → 16.2). Test failures determine fix strategy (16.2 → 16.4).
  3. Measure convergence. Track your test pass rate across iterations. If it plateaus or regresses, step back and re-examine your approach — don't keep patching.
  4. Know when to stop. 100% test pass on well-chosen tests is "done." Over-refining past this point is wasted effort. Define your acceptance threshold upfront.
  5. Document the journey. The prompt changelog, test suite, and interview notes are as valuable as the final prompt — they're your institutional knowledge for maintenance and debugging.

Detailed Explanation

The hands-on workflow integrates all four preceding techniques into a single, disciplined methodology. Here is the complete process:

The 6-Step Iterative Refinement Workflow

2. Specify Examples (16.1) Encode requirements as concrete input/output examples 3–5 example pairs (BVEN)
3. Test TDD (16.2) Write automated assertions based on examples and requirements Test suite (5–10 assertions)
4. Iterate Red-Green-Refine (16.2) Run tests, fix failures one at a time, check for regressions Refined prompt (versioned)
5. Fix Fix Strategy (16.4) Classify remaining issues; batch or sequence fixes appropriately Corrected output

💡 Tips & Tricks — 16.5

Mnemonic → "DSTIFV" (Discover → Specify → Test → Iterate → Fix → Validate) — the 6-step workflow in order.

Time-box your iterations. Set a limit: "If I can't reach 90% test pass in 5 iterations, I'll reconsider my approach." Infinite refinement loops are a real trap.

Start with the interview pattern for new tasks. Even if you think you know the requirements, Claude will almost always surface something you missed. The 5 minutes of interviewing saves 30 minutes of debugging.

Reuse test suites across prompt versions. When you update a prompt for a new feature, your existing tests become your regression safety net.

The 80/20 rule applies. The first 3 iterations typically fix 80% of issues. The remaining 20% often requires rethinking the approach, not just patching the prompt.

📝 Exam Strategy — Section 16.5

Question Types: Process-ordering ("What is the correct sequence of steps?"), scenario-based ("A prompt passes 80% of tests but convergence has stalled. What should the engineer do?"), synthesis ("Which combination of patterns is most appropriate for this scenario?").

Signal Words: "workflow", "end-to-end", "combine", "apply", "production-ready", "maturity".

Strategy: Questions about 16.5 test your ability to orchestrate all patterns together. The correct answer will usually involve the correct ORDERING of techniques (interview before examples, examples before tests, tests before refinement). Eliminate answers that skip steps or reverse the order.

Watch For: Distractors that suggest starting with coding/execution before discovery, or testing after deployment. The workflow is always: understand → specify → test → iterate → ship.

⚠️ Common Pitfalls — 16.5
  • Skipping the interview: Jumping straight to examples without discovering requirements leads to incomplete specifications.
  • Writing tests after the prompt works: This creates tests that match the prompt's current behavior, not the desired behavior — it's a false safety net.
  • Infinite refinement: If test pass rate stalls after 5+ iterations, the approach may be wrong. Step back and reconsider the task decomposition or model choice.
  • Not versioning: Without a changelog, you can't revert when a "fix" makes things worse. Every prompt change should be a trackable version.
  • Treating the prompt as final: Production prompts need monitoring. Real-world input distribution shifts over time — re-validate periodically.

📌 Section 16.5 Summary

  • The full workflow is Discover → Specify → Test → Iterate → Fix → Validate — in that order.
  • Each pattern feeds the next: interviews produce requirements, requirements become examples, examples become tests, tests drive refinement.
  • Track convergence (test pass rate over iterations); stalling signals the need to rethink, not patch.
  • A production-ready prompt includes: the prompt itself, a test suite, example pairs, and a changelog.
  • The Prompt Maturity Model: Draft → Tested → Refined → Production → Monitored.
