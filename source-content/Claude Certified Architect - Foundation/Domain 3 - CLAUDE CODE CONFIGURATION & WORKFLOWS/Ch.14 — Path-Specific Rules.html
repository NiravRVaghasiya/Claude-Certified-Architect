14.1 — .claude/rules/ with YAML Frontmatter Path Scoping

Concept Summary

The .claude/rules/ directory is a modular, first-class instruction system in Claude Code. Instead of cramming every convention into a single monolithic CLAUDE.md, you split instructions into focused .md files inside this directory. Claude Code recursively discovers every .md file in .claude/rules/ — subdirectories are supported for organization. Each rule file optionally includes YAML frontmatter with a paths: field to scope that rule to specific file patterns.

Rules without paths: frontmatter are global — they load at the start of every session with the same high priority as CLAUDE.md. Rules with paths: are path-scoped — they only enter the context window when Claude touches a file matching one of the declared glob patterns. This design is a form of progressive disclosure: domain-specific instructions cost zero tokens until they become relevant.

Key Terminology

TermDefinition
Global RuleA rule file with no paths: frontmatter. Loads unconditionally at session start, same priority as CLAUDE.md.
Path-Scoped RuleA rule file with a paths: field in YAML frontmatter. Loads only when Claude reads/writes a file matching the declared globs.
Rule HierarchyThree priority tiers: Enterprise → User → Project. Higher tiers override lower when rules conflict.
YAML FrontmatterA metadata block delimited by --- at the top of a Markdown file, parsed as YAML. Used to declare paths: for scoping.
Progressive DisclosureDesign pattern: load only what is relevant, only when it is relevant. Saves context tokens and reduces noise.
/memoryInteractive Claude Code command that lists all loaded CLAUDE.md files and rules. The primary debugging tool for rule loading.

Rule Hierarchy — Priority Order

 Priority          Location                       Scope
 ────────          ────────                       ─────
  1 (highest)      ~/.claude/enterprise/rules/     Organization-level standards
  2                ~/.claude/rules/                Personal defaults (all projects)
  3 (lowest)       .claude/rules/                  Project-specific patterns
Higher-priority rules override lower-priority ones when they conflict

Directory Structure & Discovery

your-project/
├── .claude/
│   ├── CLAUDE.md              ← main project instructions (always loaded)
│   └── rules/
│       ├── code-style.md      ← global rule (no paths:) — loads every session
│       ├── testing.md         ← global rule (no paths:) — loads every session
│       ├── INDEX.txt          ← human navigation only — NOT auto-loaded
│       ├── api/
│       │   └── endpoints.md   ← path-scoped (paths: "src/api/**/*.ts")
│       ├── database/
│       │   └── patterns.md    ← path-scoped (paths: "src/database/**")
│       └── quality/
│           └── standards.md   ← global rule — loads every session
Claude Code recursively discovers all .md files. Only .md files are loaded — .txt, .json, etc. are ignored.

Discovery rules:

  • Only .md files are auto-loaded. All other extensions are ignored.
  • Subdirectories are scanned recursively — organize by domain freely.
  • Use INDEX.txt (not README.md) for human-readable indexes — README.md would be auto-loaded and waste context tokens.
  • Symlinks are supported and resolved. Circular symlinks are detected gracefully.

YAML Frontmatter Format

The paths: key accepts glob patterns. The body after the closing --- is your rule in Markdown.

✅ YAML Array Format (standard, widely documented)
---
paths:
  - "src/api/**/*.ts"
  - "src/api/**/*.js"
---

# API Development Rules

- Validate all inputs with Zod schemas
- Return consistent error shapes: { error: string, code: number }
- Include OpenAPI doc comments on every handler
✅ Single Glob String Format
---
paths: src/api/**/*.ts
---

# API Rules
- Every endpoint validates its input.
⚠️ Watch Out — CSV String Format Discrepancy

One community guide (ytrofr/claude-code-guide) reports that YAML arrays are silently ignored in some Claude Code versions due to a parser bug (issues #13905, #17204), and recommends a comma-separated string format instead:

# CSV string format — reported as workaround for parser bug
---
paths: "src/**/*.js, src/**/*.ts"
---

However, multiple official and authoritative sources (Anthropic blog, ClaudeFast, bswen.com, groff.dev) document the YAML array format as working correctly. This discrepancy may reflect a version-specific bug that was fixed.

Exam strategy: Know both formats exist. If a question asks about the "correct" format, the YAML array is the standard documented format. If a question specifically mentions parser compatibility issues, the CSV string is the fallback.

💡 Tips & Tricks — 14.1
  • Keep each rule focused — one domain per file. A monolithic everything.md forces the whole file into context when any part matches.
  • Use INDEX.txt instead of README.md for human navigation. A README.md is auto-loaded and wastes tokens.
  • Rule budget target: Keep total auto-loaded rules under ~15k tokens. Above 20k, you likely have duplication or stale evidence.
  • Don't duplicate across levels. If a rule exists at both ~/.claude/rules/ and .claude/rules/, it loads twice. Detect with diff and keep only one copy.
  • Trim evidence out of rules. Rules should contain the rule, not the history of why it was created. Move evidence and dated narratives to memory banks.
🎯 Exam Strategy — 14.1
  • Priority order: Enterprise > User > Project. Expect questions that test whether user-level or project-level rules take precedence (user-level loads first, but project rules have higher priority).
  • What gets loaded: Only .md files. A question might test whether .yaml, .txt, or .json files in .claude/rules/ are auto-loaded (they are NOT).
  • "No paths" ≠ "not loaded": A rule with no frontmatter at all is always loaded. Only the presence of paths: makes a rule conditional.
  • Debugging: The /memory command is the canonical way to verify loaded rules — expect this as a correct answer in troubleshooting questions.

14.2 — Glob Patterns for File-Type Targeting

Concept Summary

Glob patterns are the path-matching language used in the paths: frontmatter to target specific files or directories. Claude Code uses standard glob syntax with support for * (single-level wildcard), ** (recursive wildcard), and {...} (brace expansion). Mastering glob patterns is essential for writing rules that are neither too broad (wasting tokens) nor too narrow (missing files).

Paths are relative to the project root. When Claude reads or writes a file matching a declared pattern, the associated rule loads into context. Multiple patterns can be listed under one paths: block, and all are OR-combined.

Glob Syntax Reference

Pattern ElementMeaningExampleMatches
*Any characters within one directory level (no /)*.tsapp.ts at root level only
**Any number of directories (recursive descent)**/*.tssrc/api/user.ts, lib/utils.ts
?Any single characterfile?.tsfile1.ts, fileA.ts
{a,b}Brace expansion — matches any alternative**/*.{ts,tsx}app.ts, Button.tsx
[abc]Character classfile[123].tsfile1.ts, file2.ts

Common Patterns for Exam Scenarios

PatternWhat It MatchesCommon Use Case
**/*.tsAll .ts files at any depthTypeScript conventions
src/**/*All files under src/ recursivelySource code rules
src/components/*.tsxOnly direct children of components/Top-level component rules
**/migrations/**/*.sqlSQL files in any migrations/ folderDatabase migration safety
**/*.test.tsAll TypeScript test filesTesting conventions
**/*.{ts,tsx}Both .ts and .tsxCombined TypeScript/React rules
{src,lib}/**/*.ts.ts files in src/ or lib/Multi-root source rules
Dockerfile, *.ymlDockerfiles and YAML files at rootDeployment safety
terraform/**/*All files under terraform/Infrastructure-as-code rules
**/api/**/*.tsTypeScript in any nested api/ dirAPI conventions across apps

Critical Distinction: * vs **

project/
├── main.tf                    ← terraform/*   : ✗ NO MATCH (wrong dir)
├── terraform/                     terraform/*   : matches files HERE only
│   ├── main.tf                ← terraform/*   : ✅ MATCH
│   ├── variables.tf           ← terraform/*   : ✅ MATCH
│   └── modules/
│       ├── vpc/
│       │   └── main.tf        ← terraform/*   : ✗ NO MATCH (too deep)
│       └── ecs/                   terraform/**/*: ✅ MATCH (recursive)
│           └── service.tf     ← terraform/**/*: ✅ MATCH (recursive)

  terraform/*     →  only direct children of terraform/
  terraform/**/*  →  everything under terraform/ at ANY depth
The * vs ** distinction is the #1 glob pattern exam trap

Multiple Patterns in One Rule

List multiple globs to broaden a single rule's scope:

---
paths:
  - "**/*.schema.ts"
  - "**/migrations/**"
  - "prisma/**/*"
---

# Database & Schema Rules

- Always include rollback instructions in migrations
- Use snake_case for column names
- Never modify existing migrations after merge

All patterns are OR-combined — if any one matches the current file, the rule loads.

Brace Expansion Deep Dive

# Match both .ts and .tsx files in any directory
paths:
  - "**/*.{ts,tsx}"

# Match files in both src/ and lib/ directories
paths:
  - "{src,lib}/**/*.ts"

# Combine multiple extensions AND directories
paths:
  - "{apps,packages}/*/src/**/*.{ts,tsx,js,jsx}"
🧠 Think About It This Way...

Glob patterns work like a file system filter. Imagine Claude announces: "I'm about to read src/api/users/controller.ts." Claude Code then checks every path-scoped rule's glob patterns. Any rule whose pattern matches that file path gets injected into the context window. If no patterns match, the rule stays dormant and costs zero tokens.

This is why path scoping is a form of token budgeting — you're not just organizing rules, you're deciding when each rule consumes context capacity.

💡 Tips & Tricks — 14.2
  • Always prefer **/*.ext over *.ext for recursive matching. The single * only matches root-level files.
  • Brace expansion lets you avoid duplicating patterns: **/*.{ts,tsx} is cleaner than two separate entries.
  • Don't scope too narrowly: services/api/handlers/payments.py only fires for one file. Scope to services/api/**/* instead.
  • Don't scope too broadly: **/* matches everything — it's the same as no scoping and defeats the purpose.
  • Test your globs mentally: For each pattern, imagine 3 file paths and check — does each match or not?
🎯 Exam Strategy — 14.2
  • Questions on glob patterns almost always test * vs **. "Does terraform/* match terraform/modules/vpc/main.tf?" — No, because * doesn't recurse.
  • Watch for brace expansion questions: "Does {src,lib}/**/*.ts match lib/utils/helper.ts?" — Yes.
  • Multiple patterns are OR-combined. If the question asks "does a file need to match ALL patterns?" the answer is no — any one match suffices.
  • Eliminate answers that confuse directory-scoped matching (CLAUDE.md) with pattern-scoped matching (rules).

14.3 — Path-Specific Rules vs Subdirectory CLAUDE.md Files

Concept Summary

This is the highest-weighted comparison topic in Chapter 14. Path-specific rules (.claude/rules/ with paths:) and subdirectory CLAUDE.md files both scope instructions to specific areas of a codebase, but they use fundamentally different scoping mechanisms. Understanding when to use each — and how they compose together — is critical for the exam and for real-world Claude Code configuration.

The mental model: CLAUDE.md is directory-scoped (loads when Claude works in that directory). .claude/rules/ with paths: is pattern-scoped (loads when Claude touches files matching a glob, regardless of directory). This distinction matters most for cross-cutting concerns like test file conventions, config file rules, or file-type standards that span multiple directories.

Comprehensive Comparison Table

AspectPath-Specific Rules (.claude/rules/)Subdirectory CLAUDE.md
Scope mechanismGlob pattern matching on file pathsDirectory proximity — loads when working in that dir
FormatMarkdown with YAML frontmatter paths:Markdown prose (no frontmatter needed)
LocationCentralized in .claude/rules/Distributed across the project tree
Ideal use caseFile-type targeting across directoriesDirectory-specific architecture context
Cross-cutting?✅ Excels — **/*.test.ts spans all dirs❌ Must duplicate into each directory
Monorepo fit✅ One rule governs pattern across all apps✅ Each app gets its own architecture context
Token costZero until a matching file is touchedLoads when Claude enters the directory
DiscoveryAuto-discovered recursively in .claude/rules/Auto-discovered when Claude enters dir
PrioritySame as CLAUDE.md (high priority)High priority (subdirectory overrides root)
PortabilityClaude Code specificClaude Code specific
NestingFlat (one centralized location with subdirs)Hierarchical (mirrors project structure)

The Decision Tree

Does this instruction apply to...

  ┌─── ALL files in a DIRECTORY, regardless of type?
  │     → Use subdirectory CLAUDE.md
  │     Example: "This app uses NestJS with modular services"
  │
  ├─── A specific FILE TYPE across multiple directories?
  │     → Use path-specific rule with paths:
  │     Example: "All *.controller.ts must use typed decorators"
  │
  ├─── EVERYTHING in the entire project?
  │     → Use root CLAUDE.md or global rule (no paths:)
  │     Example: "Run nx affected:test before committing"
  │
  └─── A specific TASK/PROCEDURE (not always relevant)?
        → Use a Skill (loaded on demand)
        Example: "PR review checklist"
When to use which instruction mechanism

❌ Subdirectory CLAUDE.md Approach

Must duplicate testing rules into every directory containing tests:

src/auth/CLAUDE.md      → "Use AAA pattern..."
src/billing/CLAUDE.md   → "Use AAA pattern..."
lib/utils/CLAUDE.md     → "Use AAA pattern..."
   ↑ 4 copies to maintain = silent drift risk
vs

Composition Pattern — Using Both Together

These mechanisms are additive, not exclusive. The recommended architecture uses both:

project/
├── CLAUDE.md                          ← universal: build commands, orchestration
├── .claude/
│   └── rules/
│       ├── testing.md                 ← pattern-scoped: **/*.test.ts
│       ├── controllers.md             ← pattern-scoped: **/*.controller.ts
│       └── schemas.md                 ← pattern-scoped: **/*.schema.ts
├── services/
│   ├── api/
│   │   ├── CLAUDE.md                  ← directory context: "NestJS, modular services"
│   │   └── src/
│   │       ├── users.controller.ts    ← triggers: controllers.md rule
│   │       └── users.test.ts          ← triggers: testing.md rule
│   └── billing/
│       ├── CLAUDE.md                  ← directory context: "integer cents only"
│       └── src/
│           └── invoice.test.ts        ← triggers: testing.md rule
The three-layer model: CLAUDE.md (directory) + rules (pattern) + skills (on-demand)

When Claude edits services/api/src/users.controller.ts, it loads:

  1. Root CLAUDE.md (universal rules)
  2. services/api/CLAUDE.md (directory context)
  3. .claude/rules/controllers.md (pattern match: **/*.controller.ts)
💡 Tips & Tricks — 14.3
  • Rules are additive. You don't have to restructure existing CLAUDE.md files to start using rules. Just add .claude/rules/ alongside.
  • Sizing guide: Keep each rule under ~250 words. If a convention needs a full page, put the details in a Skill and use the rule as a concise summary with a pointer.
  • If two path-scoped rules both match the same file, both load. Keep rules consistent to avoid contradictions.
  • Use CLAUDE.md for "what is this area?" and rules for "what conventions apply to this file type?"
🎯 Exam Strategy — 14.3
  • The key differentiator on the exam: directory-scoped vs pattern-scoped. If the question involves cross-cutting file types (tests, configs, schemas), the answer is path-specific rules.
  • If the question involves architecture context for a specific app or service, the answer is subdirectory CLAUDE.md.
  • Watch for trick answers that suggest putting procedures in CLAUDE.md — procedures belong in Skills, not CLAUDE.md.
  • Questions may test whether path rules and CLAUDE.md can coexist — yes, they compose additively.

14.4 — Applying Conventions Across File Types Regardless of Location

Concept Summary

This section addresses the monorepo problem: when conventions follow file types rather than directories, traditional directory-scoped instructions break down. In a monorepo with 5 apps and 10+ shared libraries, NestJS controller patterns might span apps/api/, apps/admin/, apps/worker/, and libs/shared/. Duplicating rules across all directories is unmaintainable.

Path-specific rules solve this by using glob patterns that match file types across the entire project tree. This creates a cross-cutting concern layer — conventions that apply based on what the file is, not where the file lives. Combined with the three-layer instruction architecture (CLAUDE.md + rules + skills), this enables scalable, DRY configuration.

The Three-Layer Instruction Architecture

LayerMechanismLoads WhenBest For
1. CLAUDE.md Directory-scoped Markdown Claude works in that directory App-level architecture, build commands, orchestration
2. .claude/rules/ Pattern-scoped (via paths:) Claude touches matching files File-type conventions spanning directories
3. Skills On-demand task procedures Invoked or deemed relevant Multi-step workflows, reference docs

Real-World Monorepo Example

A team with an Nx TypeScript monorepo — 5 apps, 10+ shared libraries — created 7 glob-pattern rules:

Rule FileGlob PatternWhat It Governs
backend-controllers.md**/*.controller.tsRoute ownership, guard patterns, typed decorators
backend-services.md**/*.service.tsTransaction safety, auth context, update patterns
backend-modules.md**/*.module.tsDI encapsulation, provider resolution, .forRoot()
drizzle-schema.md**/*.schema.ts, **/migrations/**Column naming, index conventions, type derivation
react-patterns.mdapps/*/src/**/*.tsx, libs/*/src/**/*.tsxEffect anti-patterns, API calls, permissions
route-definitions.mdlibs/routes/**/*.routes.tsNaming, type sourcing, contract rules
nextjs-pages.md**/page.tsx, **/layout.tsxMetadata, layout components, import aliases

Result: Total context cost when all 7 fire: ~1K tokens. Typical session: only 2-3 activate. All 11 existing CLAUDE.md files remained unchanged — rules are additive.

Design Principles for Cross-Cutting Rules

1. Reference, Don't Duplicate

# .claude/rules/database/patterns.md
---
paths:
  - "src/database/**"
  - "src/sync/**"
  - "scripts/*sync*"
---

# Database Rules

**Full reference**: see `CORE-PATTERNS.md` (authoritative source).

## Quick summary
- Golden rule: always use `employee_id` (never `id`)
- Safety: `SELECT current_database()` before destructive ops
- Validation: `grep -r 'record\.employee\.id' src/`

Duplicating content across rules leads to silent drift: one copy gets updated, the other goes stale.

2. Keep Rules Concise — Point to Skills for Depth

# .claude/rules/api/validation.md (concise — under 250 words)
---
paths:
  - "src/routes/**"
  - "src/controllers/**"
  - "src/services/**"
---

# API Patterns

- Validate inputs with Zod schemas
- Use the standard error envelope: { error, code, details }
- Include OpenAPI doc comments

**Full guide**: load the `api-development` skill for complete procedures.

3. Decision Guide: When to Use paths:

  • Use paths: when the rule is domain-specific — only relevant for certain file types or directories.
  • Omit paths: when the rule applies regardless of which file is being edited (e.g., "never use em dashes in content," "always use single quotes").
  • Use a Skill instead when the instruction is a multi-step procedure that fires occasionally (deployment checklist, PR review workflow).

4. Global Rules (No paths:) — Use Sparingly

Rules without paths: load every session, so they consume tokens unconditionally:

# .claude/rules/global/git-safety.md — no paths, always loads

# Git Safety Rules

- Never force push to main or develop
- Always use conventional commit messages
- Run `nx affected:test` before committing
🧠 Think About It This Way...

Imagine you're an architect deciding where to post construction signs. Some signs belong at the entrance to a specific floor (CLAUDE.md = "This floor is the billing department"). Other signs belong wherever a specific type of work happens, regardless of floor (path-scoped rules = "All electrical work must follow safety code"). And some procedures are in a reference manual on the shelf (Skills = "Full fire evacuation procedure"). The signs by file type follow you around based on what you're doing, not where you are.

💡 Tips & Tricks — 14.4
  • Target ≤250 words per rule file. Each triggered rule adds to context. Brevity is a design constraint, not a limitation.
  • Measure your rule budget: find .claude/rules -name '*.md' -type f | xargs wc -c — convert to tokens (÷4). Stay under 15k tokens total for always-on rules.
  • When multiple rules match the same file, all load. Ensure they don't contradict each other.
  • Existing CLAUDE.md files don't need to change — rules layer on top. Start with one rule, iterate.
🎯 Exam Strategy — 14.4
  • Questions will test whether you understand the three-layer model: CLAUDE.md (directory), rules (pattern), skills (on-demand). Know which layer each type of instruction belongs in.
  • A common distractor: "put testing conventions in root CLAUDE.md." This works but wastes tokens — the best answer is a path-scoped rule.
  • Expect scenario questions: "A monorepo has controllers in 5 different apps. What's the most efficient way to apply controller conventions?" → Single path-scoped rule with **/*.controller.ts.

14.5 — Hands-On: Implementing Path-Specific Rules

Concept Summary

This section provides a complete, step-by-step implementation walkthrough for setting up path-specific rules in a real project. We'll implement a full rule set for a TypeScript monorepo with frontend (React), backend (NestJS), infrastructure (Terraform), and testing concerns.

🔨 Hands-On — Step-by-Step Implementation

Scenario: You're configuring Claude Code for a monorepo with the following structure:

my-monorepo/
├── apps/
│   ├── web/          (React frontend)
│   └── api/          (NestJS backend)
├── libs/
│   ├── shared/       (shared utilities)
│   └── ui/           (component library)
├── terraform/        (infrastructure)
├── prisma/
│   └── migrations/   (database migrations)
└── .claude/          (Claude Code config)

Step 1: Create the Rules Directory

mkdir -p .claude/rules

This is all you need. No configuration file, no imports. Claude Code auto-discovers .md files here.

Step 2: Create a Global Rule (No Path Scoping)

.claude/rules/git-conventions.md
# Git Conventions

- Use conventional commits: `feat:`, `fix:`, `chore:`, `docs:`
- Never force push to `main` or `develop`
- Squash-merge feature branches
- Run `pnpm test:affected` before pushing

No paths: frontmatter → loads every session, same priority as CLAUDE.md.

Step 3: Create Path-Scoped Rules

.claude/rules/react-patterns.md
---
paths:
  - "apps/web/src/**/*.tsx"
  - "libs/ui/src/**/*.tsx"
---

# React Conventions

- Functional components only — no class components
- Extract reusable logic into custom hooks (useXxx naming)
- Memoize expensive computations with useMemo/useCallback
- No business logic in components — delegate to hooks/services
- Use TypeScript strict mode — no `any` types
.claude/rules/nestjs-backend.md
---
paths:
  - "apps/api/src/**/*.ts"
---

# NestJS Backend Rules

- Controllers: thin handlers, delegate to services
- Services: never call external APIs inside a transaction
- Use the request-scoped auth context for permission checks
- Repository methods return domain types, not ORM entities
- All exceptions must extend `BaseAppException`
.claude/rules/terraform-infra.md
---
paths:
  - "terraform/**/*"
---

# Terraform Conventions

- Always use snake_case for resource names
- Require `description` on all variables and outputs
- Use `terraform fmt` formatting (2-space indent)
- Pin provider versions in `required_providers`
- Tag all resources with: Environment, Team, ManagedBy=Terraform
.claude/rules/testing-standards.md
---
paths:
  - "**/*.test.ts"
  - "**/*.spec.ts"
  - "**/__tests__/**"
---

# Testing Standards

- AAA pattern: Arrange → Act → Assert
- One assertion per test when possible
- Mock external dependencies — never call real APIs in tests
- Test naming: `should [action] when [condition]`
- Edge cases: empty inputs, null values, boundary conditions
- Target 80%+ coverage on business logic
.claude/rules/database-migrations.md
---
paths:
  - "prisma/migrations/**/*"
  - "**/*.schema.ts"
---

# Database Migration Safety

- Never modify an existing migration after merge
- Always include rollback instructions
- Add columns as nullable first → populate → add constraints
- Use snake_case for table and column names
- Test migrations on production data copy before deploying

Step 5: Create INDEX.txt (Not README.md!)

.claude/rules/INDEX.txt

Common Mistakes Checklist

⚠️ Common Mistakes — Avoid These
MistakeWhy It FailsFix
Using README.md as an index Auto-loaded, wastes tokens Use INDEX.txt instead
Forgetting --- delimiters YAML frontmatter not parsed Must have --- on line 1 and closing ---
Using *.ts instead of **/*.ts Only matches root-level files Add **/ prefix for recursive matching
Scoping to exact filenames Rule triggers for only one file Scope to directory or file-type pattern
paths: **/* (match everything) Same as no scoping — defeats purpose Either remove paths: or narrow the glob
Duplicating rules across levels Rule loads twice, wastes tokens Keep one copy at the appropriate level
Putting procedures in rules Multi-step procedures waste tokens when always loaded Use Skills for procedures, rules for conventions
Contradictory overlapping rules Both load when file matches both patterns Audit for overlap; keep rules consistent
Placing .json or .yaml in rules/ Only .md files are discovered All rules must be .md files

Question 1
A developer places a rule file at .claude/rules/security.json. What happens?
  1. Claude Code loads it as a JSON rule configuration
  2. Claude Code ignores it — only .md files are discovered
  3. Claude Code throws an error at session start
  4. Claude Code converts it to Markdown and loads it
Show Answer
Answer: B
Claude Code only discovers and loads .md files from .claude/rules/. Files with other extensions (.json, .txt, .yaml) are silently ignored — no error, no conversion.
Question 2
Given this rule file, which files will trigger its loading?
---
paths:
  - "terraform/*"
---
# Terraform Rules
  1. terraform/main.tf, terraform/modules/vpc/main.tf
  2. terraform/main.tf, terraform/variables.tf only
  3. All .tf files anywhere in the project
  4. main.tf at the project root
Show Answer
Answer: B
terraform/* uses a single *, which matches only direct children of terraform/. It does NOT recurse into subdirectories. terraform/modules/vpc/main.tf is nested two levels deep and would require terraform/**/* to match. It also doesn't match root-level files (option D) because the pattern requires the terraform/ prefix.
Question 3
A team has the same rule defined in both ~/.claude/rules/testing.md and .claude/rules/testing.md. What happens?
  1. Only the project-level rule loads (higher priority)
  2. Only the user-level rule loads (loaded first)
  3. Both load — the rule is duplicated in context, wasting tokens
  4. Claude Code merges them into a single rule
Show Answer
Answer: C
Claude Code loads rules from both locations independently. If the same file exists in both ~/.claude/rules/ and .claude/rules/, it loads twice, duplicating content in the context window and wasting tokens. This is the "double-load trap." The fix: delete one copy and keep it at the appropriate level.
Question 4
A path-scoped rule declares paths: ["**/*.test.ts", "**/*.spec.ts"]. Claude is editing src/api/users.service.ts. Does the rule load?
  1. Yes — **/* matches all files
  2. No — the file doesn't end in .test.ts or .spec.ts
  3. Yes — it's a .ts file and the pattern includes *.ts
  4. It depends on whether the file is in a test directory
Show Answer
Answer: B
The glob patterns **/*.test.ts and **/*.spec.ts specifically match files ending in .test.ts or .spec.ts. The file users.service.ts ends in .service.ts, which matches neither pattern. The ** handles directory recursion, but the filename pattern must still match exactly.
Question 5
What is the FIRST step when debugging a rule that doesn't seem to be applying?
  1. Delete and recreate the rule file
  2. Run /memory to check if the rule is in the loaded list
  3. Add the rule content directly to CLAUDE.md
  4. Restart Claude Code with --clear-cache
Show Answer
Answer: B
The /memory command lists every loaded CLAUDE.md and rule file. If the rule isn't in the list, you know it's a loading issue (wrong extension, bad frontmatter, path not matched). If it IS loaded, the issue is with the rule's content being too vague. Always verify state before taking action.
Question 6
In a monorepo with co-located test files, which approach is MOST efficient for applying testing conventions?
  1. Add testing rules to the root CLAUDE.md
  2. Create a CLAUDE.md in every directory containing test files
  3. Create a path-scoped rule in .claude/rules/ with paths: ["**/*.test.ts"]
  4. Create a Skill that loads testing conventions on demand
Show Answer
Answer: C
A path-scoped rule with **/*.test.ts is the most efficient approach. Option A wastes tokens on every session (even when not testing). Option B requires duplication across many directories (maintenance nightmare). Option D requires explicit invocation and might not fire when needed. The path-scoped rule loads automatically when any test file is touched, costs zero tokens otherwise, and has a single source of truth.
Question 7
Which of these is a valid reason to use a subdirectory CLAUDE.md INSTEAD of a path-scoped rule?
  1. The convention applies to a specific file type across multiple directories
  2. The instruction describes the architecture and purpose of a specific app within the monorepo
  3. The convention should only load when matching files are touched
  4. The rule needs to use glob patterns for targeting
Show Answer
Answer: B
Subdirectory CLAUDE.md files are the right choice for directory-scoped architecture context — "This app uses NestJS with modular services" applies to everything in that directory, regardless of file type. Options A, C, and D all describe scenarios where path-scoped rules are more appropriate.
Question 8
What does the glob pattern {src,lib}/**/*.{ts,tsx} match?
  1. Only .ts files in src/ and only .tsx files in lib/
  2. All .ts and .tsx files in both src/ and lib/ at any depth
  3. Only files at the root of src/ and lib/
  4. Files matching the literal string {src,lib} in their path
Show Answer
Answer: B
Brace expansion works on both sides: {src,lib} expands to match either directory, and {ts,tsx} expands to match either extension. The **/ enables recursive matching. So this pattern matches all .ts and .tsx files anywhere under src/ or lib/. Examples: src/api/user.ts ✅, lib/ui/Button.tsx ✅, apps/web/main.ts ❌.

📋 Quick-Reference Cheat Sheet

CHAPTER 14 — PATH-SPECIFIC RULES CHEAT SHEET

═══ RULE HIERARCHY (highest → lowest) ═══
1. ~/.claude/enterprise/rules/ ← org-level (admin-enforced)
2. ~/.claude/rules/ ← user-level (personal defaults)
3. .claude/rules/ ← project-level (highest priority)

═══ LOADING BEHAVIOR ═══
No paths: frontmatter → GLOBAL → loads every session
Has paths: frontmatter → PATH-SCOPED → loads on file match only
Only .md files loaded → .txt/.json/.yaml IGNORED
Recursive discovery → subdirectories scanned automatically

═══ YAML FRONTMATTER FORMAT ═══
---
paths:
- "**/*.ts"
- "**/*.tsx"
---
# Rule content in Markdown below

═══ GLOB PATTERNS ═══
* = one level (no recursion)
** = any depth (recursive)
{a,b} = brace expansion (OR)
? = single character
[abc] = character class

CRITICAL: terraform/* ≠ terraform/**/*
^ direct children ^ all descendants

═══ RULES vs CLAUDE.md vs SKILLS ═══
CLAUDE.md → directory-scoped → architecture context
.claude/rules/ → pattern-scoped → file-type conventions
Skills → on-demand → multi-step procedures

═══ WHEN TO USE WHAT ═══
Convention for a file type → path-scoped rule
Architecture of a directory → subdirectory CLAUDE.md
Universal project command → root CLAUDE.md or global rule
Multi-step procedure → Skill

═══ DEBUGGING ═══
Rule not loading? → /memory ← lists all loaded files
Double loading? → diff ~/.claude/rules/ .claude/rules/
Token budget? → find .claude/rules -name '*.md' | xargs wc -c
Target: <15k tokens total for always-on rules

═══ ANTI-PATTERNS ═══
✗ README.md in rules/ (auto-loads, wastes tokens → use INDEX.txt)
✗ paths: **/* (matches everything = pointless scoping)
✗ Exact filename scope (too narrow, almost never triggers)
✗ Procedures in rules (belongs in Skills, not rules)
✗ Duplicate across levels (loads twice, double token cost)
