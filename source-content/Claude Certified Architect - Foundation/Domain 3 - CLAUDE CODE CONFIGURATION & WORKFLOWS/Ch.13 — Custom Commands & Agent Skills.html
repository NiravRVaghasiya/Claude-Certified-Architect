13.1 — Creating Custom Slash Commands

Concept Overview

Custom slash commands are the simplest extensibility mechanism in Claude Code. A slash command is a Markdown file placed in a recognized commands/ directory; its filename (minus the .md extension) becomes the /command-name you type at the Claude Code prompt. When invoked, Claude receives the file's contents as if you had typed the prompt yourself, enabling you to package repeatable workflows into a single keystroke.

As of mid-2026, custom commands have been merged with skills. A file at .claude/commands/fix-issue.md and a skill at .claude/skills/fix-issue/SKILL.md both create /fix-issue and behave the same way. The commands/ path is the lightweight, single-file shorthand; skills are the full-featured version. Both are valid, and existing commands continue to work.

Key Definitions

  • Slash command — A shortcut typed with a / prefix in Claude Code, executing either a built-in action or user-defined instructions from a Markdown file.
  • Built-in command — A command that ships with Claude Code (e.g., /help, /clear) running fixed internal logic.
  • Bundled skill — A command that ships with Claude Code but runs by handing Claude a skill's instructions (e.g., /code-review, /design).
  • Custom command — A user-authored Markdown file in .claude/commands/ (project) or ~/.claude/commands/ (user) that becomes a /name command.
  • $ARGUMENTS — A placeholder replaced by all text the user types after the command name.
  • $0, $1, $N — Zero-indexed positional argument placeholders. Quoting groups words into a single argument.
  • !`command` — Inline shell execution syntax. The command runs before Claude sees the prompt; output is substituted in place.

How It Works

  1. Author — Create a .md file in a commands/ directory. Add optional YAML frontmatter (description, argument-hint, allowed-tools, etc.) between --- delimiters.
  2. Discover — When you type / in Claude Code, the autocomplete menu shows all available commands (built-in + custom). The description from frontmatter is displayed beside each entry.
  3. Invoke — Type /command-name <args> and press Enter.
  4. Expand — Claude Code replaces $ARGUMENTS with the full input string, $0/$1/etc. with positional args, and !`...` with shell output.
  5. Execute — The rendered Markdown is passed to Claude as a prompt. Claude follows the instructions using the tools available in the session.
  6. Persist — The rendered content remains in the conversation for the rest of the session. Re-invoking an identical command adds a short "already loaded" note rather than a duplicate.
my-project/ ├── .claude/ │ ├── commands/ ← custom commands (legacy path, still works) │ │ ├── deploy-check.md → /deploy-check │ │ ├── commit.md → /commit │ │ └── frontend/ ← namespace folder (label only) │ │ └── component.md → /component (namespace: frontend) │ └── skills/ ← skills (recommended path) │ └── security-review/ → /security-review │ ├── SKILL.md ← must be exactly SKILL.md (case-sensitive) │ └── reference/ ← supporting files loaded on demand │ └── owasp-top-10.md │ ├── CLAUDE.md ← project memory (always loaded) └── src/...

📌 Must-Memorize
$0 is the first argument (zero-based), not the command name. This is different from shell scripting where $0 is the program name. Missing indexed placeholders ($2 with only 1 arg) stay literal. Missing named placeholders expand to empty string.
💡 Pro Tip
!`command` is a single-pass substitution. The output cannot emit another !`…` for re-expansion. Use it to ground prompts in real data (e.g., !`git diff HEAD`, !`cat package.json`) — Claude receives the actual content instead of an instruction to go fetch it, saving one tool round-trip.

Common Pitfalls

  • Escaping dollar signs: If you need a literal $1.00 in your command text, write \$1.00 — otherwise it's interpreted as positional arg $1 followed by .00.
  • Name collisions: If a project skill and a commands/ file share the same name, the skill takes precedence. A project skill named like a bundled one (e.g., code-review) replaces the bundled skill.
  • Persistence: Once invoked, the rendered content stays in context for the entire session. Write instructions as standing rules ("always run tests after editing"), not one-time steps — Claude does not re-read the file on later turns.

Exam Strategy — 13.1

⚠️ Exam Trap
Questions may test whether $0 is zero-indexed or one-indexed. Remember: zero-indexed. The entire string is $ARGUMENTS; the first word is $0.

How questions are typically framed:

  • "Where should you place a Markdown file to create a custom command available to the team?" → .claude/commands/
  • "What happens if a user passes arguments but the command file contains no $ARGUMENTS placeholder?" → Arguments are appended as ARGUMENTS: <input>
  • Scenario questions about !`command` syntax and when shell expansion occurs (answer: before Claude sees the prompt)
Sample Question — 13.1
Q — Scenario
A developer creates .claude/commands/migrate.md with the content: Migrate $0 from $1 to $2. They invoke /migrate "user table" MySQL Postgres. What does Claude receive?
A) Migrate $0 from MySQL to Postgres
B) Migrate user table from MySQL to Postgres ✓
C) Migrate "user table" from MySQL to Postgres
D) Migrate user from table to MySQL
Rationale: Quoted strings are treated as a single argument. $0 = "user table" (quotes stripped), $1 = MySQL, $2 = Postgres. The quotes group the words but are not preserved in the expansion.

13.2 — Project-Scoped vs User-Scoped Commands

Concept Overview

Claude Code supports two distinct scopes for commands and skills, determined entirely by filesystem location. Project-scoped items live inside the repository's .claude/ directory and are shared with anyone who clones the repo. User-scoped items live in the home directory (~/.claude/) and follow you across every project on your machine but are never shared with teammates.

This scoping mechanism is fundamental to understanding how teams standardize workflows (project-scoped) while individuals retain personal productivity shortcuts (user-scoped). The exam tests this distinction heavily — especially the implications for version control, visibility, and precedence.

Key Definitions

  • Project-scoped — Stored in the repo at .claude/commands/ or .claude/skills/. Committed to version control. Available to all collaborators working in that repo.
  • User-scoped — Stored in ~/.claude/commands/ or ~/.claude/skills/. Local to the machine and user. Not version-controlled. Available across all projects.

Ask yourself: "Should this workflow survive across repos, or does it belong to this specific codebase?" → If it belongs to the codebase, it's project-scoped. If it follows the developer, it's user-scoped.

How It Works

  1. Discovery: On session start, Claude Code scans both .claude/ (project) and ~/.claude/ (user) for commands/ and skills/ directories.
  2. Registration: Each .md file or skill folder is registered as a slash command. The autocomplete menu merges all sources.
  3. Precedence: When a user-scoped and project-scoped command share the same name, the user-scoped command takes precedence.
  4. Namespacing: Subdirectories within commands/ create namespace labels in the menu (e.g., commands/frontend/component.md → /component with "frontend" label) but do not change the command name.
⚠️ Exam Trap — Scope Confusion
"Global" does NOT mean project-scoped. A common wrong answer conflates "available everywhere" (user-scoped, ~/) with "shared across the team" (project-scoped, .claude/). User-scoped = global for one person. Project-scoped = shared for one repo.
🔗 Cross-Reference
This scoping pattern mirrors CLAUDE.md files: project-level CLAUDE.md is in the repo root (shared), while ~/.claude/CLAUDE.md is user-level (personal). The same principle applies. See §13.5 for more on /memory and CLAUDE.md.
💡 Pro Tip
Subdirectories in commands/ are for organization only — they appear as namespace labels in autocomplete but don't change the actual command name. .claude/commands/frontend/component.md is still invoked as /component, not /frontend/component.

Common Pitfalls

  • Precedence surprise: A personal user-scoped command will silently override a team project-scoped command with the same name. If a team workflow seems broken for one developer, check for a naming collision in ~/.claude/commands/.
  • Skills vs. commands path for user-scope: For user-scoped skills, the recommended modern path is ~/.claude/skills/<name>/SKILL.md. The ~/.claude/commands/ path still works for simple single-file commands.
  • Version control assumption: Project-scoped commands in .claude/commands/ are version-controlled only if the .claude/ directory is committed to Git. Check .gitignore.

Exam Strategy — 13.2

Keywords to watch for: "team-wide," "shared," "version-controlled," "personal," "cross-project," "override," "precedence."

Elimination technique: If an answer says a project-scoped command is "available across all projects" — eliminate it. If it says user-scoped is "committed to Git" — eliminate it. These properties are mutually exclusive.

Mnemonic
P.R.O.J. — Project Repo Only, Jointly-shared
Project-scoped lives in the Repo, is shared with the team (Jointly). User-scoped lives in ~/, is personal.
Sample Question — 13.2
Q — MCQ
A developer has .claude/commands/lint.md in the project repo and ~/.claude/commands/lint.md on their machine. They type /lint. Which command executes?
A) The project-scoped command in .claude/commands/
B) The user-scoped command in ~/.claude/commands/ ✓
C) Both are merged and sent to Claude together
D) Claude Code throws a name collision error
Rationale: When both scopes define the same command name, the user-scoped command takes precedence. No error is thrown — the project-scoped version is silently overridden.

13.3 — Agent Skills with SKILL.md Frontmatter

Concept Overview

An Agent Skill is the full-featured evolution of a custom command. While a command is a single Markdown file, a skill is a directory containing a SKILL.md file (case-sensitive!) plus optional supporting files (templates, scripts, reference docs). Skills can be invoked manually via /skill-name, or Claude can load them automatically when the conversation matches the skill's description field — something commands cannot do.

Skills use YAML frontmatter to configure behavior: what tools are allowed, whether to run in an isolated subagent, who can invoke it (user, model, or both), and more. The body of SKILL.md contains the instructions Claude follows, written as Markdown. Once loaded, the skill's content persists in the conversation like standing orders — it is not re-read on subsequent turns.

Key Definitions

  • SKILL.md — The mandatory entry file for a skill. Must be named exactly SKILL.md (case-sensitive). skill.md, Skill.md, or Skills.md will be silently ignored.
  • Frontmatter — YAML metadata block between --- delimiters at the top of SKILL.md. Processed at the system level; never shown to Claude directly.
  • Auto-discovery — Claude reads all skill description fields and automatically loads a skill when the conversation matches. This is the key difference from basic commands.
  • Skill listing budget — The combined descriptions of all skills count toward a ~1,536-character cap in the skill listing Claude sees. Exceeding this means descriptions get truncated.
  • Supporting files — Additional files (reference docs, templates, scripts) stored alongside SKILL.md. Referenced from instructions and loaded on demand.

How It Works

  1. Create: Make a kebab-case directory under .claude/skills/ (project) or ~/.claude/skills/ (user). Place a SKILL.md file inside.
  2. Describe: Write a clear description in frontmatter. This is what Claude reads to decide when to auto-load the skill. Format: What it does + When to use it + Key capabilities.
  3. Configure: Set frontmatter options: allowed-tools, context, model, invocation control flags, etc.
  4. Instruct: Write the body below the closing ---. These are Claude's instructions when the skill activates.
  5. Activate: User types /skill-name, or Claude auto-discovers it based on the description matching the task context.
  6. Execute: Claude follows the instructions, using the configured tools. Content persists in conversation context.

📁 Command (Legacy)

  • Single .md file
  • Manual invoke only (/name)
  • No supporting files
  • No auto-discovery
  • Quick personal shortcuts

🧠 Skill (Modern)

  • Directory with SKILL.md
  • Manual and/or auto-discovery
  • Supporting files (reference docs, scripts)
  • Invocation control (user-only, model-only, both)
  • Subagent isolation (context: fork)
📌 Must-Memorize — Naming Rules
  • Directory name must be kebab-case: security-review ✅ / SecurityReview ❌ / security_review ❌
  • File must be named exactly SKILL.md (all caps + .md)
  • Name cannot contain "anthropic" or "claude"
  • Description cannot contain angle brackets or XML tags
  • Description has a 1,536-character cap (shared across all skills in the listing)

13.4 — Key Frontmatter Options

context: fork

Concept Overview

Setting context: fork runs the skill in an isolated subagent context — a separate conversation that does not pollute your main session's context window. This is essential for skills that perform extensive exploration, generate verbose output, or run multiple tool calls. Without forking, a skill's output stays in the main context and consumes tokens permanently.

How It Works

  1. Skill is invoked (manually or auto-discovered).
  2. Claude Code spawns a subagent — a fresh context with access to the project filesystem but no shared conversation history.
  3. The subagent executes the skill's instructions independently.
  4. By default, the subagent runs in the background (background: true) — the main session continues while the skill works.
  5. Set background: false to make the main session wait for the subagent's result before continuing.
  6. The agent field can specify the subagent type (default: general-purpose).
Ask yourself: "Will this skill generate a lot of intermediate output that I don't need in my main conversation?" → If yes, use context: fork to isolate it.
# Forked skill — runs in isolated subagent
---
description: "Deep security audit of the codebase"
context: fork           # ← isolated subagent
agent: Explore           # ← subagent type (optional)
background: false        # ← wait for result (default: true = background)
allowed-tools: Read, Grep, Glob
---

Perform a comprehensive security audit...
📌 Must-Memorize
context: fork = isolated subagent. background: true (default) = runs in background. background: false = main session waits. Forked skills cannot see the main conversation history — they start fresh with only the skill instructions and project filesystem.
⚠️ Cost Implication
Forked subagents use their own context window, which means they can consume additional tokens (some sources cite up to ~5× for complex explorations). Use forking deliberately for tasks that justify the isolation.

allowed-tools

Concept Overview

The allowed-tools frontmatter field pre-approves specific tools so Claude can use them without permission prompts during the skill's execution. This is a convenience feature that eliminates the "Do you want to allow…" dialog for tools the skill legitimately needs. Critically, this is a one-turn grant, not a session-wide setting.

How It Works

  1. When the skill is invoked, the tools listed in allowed-tools are pre-approved for that turn.
  2. The grant clears on your next message — even though the skill's instructions remain in context.
  3. allowed-tools does not restrict anything — unlisted tools remain available under your normal permission settings.
  4. Re-invoking the skill re-applies the grant for another turn.
  5. ${CLAUDE_SKILL_DIR} expands in both the body and allowed-tools, allowing skills to pre-approve their own bundled scripts.
allowed-tools: Read, Grep, Glob, Bash(git add:*), Bash(git commit:*)
# Pre-approves: Read, Grep, Glob tools + git add/commit bash commands
# This grant clears when the user sends their next message
⚠️ Exam Trap — One-Turn Grant
The most common surprise: allowed-tools is a one-turn grant, not a session setting. If Claude asks permission again for the same command later, it's because the grant expired on the next user message. The instructions persist, but the tool approval does not.

disallowed-tools (Related)

disallowed-tools does the opposite: it removes tools from Claude's available pool while the skill is active. Use it to prevent a skill from doing something dangerous — for example, blocking AskUserQuestion for a background loop skill. The restriction also clears on the next message.

argument-hint

Concept Overview

The argument-hint field provides inline terminal usage hints displayed in the autocomplete menu when typing /. It tells the user what arguments the command expects, improving discoverability and reducing invocation errors. 

argument-hint: "<issue-number> [priority]"
# Shown in autocomplete: /fix-issue <issue-number> [priority]
# Helps users know what to pass without reading the file

How It Works

  1. The hint appears next to the command name in the autocomplete dropdown.
  2. It is purely cosmetic — it doesn't enforce argument types or counts.
  3. Convention: use <required> for required args, [optional] for optional ones.
  4. Works with both commands and skills.
💡 Pro Tip
Use argument-hint even for commands with no required arguments. A hint like [optional focus area] tells users they can pass something without making it feel required.

Exam Strategy — 13.4

Mnemonic — Key Frontmatter
F.A.H. — Fork, Approve, Hint
Fork the context (context: fork), Approve the tools (allowed-tools), Hint the arguments (argument-hint).

How questions are framed:

  • "A skill grants allowed-tools: Bash(npm test:*). The user invokes it, then sends a follow-up message. Does the tool grant persist?" → No — one-turn grant, cleared on next message.
  • "A developer wants a skill to run without polluting the main context. What frontmatter option should they use?" → context: fork
  • Scenario: "Claude keeps asking for permission even though allowed-tools is set." → Because the grant is one-turn only. The user sent a new message, clearing the approval.
Sample Question — 13.4
Q — MCQ
A skill has allowed-tools: Read, Bash(npm test:*) in its frontmatter. A user invokes the skill, and Claude runs tests successfully. The user then says "now check the logs." What happens?
A) Claude runs Bash(npm test:*) again without prompting
B) Claude asks for permission before running any Bash commands ✓
C) The skill's allowed-tools persist for the full session
D) Claude cannot use Bash at all after the skill's turn
Rationale: allowed-tools is a one-turn grant. The moment the user sends their next message ("now check the logs"), the grant clears. Bash commands revert to the user's normal permission settings.

13.5 — The /memory and /compact Commands

/memory — Persistent Memory Management

Concept Overview

The /memory command opens the project's CLAUDE.md file in your default editor, allowing you to edit persistent memory that Claude Code reads at the start of every session. Changes take effect immediately in the current session. This is Claude Code's mechanism for durable project-level context: coding conventions, build commands, style rules, business logic, and recurring instructions.

Key Definitions

  • CLAUDE.md — A Markdown file at the project root that Claude Code loads automatically. Acts as persistent memory across all sessions for that project.
  • Memory hierarchy:
    • ~/. claude/CLAUDE.md — User-level (personal, cross-project)
    • ./CLAUDE.md — Project-level (shared, repo root)
    • ./.claude/CLAUDE.md — Project-level alternative location
    • ./path/to/subdir/CLAUDE.md — Directory-level (active when working in that subtree)
  • /init — A companion command that auto-generates an initial CLAUDE.md by scanning the project structure, detecting languages, package managers, and conventions.

How It Works

  1. Type /memory at the Claude Code prompt.
  2. Your default editor opens with the project's CLAUDE.md file.
  3. Edit the file: add conventions, build commands, style rules, business-specific instructions.
  4. Save and close the editor. Changes are immediately reflected in the current session.
  5. On every new session start, Claude Code automatically loads the applicable CLAUDE.md files (user → project → directory-level).
📌 Must-Memorize
/memory edits CLAUDE.md (persistent, survives sessions). /compact summarizes conversation (ephemeral, within-session). They are complementary, not alternatives. Use /init to generate the initial CLAUDE.md instead of writing from scratch.

/compact — Context Window Management

Concept Overview

The /compact command summarizes the current conversation, freeing up context window space while preserving key decisions and working state. It is Claude Code's primary tool for managing long sessions. Unlike /clear which wipes everything, /compact intelligently compresses older context into a summary — minimal information loss with substantial token savings.

How It Works

  1. Type /compact (optionally with focus instructions: /compact focus on the database migration decisions).
  2. Claude Code analyzes the conversation history, identifying key decisions, file states, and task progress.
  3. Older messages are replaced with a condensed summary. Recent context is preserved at full fidelity.
  4. CLAUDE.md content is always preserved (it's re-loaded, not part of the compactible conversation).
  5. After compaction, recently-loaded skills are re-attached within a fixed token budget. Long sessions may silently drop older skills.
  6. Claude confirms what was retained — verify that critical decisions and file states are captured.

💡 Pro Tip — Proactive Compaction
Don't wait until output quality degrades. Run /compact as routine session hygiene on any session longer than 30 minutes. By the time responses worsen, useful context may already be lost. Use /cost or /context to monitor your context usage.
⚠️ Exam Trap — Compaction Doesn't Mean Deletion
/compact does not delete context — it summarizes it. An exam answer saying "/compact deletes older messages" is wrong. It replaces them with a summary. Also: older skills may be dropped during compaction if the re-attachment budget is exceeded.
🔗 Cross-Reference
/memory edits what Claude always knows (persistent). /compact manages what Claude currently remembers (ephemeral). Skills persist in context after invocation (§13.3) but may be dropped after compaction if the token budget overflows.

Exam Strategy — 13.5

Differentiation questions: Expect questions testing whether you can distinguish between /memory (edits CLAUDE.md, persistent), /compact (summarizes conversation, ephemeral), /clear (wipes conversation, fresh start), and /init (auto-generates initial CLAUDE.md).

Mnemonic
M.I.C.C. — Memory edits, Init generates, Compact summarizes, Clear wipes
Memory = edit CLAUDE.md. Init = generate CLAUDE.md. Compact = summarize session. Clear = fresh start.
Sample Question — 13.5
Q — Scenario
A developer is 2 hours into a complex refactoring session. Response quality is starting to degrade. The CLAUDE.md file contains critical project conventions. What is the recommended action?
A) Run /clear to start fresh
B) Run /memory to add more context
C) Run /compact to summarize and free context ✓
D) Close and restart Claude Code
Rationale: /compact frees context while preserving working state and decisions. /clear would lose all session progress. /memory adds context (making the problem worse). Restarting is unnecessary.

13.6 — Hands-On: Building Custom Commands and Skills

Exercise 1: Create a Custom Slash Command

We'll build a /commit command that generates conventional commit messages for staged changes.

Step 1 — Project-Scoped Command

# File: .claude/commands/commit.md
# This creates the /commit command, available to all repo collaborators.
# Placed in .claude/commands/ → project-scoped → committed to Git.

---
description: "Write a conventional commit message for staged changes"
argument-hint: "[optional scope]"    # shown in autocomplete menu
allowed-tools: Read, Bash(git:*)      # pre-approve git commands (one-turn grant!)
---

# WHY: !`git diff --cached` runs BEFORE Claude sees this prompt.
# Claude receives the actual diff, not an instruction to fetch it.
## Staged Changes
!`git diff --cached --stat`

## Full Diff
!`git diff --cached`

## Instructions
Write a conventional commit message for the staged changes above.

- Use the format: type(scope): summary
- Keep the summary under 60 characters
- If a scope was provided via arguments, use it: $ARGUMENTS   # ← replaced with user input
- List the key changes as bullet points in the body
